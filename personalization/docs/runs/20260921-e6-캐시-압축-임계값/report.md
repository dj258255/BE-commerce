# E6. 캐시 압축 임계값 — 몇 바이트부터 압축이 이득인가 — 2026-09-21

> M6(#129)의 실측. 형식은 `03-verification.md`의 8절을 따른다.
> **가설·판정 기준은 측정 전에 썼다** — 결과를 보고 맞추지 않았다.

## 가설 (측정 전에 적는다)

E6의 명세는 이렇게 적혀 있었다:

> **가설**: 값이 작을 때는 압축이 손해고, 일정 크기 이상에서 이득이다.
> **비교군**: 무압축 / LZ4 / Snappy
> **지표**: GET p50·p95·p99, 전송 바이트, 앱 CPU, Redis 메모리
> **방법**: 값 1만 개를 크기 구간별로 넣고 GET 1만 회
> **판정**: 임계값(KB)을 정하고, **임계값 이하에서 압축이 손해라는 것도 같은 하네스로** 보인다.

여기서 **검증 가능한 형태로** 쪼갠다:

1. **압축이 실제로 저장량을 줄이는가?** → 압축률은 값의 성질에 달렸다. **줄이지 못하면 그것만으로 손해**다
   (표식 + base64 팽창 33% 를 쓰고 얻는 것이 없다)
2. **작은 값에서는 손해인가?** → 압축 결과가 원본보다 커지는 구간이 있는가. 있으면 그 지점이
   **임계값의 하한**이다
3. **대가는 CPU 인가 지연인가?** → 압축은 CPU 를 쓰고 저장량을 줄인다. **어느 쪽이 이기는지는
   크기에 달렸다** — 작으면 CPU 만 쓰고, 크면 왕복이 줄어 tail 이 내려간다
4. **코덱 중 무엇을 쓸 것인가?** → 교과서적으로 LZ4 가 빠르지만, **그 주장이 이 환경에서도 성립하는지**
   를 같은 하네스로 본다

### 사전 등록 판정 기준

- **임계값**: 저장/원본 비율이 **1을 넘는 마지막 구간**과 **1 아래로 내려가는 첫 구간** 사이에서 정한다.
  경계에 붙이지 않는다 — 교차점 근처의 이득은 몇 %라 **값의 성질이 조금만 달라져도 뒤집힌다.**
  이득이 확실한(30% 이상) 곳을 임계값으로 잡고, 그 근거를 적는다
- **임계값 이하에서 손해**: 같은 하네스에서 비율 > 1 인 구간이 **실제로 관측**되어야 한다.
  관측되지 않으면 **"이 값 모양에서는 하한이 더 아래"** 가 결과다(가설이 틀린 것이 아니라 범위가 짧은 것)
- **코덱 선택**: 저장량이 비슷하면 **CPU·지연이 낮은 쪽**을 고른다. 교과서 순서가 아니라 **실측**으로
- **경계**: 앱의 캐시 압축은 **아직 켜지 않는다**. 근거가 생겼다고 **적용할 자리가 생긴 것은 아니다**(아래)

### 재지 못하는 것 (미리 밝힌다)

- **네트워크가 없다.** Redis 가 로컬이라 "전송량"은 루프백이다. 실제 네트워크면 줄어든 바이트가
  **지연으로 돌아오므로 압축의 이득이 더 커진다** — 여기서 나온 임계값은 **상한**이다
- **값의 모양을 우리가 정했다.** 압축률은 값의 성질에 달렸다. 이 실험은 **컨텍스트 캐시(`ctx:`) 모양의
  JSON**(반복되는 키 + 짧은 값)을 쓴다 — 사진·벡터처럼 고엔트로피면 교차점이 훨씬 오른쪽으로 간다
- **앱 CPU 는 이 스레드의 CPU 시간**이라 GC·다른 스레드의 영향은 안 들어간다. 그리고 이 장비가 논다
- **값 개수를 1만이 아니라 500으로 줄였다.** 512KB × 1만이면 5GB 라 로컬 Redis 가 버티지 못한다

## 부하 모델

- **값**: `ctx:{userId}` 모양의 JSON — `seq`·`updatedAt`·`items[]`(반복 키, 항목마다 seq/itemId/유형/시각)
- **크기 구간**: 128B ~ 512KB (교차점을 찾기 위해 **작은 쪽을 촘촘히**)
- **왕복**: 같은 값 500개를 넣고(`SET`) 같은 순서로 읽는다(`GET`) — 지연은 **압축·해제 포함**
- **정리**: bench 키는 TTL 300초 + 종료 시 삭제(측정 구간 밖)

  저장량 관점에서는 "충분히 큰 값은 이미 다 줄였다"는 뜻이다

## 판정

### 1. 임계값은 **1KB** 로 정한다 (경계가 아니라 이득이 확실한 곳)

교차점은 **187~279B 사이**로 관측됐다. 그런데 **경계에 붙이지 않는다** — 그 근처의 이득은 몇 %라
값의 성질(압축률)이 조금만 달라져도 손해로 뒤집힌다. `1KB` 에서는 **66% 감소**이고 CPU 차이가
무시할 수준(+2ms/500회)이라 **이득이 값의 성질에 기대지 않는다**.

- **187B 이하**: 압축하지 않는다. 저장량이 **7% 늘어난다**(1.070) — 표식 + base64 를 쓰고 얻는 것이 없다
- **1KB 이상**: 압축한다. 500KB 에서 저장량 83% 감소 + **왕복 p99 7.5배 개선**
- 그 사이(279B~1KB): 압축해도 이득이지만 **여기서 자르는 것이 보수적**이다

### 2. 코덱은 **`SNAPPY`** 로 정한다 — 교과서 순서가 이 환경에서 뒤집혔다

저장량은 두 코덱이 사실상 같다(LZ4 가 50KB 이하에서 몇 % 낫고, SNAPPY 가 50KB 에서 0.163 vs 0.168).
그런데 **CPU 와 지연은 SNAPPY 가 낮다** — 500KB 에서 CPU **242ms vs 359ms**, get p50 **0.11ms vs 0.13ms**.

**"LZ4 가 빠르다"는 통념이 여기서는 성립하지 않았다.** 사전 등록 기준("저장량이 비슷하면 CPU·지연이
낮은 쪽")에 따라 **SNAPPY** 를 고른다. 왜 뒤집혔는지는 **확인하지 못했다** — 추정은 아래 「남은 것」에.

### 3. 압축은 **아직 켜지 않는다** — 근거는 생겼지만 적용할 자리가 없다

기본값을 `NONE` 으로 두는 이유가 바뀌었다. E5 에서는 "근거가 없어서"였는데, **여기서는 근거가
있는데 적용할 캐시가 없다**:

- 컨텍스트 캐시(`ctx:`)는 **Lua 스크립트가 값을 읽어 병합**한다(ADR-035). 압축하면 그 스크립트가
  `cjson.decode` 를 못 한다 — **E2 에서 고친 원자적 병합을 되돌리지 않고는 압축을 넣을 수 없다**
- 그 밖의 Redis 값(토큰·카운터·큐)은 전부 작아서 임계값 아래다
- **M7(홈 컴포저)의 결과 캐시가 첫 번째 적합한 자리**다 — 그 값은 **불투명**(서버가 통째로 쓰고 읽는다)이고 크다

그래서 지금은 `CacheValueCompressor` 와 임계값 설정을 **측정된 결정과 함께** 남겨 두고,
적용은 M7 에서 한다. **켤 때 쓸 값은 `codec=SNAPPY` · `compress-threshold-bytes=1024`** 다.

## 틀렸던 것

### 1. 첫 실행이 가설의 아래쪽을 시험하지 못했다 — 크기 목록이 짧았다

첫 실행은 1KB 부터 시작했는데 **1KB 에서 이미 압축이 이겼다**(0.338). 즉 "작을 때는 손해"라는
가설의 구간에 **닿지도 못했고**, 그대로 두면 *"압축은 항상 이득"* 이라는 **틀린 결론**이 나왔을 것이다.
1KB 아래를 촘촘히 넣어(128B~448B) 다시 재서 187B 에서 손해(1.070)를 찾았다.

**가설이 맞았는지 아닌지는 측정 범위가 가설의 구간을 덮었을 때만 말할 수 있다.** 이번에는
"결과가 나왔다"와 "가설을 시험했다"가 달랐다.

### 2. 값의 모양을 UUID 로 채울 뻔했다 — 그러면 압축이 언제나 손해로 나온다

처음 `payload()` 는 채움 필드를 UUID 로 만들었다(무작위). 그대로 돌렸다면 **압축률이 1을 못 넘어**
"압축은 항상 손해"라는 **정반대의 틀린 결론**이 나왔을 것이다. 압축률은 값의 성질이라
**하네스가 값을 정하는 순간 결론도 정해진다.** 실제 캐시 값의 모양(반복되는 키 + 짧은 값)으로 고쳤고,
그 한계는 위 「재지 못하는 것」에 적었다.

### 3. "LZ4 가 CPU 를 덜 쓴다"가 성립하지 않았다

교과서적으로 LZ4 는 가장 빠른 축이다. 실측은 반대였다 — 500KB 에서 **SNAPPY 가 LZ4 보다 CPU 를
1.5배 덜 썼다**(242ms vs 359ms). 원인을 확인하지 못했고, 코덱 선택은 **실측 우선**으로 뒤집었다.
(추정: snappy-java 는 네이티브를 쓰고 lz4-java `fastCompressor` 는 순수 Java 라는 차이.
**추정이므로 근거로 쓰지 않았다** — 「남은 것」에 확인 항목으로 남긴다.)

## 남은 것

- **왜 SNAPPY 가 LZ4 보다 CPU 를 덜 쓰는가** — `LZ4Factory.fastestInstance()` 가 네이티브를
  잡았는지(플랫폼·아티팩트에 따라 다르다)를 확인해야 한다. 코덱 선택을 뒤집을 수 있는 사실이다
- **실제 네트워크에서의 임계값** — 여기는 루프백이라 임계값이 **상한**이다. 원격 Redis 면
  줄어든 바이트가 지연으로 돌아와 **임계값이 더 내려간다**
- **고엔트로피 값에서의 교차점** — 이 실험은 컨텍스트 JSON 모양만 쟀다. 사진·임베딩 같은 값은
  교차점이 훨씬 오른쪽이다(압축률이 1을 못 넘을 수 있다)
- **M7 에서 실제로 켜고 다시 재기** — 홈 컴포저 결과 캐시는 **불투명하고 큰** 첫 자리다.
  켠 뒤의 p95·메모리를 다시 재고, 그때 임계값을 확정한다
- **동시 부하에서의 꼬리** — 이번엔 한 요청씩 쟀다. 압축은 CPU 를 쓰므로 **동시 요청이 몰릴 때
  압축이 큐를 만들 수 있다**(E3 에서 본 것과 같은 모양). 그 교환비는 안 쟀다

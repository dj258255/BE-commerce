# GenPage 최소형: 학습·채점·서빙 실측 (#238)

판정 기준은 [이슈 #238](https://github.com/dj258255/BE-commerce/issues/238)에 측정 전에 적었다. 결정은
[ADR-053](../../../docs/adr/ADR-053-genpage-mini-not-default.md).

## 무엇을 만들었나

| GenPage | 이번 |
|---|---|
| 이력을 토큰 시퀀스(프롬프트)로 | 구매 이력을 상품 토큰(어휘 82,759개 = train 에서 10번 이상 팔린 상품, 전체의 79.7%)으로 |
| 사전학습(다음 토큰 예측) | causal transformer 2층 · 2헤드 · 64차원, 파라미터 5.4M, 사용자 표본 40만 명 중 어휘 안 구매가 2개 이상인 361,133명, 최근 50개 |
| 후학습(가중 이진분류·강화학습) | **하지 않았다** — 노출·보상 로그가 없다 |
| 행 토큰 생성 | 학습하지 않았다. 다음 상품 분포를 대분류별로 합쳐 행을 고른다 |
| 생성 중 규칙 강제 | 이미 나온 상품·앞 쪽 상품·다른 대분류 상품을 매 단계 마스크 |
| 하이브리드 행 디코딩 | 행마다 앞 k 개만 한 칸씩, 나머지는 한 번에 |

학습·채점은 ALS(ADR-048)와 같은 하네스다 — `features_hm` 의 `split`(cutoff 2020-09-16, 홀드아웃 7일)·`map_at_k` 를 import 했다.
평가 고객 68,984명은 ALS·기준선과 같다.

## 채점

| 학습 | 바꾼 것 | 마지막 에폭 평균 손실 | MAP@12 | 이미 산 상품 제외 | 학습 시간(MPS) |
|---|---|---:|---:|---:|---:|
| 1차 | PyTorch 기본 초기화(표준편차 1), 2에폭 | 9.76 | 0.013379 | 0.001474 | 약 9분 |
| 2차 | 임베딩 초기화 표준편차 0.02 | 8.33 | 0.018519 | 0.007534 | 약 9분 |
| 3차 | 4에폭 | 7.71 | **0.020937** | 0.007758 | 약 17분 |

| 비교 | MAP@12 |
|---|---:|
| **선: 마지막 구매 재추천(측정 전에 고정)** | **0.023354** |
| GenPage 최소형(3차) | 0.020937 (선의 90%) |
| 최근 7일 인기 | 0.008748 |
| ALS 최고 구성(ADR-048) | 0.007608 |

- **선을 못 넘었다.** 3차가 선의 90% 다
- **ALS 의 2.8배다.** 같은 데이터·같은 채점기에서 순서를 보는 모델이 행렬 분해보다 훨씬 낫다
- **이미 산 상품을 빼면 63% 떨어진다**(0.020937 → 0.007758). 점수의 상당 부분이 재구매 흉내에서 온다. ALS(−46%)와 같은 모양이다
- 1차의 첫 손실이 16.8 로 균등 분포(ln 82,760 ≈ 11.3)보다 높게 시작했다. 가중치 공유 출력에 표준편차 1 짜리 임베딩을 쓰면 로짓이 너무 크다. 2차에서 고쳤다

### 왜 3차에서 멈췄나

에폭을 두 배로 늘려 +13% 를 얻었고 선까지 11.5% 가 남았다. 한 번 더 늘리면 넘을 수도 있다. 그런데 **같은 홀드아웃을 보고 세 번 골랐다.** 여기서 더 고쳐 선을 넘기면 모델이 나아졌다는 증거보다 홀드아웃에 맞춘 결과에 가깝다.
더 튜닝하려면 검증 기간(예: 홀드아웃 직전 1주)을 따로 떼고 거기서 고른 뒤 홀드아웃은 한 번만 보는 것이 먼저다.

## 검증 기간으로 다시 튜닝했다 (#242)

위 세 번의 학습은 같은 홀드아웃을 보고 골랐다. 그래서 기간을 셋으로 나누고 다시 했다.

| 구간 | 기간 | 쓰임 |
|---|---|---|
| 튜닝용 학습 | 2020-09-09 이전 | 설정마다 학습 |
| 검증 | 2020-09-09 ~ 09-15 | 설정 고르기 |
| 최종 학습 | 2020-09-16 이전 | 고른 설정으로 다시 학습 |
| 홀드아웃 | 2020-09-16 ~ 09-22 | **한 번만** 채점 |

튜닝 범위와 고르는 규칙은 이슈에 측정 전에 적었다: 차원 {64, 128} × 에폭 {2, 4, 6, 8}, 검증 MAP@12 최고, 0.0005 안이면
작은 차원 · 적은 에폭.

| 차원 | 2에폭 | 4에폭 | 6에폭 | 8에폭 |
|---:|---:|---:|---:|---:|
| 64 | 0.018583 | 0.020431 | **0.021086** | 0.021130 |
| 128 | 0.020420 | **0.021300** | 0.021279 | 0.020718 |

- 검증 최고는 차원 128 · 4에폭(0.021300). 최고에서 0.0005 안의 넷 가운데 규칙대로 **차원 64 · 6에폭**을 골랐다
- 차원 128 은 8에폭에서 내려갔다. 더 학습해도 오르지 않는다
- 검증 주의 재구매 규칙은 0.023583 이다. 검증 최고가 그 90% 다

| 참고(검증 주) | MAP@12 |
|---|---:|
| 재구매 규칙 | 0.023583 |
| 재구매 우선 + 모델 채우기(혼합) | 0.024009 ~ 0.024047 |
| 이미 산 상품 제외(모델) | 0.007214 ~ 0.007591 |

혼합은 재구매 규칙보다 약 **2%** 높다. 재구매로 못 채운 빈칸에 모델이 맞히는 몫이다. 다만 서빙 입력에 구매 이력이 없어
이 경로는 나가는 것과 같지 않다 — 채택 후보에서 뺐다.

### 홀드아웃 한 번 (고른 설정으로 2020-09-16 이전 전체를 다시 학습)

| | MAP@12 |
|---|---:|
| **GenPage 차원 64 · 6에폭** | **0.020930** (선의 89.6%) |
| 선: 재구매 규칙(스크립트가 다시 계산한 값, 이슈의 값과 같다) | 0.023354 |
| 참고: 재구매 우선 + 모델 채우기 | 0.023779 (+1.8%) |
| 이미 산 상품 제외 | 0.007533 |

- **선을 넘지 못했다.** 기본값은 켜지 않는다
- 검증 예측(0.021086)과 홀드아웃(0.020930)의 차이는 0.7% 다. 검증 주가 홀드아웃을 잘 대신했다
- #238 에서 홀드아웃을 보고 고른 값(0.020937)과 거의 같다. 그때의 선택이 홀드아웃에 맞춰 크게 부풀지는 않았다는 뜻이고,
  **"모델 단독으로는 이 데이터에서 재구매 규칙을 넘지 못한다"는 결론이 튜닝 방식과 무관하게 선다**
- 저장된 모델(`personalization/data/hm/model/genpage/model.pt`)은 이 최종 설정이다

## 서빙

2차 모델로 쟀다. 구조가 같아 3차 모델과 지연은 같다(가중치만 다르다). 모델 서버는 표준 라이브러리 HTTP 서버 + PyTorch CPU 2스레드.

### 모델 서버 직접 (합성 이력 200개, 3행 × 8개)

| 행 디코딩 | 순전파 | p95 동시성 1 | p95 동시성 4 | 규칙 위반 |
|---|---:|---:|---:|---:|
| 한 번에(k=0) | 3 | 9ms | 20ms | 0 |
| **하이브리드(k=2, 기본)** | 9 | 19ms | 29ms | 0 |
| 전부 한 칸씩(k=8) | 27 | 46ms | 64ms | 0 |
| 추천 행 `/recommend`(12개) | 1 | 3ms | — | — |

순전파 수가 곧 비용이다. 하이브리드는 행의 앞부분만 한 칸씩 사고 나머지를 한 번에 고른다 — GenPage 가 이 방식을 쓰는 이유가 순전파 수(9 대 27)로 보인다.

### 앱을 거쳐 홈 2쪽 (사용자 30명)

> **정정(#254)**: 아래 첫 표는 **모델 서버가 요청 본문을 빈 것으로 읽던 상태**에서 잰 값이다. 앱이 본문을 길이 없이(chunked) 보냈고
> 파이썬 서버는 `Content-Length` 만 읽었다. 그래서 모델은 이력·제외 목록 없이 생성했다. 고친 뒤 다시 잰 값이 두 번째 표다.
> 원자료는 [`20260924-genpage-purchases/home-rerun`](20260924-genpage-purchases/home-rerun).

**다시 잰 값(본문을 고친 뒤)**

| 2쪽 행 | p95 | 행 전략 | 쪽 사이 중복 | 대분류 불일치(DB 대조) |
|---|---:|---|---:|---:|
| 규칙(대분류 인기, 지금 기본값) | 127ms | 세션 86 · 인기 4 | 0 | 0 / 720 |
| GenPage k=0 | 80ms | GENPAGE 90 | 0 | 0 / 720 |
| GenPage k=2 | 100ms | GENPAGE 90 | 0 | 0 / 720 |
| GenPage k=8 | 121ms | GENPAGE 90 | 0 | 0 / 720 |

- 서빙 기준(p95 300ms 이하)과 규칙 위반 0 은 그대로다. k=8 의 p95 가 91 → 121ms 로 올랐다. 실제 이력을 읽고 한 칸씩 27번 생성하기 때문으로 보지만 나눠 재지는 않았다
- 항목이 685 → 720 으로 다 찼다. 예전의 빈 칸은 빈 프롬프트가 만든 상품이 품절·카탈로그 밖이라 걸러진 것으로 보인다(확인하지 않았다)

**처음 기록한 값(빈 본문 상태)**

| 2쪽 행 | p95 | 행 전략 | 쪽 사이 중복 | 대분류 불일치(DB 대조) |
|---|---:|---|---:|---:|
| 규칙(대분류 인기, 지금 기본값) | 124ms | 세션 86 · 인기 4 | 0 | 0 / 720 |
| GenPage k=0 | 86ms | GENPAGE 90 | 0 | 0 / 685 |
| GenPage k=2 | 94ms | GENPAGE 90 | 0 | 0 / 685 |
| GenPage k=8 | 91ms | GENPAGE 90 | 0 | 0 / 685 |

- **서빙 기준(p95 300ms 이하) 충족.** 모델 행이 규칙 행보다 빠르다 — 규칙 행은 신상품 채우기 조회가 붙는다
- **규칙 위반 0.** 모델이 생성 중에 지킨 것(중복·대분류)을 앱이 DB 로 다시 대조했다
- 항목 685 대 720: 모델 행은 품절과 카탈로그에 없는 상품을 생성 뒤에 걸러 행당 평균 7.6개다
- 홈 p95 는 디코딩 방식에 거의 반응하지 않았다(86~94ms). 모델 시간(9~46ms)보다 나머지 경로가 크다

## 이 측정이 말하지 않는 것

- 후학습을 하지 않았다. GenPage 가 페이지 수준 보상으로 얻는 것(행 사이 상호작용, 다양성)은 이 모델에 없다
- 행 선택은 학습한 것이 아니라 상품 분포의 합이다
- 이력이 없는 신규 고객(홀드아웃의 8.1%)은 점수를 내지 못한다. 콘텐츠 임베딩은 넣지 않았다
- 서빙의 이력은 합성이다

## 구매 이력으로 서빙하기 (#254)

모델은 구매 시퀀스로 학습했는데 서빙은 조회·클릭을 넣었다(위의 결함). 주문 모듈이 사용자별 최근 구매를 내주게 하고
(`PurchaseHistoryFacts`), 추천이 그것을 모델 입력으로 받게 했다(`app.recommendation.history-source=purchases`). 재구매 우선 혼합도
서빙 경로에 넣었다(`app.recommendation.repeat-first=true`). 판정 기준은 [이슈 #254](https://github.com/dj258255/BE-commerce/issues/254)에
측정 전에 적었다.

**방법**: 홀드아웃(2020-09-16 ~ 22) 고객 중 과거 구매에 어휘 상품이 있는 63,409명에서 5,000명(seed 7). 각자의 과거 구매 최근 100건을
실제 `orders`·`order_items` 에 결제 완료로 심고(주문 76,429 · 항목 242,464), 앱의 추천 경로(실험 엔드포인트)로 12개를 받았다.
오프라인 기준은 서빙과 **같은 모델 서버 엔진**을 프로세스 안에서 직접 부른 값이다. 차이는 앱 경로에서만 생긴다.

| 경로 | 모델 단독 | 재구매 규칙 | 혼합(재구매 우선 + 모델) |
|---|---:|---:|---:|
| 오프라인(엔진 직접, 전체 이력) | 0.023295 | 0.025775 | 0.026373 |
| 오프라인(엔진 직접, 최근 100건) | 0.023295 | 0.025775 | 0.026373 |
| 서빙(앱 경로) — **본문 결함 상태** | **0.000504** | — | 0.025823 |
| **서빙(앱 경로) — 고친 뒤** | **0.023295** | — | **0.026373** |

- **판정 기준 1(서빙 모델 단독이 오프라인의 ±5%)**: 고친 뒤 비율 1.0000. 통과
- **판정 기준 2(서빙 혼합 ≥ 재구매 규칙)**: 0.026373 대 0.025775, **+2.3%**. 통과 → **A/B 후보**로 적는다. 기본값(`stub`)은 A/B 전에 바꾸지 않는다
- **판정 기준 3(폴백 0)**: 5,000건 모두 `source=MODEL`. p95 20ms
- 이 5,000명의 값은 위 표(0.020930 등)와 직접 비교하지 않는다. 위 값은 과거 구매가 없는 고객(점수 0)까지 평균에 넣은 68,984명 기준이다

**처음 돌렸을 때 서빙 모델 단독이 0.000504 였다.** 사용자마다 추천이 똑같았다. 앱이 모델 서버로 보낸 본문이 빈 것으로 도착했다.
`RestClient` 에 Map 을 주면 길이를 모른 채 `Transfer-Encoding: chunked` 로 보내는데, 파이썬 표준 HTTP 서버 쪽 코드가
`Content-Length` 만 읽었다. #238 부터 추천 행은 **모든 사용자를 이력 없는 사용자로** 생성하고 있었고, 오류도 경고도 없었다
(본문을 직접 잡아 확인했다). 홈 다음 쪽도 같은 코드 모양으로 보냈고, 고친 뒤 항목 수가 685 → 720 으로 바뀌었다. 클라이언트는 본문을 바이트로 만들어 길이를 붙여 보내고(`ModelRequestBody`), 서버는 chunked 도 읽되 `history` 가
없는 요청을 400 으로 거절한다. 실제 HTTP 서버로 받는 테스트(`GenPageClientWireTest`)를 더했다. 옛 코드에서는 이 테스트가 실패한다.

**남은 입력 차이**: 홈 다음 쪽(`/page`)은 여전히 세션의 조회·클릭을 넣는다. 추천 행만 구매 이력으로 바꿀 수 있다.

**재현**: `PY=<genpage venv python> bash tools/run-genpage-purchases.sh`(심은 주문은 끝나면 지운다).
원자료 요약은 [`20260924-genpage-purchases`](20260924-genpage-purchases).

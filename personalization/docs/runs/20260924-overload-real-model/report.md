# 과부하 게이트를 실제 GenPage 모델 서버로 (#271)

ADR-065 의 "다시 볼 조건"(실제 모델 서버로 다시 잰다)을 돌렸다. 결론은 셋이다.

1. **추천 행에서는 모델이 병목이 아니었다.** GenPage `/recommend` 는 이 머신에서 초당 약 1,000건을 처리한다(동시성 4 p95 4.9ms). 앱이 먼저 포화한다. 앱이 버티는 부하(150 · 300/s)에서 OBSERVED 는 99% 넘게 모델로 답했다
2. **홈 다음 쪽 `/page` 는 게이트 밖에서 모델 서버를 무너뜨릴 수 있었다.** 2쪽 121/s 를 자리 없이 보내자 모델 호출이 전부 실패했고 추천 행도 같이 실패했다. `/page` 가 추천 행과 같은 동시 호출 자리를 쓰게 했다
3. **그 부하에서 먼저 무너진 것은 앱이었다.** 모델 없이 규칙 행만 만들어도 2쪽 121/s 에서 앱이 무너졌다. 이 머신에서 2쪽 앱 경로는 초당 30~60건 사이에서 포화한다

판정 기준과 두 번의 설계 수정은 [이슈 #271](https://github.com/dj258255/BE-commerce/issues/271) 본문과 댓글에 **측정 전에** 적었다. 결정은 [ADR-067](../../../../docs/adr/ADR-067-genpage-page-shares-capacity.md).

## 환경

- Apple M2 Pro 한 대에 앱 · 모델 서버(`genpage_server.py`, torch CPU 2스레드) · k6 · MySQL · Redis 가 같이 돈다
- 추천 행: k6 열린 루프 40초(워밍업 10초 제외), 계정 8개, 활동은 모델 어휘 안 · 재고 있는 상품 400개에서 심는다. ADMISSION 예산 100ms, 앱의 모델 동시성 4
- 홈 2쪽: 계정 8개가 1쪽에서 받은 커서로 2쪽을 반복 요청한다(열린 루프). 모든 행이 GENPAGE 면 모델이 만든 쪽
- **dropped 가 0 이 아닌 실행은 무효**다. k6 가 도착률을 못 채웠으니 그 부하에서 나온 값이 아니다

## 0. 모델 서버 용량 (직접, 닫힌 루프 20초)

| 경로 | 동시성 1 | 2 | 4 | 8 |
|---|---:|---:|---:|---:|
| `/recommend` 처리량 | 457/s | 719/s | **999/s** | 867/s |
| `/recommend` p95 | 2.6ms | 3.3ms | **4.9ms** | 12.6ms |
| `/page` 처리량 | 37/s | 72/s | **121/s** | 97/s |
| `/page` p95 | 31.6ms | 34.6ms | 41.7ms | 92.7ms |

C = 999/s, Lm = 4.9ms, Cp = 121/s. 추천 행 p95 기준 (100 + Lm) × 1.2 = 126ms.

## A. 추천 행만

처음 설계(2C · 4C = 1,997 · 3,995/s)는 앱이 835 · 1,056/s 만 받아 dropped 가 수만 건이었다. 두 실행을 무효로 두고 앱이 버티는 부하로 바꿨다(이슈 첫 댓글).

| 추정 | 부하 | coverage | serving p95 | dropped | |
|---|---:|---:|---:|---:|---|
| CONFIGURED | 300 | 97.3% | 24ms | 0 | |
| CONFIGURED | 600 | 18.2% | 289ms | 718 | 무효 |
| OBSERVED | 300 | 65.5% | 433ms | 773 | 무효. 다시 재니 재현되지 않았다 |
| OBSERVED | 600 | 91.4% | 126ms | 0 | coverage 기준(95%) 미달 |
| OBSERVED | 150 | **99.1%** | 13ms | 0 | 통과 |
| OBSERVED | 300(다시) | **99.8%** | 7ms | 0 | 통과 |

- 앱이 버티는 부하에서 OBSERVED 는 기준을 넘었다
- 600/s 에서 OBSERVED 가 9% 를 거절한 것은 모델이 실제로 느려졌기 때문이다. 앱을 거친 모델 p95 가 82ms 였다(직접 잰 4.9ms 의 17배). 같은 머신에서 앱과 k6 가 CPU 를 나눠 쓰니 모델의 실제 용량은 직접 잰 C 보다 작다. 기준(95%)은 C 를 믿고 정한 것이라 못 넘었다
- CONFIGURED 는 설정의 스텁 값(4동시 · 50ms = 80/s)을 믿는다. 무효로 둔 실행이지만 방향은 적어 둔다. 2C · 4C 에서 모델 p95 5~6ms 인데 요청의 88% 를 거절했고, 600/s 에서는 82% 를 거절했다. #264 와 반대 방향의 오판이다(모델이 실제보다 느리다고 믿는다)

## B. 홈 2쪽과 함께

| 조건 | 추천 행 coverage | 추천 행 p95 | 추천 행 모델 실패 | 2쪽 모델 행 | 2쪽 p95 | dropped(추천 · 2쪽) |
|---|---:|---:|---:|---:|---:|---:|
| 자리 없음 · 2쪽 121/s | 0.0% | 2,433ms | 214 | 0.0% | 15,215ms | 9,920 · 4,210 |
| 자리 공유 · 2쪽 121/s | 10.3% | 514ms | 0 | 60.7% | 2,454ms | 4,849 · 2,465 |
| 자리 공유 · 2쪽 243/s | 11.4% | 453ms | 0 | 58.0% | 1,993ms | 3,808 · 6,975 |
| **대조**: 모델 없음 · 2쪽 121/s | — | 729ms | — | — | 3,398ms | 6,974 · 3,238 |

(추천 행 300/s, OBSERVED. 자리 없음 243/s 는 앱이 뜨지 않아 재지 못했다)

- 자리 없이 보내면 모델 서버가 앱이 300ms 에 포기한 요청까지 끝까지 계산했다(`BrokenPipeError` 70건). 파이썬 스레드 서버는 요청마다 스레드를 만들어 줄에 상한이 없다. 버려진 계산이 CPU 를 먹어 `/recommend` 까지 실패했다
- 자리를 공유하면 모델 실패는 0 이 됐다. 그래도 앱이 버티지 못했다
- **대조에서도 무너졌다.** 이 부하는 모델과 관계없이 앱이 먼저 못 받는다. 그래서 이 표로는 자리 공유의 효과를 판정하지 않았다(이슈 두 번째 댓글)

## C. 앱이 버티는 2쪽 부하에서

| 조건 | 2쪽 모델 행 | 2쪽 p95 | 추천 행 p95 | dropped |
|---|---:|---:|---:|---:|
| 모델 없음 · 2쪽 30/s(규칙 행) | — | 164.7ms | — | 0 |
| 모델 없음 · 2쪽 60/s(규칙 행) | — | 3,671.7ms | — | 721 |
| 자리 없음 · 2쪽 30/s · 추천 행 150/s | 100.0% | 91.0ms | 11ms | 0 |
| 자리 공유 · 2쪽 30/s · 추천 행 150/s | 99.9% | **79.6ms** | **10ms** | 0 |

- 2쪽 앱 용량 P = 30/s(60/s 에서 무너졌다)
- 자리 공유의 비용: 자리 없음 폴백(busy) ≤ 0.1%, 2쪽 p95 0.87배, 추천 행 p95 0.91배. 이슈 세 번째 댓글의 기준(busy ≤ 1%, 1.1배 이내)을 넘어 **자리 공유를 기본으로 둔다**
- **규칙 행이 GenPage 행보다 비싸다.** 30/s 에서 규칙 행 p95 164.7ms, GenPage 행 91.0ms. 규칙 행은 인기 표에 모자란 대분류를 신상품 조회로 채운다. 폴백이 주 경로보다 비싸면 과부하 때 폴백이 부하를 더한다. 자리 공유의 busy 폴백도 이 비싼 길로 간다

## 한계

- 모든 것이 한 머신에서 돈다. 모델 서버를 따로 두면 C 와 Cp 가 그대로 앱에 보인다
- 각 조건 한 번. OBSERVED 300/s 는 한 번 무효, 한 번 통과였다
- 2쪽 부하는 계정 8개가 같은 커서를 반복한다. 실제 사용자의 2쪽은 커서가 모두 다르다
- 2쪽 앱 경로가 왜 30~60/s 에서 포화하는지는 보지 않았다(자리 없음 121/s 로그에 커넥션 풀 대기 초과가 있었다). 트러블슈팅 기록 열린 항목으로 남겼다

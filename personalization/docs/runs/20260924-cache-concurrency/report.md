# 캐시 압축을 동시 요청 아래서 (#266)

ADR-041 의 두 결정(임계값 1KB · 코덱 SNAPPY)은 32 스레드까지 섰다. 1KB 를 압축해도 한 번의 넣고 읽기 p95 는 NONE 의 1.06배였고, 연산당 CPU 는
여섯 칸 중 다섯에서 SNAPPY 가 낮고 한 칸은 같았다. 그리고 동시성이 오르자 압축의 이득이 **오히려 커졌다.** 판정 기준은
[이슈 #266](https://github.com/dj258255/BE-commerce/issues/266)에 **측정 전에** 적었다.

E6(ADR-041)은 한 스레드로 쟀다. 압축은 CPU 를 쓰는 일이라, 요청이 동시에 몰리면 압축끼리 CPU 를 다툰다.

## 방법

- `CacheBenchmark` 를 N 개 스레드에서 동시에 돌린다(`/api/v1/experiments/cache/bench?threads=`). 스레드마다 200개를 넣고 같은 순서로 읽는다.
  실제 Redis, 앱과 같은 `StringRedisTemplate`(공유 연결), 값은 E6 와 같은 컨텍스트 JSON 모양
- 크기 1KB · 50KB · 500KB × 코덱 NONE · LZ4 · SNAPPY × 스레드 1 · 8 · 32. 코덱은 기동 설정이라 코덱마다 앱을 다시 띄운다(임계값 0 = 늘 압축)
- **넣고 읽기** = 압축 + set + get + 해제 한 번의 시간. 연산당 CPU = 스레드별 CPU 시간의 합 ÷ 연산 수

### 판정

1. **임계값 1KB 유지.** 32 스레드에서 1KB 의 SNAPPY 넣고 읽기 p95 1.57ms, NONE 1.48ms — 1.06배(기준 1.2배 이하). 다만 p99 는 3.32 대 1.84ms 로 벌어졌다
2. **SNAPPY 유지 — 한 칸은 동점.** 8 · 32 스레드 여섯 칸 중 다섯에서 SNAPPY 의 연산당 CPU 가 낮다. 1KB · 32 스레드는 64.647 대 64.649µs 로 같다.
   기준 문장은 "SNAPPY < LZ4 면 유지, 뒤집히면 다시 고른다"였고 동점을 다루지 않았다. 뒤집힌 칸이 없어 유지한다
3. **500KB 꼬리 이득은 동시성에서 더 크다.** 32 스레드 get p99 40.21 → 8.42ms(4.8배)

### 예상과 달랐던 것

**동시성이 오를수록 압축의 이득이 커졌다.** 50KB · 32 스레드에서 NONE 5.89ms 대 SNAPPY 2.24ms, 1KB · 8 스레드에서도 압축 쪽이 빨랐다(0.49 · 0.60 대 0.68ms).
앱이 Redis 연결 하나를 나눠 쓰니, 동시 요청이 많을수록 바이트 수가 줄을 세운다. 압축이 CPU 를 더 쓰는 대신 그 줄을 줄였다.
ADR-041 이 "Redis 가 로컬이라 임계값은 상한이다"라고 적은 것과 같은 방향의 효과가, 로컬에서도 동시성으로 나타났다.

LZ4 는 500KB 한 스레드에서 p99 8.54ms 로 튀었다. 한 번씩만 쟀다.

## 한계

- 각 조건 한 번. 스레드 32 는 이 머신(Apple M2 Pro)의 코어 수를 넘는다
- 공유 연결 하나다. 연결 풀을 쓰는 구성에서는 바이트 줄 서기 효과가 다를 수 있다
- 압축은 여전히 켜져 있지 않다(적용할 캐시가 없다 — ADR-041)

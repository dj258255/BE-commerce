# S2 — 결합 방식을 앱 홈 2쪽에 기능 플래그로 붙였다: 앱 = 서버, 지금 방식보다 빠르고, 대체 경로가 모두 동작했다 (#455)

**앱에 실험군으로 붙일 준비가 됐다.** 순위 모델 점수 + GenPage 줄 구성(결합 방식)을 앱 홈 2쪽에 기능 플래그 `app.recommendation.genpage-compose` 로 붙였다.

- 매핑 계정 200개 전원의 앱 2쪽이 같은 요청을 모델 서버에 직접 보낸 응답과 같았다
- 실제로 나갈 앱 설정(모델 타임아웃 300 ms · 자리 공유)에서 결합 방식의 2쪽 p95 는 119 ms 로 지금 방식(125 ms)보다 빨랐고, 규칙 행으로 물러선 요청은 0 이었다
- 매핑 없음 · 점수 없음 · 모델 서버 정지 세 경우 모두 계정 20개 전부 응답 200 · 오류 0 이었다
- 플래그 `OFF` 의 앱은 main 과 같은 2쪽을 냈다(20/20)

측정 전에 정한 판정 1 · 2 를 모두 충족했다. 기본값은 `OFF` 그대로다(ADR-068, S1 의 가상 A/B 가 이겼다고 할 수 없었다).

## 구조

- 앱: `OFF`(기본) · `RULE` · `HYBRID`. `OFF` 가 아니면 `personalization` 모듈이 매핑 표(V66 `personalization_user_map`)에서 회원의 H&M 고객 키를 내주고, 홈 2쪽 GenPage 요청에 `compose` · `customer` 를 더한다. 매핑이 없으면 지금 본문 그대로 보낸다
- 모델 서버: `customer` 가 이력 저장소에 있으면 요청의 이력 대신 그 고객의 H&M 이력(서버 요청 시각 전 최근 100건 구매)으로 프롬프트와 다시 사기 행을 만든다. 피처 저장소를 고객 키로 읽는 구조다
- 지표: `recommendation.genpage.compose{composition, fallback}`. 실제로 쓴 방식과 대체 이유(`no_mapping` · `no_scores`)를 센다

## 구현 · 측정 중 찾은 것

1. **서버의 결합 방식이 요청 행 수를 무시했다.** S1 의 `rule` · `hybrid` 는 항상 6행을 만들었다. 앱 2쪽은 3행을 요청하므로 결합 방식만 행이 두 배가 되고 지연 비교도 어긋났다. 요청의 `rows` · `items_per_row` 를 따르게 고쳤다(요청에 없으면 6 · 8 이라 S1 결과는 그대로다). S1 은 6행으로만 쟀기 때문에 실제 호출자를 붙인 뒤에야 드러났다
2. **앱이 짧은 행을 버린다.** 결합 방식은 다시 사기 행이 짧은 경우가 많다(D4 검증에서 이력 상품 수 중앙값 4). 앱은 3개 미만 행을 버려서 HYBRID 2쪽은 페이지당 2.57행이었다(OFF 3.00). 오프라인 D5 에서 이기게 한 짧은 다시 사기 행 일부가 화면에서는 빠진다. 앱에서 결합 방식의 효과를 다시 잰다면 이 규칙을 먼저 정해야 한다
3. **측정 도구가 앱 설정을 바꿨다.** 처음 실행기는 앱 타임아웃을 3 s 로, 자리 제한을 끄고 있었다. 실제로 나갈 설정으로 재지 않으면 타임아웃 대체가 측정에서 가려진다. M2 · M3 · M4 를 앱 기본 설정으로 바꾸고, 대조가 목적인 M1 만 긴 타임아웃을 쓰고 적었다
4. **미리 계산한 페이지는 앱 2쪽에 쓸 수 없다.** 2쪽 요청에는 항상 1쪽 상품 `exclude` 가 붙는다. 앱 플래그에서 `HYBRID_CACHED` 를 뺐다

# C5 — 종합몰식 구성: 재구매는 규칙, 새 상품은 모델 (#382)

**재구매 행 안의 순서만 규칙(최근 산 순서)으로 바꾸자 MAP@12 가 0.01865 에서 0.02325 로 올라 선(0.02346)의 99.1% 가 됐다. 선은 넘지 못했다.** 비슷한 상품 후보를 더한 M2 는 0.02330 으로 선에 0.00016 모자랐다. M1 과의 차이가 0.001 안이라 규칙대로 단순한 M1 을 고르고 홀드아웃은 보지 않는다. 대신 모델이 규칙 위에 더하는 것은 숫자로 나왔다. 전에 안 산 새 상품 적중이 M2 에서 0.0356 인데, 재구매 규칙은 구조상 0 이다. 페이지 적중은 규칙의 1.78배다.

## 판정

1. **선을 넘은 변형은 없다.** 가장 높은 M2(0.02330)와 M1(0.02325)의 차이가 0.001 안이라 규칙대로 단순한 **M1 을 고른다.** 선을 못 넘어 홀드아웃은 보지 않는다
2. **앞자리를 규칙에 맡기자 선의 79% 에서 99% 로 올랐다.** v2 가 선에 진 것은 다시 사기 행 **안의 순서**였다(STATUS "선 넘기기 — base"). 최근 산 순서가 모델의 순서보다 정확하다
3. **모델이 규칙 위에 더하는 것은 새 상품이다.** M2 의 새 상품 적중은 0.0356 으로 M0 보다 16% 높다. 비슷한 상품 후보(의미 임베딩)가 효과를 냈다. 재구매 규칙은 구조상 0 이다. 페이지 전체 적중은 규칙의 1.78배다. 재구매 적중만은 규칙(0.0724)이 여전히 높다
4. **재구매 성향 배치(M3)는 해로웠다.** 게이트가 사용자의 29% 에서 다시 사기 행을 셋째 행으로 미뤘고 MAP@12 가 0.0017 떨어졌다. "이력 안에 같은 상품을 두 번 산 기록"은 재구매를 가르는 신호로 약했다. 같은 날 수량이 여러 줄로 찍힌 기록도 섞여 있어, 게이트가 71% 를 "재구매 있음"으로 봤다
5. **비용.** 후보를 쓰는 M2 는 페이지 생성이 331 → 521 ms 로 1.6배다. X4 의 300 ms 예산 안에 들려면 서빙에서는 후보 계산을 캐시하거나 미리 해 둬야 한다(재지 않았다)

## 측정 중에 고친 것

- **배치 디코딩 캐시 결함 셋.** 사용자마다 고정 목록 길이가 다르면 캐시에 패딩이 섞이거나 크기가 맞지 않아 멈췄다. 실제 모델 테스트로 재현한 뒤 고쳤다
  - 같은 길이끼리 묶어 붙이기
  - 고정 뒤 남은 칸으로 모델 접두 계산
  - bulk 토큰 이중 입력 제거
- **후보 제한이 극단적으로 느렸다.** 첫 M2 는 조각 둘이 3시간 13분 동안 끝나지 않아 멈췄다
  - 측정: 100명 평가가 후보 없이 39초, 후보를 켜면 30분이 넘었다
  - 원인: 후보 제한이 행마다 상품 수천 개를 파이썬 반복문으로 확인하고 있었다(`decode.py` `_items_for_row`). 이 경로는 #320 에서 들어왔다
  - 수정: 예제마다 한 번 만든 불리언 마스크로 바꿨다. 100명이 45초가 됐고 결과는 같았다(고정 출력 테스트)
- **평가 조각 하나가 약 7 ~ 10GB 를 쓴다.** 그래서 2개씩 돌렸다(WBC 세 번째 실행에서 확인)

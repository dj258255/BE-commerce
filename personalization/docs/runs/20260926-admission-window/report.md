# 용량이 자주 바뀔 때 과부하 게이트의 관측 창 길이 (#339)

[ADR-065](../../../../docs/adr/ADR-065-admission-by-observed-throughput.md)는 게이트가 **최근 2초**에 끝난 모델 호출 수로 대기를 추정하게 했고
"용량이 갑자기 바뀌면 2초 동안은 옛 처리량으로 판단한다. 재지 않았다"고 적었다. 모델 용량을 10초마다 두 배 ↔ 절반으로 바꾸며
창 0.5 · 2 · 8초를 쟀다. 예측과 판정 기준은 [이슈 #339](https://github.com/dj258255/BE-commerce/issues/339)에 **측정 전에** 적었다.

- **2초가 가장 좋았다.** 용량이 바뀌는 조건에서 serving p95 가 0.5초 309ms · **2초 190ms** · 8초 226ms. 기본값을 그대로 둔다
- **0.5초는 표본이 모자라 설정값 추정으로 떨어졌다.** 설정값만 쓴 대조(302ms)와 같은 크기다. 낮은 용량(초당 40건)에서 0.5초 창에는 20건 남짓이 들고,
  지금 칸이 반쯤 찬 채로 세어져 표본 기준(20)에 못 미친다
- 8초는 두 용량을 섞어 봐서 낮은 용량 구간에 줄을 더 받았다. 예측대로 2초보다 나빴다
- 용량이 고정이면 창 길이는 거의 상관없었다(p95 141 · 152 · 154ms, coverage 63.2 · 60.4 · 60.2%)

## 환경

`tools/run-inference-overload.sh` 를 그대로 썼다. 모델 스텁 4동시, 지연이 **10초마다 50ms(80/s) ↔ 100ms(40/s)** 로 바뀐다
(`app.recommendation.model.stub-latency-alt-ms=100`, `stub-latency-period-ms=10000`). 게이트는 50ms 로 믿는다.
ADMISSION · 예산 100ms · 부하 120/s · 60초(전환 6번). 창은 `app.recommendation.admission-window-ms`. 일회용 MySQL(카탈로그 복사본) · Redis.

## 결과

| 조건 | 창 | 추정 | serving p95 | p99 | coverage | 거절 |
|---|---:|---|---:|---:|---:|---:|
| 용량 전환 | 0.5초 | 관측 | **309ms** | 316ms | 47.9% | 3,128 |
| 용량 전환 | **2초** | 관측 | **190ms** | 266ms | 46.0% | 3,240 |
| 용량 전환 | 8초 | 관측 | 226ms | 283ms | 46.5% | 3,208 |
| 용량 전환 | — | 설정값(대조) | 302ms | 306ms | 50.5% | 2,972 |
| 고정 50ms | 0.5초 | 관측 | 141ms | 147ms | 63.2% | 2,209 |
| 고정 50ms | 2초 | 관측 | 152ms | 157ms | 60.4% | 2,377 |
| 고정 50ms | 8초 | 관측 | 154ms | 160ms | 60.2% | 2,390 |

## 예측과 비교

- 예측: 전환 조건의 p95 는 8초 > 2초 > 0.5초. 단 0.5초는 표본이 모자라 설정값으로 떨어지면 2초보다 나빠질 수 있다
- 실제: **8초 > 2초 는 맞았고, 0.5초는 단서대로 나빠졌다.** 0.5초의 p95(309ms)와 coverage(47.9%)는 설정값 대조(302ms · 50.5%)와 같은 자리에 있다
- 고정 조건에서 0.5초의 coverage 가 2초보다 높았다(63.2 대 60.4%). 측정 전 보탬 댓글은 "칸 경계 때문에 처리량을 적게 봐서 더 거절할 것"이라고 봤는데 반대로 나왔다. 차이는 ±10% 안이라 판정에는 영향이 없고, 원인은 재지 않았다

## 판정

1. 전환 조건에서 p95 가 가장 낮은 창은 2초다. 고정 조건 ±10% 도 통과
2. 기본값 2초를 유지한다. ADR-065 대가 절의 "재지 않았다"를 이 결과로 바꾼다
3. 0.5초는 표본 부족으로 나빠졌다. 표본 기준(20)은 이번에 바꾸지 않는다. 창을 줄이려면 표본 기준을 같이 낮춰야 하고, 그러면 추정이 흔들린다

## 이 표가 말하지 않는 것

- 전환 주기는 10초 하나다. 주기가 창보다 훨씬 길면(실제 오토스케일은 분 단위) 창 길이의 영향은 더 작다. 이 실험은 창이 주기에 가까울 때를 본다
- 한 번씩만 쟀다. 스텁 모델이라 지연 꼬리가 없다

## 재현

```bash
./gradlew -p commerce bootJar
APP_RECOMMENDATION_MODEL_STUB_LATENCY_ALT_MS=100 APP_RECOMMENDATION_MODEL_STUB_LATENCY_PERIOD_MS=10000 \
APP_RECOMMENDATION_ADMISSION_WINDOW_MS=2000 ADMISSION_ESTIMATE=OBSERVED POLICIES=ADMISSION ADMISSION_BUDGET_MS=100 \
MODEL_LATENCY_MS=50 RATES=120 DURATION=60s bash tools/run-inference-overload.sh
```

원자료: [`raw/`](raw/) (실행마다 k6 출력 · 요약 · 같은 맥의 CPU, 일회용 DB 로 돌린 러너 `run.sh`)

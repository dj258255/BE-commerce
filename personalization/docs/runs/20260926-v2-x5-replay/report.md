# X5 — 문맥 저장소의 행동이 모델 입력까지 가는가 (#328)

지금 설정(`OFF`)에서는 20명 중 한 명도 저장소가 가진 사실 그대로 모델에 가지 않았다. 세 가지가 동시에 틀린다.
- 조회 · 클릭이 요청일의 온라인 구매로 읽힌다
- 12건 중 오래된 4건이 빠진다
- 요일 · 월 토큰이 2020년 학습 기준일로 들어간다

행동 종류 · 시각을 따로 넘기는 `RICH` 는 교란이 저장소에서 흡수되는 조건(기준 · 무질서 · 중복 · 창 · 짧은 지연, 전송 둘 다)에서 **20명 전원이 토큰 하나까지 같다**. `RICH` 로도 못 막는 것은 저장소 자체가 아직 모르거나(Kafka 지연) 이미 잊은(TTL) 경우뿐이고, 이는 E2 가 저장소 단계에서 잰 것과 같은 원인이다.

- 측정: 2026-09-26 05:53 ~ 06:10. v2 모델 서버(`f-base-full-1ep`, final, CPU)와 앱 bootJar. 조건마다 사용자 20명 · 12건(창 조건은 8명이 30건)
- 방법 · 지표 · 판정: `personalization/docs/genpage-v2/BACKEND.md` X5 절. 측정 전에 적었고, 코드를 읽은 뒤 좁힌 범위도 측정 전에 적었다
- 재현:
  ```
  PY=<genpage 가상환경>/bin/python GENPAGE_DATA=<데이터> bash tools/run-x5-replay.sh
  ```
  대조만 다시 하려면 `prompts.jsonl.gz` 를 풀고 `tools/x5_prompt_replay.py --skip-drive` 를 쓴다
- 원자료: `raw/<OFF|RICH>/<조건>/`
  - `manifest.json`: 주입한 것
  - `drive.json`: 2쪽 호출 구간
  - `replay.json`: 사용자별 기대 · 온라인 사건과 플래그
- 프롬프트 로그: `prompts.jsonl.gz`. 서버가 해석한 사건과 토큰을 요청마다 한 줄씩 남긴 것이고, 1쪽 추천 행 요청도 섞여 있다

## 판정

1. **`RICH` 는 사전 판정(기준 조건에서 완전 일치)을 통과했다.** IN_PROCESS · KAFKA 모두 20/20 이다. 저장소가 이미 흡수하는 교란(무질서 · 중복 · 창 · 짧은 지연)도 모델 입력까지 그대로 흡수된다. 앱과 서버 사이에서 새로 생기는 유실은 없다
2. **`OFF` 는 모든 조건에서 뜻을 바꾼다.** 저장소가 행동을 가진 사용자(TTL · Kafka 지연으로 비지 않은 사용자) 전원에서 조회 · 클릭이 "요청일의 온라인 구매"가 됐다. 이것은 교란 때문이 아니라 **기본 경로의 결과**다. 기본 설정(`history-source: activity`)이 세션 id 를 `history` 로 넘기고, v2 서버가 `history` 를 구매로 해석한다
3. **`OFF` 에는 설계 문서에 없던 유실이 하나 더 있다.** 홈 모듈은 자기 규칙 행을 위해 최근 8건만 읽는다(`app.home.context-limit: 8`). 그 8건이 그대로 모델 입력이 된다. 저장소와 추천 모듈은 20건을 기준으로 둔다. 두 모듈이 창 크기를 따로 정해 한쪽의 화면 설정이 다른 쪽 모델 입력을 줄였다. 창 조건(30건)에서 토큰 불일치가 0.533 으로 기준(0.433)보다 큰 것이 이 차이다
4. **`OFF` 는 요청 시각도 잃는다.** 앱이 `now` 를 보내지 않아 서버가 학습 기준일(2020-09)의 요일 · 월을 쓴다. 20명 전원이 틀렸다
5. **`RICH` 로도 못 막는 것은 저장소 단계의 원인이다.** TTL 이 지나 비었거나(0/20), Kafka 소비가 밀려 아직 반영되지 않았다(3/20). 두 결과는 E2 의 TTL 0% · late 와 같은 원인이고, 모델 경계에서 새로 생긴 것이 아니다. 그래서 E2 의 결론(추천 경로는 기다리지 않는다, `waitMs=0`)을 바꿀 근거가 되지 않는다
6. **대가는 요청 본문이다.** 12건 기준 251 B 가 1,064 B 가 된다(4.2배). 앱 쪽 추가 읽기는 저장소를 한 번 더 읽는 것이다. 홈이 이미 읽은 목록은 id 만 남은 것이라 재사용할 수 없다. 응답 시간 차이는 위의 흔들림 안이라 판정하지 않았다

## 결정

- **기본값은 `OFF` 로 둔다.** v2 는 기본 모델이 아니고(ADR-068), v1 서버는 `session` · `now` 를 쓰지 않는다
- **v2 를 켤 때는 `RICH` 를 같이 켠다.** `OFF` 로 v2 를 켜면 모든 사용자의 조회가 구매로 들어간다. ADR-068 의 X1 조건(구매 시각 · 가격 · 프로필 공급)에 세션 모양을 더한다

## 스모크에서 고친 것 (측정 전)

- 대조 도구 첫 버전은 상품 목록이 같을 때만 행동을 비교했다. 스모크(3명)에서 OFF 가 8건만 보내 "빠짐"으로만 세어졌고, "뜻 바뀜"이 0 으로 나왔다. 양쪽에 다 있는 사건끼리 비교하도록 고치고 테스트(`test_meaning_is_counted_even_when_items_are_missing`)를 더한 뒤 전체 측정을 돌렸다
- 18080 포트를 다른 세션의 앱이 쓰고 있었다. E2 러너는 포트가 안 비면 그 프로세스를 `kill -9` 한다. 이 러너는 포트를 18090 으로 두고, 안 비면 멈추게 바꿨다

## 한계

1. **시각 구간은 사실상 재지 못했다.** 발생 시각은 서버가 적재 시각으로 정하므로 주입으로 과거 행동을 만들 수 없다. 구간 계산은 단위 테스트(`test_session_time_bucket_comes_from_at_and_zoned_instants_meet_naive_now`)로만 확인했다. 실사용에서는 TTL 7일 안의 행동이 `AGO_4-7` 까지 갈 수 있다
2. 주입 사용자는 구매가 없다. 구매 경로(`history`)는 X1 이 쟀다
3. 주입 상품은 어휘에 없어 상품 토큰이 전부 `ITEM_FALLBACK` 이다. 그래서 상품 일치는 토큰이 아니라 서버가 해석한 사건의 상품 id 로 대조했다
4. 날짜 경계는 UTC 다. 기대 쪽과 서버가 같은 함수를 쓰므로 둘 사이에서는 어긋나지 않는다. 다만 사람이 느끼는 "오늘"(KST)과는 9시간 어긋날 수 있다
5. 사용자별 프롬프트 줄은 호출 구간으로 가렸다. 요청 모양을 바꾸지 않는 대신 사용자를 한 명씩 차례로 불렀다. 동시 부하에서의 대조는 하지 않았다
6. 학습 데이터에 조회 · 클릭이 없으므로(PLAN "똑같이 할 수 없는 것" 3), `RICH` 가 추천 품질을 바꾸는지는 이 실험의 질문이 아니고 재지 않았다

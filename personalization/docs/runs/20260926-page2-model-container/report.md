# GenPage 모델 서버를 CPU 제한 컨테이너로 떼어 놓고 2쪽 자리 없음 대 공유 (#342)

[ADR-067](../../../../docs/adr/ADR-067-genpage-page-shares-capacity.md)의 다시 볼 조건: "모델 서버를 앱과 다른 머신에 두면 2쪽 부하를 모델이 포화하는 데까지
올려 자리 없음 대 공유를 다시 잰다." [#284](../20260925-page2-capacity/report.md)는 앱 · MySQL · k6 · 모델이 한 맥의 CPU 를 나눠 써서, 자리 없음(none)이
무너진 이유가 모델 포화인지 CPU 경합인지 가르지 못했다. 예측과 판정 기준은 [이슈 #342](https://github.com/dj258255/BE-commerce/issues/342)에 **측정 전에** 적었다.

- **모델을 떼어 놓아도 none 은 두 부하 모두 무너졌다**(추천 행 coverage 0% · p95 약 700ms). #284 의 무너짐은 모델 포화 때문이었다
- **shared 는 추천 행 모델 실패를 0 으로 지켰다.** 다만 p95 가 182 · 230ms 로 측정 전에 둔 선(126ms)을 넘었다
- 모델이 느리면 shared 에서 **2쪽은 거의 모델을 쓰지 못한다**(모델 행 0.7% · 0.0%). #284 의 40~60% 와 다르다

## 환경

- GenPage v1 모델 서버를 도커 컨테이너(`--cpus=2`, `GENPAGE_THREADS=2`)로 띄웠다(`personalization/serving/Dockerfile.cpu`). 코드는 저장소, 모델 · 데이터는 읽기 전용으로 붙였다. 앱 · k6 는 맥에서 돈다
- 컨테이너 모델의 용량을 먼저 쟀다(`tools/genpage_capacity.py`, 20초씩): **추천 행 C 82.5/s · 2쪽 Cp 8.9/s**. 맥 원생(추천 행 약 1,000/s)보다 한참 작다
- 그래서 측정 전에 설계를 비율로 옮겼다([이슈 댓글](https://github.com/dj258255/BE-commerce/issues/342#issuecomment-5841202273)): 추천 행 40/s(0.5C) · 2쪽 9 · 18/s(1Cp · 2Cp). #284 는 추천 행이 C 의 15% 였다
- ADMISSION · OBSERVED · 60초 · 조건마다 모델 컨테이너를 새로 띄웠다. 일회용 MySQL(카탈로그 복사본) · Redis

## 결과

| 2쪽 부하 | page-capacity | 추천 행 coverage | 추천 행 p95 | 추천 행 모델 실패(+대기 초과) | 2쪽 모델 행 | 2쪽 p95 |
|---:|---|---:|---:|---:|---:|---:|
| 9/s(1Cp) | none | **0.0%** | 698ms | 395(+204) | 0.0% | 446ms |
| 9/s | **shared** | 96.3% | 182ms | **0** | 0.7% | 343ms |
| 18/s(2Cp) | none | **0.0%** | 702ms | 398(+202) | 0.0% | 351ms |
| 18/s | **shared** | 88.4% | 230ms | **0** | 0.0% | 334ms |

## 판정

1. **기준 1(shared: 추천 행 모델 실패 0 · p95 ≤ 126ms)은 절반만 넘었다.** 모델 실패는 두 부하 모두 0 이었지만 p95 는 182 · 230ms 였다. 126ms 는 #271 에서
   맥 원생 모델(추천 행 p95 약 5ms)을 두고 정한 선이다. 컨테이너 모델은 한 건에 24ms(동시 1) ~ 94ms(동시 4)라 같은 선을 넘기 어렵다. 선을 측정 뒤에 옮기지 않고 못 넘었다고 적는다
2. 기준 2(none 이 2Cp 에서도 버티면 #284 는 CPU 경합 탓): 해당 없음. none 은 1Cp 에서도 무너졌다
3. **기준 3: 모델 포화가 원인이다.** 모델을 떼어 놓아도 none 은 추천 행을 0% 로 만들었다. 2쪽 호출이 자리 없이 모델 줄을 채워 추천 행이 대기 상한(400ms)에 걸렸다
4. 기본값 shared 는 유지한다. none 은 추천 행을 통째로 잃고, shared 는 추천 행 모델 실패 0 에 coverage 88~96% 를 지킨다

## 예측과 비교

- none 이 2Cp 에서 무너진다: 맞았다. 1Cp 는 "경계"로 봤는데 이미 완전히 무너졌다
- shared 의 2쪽 모델 행이 2Cp 에서 절반 안팎: **틀렸다(0.0%).** 2쪽은 자리를 기다리지 않는다(ADR-067). 추천 행이 모델 동시성 4 를 자주 채우는 느린 모델에서는 빈자리가 거의 없다.
  모델이 느릴수록 shared 는 "2쪽은 규칙 행"과 같아진다

## 이 표가 말하지 않는 것

- 2쪽 p95(334~446ms)는 규칙 행을 만드는 앱 쪽 비용이 대부분이다. #284(122~131ms)보다 큰 이유는 재지 않았다(이번에는 앱 · k6 가 맥 CPU 를 모델 없이 썼다)
- "다른 머신"을 도커의 CPU 제한으로 흉내 냈다. 네트워크 지연은 없다
- 한 번씩만 쟀다
- 측정 전에 일회용 MySQL 이 도커 VM 메모리 부족으로 죽어 binlog 없이 다시 만들었다. 이 측정의 값과는 무관하다

## 재현

```bash
docker build -t genpage-serving -f personalization/serving/Dockerfile.cpu personalization/serving
# 컨테이너 띄우는 인자는 Dockerfile.cpu 머리말, 조건별 러너는 raw/run.sh
python3 tools/genpage_capacity.py <activity-items.json> capacity.json 20 --url http://localhost:18765
```

원자료: [`raw/`](raw/) (용량 측정, 조건마다 k6 출력 · 요약 · 모델 서버 로그와 자원, 같은 맥의 CPU)

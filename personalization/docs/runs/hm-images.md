# H&M 상품 이미지 확보 리포트

> 이미지 확보 경로와 커버리지 실측. **전체가 아니다** — 그 사실을 먼저 적는다.

## 왜 Kaggle이 아닌가

H&M 원본 이미지(105,542장)는 Kaggle 데이터셋에 있고 **인증이 필요**하다. 이 환경에는 자격증명이 없다
(`~/.kaggle/kaggle.json` 없음). 그래서 다른 경로를 찾았다.

## 찾은 경로 (실측)

Hugging Face의 캡션 데이터셋 `tomytjandra/h-and-m-fashion-caption`에 **이미지가 parquet 안에** 들어 있다.
핵심은 `image` 컬럼이 `struct<bytes: binary, path: string>`이고, **`path`에 원본 파일명이 남아 있다**는 점이다:

```
image[0].path  = '0108775015.jpg'      # = article_id + .jpg
image[0].bytes = b'\xff\xd8\xff\xe0...'  # JPEG 바이트
```

이게 없었으면 매핑을 못 해 못 쓸 뻔했다(캡션 데이터셋에는 `article_id` 컬럼이 없다).

## 커버리지 — **20,491장 (카탈로그의 19.4%)**

| 항목 | 값 |
|---|---|
| 이미지 | **20,491장** |
| 용량 | **6.31 GB** (장당 평균 ~308KB) |
| 부착된 상품 | 20,527 (H&M 20,491 + 레거시 테스트 상품 36) |
| 미부착 | 85,051 → 화면은 그라디언트 폴백 |

**고르지 않다.** 카테고리별 첫 페이지(60개) 기준 실측:

| 카테고리 | 이미지 있는 카드 |
|---|---:|
| 여성복 | 23/60 |
| 아동복 | **0/60** |
| Divided | 27/60 |
| 남성복 | 18/60 |
| 스포츠 | 16/60 |

정렬별로도 다르다 — `price_desc` 38/60, `price_asc` 3/60. 추천 상품 8개 중 3개만 이미지가 있다.

## 서빙

- 파일은 **리포 밖**(`personalization/data/hm/images`, gitignore)에 푼다
- Spring이 `/uploads/**` → 그 디렉터리로 **정적 매핑**(`UploadsConfig`, `app.uploads.dir`)
- `products.image_url`에는 **경로**(`/uploads/0108775015.jpg`)를 넣는다 — URL 전체가 아니라 경로다.
  S3·CDN으로 옮길 때 설정만 바꾸면 된다
- Next.js는 `/uploads/*`를 프록시해 same-origin을 유지한다
- 파일이 없으면 404 → 화면은 그라디언트+이니셜로 폴백한다(일부만 있어도 목록이 깨지지 않는다)

## 함께 고친 것

`.thumb img`에 `mix-blend-mode: luminosity; opacity: .9`가 걸려 있었다. 데모용 picsum 사진을 배경에 녹이려던
스타일인데, **실제 상품 사진을 흐리게** 만든다. `object-fit: cover`만 남겼다.

## 정직한 한계

- **19.4%만 이미지가 있다.** 나머지는 폴백이라 목록이 고르지 않게 보인다
- Kaggle 자격증명이 생기면 **같은 스크립트로 나머지를 채운다**(멱등: 이미 받은 파일은 건너뛴다)
- 이미지가 없는 상품이 사라지는 건 아니다 — 팔 수 있고 추천에도 나온다. 화면만 폴백이다

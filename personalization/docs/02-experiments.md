# 02. 실험 명세

> 각 실험은 **가설 · 지표 · 방법 · 판정 기준**을 먼저 적는다. 결과가 없으면 "측정 전"으로 두고,
> 완료처럼 보이게 하지 않는다. 재현되지 않은 가설도 결과로 남긴다.

## E1. 신선도 vs 지연 (M2)

- **가설**: 컨텍스트 신선도의 병목은 저장소가 아니라 이벤트 소비 구간이며, 대기 상한을 두면
  최신성을 사는 대신 tail latency를 낸다.
- **비교군**: 즉시 응답 / 50ms 상한 / 100ms 상한 / 200ms 상한 / 최신까지 대기
- **지표**: 최신 반영률(%), e2e p95·p99, timeout rate, 구간별 freshness 소모
- **방법**: 클릭 이벤트를 일정률로 흘리고 consumer 지연을 주입, 각 정책으로 홈 요청
- **판정**: 100ms 상한에서 반영률이 유의미하게 오르고 p95가 SLO(300ms) 안이면 채택 후보.
  아니면 "기다리지 않는다"가 결론이고 그것도 결과다.

> **측정 완료(2026-09-21)** — [리포트](runs/20260921-e1-신선도-지연/report.md). 무릎은 기준이 말한
> 100ms가 아니라 **50ms**였고(0ms 7.3% → 50ms 100%, e2e p95 40ms), 컨슈머가 못 따라오는 구간에서는
> **대기가 무력**했다(지연 300ms에서 200ms를 기다려도 0%, 컨텍스트 4.3초 뒤처짐). 같은 실험이
> **전달 방식(KAFKA·IN_PROCESS·IN_REQUEST)** 도 비교했고, 그 결과로 기본값이 바뀌었다([ADR-034](../../docs/adr/ADR-034-personalization-context-deployment-unit.md)).
> **위 가설 문장은 그대로 둔다** — 결과에 맞춰 고치지 않는다.

## E2. online/offline 컨텍스트 일치 (M2)

- **가설**: 같은 로그로 만든 피처도 late event·window 경계에서 갈라진다.
- **지표**: 일치율(%), 불일치 원인 분포(late/중복/window/TTL/순서), 대표 사례의 값 차이
- **방법**: 동일 로그를 offline 재계산과 online 서빙에 각각 통과시켜 대조
- **판정**: 원인별 비중을 낸다. 일치율을 올리는 비용(event-time 처리)은 E1과 같은 축이라 함께 본다.

> **측정 완료(2026-09-21)** — [리포트](runs/20260921-e2-online-offline-일치율/report.md). 기준 조건
> **100%**, 순서를 뒤집으면 **0%**(항목 영구 유실), TTL이 짧으면 **0%**(로그는 안전), 로그가
> max-items를 넘으면 **목록 100%·창 집계 60%**. 중복은 입력(409)과 재배달(오프셋 되감기) **둘 다**에서
> 막혔다. 그리고 **E1의 기본값 결정을 뒤집었다** — `IN_PROCESS`는 동시 적용에서 항목을 잃는다
> (33.3% vs `KAFKA` 100%). 위 가설 문장은 그대로 둔다.

## E3. 과부하 degradation (M3)

- **가설**: 모델 서버가 살아 있어도 queue가 무한이면 API는 죽는다. SLO를 지키는 값은 개인화 포기량이다.
- **비교군**: unbounded queue / bounded queue / admission control
- **지표**: p95·p99, timeout rate, fallback rate, **personalization coverage**
- **방법**: 모델 처리량을 고정하고 유입을 단계적으로 올린다
- **판정**: SLO를 지키는 각 정책의 coverage를 비교. "몇 개 큐가 정답"이 아니라 **교환비**를 낸다.

## E4. 제약 재검증 비용 (M4)

- **가설**: 생성 중 사실이 바뀌면 통과한 제약도 응답 시점엔 거짓이다. 재검증을 강하게 할수록 비싸진다.
- **비교군**: 검증 없음 / 생성 시작 / 생성 완료 후 / 응답 직전
- **지표**: 위반율(%), 추가 지연(ms), stale 창(ms), 창 안에서 바뀐 사실 수
- **방법**: 재고·판매상태를 합성하고 생성 중 상태를 바꾼다
- **판정**: 추천 단계와 구매 단계의 보장 수준을 **분리해서** 결론낸다(구매는 기존 결제 경로가 강보장).

> **측정 완료(2026-09-21)** — [리포트](runs/20260921-e4-제약-재검증/report.md). 정책을 가른 것은
> 지연이 아니라 **창**이었다: 생성 전 스냅샷은 **54ms**(= 모델 지연) 낡고, 생성 후 확인은 **0ms**다.
> **응답 직전 확인은 생성 후 확인과 위반율이 같았고**(둘 다 0.00%) 읽기만 한 번 더 썼다 —
> **마지막 확인을 늘려도 창은 사라지지 않는다.** 그래서 기본값을 `AFTER_GENERATION`으로 정하고
> ([ADR-038](../../docs/adr/ADR-038-constraint-revalidation-timing.md)), 확인 비용은 재지 못했다
> (합성 가용성이 너무 싸서 네 정책 모두 +0ms — 한계를 리포트에 적었다).
> **위 가설 문장은 그대로 둔다** — 결과에 맞춰 고치지 않는다.

## E5. 생성 범위·계산 예산 (M5)

- **가설**: AR 범위를 늘리면 페이지 일관성은 오르지만 같은 하드웨어 처리량이 급감한다.
- **비교군**: 전부 ranking / 앞부분 AR + Top-K / 전부 AR
- **지표**: 구간별 시간(context·inference·constraint·직렬화), e2e, throughput, 예산 소진율
- **판정**: 전체 budget에서 모델 몫을 낸다. 품질 판단은 시스템 지표로 대신하지 않는다(경계 명시).

## E6. 캐시 압축 임계값 (M6)

- **가설**: 값이 작을 때는 압축이 손해고, 일정 크기 이상에서 이득이다.
- **비교군**: 무압축 / LZ4 / Snappy
- **지표**: GET p50·p95·p99, 전송 바이트, 앱 CPU, Redis 메모리
- **방법**: 값 1만 개를 크기 구간별로 넣고 GET 1만 회
- **판정**: 임계값(KB)을 정하고, **임계값 이하에서 압축이 손해라는 것도 같은 하네스로** 보인다.

## E7. 요청 1건 추적 (M8)

- **가설**: 평균은 어디가 느린지 알려주지 않는다.
- **지표**: 구간 타임라인, stale 원인·나이, 제약으로 제외된 아이템, 입력 스냅샷
- **방법**: 요청 하나를 골라 전 구간을 기록
- **판정**: 도구다. 다른 실험의 원인 분석에 쓴다. **응답 재현이 가능해야** 한다.

## 공통 규칙

1. **baseline 없이 모델을 재지 않는다.** 인기/최신/재구매가 먼저다.
2. **오프라인 지표는 게이트, 최종 판정은 온라인 A/B.** 실사용자가 없으면 그 경계를 결과에 적는다.
3. **부하·SLO·표본 크기를 결과에 함께 적는다.** 수치만 남기면 재현할 수 없다.
4. **재현되지 않은 가설은 그대로 남긴다** — "내 범위에서는 아니었다"가 정보다.

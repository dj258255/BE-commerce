# GenPage v2 백엔드 실험 (측정 전에 적는다, 2026-09-25)

이 프로젝트의 본래 질문은 "AI 모델이 request path 에 들어왔을 때 백엔드가 무엇을 보장하는가"다. v1 으로 네 질문을 한 번씩 쟀다(ADR-040 · 047 · 050 · 058 · 065 · 067). v2 는 **더 무거운 의존성**이다 — 파라미터 수천만, 문맥 최대 320토큰, 한 쪽에 여러 번 생성, 프롬프트에 구매 시각 · 채널 · 가격 · 프로필 · 세션 행동이 들어간다. 같은 질문을 v2 로 다시 잰다. 정답 하나를 찾는 게 아니라 **하나를 더 보장하면 다른 쪽에서 얼마를 내는지**를 숫자로 남긴다.

공통: 앱은 bootJar + `--server.port=18080`, MySQL · Redis 는 `compose.yaml`, `APP_RATELIMIT_ENABLED=false`, v2 모델 서버는 `serving/genpage2_server.py`(8766). 원자료 · 재현 명령 · 리포트는 `personalization/docs/runs/20260925-v2-<이름>/`. 유효하지 않은 런(k6 dropped > 0, 모델 서버 오류)은 버리고 이유를 적는다. 목표 SLO 는 v1 과 같게 홈 p95 300ms(앱의 모델 타임아웃이 300ms).

## X1. 학습 문맥과 서빙 문맥이 같은가 (원래 질문 1 후반)

- 방법: 검증 주 평가 고객 N=5,000(SEED 7)에 대해 같은 모델 · 같은 디코딩으로 문맥만 바꿔 생성한다
  - (a) 학습 데이터 문맥 그대로(기준)
  - (b) 지금 앱이 주는 것: 상품 id 목록만(시각 · 채널 · 가격 · 프로필 없음 → 서버가 규칙으로 채움)
  - (c) (b) + 구매 시각
  - (d) (c) + 가격 · 채널
  - (e) (d) + 프로필(= (a) 와 같아야 한다)
- 지표: 문맥 토큰 불일치율((a) 대비 다른 토큰 비율), 생성 페이지 겹침(상위 12 자카드), MAP@12, 요청 본문 크기, 서버 문맥 구성 시간
- 판정: (e) 는 (a) 와 **토큰이 하나도 다르지 않아야** 한다(아니면 버그). (b)~(d) 는 "어떤 필드를 공급하면 점수를 얼마 되찾는가 · 그 대가(본문 크기 · 조회)"를 표로 남긴다

## X2. 무거워진 모델 앞에서 백엔드가 버티나 (원래 질문 2)

- 방법: #271 과 같은 하네스(`tools/run-overload-real-model.sh` 계열)를 v2 서버로. 먼저 v2 서버 용량(닫힌 루프, 동시성 1 · 2 · 4)을 재고, 그 용량의 0.5 · 1.0 · 1.5 · 2.0 배 부하에서 입장 제한 OBSERVED(ADR-065) 켜고 끄기
- 지표: 추천 p95 · p99, 모델 p95, 개인화 비율(coverage), 폴백 사유(rejected · timeout · failed), dropped
- 판정: v1(#271 표)과 같은 부하 배수에서 비교. "v2 의 무게가 SLO 를 지키려면 개인화를 얼마나 포기하게 만드나"

## X3. 생성하는 동안 품절되면 (원래 질문 3)

- 방법: 홈 요청을 흘리면서 동시에 노출 후보 상품의 재고를 초당 R 개씩 0 으로 만든다(`UPDATE stock`). 재고 확인 방식 네 가지를 앱 설정으로 바꾼다
  - `NONE`: 모델 출력을 그대로 믿는다
  - `POST`: 생성 뒤 조립 때 재고를 본다(지금, ADR-050)
  - `PRE`: 생성 시작 때 재고 있는 상품만 후보로 넘긴다(v2 `candidates`)
  - `POST_FINAL`: `POST` + 응답 직전 한 번 더
- 지표: **응답 시점** 품절 노출률(응답을 보낸 순간 재고 0 인 상품 비율), 홈 p95, 요청당 재고 조회 수, 행이 비어 규칙으로 물러선 비율
- 판정: 방식마다 "응답 시점 정확도를 얼마 사는 데 지연 · 조회를 얼마 내나". 구매 단계는 재고 차감(ADR-003)이 최종 보장이라는 경계를 같이 적는다

## X4. 생성 비용을 지연 예산 안에 (원래 질문 4)

- 방법: v2 서버 직접 호출로 생성 방식 × KV 캐시 × 행 수를 재고, 한 설정은 앱 경로로 끝까지
  - 방식: 전부 한 칸씩(prefix = 행당 상품 수) · 앞 2개만(prefix 2, 원문 하이브리드) · 순위만(prefix 0)
  - KV 캐시 켜고 끄기, 행 3 · 6
- 지표: 추론 ms(p50 · p95), 모델 forward 횟수, 동시성 4 처리량, 앱 홈 p95, 페이지 품질(검증 주 MAP@12, 같은 모델)
- 판정: "예산 300ms 안에 몇 행을 한 칸씩 만들 수 있나", 방식별 품질 대가

## 순서와 시간

X4 · X1 은 모델 서버만 있으면 된다(파이썬). X2 는 하네스 매개변수화, X3 는 앱 Java 수정이 필요하다. 코드는 지금 병렬로 만들고, 측정은 B 학습이 끝나 GPU 가 빈 뒤 순서대로 돌린다(모델 서버가 MPS 를 쓰면 학습과 섞여 숫자가 흔들린다).

## X5. 문맥 저장소에 있는 행동이 모델 입력까지 잃지 않고 가는가 (측정 전에 적는다, 2026-09-26)

**왜.** 온라인 문맥(Redis `ctx:{userId}:v2`)과 로그의 일치는 v1 때 E2 로 쟀다(무질서 · 중복 · 창은 고친 뒤 100%, 늦게 온 이벤트 95%, TTL 0% — `runs/20260921-e2-online-offline-일치율/`). v2 가 드러낸 새 문제는 **모델 경계**다.
- 저장소는 항목마다 행동 종류 · 시각 · seq 를 갖고 있다. 그런데 `RecentActivityFacts.recentItemIds` 가 **상품 id 만 남기고 버린다**
- 앱은 v2 에 `history`(id 목록)만 보내고, 세션을 붙이는 변형을 켜면 v2 서버가 클릭을 **요청 시각의 온라인 구매**로 해석한다(프롬프트 규칙). 요청이 조용히 뜻을 바꾼다
- 학습 데이터에는 조회 · 클릭이 없으므로(PLAN "똑같이 할 수 없는 것" 3) 세션 토큰의 효과는 이 실험의 질문이 아니다. 질문은 **백엔드가 가진 사실이 모델 입력으로 온전히 가는가**다

**바꾸는 것(기본값은 지금 그대로).**
- 앱 설정 `app.recommendation.genpage-session`: `OFF`(기본, 지금) · `RICH` — `RICH` 면 `/page` 요청에 `session`(저장소의 최근 행동을 `{item, action: CLICK|VIEW, at: 발생 시각}` 으로, 오래된 것부터)과 `now` 를 보내고, `history` 에는 구매만 둔다
- v2 서버: 세션 행동의 시각 구간을 `at` 으로 계산한다(지금은 `AGO_0-3` 고정). 응답에 요청 옵션 `debug_prompt` 가 있으면 만든 문맥 토큰 이름 목록을 돌려준다(실험용)

**방법.** 로그(`user_activities`: 종류 · 발생 시각 · seq)와 구매(`orders`)에서 **오프라인으로 기대 프롬프트**를 만들고, 같은 사용자 · 같은 순간에 앱 → 저장소 → v2 서버가 만든 **온라인 프롬프트**와 토큰 단위로 대조한다. 교란 조건은 E2 와 같다(`tools/inject-activities.py`): 기준 · 무질서 · 늦게(소비 지연 300 ms) · 중복 · 창(20개 초과) · TTL, 전송 IN_PROCESS · KAFKA. `OFF` 와 `RICH` 를 모두 잰다.

**지표.** 프롬프트 토큰 일치율(사용자 단위 완전 일치 비율 + 토큰 불일치율), 불일치 종류(빠짐 · 순서 · 종류 · 시각 구간 · 뜻이 바뀜), 생성 페이지 겹침(상위 12 자카드), 요청 본문 크기, 앱 쪽 추가 읽기 ms, 홈 p95.

**판정.** `RICH` · 기준 조건에서 온라인 프롬프트가 오프라인과 **완전히 같아야 한다**(아니면 버그). 교란 조건에서는 어긋나는 비율과 원인을 E2 결과와 나란히 적는다. `OFF` 의 "뜻이 바뀜"(클릭이 구매로 읽힘) 비율을 따로 센다.

**구현 전에 좁힌 것(2026-09-26, 코드를 읽고 측정 전에 고쳤다).**
- 기본 설정(`history-source: activity`)에서는 `purchaseHistoryForModel` 이 `null` 이라 `pageHistory` 가 **세션 id 를 그대로 `history` 로** 보낸다. v2 서버는 `history` 를 행동 · 시각 없이 받으므로 클릭이 전부 "요청일의 온라인 구매"가 된다. `OFF` 의 "뜻이 바뀜"은 예외 경로가 아니라 기본 경로다
- 주입 사용자(`tools/inject-activities.py`)는 구매가 없다. 그래서 대조 대상은 **세션 부분과 요청 토큰(요일 · 월)** 이다. 구매 경로는 X1 이 쟀다(`runs/20260925-v2-x1-context/`)
- 주입 상품 id(`userId*1000+seq`)는 v2 어휘에 없어 상품 토큰이 전부 `ITEM_FALLBACK` 이 된다. 토큰만 대조하면 상품이 바뀌어도 같게 나온다. 그래서 서버가 **해석한 사건 목록(상품 id · 행동 · 시각 구간)** 도 남기고 토큰과 사건을 둘 다 대조한다
- `debug_prompt` 응답 옵션 대신 서버가 환경변수 `GENPAGE2_PROMPT_LOG` 의 파일에 요청마다 한 줄(사용자 · 사건 · 토큰 이름)을 쓴다. 앱이 응답을 중계하지 않아도 되고, 응답 계약이 그대로다
- 날짜 경계는 UTC 다. 앱 시각과 기대 프롬프트가 같은 `build_prompt` 를 타므로 둘 사이에서는 어긋나지 않는다. 사람이 느끼는 "오늘"(KST)과는 9시간 어긋날 수 있다
- 뺀 지표: **생성 페이지 겹침**. 상품 토큰이 전부 `ITEM_FALLBACK` 이라 두 프롬프트의 차이는 행동 · 시각 토큰뿐이고, 그 차이가 만드는 페이지 변화는 이 실험의 질문(사실이 가는가)이 아니다. **앱 쪽 추가 읽기 ms** 는 따로 계측하지 않고 `OFF` · `RICH` 의 2쪽 응답 p95 로 본다
- `RICH` 는 세션을 중복 제거하지 않는다(`recentItemIds` 는 `distinct()` 를 한다). 같은 상품을 두 번 본 것도 사실이기 때문이다. 주입 상품 id 는 사용자 안에서 겹치지 않으므로 이 차이는 이번 측정 결과에 나타나지 않는다

## X6. 2쪽 부하가 v2 `/page` 용량을 넘을 때 자리 공유가 1쪽 추천 행을 지키나 (측정 전에 적는다, 2026-09-26)

**왜.** 2쪽(`/page`)은 추천 행과 같은 동시 호출 자리를 쓰고, 자리가 없으면 기다리지 않고 규칙 행으로 간다(#271, `app.recommendation.model.page-capacity: shared`). v1 에서는 이 효과를 판정하지 못했다. 2쪽 부하를 v1 `/page` 용량(121/s)까지 올리기 전에 앱이 30~60/s 에서 먼저 무너졌기 때문이다(`runs/20260924-overload-real-model/report.md` B · C). v2 의 `/page` 용량 Cp 는 16.5/s(X2)라 앱 한계보다 낮다. 모델이 먼저 병목이 되는 조건에서 같은 질문을 다시 잴 수 있다.

**설계.**
- v2 서버는 `/recommend` 와 `/page` 가 잠금 하나를 쓴다. 두 경로의 모델 점유율은 `추천 행 부하 / C + 2쪽 부하 / Cp` 로 어림한다(C 22.9/s, Cp 16.5/s, X2). 추천 행을 X2 처럼 0.52C 로 두면 2쪽 0.5Cp 만 더해도 1.0 이 되어 조건이 구분되지 않는다. 그래서 **추천 행은 0.25C(6/s)로 고정**하고 **2쪽을 0.5 · 1.0 · 1.5 Cp(8 · 16 · 25/s)** 로 올린다. 어림 점유율은 0.76 · 1.23 · 1.78 이다. 25/s 는 v1 에서 잰 앱의 2쪽 한계(30/s)보다 낮다
- 자리: `shared`(기본) 대 `none`(자리 없이 부른다) → 6조건. 입장 제한 OBSERVED, 체크포인트는 X2 와 같은 `b-base-full`(validate, CPU)
- 하네스는 X2 · #271 과 같다(`tools/run-inference-overload.sh` + `k6/home-next-page-load.js`, 조건당 40초 · 워밍업 10초). 앱 코드는 바꾸지 않는다

**지표.** 추천 행: 개인화 비율(coverage) · p95 · 모델 실패 · 거절. 2쪽: 모델 행 비율 · p95 · dropped. 모델 서버 오류(끊긴 연결).

**판정.**
1. **자리 공유의 비용**(0.5Cp): `shared` 가 `none` 보다 2쪽 모델 행 비율이 1%p 넘게 낮거나, 추천 행 · 2쪽 p95 가 1.1배를 넘으면 비용이 있다고 적는다(v1 C 와 같은 기준)
2. **자리 공유의 이득**(1.0 · 1.5Cp): `shared` 에서 추천 행의 모델 실패가 0 이고 추천 행 p95 가 SLO(300 ms) 안이며, `none` 은 둘 중 하나를 어기면 **자리 공유가 1쪽을 지킨다**고 판정한다. `none` 도 둘 다 지키면 v2 에서는 자리 공유의 이득이 없었다고 적는다
3. 어느 조건이든 k6 dropped 가 0 이 아니거나 앱이 먼저 무너지면(모델 없는 대조와 같은 모양) 그 조건은 판정하지 않고 이유를 적는다

## D. 가상 사용자 A/B, v1 대 v2 (측정 전에 적는다, 2026-09-26, #305)

**왜.** 원문 GenPage 는 오프라인 지표 뒤에 A/B 로 판정한다. 여기는 실사용자가 없다. C0(#313)의 가상 사용자(실제 H&M 고객 + 요청 뒤 7일에 실제로 산 상품 = 원하는 것 + 위치 감쇠 반응)로 **A/B 절차가 두 정책을 가르는지**, 그리고 **시뮬레이터의 판정이 실제 구매 채점과 같은 방향인지**를 본다. 모델 품질 주장이 아니다(가중치는 설정값이다).

**누출을 피하는 기간.** C0 은 WBC 학습용이라 학습 기간 안의 요청 시각을 쓴다. 그 시각으로 A/B 를 하면 두 모델 모두 "원하는 것"을 학습 데이터로 이미 봤다. 두 모델이 모두 보지 않은 기간은 **홀드아웃 주(요청 2020-09-16, 원하는 것 = 09-16 ~ 22 구매)** 하나다. v1 서빙 모델(`genpage/model.pt`)과 v2 `f-base-full-1ep` 둘 다 09-16 이전으로 학습했다.
- 홀드아웃 규칙(ADR-054: 고르는 데는 한 번만 본다)을 지키려고 **이 비교로는 어떤 설정도 고르지 않고 어떤 기본값도 바꾸지 않는다.** v2 를 켜지 않는 결정(ADR-068)은 그대로다

**설계.**
- 사용자: 홀드아웃 주에 산 고객(MAP@12 채점 모집단)에서 SEED 7 로 5,000명. 해시로 A · B 반씩 고정 배정(실제 A/B 와 같은 비대응 설계)
- 정책은 둘 다 **서빙 서버의 HTTP `/page`** 로 부른다(비교는 서빙과 같은 경로를 탄다)
  - v1: `serving/genpage_server.py`, `history` = 요청 전 구매 id(최근 것부터), 6행 × 8개, prefix 2
  - v2: `serving/genpage2_server.py`(final), `events` = 요청 전 구매(시각 · 가격 · 채널), `profile`, `now` = 요청 시각, `pin_repeat: true`(ADR-068 에서 고른 설정), 6행 × 8개, prefix 2
  - v1 의 행(대분류 코드)은 v2 행 토큰으로 옮긴다: 그 행 상품들의 H&M 섹션 중 가장 많은 것(`ROW_S<번호>`), 없으면 `ROW_FALLBACK`. 반응 모델은 행 순위와 위치만 쓰므로 이 매핑은 기록용이다
- 반응 · 보상: C0 의 규칙 그대로(`ReactionModel`, `RewardConfig`), 사용자 · 요청마다 같은 씨앗
- A/A: 같은 사용자 분할에 두 쪽 모두 v2 를 보여 준다

**지표.** 사용자당 페이지 보상 합, 클릭률, 구매율(시뮬레이션), 그리고 **실제 구매 적중(페이지 48개 안에 09-16 ~ 22 실제 구매가 든 비율)**. 차이는 부트스트랩 95% 구간(2,000회).

**판정.**
1. A/A 의 모든 지표 차이 구간이 0 을 포함해야 한다. 아니면 배정이나 하네스가 틀린 것이고 A/B 결과를 쓰지 않는다
2. v2 − v1 의 차이와 구간을 적는다. 시뮬레이션 지표(보상 · 클릭 · 구매)의 부호가 실제 구매 적중의 부호와 같은지 본다. 다르면 "이 시뮬레이터는 실제 구매 기준으로 정책을 거꾸로 가른다"고 적고 C2(RL)의 보상으로 쓰기 전에 가중치를 다시 본다

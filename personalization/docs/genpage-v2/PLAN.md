# GenPage v2 — Netflix GenPage 를 최대한 그대로 옮긴다

- 시작: 2026-09-25
- 상태: 진행 상황은 [STATUS.md](STATUS.md), 인터페이스는 [DESIGN.md](DESIGN.md)
- 원문: [GenPage: Towards End-to-End Generative Homepage Construction at Netflix](https://netflixtechblog.com/genpage-towards-end-to-end-generative-homepage-construction-at-netflix-77146fba8a08) (2026-06-29)

## 목표

v1(ADR-053)은 상품 토큰만 있는 2층 모델(파라미터 약 540만)을 다음 구매 예측으로만 학습했다. 서빙 구조(제약 디코딩 · 하이브리드 행 디코딩 · 쪽 나누기)는 원문을 따랐지만 학습은 가장 작은 형태였고, 측정 전에 정한 선(마지막 구매 재추천 MAP@12 0.0234)을 넘지 못했다(0.0209).

v2 는 원문의 구성 요소를 **데이터가 허락하는 데까지 전부** 옮긴다. 그리고 원문의 두 오프라인 발견을 이 데이터에서 다시 잰다.

1. 프롬프트를 풍부하게 하는 것이 모델을 키우는 것보다 효과가 큰가
2. RL 후학습이 목표에 없던 다양성을 늘리는가

## 원문과 1:1 대응

| 원문 | v2 | 같은가 |
|---|---|---|
| 상품(entity) 하나 = 토큰 하나 | 상품 하나 = 토큰 하나(학습 기간 10회 이상 팔린 것) | 같음 |
| 행(row) 하나 = 토큰 하나 | 행 = H&M 섹션(56개) + 특수 행 `다시 사기` | 같음. 행 종류는 H&M 분류에서 만든다 |
| 문맥 토큰: 행동(엔티티 · 행동 종류 · 시각 구간 · 길이 구간) | 구매 이벤트 = [상품][채널(온라인·매장)][며칠 전 구간] | 길이(시청 시간)에 해당하는 값이 없다 |
| 프로필 토큰(언어 · 프로필 종류) | 나이대 · 회원 등급 · 뉴스레터 빈도 · 활성 여부 | 같은 역할 |
| 요청 문맥 토큰(시각 · 요일 · 기기) | 요일 · 월(계절) | 기기 정보가 없다 |
| 구간 구분 특수 토큰 | [PROFILE] [REQUEST] [HISTORY] [PAGE] | 같음 |
| 페이지 = 행 · 상품을 배치 순서대로 | [PAGE][행][상품]…[행][상품]…[EOS] | 같음 |
| 학습 예시 = 실제 노출 페이지 + 반응 | **정답 페이지**: 그 고객이 다음 7일에 실제로 산 상품을 행으로 묶은 페이지 | **다름.** 노출 로그가 없다(아래) |
| decoder-only transformer, 입력 · 출력 가중치 분리 | 같음. 약 5천만 파라미터(원문 2억~9억) | 크기만 다름 |
| 사전학습 = 다음 토큰 예측 | 같음(페이지 토큰에만 손실) | 같음 |
| 후학습 WBC(토큰마다 가중 이진 분류) | 사전학습 모델이 만든 페이지를 "노출"로, 다음 7일 실제 구매를 "반응"으로 | 반응의 출처가 다름 |
| 후학습 RL(보상 모델 + Dr. GRPO + KL) | 같은 구성. 보상 모델은 위 노출 · 반응으로 학습 | 같음 |
| 콜드 스타트: 문맥 주입 · 의미 임베딩 융합 · 대체 토큰 | 상품 설명 · 속성을 문장 임베딩(e5-small)으로 바꿔 ID 임베딩에 더한다. 학습 중 일부 토큰을 대체 토큰으로 | 같음 |
| 다중 주기 증분 학습 | 기준 시점까지 전체 학습 → 하루씩 증분(그날 데이터 + 과거 표본) | 같음. 데이터가 2020-09-22 에 끝나 과거 구간으로 흉내 낸다 |
| 제약 디코딩(중복 · 행 고정 · 카테고리 일치) | 행 중복 금지 · 행 고정 · 행 소속 상품만 · 페이지 안 중복 금지 · 앞 쪽 상품 제외 | 같음 |
| 하이브리드 행 디코딩 | 행마다 앞 k 개 한 칸씩, 나머지 한 번에 | 같음 |
| 쪽 나누기: 앞 쪽 토큰 + 세션 행동을 프롬프트에 | 앞 쪽 페이지 토큰을 이어 쓰고 세션 행동을 최근 이벤트로 | 같음. 조회 · 클릭 행동은 학습 데이터에 없다(아래) |
| 온라인 A/B | 가상 사용자 A/B(v1 대 v2) + 실사용자 A/B 는 열린 항목 5 | 실사용자는 범위 밖 |

## 똑같이 할 수 없는 것 (처음부터 적어 둔다)

1. **노출 로그가 없다.** 원문의 사전학습 데이터는 "서비스에서 긍정 반응을 받은 페이지"다. H&M 에는 구매만 있다. 정답 페이지로 대신하므로 v2 가 배우는 것은 "다음 주에 살 것을 행으로 묶기"다
2. **보상 시스템이 없다.** 원문은 A/B 로 다듬은 만족도 점수를 쓴다. v2 의 보상은 "다음 7일에 샀는가"다
3. **조회 · 클릭 행동이 학습 데이터에 없다.** 행동 종류 토큰(조회 · 클릭)은 어휘에 두지만 학습되지 않는다. 앱의 세션 행동은 서빙에서 넣되 한계로 적는다
4. **규모.** 원문 2억~9억 파라미터, 이 노트북(M2 Pro 32GB, MPS)은 수천만이 현실적이다

## 판정 기준 (측정 전에 적는다)

평가 기간은 v1 과 같다. 튜닝은 검증 주(2020-09-09 ~ 15)로만 하고, 홀드아웃 주(2020-09-16 ~ 22)는 묶음마다 마지막에 한 번 본다(ADR-054 와 같은 원칙).

| 지표 | 정의 | 비교 대상 |
|---|---|---|
| MAP@12 | 생성된 페이지를 배치 순서로 편 앞 12개, v1 과 같은 채점 함수 | 선 0.0234(마지막 구매 재추천) · v1 0.0209 |
| 페이지 recall | 페이지 전체(최대 6행 × 8개) 중 홀드아웃 주에 산 상품 수 ÷ 산 상품 수 | 사전학습 대 WBC 대 RL |
| 행 recall | 산 상품의 섹션이 페이지의 행으로 나온 비율 | 같음 |
| 다양성 | 페이지 안 상품 쌍의 콘텐츠 임베딩 평균 거리(원문과 같은 정의) | RL 전후 |
| 규칙 위반 | 행 중복 · 행 밖 상품 · 페이지 안 중복 · 앞 쪽 상품 재등장 | 0 이어야 한다 |
| 서빙 | 앱 경로 점수 = 엔진 직접 점수, 2쪽 p95(앱이 버티는 부하) | v1 서빙 |

채택: v2 가 홀드아웃 MAP@12 에서 **선(0.0234)을 넘으면** GenPage 기본 모델 후보로 올린다(기본값 켜기는 A/B 뒤). 넘지 못하면 무엇이 모자랐는지(데이터 · 크기 · 후학습)를 절제 결과로 적는다.

원문 발견의 재현(결과가 어느 쪽이든 적는다):

- **프롬프트 대 크기**: 같은 학습 예산에서 (a) 상품 이력만 · 작은 모델, (b) 문맥 전부 · 작은 모델, (c) 상품 이력만 · 큰 모델의 검증 손실과 MAP@12
- **RL 과 다양성**: RL 단계마다 보상과 다양성

## 위험

- MPS 학습 속도: 5천만 파라미터 × 시퀀스 약 250토큰이 몇 시간에 끝나는지 모른다. 첫 스모크로 잰다
- 정답 페이지가 짧다: 고객이 일주일에 사는 상품 수의 중앙값이 작으면 페이지가 1~2행이다. 생성 통계로 먼저 본다
- RL 이 불안정하거나 보상 모델을 속일 수 있다(원문도 적은 위험). KL 계수와 형식 보상으로 막고 곡선을 남긴다
- 조회 · 클릭 토큰이 학습되지 않아 쪽 나누기의 세션 반영이 약할 수 있다(#270 에서 본 현상)

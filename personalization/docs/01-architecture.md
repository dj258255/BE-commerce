# 01. 아키텍처

> 계산을 **offline / nearline / online** 세 평면으로 가른다. 각 평면은 SLA·데이터·복잡도 특성이
> 다르고, 그래서 서로 다른 곳에 둔다. 이 구분은 규모가 커져도 그대로 유지된다.

## 1. 목표

AI 모델이 request path 안에 들어왔을 때 **백엔드가 무엇을 보장해야 하는가**를 측정한다.
모델 품질이 아니라 **모델을 의존성으로 둔 시스템의 성질**(신선도, 과부하, 일관성, 제약, 예산)을 본다.

## 2. 세 평면

| 평면 | 특성 | 담는 것 | 실패하면 |
|---|---|---|---|
| **Offline**(배치) | 데이터·복잡도 제약 없음, 대신 stale | 수집, 피처 생성, 학습, 인기 통계 | 다음 배치까지 이전 결과로 계속 |
| **Nearline**(이벤트) | 온라인처럼 계산하되 실시간 서빙 아님 | 이벤트 소비 → 온라인 컨텍스트 갱신 | 컨텍스트가 stale해짐(정지 아님) |
| **Online**(요청 시) | **SLA 지연 제약** | 컨텍스트 조회, 추론, 제약 검증, 홈 구성 | **미리 계산한 결과로 폴백** |

online은 지연 제약 때문에 복잡한 계산을 넣을 수 없다. 그래서 **폴백이 선택이 아니라 필수**다 —
추론이 느리면 개인화를 포기하고 인기/캐시로 응답한다(정지가 아니라 degrade).

## 3. 데이터 흐름

```text
[사용자 행동]  click / view / purchase
      │  (합성: impression·session — 실데이터와 구분)
      ▼
   Kafka  ──(nearline)──▶  컨텍스트 스토어(Redis)   ← 요청 시 읽는 최신 상태
      │                          ▲
      │                          │ 오프라인 배치가 같은 피처를 재계산(일치율 실험)
      ▼                          │
  오프라인 파이프라인 ──▶ 피처/모델 저장소 ──┐
   (H&M + Amazon_Fashion)                   │
                                            ▼
   홈 요청 ──(online)──▶ [홈 컴포저]
                          ├─ 컨텍스트 조회  (freshness 소모 지점)
                          ├─ 추론(inference) ← 모델 서버 = request path의 dependency
                          ├─ 제약 검증      (재고·판매상태 = synthetic)
                          └─ 폴백           (추론 실패·지연 초과 시 인기/캐시)
                                            │
                                            ▼
                                      응답 + 노출 로깅
```

## 4. 컴포넌트

| 컴포넌트 | 책임 | 이 프로젝트에서 |
|---|---|---|
| 수집·피처(offline) | 파티션된 원본 → 피처, point-in-time 정확 | M1 |
| 온라인 컨텍스트(nearline) | 이벤트 소비 → 최신 상태 유지 | M2 |
| 추론 서버 | 모델을 **하나의 dependency**로 격리 | M3 |
| 홈 컴포저 | 행 선택·순서·제약(다양성·신선도·재고) | M7 |
| 관측·실험 | 노출 로깅, 반사실 평가, 실험 화면 | M8 |

## 5. 경계

`personalization/`은 BE-commerce 모노레포 안의 **자기완결 영역**이다. 커머스 코어와의 연결은
**계약으로만** 한다.

- 커머스 → 개인화: 요청/컨텍스트 계약
- 개인화 → 커머스: 홈 구성 결과(행·아이템)와 노출 이벤트
- **금지**: 커머스 도메인 테이블 직접 조회, 개인화 저장소를 커머스가 직접 읽기

### 서비스를 뗄 조건 (지금 정하지 않는다)

측정으로 다음이 확인되면 그때 분리한다. 지금 쪼개면 얻는 것 없이 배포·디버깅만 어려워진다.

1. 개인화의 **확장 단위**가 커머스와 다르다는 것이 부하 실험으로 드러날 때
2. 개인화 배포가 커머스 가용성에 영향을 준다는 것이 측정될 때
3. 피처 저장소가 커머스 DB와 물리적으로 분리되어야 할 규모에 도달했을 때

## 6. 정직한 한계

- 실사용자가 없다. 사용자 지표(만족·체류)가 필요한 결정은 **시스템 지표로 대신하지 않는다.**
- 합성 데이터(impression·재고)에 의존하는 실험은 그 사실을 결과에 함께 적는다.
- 모델 자체의 품질은 목표가 아니다. 모델은 **교체 가능한 dependency**로 취급한다.

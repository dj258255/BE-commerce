# 23. 적체 배치의 조회 상한 설계

## 0. 어떻게 찾았나

카카오페이 데이터 조직의 기술 블로그를 훑다가 **같은 주제가 반복해서 나오는 것**을 봤다.

- 원장 통계 배치가 수억 건을 한 번에 읽다 OOM. 파티셔닝으로 500만 건 기준 97분 → 8분 55초
- 정산팀 조회가 하루 25만 번에서 **1억 번**으로 늘면서 `Limit-Offset`이 5천만 번째부터
  수십 초. 자체 Zero-Offset/Cursor Reader 를 만들어 해결
- 실시간 OLAP 의 PK 가 1억 2천만 건을 넘으면 OOM

공통점은 **"한 번에 메모리에 올리지 않는다"**였다. 그래서 이 프로젝트의 배치를 봤다.

## 1. 세어 보니 15곳이었다

리포지터리 조회 중 **상한 없이 `List`를 반환**하는 것이 15개, 페이징이 걸린 것이 5개였다.

```
정산 항목 · 에스크로 자동해제 · 주문 만료 · 멈춘 체크아웃 회수 · 미확정 결제 복구
웹훅 보류 재시도 · 가상계좌 만료 · 정기결제 청구 · 보상 재시도 · 대사 내부기록 ...
```

전부 **배치가 스캔하는 자리**다. 평소에는 하루치라 작다. 그런데 배치가 며칠 밀리거나
물량이 튀면 그만큼 커지고, **그때 죽는 것은 돈을 다루는 배치**다.

## 2. 재 봤다

주장하지 않고 실 MySQL에 밀린 상황을 만들었다.

```
쌓인 대상 500건 → 한 번의 조회가 읽은 행 500건
```

**넣은 만큼 그대로 읽는다.** 상한이 없다는 것이 숫자로 확인됐다.

## 3. 고친 방향 — 한 틱에 상한까지만

```
쌓인 대상 500건 → 한 번의 조회가 읽은 행 100건 (상한 100)
```

기본값은 500이고 설정으로 연다. 남은 것은 **다음 주기가 가져간다.**

### 비울 때까지 돌지 않는 이유

"상한만큼 읽고, 없어질 때까지 반복"으로 만들 수도 있었다. 안 했다.

**실패한 건이 대상에 남기 때문**이다. 이 배치들은 한 건이 실패해도 배치를 멈추지 않고
다음 주기에 다시 시도한다(격리). 그런데 비울 때까지 도는 구조로 만들면, **영영 성공하지
못하는 건 하나가 배치를 붙잡는다.**

틱당 일이 일정한 편이 부하도 예측된다. 밀린 물량은 여러 주기에 걸쳐 빠진다.

### 설정이 0이어도 안 죽는다

```java
private Pageable chunk() {
    return PageRequest.of(0, readChunkSize > 0 ? readChunkSize : 500);
}
```

`PageRequest`는 크기가 0이면 예외를 던진다. **잘못된 설정 하나로 돈을 다루는 배치가
멈추는 것보다 기본값으로 도는 편이 낫다.**

필드에 초기값도 함께 뒀다. `@Value`는 스프링이 만들어 줄 때만 채워지는데 단위 테스트는
서비스를 직접 생성한다. 초기값이 없어 0이 되면서 **실제로 배치 테스트가 무더기로 깨졌다.**

## 4. 남는 것

- **`Limit-Offset` 자체는 안 건드렸다.** 지금은 처리된 건이 대상에서 빠지므로 항상
  첫 페이지만 읽는다(offset 0). 그래서 뒤로 갈수록 느려지는 문제가 안 생긴다.
  대상이 남는 조회로 바뀌면 그때는 커서가 필요하다
- **커서·스트리밍은 안 썼다.** 상한만으로 메모리 문제가 사라지는데 커서를 들이면
  트랜잭션 수명과 커넥션 점유를 따로 관리해야 한다. 필요가 증명되면 그때 옮긴다
- 상한 500이 맞는 값인지는 **실 트래픽으로 안 쟀다.** 지금은 메모리를 유한하게
  묶는 것이 목적이고, 값 자체는 설정으로 열어 뒀다

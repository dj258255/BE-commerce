# 결제 시스템 포트폴리오 초안

## 한 줄 요약

PG 결제의 성공 경로보다 **응답 유실·중복 요청·부분 실패 이후에도 돈과 주문의 정합성을 회복하는 과정**을 설계하고 검증한 이커머스 백엔드 프로젝트다.

## 문제

결제 승인 API는 외부 시스템을 호출한다. 따라서 우리 서버에서 타임아웃이 발생해도 PG에서 승인되지 않았다고 단정할 수 없다. 반대로 PG 승인이 끝난 뒤 내부 주문·재고·원장 처리가 실패할 수도 있다.

단순히 `결제 성공 / 결제 실패`만 두면 다음 상태를 표현할 수 없다.

- PG에는 승인됐지만 응답이 유실된 상태
- 승인 후 내부 보상 취소가 실패한 상태
- 웹훅이 중복되거나 순서가 바뀐 상태
- 내부 원장과 PG 기록이 일시적으로 다른 상태

## 핵심 판단

타임아웃을 실패로 처리하지 않고 `UNKNOWN`으로 보존했다. 승인 요청을 무조건 재시도하면 이중 승인이 될 수 있으므로, UNKNOWN은 PG 조회·웹훅 재검증·복구 배치로 확정한다. 승인 후 내부 처리가 실패하면 일반 결제 트랜잭션과 분리된 보상 취소를 수행하고, 보상 실패도 영속화해 재시도한다.

```text
예약 → PG 승인 → 내부 확정
              ↘ 실패 시 독립 보상 취소
UNKNOWN → 조회/웹훅/복구 배치 → DONE 또는 FAILED
```

## 기반 지식의 적용

- 분산 시스템: 외부 호출 결과를 성공·실패·미확정으로 구분
- 동시성: 멱등키, 유니크 제약, 조건부 상태 전이
- 트랜잭션: 외부 호출을 DB 트랜잭션에서 분리한 Saga와 보상
- 데이터베이스: append-only 이력, 복식부기 원장, 대사 행 분리
- 네트워크: timeout과 connection failure를 동일하게 취급하지 않음
- 운영: UNKNOWN의 개수가 아니라 oldest age와 복구 지연을 관측

## 두 번째 판단: 느린 PG에서 무엇을 포기할 것인가

사가로 DB 커넥션을 풀어도 PG 응답을 기다리는 애플리케이션 워커는 점유된다. 무제한으로 PG를 호출하면 결제와 무관한 조회 API까지 느려질 수 있다.

세마포어·timeout 단축·서킷 브레이커·비동기 결제를 비교했고, 현재는 PG에 도달하기 전 동시 호출 상한을 둔다. 이 선택은 결제를 빠르게 하는 최적화가 아니라, 장애 시 일반 기능을 보호하는 격리 정책이다.

로컬 실험에서 PG 지연과 도착률을 변화시키며 결제 p95, 일반 조회 p95, 워커 점유율, 거절률, UNKNOWN 발생량을 함께 기록했다. 상한을 낮추면 일반 조회는 보호되지만 결제 거절이 늘고, timeout을 줄이면 응답은 빨라지지만 UNKNOWN 복구 부채가 증가한다.

## 검증

- PG 타임아웃과 응답 유실 장애 주입
- 승인 후 프로세스 종료
- 웹훅 중복·지연·순서 역전
- 동일 멱등키 동시 요청
- 복합결제 부분취소와 재시도
- 원장 차변·대변 불변식
- PG 지연별 워커 고갈과 일반 API 전파

성공 기준은 “API가 에러 없이 끝났다”가 아니다.

- 중복 승인 0건
- 승인 완료 후 주문·원장 누락 0건
- 누적 취소액이 승인액을 초과하지 않음
- 원장 차변 합계와 대변 합계가 항상 일치
- 장애 후 UNKNOWN이 정해진 복구 시간 안에 최종 상태로 수렴

## 범위와 한계

카드번호·유효기간·CVC는 서버가 직접 받지 않고 PG 결제창에서 처리한다. 이 결정으로 카드 데이터 환경의 범위를 줄였지만, 외부 PG 위탁에 따른 PCI DSS 책임이 사라진다고 주장하지 않는다.

실계약 PG가 하나뿐인 환경에서는 멀티 PG failover의 승인율·수수료·실제 안전성을 검증할 수 없다. 따라서 라우팅 코드는 요청이 PG에 도달하지 않은 경우에만 전환하도록 제한하고, 실계약 PG 두 곳과 운영 데이터가 생길 때까지 기본 비활성으로 둔다.

## 결과를 읽는 방법

이 프로젝트의 결과는 결제수단을 많이 붙였다는 데 있지 않다. 외부 시스템의 불확실성, 정합성, 처리량, 사용자 경험이 충돌하는 상황에서 무엇을 기준으로 선택했고, 무엇을 포기했으며, 장애 실험으로 어디까지 확인했는지를 다른 사람이 복원할 수 있게 만든 데 있다.

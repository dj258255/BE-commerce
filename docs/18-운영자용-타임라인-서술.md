# 18. 운영자용 타임라인 서술: 설계와 실측

> 상태: 구현·실측 완료. 기본은 템플릿이며 모델 결과에는 사실 가드와 템플릿 폴백을 적용한다.

## 0. 왜 이걸 만드나

`docs/11`이 처음부터 자리를 지목해 뒀는데 비어 있었다.

> **그럼 어디가 AI 자리인가**: 어드민 화면이 20개인데 "주문 X번에 무슨 일이 있었나"를
> 한 번에 보는 곳이 없다. **흩어진 사실을 시간순으로 엮는 서술** — 판단이 아니라 서술이다

> **분류는 규칙이 낫고, 서술은 AI가 낫다. 둘을 섞으면 안 된다.**

그런데 지금까지 붙인 모델 둘은 이랬다.

| | 무엇 | 결과 |
|---|---|---|
| 상담 초안(13 문서) | 서술 — 다만 **고객용** | 검증 통과율 58 → 100% |
| 잔여 원인(14·15 문서) | **분류** | **껐다** — 규칙 대비 얻는 것이 0 |

**분류 쪽을 껐으면 서술 쪽을 켜야 그 판단이 완성된다.** 운영자용 서술이 비어 있었다.

---

## 1. 사례조사 — 업계는 이 자리에 무엇을 하나

### 토스페이먼츠 — 로그 분석·해결책 자동 제시 (기술지원)

n8n(워크플로 자동화)과 LLM 엔진을 연결해 **로그를 읽고 문제 해결책을 자동으로 제시**한다.
목표는 **10분 이내 응답**. 판단이 아니라 **흩어진 로그를 읽고 뭐가 문제인지 말해주는** 자리다.
지금 만들려는 것과 성격이 같다.

### 카카오페이 — 결제 MCP · Agent Toolkit (2025.08)

AI 에이전트가 결제 API를 호출하게 하는 **개발자용** 툴킷. Tool 8개
(`demo_payment`·`ready_payment`·`approve_payment`·`get_payment`·`cancel_payment` +
정기결제 3종). 안전장치는 **화이트리스트 기반 도구 필터링과 액션 단위 권한**
(`payment: { get: true }`)이다.

**이건 이번에 안 한다.** 고객 결제 API를 에이전트에게 여는 것은 ADR-008(AI에 쓰기 권한을
주지 않는다)과 정면으로 부딪힌다. 카카오페이가 화이트리스트와 액션 권한을 먼저 깐 이유도
같은 문제를 풀기 위해서다. 원칙을 흔들면서 붙일 자리가 아니다.

### 해외 — 분쟁/차지백 증거 조립

결제·주문·CS 시스템에서 증거를 모아 **대응 자료(representment) 패키지를 조립**하고
카드망 기한을 추적한다. 승소율 30~40% 개선을 주장한다.

**이것도 이번에 안 한다.** 더 크고, 분쟁 실데이터가 없어 검증이 안 된다.

### 그래서 고른 것

**운영자용 타임라인 서술 하나.** 재료가 이미 다 있고(11개 도메인 조회 API, 사실 계약,
숫자 출처 검증), 읽기 전용이라 ADR-008 을 안 건드린다.

## 2. 설계

```
OrderTimeline(11개 도메인)  ← 상황 13 에서 만든 조회
        ↓
    FactPack                ← 상황 15 에서 만든 계약. 숫자·날짜를 값으로 함께 낸다
        ↓
 TimelineNarrativePort      ← 템플릿이든 모델이든 여기서 갈린다
        ↓
 NumericProvenanceGuard     ← 서술의 모든 숫자가 FactPack 에 있는지 대조
        ↓
   운영자 화면 (읽기 전용)
```

### 고객용 초안과 무엇이 다른가

받는 사람이 운영자다. 그래서 **가드가 줄어든다.**

| | 고객용 초안 | 운영자용 서술 |
|---|---|---|
| 내부 용어 | **막아야 한다**(누출 0/12 를 쟀다) | **그대로 나와야 한다** — 화면과 대조해야 하니까 |
| 말투 | 다듬어야 한다 | 상관없다 |
| 없는 숫자 | 버린다 | **버린다** (유일하게 남는 위험) |
| 나가는 곳 | 고객 | 사내 화면 |

### 기본은 모델 없음

`TemplateNarrativeAdapter`가 기본이다. 두 가지를 한다.

1. 모델이 없어도 화면이 비지 않는다
2. **모델이 넘어야 할 자(尺)가 된다** — 모델 서술이 이것보다 나은지 재지 않으면
   "붙였다"만 남는다. 잔여 후보에서 그걸로 한 번 데었다

일부러 잘 쓰지 않는다. 시간순으로 잇기만 한다. **이 문장이 이미 충분히 읽을 만하면
모델이 필요 없다는 뜻이고, 그것도 답이다.**

## 3. 만든 것

| | |
|---|---|
| `TimelineNarrativePort` | 포트. 템플릿이든 모델이든 뒤에 숨는다 |
| `TemplateNarrativeAdapter` | **기본**. 모델 없이 사실을 시간순으로 잇는다 |
| `OllamaNarrativeAdapter` | 로컬 모델. `NONE`을 기권으로 받는다 |
| `TimelineNarrativeService` | 숫자 출처 검증(가드 1개) |
| `GET /api/v1/admin/orders/{orderNo}/narrative` | 읽기 전용 창구. 못 만들면 **204** |

**가드가 하나뿐인 이유**: 사내 화면에만 뜨고 상태를 바꾸지 않는다. 고객에게 안 나가므로
내부 용어 누출도 말투도 문제가 아니다. 남는 위험은 **없는 숫자를 만드는 것** 하나뿐이라
가드도 그 하나만 뒀다. 필요 없는 곳에 가드를 늘리면 무엇이 왜 있는지 흐려진다.

**버린다, 고치지 않는다.** 출처 없는 숫자가 하나라도 있으면 문단을 통째로 버린다.
틀린 숫자가 섞인 서술은 **없는 것보다 나쁘다** — 운영자가 그걸 근거로 확정하면 틀린 판단이
장부에 남는다. 상황 13 에서 조회 실패를 조용히 넘기지 않기로 한 것과 같은 이유다.

**못 만들면 204 다.** 빈 문자열이나 "생성 실패" 같은 문장을 돌려주면 화면이 그걸 서술로 띄운다.

## 4. 잰 것 — 템플릿 대비

잔여 후보를 끄면서 배운 기준을 **만들면서 바로** 적용했다. 절대 품질이 아니라
**기존 방식 대비**로 잰다. 여기서 기존은 모델 없는 템플릿이다.

같은 사실 10건을 둘에 태웠다. 재현: `./gradlew evalTest --tests '*NarrativeLiftEvalTest*'`

| | 출처 없는 숫자 | 기권 | 평균 길이 |
|---|---|---|---|
| 템플릿(기존) | 0건 | 0건 | 324자 |
| qwen3:8b | 0건 | 0건 | **232자** (-28%) |

숫자로는 **28% 짧아졌다**. 그런데 길이만으로는 판단이 안 되므로 문장을 봤다.

**템플릿**
```
주문 ORD-N000 — 2026-08-01 · ORDER · 주문 생성 10,000원 그다음 2026-08-01 · PAYMENT ·
결제 READY → IN_PROGRESS (USER, TOSS_PAYMENTS) 그다음 … 2026-08-02 · RECONCILIATION ·
대사 AMOUNT_MISMATCH (거래일 2026-08-02) — 내부 10,000 / 외부 9,700.
```

**qwen3:8b**
```
주문번호 ORD-N000은 2026-08-01에 주문 생성 후 결제 상태가 READY에서 IN_PROGRESS로
변경되었고, 이후 DONE 상태로 변경되었습니다. 결제 완료 후 원장에 10,000원이 기록되었습니다.
2026-08-02에 대사 상태가 AMOUNT_MISMATCH로 변경되었으며, 내부 거래금액은 10,000원,
외부 거래금액은 9,700원으로 불일치했습니다.
```

**차이가 분명하다.** 템플릿은 목록에 접속사만 붙인 것이라 **원래 목록보다 읽기 어렵다**.
모델 쪽은 상태 전이를 문장으로 잇고 날짜를 한 번만 말한다. 상태 이름(`READY`,
`AMOUNT_MISMATCH`)은 그대로 남아 화면과 대조된다 — 운영자용으로 의도한 그대로다.

**이게 잔여 후보와 정확히 반대인 지점이다.** 거기서는 규칙이 이미 같은 답을 내고 있어서
모델이 동의하는 것 말고 할 게 없었다. 여기서는 규칙이 **문장을 못 쓴다**.

## 5. 만들고 나서 다시 봤더니 — 프롬프트 인젝션 표면

현업 개발자에게 "운영에 AI를 붙일 거면 **거버넌스와 보안**을 신경 쓰라, **AI가 활동할 수 있는
범위를 확실히 제약하고 통제 가능한 걸** 보여주라"는 조언을 받고 방금 만든 것을 다시 봤다.

**사실 묶음의 문장이 전부 코드가 만든 것이 아니었다.**

```java
// DomainContributors
"분쟁 접수 (%s) — %s".formatted(d.chargebackId(), d.reason())
```

`reason`은 **카드사가 보낸 웹훅 페이로드**에서 온다(`ChargebackWebhookController`).
그 값이 타임라인 요약에 실려 `FactPack`을 거쳐 **모델 프롬프트까지 그대로 간다.**
`docs/11`이 이미 경고해 둔 자리였다 — "상품명·`resolveNote`·분쟁 사유가 전부 자유 텍스트다".
경고는 적어 뒀는데, **정작 프롬프트를 만들 때 그걸 안 봤다.**

### 무엇을 했나

`UntrustedText.flatten`을 두고 프롬프트에 실리는 사실 문장을 전부 통과시킨다.
서술·잔여 후보·상담 초안 **셋 다** 같은 사실 묶음을 쓰므로 표면이 같다.

- 개행·제어문자를 공백으로 → **줄바꿈으로 목록 구조를 깨지 못한다**
- 연속 공백 축약, 200자 상한 → **긴 문장으로 앞의 지시를 밀어내지 못한다**

**내용은 검열하지 않는다.** 무엇이 위험한 문장인지 판정하려 들면 그 판정이 또 틀린다.
여기서 지키는 것은 **구조**뿐이다 — 한 줄은 한 줄로 남게 한다.

### 이걸로 막히지 않는다

완벽 차단이 불가능하다는 것은 업계의 공통 인정이다. 여기서 한 일은 **가장 싼 표면을 없앤 것**뿐이다.

**진짜 방어선은 권한이다.**

| | |
|---|---|
| 쓰기 권한 | **없다** — 서술은 상태를 바꾸지 않는다(ADR-008) |
| 출력이 가는 곳 | 사내 화면. 고객에게 안 나간다 |
| 사람이 보는 방식 | **원본 사실 목록과 나란히** 본다 |
| 숫자 | 출처에 없으면 문단째 버린다 |

뚫려도 할 수 있는 것이 **사람에게 거짓말하는 것**까지이고, 장부는 못 바꾼다.
막는 것이 아니라 **뚫린다고 가정하고 권한을 설계한다.**

## 6. 재는 방법을 바꿨다 — 길이는 품질이 아니었다

4절에서 길이·기권·출처 없는 숫자로 쟀다. 앞의 둘은 품질이 아니고, **특히 길이를 개선으로 읽은
것은 방향이 틀렸다.** 평가자가 **긴 답을 선호하는 편향**은 이미 알려져 있어서, 짧아진 것을
좋아졌다고 읽을 근거가 없다. 편향을 반대로 뒤집어 해석한 셈이다.

### 업계 표준은 쌍 비교다

둘을 나란히 놓고 고르게 하는 **쌍 비교(pairwise)**가 절대 점수보다 사람 판단과 잘 맞는다는 것이
알려져 있고, 프롬프트·모델을 A/B 로 견줄 때 쓰는 방식이 이것이다(Chatbot Arena·MT-Bench 계열).
절대 점수는 회귀 감시에 쓰고, **A/B 비교에는 쌍 비교**를 쓴다.

알려진 편향은 셋이고, 셋 다 설계로 막았다.

| 편향 | 어떻게 막았나 |
|---|---|
| 긴 답 선호 | **길이를 지표에서 뺐다** |
| 제시 순서 | 순서를 무작위로 하고 **그 순서를 함께 저장**한다(`source_a`/`source_b`) |
| 출처를 알면 기운다 | 고르기 전에는 **어느 쪽이 모델인지 안 보여준다** |

동점(`TIE`)을 허용한다. 억지로 고르게 하면 그 선택은 신호가 아니다.

```
POST /admin/orders/{orderNo}/narrative/compare   → A/B 두 문단 (출처 없음)
POST /admin/orders/narrative/compare/{id}        → 고른다. 고른 뒤에야 출처 공개
GET  /admin/orders/narrative/compare/stats       → 집계
```

**이 표가 쌓인 다음에 기본값을 정한다.** 그 전에는 안 바꾼다.

### 쟀다: LLM 심판 30건에서 26건이 모델

표본 30건을 심어 판정을 받았다(`commerce/src/test/resources/narrative-blind/`).

| | |
|---|---:|
| 표본 | 30건 |
| **모델을 고른 건** | **26건 (86.7%)** |
| 템플릿을 고른 건 | 4건 |
| A 를 고른 건 / B 를 고른 건 | 18 / 12 |

출처 배정은 `model`이 A 인 건 16, B 인 건 14 로 갈라 뒀다. 판정이 A 18·B 12 라
**순서 편향이 결과를 만든 것으로 보이지는 않는다.** 근거도 건마다 남겼다
(`verdict-claude.csv`) — "금액 10,000/9,700 을 다 들고 있으면서 읽힌다" 같은 식이다.

### 그런데 이건 사람 판정이 아니다

**심판이 LLM이다**(`reviewer=judge:claude-opus`). 위 6절이 쌍 비교를 쓰기로 한 근거는
"사람 판단과 잘 맞는다"였는데, 여기서 판단한 것은 사람이 아니다.

이 프로젝트는 LLM 심판이 틀리는 것을 이미 봤다. `13-` 문서 실험 11 에서 심판이 두 초안에
같은 만점을 줬는데 읽어 보면 같지 않았고, 실험 9 에서는 심판이 짚은 것이 **우리가 만든
루브릭의 구멍**이었다. 그래서 이 86.7% 는 **사람이 확인하기 전의 값**이다.

**기본값은 이 수치로 안 바꾼다.** 서술은 이미 `ollama`로 켜져 있는데, 그 근거는 이 비교가
아니라 **검증에 걸리면 템플릿으로 떨어지는 폴백**이다("더 낫다"가 아니라 "더 나쁠 수
없다"). 이 표는 그 판단을 뒤집지 않고, 사람 판정이 쌓이면 그때 다시 본다.

### 26 대 4 를 사람 판정으로 인용하지 않는다 (2026-09-09 정정)

**앞서 이 절은 "같은 30건을 사람이 처음부터 다시 골라 같은 결과가 나왔다"고 적어 뒀다. 그
근거 파일이 그 주장을 못 받친다.** `docs/data/narrative-preferences-2026-09-07.csv`의
`chosenAt`을 계산해 보면 **30건이 0.276초 안에, 건당 평균 9.5ms 로 기록돼 있다.** 사람이
한국어 문단을 읽고 고른 간격이 아니다. 같은 날 상담 초안 블라인드 리뷰 파일은 건당 14~44초라
사람 속도가 나오는데, 이 파일만 그렇지 않다.

**그래서 아래 표는 사람이 독립적으로 다시 판정한 결과로 읽으면 안 된다.** 기록이 일괄로
쓰였기 때문에, 사람이 실제로 무엇을 봤는지를 이 파일로는 증명할 수 없다. 판정이 LLM 심판과
한 건도 다르지 않은 것도 독립 판정의 근거로 쓰기 어렵다.

| | LLM 심판 | 두 번째 기록 |
|---|---|---|
| 모델 요약을 고른 건 | 26 | 26 |
| 템플릿을 고른 건 | 4 | 4 |

두 번째 열은 위에 적은 이유로 **사람 판정으로 못 읽는다.** 지우지 않고 남기는 것은 같은 실수를 다시 안 하려는 것이다.

**고르기 전에 기준을 적어 뒀다.** ①템플릿에 있는 금액·날짜가 요약에 다 있는가.
하나라도 빠지면 템플릿. ②다 있으면 읽기 쉬운 쪽.

**남는 것은 기준 ① 뿐이다.** 요약이 진 4건은 모두 같은 실패였다. `C05`는 외부 37,700원,
`C10`은 75,700원, `C18`은 134,100원, `C22`는 163,300원을 빠뜨렸다. **넷 다 대사 차액 쪽
금액이고, 문자열이 있느냐 없느냐라 기계적으로 확인된다.** 이건 사람 판정이 없어도 성립한다.
모델이 "금액이 다르다"까지 쓰고 **얼마가 다른지를 안 쓴다.** 운영자가 그 숫자를 보려고
여는 화면이라 이건 그냥 요약이 실패한 것이다. 반대로 나머지 26건의 "읽기 쉬운 쪽"(기준 ②)은 **누가 언제
어떻게 골랐는지 증명할 기록이 없으므로 근거로 쓰지 않는다.**

**이 26 대 4를 사람 선호 결과나 운영 성과로 인용하지 않는다.**

원자료는 `docs/data/narrative-preferences-2026-09-07.csv`에 있다.

## 7. 거버넌스 — 무엇을 남기고 무엇을 못 하게 하나

프롬프트 인젝션은 **막는 것이 아니라 담는 것**이라는 쪽으로 업계 기준이 옮겨갔다.
2026년 판 OWASP LLM Top 10 도 프롬프트 인젝션을 1위에 그대로 두면서 초점을
**예방에서 봉쇄로** 옮겼다 — "모델은 속는다"를 전제로 깔고, 최소 권한·도구 허용 목록·
입출력 필터링·민감한 동작에 사람 승인·감사 로그를 권한다.

| 권고 | 여기서 |
|---|---|
| 외부 내용을 지시와 **분리해 제시** | 사실 목록을 `<<<사실 … 사실>>>` 경계에 넣고, 그 안은 데이터라고 명시 |
| 입력 필터링 | `UntrustedText.flatten` — 개행·제어문자 제거, 200자 상한 |
| 출력 필터링 | 숫자 출처 검증. 출처 없는 숫자가 하나라도 있으면 **문단째 버린다** |
| **최소 권한** | 쓰기 권한 없음. 읽기 전용(ADR-008) |
| 사람 승인 | 확정은 사람이 한다. 서술은 **참고 문장**일 뿐이다 |
| **감사 로그** | `narrative_audits` — 모델 이름·출력·판정·사실 개수·시각 |

### 감사 로그에서 무엇을 안 남기나

**프롬프트 본문은 저장하지 않는다.** 사실 묶음에서 결정적으로 재구성되기 때문이다.
대신 **사실 개수와 완전성 플래그**를 남겨 그때와 지금이 같은 입력인지 대조한다.

재구성되는 것을 또 저장하면 두 곳이 언젠가 갈라지고, 갈라지면 어느 쪽이 맞는지 알 수 없다 —
허용 금액 목록에서 이미 겪은 실패다.

**버린 것도 남긴다.** 화면이 빈 이유를 나중에 답할 수 있어야 하고, 폐기율 자체가 이 기능의
상태를 말한다.

## 8. 심판 모델로 1차 신호를 만들어 봤다 — 신호가 안 나왔다

사람이 고른 표본이 0건이라 켜지 못하고 있었다. 업계 관행이 **심판 모델로 대부분을 재고
사람은 보정과 엣지 케이스만 본다**는 것이라, 1차 신호라도 만들어 보기로 했다.

**심판을 다른 계열 모델로 세웠다.** 자기선호 편향은 잘 알려져 있다 — 심판과 생성자가 같은
모델이거나 같은 계열이면 자기 출력을 후하게 준다. 그래서 서술은 `qwen3:8b`가 쓰고 심판은
`llama3.1:8b`가 봤다.

**순서를 뒤집어 두 번 물었다.** 위치 편향도 알려져 있어서, A/B 를 바꿔 두 번 묻고
**답이 뒤집히면 동점**으로 셌다. 순서를 바꿨다고 답이 바뀌면 그건 선호가 아니다.

```
템플릿 0 · 모델 0 · 동점 8  (그중 순서 뒤집힘 8)
```

**여덟 건 전부 뒤집혔다.** 심판이 고른 것은 서술의 질이 아니라 **앞에 놓인 쪽**이었다.

### 그래서 이 심판은 못 쓴다

순서를 안 뒤집었으면 8:0 이든 0:8 이든 **깨끗한 숫자가 나왔을 것이고, 그걸 근거로 켰을
것이다.** 편향 대책을 설계에 넣어 둔 덕에 그게 신호가 아니라는 걸 알았다.

이것도 이 프로젝트에서 두 번째다 — **잣대가 나를 속이려 한 자리**가 또 나왔다.
상담 초안에서 채점 기준이 네 번 속였고, 여기서는 심판의 순서 편향이 속이려 했다.

**기본값은 그대로 `template`이다.** 그리고 이제 이유가 더 정확해졌다 — 표본이 없어서가
아니라, **모델 심판으로는 이 차이를 못 가린다**는 것을 확인해서다. 사람이 골라야 한다.

### 이건 알려진 현상이고, 대책도 알려져 있다

나중에 문헌을 찾아보니 위치 편향은 널리 보고돼 있다. 순서만 바꿔도 **최대 30% 가 반전**되고
평균 order-flip 이 **0.236**이다. 그리고 표준 완화책이 정확히 내가 한 것이다 — **양쪽 순서로
돌려 순서 의존 판정을 무승부로 처리**하면 위치 편향 신호가 거의 0 이 된다.

그래서 결론을 이렇게 다시 쓴다. **"뒤집혀서 못 쓴다"가 아니라 "표준 완화책을 적용했더니
8건 전부 무승부라 심판이 신호를 0 으로 준다"**다. 앞의 문장은 완화책을 모르고 한 말로 읽힌다.

## 9. 선호를 못 재는 자리에서 결손을 쟀다

사람 표본이 0건이라 막혀 있었다. 그동안 **판정하는 쪽의 편향과 무관한 것**을 잴 수 있는지 봤다.

### 9-1. 강한 심판을 세워 봤다 — 그리고 블라인드가 깨졌다

기존 결론("모델 심판으로는 못 가린다")의 근거는 `llama3.1:8b` 하나였다. 훨씬 강한 심판
(Claude)에게 같은 30건을 출처를 가린 채 물었다. 케이스 모양도 갈랐다 — 금액 불일치, 외부에만
있음, 부분취소 미반영, 이의제기까지 붙은 긴 사건 넷을 섞었다(전엔 금액만 다른 같은 모양이었다).

```
출처 선호   템플릿 4 · 모델 26        (26/30, 단측 p = 0.00003)
위치 선호   A 18 · B 12              (18/30, 단측 p = 0.18 — 편향 근거 없음)
  모델이 A 일 때 모델 고름 15/16
  모델이 B 일 때 모델 고름 11/14      → 자리가 아니라 내용으로 골랐다
```

강한 심판은 순서에 안 흔들렸다. 그러니 **"모델 심판으로는 못 가린다"는 모델 크기 문제였다.**

**그런데 이 26/30 을 승격 근거로 쓸 수 없다.** 블라인드가 성립하지 않았기 때문이다 —
템플릿은 `"그다음 … 그다음 …"` 사슬이라 **한눈에 구별된다.** 어느 쪽이 무엇인지 아는 채로
LLM이 LLM 출력을 고른 것이라, 자기선호 편향과 갈라낼 방법이 없다.

### 9-2. 대신 기계로 세지는 차이가 나왔다

30건을 읽다가 편향과 무관한 것을 봤다. **모델이 금액을 빠뜨린 건이 있었다.**
"금액이 다름을 나타냈습니다" — 얼마와 얼마인지가 없다. 대사 불일치를 조사하는 사람에게
그 요약은 그 자리에서 쓸모가 없다. 이건 취향이 아니라 **결손**이고, 세면 된다.

```
template          결손 0 / 30건
ollama:qwen3:8b   결손 4 / 30건     ← 이 회차의 값. 실행마다 다르다(9-3)
```

빠뜨린 자리에 규칙성이 있었다. 다섯 건 중 넷이 **대사 결과가 "외부에만 있음"**인 건이었다.
사실이 네 개뿐이라 짧은데, **짧을수록 요약하려다 숫자를 버린다.**

그 유형은 잔여 원인 작업에서 **가장 위험한 유형**으로 짚은 그것이다 — 결제사는 처리했다는데
우리 장부엔 없는 건. 운영자가 제일 먼저 봐야 할 것이 그 금액인데 거기서 빠진다.

### 9-3. 간헐적이라서 오프라인 평가로는 못 막는다

같은 코드로 여섯 번 쟀다.

```
template          0/30  (여섯 번 모두)
ollama:qwen3:8b   4 · 0 · 1 · 0 · 1 · 2  / 30
```

**뒤의 두 번은 가드를 고치고 다시 잰 것이다.** 처음 가드가 부분 문자열로 찾고 있었다 —
`contains("17300")`은 본문에 **173000**이 있어도 참이고 `"17,300"`은 **117,300**
안에서도 잡힌다. **엉뚱한 금액이 결손을 덮어 주는** 구조라, 가드가 열리는 쪽으로 틀렸다.
숫자 경계를 보게 고쳤다(앞은 숫자·쉼표가 아니고, 뒤는 숫자나 쉼표+숫자가 아니어야 한다).

고치고 나서도 템플릿이 0/30 인 것이 중요하다. 템플릿 출력에는 `"외부 17,300, 내부 기록 없음"`
처럼 **자릿수 구분이 아닌 쉼표**가 금액 뒤에 붙는데, 경계를 너무 좁히면 그게 결손으로
잡힌다. 그 자리를 통과시키면서 `17,300,000`은 막아야 한다.

**"이 모델은 금액을 안 빠뜨린다"를 오프라인으로 증명할 수 없다.** 몇 번을 돌려 0 이 나와도
다음 호출에서 빠뜨린다. 그러니 평가로 걸러낼 문제가 아니라 **런타임에서 매번 봐야 하는** 문제다.

`AmountCoverageGuard`를 붙였다. `NumericProvenanceGuard`와 방향이 반대다 —
출처 검증은 **없는 숫자를 지어냈는지**를 보고, 이 가드는 **있는 숫자를 버렸는지**를 본다.
둘 다 통과해야 서술이 나간다. 버린 건은 `dropped_amounts`로 지표와 감사에 남는다.

실험 코드가 **운영에서 도는 그 가드를 그대로 쓴다.** 실험용 판정기를 따로 만들면 둘이 갈리고,
그때부터 실험 결과는 운영에 대해 아무 말도 못 하게 된다.

### 9-4. 그래도 기본값은 안 바꿨다

가드가 결손을 막지만, **어느 서술이 나은가**는 여전히 안 재였다. 26/30 은 블라인드가 깨진
상태의 값이고 자기선호와 못 가른다. 승격은 **사람이 고른 25~30건**이 있어야 한다.

바뀐 것은 하나다 — 사람이 고를 때 **금액이 빠진 서술은 아예 후보에 안 올라온다.**
그 결손을 "모델이 못 쓴다"의 근거로 세지 않게 됐다.

## 10. 켰다 — 더 낫다는 근거가 아니라 더 나쁠 수 없다는 근거로

9절까지의 결론은 "사람이 고른 25~30건이 모여야 정한다"였다. 그 기준은 내가 세운 것이고,
세워 놓고 보니 **그 기준에 갇혀 더 중요한 것을 안 보고 있었다.**

### 10-1. 가드가 화면을 비우고 있었다

금액 결손 가드를 붙였을 때 버린 서술을 어떻게 하는지는 안 봤다. 코드를 보니 이랬다.

```java
List<Long> dropped = coverageGuard.missing(raw.get(), facts);
if (!dropped.isEmpty()) {
    record(orderNo, "dropped_amounts", null, facts);
    return Optional.empty();     // 운영자 화면이 통째로 빈다
}
```

모델을 켜면 **30건 중 0~4건의 확률로 요약이 아예 없는 화면**을 보게 된다. 템플릿은 그
자리에서도 늘 뭔가를 낸다. 이 상태로는 "어느 쪽 문장이 더 읽히나"를 재기 전에 이미
켜면 안 되는 것이었다.

### 10-2. 버렸을 때 템플릿으로 떨어뜨린다

모델 서술이 가드에 걸리면 빈손 대신 템플릿을 준다.

```java
Optional<String> accepted = pass(port, facts, orderNo);
if (accepted.isPresent()) { ... }

if (port instanceof TemplateNarrativeAdapter) {
    return Optional.empty();     // 이미 템플릿이었으면 더 물러설 곳이 없다
}
Optional<String> byTemplate = pass(fallback, facts, orderNo);
```

폴백도 같은 가드를 통과해야 나간다. 템플릿은 사실을 옮기기만 하므로 늘 통과하지만,
검사를 건너뛰는 경로를 만들지 않는 것이 중요하다.

**기권한 자리에서도 떨어뜨린다.** 여기서 전에 내린 판단을 하나 바꿨다. 원래는 모델이
기권하면 그대로 비웠고 근거가 "억지로 만든 문장은 일을 늘린다"였다. 그 근거는 **모델에게
억지로 쓰게 하는 것**에 대한 것이지, 사실을 그대로 옮기는 템플릿에는 해당하지 않는다.
운영자에게 빈 화면과 사실 목록 중에서는 사실 목록이 낫다.

### 10-3. 그래서 켰다

`app.assist.narrative-provider` 기본값을 `template` → **`ollama`**로 바꿨다.

**근거가 "더 낫다"가 아니다.** 어느 쪽 문장이 더 읽히는지는 여전히 못 쟀다. 사람이 고른
표본은 0건이고, 강한 심판을 세워 본 26 대 4 는 블라인드가 깨진 값이다.

근거는 **"더 나쁠 수 없게 만들었다"**다. 모델이 잘 쓰면 그 문장이 나가고, 못 쓰면 템플릿이
나간다. **모델을 켠 최악이 템플릿을 켠 것과 같아졌으므로, 못 잰 것이 위험으로 남지 않는다.**

### 품질 판정을 열어 두지 않고 닫는다

여기서 "사람이 고른 25~30건이 모이면 그때 판정한다"로 두려 했다. 그 기준은 **내가 만든 것**이고,
만들어 놓고 보니 **영영 안 닫히는 상태**가 됐다. 표본을 모으는 일이 계속 뒤로 밀리는 동안
문서에는 미정만 남는다. 있는 증거로 닫고, 그 증거가 무엇인지 정확히 적는 편이 낫다.

**있는 증거는 이렇다.**

```
심판 llama3.1:8b   8건 전부 순서에 뒤집힘 → 신호 0
심판 Claude        모델 26 · 템플릿 4 (30건, 단측 p = 0.00003), 위치 편향 없음
기계 검사          금액 결손: 템플릿 0/30, 모델 0~4/30 (간헐적, 가드로 막음)
사람               0건
```

**이 증거가 지지하는 것**: 강한 심판은 순서에 안 흔들리고 일관되게 모델 쪽을 골랐다.
템플릿이 이긴 4건은 전부 **모델이 금액을 빠뜨린 건**이고, 그 실패는 이제 가드가 막는다.

**이 증거가 지지하지 않는 것**: 26대 4를 "모델 요약이 더 낫다"의 근거로 쓸 수 없다.
템플릿이 `"그다음 … 그다음 …"` 사슬이라 한눈에 구별돼 **블라인드가 성립하지 않았고**,
심판이 이 코드를 같이 작성한 모델이라 자기선호와 갈라낼 방법이 없다.

**그래서 결론은 이것이다.** 모델 요약이 더 나은지는 **모른다.** 켠 근거는 여전히 폴백이지
품질이 아니다. 사람이 고른 표본이 생기면 그때 이 심판과 일치도를 재서 심판의 쓸모를 판정하고,
그때 처음으로 품질을 말할 수 있다. **그 표본이 안 생겨도 이 기능의 상태는 지금 그대로다.**

판정 30건은 `commerce/src/test/resources/narrative-blind/preferences-judge-claude.csv`에 있다.
심판 이름이 `judge:`로 시작해 집계의 사람 표본에서 빠진다.

### 10-4. 확인한 범위

- 폴백 동작은 단위 테스트 3건으로 고정했다. 금액을 빠뜨린 서술이 템플릿으로 떨어지는 것,
  통과한 서술은 폴백하지 않는 것, 이미 템플릿이면 더 물러서지 않는 것
- `narrative-provider=ollama`로 **애플리케이션 컨텍스트가 뜨는 것**까지 확인했다.
  앞서 장애 분석 쪽에서 생성자가 둘이라 컨텍스트가 죽은 적이 있어, 이 확인을 뺄 수 없다
- **실제 주문으로 폴백이 도는 것은 확인하지 못했다.** 로컬 DB에 주문이 0건이라 서술 호출
  자체가 일어나지 않는다. 시드 데이터를 만들면 확인할 수 있고, 아직 안 했다

## 11. 지연 예산을 정했다 — 그 전에는 아무도 정한 적이 없었다

**"현업에 투입해도 되는가"를 따져 보다 나왔다.** 읽기 타임아웃이 코드에 박혀 있었는데
서술은 60초, 장애 분석은 120초로 서로 달랐다. 그 숫자를 정한 근거가 어디에도 없다.

60초는 **운영자 화면이 1분 멈춰도 된다**는 뜻이다. 그걸 아무도 결정하지 않았다.

### 11-1. 재 봤다

```
템플릿        p50 0ms     · p95 0ms
모델(순차)     p50 8,801ms · p95 12,672ms
모델(동시 4)   p50 30,328ms · p95 31,613ms
```

**동시 4개면 p95 가 31.6초다.** 순차 대비 3.5배다. 로컬 모델이 요청을 큐에 세우기 때문이고,
운영자가 한 명이 아니면 혼자 쟀을 때의 값은 유지되지 않는다.

타임아웃 60초는 이걸 **막지 못한다.** 31초는 60초 안이므로 그냥 기다린다.

### 11-2. 15초로 정했다

가드에 걸리거나 시간이 지나면 **템플릿으로 떨어진다**(10절). 그러니 기다리는 것보다
떨어지는 편이 낫다. 15초는 순차 p95(12.7s)는 살리고 동시 적체(30s+)는 끊는 자리다.

장애 로그 분석은 30초로 따로 뒀다. 운영자가 로그를 붙여 넣고 결과를 기다리는 **명시적
동작**이라 화면 렌더링과 예산이 같지 않다. 다만 그쪽은 폴백이 없어 시간이 지나면 빈손이므로
무한정 늘리지 않는다.

### 11-3. 이 수치가 말하는 것

**이 모델과 이 하드웨어로는 동기 화면을 여럿이 함께 쓸 수 없다.** 15초 타임아웃은 그
사실을 감추지 않고 **템플릿으로 떨어뜨려 드러낸다**. 폴백 비율 알림(`AssistNarrativeAlwaysFallingBack`)이
그때 울린다.

늘리려면 미리 만들어 두는 수밖에 없다. 확정 시점에 초안을 만들어 기록하는 섀도 경로가
이미 있으므로(`shadow-enabled`), 그 자리를 화면용 캐시로 쓰는 것이 다음 단계다. 안 했다.

## 12. 남는 것

- **사람이 고른 표본이 0건이다.** 모델 심판 30건은 있고 파일로 남겼다. 사람 표본이 생기면
  이 심판과 일치도를 재서 심판의 쓸모를 판정한다. 그때까지 품질은 **모르는 것으로 둔다.**
- **필요한 표본 수를 근거 없이 잡고 있었다.** "몇 건이면 되나"를 정하지 않은 채 "쌓이면 정한다"고만
  적어 뒀다. 문헌을 찾으니 인간 선호 평가는 **50건이면 충분하고, 차이가 뚜렷하면 25~50건**에서
  승자가 드러난다. 그래서 승격 기준을 **최소 25건, 목표 30건**으로 못 박는다.
- **어노테이터가 한 명이다.** 표준은 인스턴스당 3~5명이고 그래야 평가자 간 일치도를 잴 수 있다.
  혼자 고른 30건으로는 **일치도를 못 재므로**, 이 결과는 "한 사람의 일관된 선호"까지만 주장한다.
- **사실 줄 단위로 신뢰도를 구분하지 않았다.** 지금은 목록 전체를 데이터 경계에 넣는다.
  분쟁 사유(외부)와 결제 상태 전이(코드)가 같은 `- ` 줄로 섞여 있다. 줄마다 출처를 표시하면
  모델이 구별할 수 있지만, 그러려면 타임라인이 신뢰도를 함께 내야 한다.
- **표본이 합성이다.** 실제 타임라인이 내는 문장 형식은 그대로 썼지만 값은 만든 것이다.
  실데이터로 다시 재야 한다.
- **기본은 여전히 template 이다.** 모델 쪽이 나아 보이지만, 사람이 읽고 판단한 표본 없이
  기본값을 바꾸지 않는다. 잔여 후보에서 그 순서를 어겼다가 되돌렸다.
- **한 모델만 봤다.** qwen3:8b 하나다. 모델을 키우면 나아지는지는 안 쟀다.

# 19. 장애 로그 원인 분석: 규칙 우선 설계와 실측

> 상태: 구현·실측 완료. 규칙 우선 분석을 기본으로 사용하며 최종 판단은 운영자가 수행한다.

## 0. 왜 이걸 하나 — 그리고 왜 처음엔 못 한다고 했나

`18` 문서를 끝내고 "AI 붙일 자리가 더 없다"고 정리하면서 에러 분석 자동화를 이렇게 제쳤다.

> 내가 주입한 장애만 나온다. 에러 분석의 값은 "예상 못 한 장애를 읽어주는 것"인데,
> 내가 만든 장애로 재면 손으로 만든 27건 실패의 재현이다.

**틀렸다.** 정확히는 **장애 목록을 내 머리에서 뽑을 때만** 그렇다.

이 프로젝트가 이미 쓰는 방법이 있다 — **검산값을 코드 바깥에서 가져와 테스트에 박는다.**
장애 목록도 같은 방법을 쓰면 된다. 내가 모르는 유형은 **내가 아니라 남이 겪은 것**에서 온다.

## 1. 외부에서 가져온 장애 분류

### danluu/post-mortems — 공개 포스트모템 모음

실제 회사들의 사후검토를 모아 분류한 것이다. 카테고리가 여섯이다.

| 카테고리 | 무엇 | 예 |
|---|---|---|
| **Config** | 설정 변경 실수 | 리전 설정을 잘못 지워 장애 |
| **Hardware/Power** | 물리 인프라 | 변압기·전력·냉각 |
| **Conflicts** | 경쟁 조건·동시성·데이터 불일치 | DNS 관리의 잠복 경쟁 조건이 엔드포인트를 빈 레코드로 |
| **Time** | 시간 계산·윤초·인증서 만료 | 라이브러리 대신 "1년"을 직접 계산한 코드 |
| **Database** | 성능·마이그레이션·용량 | |
| **Uncategorized** | 나머지 — **결제 사고가 여기 몰려 있다** | Twilio 빌링, Knight Capital |

### 인시던트 178,000건 기반 근본원인 분류

큐 적체·복제 지연·**ETL 무음 실패** 같은 유형이 코드로 정리돼 있다.

### 이 목록에서 **내가 못 떠올렸을 것**

내가 카오스 테스트로 넣어 둔 것은 **DB 지연·연결 끊김** 하나뿐이다. 위 목록에서 이 프로젝트에
실제로 일어날 수 있는데 **내가 실험으로 만들어 본 적 없는** 것을 골랐다.

| 유형 | 왜 우리에게 일어날 수 있나 | 내가 넣어 봤나 |
|---|---|---|
| `TIME_SKEW` | 웹훅 서명이 timestamp 허용 오차(5분)를 쓴다. 시계가 틀어지면 정상 웹훅이 거부된다 | ❌ |
| `CERT_EXPIRY` | PG는 HTTPS 다. 인증서 만료는 **날짜가 되면** 터진다 | ❌ |
| `CONFIG_DRIFT` | 임계값·가중치를 무배포로 바꾼다. 잘못 바꾸면 조용히 동작이 바뀐다 | ❌ |
| `QUEUE_BACKLOG` | 아웃박스·심사 큐가 있다. 적체는 에러가 아니라 **느려짐**으로 나타난다 | ❌ |
| `REPLICATION_LAG` | 조회를 복제본으로 돌리면 방금 쓴 것을 못 읽는다 | ❌ |
| `DB_TIMEOUT` | Toxiproxy 로 이미 주입해 봤다 | ✅ |
| `RACE_CONDITION` | 재고·포인트에서 이미 다뤘다 | ✅ |

**다섯이 내가 안 떠올린 것이다.** 이 목록을 밖에서 가져오지 않았으면 실험 대상이
DB 지연 하나로 끝났을 것이다.

## 2. 그 목록으로 실제 장애를 넣어 봤다

**목록이 있어도 로그가 저절로 생기지는 않는다.** 여덟 유형 중 이번 회차에 **실제로 넣어서
로그를 받아낸 것**은 셋이다.

| 유형 | 실제 로그 | 어떻게 만들었나 |
|---|---|---|
| `DB_TIMEOUT` | ✅ | Toxiproxy 로 MySQL을 끊고 카오스 테스트 실행 |
| `TIME_SKEW` | ✅ | **시계가 1시간 틀어진 웹훅**을 실제로 넣어 401 을 받았다 |
| `QUEUE_BACKLOG` | ✅ | 보류 웹훅이 재시도를 소진하며 쌓인 로그 |
| `PG_UNAVAILABLE` | ✅ | **서킷브레이커를 실제로 열어** 폴백 로그를 받았다 |
| `RACE_CONDITION` | ❌ | **못 만드는 게 아니라 로그가 안 남는다** — 낙관적 락 충돌을 재시도로 흡수한다 |
| `CERT_EXPIRY` | ❌ | TLS 구성이 필요하다 |
| `REPLICATION_LAG` | ❌ | 복제본이 없다 |
| `CONFIG_DRIFT` | ❌ | **못 만드는 게 아니라 로그가 안 남는다** — 그게 이 유형의 성질이다 |

**로그가 안 남는 유형이 둘이다.** 이게 이 표에서 제일 중요하다.

- `CONFIG_DRIFT` — 설정을 잘못 바꾸면 **에러가 안 난다.** 동작이 조용히 바뀔 뿐이다
- `RACE_CONDITION` — 충돌이 나긴 하는데 **재시도가 흡수한다.** `StockDeductionService`가
  `ObjectOptimisticLockingFailureException`을 잡아 다시 시도하고, 상한을 넘길 때만 예외를 던진다.
  경합이 있어도 성공하면 아무 줄도 안 남는다

**로그로 원인을 찾는 방식은 이 둘을 구조적으로 못 본다** — 모델을 붙이든 안 붙이든.
잘 만든 재시도가 관측을 지운 셈이고, 이건 이 프로젝트가 의도한 동작이라 고칠 것도 아니다.

## 3. 설계 — 규칙을 먼저 만들었다

```
로그 조각
   ↓
IncidentAnalysisPort          ← 규칙이든 모델이든 뒤에 숨는다
   ├── RuleBasedIncidentAnalyzer   ← 기준선. 로그에 찍힌 <말>로 고른다
   └── OllamaIncidentAnalyzer      ← 목록 밖 값은 버린다
   ↓
IncidentDiagnosis(원인, 근거 한 줄)
```

**근거 인용을 강제한다.** 유형만 내면 사람이 그 판단을 확인할 방법이 없다. 상담 초안에서
숫자 출처를 강제한 것과 같은 결이다.

**로그도 남이 쓴 문장이다.** 예외 메시지에 주문명·분쟁 사유가 그대로 찍힐 수 있어서,
프롬프트에 넣기 전에 눌러 담고 경계 안에 넣는다(17 문서에서 만든 것을 그대로 쓴다).

규칙은 **일부러 잘 만들지 않았다**. 로그에 원인 이름이 그대로 찍히는 경우만 잡는다.
이것만으로 충분하면 모델이 필요 없다는 뜻이고, 그것도 답이다.

## 4. 잰 것 — 표본을 늘리니 결론이 뒤집혔다

재현: `./gradlew evalTest --tests '*IncidentAnalysisEvalTest*'`

**3건일 때는 모델이 규칙보다 나빴다.**

| | `DB_TIMEOUT` | `TIME_SKEW` | `QUEUE_BACKLOG` | 합계 |
|---|---|---|---|---|
| 규칙 | 맞음 | 맞음 | 기권 | 맞음 2 · **틀림 0** |
| qwen3:8b | 맞음 | 맞음 | **틀림** | 맞음 2 · **틀림 1** |

여기서 멈췄으면 "모델이 규칙보다 나쁘다"로 적었을 것이다. **서킷브레이커를 실제로 열어
한 건을 더 만들자 그림이 달라졌다.**

| | `DB_TIMEOUT` | `TIME_SKEW` | `PG_UNAVAILABLE` | `QUEUE_BACKLOG` | 합계 |
|---|---|---|---|---|---|
| **규칙(기준선)** | 맞음 | 맞음 | **기권** | **기권** | 맞음 2 · 기권 2 · 틀림 0 |
| **qwen3:8b** | 맞음 | 맞음 | **맞음** | **틀림** | **맞음 3** · 기권 0 · 틀림 1 |

**모델이 하나 더 맞힌다.** 규칙은 `PG 서킷 오픈` 이라는 우리말 로그에 아는 신호가 없어
기권했는데, 모델은 그 문장을 읽고 맞혔다. **규칙이 못 하는 자리가 실제로 있었다** —
잔여 후보·서술·에러 분석을 통틀어 처음이다.

### 그런데도 켜지 않았다

두 가지 때문이다.

**① 틀린 답이 기권보다 나쁘다.** 큐 적체 로그에서 규칙은 기권했고 모델은 `RACE_CONDITION`
을 찍었다. 기권은 사람이 원래 하던 대로 보게 두지만, 틀린 답은 사람을 **엉뚱한 곳으로
보낸다**. 로그 분석에서 잘못된 원인 지목은 장애 시간을 늘린다. 맞은 것 하나를 얻고 틀린 것
하나를 얻은 것을 **순이득이라 부를 수 없다**.

이건 잔여 후보에서 본 것과 같은 실패다. **모델은 모를 때 기권하지 않는다.** 그때는
"고를 게 하나뿐"을 "그러니 그걸 골라라"로 읽었고, 여기서는 "재시도가 반복된다"를
"동시성 문제"로 읽었다.

**② 표본이 4건이다.** 3건에서 4건으로 가는 것만으로 결론이 뒤집혔다. 그 정도로 얇은
표본에서 "규칙보다 낫다"를 결정 근거로 쓸 수 없다. **한 건이 결론을 뒤집는 실험은 아직
실험이 아니다.**

기본값은 `rule`이다. 다만 이번에는 **이유가 다르다** — 앞의 둘은 "규칙 대비 얻는 게
없어서"였고, 이번은 **"얻는 게 있는데 잃는 것도 있고, 표본이 얇아서"**다.

## 5. 근거 대조로 막아 보려다 — 세 번째로 같은 벽을 만났다

틀린 답 하나가 켜지 못하는 이유였으니, 그것만 막으면 되겠다고 생각했다. 이 프로젝트가
이미 쓰는 방법이 있다 — 상담 초안에서 **초안의 숫자가 사실 목록에 있는지** 대조해
하나라도 없으면 버렸다. 로그 진단도 같게 하면 될 것 같았다.

`EvidenceGroundingGuard`를 만들어 **모델이 인용한 줄이 실제 로그에 있는지** 대조했다.

**못 잡았다.**

| | 맞음 | 기권 | 틀림 |
|---|---|---|---|
| 규칙 | 2 | 2 | **0** |
| qwen3:8b | 3 | 0 | **1** |
| qwen3:8b + 근거 대조 가드 | 3 | 0 | **1** |

모델이 낸 답을 보면 이유가 분명하다.

```
CAUSE: RACE_CONDITION
EVIDENCE: 웹훅이 결제보다 먼저 도착 — 보류 paymentKey=tviva… retry=6
```

**인용은 진짜다.** 로그에 그대로 있는 줄이다. 틀린 것은 **그 줄에서 끌어낸 결론**이다.
"재시도가 반복된다"를 읽고 "동시성 문제"라고 답했다.

### 이 프로젝트에서 세 번째다

- **상담 초안** — 근거 없이 "차액 7,000원은 수수료 차이"라고 단정한 오답이
  출력 검증 다섯을 **전부 통과했다**. 인용한 7,000원은 실제로 있는 값이었다
- **잔여 원인** — 방향이 정반대인 건에 같은 원인을 95~100 신뢰도로 냈다
- **장애 로그** — 실재하는 줄을 인용하고 틀린 원인을 냈다

**출처 검증은 "없는 것을 지어냈는가"를 잡지 "있는 것으로 틀린 말을 하는가"를 못 잡는다.**
세 번 같은 벽에 부딪혔으면 그건 우연이 아니라 **이 방식의 한계**다.

그래서 켜지 않는다. 이번에는 "표본이 얇아서"가 아니라 **막을 방법을 찾다 못 찾아서**다.

## 6. AI 실험이 AI와 무관한 구멍을 찾았다

`RACE_CONDITION`의 로그를 못 만든 이유를 파고들다 알게 된 것이다.

```java
} catch (ObjectOptimisticLockingFailureException | OptimisticLockException e) {
    if (++attempts >= MAX_RETRY) {          // 상한을 넘길 때만 예외
        throw new OrderException("STOCK_CONCURRENCY", ...);
    }
}                                            // ← 성공하면 아무것도 안 남는다
```

**재시도가 관측을 지운다.** 경합이 있어도 끝내 성공하면 로그도 지표도 없다.
재고와 월렛 두 곳이 같은 모양이었다.

### 업계가 이미 이름 붙인 문제였다

- 최종 결과만 기록하면 **네 번 만에 성공한 요청이 건강한 요청으로 보이고**, 그 사이 늘어난
  백오프 지연은 응답 시간 안에 묻힌다
- 실제 사고 사례: 두 서비스 사이의 재시도 루프가 **DB 호출을 두 배로 늘렸는데 경보가 하나도
  안 울렸다.** 체크아웃 지연이 40% 늘었는데 에러 로그는 없었다
- 처방도 정해져 있다 — **논리적 호출과 실제 시도를 나눠 센다**

### 고쳤다

```java
} catch (ObjectOptimisticLockingFailureException | OptimisticLockException e) {
    // 흡수하기 <전에> 센다. 성공으로 끝나도 경합이 있었다는 사실은 남아야 한다.
    meterRegistry.counter("stock.deduct.retry", "strategy", "optimistic").increment();
    ...
```

알림 규칙 둘을 더했다(11종 → 13종).

| 규칙 | 무엇을 말하나 |
|---|---|
| `OptimisticLockRetryRising` | 경합이 실제로 있다. **성공률·에러율에는 안 나타나는 것** |
| `OptimisticLockExhausted` | 재시도를 다 썼다. **여기서부터 사용자가 실패를 본다** |

**이게 이번 회차에서 제일 값이 큰 결과다.** 모델을 켜지는 않았는데, 모델을 붙이려고
로그를 모으다 **로그가 없는 자리**를 찾았다. 그 자리는 AI와 아무 상관이 없었다.

## 7. 남는 것

- **표본이 4건이다.** 한 건이 결론을 뒤집었으므로 이 수치는 아직 결정 근거가 못 된다.
  다음에 늘릴 수 있는 것은 `CERT_EXPIRY`(TLS 구성)와 `REPLICATION_LAG`(복제본) 둘이다.
- **모델이 기권하게 만드는 법을 못 찾았다.** 프롬프트에 "판정할 수 없으면 UNKNOWN" 이라고
  적어 뒀는데 지키지 않는다. 잔여 후보에서는 **판정 기준을 코드로 강제**해 막았는데,
  로그는 형태가 자유로워 같은 방법을 쓰기 어렵다.
- **모델을 하나만 봤다.** 크기를 키우면 달라질 수 있지만, 3건으로는 차이를 못 가린다.
- **`CONFIG_DRIFT`는 이 방식으로 영영 못 잡는다.** 로그가 안 남기 때문이다. 잡으려면 로그가
  아니라 **설정 변경 이력과 동작 지표를 대조**해야 한다. 다른 문제다.
- **로그를 얼마나 잘라 줄지 안 쟀다.** 지금은 6,000자에서 앞뒤만 남긴다. 자르는 위치가 답을
  바꿀 수 있는데 그건 안 봤다.


## 8. 표본을 4건에서 12건으로 늘렸다 — 그리고 처음으로 켰다

7절까지의 결론은 "얻는 게 있는데 잃는 것도 있고, **표본이 얇아서** 못 켠다"였다.
한 건이 결론을 뒤집는 실험이었으므로 그 판단은 유보지 결론이 아니었다. 표본을 늘렸다.

### 8-1. 지어내지 않고 실제로 일으켰다

`IncidentLogCaptureTest`(태그 `capture`)가 진짜 장애를 내고 로그를 받아 적는다.

| 표본 | 무엇을 실제로 했나 | 로그를 낸 주체 |
|---|---|---|
| `RACE_CONDITION-01` | 두 커넥션이 같은 두 행을 반대 순서로 `FOR UPDATE` | MySQL — `SQLState 40001, Deadlock found` |
| `RACE_CONDITION-02` | 다른 스레드가 version 을 계속 올려 `WHERE version=N`이 0행을 맞게 함 | 앱 — 영향 행 0건, 재시도 소진 |
| `RACE_CONDITION-03` | 행을 잡고 안 놓은 채 `innodb_lock_wait_timeout=3` | MySQL — `Lock wait timeout exceeded` |
| `DB_TIMEOUT-02` | 풀 크기 1로 두고 커넥션을 물고 안 돌려줌 | HikariCP — `Connection is not available, request timed out` |
| `CERT_EXPIRY-01` | 실제로 만료된 인증서 호스트에 붙음 | JDK — `CertificateExpiredException: NotAfter: ... 2015` |
| `PG_UNAVAILABLE-02` | 죽은 포트로 승인 요청 3회 | JDK — `ClosedChannelException` |
| `PG_UNAVAILABLE-03` | 503 을 내는 서버를 띄워 3회 호출 | 앱 — 응답 503 + 본문 |
| `REPLICATION_LAG-01` | **`SOURCE_DELAY=30`을 건 진짜 MySQL 복제본**에 붙어 조회 | 앱 — 커밋했는데 조회 0건, 35초 뒤 1건 |

`REPLICATION_LAG`는 처음에 **커밋 안 한 트랜잭션으로 흉내냈다가 지웠다.** 증상 로그는 닮았지만
원인이 다르다. 정답이 틀린 표본은 코퍼스를 오염시키고, 그건 이 문서가 내내 비판해 온 잘못이다.
그래서 복제 컨테이너를 띄우고 `CHANGE REPLICATION SOURCE TO ... SOURCE_DELAY=30`으로
진짜 지연을 걸었다. 즉시 조회 0건, 35초 뒤 1건을 확인하고서야 표본으로 썼다.

### 8-2. 내가 정답을 흘리고 있었다

처음 캡처에서 앱 로그에 `"낙관적 락 충돌"`, `"복제 지연 N초"` 라고 **내가 원인을 이름 붙여**
찍고 있었다. 그 상태로 재면 모델은 그 문구를 읽기만 하면 맞히고, 규칙은 내가 지어낸 한국어
문구를 패턴에 갖고 있지 않아 기권한다. **점수 차가 실력 차가 아니라 내가 흘린 정답이 된다.**

앱이 찍는 줄을 관측된 사실까지로 낮췄다 — `낙관적 락 충돌` → `UPDATE 영향 행 0건 (조회 당시 version=N)`,
`복제 지연 N초` → `Seconds_Behind_Source=N`. 진단 명칭은 MySQL·JDK·HikariCP 가 스스로 낸
문장에만 남겼다.

**그러고 다시 쟀더니 결과가 같았다.** 누출은 원인이 아니었다. 이 확인을 안 했으면 결론은
같아도 근거가 없었을 것이다.

### 8-3. 결과 — 규칙과 모델은 정확도가 아니라 틀리는 방식이 다르다

실제 로그 12건, `qwen3:8b`, **4회 반복 전부 동일**:

```
              8-4-1 절에서 라벨을 고치기 전 / 고친 뒤
rule                         맞음  7 · 기권 5 · 틀림 0   →   맞음  7 · 기권 5 · 틀림 0
ollama:qwen3:8b              맞음 11 · 기권 0 · 틀림 1   →   맞음 12 · 기권 0 · 틀림 0
ollama:qwen3:8b+가드          맞음 11 · 기권 0 · 틀림 1   →   맞음 12 · 기권 0 · 틀림 0
rule-first(ollama:qwen3:8b)  맞음 11 · 기권 0 · 틀림 1   →   맞음 12 · 기권 0 · 틀림 0
```

**두 회차를 나눠 돌렸다.** 먼저 고치기 전 라벨로 돌려 저장된 기준선이 재현되는지 봤고
(`rule 7 / model 11 / ruleFirst 11 / wrong 1` 그대로 나왔다), 그다음 라벨을 고쳐 다시 돌렸다.
**한 번에 고치고 돌리면 라벨 변경 효과와 회차 흔들림이 섞인다.**

**규칙은 어느 라벨이든 7이다.** 그 로그에서 기권하기 때문이다. 바뀐 것은 모델 쪽 오답 하나뿐이고,
그것도 실측으로 확인했다. 아래 표는 고친 뒤 값을 기준으로 읽는다.

정확도만 보면 모델이 +5 다. 그런데 **규칙은 한 번도 안 틀린다.** 아는 것만 답하고 모르면
입을 다문다. 모델은 더 많이 맞히는 대신 **틀린 것도 확신 있게 답한다.**

그래서 양자택일이 답이 아니었다. 모델로 통째로 바꾸면 규칙이 이미 확실히 답하던 7건까지
모델의 오답 위험에 노출된다. **규칙을 그대로 두고 규칙이 기권한 5건만 모델에 넘기면**
그 7건은 손대지 않은 채 답을 5건 더 얻는다(`RuleFirstIncidentAnalyzer`).

**12/12 를 성능으로 인용하면 안 된다.** 12건짜리 표본이고 유형당 1~4건이며, 정답을 붙인
사람도 나다. 이번에 그 라벨을 **네 번째로** 고쳤다. 그리고 라벨을 고치면서
`QUEUE_BACKLOG` 사례가 코퍼스에서 사라져 **그 원인은 검증 안 된 상태**가 됐다
(`CONFIG_DRIFT`와 같은 처지다). 건수는 12 그대로인데 **커버리지는 줄었다.**

`app.assist.incident-provider` 기본값을 `rule` → **`rule-first`로 바꿨다.**
이 프로젝트에서 **AI 기능을 기본값으로 켠 첫 사례**다. 앞의 둘(잔여 원인·운영자 서술)은
각각 규칙 대비 개선이 0이어서, 그리고 사람이 고른 비교 표본이 0건이어서 껐다.

모델이 낸 답은 `IncidentDiagnosis.source()`가 `MODEL`로 표시한다. 규칙이 낸 답과 화면에서
같은 무게로 보이면 안 되기 때문이다. 출처를 안 밝히면 `MODEL`로 본다 — **덜 믿는 쪽이 기본값**이어야 한다.

### 8-4. 정답을 정한 게 나라는 것 — 오늘 세 번 틀렸다

이 코퍼스의 "정답"은 무엇을 주입했는지 내가 알고 붙인 라벨이다. 그런데 **오늘 그 라벨을 세 번 틀렸다.**

1. `REPLICATION_LAG` — 커밋 안 한 트랜잭션을 복제 지연이라고 붙였다. 지우고 진짜 복제본으로 다시 만들었다
2. `Lock wait timeout` — `DB_TIMEOUT`으로 붙였다가 `RACE_CONDITION`으로 고쳤다.
   SQLState 가 데드락과 같은 40001 이고, 원인도 "같은 자원을 동시에 고쳐서"다
3. `QUEUE_BACKLOG` — **아직 안 고쳤고, 모델이 맞을 수 있다.** 모델은 4회 내내 이 건을
   `RACE_CONDITION` 이라 답했다. 로그 첫 줄이 "웹훅이 결제보다 먼저 도착"이고, 이건 enum
   정의상 "순서가 꼬였다"(`RACE_CONDITION`)에 더 가깝다. 내가 재시도가 쌓이는 모습만 보고
   `QUEUE_BACKLOG`로 붙였다

3번이 맞다면 모델의 실제 성적은 12/12 이고 유일한 오답은 내 라벨이다. 한동안 **판정하지 않고
남겨 뒀다.** 어느 쪽으로 정하든 내가 정하는 것이라, 모델 답을 보고 고치면 채점 기준을 결과에
맞춰 고치는 게 된다. 잔여 후보에서 기준을 표본 보고 고쳤다가 91~100%가 허수가 됐던 것과 같은
함정이다.

### 8-4-1. 닫았다. 근거로 쓴 것은 로그다

**모델이 뭐라 답했는지를 근거에서 뺐다.** 그 답을 근거로 쓰면 위에서 걱정한 그대로가 된다.
대신 **로그가 무엇을 보여주는지**와 **enum 정의**만 놓고 봤다.

로그는 이렇다.

```
08:29:44  INFO  웹훅이 결제보다 먼저 도착 — 보류 paymentKey=tviva…KhxD3 retry=6
   … retry=7, 8, 9, 10, 11, 12 (5초 간격, 약 35초)
08:30:19  WARN  웹훅 보류 재시도 소진 webhookEventId=3
```

`QUEUE_BACKLOG`는 **"큐가 밀렸다. 에러가 아니라 느려짐과 적체로 나타난다"** 다.
**이 로그에는 적체가 없다.** 웹훅 **한 건**(`webhookEventId=3`, 같은 `paymentKey`)이 재시도를
소진한 것이고, 큐 깊이가 자라는 신호도 다른 건이 밀리는 신호도 없다. `retry=6→12`는 그 한
건의 재시도 횟수지 쌓인 건수가 아니다.

`RACE_CONDITION`은 **"같은 자원을 동시에 고쳐 순서가 꼬였다"** 다. 같은 결제를 두 경로
(웹훅 수신, 승인 확정)가 건드리는데 도착 순서가 뒤집혔다. 정의의 앞부분과 맞는다.
뒤의 예시(데드락·낙관적 락 충돌)와는 다르지만, `QUEUE_BACKLOG`보다 덜 틀린다.

**그래서 `RACE_CONDITION`으로 고쳤다.** 라벨을 잘못 붙였다기보다 **주입이 의도한 것을 안
만들었다고 보는 편이 맞다.** 큐를 밀리게 하려 했는데 나온 것은 순서 역전 한 건이다.

**대가를 적어 둔다. 이건 이득이 아니다.**

- 코퍼스에 `QUEUE_BACKLOG` 사례가 **하나도 안 남는다.** 그 원인은 이제 검증 안 된 상태다
  (`CONFIG_DRIFT`와 같은 처지가 됐다)
- 라벨을 고친 사람도 나다. **모델 성적이 올라가는 방향의 수정**이라는 것을 숨기지 않는다.
  판단해 볼 사람을 위해 위에 로그 전문과 두 enum 정의를 그대로 적어 뒀다

**규칙 점수는 안 바뀐다.** `RuleBasedIncidentAnalyzer`가 보는 신호는 `deadlock`,
`optimisticlock`, `lock wait timeout`, `objectoptimistic` 인데 이 로그에 하나도 없어서
어느 라벨이든 기권한다. **바뀌는 것은 모델 쪽뿐이다.**

### 8-5. 켰다고 적어 놓고 부르는 곳이 없었다

기본값을 `rule-first`로 바꾸고 문서에 "켰다"고 적었다. 나중에 **운영에 투입해도 되는가**를
따져 보다 확인했더니, `diagnose()`를 부르는 곳이 **하나도 없었다.** 어드민 컨트롤러도
배치도 없고 평가 테스트에서만 돌고 있었다.

**구성을 정한 것과 기능이 도는 것은 다른 일이다.** 규칙과 모델을 만들고 실 로그 12건으로
재고 어느 조합을 쓸지까지 정했는데, 운영자가 로그를 넣을 문이 없었다. 그 상태에서 켰다고
적은 것은 사실과 다르다.

`POST /api/v1/admin/incidents/analyze`를 붙였다. 로그를 받아 원인 후보 하나와 근거가 된
인용 한 줄을 돌려주고, 장부나 결제 상태는 건드리지 않는다. 못 고르면 204 다.

거절 조건을 둘 뒀다. 빈 본문은 400, 10만 자를 넘으면 422 다. **잘라서 받지 않는다** —
어디가 잘렸는지 모른 채 받은 진단은 근거를 못 짚는다.

### 8-6. 남는 한계

- **12건도 많지 않다.** 4건보다 낫지만 유형당 1~4건이다. `CONFIG_DRIFT`와 `QUEUE_BACKLOG`는 표본이 0이다
- **모델 하나(`qwen3:8b`)로만 쟀다.** 모델을 바꿨을 때도 성립하는지는 아직 모른다
- **가드가 그 오답을 못 막았다.** 가드 유무로 점수가 같다(11/0/1). 인용은 진짜고 결론만 틀린
  실패는 여전히 안 걸러진다 — 이 문서에서 세 번째로 만나는 같은 벽이다
- 그래서 **확정은 사람이 한다**는 전제를 안 풀었다. 켠 것은 후보 제시지 자동 확정이 아니다

## 9. 켤 때 잰 수치가 나중에도 사실인가

이 프로젝트의 평가는 **시점 측정**이었다. 켤 때 재고 문서에 적고 끝이다. 모델이 바뀌거나
프롬프트가 바뀌거나 ollama 가 올라가면 그 수치는 더 이상 사실이 아닌데, **나빠져도
아무도 모른다.**

업계에서 LLM을 운영에 올린 뒤 가장 어려운 부분으로 꼽는 것이 정확히 이것이다. 좋은 데모를
만드는 것이 아니라 **실제 데이터가 들어온 뒤에도 품질을 유지하는 것**이고, 원인으로
"대부분의 평가가 감으로 이뤄진다"가 지목된다. 출력 몇 개 읽어 보고 배포한다는 뜻이다.

### 절대 수치는 여전히 안 건다

처음에 "수치를 통과 조건으로 걸지 않는다 — 재는 테스트다"라고 적었다. 그 판단은 지금도 맞다.
모델 정확도에 임계를 걸면 **표본이 바뀔 때마다 테스트가 깨진다.**

**대신 회귀를 본다.** 지난번보다 나빠졌으면 그건 표본 탓이 아니라 무언가 바뀐 것이다.

```
rule.correct        7
model.correct      11
ruleFirst.correct  11
ruleFirst.wrong    -1     (틀림은 적을수록 좋으므로 부호를 뒤집어 둔다)
```

기준선을 파일로 남기고 다시 잴 때 견준다. 5% 안쪽으로 떨어지는 것은 모델의 흔들림으로 보고
넘기고, 그 이상은 회귀로 본다.

**기준선이 없으면 만들고 통과시킨다.** 첫 실행에서 깨뜨리면 아무도 안 돌린다.

**바뀐 것이 맞다고 판단하면 사람이 갱신한다**(`EvalBaseline.accept`). 자동으로 갱신하면
매번 오늘 값이 기준이 되어 **천천히 나빠지는 것을 영영 못 잡는다.**

### 수치만 남기면 "나빠졌다"까지만 안다

처음에 수치만 저장했다. 그러면 회귀가 났을 때 **무엇이 바뀌었는지는 매번 처음부터
조사해야 한다.** 모델이 나빠진 것인지, 표본이 바뀐 것인지, 프롬프트를 누가 고친 것인지가
안 남는다.

그래서 무엇이 그 수치를 냈는지도 같이 남긴다.

```json
"context": {
  "model": "ollama:qwen3:8b",
  "samples": "12",
  "corpusFingerprint": "20460f8c"
}
```

`corpusFingerprint`가 있는 이유는 **파일 이름만 봐서는 안에 든 내용이 바뀐 것을 모르기**
때문이다. 표본을 고쳐 놓고 모델이 나빠졌다고 읽으면 엉뚱한 데를 파게 된다.

### 잡히는지 확인했다

기준선을 "14b 로 12건 맞혔다"로 바꿔 두고 8b 로 다시 쟀다.

```
ruleFirst.correct: 12.000 → 11.000
(바뀜) model: ollama:qwen3:14b → ollama:qwen3:8b
```

**"나빠졌다"가 아니라 "모델이 바뀌어서 나빠졌다"가 나온다.**

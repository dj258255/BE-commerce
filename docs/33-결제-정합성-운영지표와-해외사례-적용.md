# 33. 결제 정합성 운영 지표와 해외 사례 적용

## 목적

결제 시스템에서 `정합하다`는 말은 차변과 대변의 합이 맞는다는 뜻만으로 부족하다.
외부 PG·은행·웹훅·정산 파일·내부 원장이 서로 다른 시각과 형식으로 움직이므로,
돈이 어디에 있고 무엇이 아직 확인되지 않았는지를 계속 설명할 수 있어야 한다.

해외 결제 플랫폼의 공개 자료를 참고하되, 규모를 그대로 흉내 내지 않는다.
이 저장소에서 실제로 검증한 것, 현재 코드에 있는 것, 외부 계약 없이는 검증할 수 없는 것을 분리한다.

## 해외 사례에서 가져온 기준

| 사례 | 가져온 기준 | pay에 적용한 범위 |
|---|---|---|
| Stripe Ledger | 불변 원장, 자금 이동의 completeness·timeliness·accuracy·explainability | 복식부기 원장, 차변=대변, 승인·취소·분쟁·지급 역분개, 대사 pending/oldest age |
| Adyen architecture | 결제 요청은 availability·latency, 회계는 accuracy·reliability, 데이터 처리는 throughput을 우선 | PG 호출 상한·UNKNOWN 복구·원장·정산 배치를 같은 지표로 섞지 않음 |
| Adyen reconciliation | 거래·회계·지급을 서로 다른 reconciliation 대상으로 구분 | 승인/취소, 정산, 지급 확정을 별도 사건과 분개로 유지 |
| Uber settlement accounting | PSP 이벤트와 내부 이벤트를 결정적 reference로 연결하고 실패 이벤트를 재처리 | 거래 reference, 중복 파일 업로드 멱등, 실패 건 재시도·DLT 경계 |
| Stripe idempotency | 불확실한 네트워크 실패는 안전한 재시도와 멱등키로 수렴 | 승인 재시도 금지, 조회 재시도 허용, 지수 백오프와 지터 |
| Adyen webhooks | ACK·원본 저장·비동기 처리·retry/replay를 분리 | 웹훅 원본 보존, 선행 웹훅 보류, pending retry, 서명 없는 이벤트는 조회 재검증 |
| Uber retry storm | 재시도 횟수보다 오류 원인·호출 깊이·retry budget을 함께 판단 | 조회 retry 횟수·소진 횟수 계측, 다단 호출 error ownership은 미도입 |
| Modern Treasury tentative reconciliation | 외부 pending과 최종 posted를 구분하고 게시 후 다시 대사 | 현재 `PENDING`은 사람 예외 큐로 한정, tentative/posted는 별도 검토 |
| Adyen orchestration | 장애 우회가 데이터·계약·운영 복잡성을 없애지 않고 이동시킴 | 두 PG failover는 provider 계약 전까지 미활성 |
| Uber hot entity | 강한 일관성을 유지하면서 hot account의 직렬화 비용을 처리량 문제로 다룸 | append-only 원장 유지, 스냅샷·직렬화 batch는 병목 실측 후 판단 |
| Square webhooks | 중복·순서 역전·재전송을 정상 동작으로 보고 빠른 ACK와 event id 멱등을 요구 | 원본 저장·event id 멱등·비동기 처리·재처리 경계 |
| Modern Treasury ledger | 원장에 불변성·멱등성·동시성 제어를 먼저 두고 지급·대사를 그 위에 올림 | 이미 구현한 append-only·유니크 source·차대 균형을 원장 기준으로 유지 |
| Modern Treasury reconciliation | N:M 대사는 결정적 규칙·수학으로 풀 영역과 AI 후보 영역을 분리 | 자동 확정은 규칙과 검증된 표본이 있을 때만 검토 |

## 이미 닫힌 구현

- 차변 합계와 대변 합계가 다르면 원장 거래를 만들 수 없다.
- 승인·부분취소·차지백 패소·정산 지급을 원거래 수정이 아닌 별도 분개로 남긴다.
- 원장 원천 키와 사건 순번을 DB 유니크로 묶어 중복 이벤트를 흡수한다.
- `UNKNOWN`은 실패가 아니라 결과 미확정으로 남기고 PG 조회로 수렴시킨다.
- 승인에는 자동 재시도를 붙이지 않고, 안전한 조회에만 bounded retry와 exponential backoff+jitter를 적용한다.
- PG 호출 상한 초과는 PG에 닿지 않았음이 보장되므로 확정 실패로 처리하고, PG 호출 예외·서킷 오픈은 UNKNOWN으로 처리한다.
- 웹훅은 페이로드의 상태를 진실로 쓰지 않고 원본을 저장한 뒤 `paymentKey` 조회로 재검증한다.
- 대사에는 PENDING 건수와 가장 오래된 PENDING의 age를 노출한다.
- 분쟁과 지급 보류는 차지백 식별자·지급 상태·보류 사유를 별도로 보존한다.

## 추가할 운영 지표

다음 지표는 아직 실서비스 SLO가 아니다. 로컬 장애·합성 데이터에서 기준선을 만들고,
실 트래픽이 생기면 다시 보정해야 한다.

| 축 | 지표 | 의미 | 현재 상태 |
|---|---|---|---|
| completeness | 원장에 있어야 할 사건 중 실제 분개된 비율 | 누락 탐지 | 이벤트·대사 테스트로 부분 검증 |
| timeliness | 승인/취소/지급 사건의 원장 반영 지연 | 늦은 반영 탐지 | 이벤트·웹훅 로그로 확인, 통합 SLO는 미정 |
| accuracy | 차변=대변, 내부=외부, 정산=지급 수식 위반 건수·금액 | 금액 오류 탐지 | 원장 불변식·대사 결과로 검증 |
| explainability | 미해결 금액 중 원인·출처·다음 행동이 없는 금액 | 운영자 복원 가능성 | 대사 근거와 missing source를 저장 |
| backlog | PENDING count, oldest age, DLQ count, webhook retry age | 복구 지연 | PENDING count/oldest age 구현, DLQ·webhook 상세 지표 확장 대상 |
| retry safety | 승인 재시도 수, 조회 재시도 수, retry exhaustion | 이중 결제·장애 증폭 탐지 | 승인 1회·조회 3회 bounded 테스트 |

## 남은 구현·실험

### 1. 웹훅 replay와 DLQ 운영 화면

현재 웹훅 보류 재시도와 일반 이벤트 DLT는 따로 존재한다. 다음 단계는 운영자가
`eventId`, 마지막 오류, retry count, oldest age를 보고 한 건만 재처리할 수 있게 하는 것이다.
재처리 전에 같은 이벤트가 이미 적용됐는지 확인하고, 재처리 결과를 감사 로그에 남긴다.

완료 기준:

- 같은 이벤트 replay 후 상태·원장·대사 결과가 변하지 않는다.
- poison event는 일반 큐를 막지 않는다.
- replay 전후의 금액·분개 수·상태를 비교할 수 있다.

### 2. 지급 reconciliation의 reference와 보류

정산 금액과 실제 지급 금액은 같지 않을 수 있다. 수수료·환불·차지백·reserve·조정액을
각 사건으로 남기고 다음 식을 검증한다.

```text
payout = settlements - refunds - chargebacks - fees - reserves + adjustments
```

지급 reference와 settlement id의 연결이 없는 지급은 `UNMATCHED_PAYOUT`으로 두고,
`PAID_OUT`으로 확정하지 않는다.

### 3. retry storm 실험

PG 장애 시 100개의 요청이 같은 순간 재시도하지 않는지 확인한다.
도착률·PG 지연·동시 사용자·backoff·jitter seed를 고정하고 다음을 측정한다.

- PG로 실제 나간 조회 수
- retry별 간격 분포

재시도 계측은 `payment.pg.query.retry`와 `payment.pg.query.retry.exhausted`로 추가했다. 실험에서
재시도 성공률만 보고 결론내리지 않고 정상 API p95, connection wait, CPU saturation, UNKNOWN age를
함께 비교한다. 상세한 가설·조건·완료 기준은 [34 문서](34-결제-재시도와-retry-storm-실험.md)에 둔다.

### 4. pending/posted와 오케스트레이션

현재 대사의 `PENDING`은 사람이 조사할 예외이지, 외부 금융 거래의 provisional 상태를 뜻하지 않는다.
실제 posted reference가 생길 때만 잠정 대사 모델을 추가한다. 두 PG도 routing abstraction만으로
완료로 표시하지 않고, UNKNOWN failover 금지·원 provider 환불·정산 reference 연결을 계약 테스트로
확인한다. 각각 [35 문서](35-대사의-pending과-posted-경계.md), [36 문서](36-결제-오케스트레이션의-복잡성-이동-판단.md)에 둔다.

### 5. 원장 hot entity

현재 원장은 append-only와 차대 균형을 생성 시점에 강제한다. 잔액 스냅샷은 조회 비용만 보고 추가하지
않는다. 일반 계정과 hot 계정의 lock wait, p95/p99, throughput, 원장 재생성 잔액을 비교한 뒤 도입
기준을 정한다. [37 문서](37-결제-원장의-hot-entity와-처리량.md)에 실험 조건을 남겼다.
- circuit open 이후 호출 수
- UNKNOWN age
- 정상 API의 p95 latency와 connection wait

### 4. 다통화·환율·반올림

통화별 원장 분리, 환율 source와 effective time, 반올림 잔액 귀속,
환불 시 최초 환율 사용 여부를 별도 결정해야 한다. 실 카드사 계약이 없으므로
환율 정책을 확정했다고 쓰지 않고, 정책 선택과 합성 데이터 검증까지만 닫는다.

### 5. 두 PG 라우팅

현재 기본값은 꺼져 있다. 켜는 조건은 다음 셋을 모두 만족해야 한다.

- 두 PG의 실계약과 취소·조회·웹훅 계약이 존재한다.
- PG·결제수단·지역별 승인율, p95 latency, 수수료를 같은 조건에서 측정한다.
- timeout·UNKNOWN을 다른 PG로 넘겨 이중 승인을 만들지 않는 것을 실 PG로 확인한다.

## 이 문서의 정합성 규칙

- 실서비스 SLO와 로컬 합성 실험 수치를 섞지 않는다.
- 외부 기술 블로그의 규모 수치를 pay의 성능으로 인용하지 않는다.
- 구현된 기능과 계약 테스트가 필요한 기능을 문장으로 분리한다.
- 실패한 실험도 가설·조건·관측·배제한 원인·다음 행동을 남긴다.

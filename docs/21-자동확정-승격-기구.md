# 21. 자동확정 승격 조건과 측정 기구

## 0. 무엇이 문제였나

자동 확정(사람 없이 대사를 종결하는 것)의 조건을 문서에 셋으로 적어 뒀다.

1. 증거가 결정적일 것
2. 금액이 임계 미만일 것
3. **그 유형의 실측 오류율이 선언한 한도 안일 것**

그런데 3번을 **계산하는 코드가 없었다.** 조건은 글로만 있고 재는 기구가 없으면,
승격은 판단이 아니라 인상이 된다.

## 1. 있던 것과 없던 것

승인 여부를 재는 장치는 있었다. `ResidualAcceptanceRecorder`가 확정 이벤트를 받아
제안과 대조해 `accepted / rejected / abstained`를 센다.

**그런데 프로메테우스 카운터다.** 둘이 막혔다.

- **재시작하면 사라진다.** 자동화 권한을 며칠짜리 메모리 값으로 정할 수 없다
- **태그가 `outcome`·`blind` 뿐이라 원인 유형별로 안 갈린다.** 조건이 "그 유형의"인데
  유형이 없다

## 2. 행으로 남긴다

`suggestion_outcomes` 테이블을 만들고 확정마다 한 행을 쓴다(V35).

```
recon_result_id · suggested_cause · chosen_cause · outcome · blind · resolved_at
```

**`blind`를 함께 남기는 이유**: 제안을 보여준 뒤 고르게 하면 앵커링이 생겨 일치율이
올라간다. 섞어서 세면 **모델이 사람을 설득한 결과를 모델의 정확도로 읽게 된다.**

같은 대사 건이 두 번 확정되지 않으므로 `recon_result_id`에 유니크 제약을 걸었다.
집계에 실패해도 확정은 이미 끝났으므로 저장 실패는 로그만 남기고 삼킨다 — 여기서 던지면
되돌릴 것도 없는데 확정 흐름만 시끄러워진다.

## 3. 오류율을 계산한다

`AutomationReadiness`가 유형별로 판정한다.

```
표본 = accepted + rejected      (기권은 맞고 틀림이 아니라 분모에서 뺀다)
오류율 = rejected / 표본
```

**가린 표본만 센다.** 보여준 뒤 고른 것은 앵커링이 섞여 승격 판단에 못 쓴다.

기본값은 최소 표본 30건, 허용 오류율 5% 다. 둘 다 설정으로 열어 뒀다.

### 이 서비스는 켜지 않는다

판정만 낸다. 실제로 올리는 것은 **코드 변경이어야 한다.** 지표가 좋아졌다고 권한이
자동으로 올라가면 되돌릴 자리가 없다. 그리고 조건 셋 중 여기서 보는 것은 둘뿐이다 —
증거가 결정적인지와 금액이 임계 미만인지는 건별이라 확정 화면에서 따로 본다.

## 4. 왜 이게 사다리의 2단인가

업계에서 자동 조치는 **`알림 → 승인 후 실행 → 자동 실행`** 3단으로 올라간다.
신뢰가 쌓이는 만큼 칸을 올린다.

이 프로젝트는 1단에 있었고 3단의 조건을 적어 뒀는데, **2단이 3단의 데이터를 만든다는 것을
놓치고 있었다.** 사람이 승인한 기록이 유형별로 쌓여야 오류율이 생기고, 그게 없으면
3단은 영영 못 켠다. 조건을 적어 두는 것과 그 조건을 만족시킬 경로를 만드는 것은 다른 일이다.

## 5. 남는 것

- **표본이 0건이다.** 실제 대사 확정이 없다. 이 기구는 데이터가 쌓이기 시작할 때부터 값이 난다
- 증거·금액 조건은 여전히 코드로 안 재고 있다. 건별이라 확정 시점에 봐야 하는데 그 자리를 안 만들었다
- 자동 확정 자체는 **아무것도 안 켰다.** 이 문서는 켤 수 있는지 재는 방법을 만든 기록이다

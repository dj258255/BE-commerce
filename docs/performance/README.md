# 성능 리포트: 방법론과 실측

## 재현 — `./gradlew -p commerce bench`

아래 수치들은 전부 **한 대의 맥북에서 손으로** 잰 값이다. 그래서 한 번 틀렸었다.
9절의 용량 수치는 닫힌 루프로 재서 과소평가했고, 열린 루프로 다시 재서 뒤집었다.
그 외에도 좀비 JVM으로 대조군이 오염된 적, DB 누적으로 회차 비교가 무의미했던 적이 있다.

`bench` 태스크는 그 절차를 스크립트로 고정한 것이다. 하는 일은 성능 개선이 아니라
**측정을 못 믿게 만드는 것들을 막는 것**이다.

| 과거에 겪은 문제 | 스크립트가 막는 방법 |
|---|---|
| 회차 사이 DB 누적으로 비교 불가 | 매 회차 볼륨 삭제(외부 모드는 스키마 드롭) |
| `pkill`이 래퍼만 죽여 좀비 JVM 잔존 | 포트를 잡은 PID 를 찾아 직접 종료하고, 종료 후 포트가 빈 것까지 확인 |
| MySQL이 "떴는데" 아직 못 쓰는 상태 | 앱이 쓰는 계정으로 질의가 되는지 확인(초기화 완료 신호) |
| 인프라가 죽었는데 앱 문제로 오인 | 헬스 실패 시 Docker·컨테이너 생존을 먼저 확인해 원인을 구분 |
| 맥북 수치를 운영 근거로 사용 | 환경(CPU·코어·메모리·JVM·커밋)을 리포트에 박아 넣음 |

```bash
./gradlew -p commerce bench -Pprofile=smoke     # 배관 검증(1분)
./gradlew -p commerce bench                     # capacity
./gradlew -p commerce bench -Pprofile=all
```

`smoke`는 성능을 재지 않는다. 본 측정이 20분 가까이 걸리는데 배관 하나가 어긋나 있으면
그 20분이 통째로 날아가므로, 그 전에 1분으로 확인하는 용도다.


> 카카오페이 "온라인 결제 2.5배 성능 개선기"의 프레임을 따른다:
> **목표 산정 → 현재 한계 측정 → 병목 계측 → 개선(하나씩) → 전후 수치**.
> "측정 없이는 개선 없다."

## 1. 재고 차감 락 3종 비교 (실측 완료)

동시성 제어 전략은 실측으로 골랐다. 안전 불변식은 `StockLockComparisonTest`(H2 인메모리,
Docker 불필요·CI 결정적)가 매번 검사하고, 성능 수치는 `StockLockComparisonMySqlTest`(Testcontainers
MySQL 8.4·InnoDB)가 낸다. 인메모리는 왕복이 사실상 공짜라 재시도 기반 전략에 유리하게 기울기 때문이다.

**실 MySQL 8.4(InnoDB) · 재고 20 · 워밍업 후 5회 중앙값**

| 전략 | 초과판매 | 완판 | 30스레드 | 150스레드 |
|---|---|---|---|---|
| **조건부 UPDATE** | 0 | 20/20 | **40ms** | **79ms** |
| 비관적 락 | 0 | 20/20 | 75ms | — |
| 낙관적 락 | 0 | 20/20 | 151ms | 429ms |

**결론**: 단일 재고 행 차감은 조건부 UPDATE가 최속이자 최저비용 → 기본 전략으로 채택([ADR-004](../adr/ADR-004-stock-deduction-locking.md)).
낙관적 락은 충돌마다 조회·갱신을 다시 왕복해 실 DB에서 가장 느리고, 고경합(150스레드)에서 조건부의 5.4배까지 벌어진다(hot row 부적합).

재현:
```bash
JAVA_HOME=<jdk21> ./gradlew -p commerce test --tests "com.beomsu.becommerce.order.StockLockComparisonMySqlTest"
```

## 2. 엔드투엔드 부하테스트 (k6)

`k6/checkout-load.js`가 주문 생성 → 결제 승인 흐름을 실제 사용자 시나리오로 두들긴다.
(FakePgClient가 승인을 성공 처리하므로 실제 PG 키 없이 부하를 준다.)

### 실행

```bash
# 1) 인프라 + 앱
docker compose up -d              # MySQL 8.4 + Redis 7.4
./gradlew -p commerce bootRun                 # (스키마·시드 준비 후)
# 2) 부하
k6 run k6/checkout-load.js
```

### 개선 스토리 프레임 (리포트 작성 시)

1. **목표 산정 근거**: 예) "선착순 이벤트 1만 명 → 순간 목표 300 TPS"
2. **현재 한계 측정**: k6 ramping-vus로 TPS가 꺾이는 지점·p99·오류율
3. **병목 계측**: slow query 로그, `EXPLAIN`, 커넥션 풀 사용률, APM
4. **개선(하나씩, 재측정)**:
   - HikariCP 풀 튜닝 (데드락 회피 공식 `pool ≥ Tn×(Cm−1)+1`)
   - 조회 쿼리 인덱스/커버링 인덱스 (`Using Where` → `Using Index`)
   - 캐싱 (TTL 지터·널 오브젝트)
   - 선착순은 Redis Sorted Set 대기열로 DB 유입 제어
5. **전후 수치 대비** + 남은 한계

### thresholds (성능 회귀 게이트)

`checkout-load.js`는 `p95<300ms`, `p99<800ms`, 오류율 `<1%`를 임계치로 두어, 위반 시 k6가
실패로 종료한다. PR마다 소규모 부하로 성능 회귀를 커밋 단위로 잡을 수 있다.

## 3. 관측성 (Phase 6에서 대시보드화)

핵심 패널: 결제 성공률(SLO), p99 레이턴시, HikariCP 풀 사용률, 서킷브레이커 상태, Kafka lag.
Actuator + Micrometer → Prometheus → Grafana. (Phase 6 참조)

## 메모

- 락 비교는 처음 H2 인메모리로 쟀다가 실 MySQL 8.4(Testcontainers)로 다시 쟀고, **전략 간 상대 우열이 뒤집혔다**. 인메모리에서는 낙관적(17ms)이 비관적(32ms)보다 빨랐지만 실 InnoDB에서는 비관적 75ms < 낙관적 151ms다. 낙관적 락이 충돌마다 하는 조회·갱신 왕복이 인메모리에서는 거의 공짜였기 때문이다. 위 표는 실 MySQL 수치다.
- H2 비교(`StockLockComparisonTest`)는 CI에서 결정적으로 도는 경량 스위트로 남겨 뒀다. 실 MySQL 비교(`StockLockComparisonMySqlTest`)는 Docker가 필요해 CI 기본 스위트에서는 제외한다.
- 락 비교는 raw JDBC로 SQL 패턴만 격리해 잰다. 서비스 계층(JPA·트랜잭션) 포함 수치가 아니라 **전략 간 상대 비교**다.

## 4. 확장 후 엔드투엔드 재측정 (인증 포함)

확장 모듈(point·subscription·wallet·fraud·audit·receipt·va)까지 스키마에 얹고, 인증(ROLE_USER)이
걸린 상태로 k6 재실행:

- 50 VU, 오류율 0%, **p95 567ms · p99 712ms** (min 110ms)

무인증 초기 측정(min ~3.5ms, p95 96ms)과 비교하면 **요청당 최소 지연이 ~110ms로 상승**했다.
원인은 **HTTP Basic + BCrypt**다. 무상태 Basic 인증은 요청마다 비밀번호를 BCrypt로 재검증하는데,
BCrypt는 의도적으로 느리다(브루트포스 방어). 즉 이 지연은 앱 로직이 아니라 **인증 방식의 비용**이다.

실서비스는 이를 **토큰/세션**으로 해소한다. 로그인 때 한 번만 검증하고 이후엔 서명 검증(JWT)이나
세션 조회로 요청당 재해싱을 피한다. 부하테스트가 "무엇이 병목인지"를 정확히 짚어준 사례다.

## 5. 병목 제거: JWT 전환 후 재측정 (실측 완료)

4절에서 짚은 병목(요청당 BCrypt)을 실제로 제거했다. 인증을 **HTTP Basic + 요청당 BCrypt →
JWT Bearer**(로그인 시 BCrypt 1회, 이후 서명 검증만)로 교체하고, **같은 머신·같은 부하 조건**
(50 VU, load avg ~6)에서 `k6/checkout-load.js`를 재실행했다.

| 지표 | HTTP Basic + BCrypt (4절) | **JWT (5절)** | 개선 |
|---|---|---|---|
| min | 110ms *(BCrypt 바닥)* | **4.17ms** | ~26배 |
| p95 | 567.84ms | **37.09ms** | ~15배 |
| p99 | 712.27ms | **58.47ms** | ~12배 |
| 오류율 | 0% | 0% | — |
| 처리 | — | 4,071 req, 50 req/s | — |

**요청당 ~110ms의 BCrypt 바닥이 사라졌다.** 한 번의 체크아웃이 주문+승인으로 인증을 두 번
타므로 개선폭이 특히 컸다. 병목이 **앱 로직이 아니라 인증 방식의 비용**이었음을 전후 수치가
확증한다. "측정 → 병목 지목 → 개선 → 재측정"의 한 사이클을 닫았다.

재현:
```bash
docker compose up -d && ./gradlew -p commerce bootRun          # 스키마·시드 자동 준비(V1~V4)
USER_PASSWORD=user-local-only k6 run k6/checkout-load.js
```

## 6. 카오스 테스트: 실제 네트워크 장애로 복원력을 검증한다

성능이 "빠른가"라면, 복원력은 "장애가 나도 정합성이 깨지지 않는가"다. 서킷브레이커·타임아웃=UNKNOWN·
멱등 같은 복원력 설계를 **코드로 주장만** 하지 않고 **장애를 주입해** 확인한다. 두 층위로 나눴다.

### (1) 서킷브레이커 단위 테스트: 컨테이너 없이 결정적으로

`ResilientPgClientTest`는 장애를 주입하는 `PgClient` 더블을 `new ResilientPgClient(faulty)`로 감싸,
resilience4j 데코레이터의 동작을 순수 단위로 못박는다(부팅·컨테이너 없음, 기본 스위트 포함).

- **승인은 재시도하지 않는다**: faulty delegate가 예외를 던져도 delegate를 **딱 1번** 호출하고
  결과는 `TIMEOUT`(=UNKNOWN). 멱등키 없는 승인 재시도는 이중결제라서, 실패로 단정하지 않고 미확정으로 돌린다.
- **서킷 오픈 폴백**: 반복 실패로 서킷이 OPEN되면, 이후 승인은 delegate를 **아예 호출하지 않고**
  즉시 `TIMEOUT`으로 폴백한다(호출 횟수가 더 늘지 않음을 검증 → PG 장애가 우리 스레드를 고갈시키지 않음).
- **조회는 재시도한다**: 읽기라 안전하므로 몇 번 실패 후 성공하면 재시도로 흡수한다(호출 > 1).
  단, 재시도는 **무한이 아니라** maxAttempts(3)에서 멈추고 예외를 전파해 복구 배치가 다음 주기에 다시 잡는다.

### (2) Toxiproxy 네트워크 카오스: 실제 장애를 주입해 정합성 확인

`MySqlChaosTest`(`@Tag("chaos")`)는 MySQL 컨테이너와 Toxiproxy 컨테이너를 같은 네트워크에 띄우고
앱을 부팅한다. 앱의 `spring.datasource.url`을 **Toxiproxy 프록시 주소**로 주입해 모든 DB 트래픽이
장애 구간을 통과하게 만든 뒤:

1. 정상 상태에서 체크아웃(주문 생성 → 승인) 1건 성공.
2. `latency(UPSTREAM, 5s)` toxic 주입. JDBC `socketTimeout`(3s)·Hikari `connectionTimeout`(2s)을
   짧게 둬, 장애가 **무한 hang이 아니라 타임아웃 예외(5xx)로 깨끗하게** 끝나는지(부분 커밋 없음) 확인.
3. toxic 제거 후 **같은 Idempotency-Key로 재시도** → 첫 응답이 그대로 재반환되어
   **이중 결제/이중 차감이 없음**(멱등이 장애를 건너 생존)을 확인.

### 실행법과 기본 스위트 제외 이유

```bash
./gradlew -p commerce test        # 기본: 카오스 제외(excludeTags 'chaos'), 컨테이너 안 뜸 — 빠르고 결정적
./gradlew -p commerce chaosTest   # 카오스만: 컨테이너 2개 + 부트 필요, 전용 환경에서 수동 실행
```

카오스 테스트는 컨테이너 2개 + 앱 부팅이 필요해 무겁고, 머신에 따라 부팅이 불안정하다. CI 기본
스위트의 **결정성과 속도**를 지키려고 `@Tag("chaos")`로 분리해 기본 `test`에서 제외하고, 네트워크가
준비된 전용 환경에서만 `chaosTest`로 돌린다.

## 7. 폭주 유입 제어: 스파이크 실측 (실측 완료 — **트래픽 모델 한계는 9절에서 정정**)

> **9절 먼저 읽을 것.** 이 절의 실측은 **계정 1개**로 돌렸다. per-user 한도가 5/s라 그 계정은
> 무슨 짓을 해도 초당 5건까지만 통과한다. 즉 아래 "제어 있음"의 97.5% 거절은 **per-user 한 층이**
> 만든 것이고, 전역 100/s 층은 요청이 도달한 적조차 없다. 숫자 자체는 정확하지만 비교 대상이
> "무제한 vs 한 사람당 5/s"라 **유입 제어 전체의 효과로 읽으면 안 된다**. 다계정으로 다시 재니
> 결론이 상당히 달라졌다(9절).

순간 트래픽 폭증(선착순 등)에 대한 유입 제어를 넣고, **같은 스파이크(0→150 VU 10초 급증)**를
제어 전/후로 두 번 실측했다(`k6/spike-test.js`, `app.ratelimit.enabled`로 전환).

제어 3층: ① Redis 분산 rate limiter(사용자별 5/s + 전역 100/s → 초과분 `429 + Retry-After`)
② 한정판 상품 대기열 게이트 강제(입장권 없으면 `429 QUEUE_PASS_REQUIRED`)
③ 빠른 실패 풀 설정(Hikari connection-timeout 3s·pool 20, Tomcat threads 100, 매달리지 않고 실패).

| 지표 | 제어 없음 | **제어 있음** |
|---|---|---|
| 유입 | 304 req/s, **전량 DB까지 처리** | 398 req/s 중 **97.5%를 429로 거절** |
| DB 도달 요청 | 15,445건 (100%) | ~510건 (2.5%) |
| 성공 요청 p95 | 737.81ms | **52.01ms (14배↓)** |
| 성공 요청 max | 1.48s | 105ms |
| 5xx | 0% | 0.55% (아래) |

**해석**: 제어가 없으면 폭주가 전량 DB로 흘러 정상 요청까지 같이 느려진다(p95 738ms, 평시 37ms의
20배). 제어를 켜면 감당 못 할 요청을 바깥 층에서 싸게(429) 거절하고, **통과한 요청은 평시에 가까운
속도(p95 52ms)를 유지**한다. "모두가 느려지는 것"에서 "일부는 기다리고 나머지는 정상"으로 바뀐다.

**부수 발견 → 해소**: 제어 ON에서만 5xx 113건(0.55%)이 났다. 고정 윈도우 경계에 통과 요청이
버스트로 몰리며 `event_publication`(outbox) INSERT가 MySQL 데드락(1213). 제어가 없을 땐 지연이
자연 직렬화해 0건이었다. **후속 조치**: 데드락은 MySQL이 "재시작하라"고 명시하는 transient
실패라, 모든 변경 API를 감싸는 `IdempotencyService`에 재시도(최대 3회, 지터 백오프)를 넣었다.
타임아웃 무재시도 규칙과 충돌하지 않는 이유는 이렇다. 타임아웃은 결과 미상(UNKNOWN)이지만 데드락은
**전체 롤백이 확정된 실패**라 재실행이 안전하다. 재실측: 5xx **0.00%**(이번 런은 데드락 자체가
확률적으로 0건이고, 재시도는 단위 테스트 3종으로 검증된 안전망이다), `idempotency.deadlock.retry`
카운터로 발동을 관측한다.

재현:
```bash
./gradlew -p commerce bootRun --args='--app.ratelimit.enabled=false'   # 전
USER_PASSWORD=user-local-only k6 run k6/spike-test.js
./gradlew -p commerce bootRun                                           # 후(기본 on)
USER_PASSWORD=user-local-only k6 run k6/spike-test.js
```

## 8. 비밀번호 해싱: BCrypt → Argon2id 실측 (실측 완료)

느린 것이 목적인 연산이라 **"빨라졌다"가 개선이 아니다.** 잰 이유는 두 가지다. ① 로그인 응답에 얼마가 붙는지 ② `/auth/login`의 DoS 표면이 얼마나 커지는지.

**로컬(Apple Silicon), 워밍업 후 7회 중앙값** (`PasswordEncoderBenchTest`)

| | 소요 | 메모리 |
|---|---|---|
| BCrypt (strength 10) | 87ms | ~4KB |
| **Argon2id (19MiB·t=2·p=1)** | **32ms** | **19MiB** |

**예상과 반대로 더 강한 쪽이 더 빨랐다.** BCrypt의 비용은 반복 횟수에서 나오고 Argon2id는 상당 부분을 메모리에서 가져오기 때문이다. **시간을 덜 쓰면서 공격자에게는 더 비싸다** — 메모리 하드의 목적이 그것이다.

### 대신 메모리를 쓴다 — 이 교체는 DoS 표면을 키운다

로그인 1건마다 19MiB를 잡는다.

```
동시 로그인 100건 → 순간 약 1.9GB
```

`/auth/login`은 **인증 없이 누구나 부를 수 있는 경로**다. 이전에는 CPU만 태웠지만 이제 메모리도 잡는다. 즉 **알고리즘을 강화하면서 그 경로의 DoS 표면은 오히려 커졌다.**

그래서 이 교체는 **유입 제어가 먼저 있었기 때문에** 안전한 변경이 됐다. `RateLimitFilter`가 `/auth/login`·`/members/signup`을 IP 기준으로 막는다(사용자별 제한은 principal이 없어 이 경로를 그냥 통과한다). 유입 제한이 없었다면 파라미터를 더 낮게 잡거나 교체를 미뤘어야 했다.

**함께 볼 것**: 3절 JWT 전환은 **요청마다** 하던 BCrypt 재검증(min ~110ms)을 없앤 것이다. 로그인 1회의 해싱은 **비밀번호를 실제로 대조하는 자리라 없앨 수 없다.** 같은 비용이 성능에서는 제거 대상이고 보안에서는 유지 대상이다.

### 이관 진행은 지표로 본다

해시 이관은 **끝을 코드로 강제할 수 없다.** 원문 비밀번호가 로그인 순간에만 존재하므로, 로그인하지 않는 계정은 옛 해시로 남는다. 그래서 남은 수를 게이지로 올렸다.

```
password_hash_legacy_count   현재 알고리즘으로 안 옮겨진 해시 수
```

**0이 되면 레거시 인코더를 제거할 수 있다.** 그 시점이 이관의 진짜 종료이고, 판정을 사람의 기억이 아니라 이 값으로 한다. 7일 이상 남아 있으면 `PasswordHashMigrationStalled`(severity: info)가 뜬다 — 경보가 아니라 **언제 끝나는지 보이게** 하는 용도다.

재현:
```bash
JAVA_HOME=<jdk21> ./gradlew -p commerce test --tests "*PasswordEncoderBenchTest" -i
```

상세 결정과 트레이드오프는 [ADR-009](../adr/ADR-009-password-hashing-and-migration-path.md).

## 9. 유입 제어 재실측: 다계정으로 전역 층을 깨우다 (실측 완료)

### 왜 다시 쟀나 — 산수가 안 맞았다

7절 실험은 계정 1개에 150 VU를 던졌다. per-user 한도가 5/s이므로 그 계정이 통과시킬 수 있는 양은
경로 2개(`/orders`, `/payments/confirm`)를 합쳐 **최대 10/s**다. 전역 상한은 100/s다.
**전역 층까지 요청이 도달할 수 없는 구조**였다. 1차 실행의 DB 도달량이 10.2 req/s로 나온 게
그 산술적 증거다 — 정확히 `5/s × 2경로`다.

층을 둘 만들어놓고 바깥 층은 한 번도 부하를 받은 적이 없는 채로 "유입 제어를 검증했다"고
적어둔 상태였다. 전역 층을 깨우려면 `계정 수 × 5/s > 100/s`, 즉 **계정이 21개 이상** 필요하다.
`k6/spike-multi-account.js`는 40계정(제공량 200/s)을 쓴다.

### 어느 층이 잘랐는지 구분할 수 있게 먼저 고쳤다

기존 429는 본문·헤더가 모두 같아서 per-user가 잘랐는지 전역이 잘랐는지 알 수 없었다.
실험이 결론을 못 낼 뿐 아니라, **운영에서도 대응이 정반대인 두 상황을 구분할 수 없다**:
`user`는 그 클라이언트만 물러나면 풀리고(재시도가 유효), `global`은 시스템이 포화라 그 클라이언트가
얌전해져도 안 풀린다(증설·원인 규명이 필요). `RateLimitFilter`가 `X-RateLimit-Scope: user|ip|global`을
붙이도록 바꾸고, k6가 이 헤더로 거절을 귀속한다.

### 결과 (200 VU / 600 VU × 제어 ON/OFF, 40계정)

**매 실행 전 DB를 `docker compose down -v`로 초기화했다.** 처음엔 초기화 없이 돌렸는데 회차마다
결과가 달라졌다(600 VU·제어 ON에서 처리량 75/s → 93/s, p95 2.98s → 4.92s). 원인은 부하가 아니라
누적된 데이터였다(→ 10절). 실행 간 비교를 하려면 시작 상태가 같아야 한다.

| 부하 | 제어 | 제공량 | **앱 도달(2xx)** | 429 거절 | **통과 p95** | 5xx |
|---|---|---|---|---|---|---|
| 200 VU | OFF | 120.4/s | **120.4/s** | 0 | **1.46s** | 0% |
| 200 VU | ON | 140.6/s | **109.9/s** | 30.7/s | **1.68s** | 0% |
| 600 VU | OFF | 123.2/s | **123.2/s** | 0 | **3.77s** | 0% |
| 600 VU | ON | 301.1/s | **115.1/s** | 185.9/s | **3.11s** | 0% |

전역 층이 실제로 개입했다: 200 VU에서 1,355건, 600 VU에서 3,601건을 `scope=global`로 거절했다.
**이 프로젝트에서 전역 상한이 부하를 받은 것은 이번이 처음이다.**

### 해석 — 기대와 다른 결과가 나왔다

**① 서버는 무너지지 않았다.** 제공 부하를 3배로 올려도(200 → 600 VU) 네 조건 모두 5xx가 0%다.
제어가 없어도 서버는 깨지지 않고 **느려질 뿐이다**. 7절이 암시하던 "제어가 붕괴를 막는다"는
이 부하 구간에서는 성립하지 않는다. 붕괴가 없으니 막을 것도 없었다.

**② 포화점 아래에서 제어는 순손실이다.** 200 VU에서 제어를 켜면 처리량 −8.7%, p95 +15.1%로
**두 축 모두 나빠진다.**

> **⚠️ 아래 "상한이 낮다"는 해석은 12절에서 뒤집혔다.** 이 실험은 `ramping-vus`, 즉 **닫힌 루프**다.
> VU는 응답을 받아야 다음 요청을 보내므로, 서버가 느려지면 **부하도 같이 줄어든다.** 그래서
> "서버가 120/s를 소화한다"가 아니라 "이 VU 수로는 120/s까지밖에 못 밀어넣는다"를 잰 것이었다.
> 도착률을 고정한 개방 루프로 다시 재니 무릎은 **100~120/s 사이**였고, 상한 100은 낮게 잡힌 게
> 아니라 **거의 무릎 위**였다. 12절을 함께 읽을 것.

당시 해석은 이랬다 — 전역 상한 100/s가 측정된 처리 능력(~120/s)보다 낮아 처리할 수 있는 일을
버리고 있다. 100이라는 숫자가 측정이 아니라 짐작으로 정해진 값인 것은 사실이지만, **그 값이
틀렸다는 결론은 측정 방식의 한계에서 나온 것이었다.**

**③ 포화점 위에서는 값을 한다.** 600 VU에서는 처리량 −6.6%를 내주고 p95 −17.5%를 얻는다
(3.77s → 3.11s). 그리고 거절이 **싸다** — 429는 필터에서 바로 나가 DB·커넥션을 쓰지 않는다.
제어 ON의 제공량이 301/s로 OFF(123/s)의 2.4배인 것이 그 증거다. 거절이 1ms 안에 끝나니
클라이언트가 훨씬 빨리 순환한다. **서버가 하는 일의 양은 그대로인데 대기열만 사라진 것**이다.

정리하면 유입 제어가 실제로 사는 값은 "붕괴 방지"가 아니라 **"포화 이후 지연 억제 + 싼 거절"**이고,
per-user 층은 그와 별개로 한 사용자의 남용을 막는 역할을 그대로 한다.

### 그래서 상한값을 바꿨나 — 안 바꿨다

측정된 처리 능력이 ~120/s이므로 전역 상한을 100 → 120 근처로 올리면 ②의 손실이 사라진다.
그런데 **이 수치는 M-시리즈 맥북 로컬(앱·MySQL·Redis·k6가 한 머신)에서 나온 값이다.** 운영
하드웨어에서 이 숫자는 다르다. 로컬 실측으로 운영 기본값을 바꾸는 건 짐작을 다른 짐작으로
바꾸는 것에 불과하다.

대신 `application.yml`의 해당 설정에 **이 값의 출처와 재측정 방법을 주석으로 박았다.** 다음 사람이
"100이 어디서 나온 숫자인지" 묻지 않아도 되게 하는 것이 지금 할 수 있는 정직한 조치다.

### 재현

```bash
docker compose down -v && docker compose up -d mysql redis   # 실행마다 초기화 — 안 하면 비교 불가
APP_RATELIMIT_ENABLED=false ./gradlew -p commerce bootRun
VUS=200 ACCOUNTS=40 k6 run k6/spike-multi-account.js          # 대조군

docker compose down -v && docker compose up -d mysql redis
./gradlew -p commerce bootRun                                             # 기본값 on
VUS=200 ACCOUNTS=40 k6 run k6/spike-multi-account.js          # 실험군
```

스크립트는 `shed_global > 0`을 threshold로 걸어둔다. **이게 0이면 전역 층이 개입하지 않은 것이라
나머지 지표가 아무리 좋아도 실험이 성립하지 않는다** — 7절이 그 상태였다.

> 실행 중 앱을 재기동할 땐 `pkill -f bootRun`으로는 부족하다. Gradle 래퍼만 죽고 포크된 JVM이
> 포트를 물고 살아남아, 새 설정이 반영되지 않은 옛 프로세스가 계속 응답한다. 실제로 이걸 놓쳐
> "제어 OFF" 대조군이 실은 ON 2회차였던 적이 있다(두 결과가 0.2% 차이로 겹쳐서 발각됐다).
> `lsof -nP -iTCP:8080 -sTCP:LISTEN -t`로 확인하고 PID로 죽인다.

## 10. 부수 발견: 아웃박스가 무한히 자라고 매번 풀스캔되고 있었다 (해소)

9절 실험이 회차마다 다른 결과를 낸 원인을 쫓다 나온 것이다. 부하 실험 6회 뒤
`event_publication`이 **150,372행**(완료 103,495 / 미완료 42,335)까지 자라 있었다.

두 가지가 겹쳐 있었다.

**① 완료 행을 지우는 스케줄러가 있는데 기본값이 off다.** `OutboxCleanupScheduler`가 7일 지난
완료분을 지우도록 이미 만들어져 있었다. 다만 `APP_OUTBOX_CLEANUP_ENABLED` 기본값이 `false`라
**켜지 않은 환경에서는 아무것도 지워지지 않는다** — 모든 로컬·개발 실행이 그렇고, 플래그를 빠뜨린
배포도 그렇다. Modulith의 `completion-mode` 기본값이 `update`(완료 시 `completion_date`만 채우고
행은 남김)라 정리가 없으면 발행량에 비례해 무한히 자란다. 부하 실험 6회에 150,372행이 된 게
그 모습이다.

> 처음에 이걸 "아무도 안 지운다"로 적었는데 틀렸다. 정리 로직은 있었고, 꺼져 있었을 뿐이다.
> 문제의 성질이 다르다 — 없는 걸 만드는 게 아니라, **기본값이 안전하지 않은 쪽으로 잡혀 있는 것**이다.

**② 인덱스가 PK 하나뿐이라 완료 처리가 매번 풀스캔이다.** Modulith가 리스너 완료마다 실행하는
쿼리는 이렇다.

```sql
update event_publication set completion_date = ?
 where serialized_event = ? and listener_id = ? and completion_date is null
```

두 컬럼 모두 인덱스가 없었다. `EXPLAIN` 결과 `type=ALL, key=NULL, rows=150372`.
`PaymentConfirmedEvent`에는 리스너가 6개라 **결제 한 건당 이 풀스캔이 6회** 돈다. 즉
결제 지연이 현재 부하가 아니라 **"그동안 처리한 이벤트 누적량"에 비례해** 나빠진다.
부하 시험을 반복할수록 느려진 게 이것이었고, 운영에서라면 서서히·되돌릴 수 없이 나빠졌을 것이다.

**조치**(`V24__event_publication_archive_and_index.sql`, `completion-mode: archive`):
- 완료분을 `event_publication_archive`로 옮긴다 → **정리 스케줄러를 켜지 않아도** 핫 테이블은
  "아직 처리 안 된 것"만 남는다. 즉 크기 상한이 운영 플래그가 아니라 구조에서 나온다.
  `delete`가 아니라 `archive`를 고른 이유는 "무엇이 언제 발행됐는가"가 감사 자료이기 때문이다.
- `(listener_id, serialized_event(191))` — 완료 처리 핫패스.
- `(completion_date, publication_date)` — 재기동 시 미완료 재발행 경로.

**기존 스케줄러를 대체하는 게 아니라 짝을 이룬다.** 아카이브가 핫 테이블을 작게 유지하고,
스케줄러는 아카이브를 보존기간(7일) 뒤에 비운다. Modulith의 `CompletedEventPublications`는
`completion-mode`에 따라 대상 테이블을 바꾸므로, 아카이브 모드에서는 스케줄러가 아카이브
테이블을 정리한다 — 코드 변경 없이 그대로 맞물린다.

인덱스는 아카이브가 있어도 필요하다. 아카이브만 하면 평시엔 빠르지만 **장애로 미완료가 쌓인
순간 다시 풀스캔으로 돌아간다** — 하필 가장 급할 때. 그리고 인덱스 부재는 정리 여부와 무관한
독립 결함이다. 보존기간을 7일로 켜둬도 발행량이 많으면 그 7일치를 매 완료마다 훑는다.

### 곁가지: 소비가 비동기라는 사실이 눈에 보이게 됐다

아카이브 모드로 바꾸니 핫 테이블 행 수가 곧 **처리 대기분**이 됐다. 부하 직후 22,492건이 남아 있다가
몇 분 뒤 6,174건으로 빠지는 게 보였다. `@ApplicationModuleListener`는 커밋 이후 별도 스레드에서
돌기 때문에(= 결제 200 응답 시점에 정산·원장·알림은 아직일 수 있다) 이 적체 자체는 정상이다.

문제는 **그게 보이지 않았다는 것**이다. 정상적인 적체와 소비가 멈춘 상태는 겉으로 똑같이
"결제는 되는데 원장이 안 쌓인다"로 보인다. `OutboxMetrics`로 두 게이지를 올렸다.

- `outbox.pending.count` — 대기분. 부하 중 증가는 정상이다.
- `outbox.pending.oldest.age` — **알람은 이쪽에 건다.** 수천 건이 밀려도 빠지는 중이면 정상이고,
  10건뿐이어도 30분째 그대로면 사고다. 개수는 그 둘을 구분하지 못한다.
  (미확정 결제에 `payment.unknown.oldest.age`를 붙인 것과 같은 판단이다.)

## 11. Argon2id의 진짜 비용: 메모리는 동시성과 곱해진다 (실측 완료)

8절에서 Argon2id가 BCrypt보다 **빠르다**(32ms vs 87ms)는 걸 재고, 대신 메모리를 쓴다고 적었다.
그때 재지 않은 게 있다. **19MiB는 해시 1건당이다.** 동시 로그인 수만큼 곱해진다.

Tomcat 스레드 상한이 100이므로 최악의 경우 100건이 동시에 해시를 돌린다. 그게 얼마인지 쟀다.

| 힙 상한 | 동시 25 | 동시 50 | 동시 100 |
|---|---|---|---|
| **512MB** | 성공 (505MB, 696ms) | **50건 전부 OOM** (4.2s) | **75건 실패** (12.1s) |
| **1GB** | 성공 (530MB, 587ms) | 성공 (1,001MB, 905ms) | **12건 실패** (7.2s) |
| **2GB** | 성공 (528MB, 484ms) | 성공 (1,032MB, 667ms) | 성공 (**1,984MB**, 1.5s) |

사용량은 정확히 선형이다 — 동시 100건에서 1,984MB, 즉 **동시 1건당 약 20MB**.
경험칙은 이렇다: **필요 힙(Argon2 몫) ≈ Tomcat 스레드 수 × 20MB.**
현재 설정(스레드 100)에서는 **Argon2 몫만 2GB**이고, 애플리케이션이 쓰는 나머지는 별도다.

### 실패하는 방식이 더 나쁘다

숫자보다 중요한 건 **어떻게 죽느냐**다. 512MB·동시 100건에서 성공했을 때 0.7초짜리 작업이
**12.1초를 쓰고 75건이 죽는다.** 즉 힙이 모자란 상태에서 로그인이 몰리면 **느려지면서 죽는다.**
응답이 늦으니 클라이언트는 재시도하고, 재시도가 다시 메모리를 잡는다. 스스로 증폭되는 실패다.

8절에서 "알고리즘 강화가 로그인 경로의 DoS 표면을 키웠다"고 적었는데, 그 표면의 크기가
이번에 숫자로 나왔다. 유입 제어(IP당 5/s, 경로 전체 100/s)가 1차 방어이긴 하나
**고정 윈도우라 100건이 같은 순간에 도달할 수 있어, 전역 상한 자체가 위험 구간과 겹친다.**

### 조치: 부팅 때 숫자로 알린다

`PasswordHashingCapacityCheck`가 기동 직후 `스레드 수 × 20MB`와 힙 상한을 비교해, 넘칠 수 있으면
경고를 남긴다(넘지 않으면 info로 여유를 남긴다).

부팅을 **막지는 않는다.** 스레드가 전부 동시에 해시를 돌리는 건 최악의 경우이고 실제 트래픽은
그보다 낮게 흐른다. 힙 여유가 적은 환경에서 부팅을 거부하면 그게 더 큰 사고다. 판단은 배포하는
사람이 하되, **모르고 지나가지는 않게**한다 — 운영 중 OOM으로 알게 되면 원인이 로그인 경로라는
사실을 찾는 데만 한참 걸린다.

세마포어로 동시 해시 수를 직접 묶는 방법도 검토했다. 메모리 상한이 스레드 설정과 분리되어 더
정확해지지만, 대기열이 하나 더 생기고 그 큐가 넘칠 때의 동작을 또 정해야 한다.
**유입 제어가 이미 그 층을 맡고 있으므로**, 지금은 상한을 보이게 하는 쪽을 골랐다.
전역 상한을 실측 기반으로 재조정할 때(9절) 같이 다룰 문제다.

### 재현

```bash
# 클래스패스를 뽑아 스탠드얼론으로 잰다(부팅·DB 없이 해싱만 격리해서 본다)
CP=$(./gradlew -q printRuntimeClasspath | tail -1)
javac -cp "$CP" -d /tmp Argon2Concurrency.java
for heap in 512m 1g 2g; do for n in 25 50 100; do
  java -Xmx$heap -cp "$CP:/tmp" Argon2Concurrency $n
done; done
```

## 12. 전역 상한을 정하는 방법을 만든다 (실측 완료)

9절은 "전역 상한 100/s는 짐작이고, 배포 환경마다 다시 재야 한다"로 끝났다. 그리고 재는 방법을
주석으로 적어뒀다. **그게 부족했다.** 절차를 글로만 적어두면 아무도 안 한다. 그리고 더 큰 문제가
있었다.

### 운영에서 한도를 조정할 근거가 아예 없었다

429를 **지표로 내보내지 않고 있었다.** 얼마나 쳐내는지, 어느 층이 쳐내는지 대시보드에서 볼
방법이 없었다. 그러면 `global-per-sec` 같은 값은 처음 정한 짐작에 **영원히 머문다** — 바꿀
근거가 생길 수 없으니까.

`RateLimitFilter`가 이제 두 가지를 낸다.

- `ratelimit.rejected{scope, path}` — 층·경로별 거절 수
- `ratelimit.limit.global`, `ratelimit.limit.per.user` — 설정된 한도 값

한도 값도 같이 내보내는 이유는, 거절 수만 보면 "많이 쳐낸다"까지만 알 수 있기 때문이다.
그게 한도가 낮아서인지 부하가 큰지는 **둘을 나란히 놓아야** 판단된다.

판독은 `scope`로 갈린다. `global`이 오르면 시스템 차원 문제이고, `user`/`ip`만 오르면 특정
클라이언트 남용이라 **상한을 올릴 일이 아니다.** 알람(`GlobalRateLimitBinding`)은 `global`만 본다.

### 재는 것을 스크립트로 만들었다 — 그리고 결론이 뒤집혔다

`k6/capacity-knee.js`가 도착률을 계단식으로 올리며 무릎을 찾는다. 9절 스크립트와 **executor가
다르다.**

| | 9절 (`spike-multi-account.js`) | 12절 (`capacity-knee.js`) |
|---|---|---|
| executor | `ramping-vus` (닫힌 루프) | `constant-arrival-rate` (개방 루프) |
| 부하 모델 | VU가 응답을 기다렸다 다음 요청 | 도착률 고정, 응답과 무관 |
| 서버가 느려지면 | **부하도 같이 준다** | 부하는 그대로, 대기열이 자란다 |

이 차이가 결정적이었다. 닫힌 루프는 **서버가 느려지면 스스로 부하를 줄인다.** 그래서 9절에서
잰 ~120/s는 "서버가 소화하는 양"이 아니라 "그 VU 수로 밀어넣을 수 있는 양"이었다. 실사용
트래픽은 우리 서버가 느리다고 요청을 줄여주지 않으므로, **개방 루프가 더 정직한 모델이다.**

개방 루프로 재니 이렇게 나왔다.

| 도착률 | 성공률 | 판정 |
|---|---|---|
| 40/s | 100.0% | |
| 60/s | 100.0% | |
| 80/s | 100.0% | |
| 100/s | 100.0% | **무릎(마지막 온전한 단계)** |
| 120/s | 92.4% | 포화 시작 |
| 140/s 이상 | 55% → 28% | 붕괴 |

**전역 상한 100/s는 거의 무릎 위였다.** 9절에서 "능력보다 낮게 잡혀 있다"고 쓴 건 측정 방식의
한계에서 나온 결론이었다. 그래서 9절에 정정 주석을 달았다.

기본값을 바꾸지 않기로 한 판단은 유지된다. 다만 **이유가 달라졌다** — "로컬 값이라 못 바꾼다"가
아니라 **"재보니 대체로 맞는 값이더라"**다.

### 서버는 에러를 내지 않는다, 받지 않을 뿐이다

무릎 너머에서 무슨 일이 나는지도 확인했다. 성공률이 28%까지 떨어졌는데 **DB에는 실패가 0건**이고
애플리케이션 예외도 없다. 5xx가 아니라 **연결 단계 실패(status 0)**였다 — 수용 큐가 넘쳐
요청이 서버에 닿지도 못한 것이다.

그래서 스크립트가 `conn`(status 0)과 `5xx`를 따로 센다. 둘을 뭉뚱그리면 "서버가 깨졌다"로
잘못 읽는다. 실제로는 **서버가 멀쩡한 채로 받지 않는 상태**이고, 대응이 다르다(스레드·큐 설정과
증설이지, 버그 수정이 아니다).

### 판정 로직을 한 번 틀렸다

처음엔 무릎을 **지연 급증**으로 잡게 짰다. 결과가 이상했다 — 무릎이 세 번 찍혔고, 120/s에서
p95가 2.2초였다가 140/s에서 287ms로 **내려갔다.**

원인은 이렇다. 성공률이 무너지면 **느린 요청이 실패로 빠져나간다.** 남은 성공분만 보면 p95가
오히려 좋아진다. 지연만 보면 "회복됐다"고 읽게 된다.

그래서 판정 기준을 **성공률**로 바꿨다 — 무릎은 "성공률이 온전한 마지막 단계"다.
지연은 보조 지표로만 쓴다.

### 재현

```bash
docker compose down -v && docker compose up -d mysql redis
APP_RATELIMIT_ENABLED=false ./gradlew -p commerce bootRun    # 제어를 켠 채 재면 "설정한 한도"를 잴 뿐이다
k6 run k6/capacity-knee.js
```

스크립트가 setup에서 429를 만나면 **바로 중단한다.** 제어를 끄는 걸 잊으면 무릎이 아니라
자기가 설정한 숫자를 재게 되고, 그건 측정이 아니라 동어반복이다.

## 13. 느린 쿼리를 우연이 아니라 로그로 찾는다 (검증 완료)

10절의 아웃박스 풀스캔은 **우연히 찾았다.** 부하 실험 결과가 회차마다 달라 원인을 쫓다가
DB를 열어보고서야 `event_publication`이 150,372행이고 완료 처리가 매번 풀스캔이라는 걸 알았다.

그리고 확인해 보니 **느린 쿼리를 알아챌 수단이 하나도 없었다.**
이 문서 46줄에는 병목 계측 방법으로 *"slow query 로그"*가 적혀 있는데 **정작 켜져 있지 않았다.**
방법을 적어두고 켜지 않은 것이다.

```yaml
spring.jpa.properties.hibernate.log_slow_query: ${APP_SLOW_QUERY_MS:300}
```

### 임계 300ms를 고른 이유

12절 실측에서 이 서버의 무릎이 도착률 100/s이고, 그 아래에서 결제 승인 p95가 수십~수백 ms다.
**개별 쿼리 하나가 300ms를 넘으면 요청 하나가 통째로 느려질 만한 크기**이므로,
정상 트래픽에서는 거의 안 찍히고 이상할 때만 찍힌다.
너무 낮으면 로그가 시끄러워 아무도 안 보게 되고, 너무 높으면 오늘 같은 풀스캔을 놓친다.

### 프로퍼티 이름에 함정이 있다

처음에 `hibernate.session.events.log.LOG_QUERIES_SLOWER_THAN_MS`로 적었다. **틀렸다.**
그건 Hibernate 6.1까지의 이름이고, **6.2에서 `hibernate.log_slow_query`로 바뀌었다.**
이 프로젝트는 Hibernate 7.4를 쓴다.

**옛 이름을 쓰면 예외도 경고도 없이 조용히 무시된다.** 그대로 뒀다면
"슬로우 쿼리 로깅을 켰다"고 문서에 적힌 채 아무것도 안 찍혔을 것이다 —
이 프로젝트에서 반복해 잡은 "만들어놓고 안 도는 것"이 하나 더 늘어날 뻔했다.

Hibernate 7 jar에서 상수를 직접 확인했다: `LOG_SLOW_QUERY = "hibernate.log_slow_query"`.

### 실제로 찍히는 것을 확인했다 — DB 없이

**설정이 맞다는 것과 로그가 찍힌다는 것은 다른 문장이다.** 그래서 발화를 검증했다.

처음엔 앱을 띄워 확인하려 했는데 로컬 도커 데몬이 반복해서 내려갔다. 그러다 알아챈 것 —
**이건 Hibernate 기능이지 MySQL 기능이 아니다.** DB가 전혀 필요 없다.
`SqlStatementLogger`를 직접 호출해 `org.hibernate.SQL_SLOW` 로거로 나가는지만 보면 된다
(`SlowQueryLoggingTest`, 4건).

- 임계 초과 → 찍힌다. SQL 본문과 소요 시간을 함께 남긴다
- 임계 이내 → 안 찍힌다
- 임계 0 → 기능이 꺼진다
- `application.yml`의 프로퍼티 이름이 이 Hibernate 버전 상수와 일치한다

**컨테이너 없이 기본 스위트에서 매번 돈다.** 나중에 Hibernate를 올려 로거 이름이나 프로퍼티가
또 바뀌면 여기서 깨진다.

### 검증하다 하나 더 찾았다 — 메시지 형식

실제 로그는 이렇게 나온다.

```
Slow query took 5 milliseconds [select * from payments where order_no = ?]
```

처음엔 `SlowQuery`라는 단어를 단언했다가 테스트가 깨졌다.
**그래서 이 문서에 적어뒀던 `grep SlowQuery`도 틀린 것이었다.**
로그가 제대로 찍혀도 **검색어가 틀리면 못 찾는다.**

운영에서 확인할 때는 이렇게 본다.

```bash
grep "Slow query took" <로그>
```

임계를 낮춰 눈으로 보고 싶으면:

```bash
APP_SLOW_QUERY_MS=1 ./gradlew -p commerce bootRun   # 1ms면 평범한 쿼리도 걸린다
```

## 14. 느린 PG 앞에서 마르는 자원은 커넥션이 아니라 워커다 (실측 완료)

체크아웃을 사가로 옮겨 PG 호출을 트랜잭션 밖으로 뺐다(ADR-007). 그러면 느린 PG 가 DB 커넥션 풀을 마르게 하는 경로는 끊긴다. **그런데 워커 스레드는 여전히 PG 응답까지 묶인다.** ADR-007 에 "아직 안 쟀다"고 적어 둔 자리를 여기서 잰다.

측정은 `tools/run-pg-brownout.sh` + `k6/pg-brownout.js`. 가짜 PG 에 지연을 주입하고, 15초 워밍업 뒤 45초를 잰다. 워커 상한 100, Hikari 풀 20.

### 14.1 병목은 사라진 것이 아니라 옮겨갔다 (도착률 30/s)

| PG 지연 | Hikari 활성(평균) | 워커 busy(평균/최대) | 결제 p95 | 처리량 |
|---|---|---|---|---|
| 0 | 5.9 | 3.6 / 9 | 99.5ms | 29.9/s |
| 200ms | 5.9 | 9.0 / 13 | 303ms | 29.8/s |
| 1s | 5.4 | 32.6 / 37 | 1.08s | 29.3/s |
| 3s | 5.0 | 86.6 / 96 | 3.07s | 28.1/s |
| 5s | 9.6 | 79.0 / **100** | **14.26s** | **17.6/s** |

PG 지연이 30 배가 되는 동안 **커넥션은 평평하고 워커만 24 배가 된다.** 점유 수는 `도착률 × 응답시간` 그대로다(30 × 3s = 90, 실측 86.6). 그래서 워커 100 개가 버티는 한계는 도착률 30/s 에서 PG 지연 약 3.3초다.

### 14.2 상한은 결제를 깎아 나머지를 지킨다 (PG 지연 3s · 도착률 50/s)

수요가 워커 수를 넘도록 올리고(50 × 3s = 150 > 100), 가벼운 조회를 초당 20 건 같이 밀어 넣어 태그를 갈라 쟀다.

| PG 동시 호출 상한 | **조회 p95** | 결제 p95 | 결제 성공 | 결제 거절 | 워커 busy(평균) |
|---|---|---|---|---|---|
| 없음 | **7.31s** | 9.78s | 1,729 | 0 | 84.1 |
| 40 | 769ms | 4.32s | 598 | 1,653 | 53.0 |
| 20 | **18.6ms** | 3.06s | 300 | 1,951 | 23.3 |

**상한이 없으면 느린 PG 가 결제와 무관한 조회까지 7.31초로 끌어내린다.** 평시 8ms 짜리다. 7절의 유입 제어가 "모두가 느려짐"을 "일부는 거절, 나머지는 정상"으로 바꾼 것과 같은 그림이고, 이번에는 막는 자리가 문 앞이 아니라 PG 호출 앞이다.

상한 20 은 조회를 390 배 지키는 대신 결제 1,951 건을 거절한다. 처리량 천장이 `상한 ÷ PG 지연` 이라 6.7 건/초이고 실측 6.5 다. 정상 구간(지연 0·30/s·상한 40)에서는 거절 0 건이라 **상한은 PG 가 망가졌을 때만 발동한다.**

### 14.3 타임아웃을 조이면 미확정을 낸다 (PG 지연 5s · 도착률 30/s)

| read-timeout | 결제 p95 | 처리량 | 미확정(202) |
|---|---|---|---|
| 5s | 14.26s | 17.6/s | 0 |
| 2s | **2.13s** | 28.6/s | **1,351 (전량)** |

p95 가 6.7 배 좋아지는 대신 그 구간 결제가 전부 미확정이 되어 복구 배치 일거리가 0 에서 1,351 건이 된다. 가용성과 정합성 부채를 맞바꾼 크기다. **그 1,351 건이 언제 풀리는지는 14.5 에서 잰다** — 기본값으로 약 3.7분이고, 전량이 `DONE` 으로 확정된다.

**결론(측정 당시)**: 상한 메커니즘을 채택하되 기본값은 상한 없음으로 둔다. 상한값은 실 PG 응답시간 분포의 함수인데 이 프로젝트에는 그 분포가 없다. 켤 때는 40 에서 시작한다([ADR-022](../adr/ADR-022-pg-brownout-resource-limits.md)).

> **이후 바뀐 것.** 기본값은 지금 **40 으로 켜져 있다**(`application.yml` 의 `PAYMENT_PG_MAX_CONCURRENT_CALLS:40`). 실 PG 분포는 여전히 없지만, ADR-022 가 가정한 분포(피크 30/s · 정상 p99 1초)로 하한 30 · 상한 60 을 유도하고 그 사이에서 40 을 골랐다. 그 유도에 쓴 `도착률 × 지연` 관계가 성립하는지는 14.4 에서 확인했다. 위 결론은 그때의 판단으로 남긴다.

**부수 발견**: 이 실험을 하려고 보니 `tomcat_threads_busy_threads` 가 Prometheus 에 안 나가고 있었다. Spring Boot 는 Tomcat MBean 레지스트리를 기본으로 끈다. 커넥션은 보이고 워커는 안 보이는 상태였고, 여기서 마르는 자원이 바로 그것이다. `server.tomcat.mbeanregistry.enabled` 를 켰다.

### 14.4 지연을 축으로 쓸면 상한의 비용이 계산된다 (도착률 50/s · 회귀, #223)

14.2 는 **지연 3초 한 점**에서만 쟀다. 한 점으로는 "상한이 좋다/나쁘다" 밖에 못 말한다.
지연을 축으로 쓸어 **상한이 언제부터 발동하고 언제 결제를 대부분 포기하게 되는지**를 봤다.

측정: `tools/run-pg-brownout-sweep.sh 50 45s` (지연 6 × 상한 2 = 12회). 표는
`tools/brownout_sweep_report.py` 가 원자료에서 직접 만든다 — 손으로 옮기지 않는다.

| PG 지연 | 상한 | 결제 p95 | **조회 p95** | 성공 | 거절 | 거절률 | 워커 max |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 0ms | 없음 | 69ms | 9ms | 2,251 | 0 | 0.0% | 7 |
| 0ms | 40 | 69ms | 10ms | 2,250 | 0 | **0.0%** | 6 |
| 500ms | 없음 | 567ms | 9ms | 2,251 | 0 | 0.0% | 33 |
| 500ms | 40 | 603ms | 12ms | 2,250 | 0 | **0.0%** | 34 |
| 1,000ms | 없음 | 1,080ms | 10ms | 2,251 | 0 | 0.0% | 62 |
| 1,000ms | 40 | 1,060ms | 9ms | 1,764 | 486 | **21.6%** | 45 |
| 2,000ms | 없음 | 3,050ms | **1,030ms** | 2,251 | 0 | 0.0% | **100** |
| 2,000ms | 40 | 2,040ms | **8ms** | 903 | 1,348 | 59.9% | 45 |
| 3,000ms | 없음 | 10,510ms | **7,720ms** | 1,758 | 0 | 0.0% | **100** |
| 3,000ms | 40 | 3,050ms | **8ms** | 600 | 1,651 | 73.3% | 44 |
| 5,000ms | 없음 | 15,770ms | **14,080ms** | 1,200 | 0 | 0.0% | **100** |
| 5,000ms | 40 | 5,040ms | **7ms** | 360 | 1,890 | 84.0% | 44 |

**1. 상한은 공짜로 켜 둘 수 있다.** 지연 0·500ms 에서 거절이 **0 건**이다. 상한은 PG 가 이미
느려졌을 때만 발동하고, 정상 구간에서는 존재하지 않는 것처럼 동작한다.

**2. 상한이 지키는 것은 결제가 아니라 조회다.** 상한 없이 지연 2초를 넘기면 워커가 **100(최대)에
붙고** 조회가 10ms 에서 1,030ms → 7,720ms → 14,080ms 로 무너진다. 상한 40 이면 같은 구간에서
조회가 **7~8ms 로 평평하다.** 지연 5초에서 **2,011배** 차이다.

**3. 그 대가는 계산된다.** 거절률이 Little's Law 로 예측된다 — 처리 가능량은 `상한 ÷ 지연`,
거절률은 `1 − 상한 ÷ (도착률 × 지연)`.

| 지연 | 예측 거절률 | 실측 | 차이 |
|---:|---:|---:|---:|
| 1s | 20.0% | 21.6% | +1.6%p |
| 2s | 60.0% | 59.9% | −0.1%p |
| 3s | 73.3% | 73.3% | −0.0%p |
| 5s | 84.0% | 84.0% | +0.0%p |

3초 이상에서는 **소수점까지 맞는다.** 그래서 **발동 지점도 계산된다**: 거절이 시작되는 지연은
`상한 ÷ 도착률 = 40 ÷ 50 = 0.8초`. 실측도 500ms 무거절 / 1,000ms 거절 시작이다.

**이 식이 맞으면 상한값을 다시 재지 않고 고를 수 있다.** "피크 도착률 R 에서 지연 L 까지는
거절 없이 버틴다" 를 원하면 상한은 `R × L` 이다. ADR-022 가 가정으로 유도한 40 은
`30/s × 1.3s` 근처이고, 이 측정은 **그 유도 방식이 실제로 성립한다는 것**을 보인 것이다.

**4. 상한은 동작을 결정론으로 만든다.** 지연 1s·3s 를 다시 돌렸더니 상한 켠 쪽은 거절
486 → 488, 1,651 → 1,650 으로 사실상 같았다. 상한 없는 쪽은 조회 p95 가 7,720 → 7,850ms,
결제 p95 가 10,510 → 9,710ms 로 흔들린다 — **포화는 재현이 잘 안 된다는 것 자체가 결과다.**

#### 이 표가 말하지 않는 것

- **미확정(202)이 전 구간 0 이다.** read-timeout 5초에 지연 최대 5초라 타임아웃이 거의 안 걸렸다.
  미확정은 지연이 아니라 **타임아웃 축**에서 생긴다 — 그건 14.3 이 따로 잰다
- **절대값은 이 맥의 값이다.** 가짜 PG 이고 단일 장비다. 정책 간 비교로만 읽는다
- **실 PG 응답시간 분포는 여전히 없다.** 바뀐 것은 값이 아니라 **"언제 상한이 의미 있는가"의 근거**다.
  기본값 40 은 그대로 둔다

### 14.5 미확정은 언제 풀리는가 — 복구 지연을 정하는 것은 둘 중 하나다 (#225)

14.3 은 미확정을 **만드는 것까지**만 쟀다. "복구 배치 일거리가 0 에서 1,351 건이 된다" 고 적고
**그 일거리가 언제 어떻게 풀리는지는 안 쟀다.**

같은 조건(PG 지연 5s · read-timeout 2s)으로 미확정을 만들고, 복구를 켠 채 `payments` 테이블을
2초마다 찍었다. 상태 수는 **DB 에서 직접 읽는다** — 응답 코드도 지표도 아니고 그 테이블이 진실이다.
측정은 `tools/run-unknown-recovery.sh`.

| 청크 | 주기 | 만든 미확정 | 첫 해소 | 전량 해소 | 해소율 | 최종 상태 |
|---:|---:|---:|---:|---:|---:|---|
| 500 | 5s | 887 | t+18s | **t+61s** | 생성 속도 그대로 | **전량 `DONE`** |
| 500 | 5s (재현) | 886 | t+18s | **t+62s** | 〃 | 전량 `DONE` |
| **50** | 5s | 885 | t+18s | **t+106s** | **정확히 50건/틱** | 전량 `DONE` |

`t` 는 부하가 끝난 시각이다.

**1. 하한은 `MIN_AGE` 가 정한다.** `PaymentRecoveryService.MIN_AGE = 1분` — 그보다 어린 미확정은
복구 대상이 아니다(진행 중인 정상 요청을 건드리지 않으려는 값이다). 청크가 넉넉하면 **해소 곡선은
생성 곡선을 정확히 1분 뒤로 민 모양**이 된다.

- 부하는 45초였다. 첫 미확정은 `t−45s` 에 생겨 `t+15s` 에 자격을 얻는다 → **실측 첫 해소 t+18s**
- 마지막 미확정은 `t` 에 생겨 `t+60s` 에 자격을 얻는다 → **실측 전량 해소 t+61s**

**2. 상한은 `청크 ÷ 주기` 가 정한다.** 틱당 자격자가 청크를 넘으면 그때부터는 배치가 병목이다.
청크를 50 으로 줄이자 곡선이 **완벽한 직선**이 됐다(885 → 835 → 785 → 735 → … 틱마다 정확히 50).

```
해소율 = 청크 ÷ 주기 = 50 ÷ 5s = 10/s
전량 해소 = 첫 자격(t+18s) + 885 ÷ 10 = t+106.5s      실측 t+106s
```

**3. 전량이 `DONE` 으로 확정됐다.** 복구 중 `ABORTED` 는 0 건이다. 우리는 타임아웃이었지만 PG 측은
승인이었기 때문이고(`FakePgClient` 가 그 상황을 재현한다), **그것이 미확정을 실패로 단정하면 안 되는
이유**다. 복구가 PG 에 다시 묻지 않고 실패로 적었다면 887 건이 전부 **잘못된 실패**가 됐을 것이다.

#### 그래서 운영에서 무엇을 보면 되나

기본값은 주기 60초 · 청크 500 이다. 위 식에 넣으면 **해소율 8.3건/초**다.

| 쌓인 미확정 | 전량 해소까지(기본값) |
|---:|---:|
| 500 | 1분 (청크 안 걸림 — `MIN_AGE` 만) |
| 1,351 (14.3 의 값) | **약 3.7분** |
| 10,000 | 약 20분 |

**미확정이 청크를 넘기 시작하면 복구가 선형으로 길어진다.** 그 지점을 알림으로 잡으려면 건수가
아니라 **가장 오래된 미확정의 나이**를 봐야 한다 — `UnknownPaymentAging` 이 이미 그렇게 걸려 있다.

#### 이 표가 말하지 않는 것

- **실 PG 장애 분포는 없다.** 여기서는 PG 측이 전부 승인이었다. 실제로는 `NOT_FOUND`·`CANCELED`·
  `IN_PROGRESS` 가 섞이고, `IN_PROGRESS` 는 **다음 주기로 미뤄져** 해소가 더 걸린다
  - 미뤄진 건이 다음 주기에 **같은 앞자리**에 서는 것을 쟀다([#248](recovery-order.md)): 청크만큼 쌓이면 뒤의 건을
    5분 동안 한 건도 못 풀었다. 다음 시도를 뒤로 미는 `backoff` 로 바꿨다([ADR-057](../adr/ADR-057-recovery-backoff-over-order.md))
- `MIN_AGE` 는 코드 상수라 설정으로 못 줄인다. 이 측정으로 바꾸지 않았다 — 그 값의 목적은
  속도가 아니라 **진행 중인 정상 요청과 안 겹치는 것**이다
- 절대값은 이 맥의 값이다. 정책 간 비교로만 읽는다

### 14.6 PG 가 느리면 웹훅이 토스 규약을 넘긴다 — 재전송 되먹임 (#230)

토스 웹훅 규약은 **10초 안에 2xx** 다. 못 주면 재전송한다. 우리 컨트롤러는 **PG 를 안 부른다** —
저장하고 바로 200 을 준다. 구조상 빠를 수밖에 없어 보이는데, **톰캣 워커를 결제와 공유**한다.

14.1 에서 PG 지연 2초를 넘기면 워커가 100(최대)에 붙는 것을 쟀다. **그러면 웹훅도 같은 큐에 선다.**

결제 부하(50/s)와 웹훅(10/s)을 **같이** 밀어 넣어 쟀다. 웹훅만 재면 이 문제가 안 보인다.

| PG 지연 | 상한 | **웹훅 p95** | 웹훅 p99 | **10초 초과** | 결제 p95 | 웹훅 저장 |
|---:|---:|---:|---:|---:|---:|---:|
| 0ms | 없음 | 13ms | 20ms | 0.00% | 62ms | 527 |
| 0ms | 40 | 31ms | 92ms | 0.00% | 199ms | 526 |
| 3,000ms | 없음 | **7,246ms** | 7,974ms | 0.00% | 9,695ms | **493** |
| 3,000ms | 40 | **13ms** | 20ms | 0.00% | 3,046ms | 527 |
| 5,000ms | 없음 | **13,056ms** | 13,923ms | **26.11%** | 15,865ms | **459** |
| 5,000ms | 40 | **9ms** | 12ms | **0.00%** | 5,042ms | 527 |

**1. 되먹임이 실재한다.** PG 지연 5초에서 웹훅 p95 가 **13초**이고 **26.11% 가 토스 규약을 넘긴다.**
그 건들은 재전송 대상이 되고, 재전송이 다시 워커를 먹는다. **PG 장애가 웹훅 폭주로 번지는 경로다.**

**2. 상한이 그것을 막는다.** 같은 조건에서 상한 40 이면 웹훅 p95 **9ms · 초과 0%** 다.
**1,450배** 차이다. 상한은 결제를 깎아 조회를 지킨다고 14.2 에 적었는데, **지키는 것에 웹훅도 있다.**

**3. 웹훅이 아예 못 들어온 것도 있다.** 저장 건수가 527 → **459** 로 떨어진다(5초·상한 없음).
200 을 줬는지가 아니라 `webhook_events` 행 수로 확인했다 — **68건이 들어오지 못했다.**

**4. 재현된다.** 지연 5초를 다시 돌려 **26.11% → 26.77%**, 상한 40 은 양쪽 다 0.00% 였다.

#### 첫 회차는 아무것도 재지 못했다

부하가 `/api/v1/orders` 만 치고 **승인 경로를 안 탔다.** PG 지연 5초인데 결제 p95 가 13ms 로 나와서
알았다 — PG 를 불렀다면 5초여야 한다. **"영향이 없다" 가 아니라 "PG 를 안 불렀다" 였다.**
그 회차 표는 버렸다.

#### 이 표가 말하지 않는 것

- **실제 토스 재전송을 잰 것이 아니다.** 우리 응답 시간을 쟀고, 재전송은 그 결과로 **일어날 수 있는 일**이다.
  공개 URL 수신은 여전히 미검증이다
- 0ms·상한 40 에서 웹훅 31ms·결제 199ms 로 약간 높은데, **상한이 정상 구간에서 무는 것은 아니다**
  (14.2 에서 거절 0 건 확인). 워밍업 잔여로 보이나 **원인을 확정하지 못했다**
- 절대값은 이 맥의 값이다. 정책 간 비교로만 읽는다

## 15. 배포 단위만 나눠도 두 결합은 풀린다 (실측 완료)

[모놀리스 한계 실측](msa-baseline-experiments.md)이 재현한 두 결합 — 수평 확장 시 정산 스케줄러 중복(실험 2), 무관 모듈 배포가 결제를 중단(실험 3) — 은 **배포 단위를 나누기만 해도 풀린다.** 저장소·브로커까지 나눈 것은 그 위에 얹은 별도 선택인데, 그 근거가 따로 없었다(외부 피드백). 여기서 기준선을 만든다([ADR-029](../adr/ADR-029-deployment-unit-vs-service-boundary.md)).

**형태**: 같은 jar, 프로파일 하나. `application.yml` 의 `worker` 프로파일이 배치 실행 주체다. API 배포는 프로파일 없이 떠서 모든 스케줄러가 기본 off다. 저장소는 그대로라 트랜잭션·조인이 남는다.

측정은 `k6/seed-settlement-scheduler-split.sql`(어제 KST 정산 항목 2만 건) + `k6/redeploy-blast-radius.js`.

### 15.1 스케줄러 중복: 인스턴스 2개 → 0

**before (모놀리스, 정산 켠 인스턴스 2개 동시 기동)**: 두 인스턴스가 같은 틱에 진입해 같은 1만 건을 중복 집계하고, 늦은 쪽이 `Duplicate entry '2026-09-18-KRW-1'` 로 배치 실패.

## 16. 원장 잔액 읽기: SUM 은 O(N) 이고, 어디서 스냅샷이 필요해지나 (실측 완료)

`ledger/package-info` 가 **"잔액은 엔트리의 합으로 파생된다"** 고 처음부터 선언했는데, **그 선언을 쓰는 코드가 없었다.** 잔액 조회가 없으니 "SUM 이 느려진다"는 예상일 뿐이었고, 대가를 한 번도 치른 적이 없었다. 조회를 만들면 그 대가를 매번 치른다. 그 비용과 커버링 인덱스가 버는 몫, 그리고 스냅샷이 필요해지는 행 수를 쟀다([ADR-025](../adr/ADR-025-ledger-balance-read-strategy.md)).

**부수로 잠복 버그를 하나 잡았다.** `AccountType` 은 `CASH`·`PG_FEE` 를 쓰는데 DB `account` enum 은 `PG_RECEIVABLE`·`SALES` 뿐이었다. 정산 지급 확정(입금 분개)이 원장에 기록되는 순간 MySQL 이 값을 거부한다 — 아직 `PAID_OUT` 정산이 없어 드러나지 않았고, H2 단위 테스트는 enum 을 강제하지 않아 통과했다. V50 이 enum 을 코드에 맞췄다.

측정은 `tools/measure-ledger-balance.sh`(서버 안에서 30회, p95) + `LedgerBalanceReadCostMySqlTest`(CI). MySQL 8.4, buffer pool 512MB, 로컬. **실 트래픽이 아니라 행 수만 늘린 측정이다.**

| 원장 행수 | 조회 | 인덱스 | p95 |
|---|---|---|---|
| 240,692 | 한 계정 / 계정별 전체 | 있음 | 32.6ms / 82.0ms |
| 1,616,948 | 한 계정 / 계정별 전체 | 있음 | 235.2ms / 564.4ms |
| 12,626,996 | 한 계정 / 계정별 전체 | 있음 | 1722.8ms / 4812.6ms |
| 12,626,996 | 한 계정 / 계정별 전체 | **없음** | 4469.8ms / 8056.8ms |

- **SUM 은 O(N) 을 벗어나지 못한다.** `(account, direction, amount)` 커버링 인덱스가 1000만 행에서 한 계정 조회를 **2.6배**, 계정별 전체를 **1.7배** 줄이지만 상수 시간은 아니다.
- **인덱스만으로 버티는 구간은 100만 행 아래다.** SLO(잔액 조회 p95 200ms)로 보면 계정별 전체 조회는 **약 60만 행**, 한 계정 조회는 **약 130만 행**에서 선을 넘는다 → 그때 스냅샷이 필요해진다.
- **쓰기 비용은 +12.7%.** 20만 행 INSERT: 인덱스 없음 1,906.8ms → 커버링 인덱스 추가 2,149.5ms. 인덱스는 공짜가 아니다(`IndexWriteCostMySqlTest` 와 같은 방식).

**결론**: SUM + 커버링 인덱스를 채택하되 **스냅샷은 지금 만들지 않는다.** 이 저장소는 100만 행에 한참 못 미치고, 지금 스냅샷을 넣으면 갈라짐을 감시할 대조 배치만 늘고 얻는 것이 없다. 필요해지는 지점(60만~130만 행)을 숫자로 남긴다.

**재현**: `RUNS=30 tools/measure-ledger-balance.sh` (벤치 행은 마커 `transaction_id` 로 심고 지운다 — 실제 분개는 건드리지 않는다).

## 17. 커밋은 됐는데 발행이 안 된 구간을 재기동이 메우는가 (실측 완료)

이벤트 발행은 Spring Modulith 의 Event Publication Registry(= 트랜잭셔널 아웃박스)를 탄다. DB 커밋과 발행 기록이 **같은 트랜잭션**이고, 재기동 시 미완료 이벤트를 다시 발행하는 설정(`republish-outstanding-events-on-restart: true`)도 켜져 있다. **설계는 있고, 그 경로를 장애로 검증한 적이 없었다.** "아웃박스를 썼으니 됐다"와 "죽여 봤더니 됐다"는 다르다.

측정은 `tools/outbox-republish-experiment.sh`. Kafka를 내린 채 결제를 승인해 **커밋은 되고 발행은 안 된** 상태를 결정적으로 만들고(Kafka가 살아 있으면 프로듀서 버퍼가 즉시 메워 그 상태를 못 잡는다), 앱을 **SIGKILL**(프로듀서 버퍼 소실)한 뒤 Kafka를 올리고 재기동한다.

| 단계 | 관측 |
|---|---|
| Kafka 내린 채 승인 | 결제는 `PAID`(커밋 성공), `event_publication` 미완료 **2건** |
| 앱 SIGKILL | (버퍼 소실) |
| Kafka 복구 후 재기동 | 토픽에 **재기동 후 8초 만에** 나타남 |
| 아카이브 | `completion_date − publication_date = 21초` (Kafka 복구 대기 + 재기동 포함) |
| 재기동 후 미완료 | **0건** |

**미완료 2건의 정체가 중요하다.** 하나는 `DelegatingEventExternalizer`(Kafka 발행, 브로커가 없어 실패)이고, 다른 하나는 `FraudPostHocListener.onConfirmed`(**SIGKILL 로 중단된 인-프로세스 리스너**)다. 즉 재기동 재발행은 Kafka 발행뿐 아니라 **처리 중에 죽은 인-프로세스 리스너까지** 복구한다. 아웃박스가 인-프로세스 소비에도 at-least-once 를 보장한다는 뜻이다.

**부수 발견 — 방어선이 두 겹이다.** 앱을 죽이기 전에 Kafka가 먼저 복구되면 **재기동 없이 프로듀서 버퍼 재시도**가 메운다(첫 시도에서 재기동 없이 14초 만에 발행됐다). 즉 이 구간은 (1) 프로듀서 버퍼 재시도, (2) 재기동 재발행으로 메워지고, 프로세스가 죽어 (1)이 사라져도 (2)가 남는다.

**멱등을 확인하다 구멍을 찾았다.** 재발행은 같은 이벤트를 두 번 배달할 수 있으므로 소비자는 멱등해야 한다. 이력(`card_transactions`)은 `order_no` 유니크로 막고 있었지만, **정작 사람이 보는 심사 큐(`fraud_reviews`)는 막는 장치가 없었다.** `FraudPostHocListener` 가 재배달 때 REVIEW/BLOCK 을 다시 판정하면 같은 주문이 두 줄로 쌓인다. `V51` 로 `order_no` 유니크를 걸고 `existsByOrderNo` 가드 + 중복 흡수를 넣었다(`FraudPostHocListenerTest.redeliveryDoesNotDuplicateReview`).

**결론**: 커밋 후 발행 실패 구간은 프로세스 강제 종료에도 재기동 재발행으로 **8초 안에** 메워진다. 그 8초(로컬 기준, 대부분 앱 기동)가 이 경로에서 정산 지연의 하한이다. 다만 그 대가는 **at-least-once** 이고, 소비자 멱등이 깨진 자리가 하나 있어 같이 막았다.

**재현**: `tools/outbox-republish-experiment.sh` (Kafka 내림 → 승인 → SIGKILL → Kafka 올림 → 재기동 → 토픽 확인).

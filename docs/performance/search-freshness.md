# 검색 색인의 반영 지연: 10분 재색인 · Lucene + CDC · ES + CDC (#246)

상품·가격·재고 변경이 검색 결과에 반영되기까지 p95 는 Lucene + CDC 가 1.12초, ES + CDC 가 1.20초였다. 두 방식 모두 600건 중
놓친 변경이 없었다. 지금 방식(10분마다 전체 재색인)은 60건 모두 30초 안에 반영되지 않았다. 판정 기준은
[이슈 #246](https://github.com/dj258255/BE-commerce/issues/246)에 **측정 전에** 적었다. 결정은
[ADR-056](../adr/ADR-056-search-index-freshness-by-cdc.md).

ADR-051 의 대가에 "새 상품이 검색에 보이기까지 최대 10분"을 적었다. #244 에서 가격·재고가 필터에 들어가면서 이 지연이
필터 결과로 번졌다. 품절된 상품이 "재고 있음" 결과에 최대 10분 남는다.

## 비교한 셋

| 모드 | 변경이 색인에 들어가는 길 | 인스턴스 |
|---|---|---:|
| `lucene-rebuild` | 10분마다 전체 재색인(지금 동작) | 1 |
| `lucene-cdc` | products·stock 변경을 Debezium → Kafka(`catalog.change`)로 받아 **인스턴스마다** 문서를 갈아 끼우고 1초마다 검색기를 다시 연다 | 2 |
| `elasticsearch-cdc` | 같은 이벤트를 색인기 하나(공유 컨슈머 그룹)가 받아 ES 에 bulk. 인스턴스 둘이 ES 하나를 같이 읽는다 | 2 |

두 CDC 모드 모두 **이벤트 내용을 믿지 않고 상품 id 로 DB 를 다시 읽어** 반영한다. products 이벤트와 stock 이벤트의 모양이
다르고, 순서가 바뀌거나 두 번 와도 결과가 지금 DB 와 같아진다.

## 방법

- 변경 셋(종류마다 200건, 초당 20건, 섞어서)을 DB 에 직접 쓴다. 커밋 직후 시각부터 **모든 인스턴스의 검색 API 결과**가 바뀔
  때까지 50ms 간격으로 확인한다
  - 새 상품: 고유한 10글자 검색어. `q=<검색어>` 에 나타나면 반영
  - 가격 인하: 500원으로(카탈로그 최저가 1,000원 아래). `q=<이름>&maxPrice=500` 에 나타나면 반영
  - 품절: 재고 0. `q=<이름>&inStock=true` 에서 빠지면 반영
- 30초 안에 반영되지 않으면 놓친 것으로 센다. 끝나면 바꾼 것을 되돌린다
- `lucene-rebuild` 는 30초 안에 반영될 수 없는 구조라 종류마다 20건만 흘렸다

## 결과

| 모드 | 인스턴스 | 변경 | 놓침(30초) | p50 | **p95** | 최대 | 새 상품 p95 | 가격 p95 | 품절 p95 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| `lucene-rebuild` | 1 | 60 | **60** | — | — | — | — | — | — |
| `lucene-cdc` | 2 | 600 | 0 | 873ms | **1,122ms** | 1,262ms | 1,109ms | 1,112ms | 1,126ms |
| `elasticsearch-cdc` | 2 | 600 | 0 | 735ms | **1,197ms** | 1,390ms | 1,171ms | 1,191ms | 1,243ms |

- **판정 기준(p95 ≤ 3초, 놓침 0)**: 두 CDC 모드 모두 통과. 기준에 적은 대로 **Lucene 을 유지하고 CDC 반영을 켠다**
- **인스턴스 사이 반영 시각 차이**: Lucene 은 중앙값 405ms · p95 672ms, ES 는 40ms · 94ms. Lucene 은 인스턴스마다 검색기를
  다시 여는 1초 타이머가 어긋나 있다. 그 사이 두 인스턴스가 다른 결과를 낸다. ES 는 색인이 하나라 차이가 폴링 오차 수준이다
- **읽는 비용**: 변경 600건과 되돌림 600건에 대해 Lucene 인스턴스는 **각각** 1,200건을 반영했다(DB 재조회 1,200번씩).
  ES 색인기는 전체에서 1,200건이다. Lucene 은 인스턴스 수만큼 곱해진다

Lucene 의 p50 873ms 는 대부분 검색기 갱신 주기(1초, 평균 대기 0.5초)다. 주기를 줄이면 내려갈 것으로 보지만 재지 않았다.

## 이번에 드러난 것

실측 중에 결함 셋이 나왔다. 셋 다 단위 테스트로는 안 보였고 실제 경로로 재서 드러났다. 머지 전에 고쳤다.

| 무엇 | 어떻게 드러났나 | 고친 것 |
|---|---|---|
| **ES 색인기가 비 ASCII 설명을 깨뜨렸다** | 1차 실측에서 ES 가 20건을 놓쳤다. 로그에 `document_parsing_exception`. bulk 본문을 문자열로 보내 `application/x-ndjson` 에 문자셋이 없었다 | UTF-8 바이트로 보내고 문자셋을 밝힌다. `EngineIndexerTest` |
| **문서 하나의 거절이 배치 전체를 붙잡았다** | 거절된 문서 때문에 배치를 던지니 같은 배치의 다른 변경까지 재시도에 묶였다 | 문서 거절(4xx)은 세고 넘기고(`catalog.search.indexer.rejected`), 연결 실패·5xx·429 만 던진다 |
| **Lucene 인스턴스가 기동마다 토픽 전체를 다시 읽었다** | 반영 수가 변경 수의 두 배였다. 변경 없이 기동만 해도 2,299건을 반영했다. 적재 시각으로 찾기가 뒤에 레코드가 없으면 위치를 못 정하고 전역 `earliest` 로 떨어졌다 | 이 리스너만 `auto.offset.reset=latest`. 기동 도중(적재 뒤, 구독 전)에 넣은 상품이 검색되는 것도 확인했다 |

1차(문자셋 결함 포함)와 2차(탐색 결함 포함) 결과는 원자료에 남겼다. 위 표는 셋을 고친 코드로 잰 3차다.

## 한계

- 초당 20건으로만 쟀다. 카탈로그를 통째로 다시 넣는 것 같은 몰림(수만 건)은 재지 않았다. 그때 Lucene 은 인스턴스마다 같은
  수만 건을 DB 에서 다시 읽는다
- 확인 요청(50ms 간격)이 앱에 부하를 더한다. 지연은 높게 나오는 쪽이다
- 인스턴스 둘, ES 단일 노드, 이 머신 한 대(Apple M2 Pro, 32GB)
- 앱 밖 경로(Debezium 커넥터 장애, 브로커 장애)는 재지 않았다. 10분 전체 재색인을 안전망으로 남긴 이유다

## 재현

```bash
./gradlew -p commerce bootJar
bash tools/run-search-freshness.sh        # 세 모드. debezium·ES 는 스크립트가 띄우고 지운다
python3 tools/search/freshness_eval.py report docs/performance/runs/<날짜>-search-freshness
```

앱 인스턴스는 18090·18091 포트를 쓴다(18081 은 다른 로컬 프로젝트가 쓰는 일이 있다).

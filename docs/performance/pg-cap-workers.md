# 워커 수를 바꿔도 PG 상한의 거절률 식이 맞는가, 상한 40 에서 타임아웃 2초는 무엇을 내는가 (#335)

[ADR-022](../adr/ADR-022-pg-brownout-resource-limits.md)의 다시 볼 조건 두 개를 쟀다. 예측과 판정 기준은
[이슈 #335](https://github.com/dj258255/BE-commerce/issues/335)에 **측정 전에** 적었다.

- **거절률 `1 − 상한 / (도착률 × 지연)` 은 워커 수와 무관하다.** 워커 100 · 150 · 200 × 상한 40 · 80 · 120 중 상한이 워커보다 작은 여덟 칸이 식과 0.0%p 로 같았다
- **상한이 워커 이상이면 상한이 없는 것과 같다.** 워커 100 · 상한 120 에서 거절 0 · 무관한 조회 p95 6.8초 · 결제 p95 9.4초
- **상한 40 에서 read-timeout 2초**는 거절을 73.3% 에서 59.6% 로 줄이고(예측 60%), PG 에 닿은 결제를 전부 미확정으로 만든 뒤(45초에 909건) 복구가 3분 안에 모두 승인으로 닫았다. 대가는 **즉시 승인 0 건**이다. 기본값(5초)은 바꾸지 않는다

## 방법

- `tools/run-pg-brownout.sh 3000 50 45s <read-timeout> <상한>`: PG 지연 3초 · 결제 50/s · 조회(주문 목록) 20/s · 15초 워밍업 뒤 45초. 요구 동시성 50 × 3 = 150
- 워커는 `EXTRA="--server.tomcat.threads.max=N"` 로 바꿨다. 타임아웃 2초 실행은 복구 배치를 기본값(주기 60초 · 청크 500)으로 켜고 `DRAIN_S` 로 미확정이 0 이 될 때까지 1초마다 셌다
- 일회용 MySQL · Redis, 실행마다 DB 를 새로 만들었다. 실행 직전 같은 맥의 CPU 상위 프로세스를 `ps-before.txt` 에 남겼다
- 거절률은 거절 / (승인 + 미확정 + 거절)

- 결제 p95 3,030~3,040ms 는 승인된 결제가 PG 지연 3초를 기다린 값이다. 거절은 바로 돌아오지만 95번째 백분위는 기다린 쪽에 걸린다
- 워커 busy 최대가 상한 + 3~5 에 머문 것은 조회와 로그인 요청 몫이다. 상한 120 · 워커 100 만 워커가 100 에 닿았다
- 타임아웃 2초 실행의 미확정 1,060 은 워밍업(15초 · 초당 10건, 동시성 20 이라 거절 없이 전부 미확정) 151건을 더한 값이다. 결제 최종 상태는 승인 1,060 · 확정 실패(상한 거절) 1,342

## 이 표가 말하지 않는 것

- PG 지연이 3초로 고정이다. 실 PG 처럼 지연이 흩어지면 타임아웃 2초가 끊는 비율은 분포의 꼬리만큼이고, "즉시 승인 0 건"은 가장 나쁜 쪽이다
- 한 번씩만 쟀다. 거절률이 식과 딱 맞은 것은 도착률이 열린 루프로 고정되고 지연이 일정해서다
- 워커를 늘렸을 때의 메모리 · 문맥 전환 비용은 재지 않았다

## 재현

```bash
./gradlew -p commerce bootJar
EXTRA="--server.tomcat.threads.max=150" bash tools/run-pg-brownout.sh 3000 50 45s 5000 80
EXTRA="--app.recovery.enabled=true" DRAIN_S=420 bash tools/run-pg-brownout.sh 3000 50 45s 2000 40
python3 tools/brownout_workers_report.py <실행 폴더들의 상위 폴더>
```

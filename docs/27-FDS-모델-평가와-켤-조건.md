# 27. FDS 모델 평가와 활성화 조건

## 0. 무엇을 했나

규칙 여섯은 **건 하나**만 본다. 금액이 임계를 넘었나, 1분 안에 몇 번 왔나.
그래서 **임계 바로 밑에 붙여 천천히 밀면 아무것도 안 걸린다.**

건들 사이의 관계를 보는 피처 여덟 개를 만들고 로지스틱 회귀 하나를 얹었다. 그리고
그 모델을 **켤 조건을 먼저 숫자로 적었다.** 결론부터 적으면 이렇다.

> **규칙의 창을 늘리는 것이 먼저다.** 여섯 축 중 셋은 손으로 쓴 시간창 규칙 세 줄로 잡히고,
> 모델이 단독으로 이기는 축은 하나다. 그리고 가정 기저율 1% 로 환산하면 정밀도가 8.1% 라
> 이진 플래그로는 못 쓴다. **켠 것은 규칙이 올린 큐의 순서를 바꾸는 것 하나다.**

## 1. 규칙 여섯의 빈틈

| 규칙 | 임계 | 피해 가는 법 |
|---|---|---|
| `HIGH_AMOUNT` | 100만원 초과 | 99만원으로 여러 번 |
| `VELOCITY_EXCEEDED` | 카드당 1분 5회 초과 | 5분 간격으로 민다 |
| `DEVICE_VELOCITY_EXCEEDED` | 기기당 1분 8회 초과 | 매번 기기를 바꾼다 |
| `IP_VELOCITY_EXCEEDED` | IP당 1분 15회 초과 | 매번 IP를 바꾼다 |
| `LONG_INSTALLMENT_HIGH_AMOUNT` | 6개월 이상 **그리고** 100만원 이상 | 금액을 임계 밑에 둔다 |
| `BLACKLISTED_CARD` | 이미 거부된 카드 | 새 카드를 쓴다 |

**시간 창이 1분뿐이다.** 속도 규칙 셋이 창을 쓰기는 하는데 그 길이가 1분이라,
5분 간격으로 미는 것을 못 본다. **시각 자체를 보는 규칙은 없어서** 새벽 3시에 몰아서
하는 것과 낮에 하는 것을 구별하지 못한다.

그리고 **그 카드의 평소 씀씀이라는 기준선이 없다.** 평소 5만원 쓰던 카드의 50만원과
평소 50만원 쓰던 카드의 50만원이 같은 값으로 들어간다. **신호를 조합하지도 않는다.**
금액과 속도가 각각 임계를 넘어야 점수가 붙고, 둘 다 임계 밑인 조합은 0점이다.

## 2. 피처 여덟 개

빈틈 하나에 피처 하나를 맞췄다. `SequenceFeatures` 다.

| 피처 | 겨냥한 빈틈 |
|---|---|
| `nearThresholdRatio` | 고액 임계의 90~100% 구간에 붙여 쪼개는 것 |
| `microCount` | 카드가 살아 있는지 떠보는 1,000원 이하 시도 |
| `escalation` | 승인될 때마다 금액을 올리는 한도 탐색 |
| `deviceChurn` · `ipChurn` | 건수 대비 서로 다른 키 수 |
| `nightRatio` | 00~06시 결제 비율 |
| `windowCount` | 1분 창을 넘겨 천천히 미는 것 |
| `amountToMedian` | 이번 금액 ÷ 그 카드의 과거 중앙값 |

**전부 0~1 로 눌러 담는다.** 단위가 섞이면 가중치가 크기 차이를 흡수해 어느 피처가 일하는지
못 읽는다. 그리고 **어느 피처가 점수를 올렸는지 그대로 내려보낸다**(`topContributors`).
모델이 말하는 신뢰도는 못 믿는다는 것을 docs/19 에서 이미 봤다. **피처 값은 사실이라 사람이
대조할 수 있다.** 다만 기여도(가중치 × 값)는 모델의 결정 함수를 쪼갠 것이지 **실제 부정의
원인을 증명하는 값이 아니다.** 점수가 어떻게 계산됐는지까지만 보여준다.

## 3. 코퍼스: 규칙을 피해 가는 여섯 축

**고액 임계를 넘기는 패턴은 안 만들었다.** 만들면 규칙이 잡고, 그러면 모델이 규칙을 다시
배우는 것을 재게 된다.

```
구조화        임계의 92~99% 를 5~20분 간격으로 6~11회
카드 테스팅   100~900원을 5~10회 떠본 뒤 70~95만원 한 번
한도 탐색     2만원에서 시작해 승인될 때마다 1.6~2.6배
기기 회전     매 건 다른 기기, 같은 IP
IP 회전       매 건 다른 IP, 같은 기기
심야 몰림     새벽 2시대에 5~9회
```

### 3-1. 처음 결과가 100% 였다. 그게 신호였다

첫 회차에 축별 재현율이 여섯 다 100% 로 나왔다. 상위 기여 피처를 찍어 보고 알았다.

```
카드 테스팅 건의 상위 기여 피처: windowCount +12.21, microCount +4.72, ...
```

**모델이 배운 것은 "건수가 많으면 부정"이었다.** 겨냥한 패턴은 안 봤다. 정상을 1~6건에 낮 시간,
같은 기기로 만들어 두고 부정을 5~13건으로 만들었으니 건수만으로 갈렸다.
docs/19 에서 앱 로그에 원인을 이름으로 찍어 두고 모델이 맞혔다고 좋아했던 것과 같은 종류다.
**내가 답을 흘리고 있었다.**

정상도 부정과 같은 구간에서 놀게 고쳤다. 건수 1~14, 다섯에 하나는 야간, 넷에 하나는 기기·IP
를 여러 개 쓰고, 여섯에 하나는 금액이 계단으로 오르고, 다섯에 하나는 임계 바로 밑 고액을 쓴다.

고친 뒤 상위 기여 피처가 `microCount +7.78`로 바뀌었다. 그제야 겨냥한 피처가 일한다.

## 4. 잰 것

학습 절반에서 가중치와 임계를 뽑고, **그 절반을 한 번도 안 본 홀드아웃**에서 잰다.

```
                  재현율    정밀도   정상오탐    경보율
규칙 여섯          24.1%    38.4%    16.9%    19.0%
손으로 쓴 시간창 규칙  39.2%    65.3%     9.1%
모델              55.7%    79.3%     6.4%    21.3%
규칙 또는 모델      69.0%    56.5%    23.2%    37.1%

평균 정밀도(PR-AUC)   규칙 0.339 · 모델 0.752
```

**규칙 재현율 24.1% 는 여덟 축 전체 값이다.** 규칙을 피해 가게 만든 여섯 축만 보면
**0% 다.** 두 값을 섞어 쓰면 안 된다. `rulesCatchNothingByDesign`이 여섯 축에 한정해
그 선을 고정한다.

**지표를 셋으로 두는 이유.** 재현율만 보면 전부 올리면 100% 가 되고, 정밀도만 보면 확실한
것만 올려 대부분을 놓친다. **경보율**이 있어야 심사 인원이 감당할 양인지 알 수 있다.
임계와 무관한 비교는 **PR-AUC**로 한다. 정상이 압도적으로 많은 표본에서 ROC-AUC 는 오탐이
늘어도 거의 안 움직여 좋아 보인다.

### 4-1. 손으로 쓴 시간창 규칙 세 줄이 세 축을 잡는다

**이게 이 문서에서 제일 중요한 결과다.** 모델을 고른 이유를 대려면 **더 단순한 것으로
안 되는지**를 먼저 봐야 한다. 그래서 같은 창을 쓰는 규칙 세 줄을 손으로 짜서 같이 쟀다.

```
소액(1,000원 이하) 3건 이상  또는  임계 90~100% 구간 3건 이상  또는  기기 5개 이상
```

```
축별 (시간창 규칙 / 모델)
  structuring      17/17  /  13/17     규칙이 더 잘 잡는다
  card_testing     21/21  /  21/21     같다
  device_rotation  20/20  /  13/20     규칙이 더 잘 잡는다
  escalation        4/16  /   5/16     둘 다 못 잡는다
  ip_rotation       0/24  /   1/24     둘 다 못 잡는다
  night_burst       0/22  /  18/22     모델만 잡는다
```

**모델이 단독으로 이기는 축은 심야 몰림 하나다.** 나머지 다섯 중 셋은 규칙 세 줄로 잡히고,
둘은 양쪽 다 못 잡는다. 그러니 이 실험이 말하는 것은 **"규칙의 창을 늘리는 것이 먼저다"** 다.
"ML 이 필요하다" 까지는 못 간다.

합계로는 모델이 낫다(재현율 55.7% 대 39.2%, 정상 오탐 6.4% 대 9.1%). 그런데 그 차이의
대부분이 한 축에서 나온다. **규칙 세 줄을 엔진에 올리고 나서, 남는 축에 대해 모델이 그
값어치를 하는지 다시 재는 것이 순서다.** 대사 원인 분류(`docs/15`)에서 판정 조건을 코드로
강제하고 보니 그 조건을 통과하는 자리에서는 규칙이 이미 같은 답을 내던 것과 같은 자리다.
규칙으로 되는 것을 모델로 하면 운영 비용만 는다.

### 4-2. 축별로 갈라 보면 다르다

```
card_testing        21/21 (100%)
night_burst         18/22 ( 82%)
structuring         13/17 ( 76%)
blatant_high_amount 12/19 ( 63%)
escalation           5/16 ( 31%)
ip_rotation          1/24 (  4%)
```

**IP 회전을 거의 못 잡는다.** `ipChurn`이 여행하거나 와이파이를 바꾸는 정상 사용자와
안 갈리기 때문이다. 정상 넷에 하나를 그렇게 만들어 뒀다.

### 4-3. 정밀도 79.3% 는 인용하면 안 되는 숫자다

정밀도는 **기저율에 그대로 끌려간다.** 이 코퍼스는 부정이 30.4% 다. 재현율과 정상 오탐을
고정한 채 환산하면 이렇다. **실 트래픽에서 확인한 값이 아니므로 "가정한 기저율" 이다.**

```
이 코퍼스   30.4%  ->  정밀도 79.3%
가정 기저율  1.0%  ->  정밀도  8.1%   (심사 100건에 진짜 8건)
가정 기저율  0.1%  ->  정밀도  0.9%   (심사 100건에 진짜 1건)
```

**이 한 줄이 결론을 정한다.** 가정 기저율 1% 에서 8.1% 다. 아래 5-2 절의 조건 A(20%)를
**못 넘겼다.** 지금 성능으로 이진 플래그를 걸면 심사 큐가 정상으로 찬다.

### 4-4. 런타임 조건으로 다시 쟀다

결제 완료 이벤트가 Zero-Payload 라 런타임에는 `ip`·`deviceId`가 없다. 홀드아웃 성적은
피처 여덟로 낸 값이라 그대로 쓸 수 없다. **그 두 값을 지우고 같은 조건으로 다시 학습하고
다시 쟀다.**

```
피처 여덟   재현율 55.7% · 정밀도 79.3% · 정상 오탐 6.4%
피처 여섯   재현율 52.5% · 정밀도 77.6% · 정상 오탐 6.6%
```

**3.2%p 낮다. 잰 값이다.** 앞서 "낮을 것" 이라고만 적어 뒀던 자리를 숫자로 채웠다.
잃는 것이 적은 이유는 애초에 `ipChurn` 축의 재현율이 4% 였기 때문이다.

## 5. 그래서 켤 조건

업계가 부정거래 모델을 올리는 순서를 그대로 따른다.

### 5-1. 켠 것: 큐 정렬

**처음에는 이 근거를 틀리게 댔다.** 전체 홀드아웃에서 잰 `P@10`·`P@30`으로 큐 정렬을
정당화했는데, 그 표본에는 **규칙이 올리지도 않은 건들이 들어 있다.** 큐 정렬이 나은지에
대해 아무 말도 못 하는 값이었다.

**규칙이 올린 건들만 놓고 다시 쟀다.** 그러려면 코퍼스에 규칙이 잡는 부정과 규칙이 잘못
잡는 정상이 있어야 한다. 고액 장기할부를 양쪽에 만들었다. **훔친 카드로 한도를 긁는 것과
혼수를 12개월 할부로 사는 것은 규칙에 똑같이 보인다.** 둘 다 30 + 20 = 50점이라 같은 큐에
들어간다. 가르는 것은 흐름뿐이다.

```
규칙이 올린 99건 중 부정 38건 (38.4%)

              P@5    P@10   P@20
무작위          0%     10%    35%
기존(최신순)     0%      0%    20%
모델 점수순    100%    100%   100%
```

**무작위 순서가 기준선이다.** 그 값은 큐의 부정 비율로 수렴한다. 최신순은 이 코퍼스의
시각 분포에 휘둘려 실 트래픽의 도착 순서를 재현하지 못하므로 참고만 한다.

**주장할 수 있는 것을 정확히 적는다.**

- 이 코퍼스의 큐에서 모델 순서가 무작위·최신순보다 위쪽에 부정을 더 모은다
- **모델 때문에 심사 대상 건수가 늘지 않는다.** 큐에 넣고 빼는 것은 규칙만 한다
- 정렬 품질은 **후보 집합의 구성에 따라 달라진다.** 순위 지표라고 기저율 영향이 사라지지
  않는다. 실 트래픽의 큐가 이 코퍼스와 다르면 이 값도 다르다

### 5-2. 큐에 새로 넣으려면

**조건 A.** 가정 기저율 **1% 에서 환산 정밀도 20% 이상.** 지금 8.1% 라 **못 넘겼다.**
정상 오탐 6.4% 를 **1% 아래로** 내려야 닿는다.

**조건 B.** 축 여덟 중 **다섯 이상이 50% 를 넘을 것.** 지금 넷이다.

**조건 C.** 섀도 모드로 **먼저 돌린다.** 붙였다(6-2절).

**조건 D.** 상시 홀드아웃을 둔다. 붙였다(6-2절).

**조건 E.** 손으로 쓴 시간창 규칙 세 줄을 **먼저 엔진에 올리고**, 그 위에서 모델이 여전히
이기는지 다시 잰다. 4-1 절이 그 이유다. 규칙으로 되는 것을 모델로 하면 운영 비용만 는다.

### 5-3. 차단까지 가려면 조건이 다르다

차단은 오탐이 곧 매출 손실이다. 위에 더해 docs/17 §5 가 적은 셋이 남는다.

- Redis가 죽으면 결제가 어떻게 되나. 지금 `fail-open`은 사후 탐지라 되는 선택이고,
  승인 경로에서는 **부정거래를 통과시키는 결정**이 된다
- `CHALLENGE`를 받을 곳이 없다. 추가 인증 흐름이 없어 지금 이 등급은 이름만 있다
- 홀드아웃이 필요해진다. 지금은 아무것도 안 막아서 필요 없던 것이다

**막을 준비가 판정 속도보다 큰 일이다**는 판단은 그대로다.

### 5-4. 지금 무엇이 켜져 있나

| 기능 | 상태 |
|---|---|
| ML 점수 산출·기록 | **런타임에서 돈다.** 사후 탐지 리스너가 결제마다 낸다. 홀드아웃 5% 는 안 낸다 |
| 심사 큐 순서 변경 | **옵션으로 열려 있고 기본이 아니다.** `?order=risk`로 고를 때만 바뀐다 |
| LLM 심사 초안 | **평가용으로만 만든다.** 심사 화면에는 템플릿이 나간다 |

"켰다" 와 "섀도" 를 섞어 쓰지 않는다. 셋의 상태가 각각 다르다.


## 6. 붙인 것

5-1 절의 큐 정렬과 5-2 절의 조건 C·D 를 실제로 만들었다.

### 6-1. 창이 없어서 모델이 런타임에 아예 못 돌고 있었다

피처는 그 카드의 최근 결제가 있어야 만들어지는데 **그 목록이 어디에도 없었다.**

```
payments        card_key 컬럼이 없다. paymentKey 만 있다
fraud_reviews   card_key 는 있는데 걸린 건만 들어간다. 정상 거래가 빠져 창이 아니다
Redis velocity  1분 TTL 이라 창이 아니고, 죽으면 그 집계가 사라진다
```

docs/17 §5-1 이 "속도 집계를 캐시에만 두고 있다" 고 적어 둔 그 구멍이 여기서 그대로 막았다.
`card_transactions`(V43) 를 만들어 사후 탐지 리스너가 **판정보다 먼저** 한 줄 남긴다.
순서가 뜻을 갖는다. 이번 건이 창에 들어야 `windowCount`와 `escalation`이 이번 결제를 반영한다.

**주문번호에 유니크를 걸었다.** 아웃박스가 at-least-once 라 같은 이벤트가 두 번 온다.
두 번 들어오면 창의 건수가 부풀어 두 피처가 통째로 틀어진다.

### 6-2. 섀도와 홀드아웃 (조건 C·D)

`ShadowRiskScorer`가 점수를 내고 **기록만 한다.** 심사 큐에 넣지 않으므로 경보율이 안 늘고,
켤지 정할 근거가 실 트래픽에서 쌓인다. `fds.model.shadow.enabled`로 끈다.

홀드아웃은 **켜기 전에 뒀다.** 켠 다음에 만들면 이미 비교할 이전이 없다. 5% 는 점수를
아예 안 내고 그 구간이 나중에 기준선이 된다. **주문번호 해시로 가른다.** 난수면 재배달마다
결과가 바뀌어 그 건이 어느 쪽이었는지 사후에 못 짚는다.

### 6-3. 남은 한계

- **`deviceChurn`과 `ipChurn`이 런타임에는 못 돈다.** `PaymentConfirmedEvent`가
  Zero-Payload 라 요청 시점 신호(ip·deviceId)가 안 실려 온다. 여덟 중 여섯만 산다.
  코퍼스에서 이미 IP 회전 축의 재현율이 0% 였으니 잃는 것이 적기는 하지만, **런타임 성적이
  홀드아웃 성적보다 낮을 것**이라는 뜻이다
- **가중치를 서비스가 다시 학습하지 않는다.** 학습은 평가 하네스가 하고 결과 가중치를
  설정으로 준다. 서비스가 스스로 배우면 언제 무엇으로 배운 모델인지 못 짚는다
- **이 라벨이 실제 부정거래라는 근거는 없다.** 우리가 정의한 패턴이다. 낼 수 있는 말은
  **"규칙이 건 하나만 보기 때문에 이런 축을 못 잡는다"** 까지다

### 6-4. 정답의 입구는 차지백이다

**라벨의 입구를 새로 만들 뻔했는데 이미 있었다.** `disputes`가 `chargeback_id`를 멱등키로
PG 웹훅을 받고 `reason`과 승패를 남긴다. 새 표를 만들었으면 같은 사실이 두 곳에 갈라져
앉는다. `narrative_audits`가 "재구성되는 것을 또 저장하면 두 곳이 언젠가 갈라진다" 고
적어 둔 것과 같은 실수가 된다.

**심사 결과와 다른 값이다.** 심사를 승인으로 닫은 것은 그 사람이 정상이라고 봤다는 뜻이다.
분쟁 결과는 카드 소유자가 이의를 제기하고 발급사가 판정한 것이다.
상황 6.1 이 "운영자 심사 결과이지 따로 검증된 사실은 아니다" 라고 적어 둔 빈자리가 여기다.

**다만 이것은 정답이 아니다. 대리 라벨(proxy label)이다.** 분쟁 승패에는 우리가 낸 증거의
질과 카드 브랜드의 책임 이전 규정이 함께 작용한다. 실제 도용이었는데 증거를 잘 내서 이길
수도 있고, 정상 거래인데 증거가 부족해 질 수도 있다. **승패를 정상·부정의 확정 정답으로
쓰면 안 되고, 지금 있는 것 중 가장 독립적인 신호라서 쓰는 것이다.**

| 사유 | 승패 | 라벨 |
|---|---|---|
| `10.4` · `4837` · `FRAUD` · `도용` | LOST | **FRAUD** |
| 같은 사유 | WON | LEGITIMATE. 발급사가 우리 손을 들어 줬다 |
| `13.1 상품 미도착` · `중복 청구` | LOST | LEGITIMATE. 부정 판정의 정답이 아니다 |
| 무엇이든 | OPEN | UNKNOWN. 밀릴수록 라벨이 좋아 보이면 안 된다 |

`LabelledScoreReport`가 이 라벨로 섀도 점수를 다시 잰다.
**그 결제 뒤에 일어난 거래는 창에서 뺀다.** 넣으면 미래를 보고 채점하는 셈이라 당시엔 못
잡았을 건을 잡은 것으로 센다.

**이 라벨도 완전하지 않다. 셋 다 업계가 안고 가는 것이다.**

- **사유 코드에 잡음이 있다.** Visa 10.4(Fraud, Card-Absent Environment)와 Mastercard
  4837(No Cardholder Authorization)에 진짜 도용·친구사기·가맹점 오류가 섞여 온다
- **승패가 사실을 뒤집지 않는다.** 증거의 질과 책임 이전 규정이 결과를 바꾼다
- **안 걸린 부정은 안 보인다.** 카드 소유자가 못 알아챘거나 이의 기한을 놓친 건은 영원히
  정상으로 남는다. 놓친 것을 못 세니 **재현율이 실제보다 높게 나온다**
- **늦게 온다.** 차지백은 결제 뒤 수십 일에서 몇 달 걸려 도착한다. 오늘 낸 점수를 오늘
  채점할 수 없다

**표본이 없으면 비율을 `null`로 낸다.** 0 으로 채우면 다 놓친 것처럼 읽히고, 그 숫자를
근거로 모델을 손보게 된다. 부정 라벨 20건 밑이면 `usable`이 거짓이다.

## 7. 심사 초안도 같은 순서를 밟는다

심사 초안(`assist.fraudreview`)은 **기본이 템플릿이다.** 상황 5.2 의 상담 초안은 블라인드
비교로 템플릿보다 수정량이 적은 것을 보고 켰는데, 이 자리는 **그 표본이 0 건이다.**

`fraud_draft_reviews`(V44) 로 그 비교를 만들었다. V26 을 재사용하지 않은 것은 그 표가
대사 상담 초안에 묶여 있어 **두 실험의 표본이 한 표에 섞이기** 때문이다.

**순서를 엔티티가 강제한다.** 메모를 쓰기 전에는 초안을 못 보고, 초안을 본 뒤에는 메모를
못 쓴다. 다시 열어도 같은 문장 같은 순서다. 채점이 심사자가 본 화면과 맞아야 한다.

### 7-0. 심사 메모에 무엇이 들어가야 하나

업계의 수동 심사는 **① 왜 걸렸는지 확인 → ② 오탐인지 본격 조사할지 판단 → ③ 고객·거래 자료로
검증 → ④ 결정과 근거를 남긴다** 순으로 돈다. 사건 관리 도구가 하는 일이 증거를 모으고
**결정 근거를 감사 추적으로 남기는 것**이다.

그 넷 중 **③을 이 시스템은 대부분 못 한다.** 배송지·이메일·과거 기록으로 검증하는 자리인데,
사후 탐지는 승인된 건만 받고(거절 비율이 없다) 창이 카드 하나로만 묶인다(같은 기기의 다른
카드를 못 본다). 그래서 심사 메모가 담을 수 있는 것은 셋이다.

| 칸 | 무엇을 적나 |
|---|---|
| **걸린 것** | 발동한 규칙과 그 값 |
| **의심되는 것** | 그 규칙이 가리키는 축(카드 떠보기·기기 회전·금액 쪼개기 등) |
| **못 봐서 확정 못 하는 것** | 판정 표본이 없다 · 지난 심사가 없다 · 이 화면에 없는 자료 |

**셋째 칸이 이 실험에서 제일 값이 크다.** 초안이 그 자리를 채워 주는지가 곧 "초안이 심사자의
일을 덜어 주나"다. 그리고 이 시스템은 못 보는 것이 원래 많다.

#### 7-0-1. 자료가 말한 것과 내가 해석한 것

섞어 두면 나중에 "이 기준의 근거가 뭐였나"에 답을 못 한다. 갈라 적는다.

**자료에 숫자로 명시된 것** (Chargeflow, 카드 테스팅)

- 소액 승인이 **0.50~5 달러 구간**에서 급증하거나 **0 달러 승인 요청**이 연달아 뜨는 것
- **한 IP 에서 분당 수십 건** 시도
- 거절 급증은 "abnormal surge" 라고만 하고 **비율 임계는 안 준다**

**자료가 개념만 말하고 숫자를 안 준 것** (SEON, 카드 테스팅)

- "같은 기기나 위치에서 여러 카드로 여러 번 시도" — 몇 개가 여럿인지 안 적혀 있다
- 기기 지문·위험 점수 — 임계값 없음

**내가 해석해서 만든 것** (자료에 없다)

- `MICRO_PROBE(300)`을 카드 떠보기 축으로 읽은 것. **자료의 구간은 달러이고 우리 임계는 원**이라
  같은 값이 아니다. 300 원이 0.5~5 달러 구간에 대응한다는 근거는 없다
- `DEVICE_CHURN(6)`을 **자동화·계정 탈취** 축으로 읽은 것. 자료의 신호는 **같은 기기에 여러 카드**
  인데 우리 규칙은 **한 카드에 여러 기기**다. 방향이 반대라 자료가 그대로 적용되지 않는다
- 판정 표본이 0 건일 때 "확정 못 한다"고 쓰는 것. 이건 자료가 아니라 **이 저장소의 6.1 이 만든
  지표**에서 나온 판단이다

**그래서 이 기준으로 낸 판정은 업계 관행의 적용이 아니라, 그것을 참고해 내가 만든 규칙의 적용이다.**

**고치는 기준을 재기 전에 못 박았다.** 상황 5.2 에서 무너진 자리가 여기다.

> 발송 가능하게 고친다. 사실이 틀렸거나 빠졌으면 고치고, 심사자를 오해시킬 표현도 고친다.
> **뜻이 통하는데 어색하기만 한 문장은 안 고친다.**

**무엇을 고치는지도 셋으로 못 박는다.** 회차마다 다르게 판단하면 두 편집률이 비교가 안 된다.

| | 이 실험의 선택 | 왜 |
|---|---|---|
| 규칙 이름(`DEVICE_CHURN`) | **그대로 둔다** | 내부 심사자가 읽는 글이고 이름 자체가 정보다 |
| 사실과 다른 표현 | **고친다** | 기준에 명시돼 있다 |
| 문장 순서·형식 | **안 손댄다** | 뜻이 통하면 안 고친다 |

마지막 줄이 상담 초안에 없던 것이다. 비문을 고칠지를 안 정해 둔 탓에 회차별 편집률이 두 배
벌어졌고 개선 폭을 확정하지 못했다. 기준을 좁게 두는 이유는 하나 더 있다 — 이 글은 내부
심사자가 읽는 것이라 문장을 다듬는 것이 목적이 아니다.

켤 조건은 상담 초안과 같다. **판정 12건 이상에서 모델 초안의 편집률 중앙값이 템플릿보다
낮을 것.** 지금은 0건이라 못 켠다.

### 7-1. 표본이 영원히 안 쌓이는 구조였다

처음에는 `provider` 하나로 **모델을 돌릴지**와 **화면에 무엇을 내보낼지**를 같이 정했다.
그러면 `provider=template` 일 때 모델 어댑터가 아예 빈이 안 뜨고, 블라인드 비교의
`FraudReviewDraftPort`에 **템플릿이 주입된다.**

**템플릿 대 템플릿을 비교하고 있었다.** 편집률 차이가 0 으로 나오고, 그 0 을 보고
"모델이 템플릿보다 낫지 않다" 고 읽게 된다. 비교를 안 한 것인데 했다고 착각하는 형태다.

플래그를 둘로 갈랐다.

```
app.assist.fraud-review-provider          화면에 무엇이 나갈지    (template)
app.assist.ollama.fraud-review-enabled    모델을 돌릴지          (별도)
```

모델을 켜면 블라인드 비교에서 모델 초안이 만들어지고 **심사 화면에는 여전히 템플릿이
나간다.** 탐지 모델을 섀도로 돌리는 것과 같은 구조다. 표본이 쌓여 조건을 넘기면 그때
`provider`를 바꾼다.

**`@Primary`로 갈라서는 안 된다.** 모델이 빈으로 떠 있다는 사실만으로 화면이 바뀌면
근거를 모으기도 전에 켜 버리는 셈이 된다. 서빙 쪽은 이름으로 고르고, 블라인드 비교는
템플릿이 아닌 구현을 명시적으로 집는다. 없으면 공개를 거절해 **"표본 0건" 과
"모델이 꺼져 있음" 이 화면에서 구별된다.**

### 7-2. 재 보다 멈췄다 (2026-09-09)

**전환 조건은 못 채웠고, 채우려다 표본이 오염된 것을 알고 멈췄다.**

| 평가 주체 | 판정 | 모델 초안 편집률 중앙값 | 템플릿 | 경과 시간 중앙값 |
|---|---|---|---|---|
| `HUMAN` (전환 조건) | **0건** | — | — | — |
| `HUMAN_AI_ASSISTED` | 3건 | 25.1% | 0.0% | 95초 |
| `AI` | 12건 | 2.5% | 0.0% | 151초 |

#### 왜 멈췄나

사람 판정을 세 건 저장한 뒤, **그 수정본과 메모가 외부 AI의 도움으로 작성됐다는 것을 심사자가
밝혔다.** 독립적인 사람 평가가 아니다. `HUMAN`으로 두면 전환 조건을 그것으로 채우게 된다.

`HUMAN_AI_ASSISTED`를 따로 뒀다(V48). 이유가 둘이다.

- **편집량이 보조의 영향을 받는다.** 25.1% 대 2.5% 라는 차이를 편집 방식이나 능력 차이로
  설명할 수 없다. 보조 도구가 다른 문장을 낸 것인지, 초안 자체가 회차마다 다른 것인지
  (모델은 부를 때마다 다르게 쓴다) 이 자료로는 못 가린다
- **경과 시간에 외부 AI에 문의한 시간이 들어간다.** 95초를 작업 시간으로 읽으면 안 된다

**세 건에서 멈춘 것이 맞다.** 열둘을 채워도 `HUMAN`은 0 건이고, 못 쓰는 값의 표본을 늘리는
것뿐이다. 그리고 1~3 번은 이미 초안을 봤으므로 **다시 재지도 못한다** — "초안을 보기 전에
메모를 쓴다" 는 순서가 그 건에서는 이미 깨졌다.

#### 그래도 남는 것 — 초안이 사실을 틀리는 자리

편집률은 못 쓰지만 **무엇을 고쳤는지는 남는다.** 세 건에서 나온 것이다.

| 초안이 쓴 것 | 사실 |
|---|---|
| "NEAR_THRESHOLD 규칙의 임계값 970,000원" | 970,000 은 **결제 금액**이고 임계는 1,000,000원 |
| "3건의 결제가 **1만 건 기준**을 넘었지만" | `3/1m`은 **1분에 3건**이다 |
| "같은 카드로 **이전 결제가 없어**" | 없는 것은 **판정이 끝난 심사**이지 거래가 아니다 |
| "판정 표본 0건이므로 **규칙 적용 여부를 재검토**해야 한다" | 표본이 0 이면 **비율을 못 내는 것**이지 규칙을 의심할 일이 아니다 |

**넷째가 가장 위험하다.** 숫자를 안 틀리고 **해석을 틀린다.** `NumericProvenanceGuard`는
숫자만 보므로 안 걸리고, 심사자가 읽으면 규칙을 의심하게 된다. 5.3 에서 본 것과 같은 형태다.

#### 셋은 입력 형식이 원인이었다

앞의 셋은 프롬프트가 규칙 값을 `980000/1000000` 꼴로 **그대로 넘겨서** 생겼다. 어느 쪽이
임계인지 문장에 없으니 모델이 앞 숫자를 집었다. `3/1m`의 `1m`은 백만으로 읽었다.

**타이르는 대신 형식을 바꿨다.** 프롬프트에 "헷갈리지 마라" 고 적으면 지킬 때도 있고 안
지킬 때도 있다. 애초에 헷갈릴 수 없게 준다.

```
NEAR_THRESHOLD    (값 980000/1000000)  ->  (결제 금액 980,000원, 고액 임계 1,000,000원)
VELOCITY_EXCEEDED (값 3/1m)            ->  (최근 1분 안에 3건)
MICRO_PROBE       (값 500)             ->  (소액 결제 500원)
DEVICE_CHURN      (값 6)               ->  (쓰인 기기 6개)
```

같은 세 건에 초안을 다시 뽑으니 **셋 다 사라졌다** — "고액 임계 1,000,000원", "1분 내에 3건",
"500원 소액 결제" 로 나온다.

**템플릿은 안 바꿨다.** 템플릿은 이 실험의 기준선이고 **사람은 이 표기를 오해하지 않았다.**
둘 다 바꾸면 이번에 잰 값과 다음에 잴 값을 견줄 수 없다.

**형식으로 막을 수 있는 데까지다.** 다시 뽑은 초안에도 "1분 내에 3건 **이상**"(사실은 3건)과
"같은 카드로 **이전 결제가 없다**"(없는 것은 판정이 끝난 심사다)가 남았다.

#### 남은 둘은 검사를 하나 더 붙였다

둘 다 **숫자는 맞는데 뜻을 넓힌다.** 3 도 맞고 0 도 맞으니 `NumericProvenanceGuard`를
통과한다. `FactWideningGuard`를 붙여 걸리면 템플릿으로 떨어뜨린다.

| 검사 | 무엇을 보나 |
|---|---|
| 수량 부풀리기 | 규칙이 준 값이 정확한 수인데 초안이 `N건 이상`·`초과`·`넘`으로 쓰는 것 |
| 심사를 거래로 넓히기 | 판정이 끝난 심사가 0 건일 때 `결제·거래·구매 이력이 없다` 고 쓰는 것 |

**실측에서 나온 두 모양만 잡는다.** 일반적인 "넓히지 마라" 는 함의 판정이라 이 자리에서 못 한다.
좁게 잡고 못 잡는 것을 밝혀 두는 편이, 넓게 잡아 멀쩡한 문장을 반려하는 것보다 낫다.

**두 자리에 안전장치를 뒀다.** 사실에 없는 수의 `이상`은 안 잡는다(그건 출처 검증이 맡는다).
지난 심사가 **있는** 경우에는 이력 검사를 안 돌린다(그때는 그 문장이 안 나온다).

**돌려서 확인했다.** 네 건에 초안을 뽑으니 둘이 반려됐다.

```
review=1  없는 것은 판정이 끝난 심사인데 결제·거래가 없다고 씀
review=3  정확한 수를 하한으로 넓힘: 3건 이상
```

**여기까지가 코드로 막은 것이다.** 이 둘 말고 다른 모양으로 넓히면 여전히 통과한다.

### 7-3. AI 평가 12건 — 켤 근거가 아니다

**사람 표본이 0 건인 채로, 같은 12 건을 모델이 평가해 봤다.** `fraud_draft_reviews.evaluator_kind`
를 `AI`로 남겨 사람 기록과 갈라 둔다. **전환 조건이 보는 값은 `HUMAN` 뿐이고 그것은 여전히 0 건이다.**

| 평가 주체 | 판정 | 모델 초안 편집률 중앙값 | 템플릿 편집률 중앙값 |
|---|---|---|---|
| `HUMAN` (전환 조건) | **0건** | — | — |
| `AI` (참고) | 12건 | 2.52% | 0.00% |

**이 표를 사람의 편집 시간 절감으로 읽으면 안 된다.** 재는 것이 다르다.

#### 템플릿 0.00% 는 결과가 아니라 설계의 산물이다

고치는 기준이 **"사실이 틀렸거나 빠졌으면 고친다"** 인데, 템플릿은 사실 묶음을 기계적으로
옮기므로 **사실 오류가 구조적으로 나올 수 없다.** 그래서 이 기준에서 템플릿은 늘 0 이다.

**그래서 이 수치가 답하는 질문은 원래 질문과 다르다.**

| | 질문 |
|---|---|
| 원래 재려던 것 | 초안이 심사자의 일을 얼마나 덜어 주나 |
| 이 기준이 실제로 잰 것 | **모델이 사실을 얼마나 틀리나** |

둘째 질문의 답으로 읽으면 값이 있다. **12 건 중 7 건에서 사실 오류를 고쳤다.**

#### 고친 자리 (7/12)

| 심사 | 무엇이 틀렸나 |
|---|---|
| 1 | "이전 거래 내역이 없다" — 사실은 **심사**가 없는 것이지 거래가 아니다 |
| 2 | "임계값 970000/1000000" — 970,000 은 결제 금액이고 임계값은 1,000,000원이다 |
| 3 | 같은 임계값 오류. 그리고 `3/1m`을 "3건 이상"으로 읽었다(1분에 3건이다) |
| 6 | `MICRO_PROBE(500)`을 **"500점"** 으로 읽었다. 점수가 아니라 금액이다 |
| 7 | `VELOCITY_EXCEEDED(4/1m)`의 4 를 **"4원"** 으로 읽고 "정보가 제공되지 않았다"고 적었다 |
| 10 | 임계값 오류. 그리고 **사실 목록에 없는 문장**("같은 규칙이 발동한 이력이 없습니다")을 지어냈다 |
| 12 | "같은 카드로 결제한 이력은 없습니다" — 심사이지 결제가 아니다 |

**임계값을 결제 금액으로 읽은 것이 셋(1·2·3·10 중 셋)이다.** `NEAR_THRESHOLD(980000/1000000)`
에서 앞 숫자를 임계값으로 집었다. 규칙 근거를 `금액/임계` 꼴로 실어 보내는 형식 자체가
오해를 부르는지 볼 자리다.

**10 번은 출처 검증을 통과한 지어내기다.** "같은 규칙이 발동한 이력이 없습니다" 는 숫자를
안 쓰므로 `NumericProvenanceGuard`에 안 걸린다. 5.3 에서 본 것과 같은 형태 — **가드를 다
통과하고도 사실에 없는 주장이 나온다.**

#### 무엇을 확정하지 않았나

- **모델이 템플릿보다 나은지** — 이 기준으로는 잴 수 없다(템플릿이 구조적으로 0)
- **사람이 얼마나 덜 고칠지** — 사람 표본이 0 건이다
- 사실 오류 7/12 라는 비율 — **한 회차, 표본 12 건, 모델 하나(`qwen3:8b`)**의 값이다. 같은
  프롬프트로 다시 돌리면 모델이 다르게 쓴다(18 문서 9-3 에서 같은 코드로 여섯 번 재니 결손이
  4·0·1·0·1·2 로 흔들렸다) 그리고 그 조건을 넘겨도 **수치를 성능으로 인용하면 안
된다.** 상황 5.2 에서 같은 12건을 두 번 돌려 회차마다 두 배 벌어진 것을 봤다.

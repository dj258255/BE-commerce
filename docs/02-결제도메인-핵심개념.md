# 02. 결제 도메인 핵심 개념: 한국 결제 생태계 이해

> 결제가 어떻게 흘러가는지 이해하기 위한 도메인 지식.
> 이커머스 플랫폼 BE-commerce의 **코어 도메인**이다 — 나머지 화면(탐색·주문·개인화)이 이 위에 얹힌다.
> 주 출처: 토스페이먼츠 공식 개발자 문서 (docs.tosspayments.com)

## 1. 참여자 구조: 가맹점 → PG → 카드사/VAN

```
구매자 ──> 가맹점(우리 서버) ──> PG사(토스페이먼츠 등) ──> 카드사
                                        │
                                       VAN (승인 전문 통신망)
```

- **PG(Payment Gateway)**: 온라인 가맹점을 대신해 카드사 계약·정산을 대행하고 수수료를 받는 사업자. 토스페이먼츠, KG이니시스, 나이스페이먼츠, 다날 등
- **VAN(Value Added Network)**: 상점과 카드사 사이에서 거래 정보(승인 전문)를 주고받는 통신망 사업자
- **간편결제/페이**(카카오페이, 네이버페이, 토스페이, 쿠팡페이)는 단순히 PG 위의 인증 레이어가 아니다.
  이들은 **선불전자지급수단 발행·관리업**(업계에서는 "선불전자금융업") 등록 사업자로, 자기 명의의 선불
  잔액을 발행·관리한다. 그래서 **회원제**이고(내부 이체에 명의가 필요), 카드 결제도 지원하지만 카드사에
  마진을 떼주는 구조라 **선불 충전을 유도한다** — 이 지점에서 카드사와 경쟁 관계가 된다.
  (PG는 별도로 **전자지급결제대행업** 등록이 필요하다. 이름 그대로 대행이고, 실제 결제 처리는 카드사에서 난다.)

## 2. 결제 3단계: 요청 → 인증 → 승인 (토스페이먼츠 공식 정의)

이 3단계 분리가 결제 시스템 설계의 출발점이다.

### ① 요청 (Request)

'결제하기' 클릭 → 토스페이먼츠 SDK의 결제 요청 메서드 호출 → 결제창 오픈.
이때 `orderId`(가맹점 채번), `amount`, `successUrl`/`failUrl` 전달.

### ② 인증 (Authentication)

결제창에서 카드번호·CVC 입력 또는 앱카드/간편결제 → **카드사가 구매자를 카드 소유자로 인증**.
인증 성공 시 `paymentKey` 발급 + `successUrl`로 리다이렉트 (쿼리에 `paymentKey`, `orderId`, `amount`).

### ③ 승인 (Approval)

**가맹점 서버가 시크릿 키로 승인 API(`POST /v1/payments/confirm`) 호출** → PG가 카드사에 최종 승인 요청.

> **왜 요청과 승인을 분리하나?**
> 토스페이먼츠 공식 답변: "데이터 정합성을 보장하고, 상점에서 직접 해야 할 일을 줄이기 위해."
> 한 번에 처리하면 비동기 처리로 인한 데이터 불일치 위험이 커진다. **승인의 최종 트리거를 가맹점 서버가 쥐게 하는 설계**다. 서버가 재고 확인과 금액 검증을 마친 뒤에만 돈이 움직인다.

### 금액 위변조 검증

`successUrl`의 쿼리 파라미터는 클라이언트를 거쳐 오므로 조작될 수 있다.

```
1. 결제 요청 전: 서버에 (orderId, amount) 저장
2. successUrl 리다이렉트 후: 돌아온 amount와 저장된 amount 비교
3. 일치할 때만 승인 API 호출. 불일치 → 승인 거부 + 알림
```

토스페이먼츠 배포 체크리스트에 "클라이언트 요청 금액과 실제 결제 금액 일치 확인 필수"로 명시되어 있다.

### 결제창 방식 vs 키인(Key-in) 방식

- **결제창(인증 결제)**: 카드사 인증을 구매자가 직접 수행하는 일반적인 방식
- **키인(수기/비인증 결제)**: 카드번호만으로 결제. 제한 업종 + 엄격한 심사 필요. 이 시스템은 결제창(위젯) 방식을 쓴다

## 3. 취소: 전액취소 / 부분취소 / 망취소

### 취소 API

`POST /v1/payments/{paymentKey}/cancel`, `cancelReason` 필수.
- `cancelAmount` 생략 → 전액취소 / 지정 → **부분취소**
- 부분취소를 여러 번 하면 응답의 `cancels` 배열에 취소 객체가 누적, 각 건마다 고유 `transactionKey` 발급
- 가상계좌: 입금 전 부분취소 불가, 입금 후 환불은 환불계좌(`refundReceiveAccount`) 필수

### 망취소 (Network Cancel)

**정의**: 승인 요청 후 타임아웃·응답 유실 등 비정상 실패 시 결제를 취소해 원복시키는 처리.
클라이언트는 실패로 판단했지만 PG/카드사에서는 승인이 완료된 **"유령 승인"**을 정리하는 것이 목적.

**토스페이먼츠 정책**: 별도 망취소 API 없음. **일반 취소 API를 쓰되 `cancelReason`에 망취소임을 구분 기재**하라고 안내. (DB 저장 중 에러, 재고 없음 등으로 승인 직후 롤백해야 하는 경우 포함)

**실무 구현 포인트** (taes-k 사례 + 나이스페이 매뉴얼):
- **타임아웃 직후 즉시 취소하면 PG측에 아직 결제정보가 생성되지 않아 망취소가 실패할 수 있다 → 약 1분 지연 후 요청**
- 망취소 유효기간은 통상 1시간 (나이스페이 기준)
- 아키텍처 선택지: ① Kafka 지연 발행 ② 이벤트 테이블 + 1분 주기 배치 폴링 → 실무에선 "확실한 처리"가 중요해 **배치 방식** 선택 (재시도 용이, 구현 단순)
- 망취소 모듈은 일반 결제 프로세스와 물리적으로 분리
- 결제 요청 시 가맹점 채번 요청 ID를 반드시 포함해 추적 가능하게

## 4. 결제 상태머신

### 토스페이먼츠 Payment.status (공식)

```
READY ──> IN_PROGRESS ──> DONE ──> CANCELED / PARTIAL_CANCELED
  │            │            ↕ (가상계좌 입금오류 시 역전이!)
  │            ├──> ABORTED (승인 실패)
  └────────────┴──> EXPIRED (30분 경과)
        WAITING_FOR_DEPOSIT (가상계좌 입금 대기)
```

| 상태 | 의미 |
|---|---|
| `READY` | 결제 생성 초기 상태 |
| `IN_PROGRESS` | 인증 완료 (이 상태에서 승인 API 호출하면 완료) |
| `WAITING_FOR_DEPOSIT` | 가상계좌 입금 대기 |
| `DONE` | 승인 완료 |
| `CANCELED` / `PARTIAL_CANCELED` | (부분) 취소됨 |
| `ABORTED` | 승인 실패 |
| `EXPIRED` | 유효시간 30분 경과로 거래 취소 |

**주의**: 가상계좌에서 송금한도 초과·네트워크 이슈로 입금 오류 시 **DONE → WAITING_FOR_DEPOSIT 역전이**가 발생할 수 있다. 즉, 상태는 웹훅으로 계속 추적해야 한다.

### Stripe PaymentIntent (글로벌 비교 대상)

`requires_payment_method` → `requires_confirmation` → (`requires_action`: 3DS) → `processing` → `succeeded` / `canceled`. 실패 시 `requires_payment_method`로 회귀. `succeeded`, `canceled`만 최종(terminal) 상태.

### 우리 서버의 상태머신 설계 원칙

1. **PG 상태와 별개로 내부 주문/결제 상태머신을 둔다**
2. **허용된 전이만 코드로 강제**: enum + 전이 테이블, `CANCELED → DONE` 같은 불법 전이는 예외 발생
3. 전이는 **조건부 UPDATE** (`WHERE status = :expected`)로 낙관적 동시성 제어
4. **상태 전이 이력(payment_history)을 append-only로 기록** → 감사·대사에 활용
5. 웹훅/폴링/사용자 액션이 동시에 같은 결제를 전이시킬 수 있으므로 **멱등 전이** (이미 목표 상태면 no-op)

## 5. 정산과 대사 (개념, 구현은 03 문서)

- **정산(Settlement)**: 구매자 결제금액에서 PG/플랫폼 수수료를 제외한 금액을 가맹점(판매자)에게 지급하는 프로세스. 결제수단별 수수료율이 다름
- **대사(Reconciliation)**: 내부 기록(주문/결제/원장)과 외부 기록(PG 정산 파일, 카드사 매입 내역)을 건 단위로 대조해 불일치를 찾는 작업
- 신용카드는 **승인 → 매입(전표 제출) → 정산 입금**의 단계적 처리라 각 단계 간 시차·불일치가 구조적으로 발생한다. 이것이 대사가 필요한 근본 이유


## 6. 이 프로젝트는 이 지형의 어디에 있나

위 참여자 구조에서 BE-commerce가 무엇을 구현하고 무엇을 **일부러 안 만들었는지**를 분명히 해둔다.
구현하지 않은 기능은 누락과 의도적 범위 제외를 구분하고, 확장 조건을 함께 기록한다.

| 참여자 | BE-commerce에서 | 이유 |
|---|---|---|
| **가맹점(온라인)** | **구현** — 주문·결제·취소·원장·정산·대사 | 이 프로젝트의 본체 |
| **PG** | **모의(`FakePgClient`) + 실 어댑터(`TossPgClient`)** | 가맹점 입장의 연동 계약을 정확히 재현하는 것이 목적 |
| **페이(선불)** | **부분 구현** — `wallet` 모듈(`CHARGE`/`USE`/`RESTORE`/`REFUND`) | 혼합 결제(카드+포인트+월렛)의 취소 배분을 다루려면 필요 |
| **VAN** | **안 만듦** | 오프라인 단말 영역. 온라인 가맹점은 닿을 일이 없다 |
| **카드사** | **안 만듦** | PG 뒤편. 가맹점이 모델링할 대상이 아니다 |
| **2차 PG(PF)** | **부분** — `RoutingPgClient`의 다중 PG 라우팅 | 포트원·Stripe식 통합 API의 축소판. 다만 정산 대행까지는 아니다 |

### 승인 → 매입 → 정산 중 "매입"을 왜 안 만들었나

매입(전표 제출)은 **PG·카드사 쪽 업무**다. 가맹점은 매입 상태를 직접 전이시키지 않는다.
그래서 BE-commerce에 `CAPTURED` 같은 상태는 없다.

다만 매입이 만드는 **시차는 모델링한다.** 정산의 지급예정일을 `정산일 + N영업일`
(`app.settlement.payout-business-days`, `BusinessDays`가 주말 skip)로 계산하는 것이 그것이다.
가맹점에게 매입은 "상태"가 아니라 **"돈이 늦게 들어오는 이유"**로 나타나고, BE-commerce는 그 형태로 담았다.

같은 이유로 **대사(reconciliation)가 필요해진다.** 승인·매입·정산이 다른 시점에 일어나므로 내부
기록과 PG 기록이 어느 순간에는 반드시 어긋난다. 그 어긋남이 정상인지 사고인지 가르는 것이 대사다.

### 업계에서 "반드시 만난다"고 하는 세 가지

온라인 가맹점이 자체 결제 시스템을 만들면 공통으로 겪는다고 알려진 문제들이다.
BE-commerce가 각각을 어떻게 다루는지 적어둔다.

**① 결제는 됐는데 주문이 안 보인다** — 요청은 갔는데 응답을 못 받은 경우. PG에는 승인, 우리에겐 없음.
> BE-commerce는 이걸 **`UNKNOWN`이라는 3번째 상태**로 명시한다(성공/실패 이분법을 쓰지 않는다). 그리고
> 동기화 경로를 **둘 다** 둔다 — 웹훅 수신(서명 검증·멱등·조회 재검증)과 조회 폴링
> (`PaymentRecoveryService`). 웹훅만 두면 웹훅이 유실될 때 영영 모르고, 폴링만 두면 반영이 느리다.
> 방치 시간은 `payment.unknown.oldest.age` 게이지로 본다 — **개수가 아니라 나이**여야
> "밀리는 중"과 "멈춤"이 갈린다.

**② 이중 결제(따닥)** — 프런트가 못 막으면 서버로 온다.
> 세 겹이다. `Idempotency-Key` 기반 멱등 처리(`IdempotencyService`, 요청 해시까지 대조),
> 주문 상태의 **조건부 전이**(`PENDING_PAYMENT → PAYMENT_IN_PROGRESS`가 성공해야 진행),
> 그리고 `orderNo` 유니크. 프런트를 신뢰하지 않는다.

**③ 부분취소 금액 계산** — 혼합 결제에서 무엇부터 환불할 것인가.
> 업계 조언은 대체로 "정책을 먼저 정하라"에서 멈춘다. BE-commerce는 **정책과 그 근거**를 코드에 둔다
> (`RefundAllocator`): **포인트 → 월렛 → 카드** 순으로 환불한다.
> 카드부터 환불하면 무상 지급 포인트가 현금화되는 어뷰징이 가능하기 때문이다 — 10,000원을
> 포인트 3,000 + 카드 7,000으로 결제한 뒤 7,000원을 카드로 돌려받으면, 포인트 3,000이 사실상
> 현금이 된다. 포인트를 월렛보다 앞에 두는 건 포인트가 적립·프로모션으로 **무상 지급될 수 있어**
> 현금화 유인이 더 크기 때문이다.
> 불변식 `fromPoint + fromWallet + fromCard == cancelAmount`를 생성 시점에 강제한다.

### 원장은 왜 UPDATE가 없나

업계에서 흔히 하는 조언은 "원장 테이블에 update/delete를 하지 마라"다. BE-commerce는 그걸 관례가 아니라
**타입으로 강제한다** — `LedgerTransaction`은 생성 시점에 `차변 합 == 대변 합`을 검증하고,
정정은 오직 **역분개**(반대 분개를 새로 insert)로만 한다. 5,000원 결제 후 취소면
`+5,000` 다음에 `-5,000`을 넣고, 합이 0이 된다. 기존 행은 건드리지 않는다.

이건 회계 원칙이기도 하지만 실무적으로는 **대사와 CS를 위해서**다. 행을 고치면 "그때 무슨 일이
있었는지"가 사라지고, 그러면 고객이 이의를 제기했을 때 재구성할 방법이 없다.

> 이 절은 업계 통용 지식을 정리한 것으로, 라이선스·업무 구분은 실제 계약과 규정에 따라 다를 수
> 있다. 결제 흐름·상태 정의 등 공식 근거가 있는 항목은 아래 출처를 따랐다.

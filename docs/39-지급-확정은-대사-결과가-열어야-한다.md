# 지급 확정은 대사 결과가 열어야 한다

## 이전 경로의 문제

기존 어드민은 `POST /api/v1/admin/settlements/{id}/payout`을 호출하면 외부 지급 결과를
확인하지 않고 `CREATED → PAID_OUT`으로 바꿀 수 있었다. 이 구현은 화면에서는 단순하지만,
내부 정산 금액과 실제 PG·은행 게시 금액이 다를 때도 원장에 지급 회수 분개가 남는다는 문제가 있다.

`PAID_OUT`은 “지급 요청을 보냈다”가 아니라 “외부 지급이 최종 게시됐고 내부 기대치와 연결됐다”는
사건이어야 한다. 이제 해당 API는 외부 report 한 행을 받아 대사하고, `MATCHED`일 때만 상태를
바꾼다.

## 현재 확정 경계

정산은 생성될 때 `payoutInstructionReference`를 만든다.

```text
SETTLEMENT-{settlementDate}-{currency}-{sellerId}
```

외부 report 한 행은 `payoutReference`, `currency`, `amount`, `posted`를 보낸다.
`PayoutReconciliationEngine`의 결과가 `MATCHED`일 때만 같은 트랜잭션에서 `PAID_OUT`으로 전이하고,
그때만 `SettlementPaidOutEvent`를 발행한다. 그 외 결과는 지급하지 않고 마지막 관측값을 저장한다.

| 결과 | 정산 상태 | 다음 행동 |
|---|---|---|
| `PENDING` | `CREATED` | 같은 reference의 다음 report를 기다린다 |
| `AMOUNT_MISMATCH` | `CREATED` | 수수료·reserve·환불·차지백 계약을 확인한다 |
| `CURRENCY_MISMATCH` | `CREATED` | 환율·반올림 정책을 확인한다 |
| `UNMATCHED_SETTLEMENT` | `CREATED` | 외부 report 누락 또는 reference 매핑을 확인한다 |
| `MATCHED` | `PAID_OUT` | 지급 회수 분개와 감사 로그를 확인한다 |

금액만 같다는 것은 같은 지급이라는 증거가 아니다. 두 판매자의 지급액이 같을 수 있고 외부
report가 재수집되면서 같은 행이 중복될 수도 있다. reference·통화·posted 금액을 모두 요구하면
확정이 늦어질 수 있지만, 현재 실제 은행·PG report 계약이 없는 상태에서는 잘못된 원장 회수를
막는 쪽을 선택했다.

## 검증

- `SettlementTest`: `MATCHED` 없이는 엔티티가 지급 확정되지 않음
- `SettlementAdminServiceTest`: pending은 기록만 하고 exact posted report만 `PAID_OUT`
- `PayoutReconciliationEngineTest`: 누락·중복·pending·금액·통화 불일치 결정론적 판정
- Flyway `V65__settlement_payout_reconciliation.sql`: 기존 행은 legacy reference만 백필하고 외부
  대사 결과는 만들지 않음

아직 실제 PG·은행 report 계약을 검증한 것은 아니다. 해당 검증에는 테스트 계정, report 샘플,
reference의 생명주기, 재수집 시 식별자 보장이 필요하다.

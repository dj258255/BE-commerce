# 26. FDS 규칙별 오탐 분석

## 0. 무엇이 문제였나

이상거래 심사의 전체 오탐률을 세기 시작했다(`fraud.review.false.positive.ratio`).
70% 를 넘고 판정이 20건 이상이면 알림이 운다.

**그런데 알림을 받고 나서 할 일이 없다.** 규칙이 여섯인데 어느 것이 정상 거래를 잡고
있는지 지표가 말해 주지 않는다. 그 상태에서 할 수 있는 것은 임계를 다 조이는 것뿐이고,
그러면 **잘 잡던 규칙의 정탐까지 같이 사라진다.**

대사 쪽에는 이미 이 순환이 있었다.

```
규칙이 답한다 → 맞히는 비율을 잰다 → 못 가른 것만 모델 → 사람 패턴을 규칙으로 올린다
                (ClassifierAccuracyMetrics)              (RulePromotionService)
```

이상거래 쪽은 두 번째 칸까지만 있었다.

## 1. 라벨은 이미 있었다

심사를 **승인**으로 닫으면 규칙이 잡았는데 정상이었다는 뜻이고, **거부**면 실제
부정이었다는 뜻이다. 발동한 규칙도 `fraud_reviews.reasons`에 콤마로 이어 저장돼 있다.

```
"VELOCITY_EXCEEDED(7), HIGH_AMOUNT"
```

새로 남길 것이 없었다. **세는 곳만 없었다.**

## 2. 괄호 안을 떼야 표본이 모인다

근거에는 그때의 발동 횟수나 할부 개월이 붙는다. `VELOCITY_EXCEEDED(3)`과
`VELOCITY_EXCEEDED(9)`는 같은 규칙인데, **떼지 않으면 값마다 쪼개져** 표본이 하나씩
흩어지고 어느 것도 판정 20건을 못 넘긴다.

콤마로 나누고 괄호 앞까지만 남긴다. 한 건 안에서 같은 규칙이 두 번 나오면 한 번만 센다.
**발동 횟수가 아니라 심사 건수를 센다.**

## 3. 규칙 둘이 같이 걸린 건은 양쪽에 다 센다

한 건에 `HIGH_AMOUNT`와 `IP_VELOCITY_EXCEEDED`가 같이 걸렸는데 사람이 정상으로 닫았다면
둘 다 오탐 쪽으로 올린다. **어느 쪽이 진짜 원인인지는 심사 기록에 안 남아 있다.**
한쪽에 몰아주려면 없는 근거를 지어내야 한다.

그래서 규칙별 합계는 심사 건수보다 클 수 있다. 이건 버그가 아니라 이 집계의 정의다.

## 4. 문턱을 알림과 같은 숫자로 맞췄다

```
MIN_JUDGED = 20        FraudFalsePositiveHigh 의 fraud_review_judged_count >= 20
MIN_RATIO  = 0.7       FraudFalsePositiveHigh 의 ratio > 0.7
```

**알림이 울려서 화면을 열었는데 화면의 기준이 다르면**, 알림은 울리는데 짚이는 규칙은
없는 상태가 생긴다. 그때 사람은 화면을 안 믿게 된다.

## 5. 기준을 넘긴 것만 주지 않는다

`GET /api/v1/admin/fraud-reviews/rule-false-positives`는 **전부** 돌려준다. 잘 맞히는
규칙도 오탐률 0 으로 목록에 남는다.

넘긴 것만 주면 화면이 비었을 때 **규칙이 다 멀쩡한 것인지 표본이 아직 없는 것인지**
구분이 안 된다. 그 둘은 다음에 할 일이 다르다. 대사의 `RulePromotionService`가 후보를
전부 주는 것과 같은 이유다.

판정 이력이 아예 없으면 **빈 목록**이다. 오탐률 0 으로 채우지 않는다 — 표본이 없는
것을 0 으로 적으면 규칙이 멀쩡한 것처럼 보인다.

## 6. 여기서 임계를 자동으로 바꾸지 않는다

규칙을 조이면 놓치는 부정 거래가 생기고 그건 돈이다. 이 서비스가 하는 일은
**"이 규칙을 볼 이유"를 숫자로 만드는 것**까지다. 대사에서 규칙을 **올리는** 판단을
사람에게 남긴 것과 같고, 방향만 반대다.

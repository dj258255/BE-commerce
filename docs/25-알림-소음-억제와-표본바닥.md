# 25. 알림 소음 억제와 최소 표본 설계

## 0. 무엇이 문제였나

알림 규칙이 스물이 됐다(이 글에서 하나를 더 붙여 지금은 **알림 21개 + 기록 규칙 1개**다.
`promtool`은 둘을 합쳐 22 로 세는데, **기록 규칙은 울리지 않는다**). 그런데 세 가지를 안 보고 있었다.

1. **한 고장이 만드는 알림을 묶기만 했지 줄이지는 않았다.** DB 하나가 죽으면 여섯이
   뜨는 것을 재서 `db-outage-probe`로 고정해 뒀는데, 고정만 했지 억제는 안 걸었다
2. **비율 알림의 분모가 작을 때를 안 봤다.** 성공률 95% 임계는 하루 종일 같은 숫자다
3. **시간대별 편차를 못 본다.** 평일 점심의 96% 와 새벽의 96% 는 같은 값이 아니다

## 1. 묶는 것과 안 보내는 것은 다르다

`group_by: ['domain', 'severity']`는 여섯 건을 두 묶음으로 만든다. 그런데 **묶음 안에서
무엇이 원인이고 무엇이 파생인지는 말해 주지 않는다.** 사람이 다섯 줄을 읽고 스스로 골라야
한다. 승인이 안 되니까 아웃박스가 안 비는 것인데, 화면에서는 둘이 나란히 있다.

`inhibit_rules` 넷을 걸었다.

```
PaymentSuccessRateLow   → 같은 도메인의 warning 전체
FraudVelocityFailOpen   → FraudFalsePositiveHigh
DisputeDeadlineMissed   → DisputeDeadlineApproaching
OptimisticLockExhausted → OptimisticLockRetryRising
```

첫 줄 하나로 DB 장애 시 여섯이 넷이 된다. 남는 넷은 critical 셋과 settlement 하나다.

**critical 은 억제 대상에 안 넣었다.** 억제된 알림은 울린 적이 없으므로, 잘못 걸면
고장이 조용해진다. 돈이 걸린 판정은 원인이 무엇이든 사람이 본다. `equal: ['domain']`을
붙인 것도 같은 이유다 — 결제 장애가 대사 알림을 지우면 안 된다. 대사는 다른 시간대에
다른 사람이 본다.

두 번째 줄은 인과가 특히 분명하다. **속도 제한이 꺼진 동안의 오탐률은 규칙 하나가 빠진
값이다.** 그 수치를 보고 규칙을 조이면 Redis가 돌아왔을 때 정탐까지 같이 사라진다.

## 2. 비율은 분모가 작으면 거짓말을 한다

새벽에는 5분에 네 건이 들어온다. 그때 한 건이 실패하면 성공률이 75% 로 찍힌다. 이건
고장이 아니라 **표본이 얇은 것**인데, 임계값 하나로는 낮 시간의 75% 와 구별되지 않는다.

그렇다고 바닥만 걸면 저트래픽 시간대의 진짜 장애가 통째로 조용해진다. 그래서 둘로 나눴다.

```
(성공률 < 0.95  그리고  초당 0.1건 이상)   ← 평소 구간
또는
 성공률 < 0.5                              ← 붕괴는 몇 건이든 고장
```

한 알림 안에 두 항으로 담은 것은 같은 고장에 알림 두 건이 안 나가게 하기 위해서다.
`success-rate-sampling-test`가 셋을 고정한다: 분당 4건에 75% 는 안 울고, 같은 분당
4건이라도 0% 면 울고, 분당 20건에 90% 면 운다.

## 3. baseline 은 학습이 아니라 지난주다

시간대별 편차는 **지난주 같은 요일 같은 시각**과 비교하면 잡힌다. 요일과 시간대가 곧
결제량의 주기라서 학습해야 알 수 있는 것이 아니다. 모델을 넣으면 "왜 울렸는가"를 설명해야
하는 자리가 하나 더 늘 뿐이다.

```
payment:confirm_success_ratio:rate30m
  < (payment:confirm_success_ratio:rate30m offset 1w) - 0.02
```

### 5%p 로 썼다가 지웠다

**처음에 5%p 로 잡았는데, 그러면 이 규칙은 혼자서 울 수가 없다.** 성공률 상한이 1.0 이라
5%p 가 떨어지면 이미 95% 밑이고, 그러면 절대 임계가 먼저 운다. 뜨긴 뜨는데 언제나 다른
알림 뒤에 붙어서 아무것도 더 알려 주지 않는 규칙이 되는 것이다.

이 알림이 값을 하는 구간은 **"아직 SLO 안인데 평소보다 낮다"**뿐이다. 폭이 그 안에
들어와야 한다. `weekly-baseline-test`가 그 구간을 고정한다 — 성공률 96% 에서 이 알림은
울고 절대 임계는 조용하다.

### 표본 바닥이 위보다 높다

2%p 는 좁아서 표본이 얇으면 흔들림에 묻힌다. 성공률 0.98 에서 표준편차가 √(0.98·0.02/N)
이라 540건이면 0.006 이고 2%p 는 그 3.3배다. 180건이면 1.9배라 절반이 잡음이 된다.
그래서 이 알림만 바닥이 초당 0.3건(30분에 540건)이고, 지난주 쪽에도 같은 바닥을 건다.

**첫 일주일은 조용하다.** `offset 1w`가 빈 값을 돌려주므로 비교가 성립하지 않는다.
이건 결함이 아니라 전제다.

## 4. 억제를 실측한다

`amtool check-config`는 문법만 본다. **여섯이 넷이 된다는 것은 그때까지 내가 규칙을 읽고
센 값**이었고, 잰 값이 아니었다.

`run-inhibit-probe.sh`가 alertmanager 를 띄우고 v2 API로 알림 여섯을 밀어 넣은 뒤 되읽는다.
응답의 `status.inhibitedBy`가 비어 있지 않은 것이 억제된 것이다. 수신자(슬랙)를 안 거치므로
웹훅 없이도 잰다.

```
규칙 단에서 뜬 것   6건
억제된 것          2건  ['OptimisticLockRetryRising', 'OutboxConsumptionStalled']
사람이 받는 것     4건  ['CompensationExhausted', 'PaymentSuccessRateLow',
                        'ReconPendingBacklog', 'UnknownPaymentAging']
```

억제 규칙을 지우고 돌리면 **여섯이 그대로 나가고 프로브가 깨진다.** 지우기 전에 그것을
먼저 확인했다. 깨지지 않는 검사는 검사가 아니다.

프로브는 **수만 세지 않는다.** critical 셋과 다른 도메인 하나가 억제되면 각각 따로
실패한다. 그 넷이 억제되지 않는 것이 이 설계의 전제라서, 수만 맞으면 통과되게 두면
전제가 깨진 채로 넷이 될 수 있다.

## 5. 억제는 조용히 안 걸린다

`inhibit_rules`는 문법이 틀려도 알림이 멈추지 않는다. 그냥 **안 걸릴 뿐**이고, 그러면
소음이 줄었는지 아닌지를 사람이 알 수 없다. CI 에 `amtool check-config`를 넣었다.
웹훅 URL 은 실행 시 환경변수로 들어가므로 검사용 더미로 바꿔 넣는다.

넣고 보니 **이 설정은 그때까지 한 번도 검증된 적이 없었다.** `${SLACK_WEBHOOK_URL}`을
alertmanager 가 확장하지 않아서, 파일 그대로는 `unsupported scheme ""`로 떨어진다.

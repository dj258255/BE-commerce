# 24. 조회 인덱스 실측: 반환 건수와 스캔 범위

배치의 무제한 조회를 잡고(`23-배치-조회-상한.md`) 나서, 서빙 쪽은 안 봤다는 것을 알았다.

앞 글은 카카오페이 데이터 조직의 기술 블로그에서 시작했다. 원장 통계 배치 OOM, 정산 조회의
`Limit-Offset` 한계, 실시간 OLAP 의 PK 한계. 세 글의 공통점이 "한 번에 메모리에 올리지 않는다"였고
그래서 배치를 셌다. 이 글은 **그 다음에 남은 질문**이다 — 배치 말고 사용자가 직접 부르는
조회는 괜찮은가.

## 1. 건수는 이미 묶여 있었다

내 주문 목록 조회(`GET /api/v1/orders`)를 보니 `findTop50ByUserIdOrderByIdDesc`였다.
50건으로 묶여 있으니 문제없다고 넘길 뻔했다. **건수가 묶인 것과 그 건수를 싸게 찾는 것은 다른 일이다.**

`orders`에 걸린 인덱스는 `(status, created_at)`과 PK뿐이었다. 조회는 `WHERE user_id = ?` 다.

## 2. 흔한 경우가 곧 최악의 경우였다

인덱스가 없으면 `ORDER BY id DESC LIMIT 50`은 PK를 역방향으로 훑으며 걸러낸다.
그 사용자의 주문이 50건 이상이면 위쪽에서 금방 채우고 멈춘다. 그런데
**주문이 50건 미만인 사용자는 그 50건을 영영 못 채워 테이블 끝까지 간다.**
그리고 실제 서비스에서 주문 50건 미만은 예외가 아니라 대다수다.

30만 행(사용자 1만 × 30건), 실 MySQL 8.4 InnoDB, 버퍼 풀에 다 올라간 상태에서 쟀다.

| | EXPLAIN 추정 | EXPLAIN ANALYZE 실제 | 중앙값 |
|---|---|---|---|
| As-is (인덱스 없음) | `type=index key=PRIMARY rows=50` | **rows=300000** | **65.6ms** |
| To-be `(user_id, id)` | `type=ref rows=30` | rows=30 | **0.6ms** |

**107배.** 그런데 이 표에서 더 중요한 것은 왼쪽 칸이다.

## 3. EXPLAIN 만 봤으면 못 잡았다

옵티마이저는 `rows=50` 이라고 추정했다. 계획만 보면 멀쩡하다 — PK를 쓰고, 정렬도 없고,
읽는 행도 50건이라니 나무랄 데가 없다. 실제로 훑은 것은 30만 행이었다. **추정이 6,000배 틀렸다.**

옵티마이저는 "user_id로 걸러도 50건은 금방 나오겠지"라고 봤는데, 그 사용자에게 30건밖에 없다는 것은
통계로 알 수 없었다.

**추정과 실제가 같은 노드에 붙어 있는지 다시 확인했다.** 다른 단계의 숫자를 견주면 6,000배라는 말이
성립하지 않기 때문이다. 재현해 보니 한 노드다.

```
-> Limit: 50 row(s)                        (cost=4.5 rows=5)  (actual rows=30)
    -> Filter: (t.user_id = 1)             (cost=4.5 rows=5)  (actual rows=30)
        -> Index scan using PRIMARY (rev)  (cost=4.5 rows=50) (actual rows=300030)
```

`EXPLAIN`의 `rows=50`은 맨 아래 인덱스 스캔에 붙은 값이고, 실제 300,030 도 같은 줄이다.

**이번에 쓴 확인 방법이 `EXPLAIN ANALYZE` 였다는 뜻이지, 그것으로만 보인다는 뜻은 아니다.**
느린 쿼리 로그에 안 남은 것도 65ms 가 **그때 걸어 둔 임계값 아래**여서다. 임계값을 낮추거나
`rows_examined`를 보는 방법도 있다. 사용자 수만 늘면 그대로 커진다.

## 3-1. `(user_id, id)`의 둘째 칸은 없어도 됐다

이 문서는 원래 "`id`를 둘째에 둬야 정렬 없이 집는다"고 적어 뒀다. **틀렸다.**
`(user_id)` 하나만 걸고 다시 재 봤다.

| 인덱스 | 계획 | 인덱스 크기 |
|---|---|---|
| `(user_id)` | `Index lookup (reverse)` cost=10.5 rows=30 | 7.52 MB |
| `(user_id, id)` | `Index lookup (reverse)` cost=10.5 rows=30 | 7.52 MB |

**InnoDB 는 보조 인덱스 leaf 에 PK 를 이미 붙여 둔다.** 그래서 `(user_id)`는 물리적으로
`(user_id, id)` 이고, 명시한 둘째 칸은 계획도 크기도 바꾸지 않는다.

맞는 설명은 여기까지다 — **`user_id`를 선두에 둬야 그 사용자 행만 좁혀진다.**
인덱스 정의는 그대로 두고(같으므로) 설명만 고쳤다.

## 4. status 인덱스는 통념이 반만 맞았다

`status`는 값이 세 가지뿐이라 "카디널리티가 낮아 인덱스가 소용없다"는 말의 대상이다.
갈라서 재 봤다. `settlement_items` 30만 행, `PENDING` 300행(0.1%).

| 무엇을 찾나 | As-is | To-be `(status, id)` | |
|---|---|---|---|
| 드문 값 `PENDING` 0.1% | 15.2ms | **0.7ms** | 20배 빨라짐 |
| 흔한 값 `DONE` 99.9% | 0.6ms | **1.0ms** | 1.7배 느려짐 |

(재실행에서 15.1ms → 0.5ms 로 28배까지 갔다. 배수는 회차마다 갈리지만 방향은 두 번 다 같았다.)

**같은 인덱스가 한 조회는 살리고 다른 조회는 죽인다.** 흔한 값을 찾을 때는 PK 역방향 스캔이
바로 100건을 채우는데, 인덱스를 타면 세컨더리 인덱스에서 PK로 한 번 더 건너가는 값만 낸다.

그래서 판단 기준은 컬럼의 성질이 아니라 **그 조회가 무엇을 찾는지**다.
이 저장소의 `status` 조회는 전부 할 일을 찾는 조회다 — `PENDING`·`UNKNOWN`·`HELD`·`OPEN`·`WAITING_FOR_DEPOSIT`.
성숙한 테이블에서 드문 값 쪽이다.

예외가 하나 있다. 구독 청구 배치는 `ACTIVE`를 찾는데 이건 흔한 값이다. 그래도 값을 하는 이유는
선택도가 상태가 아니라 날짜에서 나오기 때문이다(`next_billing_date <= 오늘`).
그래서 `(status, next_billing_date)`로 날짜를 반드시 둘째 자리에 뒀다. `status`만 걸었다면 아무 값도 못 했다.

## 5. 전수로 셌다

한 곳을 고치고 끝내면 나머지는 그대로다. 리포지터리의 파생 쿼리에서 선두 조건 컬럼을 뽑아
마이그레이션의 인덱스와 대조했는데, **소스만 봐서는 양쪽으로 틀렸다.** JPA가 유니크 제약으로
만들어 준 인덱스를 못 봤고(있는데 없다고 함), 조건이 없는 `findAllByOrderBy...`를 조건으로 셌다(없는데 있다고 함).

그래서 마이그레이션을 실제로 다 돌린 뒤 `information_schema.STATISTICS`에 물어봤다.
**조회 조건 22개가 인덱스 선두에 없었다.** 그중 18개에 인덱스를 걸고 4개는 일부러 안 걸었다.

안 건 것과 근거:

| | 왜 안 걸었나 |
|---|---|
| `audit_logs.target_type` | 쓰기가 많고 조회는 사후 조사뿐이다. 쓰기 비용을 상시로 내는 쪽이 손해다 |
| `blind_reviews.edited_at` | 평가용 테이블이라 행이 수백 단위다. 풀스캔이 인덱스보다 싸다 |
| `narrative_preferences.choice` | 같은 이유 |
| `ledger_transactions.source_type` | 어드민이 최근 50건을 보는 용도뿐이라 PK 역방향 스캔으로 충분하다 |

## 6. 버는 쪽만 적으면 인덱스가 공짜라는 주장이 된다

결제는 쓰기가 많은 시스템이고, 인덱스는 조회에서 버는 것을 쓰기에서 갚는다. 그래서 갚는 쪽도 쟀다.
같은 표에 `orders` 10만 행을 넣되 인덱스 개수만 바꿨다.

처음엔 1회씩만 재고 **"쓰기 3.8% 느려짐"**이라고 적었다. 다시 돌리니 **-2.3%**가 나왔다.
인덱스 있는 쪽이 더 빨랐다는 뜻이고, 3%대 차이를 1회 측정으로 주장한 것이 잘못이었다.
이 저장소의 락 비교는 5회 중앙값을 쓰는데 여기만 1회였다.

교대로 5회 재고 회차 간 폭을 함께 적는 것으로 고쳤다. 몰아서 재면 디스크 상태의 표류가
한쪽에만 실린다.

| | 중앙값 | 처리량 | 회차 간 폭 |
|---|---|---|---|
| 인덱스 1개 | 37.08s | 2,697행/s | 2.0% |
| 인덱스 3개 | 38.14s | 2,622행/s | 2.3% |

**차이 +2.9%, 노이즈 폭 2.3%.** 노이즈보다 크지만 아슬아슬하다. 다만 5회 전부 인덱스 쪽이
느렸으므로 방향은 믿는다. 크기는 "3% 안쪽" 정도로만 말할 수 있다.

**쓰기 3% 안쪽을 내고 조회 107배를 받는다.** 이 교환은 받는다.

## 7. 고정했다

같은 실수가 다시 들어오는 것을 막는 쪽이 이번에 고친 18개보다 오래 간다.
`SchemaIndexAuditMySqlTest`가 마이그레이션을 다 돌린 뒤 실 스키마에 물어보고,
조회 조건 컬럼이 인덱스 선두에 없으면 CI에서 깨진다. 안 걸기로 한 4개는 목록에서 빼되
근거를 마이그레이션과 테스트 주석 양쪽에 적었다 — **빠진 것과 일부러 뺀 것을 구별할 수 있어야 한다.**

---

## 조회 부하 실측 — 캐시가 필요한지 재서 정했다

위까지는 조회 **한 건**의 비용이다. 커넥션 하나로 잰 값이라 **동시에 들어올 때도 그런지는 다른 질문**이다.
그리고 이 저장소의 k6 스크립트 아홉 개가 **전부 쓰기 경로**였다. 체크아웃·스파이크·정산 경합·재배포까지
다 재면서 조회는 한 번도 안 쟀다.

### 1. 무엇을 답하려고 쟀나

- 조회 경로가 어디서 꺾이는가 — 쓰기 경로의 무릎(~120 req/s)과 비교할 숫자가 생긴다
- **읽기 캐시가 필요한가** — 안 넣은 이유를 "근거가 없어서"라고 적어 뒀는데, 근거가 없던 건
  **재 본 적이 없어서**다. 재면 필요하다는 근거나 필요 없다는 근거가 생긴다

도착률을 고정한다(constant-arrival-rate). 이 저장소는 한 번 닫힌 루프로 재서 용량을 과소평가한 적이 있다.
서버가 느려지면 VU가 다음 요청을 늦게 보내 **도착률이 같이 줄어** 병목을 가린다. 조회는 응답이 빨라 그 함정에 더 잘 빠진다.

주문 30만 건(사용자 1만 × 30건)을 넣고 계정 40개로 돌렸다. 사용자를 **라운드로빈으로 흩뿌린다** —
한 사람의 주문을 연속으로 넣으면 id가 뭉쳐서 인덱스 없이도 금방 찾아진다. 실제 주문 순서와 다르고,
측정이 좋게 나오도록 데이터를 고르는 셈이 된다.

### 2. 세 번 잘못 쟀다

**하나 — 판정 기준이 조회에 안 맞았다.** 쓰기 경로에서 쓰던 "성공률이 온전한 마지막 단계"를
그대로 가져왔더니 2400/s까지 성공률 100%로 나와 무릎을 못 찾았다. 조회는 **아무것도 실패하지 않고
지연만 오른다.** 요청이 그냥 줄을 선다. 그래서 판정을 지연 기반으로 바꿨다 —
평탄 구간 p95의 3배를 넘는 첫 단계 직전이 무릎이다.

**둘 — 부하기가 굶은 것을 서버 한계로 읽을 뻔했다.** 3200/s부터 k6가 maxVUs 2000에 걸려
Insufficient VUs 경고를 냈다. 목표 도착률을 못 낸 것이고, 그때 오른 지연(946·987·1034ms)은
서버가 아니라 **부하기가 굶은 값**이다. 단계마다 실제로 보낸 요청 수를 세어 목표의 95% 미만이면
그 줄을 판정에서 빼도록 고쳤다. 부하기와 서버가 같은 기계에 있으면 위쪽 단계는 원래 못 믿는다.

**셋 — 단계가 짧아 노이즈에 속을 뻔했다.** 20초 단계로 재니 p95가 이렇게 나왔다.

```
1200/s  31ms    1400/s  58ms    1600/s  20ms    1800/s 134ms    2000/s  36ms
```

**낮은 부하가 더 느리다는 것은 측정이 틀렸다는 뜻이다.** 4~6배씩 튀는데 여기서 무릎을 정하면
서버의 한계가 아니라 **첫 번째 노이즈 튐**을 무릎이라 부르게 된다. 실제로 그렇게 900/s가 나왔다.
60초로 늘리니 단조로워졌다. 부하기와 서버가 한 기계에 있어 GC·JIT가 단계 경계에 걸리는 탓이다.

### 3. 결과

| 목표 | 실제 | 성공률 | p95 | |
|---|---|---|---|---|
| 600/s | 600/s | 100.0% | 5ms | |
| 1000/s | 1000/s | 100.0% | 6ms | |
| 1400/s | 1400/s | 100.0% | 7ms | |
| **1800/s** | **1800/s** | **100.0%** | **10ms** | **← 무릎** |
| 2200/s | 2197/s | 100.0% | 27ms | |

**조회 경로 ≈ 1,800 req/s (평탄 p95 5ms).** 쓰기 경로의 무릎이 ~120 req/s였으니 **약 15배**다.

### 4. 캐시는 안 넣는다 — 이제는 근거가 있다

판정 기준을 결과보다 **먼저** 정해 뒀다. 결과를 보고 기준을 만들면 원하는 답이 나온다.

> 평탄 구간의 p95가 이미 크면 조회 한 건이 비싼 것이라 캐시가 값을 한다.
> 평탄 p95가 작고 무릎이 높으면 DB는 병목이 아니다.

평탄 p95가 **5ms**고 무릎이 **1,800/s**다. 조회 한 건은 이미 싸고, 1800/s 위에서 오르는 지연은
쿼리가 비싸서가 아니라 **줄을 서기 때문**이다. 캐시는 한 건의 비용을 줄이는 장치라 이 병목에
안 닿는다. 게다가 이 시스템이 읽는 데이터를 만드는 **쓰기 경로가 ~120/s에서 꺾인다** —
읽을 것을 만드는 쪽이 15배 좁다.

그래서 캐시를 안 넣는다. 넣으면 얻는 것 없이 **무효화라는 더 어려운 문제**만 는다.
조회 패턴이 바뀌거나(집계·조인이 늘거나) 평탄 p95가 커지면 그때 다시 잰다.

### 5. 남은 것

- 잰 것은 **목록 조회 한 종류**다. 타임라인 조립은 기여자가 늘수록 쿼리가 느는 구조라 따로 재야 한다
- 부하기와 서버가 같은 노트북이다. 2200/s 위는 이 구성으로 못 잰다
- 버퍼 풀에 다 올라간 상태의 값이다. 콜드 상태나 데이터가 메모리보다 커지면 다시 재야 한다

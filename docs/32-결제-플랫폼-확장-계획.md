# 32. 결제 플랫폼 확장 계획: 개인 프로젝트에서 운영 가능한 축소 모델까지

## 목적

이 문서는 결제 기능을 더 많이 붙이기 위한 목록이 아니다. Stripe·Uber·Square·Adyen의
결제 시스템에서 반복해서 나타나는 문제를 BE-commerce의 규모에 맞게 축소하고, 각 판단을
실험과 운영 지표로 검증하기 위한 계획이다.

핵심 흐름은 다음이다.

> 문제 → 가설 → 선택지 → 트레이드오프 → 결정 → 구현 → 실험 → 운영 증거 → 포트폴리오

## 외부 사례에서 가져온 원칙

| 원칙 | 이 프로젝트에 적용하는 형태 |
|---|---|
| 멱등성 | 같은 키·같은 요청은 첫 결과 재생성, 같은 키·다른 요청은 충돌, 처리 중 요청은 명시적 거절 |
| 웹훅 | ACK·원본 저장·비동기 해석·재시도·조회 재검증을 분리 |
| 원장 | append-only 복식부기와 차변=대변 불변식 |
| 대사 | 금액·건수·최고 지연·미해결 oldest age를 측정하고 재처리 가능하게 함 |
| 장애 격리 | PG 동시 호출 상한·timeout·circuit breaker·backoff로 일반 API 보호 |
| 확장 | active-active 대신 버전·재처리·대사·축소 장애 실험부터 검증 |

## 현재 닫힌 범위

- `UNKNOWN` 상태 보존과 PG 조회 기반 복구
- 승인 후 독립 보상 취소와 보상 재시도
- `Idempotency-Key`·요청 본문 해시·처리 중 상태·첫 응답 재생성
- 웹훅 원본 저장·중복 흡수·순서 역전 보류·Outbox 기반 비동기 해석
- 복합결제 환불 배분과 원장 차변=대변 검증
- PG 동시 호출 상한·timeout·circuit breaker
- PG 승인 latency·UNKNOWN·동시성 거절 메트릭
- 대사 PENDING 건수와 가장 오래된 PENDING age 메트릭
- MySQL·Redis 통합 테스트와 MySQL 장애 주입 카오스 테스트

## 단계별 계획

### P0. 계약과 기준선 — 완료

완료 조건:

- API 계약에 상태·오류·멱등 의미가 적혀 있다.
- 정상·중복·본문 변경·처리 중·응답 유실을 각각 재현한다.
- 실 PG 계약 테스트와 모의 PG 테스트를 구분한다.

산출물: [API 스펙](10-API-스펙.md), [결제 의사결정 검증](29-결제-의사결정-검증.md)

### P1. 승인과 웹훅의 수렴 — 완료

완료 조건:

- 승인 timeout을 실패로 단정하지 않는다.
- 웹훅은 상태 변경 명령이 아니라 동기화 신호로 저장한다.
- 웹훅이 결제 행보다 먼저 오거나 중복되어도 유실되지 않는다.
- 최종 상태는 PG 조회·복구 배치·대사 중 하나로 수렴한다.

산출물: `WebhookService`, `PaymentRecoveryService`, 웹훅 통합 테스트

### P2. 운영 가시성 — 진행 중

완료 조건:

- 멱등 replay·conflict·processing·동시 삽입 경합을 카운터로 확인한다.
- PG 승인 latency·UNKNOWN·concurrency rejection을 확인한다.
- 대사 pending count와 oldest age를 확인한다.
- 운영자가 주문번호 하나로 결제·원장·대사·웹훅 이력을 복원한다.

현재 구현: 멱등성과 PG 지표, 대사 count/oldest age까지 구현했다.
남은 확인: Prometheus scrape 결과와 알림 규칙을 통합 테스트에서 캡처한다.

### P3. 원장·대사·재처리 — 완료에 가까움

완료 조건:

- 승인·부분취소·복합환불·차지백을 모두 별도 분개로 남긴다.
- 같은 정산 파일을 두 번 올려도 대사 결과가 중복되지 않는다.
- PENDING 예외는 사유·담당자·메모와 함께 수동 확정한다.
- 재처리 후 동일 불변식이 다시 통과한다.

남은 실험: 고의적인 내부 전용·외부 전용·금액 불일치 샘플을 섞고, oldest age와 자동 해결률을
측정한다.

### P4. 장애·규모 축소 실험 — 진행 중

현재 규모에서 검증할 시나리오:

- PG 응답 지연과 timeout
- PG 5xx와 circuit open
- 웹훅 재전송·순서 역전·보류 재시도
- MySQL 연결 단절과 재기동
- 승인 직후 프로세스 종료
- 동일 멱등키 동시 요청
- 대사 파일 중복 업로드

각 실험은 다음 표를 남긴다.

| 항목 | 기록할 내용 |
|---|---|
| 가설 | 어떤 장애가 어떤 전파를 일으킬 것인가 |
| 조건 | 도착률·지연·동시성·데이터 크기 |
| 관측 | p50/p95/p99, error rate, connection wait, UNKNOWN age |
| 판정 | 가설 채택·기각·범위 제한 |
| 산출물 | 테스트·로그·리포트·ADR |

### P5. 외부 운영 경계 — 미검증

다음은 코드만으로 완료할 수 없다.

- 실제 Toss 승인·취소·웹훅 계약 테스트
- 실제 두 PG 간 failover 성공률·수수료·정산 데이터 비교
- PCI SAQ와 가맹점 책임 범위 확인
- 다지역 active-active와 실제 장애 전환

이 항목들은 “구현 완료”라고 쓰지 않고, 필요한 계정·계약·운영 조건과 함께 미검증으로
기록한다.

## 채용 관점의 최종 증거

포트폴리오에는 기술 이름보다 다음 다섯 사례를 남긴다.

1. timeout을 실패로 처리하지 않고 UNKNOWN으로 보존한 이유와 복구 결과
2. 느린 PG에서 무제한 재시도 대신 호출 상한을 선택한 이유와 latency/거절률 변화
3. 웹훅이 먼저 도착한 실패를 보류 이벤트와 조회 재검증으로 수렴시킨 과정
4. 복합결제 환불 정책에서 포인트·월렛·카드 순서를 선택한 근거와 포기한 것
5. 예상과 달리 대사·배치가 결제 latency를 악화시키지 않았거나, 반대로 어떤 조건에서 악화시켰는지

각 사례는 문제·가설·대안·트레이드오프·결정·검증·남은 불확실성 순서로 작성한다.

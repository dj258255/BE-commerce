# ADR-058. 자원이 마르면 조회를 먼저 돌려보낸다: 웹훅은 PG 상한만으로는 지켜지지 않았다

- 상태: **채택**. 기본값 `app.web.browse-shed.enabled=true`, 문턱 `max-in-flight=12`(2026-09-26 #329 에서 16 → 12)
- 날짜: 2026-09-24
- 관련: `BrowseShedFilter`, `BrowseShedConfiguration`, [실측 리포트](../performance/webhook-priority.md), [성능 §14.6](../performance/README.md),
  [ADR-022](ADR-022-pg-brownout-resource-limits.md), 이슈 #250 · #329(문턱 스윕)

## 맥락

웹훅·결제·조회는 톰캣 워커와 DB 커넥션 풀(20)을 같이 쓴다. 늦을 때의 대가가 다르다. 웹훅은 10초를 넘기면 토스가 재전송하고,
결제는 미확정이 되어 복구 배치의 일거리가 된다. 조회는 사용자가 다시 누르면 된다.

성능 §14.6 은 PG 가 느릴 때 PG 동시 호출 상한(40, ADR-022)이 웹훅을 지킨다는 것을 쟀다. 상한이 묶는 것은 PG 를 부르는 워커뿐이라,
PG 가 아닌 이유로 자원이 마르는 경우는 남아 있었다(트러블슈팅 기록의 열린 항목 6).

## 판정 기준 (이슈 #250 에 측정 전에 적었다)

- 1단계: 조회 부하를 더해도 웹훅 p95 ≤ 1초 · 10초 초과 0% 면 등급을 나누지 않는다
- 2단계(재현되면): 진행 중 조회가 문턱(16)이면 새 조회를 503. 웹훅 p95 ≤ 1초 · 10초 초과 0% 면 채택

## 결과 (대입)

PG 지연 5초 · 상한 40 · 결제 50/s · 웹훅 10/s.

| 조회/s | 셰딩 없음: 웹훅 10초 초과 | 셰딩 16: 웹훅 p95 · 10초 초과 | 셰딩 16: 조회 503 |
|---:|---:|---:|---:|
| 200 | 15.57% | 152ms · 0.00% | 31% |
| 400 | 67.62% | 186ms · 0.00% | 67% |
| 800 | 81.90% | 161ms · 0.00% | 83% |

1단계에서 재현됐고 2단계가 기준을 통과했다.

### 문턱을 바꿔 다시 쟀다 (#329, 2026-09-26)

판정 기준(두 부하 모두 웹훅 10초 초과 0% · p95 1초 안, 그중 조회 503 이 가장 낮은 문턱, 1·2위가 5%p 안이면 3회 중앙값)은 측정 전에 이슈에 적었다.

| 문턱(풀 20) | 조회 503(200·400/s 평균) | 웹훅 p95(400/s) |
|---:|---:|---:|
| 8 | 58.0% | 58ms |
| **12** | **50.1%**(3회 중앙값) | 78~111ms |
| 16 | 58.4% | 253ms |
| 20 | 50.4%(3회 중앙값) | 210~864ms |
| 24 · 28 · 32 | (400/s 만) 64.4 · 60.3 · 46.8% | 342 · **4,111** · **11,123ms**(10초 초과 22.47%) |

**16 을 고른 이유가 틀렸다.** 남는 몫이 0 인 20 도 웹훅을 지켰고 풀(20)을 넘는 28 부터 무너졌다. 문턱은 결제·웹훅 몫을 남기는 것이 아니라
커넥션 줄의 길이를 묶는다. 풀을 30 으로 키워도 조회 503 은 52~57% 로 줄지 않았다. 자세한 표는 [리포트 3단계](../performance/webhook-priority.md#3단계-문턱을-바꿔-보니-329).

## 결정

- **진행 중인 조회를 12개로 묶는다**(처음 16, #329 에서 바꿈). 넘치는 조회는 필터에서 바로 503 + `Retry-After: 1` 을 받는다
- **문턱은 커넥션 풀보다 작게 둔다.** 풀을 넘으면 커넥션 줄이 생겨 웹훅이 그 줄에 선다(풀 20 에서 28 부터 p95 4초). 12 는 무너지는 문턱까지 두 배 넘게 남는다
- **세는 단위는 "진행 중인 조회"다.** 막히는 자원은 커넥션인데, 전체 요청 수로 세면 PG 를 기다리는 결제(커넥션을 쥐지 않는다)가 섞인다
- **웹훅·결제·주문은 이 필터가 돌려보내지 않는다.** 결제는 PG 상한이 따로 있다
- **보안 체인보다 앞에 건다.** 돌려보낼 요청에 토큰 검증 비용을 쓰지 않는다. 조회 API 는 인증이 없어 앞에 두어도 잃는 것이 없다

## 버린 것

| 안 | 이유 |
|---|---|
| 웹훅 전용 커넥션 풀(격벽) | 웹훅은 지키지만 결제의 주문 생성은 그대로 조회와 줄을 선다. 셰딩은 결제도 함께 살렸다(p95 15.8초 → 5.5초). JPA 에 풀을 둘 두는 설정 비용도 있다 |
| 웹훅을 받기만 하고 저장을 비동기로 | 200 을 준 뒤 저장이 실패하면 토스는 재전송하지 않는다. 받았다고 답한 웹훅을 잃는다 |
| 전체 요청 수로 셰딩 | PG 를 기다리는 결제 40개가 늘 문턱을 먹는다. 조회를 필요 이상으로 돌려보낸다 |
| 커넥션 풀을 키우기 | DB 쪽 동시성이 그대로 늘어 문제를 DB 로 옮긴다. #329 에서 풀 30 은 조회 503 을 줄이지 못했다(52~57%) |
| 문턱 20(503 이 12 와 0.4%p 차이) | 규칙상 12 가 앞섰고, 20 은 한 회차에서 웹훅 p95 864ms 로 기준(1초)에 붙었다. 무너지는 문턱(28)과 가깝다 |

## 대가 (정직하게)

- **조회를 버린다.** 초당 200건에서 31%를 돌려보냈고, 처리한 조회 수도 45초에 7,613 → 6,179 로 줄었다. 셰딩이 없을 때 처리한 조회는
  p95 12초였지만 건수로는 셰딩 쪽이 적다
- ~~문턱 16 은 하나만 쟀다~~ → #329 에서 8~100 을 쟀다. 12 와 20 의 차이는 잡음 안이다(한 조합 안에서 3회에 6~7%p 흔들렸다). 12 를 고른 것은 규칙과 여유 폭 때문이다
- **조회 용량을 재는 벤치마크는 셰딩을 끄고 잰다**(`tools/bench.sh`, `run-search-baseline.sh` 에 끄는 변수를 넣었다). 켠 채로 재면 용량이 아니라 문턱을 잰다
- 인스턴스마다 따로 센다. 인스턴스가 여럿이면 커넥션 풀도 인스턴스마다라 같은 의미가 유지되지만, DB 전체 커넥션 상한은 따로 봐야 한다

## 다시 볼 조건

- 커넥션 풀 크기를 바꿀 때 → 문턱이 풀보다 작은지 본다. 풀을 줄여 문턱 이하가 되면 다시 잰다
- 조회 한 건이 커넥션을 쥐는 시간이 바뀔 때(조회 쿼리 변경) → 무너지는 문턱이 옮겨 간다. `tools/run-webhook-under-browse.sh` 로 24~32 를 다시 잰다
- `web.browse.shed` 가 평소에도 오를 때 → 조회 경로가 느려진 것이다. 문턱이 아니라 조회를 고친다

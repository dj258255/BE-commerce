# ADR-017. 주문·상품·재고를 각각 애그리거트로 두고 ID 로만 잇는다

- 상태: 채택
- 관련: `order` 모듈, ADR-004(재고 차감 전략), 1편 신뢰 경계

## 문제

주문 한 건이 상품 정보와 재고를 함께 다룬다. 이 셋을 어떻게 묶을지에 따라
**금액이 언제의 값인지**와 **어디를 잠그는지**가 갈린다.

가장 쉬운 쪽은 `OrderItem`이 `Product`를 객체로 물고, 재고를 `Product` 안에 두는 것이다.
JPA 로 짜면 자연스럽고 조회도 편하다. 그런데 두 가지가 깨진다.

## 결정

**세 애그리거트로 나눈다.**

```
주문   Order (루트) ── OrderItem        cascade = ALL, orphanRemoval
상품   Product (루트)
재고   Stock (루트)
```

**애그리거트끼리는 객체가 아니라 ID 로 참조한다.**

```java
// OrderItem
private long productId;       // Product 를 물지 않는다
private String productName;   // 주문 시점 스냅샷
private long unitPrice;       // 주문 시점 스냅샷
```

### 왜 `Product`를 물지 않나

물면 **가격이 항상 현재 가격을 따라간다.** 상품 값을 올리는 순간 이미 만들어진 주문의
`totalAmount`가 흔들리고, 그러면 결제 승인 때 검증한 금액과 나중에 조회한 금액이 달라진다.

주문은 **만들어진 시점의 사실**이어야 한다. 그래서 이름과 단가를 그 자리에 박는다.

1편에서 정한 신뢰 경계와 같은 결정이다. 거기서는 "가격의 원천이 서버냐 클라이언트냐"를 갈랐고,
여기서는 "가격이 언제의 값이냐"를 가른다. **애그리거트 경계가 곧 "언제의 진실인가"의 경계다.**

### 왜 재고를 `Product` 안에 안 두나

재고는 **동시에 깎이는 지점**이다. 상품 정보와 한 행에 있으면 상품명을 고치는 트랜잭션이
재고 행을 잠그고, 반대로 재고 차감이 상품 조회를 막는다. 바뀌는 빈도와 잠금 성격이 다르다.

분리해 뒀기 때문에 락 세 전략을 `Stock` 하나만 두고 잴 수 있었다(ADR-004).
`Product`와 묶여 있었다면 그 실측 자체가 성립하지 않는다.

## 결과

- `Order` 만이 `OrderItem`의 수명을 관리한다(`cascade = ALL`, `orphanRemoval = true`).
  `OrderItem`을 밖에서 따로 만들거나 지우지 않는다
- 주문 금액은 주문 생성 시점에 확정된다. 이후 상품 가격이 바뀌어도 안 흔들린다
- 재고 차감은 `Stock` 한 행만 건드린다

## 남는 것

- **`Order`가 `Payment`를 모른다.** 결제는 `payment` 모듈의 애그리거트이고 `orderNo` 로만 잇는다.
  덕분에 한 주문에 결제 시도가 여럿 붙을 수 있다(카드를 바꿔 재시도하는 경우). 다만
  "이 주문의 현재 결제 상태"를 물으면 `payment` 쪽을 따로 조회해야 한다
- **주문 하나에 품목이 아주 많아지면** `cascade = ALL` + `orphanRemoval`이 비싸진다.
  지금 규모에서는 문제가 아니라 재 보지 않았다

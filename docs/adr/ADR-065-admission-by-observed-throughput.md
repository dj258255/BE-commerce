# ADR-065. 과부하 게이트는 관측한 처리량으로 대기를 추정하고, 기본 정책을 ADMISSION 으로 맞춘다

- 상태: **채택**. `app.recommendation.policy=ADMISSION`, `app.recommendation.admission-estimate=OBSERVED`
- 날짜: 2026-09-24
- 관련: `OverloadGate`, `RecommendationService`, `StubModelClient`,
  [실측 리포트](../../personalization/docs/runs/20260924-overload-sensitivity/report.md), [ADR-037](ADR-037-overload-admission-policy.md), 이슈 #264

## 맥락

ADR-037 은 `ADMISSION`(대기 예산)을 골랐고 대가로 두 가지를 적었다: 파라미터 민감도를 모른다, 모델 용량을 안다고 가정한다. 스텁 모델과 게이트가
같은 설정을 읽어 그 가정은 시험된 적이 없었다. 그리고 ADR-037 이 정한 기본값(`ADMISSION`)은 설정에 들어간 적이 없어, 실제 기본은 `BOUNDED` 였다.

## 판정 기준 (이슈 #264 에 측정 전에 적었다)

- 용량 오판(실제 100ms · 믿음 50ms)에서 `ADMISSION` p95 가 (예산 + 실제 지연) × 1.5 를 넘으면 관측 추정을 넣고 다시 잰다
- 오판일 때 p95 ≤ (예산 + 실제 지연) × 1.2 이고 제대로 알 때 p95·coverage 가 ±10% 안이면 채택

## 결과 (대입)

| | 설정값 추정 | 관측 추정 | 판정선 |
|---|---:|---:|---:|
| 용량 오판 p95 | 315ms | **193ms** | 300 → 240ms |
| 제대로 알 때 p95(2× · 4×) | 168 · 164ms | 153 · 153ms | ±10% |
| coverage(2× · 4×) | 44.5 · 22.6% | 44.7 · 22.7% | ±10% |

민감도: `ADMISSION` p95 ≈ 예산 + 60~80ms, coverage 는 예산과 무관. `BOUNDED` 는 상한 48 에서 모델 앞 대기 상한(400ms)에 먼저 걸렸다.

## 결정

- **대기는 최근 2초의 처리량으로 추정한다**(100ms 칸 20개, 표본 20건 이상). 그 전에는 설정값으로 추정한다
- **처리량은 성공한 모델 호출만 센다.** 대기 초과·실패는 모델을 쓰지 못한 것이다
- **호출 시간이 아니라 끝나는 속도를 쓴다.** 호출 시간에는 모델 앞 대기가 섞여, 줄이 길수록 지연을 크게 보고 더 거절하는 되먹임이 생긴다
- **기본 정책을 `ADMISSION` 으로 맞춘다.** ADR-037 의 결정이 설정에 반영되지 않았던 것을 고친다. 관측 추정으로 ADR-037 이 적은 약점(용량 가정)을 덜었다
- 예전 실험 스크립트(E3·E5)는 설정값 추정을 명시해 재현 조건을 지킨다

## 버린 것

| 안 | 이유 |
|---|---|
| 호출 시간의 이동 평균 | 모델 앞 대기가 섞인다 |
| 설정값 그대로 | 용량이 바뀌면 예산이 깨진다(315ms) |
| `BOUNDED` 를 기본으로 두기 | 같은 조건에서 상한 24 가 p95 348ms · coverage 40.8%, `ADMISSION` 100 이 168ms · 44.5% 였다. 상한은 용량이 바뀌면 뜻이 바뀐다 |

## 대가 (정직하게)

- **용량이 갑자기 바뀌면 창 길이만큼은 옛 처리량으로 판단한다.** #339 에서 쟀다(아래). 용량이 10초마다 두 배 ↔ 절반으로 바뀔 때 2초 창이 p95 190ms 로 0.5초(309ms) · 8초(226ms)보다 나았다
- 부하가 모델 용량보다 낮으면 처리량이 곧 도착률이라 용량을 과소평가한다. 그때는 줄이 없어 판단에 쓰이지 않는다(줄 길이 0 → 대기 0)
- 모델이 스텁이라 실제 지연 꼬리는 반영되지 않았다
- **기본 정책이 바뀐다.** 운영 설정에서 `BOUNDED` 를 명시하지 않았다면 이번 배포부터 `ADMISSION` 이다

## 다시 볼 조건

- 실제 모델 서버(GenPage 등)를 켜면 → 같은 스윕을 실제 모델로 다시 돈다
- ~~용량이 자주 바뀌는 환경(오토스케일)이면 → 창 길이를 잰다~~ → #339 에서 쟀다. 창을 줄이려면 표본 기준(20)도 같이 봐야 한다. 낮은 용량에서 짧은 창은 표본이 모자라 설정값으로 떨어진다

## 실제 모델로 다시 잰 결과 (#271, 2026-09-25)

위 "다시 볼 조건"의 첫 줄을 돌렸다([리포트](../../personalization/docs/runs/20260924-overload-real-model/report.md)).

- 실제 GenPage `/recommend` 는 이 머신에서 초당 약 1,000건(동시성 4 p95 4.9ms)이라 **추천 행에서는 앱이 모델보다 먼저 포화했다.** 앱이 버티는 150 · 300/s 에서 OBSERVED 는 coverage 99.1 · 99.8%, p95 13 · 7ms 로 기준(95%, 126ms)을 넘었다
- CONFIGURED 는 설정의 스텁 값(80/s)을 믿어 **반대 방향으로 틀렸다.** 모델 p95 가 5~6ms 인데 부하 600/s 이상에서 요청의 82~88% 를 거절했다(그 실행들은 k6 dropped 가 있어 무효로 뒀다). 설정값 추정은 모델이 바뀌면 어느 쪽으로든 틀린다
- 600/s 에서 OBSERVED 가 9% 를 거절한 것은 앱을 거친 모델 p95 가 82ms 로 실제로 느려졌기 때문이다(같은 머신에서 CPU 를 나눠 쓴다). 거절은 모델의 실제 상태를 따랐다
- 결정은 그대로다. 게이트 밖에 있던 홈 다음 쪽 `/page` 호출은 [ADR-067](ADR-067-genpage-page-shares-capacity.md) 에서 같은 동시 호출 자리 뒤에 뒀다

## 창 길이를 다시 잰 결과 (#339, 2026-09-26)

모델 스텁의 지연을 10초마다 50ms ↔ 100ms 로 바꾸고(용량 80/s ↔ 40/s) 부하 120/s 에서 창 0.5 · 2 · 8초를 쟀다([리포트](../../personalization/docs/runs/20260926-admission-window/report.md)).
예측과 판정 기준은 이슈에 측정 전에 적었다.

| 창 | 용량 전환 p95 · coverage | 용량 고정 p95 · coverage |
|---:|---:|---:|
| 0.5초 | 309ms · 47.9% | 141ms · 63.2% |
| **2초** | **190ms** · 46.0% | 152ms · 60.4% |
| 8초 | 226ms · 46.5% | 154ms · 60.2% |
| 설정값 추정(대조) | 302ms · 50.5% | — |

- **2초를 유지한다.** 전환 조건에서 가장 낮았고 고정 조건에서는 창 길이가 거의 상관없었다
- 8초는 두 용량을 섞어 봐서 낮은 용량 구간에 줄을 더 받았다(예측대로)
- 0.5초는 표본이 모자라 설정값 추정으로 떨어졌다(설정값 대조와 같은 크기). 창을 줄이는 것만으로는 빨라지지 않는다

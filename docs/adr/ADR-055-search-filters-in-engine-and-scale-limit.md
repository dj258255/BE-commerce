# ADR-055. 필터·패싯은 검색 엔진 안에서 건다. 앱 안 Lucene 의 전환점은 300만 건이다

- 상태: **채택**. 기본값 `app.catalog.search.filters-in-engine=true`. 검색 엔진 기본값(`lucene`)은 바꾸지 않는다(#246 까지 본다)
- 날짜: 2026-09-24
- 관련: `SearchFilters`, `CandidateFiltering`, `LuceneProductSearch`, `EngineQuery`, `LuceneScaleBenchmark`,
  [실측 리포트](../performance/search-filters-scale.md), [ADR-051](ADR-051-search-engine-by-quality.md), 이슈 #244

## 맥락

ADR-051 은 검색어 매칭 품질만 재서 앱 안 Lucene 을 골랐다. 그때 검색은 검색어가 있으면 카테고리·가격·재고·색상 필터를
**전부 무시했다**. 이커머스 검색은 "원피스 + 여성복 + 3만 원 이하 + 재고 있음"과 그 조건의 패싯 개수를 함께 낸다.
ADR-051 의 "다시 볼 조건"에 적은 "카탈로그가 앱 힙에 부담이 될 때"도 숫자가 없었다.

## 판정 기준 (이슈 #244 에 측정 전에 적었다)

1. 결과 수·패싯 개수가 정답과 같아야 한다(오차 0). 동시성 10 p95 ≤ 100ms
2. 앱 안 Lucene 의 예산: 색인 다시 만들기 ≤ 60초, 색인 크기 ≤ 256MB, 검색 p95(c10) ≤ 100ms.
   하나라도 넘는 가장 작은 규모(10만 · 100만 · 300만)를 전환점으로 적는다

## 결과 (대입)

| | 결과 수·패싯 일치 | 잃은 비율 | API p95 c10 |
|---|---:|---:|---:|
| Lucene 안에서 | 171/171 | 0% | 37ms |
| 상위 500개를 DB 에서 | 19/171 | 95.5% | 48ms |
| ES 안에서 | 171/171 | 0% | 39ms |

| 규모 | Lucene 재색인 | 색인 크기 | Lucene p95 c10 | ES p95 c10 |
|---:|---:|---:|---:|---:|
| 10.6만 | 1.9초 | 6MB | 19ms | 18ms |
| 106만 | 12.6초 | 58MB | 86ms | 60ms |
| 317만 | 36.4초 | 175MB | **232ms** | **148ms** |

## 결정

1. **필터와 패싯은 엔진 안에서 건다.** Lucene 은 FILTER 절과 문서값, ES·OpenSearch 는 filter 절과 filter 집계를 쓴다.
   필터 필드(대분류·중분류·색상·종류·가격·재고)를 색인에 넣는다
2. **엔진이 실패하면 후보 자르기로 물러선다.** 물러선 쪽(`like-fields`)의 상위 500개를 DB 에서 거른다. 개수가 틀릴 수 있지만
   검색이 죽지는 않는다. `catalog.search.fallback` 이 센다
3. **앱 안 Lucene 은 100만 건까지 쓴다.** 300만에서 지연 예산을 넘었다. 100만에서는 p95 86ms 로 예산까지 14ms 남는다.
   카탈로그가 100만을 넘기 전에 옮길 준비를 시작한다
4. **옮길 곳이 단일 노드 ES 는 아니다.** 단일 노드 ES 도 300만에서 148ms 로 예산을 넘었다. 옮긴다면 샤드를 나눈 클러스터이고,
   그 구성은 옮길 때 다시 잰다

## 설계에서 정한 것

- **필터는 점수에 끼지 않는다.** 순서는 검색어의 관련도가 정한다. 필터를 must 에 넣으면 "여성복"이라는 조건이 관련도를 올린다
- **패싯은 축마다 자기 축을 뺀 필터로 센다.** DB 패싯(ADR-044)과 같은 의미라 화면이 모드를 몰라도 된다
- **패싯은 일치 집합 전체를 센다.** 상위 몇 개가 아니다. Lucene 은 점수를 계산하지 않는 수집기(`COMPLETE_NO_SCORES`)로 센다
- **재고는 색인 시점 값이다.** 화면의 재고와 가격은 여전히 DB 에서 채운다. 필터 결과에 색인 뒤 품절된 상품이 섞일 수 있다
- **후보 자르기 모드를 설정으로 남긴다**(`filters-in-engine=false`). 측정의 비교 대상이고, 엔진이 필터 필드 없는 옛 색인일 때
  물러설 자리다

## 버린 것

| 안 | 이유 |
|---|---|
| 상위 500개를 받아 DB 에서 거르기 | 결과 수 95.5% 손실, 패싯 152/171 틀림. 첫 페이지는 153/171 이 같아 **눈에 덜 띄는 방식으로** 틀린다 |
| 후보를 늘리기(5,000개) | 재지 않았다. 정답 결과 수 중앙값이 1,246건이라 지금 규모의 중앙 쿼리는 덮지만, 결과 수는 카탈로그와 함께 커진다. 엔진에서 거르면 후보 수를 정할 일이 없다 |
| 지금 ES 로 옮기기 | 10.6만 건에서 지연이 같고(19 대 18ms), 반영 지연(#246)을 아직 재지 않았다 |

## 대가 (정직하게)

- **색인이 커진다.** 필터 필드와 문서값이 들어가 10.6만 건 색인이 6.0MB 가 됐다(ADR-051 때 5MB)
- **합성 카탈로그는 복제다.** 일치 집합이 규모에 비례해 커지는 가정이라 전환점은 작게 나온 쪽이다. 실제 카탈로그의 전환점은 이보다 클 수 있다
- 힙 증가는 색인 파일보다 1.6배 컸다(300만에서 276MB 대 175MB). 예산은 색인 크기로 적어 그것으로 판정했다

## 다시 볼 조건

- 카탈로그가 **100만 건**에 가까워질 때 → 실제 카탈로그로 이 벤치마크를 다시 돈다. 복제가 아닌 데이터라 전환점이 바뀔 수 있다
- #246 의 반영 지연 결과 → 즉시 반영이 필요하면 규모와 무관하게 엔진 선택을 다시 본다
- 여러 서비스가 같은 색인을 읽어야 할 때 → 앱 안 색인은 나눠 쓸 수 없다

# ADR-047. CDC 는 활동 로그에 쓰고, 아웃박스 릴레이는 그대로 폴링으로 둔다

- 상태: **채택**
- 날짜: 2026-09-23
- 관련: `compose.yaml`(debezium), `cdc/register-user-activity-connector.json`,
  `KafkaContextTransport`, `UserActivityEvent`, `docs/03-아키텍처-설계.md`, 이슈 #209

## 맥락

`docs/03-아키텍처-설계.md` 는 **트랜잭셔널 아웃박스의 릴레이 방식**을 고르면서 두 후보를 적었다.

> Relay 구현: ① **Polling Publisher**(주기 폴링, 구현 단순, 이 시스템에서 채택) ② CDC/Debezium(binlog 추적)

그런데 이번에 **Debezium 을 도입했다.** 문서가 "채택하지 않은 대안" 으로 적어 둔 것을 들여온 셈이라,
읽는 사람은 **그 결정이 뒤집힌 것인지** 묻게 된다.

**뒤집지 않았다.** 두 CDC 는 **다른 문제를 푼다.**

## 두 자리가 어떻게 다른가

| | 아웃박스 릴레이 (`docs/03`) | 활동 로그 전달 (이번) |
|---|---|---|
| 무엇을 나르나 | **트랜잭션이 이미 커밋한 사실** | 사용자 활동 원본 행 |
| 왜 어려운가 | DB 커밋과 발행이 갈라지면 **유실이거나 유령 이벤트** | 쓰기 경로에 브로커가 붙으면 활동이 주문을 건드린다 |
| 무엇을 지키나 | **at-least-once 발행 보장** | **결제·주문 경로의 격리** |
| 늦으면 | 정합성 문제 | 개인화 신선도 문제 |

아웃박스는 **정합성 장치**다. 릴레이가 폴링이든 CDC 든 "커밋된 것은 반드시 나간다" 는 성질이 핵심이고,
폴링으로도 그 성질이 성립한다. 주기가 늦으면 이벤트가 늦게 갈 뿐 **사라지지는 않는다.**

활동 로그는 다르다. 여기서 아픈 것은 유실이 아니라 **결합**이다. 활동을 앱이 직접 발행하면 브로커가
흔들릴 때 그 여파가 주문·결제 경로에 들어온다. 그리고 **주기가 곧 신선도 상한**이 된다 — 활동은 양이
많고 빨라야 한다. 아웃박스 폴링에 활동까지 얹으면 그 주기 하나가 두 성질을 동시에 정한다.

## 결정

- **아웃박스 릴레이는 Polling Publisher 를 유지한다.** `docs/03` 의 결정은 그대로다
- **활동 로그(`user_activities`)만 CDC 로 나른다.** `user.activity` 토픽으로 흘리고
  기존 `KafkaContextTransport` 가 그대로 소비한다 — **새 컨슈머를 만들지 않았다**

## 버린 것

**운영 부품이 하나 늘었다.** Debezium Connect 를 띄워야 하고, 커넥터 설정·스키마 히스토리 토픽·
복제 클라이언트 id 가 관리 대상이 된다. 폴링 릴레이에 얹었다면 늘지 않았을 것들이다.

**binlog 를 켜야 한다.** `ROW` + `FULL` 이라 binlog 크기가 커진다. 로컬은 무시할 수 있지만 운영이면
보존 기간과 디스크를 같이 정해야 한다.

**DB 스키마가 계약이 된다.** 컬럼 이름이 곧 메시지 필드라, 표를 바꾸면 소비자가 깨진다. 아웃박스는
그 사이에 이벤트 레코드를 두어 막아 준다. 여기서는 SMT 의 `renames` 가 그 얇은 완충재다 —
**표를 고치면 이 설정도 같이 고쳐야 한다.**

## 지키기로 한 성질 하나

`UserActivityEvent` 의 `@Externalized` 는 라우팅 키를 **`userId`** 로 잡는다. 같은 사용자의 활동이
같은 파티션에 들어가 순서가 보존되고, 그래서 컨슈머가 사용자별 read-modify-write 에 **분산 락을 쓰지
않는다.**

Debezium 의 기본 키는 테이블 PK(`id`) 다. 그대로 두면 **그 전제가 조용히 깨진다.** 지금 파티션이
하나라 드러나지 않을 뿐이다. `ValueToKey` + `ExtractField$Key` 로 키를 `userId` 로 만들었다.

**CDC 로 바꿀 때 지켜야 하는 것은 토픽 이름이 아니라 이 성질이었다.**

## 아직 재지 않은 것

**신선도가 좋아졌다고 쓰지 않는다.** 이 결정은 결합을 끊으려고 한 것이고, 지연이 실제로 어떻게
변했는지는 E1 하네스 재측정 전에는 모른다. 그 전까지 "빨라졌다" 도 "같다" 도 쓰지 않는다.

`snapshot.mode=schema_only` 라 **기존 49,010 행은 흐르지 않는다.** 그 백필이 필요한지는 별도 결정이고,
지금 켜면 측정이 백필 트래픽에 오염된다.

## 다시 볼 조건

- `user.activity` 파티션을 **1 보다 크게 늘리면** 키 설정을 반드시 다시 확인한다(#361 에서 4파티션으로 확인했다, 아래 절). 그때가 위 성질이
  실제로 시험되는 시점이다
- `user_activities` 컬럼을 바꾸면 `renames` 를 같이 고친다. 표와 설정이 갈라지면 소비가 조용히 깨진다
- 커넥터의 `topic.prefix` 를 바꾸면 `predicates.isData.pattern` 을 같이 고친다. 패턴이 prefix 를 박고 있어 어긋나면 라우팅 · 키 변환이 조용히 빠진다(#361)
- 활동 외에 다른 표를 CDC 로 나르고 싶어지면 **이 문서를 다시 연다.** 표가 늘수록 "스키마가 계약"
  이라는 대가가 커지고, 어느 선부터 아웃박스에 이벤트를 싣는 편이 싼지가 갈린다

## 파티션이 여럿일 때 키가 사용자별 순서를 지키는지 (#361, 2026-09-26)

일회용 CDC 스택에서 저장소의 `user-activity` 커넥터 설정을 **4파티션 토픽**으로 보내고, 키 변환(`keyFromValue` · `keyField`)을 뺀 대조를 다른 4파티션 토픽으로
같이 보냈다. 사용자 50명 × 40건(사용자마다 seq 1..40)을 사용자를 섞어 넣었다. 예측과 기준은 이슈에 측정 전에 적었다.

| 설정 | 받은 레코드 | 파티션 하나에 모인 사용자 | 사용자당 파티션 수 | 파티션 안 seq 역전 | 키 |
|---|---:|---:|---:|---:|---|
| **저장소 설정(키 = userId)** | 2,000 / 2,000 | **50 / 50** | 1 | 0 | `7000009` 같은 사용자 id |
| 키 변환 없음(기본 키 = PK) | 2,000 / 2,000 | 0 / 50 | **4(50명 모두)** | 0 | `{"id":13004}` 같은 행 id |

- **파티션 4개에서도 같은 사용자의 활동은 한 파티션에 순서대로 들어갔다.** ADR 이 적은 성질이 파티션을 늘려도 선다
- 키 변환을 빼면 50명 모두 4개 파티션에 흩어졌다. 파티션 안 순서는 지켜지지만 사용자 단위 순서는 보장되지 않는다. "조용히 깨진다"가 실제로 이 모양이다
- **또 하나의 조용한 결합**: 변환에 붙인 조건식(`predicates.isData.pattern`)이 `pay\-cdc\.becommerce\..*` 로 `topic.prefix` 를 박아 두었다. 측정에서 prefix 만 바꾸자
  라우팅 · 키 변환이 통째로 빠져 레코드가 `<prefix>.becommerce.user_activities` 로 갔고 받은 토픽은 0건이었다(첫 두 시도). prefix 를 바꿀 때는 조건식 패턴도 같이 바꾼다
- 토픽 파티션 수(1)와 설정은 바꾸지 않았다. 원자료 [`performance/raw/20260926-a047-361/`](../performance/raw/20260926-a047-361/)

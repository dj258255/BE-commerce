# ADR-073. 정산 배치 병렬화 — 나누는 키(모듈러 대 항목 id 범위 대 판매자 크기 묶음)

- 상태: 채택(비교 실험, 프로덕션 미배선)
- 날짜: 2026-09-28
- 관련: `SettlementService`(34~35행, 단일 스레드 서비스 루프), ADR-027(정산 공정성), [ADR-072](ADR-072-restart-warmup-ramp-vs-immediate.md)(같은 27절 실험 방법론), 이슈 #424, `SettlementBatchPartitionExperimentTest`

## 맥락

토스페이먼츠 "레거시 정산 개편기"는 Multi-Threaded Step의 읽기가 스레드 안전하지 않아 모듈러 연산과 날짜 기반 Range 파티셔닝으로 각 스레드가 처리할 데이터를 미리 나눠 처리 시간을 크게 줄였다고 밝혔다. 다만 특정 판매자 쏠림은 원문에 언급이 없었다. 이 저장소의 `SettlementService`는 지금 단일 스레드 루프로 판매자별 순회하며 집계한다. 정산 항목을 여러 스레드로 나눌 때 나누는 키에 따라 스레드별 부하 균형과 판매자별 집계의 동시 쓰기 위험이 어떻게 달라지는지 쟀다.

## 측정 방법

`SettlementBatchPartitionExperimentTest`(`@Tag("experiment")`, 순수 JUnit, Docker 불필요, `SettlementService`에 배선하지 않음)로 항목 20만 건(토스 사례 100만 건에서 축소)을 판매자 200곳에 분포 둘로 나눴다.

- **UNIFORM**: 판매자마다 1000건씩 균등.
- **SKEWED**: 판매자 1곳이 50%(10만 건), 남은 199곳이 나머지 50%를 나눠 가짐.

세 가지 나누기를 스레드 4개로 비교했다(스레드 1은 직렬 기준).

- **MODULO**: 판매자 id % 스레드 수.
- **RANGE**: 항목 id 순서로 균등하게 자름(판매자 경계 무시).
- **SIZE_GROUPED**: 판매자별 항목 수를 먼저 구해 LPT(longest processing time first) bin-packing으로 스레드에 배정(판매자는 항상 통째로 한 스레드).

항목 처리는 실제 DB I/O 없이 수수료 계산(산술)만 하고, 판매자별 gross 합산은 `ConcurrentHashMap`의 원자적 `addAndGet`으로 모았다 — 동시 쓰기 자체가 사고인지, 원자적 병합이면 안전한지를 구분해서 봤다.

판정 기준은 측정 전 [이슈 #424](https://github.com/dj258255/BE-commerce/issues/424)에 적었다.

## 실측 결과

| 조건 | 처리 건수 | 불균형(최대/평균) | 판매자 분산(2개 이상 스레드에 걸침) | 불변식 위반 | 완료 시간(참고) |
|---|---:|---:|---:|---:|---:|
| SERIAL(1스레드)/UNIFORM | 200000 | 1.00 | 0 | 0 | 42ms |
| MODULO/UNIFORM | 200000 | 1.00 | 0 | 0 | 33ms |
| RANGE/UNIFORM | 200000 | 1.00 | 200 | 0 | 43ms |
| SIZE_GROUPED/UNIFORM | 200000 | 1.00 | 0 | 0 | 22ms |
| MODULO/SKEWED | 200000 | 2.49 | 0 | 0 | 5ms |
| RANGE/SKEWED | 200000 | 1.00 | 200 | 0 | 52ms |
| SIZE_GROUPED/SKEWED | 200000 | 2.00 | 0 | 0 | 56ms |

완료 시간은 참고용으로만 남긴다. 이 기계에 다른 세션의 `run-d2.sh`가 같은 시간대에 돌고 있었고(측정은 20만 건을 4스레드로 나눠 1초 미만에 끝나 그 부하와 실질적으로 겹치지 않았다고 보지만), 애초에 항목당 실제 I/O 없이 산술만 해 완료 시간 자체가 이 실험의 판정 대상이 아니다.

## 가설 판정

측정 전 이슈 #424에 적은 다섯 가지 중 넷은 판정 기준대로 맞았고, 하나(SIZE_GROUPED의 균등 분배 기대)는 부분적으로 틀렸다.

1. **맞았다.** 모든 조건에서 처리 건수가 입력(20만 건)과 정확히 같다.
2. **맞았다.** 모든 조건에서 정산 불변식(판매자별 항목 합 = 집계 gross) 위반이 0건이다. `ConcurrentHashMap.addAndGet`의 원자적 병합이 RANGE처럼 판매자가 여러 스레드에 흩어져도 안전했다.
3. **맞았다.** SKEWED에서 MODULO의 불균형(2.49)이 RANGE(1.00)·SIZE_GROUPED(2.00)보다 크다.
4. **맞았다.** RANGE의 판매자 분산(200곳 모두 2개 이상 스레드에 걸침, UNIFORM·SKEWED 둘 다)이 SIZE_GROUPED(0곳)보다 뚜렷이 크다. SIZE_GROUPED·MODULO는 설계상 판매자를 쪼개지 않아 분산이 항상 0이다(구현이 그렇게 만든 것이지 실측 발견이 아니다).
5. **부분적으로 틀렸다.** "SIZE_GROUPED가 균등 분배와 판매자 단일 스레드 처리를 동시에 얻을 것"이라고 예상했지만, SKEWED에서 SIZE_GROUPED의 불균형도 2.00으로 MODULO(2.49)보다 낮을 뿐 1.00에 가깝지 않았다. 이유는 산술적으로 자명하다 — 판매자 1곳이 전체의 50%(스레드 4개 기준 평균 점유율 25%의 2배)를 차지하면, 그 판매자를 <b>쪼갤 수 없는 단위</b>로 다루는 한(SIZE_GROUPED·MODULO 둘 다 그렇다) 그 판매자를 받은 스레드는 최소 전체의 50%를 지게 되어 불균형이 2.00 밑으로 내려갈 수 없다. bin-packing은 "남은 판매자들을 어떻게 배정하느냐"만 최적화할 뿐, 압도적으로 큰 단일 판매자 자체는 어떤 배정 알고리즘으로도 못 나눈다. RANGE만 항목 단위로 잘라 이 하한을 피한다 — 대신 판매자 분산(동시 쓰기 위험)을 대가로 치른다.

## 이 실험이 답하지 못하는 것

- 실제 MySQL 데드락·행 락 대기는 재지 않았다. 시뮬레이션은 비차단(각 스레드가 자기 파티션만 쓰고, 판매자별 합산만 원자적 자료구조로 공유) 설계라 애초에 데드락이 날 수 없다 — "데드락 0건"은 설계상 자명하지 실측 근거가 아니다.
- 스레드 수 스윕(1·2·4·8)은 하지 않았다. 1(기준)과 4만 비교했다.
- 항목 100만 건 전체 규모는 재지 않았다(20만으로 축소).
- 동시 결제 경로에 대한 실제 지연 영향(같은 MySQL 버퍼 풀·redo·원장 hot account 행 락)은 재지 않았다. 순수 JUnit이라 실제 DB 경합을 재현할 방법이 없다.
- `SettlementService`에 실제로 배선하지 않았다. 26·27절의 다른 실험과 같은 스코프로, 비교 근거만 남긴다.
- RANGE가 만드는 "판매자별 집계 동시 쓰기"가 이 실험처럼 항상 원자적 자료구조로 안전하게 병합된다는 보장은 실제 `SettlementService`(JPA 엔티티 dirty-check, `saveAndFlush`)에는 없다 — 같은 판매자의 `Settlement` 행을 두 스레드가 동시에 갱신하면 낙관적 락 충돌이나 갱신 유실이 생길 수 있다. 이 실험은 "쪼개짐 자체가 위험 신호"라는 것만 보여주지, 실제 JPA 엔티티에서 그 위험이 어떤 형태로 나타나는지는 재지 않았다.

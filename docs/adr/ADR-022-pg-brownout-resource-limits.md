# ADR-022. 느린 PG 앞에서 무엇을 먼저 포기할 것인가

- 상태: **채택(기본값 40 으로 켬)**. 실측을 마쳤고(아래 "실측 결과"), **가정한 PG 응답시간 분포로 값을 유도해 기본값을 켰다**(맨 아래).
- 날짜: 2026-09-18 (원안) / 2026-09-18 (실측 반영)
- 관련: [ADR-007](ADR-007-checkout-transaction-boundary.md), [ADR-020](ADR-020-multi-pg-routing-off-by-default.md), `ResilientPgClient`, `TossPgClient`

## 맥락

ADR-007에서 체크아웃을 3단계 사가로 옮겼다. PG 승인이 트랜잭션 밖으로 나가서 **DB 커넥션은 더 이상 PG 응답까지 묶이지 않는다.** 거기까지는 맞다.

그런데 그 ADR 마지막에 이렇게 적어 뒀다.

> **아직 안 잰 것**: 필요한 커넥션 수는 대략 `초당 결제 요청 × PG 응답 시간`이다. PG 지연을 주입한 부하로 풀 점유를 재기 전까지는 "여유 있다"고 쓰지 않는다.

아직 안 쟀다. 그리고 재려고 설정을 다시 보니, 사가가 푼 것은 **DB 커넥션 하나**였다.

| 자원 | 설정 | PG가 느려질 때 |
|---|---|---|
| Hikari 커넥션 | `maximum-pool-size: 20` | 사가 이후 PG 응답과 무관해졌다 |
| 톰캣 워커 스레드 | `threads.max: 100` | **여전히 PG 응답까지 묶인다** |
| PG 동시 호출 | **상한 없음** | 들어온 만큼 전부 나간다 |

PG read-timeout은 `TossPgClient`의 `@Value` 기본값으로 5초다(connect 2초). PG가 5초에 수렴하면 워커 100개가 각각 5초를 붙잡으므로 **처리량 상한이 초당 20건**으로 내려앉는다. 이때 Hikari 풀 20은 오히려 한가하다. 병목이 사라진 것이 아니라 **DB 풀에서 스레드 풀로 옮겨갔다.**

**서킷 브레이커는 이 경우를 못 잡는다.** `ResilientPgClient`의 설정은 5건 창, 실패율 50%, open 5초다. 서킷은 **실패**를 센다. PG가 4.9초씩 걸리면서 **성공**하면 실패율은 0이고 서킷은 열리지 않는다. 죽지 않고 느려지는 장애(브라운아웃)가 완전 장애보다 어려운 이유가 이 설정에 그대로 있다.

## 결정할 것

PG가 느려져 자원이 마를 때 **무엇을 먼저 버릴 것인가.** 네 가지 선택지가 있고 전부 다른 것을 포기한다.

| 선택지 | 포기하는 것 | 이 맥락에서 걸리는 질문 |
|---|---|---|
| **A. PG 동시 호출 세마포어** | 상한을 넘은 요청의 처리 자체(즉시 429) | 상한을 몇으로 잡나. `스레드 100 ÷ PG 5초`는 산수지 근거가 아니다 |
| **B. 느림도 실패로 세어 서킷을 연다** | 아직 성공할 수 있었던 요청 | 임계 응답시간을 넘으면 실패로 볼지, 그 오탐 비용이 얼마인지 |
| **C. read-timeout을 5초에서 2초로** | 5초면 왔을 승인 | **끊은 호출은 전부 `UNKNOWN`이 된다.** 미확정 재고를 내 손으로 만드는 것이다 |
| **D. 대기열에 넣고 나중에 확정** | 즉시 응답이라는 사용자 경험 | 결제가 비동기가 되면 화면·환불·CS 규약이 전부 바뀐다 |

**C가 이 시스템에서 특히 까다롭다.** 타임아웃을 조이면 장애는 빨리 끝나는데, 끊긴 호출은 ADR-007의 규약대로 TIMEOUT(=`UNKNOWN`)으로 흘러 복구 배치의 일거리가 된다. **가용성을 사면서 정합성 부채를 내는 거래**라서, 얼마나 사고 얼마나 내는지를 숫자로 보기 전에는 고를 수 없다.

## 재는 방법

측정 없이는 고르지 않는다(docs/performance의 기존 원칙과 같다).

**준비**: `FakePgClient`에 응답 지연 주입 스위치를 붙인다. `TossPgClient`는 실 PG라 지연을 주입할 수 없고, 앱↔PG 사이에 Toxiproxy를 세우는 것보다 가짜 PG에 지연을 넣는 쪽이 재현이 결정적이다. 기본값 0이면 지금 동작과 같다.

**1단계. 병목이 어디로 옮겨갔는지 본다.** PG 지연을 200ms → 1s → 3s → 5s로 올리며 각 단계에서 다음을 동시에 기록한다.

- Hikari 활성 커넥션 수 (`hikaricp_connections_active`)
- 톰캣 활성 스레드 수 (`tomcat_threads_busy_threads`)
- 체크아웃 p95와 처리량

사가 전후를 같은 방식으로 재면 "커넥션은 풀렸고 스레드는 안 풀렸다"가 한 표로 나온다. (재려고 보니 워커 지표는 Prometheus에 **나가고 있지 않았다.** 아래 "부수 발견" 참고.)

**2단계. 세마포어 상한을 고른다.** 상한 없음·40·20으로 돌리며 잰다.

- 정상 요청 p95 (상한이 지키는 값)
- 429 거절률 (상한이 내는 비용)
- 상한 없음에서 스레드가 마르기까지 걸리는 시간

**3단계. 타임아웃이 만드는 부채를 센다.** read-timeout 5초와 2초로 같은 부하를 돌리고 `UNKNOWN` 생성 건수와 복구 배치가 확정하기까지의 최고 경과시간을 비교한다.

**나올 문장의 형태**는 이렇다. "몇 ms 빨라졌다"가 아니다.

> PG가 3초를 넘기면 상한 없이는 N초 만에 워커가 마른다. 상한을 10으로 두면 거절률 X%를 내고 정상 요청 p95를 Yms로 지킨다. 대신 타임아웃을 2초로 조이면 미확정이 Z배가 되고 복구 배치가 그만큼 더 돈다.

## 대가 (어느 쪽을 고르든)

**상한을 두면 거절이 생긴다.** 지금은 느려도 언젠가는 처리된다. 상한을 두는 순간 "처리하지 않기로 한 결제"가 생기고, 그것이 사용자에게 어떻게 보일지를 정해야 한다. 결제 실패 화면은 재고 부족과 자원 부족을 구분하지 않는다.

**그리고 이건 ADR-020과 붙어 있다.** 실 PG가 둘이면 브라운아웃은 라우팅으로도 다룰 수 있다. 다만 ADR-020의 규칙대로 **타임아웃은 failover 하지 않으므로**, 느린 PG에서 넘길 수 있는 것은 아직 보내지 않은 요청뿐이다. 이미 나간 요청은 여기서 정한 방식으로 처리해야 한다.

## 참고

- Netflix Hystrix: bulkhead 격리. 타임아웃만으로 부족하고 동시성 상한이 따로 필요한 이유
- Google SRE Book, Handling Overload: 느려지는 장애가 죽는 장애보다 다루기 어렵다
- "Connection Pool Exhaustion" postmortem 모음 (ADR-007에서 인용). 서킷 브레이커도 기다리는 동안 자원이 찬다

## 실측 결과

로컬 Apple Silicon, 실 MySQL 8.4·실 Redis, 가짜 PG 에 지연 주입. 각 런은 15초 워밍업 뒤 45초 본 측정이고, `tools/run-pg-brownout.sh` 와 `k6/pg-brownout.js` 로 재현한다. 톰캣 워커 상한은 100, Hikari 풀은 20 이다.

**워밍업이 없으면 결론이 뒤집힌다.** 기동 직후 첫 런은 JIT·커넥션 생성이 섞여 지연 0 의 p95 가 903ms 로 나왔다. 같은 설정에 워밍업을 넣으니 99.5ms 다. "지연 0 이 200ms 보다 느리다"는 값이 여기서 나왔다.

### 1단계. 병목이 어디로 옮겨갔는가 (도착률 30/s · read-timeout 5s · 상한 없음)

| PG 지연 | Hikari 활성(평균/최대) | 워커 busy(평균/최대) | 결제 p95 | 처리량 |
|---|---|---|---|---|
| 0 | 5.9 / 16 | 3.6 / 9 | 99.5ms | 29.9/s |
| 200ms | 5.9 / 15 | 9.0 / 13 | 303ms | 29.8/s |
| 1s | 5.4 / 16 | 32.6 / 37 | 1.08s | 29.3/s |
| 3s | 5.0 / 14 | 86.6 / 96 | 3.07s | 28.1/s |
| 5s | 9.6 / 20 | 79.0 / **100** | **14.26s** | **17.6/s** |

**커넥션은 평평하고 워커만 오른다.** PG 지연이 0 에서 3초로 30 배가 되는 동안 Hikari 활성은 평균 5.9 에서 5.0 으로 오히려 줄었고, 워커는 3.6 에서 86.6 으로 24 배가 됐다. 사가가 푼 것은 커넥션이고 마르는 자리는 워커로 옮겨갔다는 것이 수치로 확인된다.

점유 수는 리틀의 법칙 그대로다. `도착률 × 응답시간` = `30 × 3` = 90 이고 실측 86.6 이다. 그래서 **워커 100 개로 버틸 수 있는 PG 지연의 상한은 도착률 30/s 에서 약 3.3초**다. 5초에서는 워커를 다 쓰고 p95 가 PG 지연(5초)의 세 배인 14.26초까지 밀렸다. 대기가 쌓인 것이고, 그 구간에서 부하기는 도착률조차 유지하지 못했다(205 건 미발사).

### 2단계. 상한이 지키는 것은 결제가 아니라 나머지다 (PG 지연 3s · 도착률 50/s)

수요가 워커 수를 넘도록 도착률을 50/s 로 올렸다(`50 × 3s` = 150 > 100). 같은 앱에 가벼운 조회(주문 목록)를 초당 20 건 같이 밀어 넣고 태그를 갈라 쟀다.

| 상한 | **조회 p95** | 결제 p95 | 결제 성공 | 결제 거절 | 워커 busy(평균/최대) |
|---|---|---|---|---|---|
| 없음 | **7.31s** | 9.78s | 1,729 | 0 | 84.1 / 100 |
| 40 | 769ms | 4.32s | 598 | 1,653 | 53.0 / 100 |
| 20 | **18.6ms** | 3.06s | 300 | 1,951 | 23.3 / 31 |

> 상한 40 행(769ms · 워커 100)은 재현되지 않았다(2026-09-26, #326). 같은 커밋과 현재 main 에서 3회씩 다시 재니 조회 p95 6.57~9.14ms · 워커 최대 44~45 로 [성능 §14.4](../performance/README.md) 와 같았다. 코드가 아니라 당시 측정 환경의 차이로 보고, 상한 40 의 대표값은 §14.4 를 쓴다.

**상한이 없으면 느린 PG 가 결제와 무관한 조회까지 7.31초로 끌어내린다.** 평시 8ms 짜리 조회다. ADR-007 이 커넥션 풀에서 막았던 연쇄 장애가 워커 풀에서 그대로 재현됐다.

**상한은 결제를 빠르게 하지 않는다. 결제를 깎아 나머지를 지킨다.** 상한 20 에서 조회 p95 는 7.31초에서 18.6ms 로 약 390 배 나아지는데, 그 대가로 결제 1,951 건이 거절된다. 처리량 상한은 `상한 ÷ PG 지연` 이라 상한 20·지연 3초면 초당 6.7 건이 천장이고 실측 6.5 건이다.

**정상 구간에서는 물지 않는다.** 지연 0·도착률 30/s·상한 40 에서 거절 0 건, 조회 p95 26.7ms, 워커 평균 4.2 였다. 상한은 PG 가 이미 망가졌을 때만 발동한다.

### 3단계. 타임아웃을 조이면 무엇을 내는가 (PG 지연 5s · 도착률 30/s)

| read-timeout | 결제 p95 | 처리량 | **미확정(202)** | 워커 busy 평균 |
|---|---|---|---|---|
| 5s | 14.26s | 17.6/s | 0 | 79.0 |
| 2s | **2.13s** | 28.6/s | **1,351 (전량)** | 59.5 |

타임아웃을 5초에서 2초로 조이면 p95 가 6.7 배 좋아지고 처리량이 돌아온다. 대신 **그 구간의 결제가 전부 미확정이 된다.** 복구 배치가 조회로 닫아야 할 일거리가 0 건에서 1,351 건으로 바뀐다. 가용성을 사면서 정합성 부채를 낸다는 말의 실제 크기가 이것이다.

### 4단계. 워커 수를 바꿔도 식이 맞는가, 상한 40 에서 타임아웃 2초는 무엇을 내는가 (#335, 2026-09-26)

PG 지연 3초 · 결제 50/s · 조회 20/s · 45초. 요구 동시성은 50 × 3 = 150. 예측과 판정 기준은 [이슈 #335](https://github.com/dj258255/BE-commerce/issues/335)에 측정 전에 적었다.
표와 원자료는 [리포트](../performance/pg-cap-workers.md).

| 상한 | 예측 거절 | 워커 100 | 워커 150 | 워커 200 |
|---:|---:|---|---|---|
| 40 | 73.3% | 73.3% · 조회 6.9ms | 73.3% · 6.8ms | 73.3% · 7.3ms |
| 80 | 46.7% | 46.7% · 8.2ms | 46.7% · 7.3ms | 46.7% · 7.5ms |
| 120 | 20.0% | **0% · 조회 6,820ms**(결제 p95 9.4초) | 20.0% · 8.1ms | 20.0% · 8.6ms |

- **상한이 워커보다 작은 여덟 칸에서 거절률이 식과 0.0%p 로 같았다.** 식은 워커 수와 무관하다
- **상한이 워커 이상이면(100 · 120) 상한이 없는 것과 같다.** 거절은 0 이 되고 워커 100 개가 다 차서 무관한 조회가 6.8초가 됐다. 상한은 워커보다 작아야 의미가 있다

상한 40 · 워커 100 에서 read-timeout 만 2초로 줄이면(PG 3초보다 짧다):

| read-timeout | 거절(예측) | 즉시 승인 | 미확정(측정 45초) | 복구 뒤 | 조회 p95 |
|---:|---:|---:|---:|---|---:|
| 5초 | 73.3%(73.3%) | 600 | 0 | — | 6.9ms |
| 2초 | 59.6%(60.0%) | **0** | 909(약 900) | 워밍업 포함 1,060건이 측정 끝 179초 뒤 전부 승인(예측 1~3분) | 6.1ms |

2초는 거절을 13.7%p 줄이고 PG 에 닿은 결제를 모두 결국 승인으로 확정했다. 대가는 **즉시 확정되는 결제가 0 건**이 되는 것이다. 사용자는 최대 3분 동안 "처리 중"을 본다.

## 고른 것

**상한 메커니즘을 채택한다.** `payment.pg.max-concurrent-calls` 로 PG 동시 호출에 세마포어를 건다.

**상한에 걸린 요청은 확정 실패로 돌린다. 미확정이 아니다.** permit 을 못 얻으면 호출이 나가기 전에 끊기므로 요청이 PG 에 **닿지 않은 것이 보장된다.** 그때 미확정으로 적으면 복구 배치가 조회할 대상조차 없는 유령 미확정이 생긴다. 닿지 않았음이 보장될 때만 실패로 확정한다는 규칙은 [ADR-020](ADR-020-multi-pg-routing-off-by-default.md) 의 failover 판정과 같은 근거다.

> **서킷 오픈도 같은 규칙을 따른다(2026-09-26, #372).** 서킷이 열려 보내지 않은 승인을 그동안 미확정으로 적어 왔다.
> 호출이 나가지 않았으니 닿지 않은 것이 보장되는 자리라 확정 실패로 바꿨다. 같은 PR 에서 서킷을 승인 · 취소 · 조회로 나눴다.

> **상한이 지키는 것에 웹훅도 있다(2026-09-24, #230).** PG 지연 5초에서 상한이 없으면 웹훅 p95 가
> **13초**가 되고 **26.1% 가 토스 10초 규약을 넘긴다** — 그 건들은 재전송 대상이 되고 재전송이 다시
> 워커를 먹는다. 상한 40 이면 같은 조건에서 **9ms · 초과 0%** 다. 표는 [성능 14.6절](../performance/README.md).

**상한은 워커 수보다 작게 둔다.** 워커 이상이면 상한 없음과 같다(4단계, 워커 100 · 상한 120 에서 조회 6.8초). 워커를 늘리면 상한을 올릴 여지가 생기지만 거절률은 워커가 아니라 상한이 정한다.

**기본값은 40 으로 켠다.** 유도 과정은 맨 아래 "값을 어떻게 골랐나" 에 적는다. 조회를 더 지켜야 하면 20 으로 내리되 결제 처리량이 절반이 된다는 것을 알고 내린다.

## 안 고른 것과 이유

**느림을 실패로 세어 서킷을 여는 것**은 채택하지 않았다. 임계 응답시간을 넘으면 실패로 보는 방식인데, 그 임계값 역시 PG 응답시간 분포가 있어야 정할 수 있어서 상한과 같은 문제를 하나 더 만든다. 상한은 적어도 "워커를 몇 개까지 내줄 것인가"라는 **우리 쪽 자원**으로 정할 수 있다.

**read-timeout 을 2초로 조이는 것**도 하지 않는다. 3단계에서 봤듯 이건 미확정을 만드는 거래다. 4단계에서 복구 배치는 그 양(45초에 909건)을 3분 안에 전부 승인으로 닫았다. 감당은 된다. 그래도 PG 가 타임아웃보다 느리면 **즉시 승인이 0 건**이 되고, 줄어드는 거절은 13.7%p 다. 실 PG 분포 없이 사용자 경험을 그렇게 바꿀 근거가 없다.

**대기열 전환**은 범위 밖이다. 결제가 비동기가 되면 화면·환불·상담 규약이 같이 바뀐다.

## 값을 어떻게 골랐나 (2026-09-19)

실 PG 응답시간 분포가 없으므로 **가정한다. 그 가정을 여기 적는다.** 가정이 틀리면 값도 틀리고, 다시 계산하는 방법은 아래 그대로다.

**가정**: 피크 도착률 30/s, 정상 구간 PG 승인 p99 1초.

**하한 — 정상에서 물면 안 된다.** 동시 점유는 `도착률 × 응답시간` 이므로 `30 × 1s = 30` 이다. 상한이 30 보다 작으면 **아무 장애가 없는데도 결제를 거절한다.** 그래서 30 이 하한이다. 실측으로도 확인했다. 지연 0·도착률 30/s·상한 40 에서 거절 0 건, 워커 평균 4.2 였다.

**상한 — 브라운아웃에서 워커를 남겨야 한다.** 워커는 100 이다. 40 까지만 내주면 60 이 남는다. 상한 없이 두면 PG 지연 3초·도착률 50/s 에서 워커 84.1 개가 상시 점유되고, 결제와 무관한 조회 p95 가 8ms 에서 **7.31초**가 됐다.

**둘을 만족하는 구간이 30~60 이고 40 을 고른다.** 하한에 여유를 두되(33%) 워커의 과반을 남긴다.

> **유도 방식이 성립하는지 나중에 확인했다(2026-09-23, #223).** 지연을 축으로 쓸어 재니
> 거절률이 `1 − 상한 ÷ (도착률 × 지연)` 으로 **소수점까지 예측됐다**(3초 이상에서 오차 0.1%p 이내).
> 거절이 시작되는 지연도 `상한 ÷ 도착률` 로 계산되고 실측이 그 사이에 떨어진다.
> 즉 **위의 `도착률 × 응답시간` 계산은 실제로 맞는 모델이다** — 가정한 것은 분포이지 계산이 아니다.
> 표는 [성능 14.4절](../performance/README.md).

| 상한 | 정상에서 무나 | 브라운아웃 조회 p95 | 브라운아웃 결제 처리량 |
|---|---|---|---|
| 없음 | 안 뭄 | 7.31s | 30/s |
| 40 | 안 뭄 (거절 0 확인) | 769ms | 12.4/s |
| 20 | **가정 피크에서 문다** | 18.6ms | 6.5/s |

20 이 조회를 가장 잘 지키지만 **가정한 피크(30 동시)보다 낮아서 평시에도 거절이 난다.** 그래서 고르지 않았다. 조회를 그만큼 지켜야 하는 상황이라면 상한을 내릴 것이 아니라 결제와 조회의 워커 풀을 나누는 쪽이 맞다.

## 이 값을 다시 계산해야 하는 때

- **실 PG 를 붙여 p99 가 잡히면.** 위 계산의 1초를 그 값으로 바꾼다
- **피크 도착률이 30/s 를 넘으면.** 하한이 올라가므로 상한도 올린다. 안 올리면 평시에 거절이 난다
- **`server.tomcat.threads.max` 를 바꾸면.** 상한의 천장이 워커 수에서 나온다
- 셋 중 하나라도 바뀌었는데 이 값이 그대로면, 그건 근거 없는 숫자다

## 2026-09-27 여러 대일 때 상한을 어떻게 나누나 (#387)

위 40 은 워커 100 개 중 60 개를 무관한 요청 몫으로 남기는 값이라 인스턴스 안에서는 맞다. 그런데 API 를 여러 대 띄우면 PG 가 받는 동시 호출은 40 × 대수가 된다. PG(가맹점 계약)에 동시 처리 한도가 있으면 대수를 늘리는 순간 그 한도를 넘고, 넘은 호출은 PG 안에서 줄을 서다 읽기 타임아웃(5초)에 걸려 결과 모름이 된다.

`MultiInstancePgLimitExperimentTest` 로 쟀다. 실제 `ResilientPgClient` 를 대수만큼 만들어 공유 PG 스텁 하나를 부르게 했다(`prod` 프로필은 청구 게이트웨이 구현이 없어 뜨지 않고 가짜 PG 는 인스턴스마다 따로라서다). PG 계약 한도 60 은 가정이다. 초당 50건 승인, 느린 PG(처리 3초) 30초.

정상 PG(200ms)에서는 모든 조건이 1,500건 모두 성공하고 거절 0 이었다. 같은 조건을 두 번 잰 것은 같은 값이 나왔다.

- **대수를 늘리면 장애 때 오히려 덜 판다.** 3대는 1대보다 성공이 적고(291 대 400) 결과 모름 252건을 만들었다. PG 한도를 넘은 호출이 한도 안의 호출까지 늦춰 모두가 타임아웃에 가까워진다. 승인 서킷이 열려 거절한 것도 627건이다
- **합을 PG 한도에 맞추면 가장 많이 판다.** 나누든(20 × 3) 전역으로 세든 성공 600, 결과 모름 0 이다. 한 건이 3초에 끝나니 한도 60 을 채우면 초당 20건이다
- **적응형은 PG 의 느림을 혼잡으로 읽었다.** Gradient2 는 지연이 200ms → 3초로 뛰자 한도를 초기값(20) 아래로 줄였다. 결과 모름은 0 이지만 성공이 1대일 때보다 적다. Vegas 는 반대로 한도를 키워 PG 에 120 이 몰렸다

**고른 것: PG 계약 한도를 대수로 나눈다.** `payment.pg.merchant-concurrency-limit` 과 `payment.pg.instances` 를 적으면 인스턴스 상한이 `min(40, 계약 한도 ÷ 대수)` 가 된다. 둘 다 비우면 지금처럼 40 이다.

**어떻게 골랐나.** 1차 기준(#387 본문)은 "결과 모름이 1대 수준 이하이고 정상 때 거절 0 인 것 중 전역과 적응형이 둘 다 되면 적응형"이었고 규칙대로면 적응형이었다. 그런데 기준에 성공 건수가 없었다. 적응형의 성공이 전역의 절반인 것을 보고 기준을 바꾸면 사후 변경이라 1차로는 정하지 않았다. 성공 건수를 넣은 2차 기준을 재측정 전에 이슈 댓글로 적었다. **자기 실패 모드까지 포함한 가장 나쁜 경우의 성공**이 큰 것을 고른다.

| 선택지 | 가장 나쁜 경우 | 그때 성공 |
|---|---|---:|
| **대수로 나눔** | 한 대가 빠져 합이 40 | **400** |
| Redis 전역 한도 | Redis 장애. 닫히면 결제 전부 거절, 열리면 결과 모름 252 | 0 |
| 적응형 Gradient2 | 자기 자신 | 288~291 |

**대가.** 대수가 바뀌면 설정도 같이 바꿔야 한다. 한 대가 빠진 동안은 합이 계약 한도보다 작아 덜 판다(400 대 600). 대신 이 실패는 결과 모름을 만들지 않는다. 전역 한도는 정확하지만 결제 경로에 Redis 라는 단일 장애점을 들인다.

**다시 볼 조건.** 오토스케일로 대수가 수시로 바뀌면 설정으로 맞출 수 없다. 그때는 대수를 서비스 디스커버리에서 읽거나 적응형을 PG 느림과 혼잡을 가르는 신호(PG 의 한도 초과 응답)로 다시 잰다.

## 2026-09-29 가상 스레드를 기본으로 켜지 않는 이유

위 절은 "켜도 되는 선택지"로 두고 기본값으로 켜지 않았지만 이유를 적지 않았다. 적는다.

- **이득이 작다.** 상한 40과 함께 켜도 무관한 조회 p95는 11ms에서 9.6ms로 1.4ms 줄었다. 기다림을 정하는 것은 상한이다.
- **문제를 풀지 않는다.** 가상 스레드는 워커라는 대기 줄 하나를 없애고 기다림을 커넥션 풀과 PG로 옮긴다(상한 없이 켜면 PG 동시 승인 174, Hikari 대기 23). 이 ADR이 다루는 "느린 PG를 기다리는 동안 공유 자원이 붙잡힌다"는 문제는 상한이 푼다.
- **Java 21의 고정(pinning) 위험.** `synchronized` 안에서 막힌 가상 스레드가 캐리어 스레드를 모두 붙잡아 교착에 이른 사례가 있다(Netflix, "Java 21 Virtual Threads, Dude, Where's My Lock?", 2024). 위 측정의 결제 · 조회 경로에서는 고정 경고가 0이었지만 다른 라이브러리와 `ThreadLocal`을 쓰는 경로는 재지 않았다.

**다시 볼 조건.** 상한이 있는데도 톰캣 워커(100)가 먼저 차는 것이 측정될 때 켠다(PG 밖의 느린 호출이 늘어나는 경우). JEP 491(`synchronized` 고정 제거)이 들어간 Java 25 LTS로 올리면 세 번째 이유가 사라지므로 그때는 이 조건만 본다. 켜더라도 PG 동시 호출 상한과 진행 중 조회 상한은 남긴다.

## 2026-09-28 승인 재전송이 브라운아웃에 얹는 부하 (#398)

PR #396(213b46c)이 승인 타임아웃 재전송(`payment.pg.approve-resend-max-attempts`, 기본 1)을 추가했다. 재전송도 이 문서의 상한(40)과 승인 서킷을 그대로 거치므로, 느리거나 일부 응답을 잃는 PG 브라운아웃에서 재전송이 PG 부하와 사용자 체감 지연에 어떤 대가를 내는지 쟀다. 판정 기준은 측정 전에 [이슈 #398](https://github.com/dj258255/BE-commerce/issues/398)에 적었다.

조건 넷을 순서대로 돌렸다(도착률 30/s · 60초 · 워밍업 15초 · 상한 40). **느림**은 기존 하네스(`tools/run-pg-brownout.sh`)의 지연 주입을 그대로 썼다(지연 5초 · read-timeout 2초, 첫 시도가 항상 타임아웃). `TossPgClient`엔 지연을 주입할 수 없어 Toxiproxy보다 `FakePgClient` 지연 주입이 결정적이라는 이 문서의 기존 결정을 그대로 따랐다. **손실**은 `FakePgClient`에 새로 더한 `payment.fake-pg.approve-timeout-lost-rate`를 썼다(승인마다 독립적으로 15% 확률로 PG에서 완전히 사라짐, PG 측 기록 없음). 기존 `timeout-lost-prefix`는 특정 키 접두어에만 걸려 k6가 무작위로 만드는 `paymentKey`로는 이 축을 못 재서, 접두어 대신 모든 승인 호출에 독립적으로 걸리는 확률 주입을 새로 추가했다.

| 조건 | PG 로 나간 승인 호출 | 재전송 시도 · 성공 | 상한 거절 | 최종 실패(ABORTED) | 확정(DONE) | confirm p95 | 미확정 0 까지 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 재전송 0 · 느림 | 1,342 | — | 610 | 610(31.3%) | 1,342 | 2.02s | 167s |
| 재전송 1 · 느림 | 1,514(+12.8%) | 659 · 0 | 1,097 | 1,097(56.2%) | 855 | 4.07s(+101%) | 100s |
| 재전송 0 · 손실 | 1,952 | — | 0 | 295(15.1%) | 1,657 | 24.9ms | 104s |
| 재전송 1 · 손실 | 2,234(+14.4%) | 283 · 236(83%) | 0 | 47(2.4%) | 1,904 | 72.2ms(+190%) | 103s |

**느림 조건의 가설이 틀렸다.** 측정 전엔 "PG 가 매번 같은 지연이라 재전송도 다시 타임아웃되니 최종 실패 비율은 그대로"라고 적었다(판정 기준 2, 2%p 이내 차이). 실측은 정반대다. 재전송이 최종 실패를 31.3%에서 56.2%로 **24.9%p 늘렸다.** 원인은 재전송 자체가 아니라 상한(40)과의 상호작용이다. 이 조건은 요구 동시성이 도착률 30/s × read-timeout 2초 = 60 으로 상한 40 을 이미 넘겨 포화 상태다. 재전송은 같은 결제가 PG 슬롯(세마포어)을 두 번, 도합 약 4초 가까이 쥐게 만들어 처리율을 사실상 절반으로 떨어뜨리고, 그만큼 뒤에 도착한 요청이 상한에 걸려 확정 실패(`concurrency_limit`)로 밀려난다. **포화 상태에서는 재전송이 PG 손실을 흡수하지 못하고 상한 거절만 늘린다.**

**손실 조건은 가설대로였다.** 재전송을 켜면 최종 실패가 15.1%에서 2.4%로 **12.7%p 줄었다**(판정 기준 3, 5%p 이상). 재전송 283건 중 236건(83%)이 성공해 손실률 15%에 가까운 비율을 그대로 회수했다. 이 조건은 지연이 없어 상한이 전혀 물지 않았다(상한 거절 0건, 양쪽 다).

**판정 기준 1(PG 동시 호출 최대가 20% 이상 늘면 유의미)은 쓸 수 없었다.** 느림 조건은 재전송 유무와 무관하게 게이지 표본 최대가 상한 그대로 40 으로 찍혀 상한에 가려 차이가 안 보였다. 손실 조건은 지연이 없어 승인 하나가 1ms 안팎으로 끝나 1 초 표본 게이지가 아예 못 잡았다(양쪽 다 0). 대신 **PG 로 실제로 나간 승인 호출 총수**(새로 더한 `fake.pg.approve.calls`)로 부하를 본다. 느림 +12.8%, 손실 +14.4% 로 둘 다 20% 에는 못 미쳤다. 재전송 최대 1회 설정에서 PG 콜 자체의 증가폭은 크지 않다. 부하는 콜 수가 아니라 **콜이 슬롯을 쥐는 시간**에서 났다(느림 조건).

**판정 기준 4(confirm p95 가 20% 이상 늘면 유의미)는 둘 다 확인됐다.** 느림은 +101%(2.02s → 4.07s), 손실은 +190%(24.9ms → 72.2ms)다. 손실 조건은 상대 증가율은 크지만 절대값은 25ms → 72ms 로 작다. 상한이 안 걸리는 구간에서는 재전송의 지연 비용이 체감상 크지 않다.

**정리.** 재전송은 손실형 브라운아웃에서는 확실히 이득이다(최종 실패 12.7%p 감소, PG 콜 +14.4%). 느림형 브라운아웃, 특히 상한이 이미 포화된 구간에서는 손해다(최종 실패 24.9%p 증가). 이 상한(40)은 "정상에서 안 물고 브라운아웃에서 워커를 지킨다"는 근거로 골랐지 재전송을 겨냥한 값이 아니다(위 "값을 어떻게 골랐나"). 재전송 최대 횟수(`payment.pg.approve-resend-max-attempts`)는 상한이 이미 포화된 브라운아웃에서는 낮추거나 끄는 쪽이 나을 수 있다는 근거가 이번에 생겼다. 지금 기본값 1 을 그대로 켠 채로도 안전하다고 보는 근거는, 정상 구간(요구 동시성이 상한 아래)에서는 애초에 타임아웃이 거의 안 나 재전송이 거의 걸리지 않고, 상한이 포화되는 조건 자체는 이미 ADR-022 3 단계 · 4 단계가 다룬 별도의 대가(미확정 폭증, 조회 폭주)를 내는 구간이기 때문이다. 이 측정은 그 대가에 하나를 더 보탰다는 뜻이지, 상한 40 자체를 다시 고를 근거는 아니다.

**다시 볼 조건.** 실 PG 응답시간 분포가 잡히면 이 조건의 재전송이 실제로 상한을 포화시키는 지연 구간인지 다시 잰다. 손실률이 15% 보다 크거나 작으면 재전송 이득도 그 비율로 다시 스케일한다.

## 2026-09-28 재전송에 상한 여유 기반 예산을 둔다 (#404)

위 절의 결론대로 느림 조건(상한 포화)에서는 재전송이 최종 실패를 31.3%→56.2%로 늘렸고, 손실 조건(상한 안 물림)에서는 15.1%→2.4%로 줄였다. 재전송 시점에 상한(`payment.pg.max-concurrent-calls`, 기본 40) 중 빈 자리가 일정 수 미만이면 재전송하지 않고 기존 UNKNOWN을 유지하는 예산(`payment.pg.approve-resend-min-headroom`)을 두면 두 조건을 가려낼 수 있는지 잰다. 판정 기준은 측정 전에 [이슈 #404](https://github.com/dj258255/BE-commerce/issues/404)에 적었다.

**설계 선택: 토큰 버킷 대 상한 여유.** 토큰 버킷(최근 승인 대비 재전송 비율)은 최근 승인 처리율을 시간창으로 집계하는 별도 상태가 필요하고, 그 집계 자체가 동시 접근의 새 경합 지점이 된다. 상한 여유는 상한이 이미 들고 있는 `Semaphore.availablePermits()`를 그대로 읽는다. 별도 상태가 없고 보호 대상(동시 호출 슬롯)과 직접 연결된다는 점에서 이쪽을 골랐다. 기본값 4는 상한 40의 10%로, 후보였던 토큰 버킷의 "최근 승인 대비 10%"와 자릿수를 맞췄다.

기존 넷(R0/R1 × SLOW/LOSS)을 같은 실행 안에서 다시 재고, 예산 4를 준 RB-SLOW·RB-LOSS 둘을 더해 여섯 조건을 돌렸다(도착률 30/s · 60초 · 워밍업 15초 · 상한 40, 손실률 15%).

|---|---:|---:|---:|---:|---:|---:|---:|
| R0-SLOW(재전송 0) | 1,336 | — | — | 616 | 616(31.56%) | 2.04s | 171s |
| R1-SLOW(재전송 1) | 1,517 | 643 · 0 | 0 | 1,078 | 1,078(55.23%) | 4.08s | 101s |

다시 잰 R0/R1 넷은 지난 절의 값과 오차범위 안에서 재현됐다(최대 차이 R1-SLOW 0.97%p, 나머지는 1%p 미만). 이 정도가 이 하네스의 실행 간 잡음 크기다.

**판정 기준 1(RB-SLOW가 R1-SLOW보다 낮고 R0-SLOW와 10%p 이내)이 맞았다.** RB-SLOW의 최종 실패는 31.40%로 R1-SLOW(55.23%)보다 훨씬 낮고 R0-SLOW(31.56%)와 0.16%p 차이다. 실행 간 잡음(위 1%p 미만)보다도 작다. confirm p95도 2.09s로 R0-SLOW(2.04s)에 가깝고 R1-SLOW(4.08s)와는 멀다. 미확정 0까지도 168s로 R0-SLOW(171s)와 가깝다. 예산이 느림 조건에서 재전송을 사실상 무력화해 재전송 0과 같은 모양을 만든다는 가설이 그대로 맞았다.

**판정 기준 2(RB-LOSS가 R1-LOSS와 5%p 이내)도 맞았다.** RB-LOSS의 최종 실패는 2.82%로 R1-LOSS(1.90%)와 0.92%p 차이다. 손실 조건은 애초에 상한이 안 걸려(양쪽 다 상한 거절 0) 빈 자리가 항상 예산 이상이므로 예산이 켜져 있어도 걸릴 일이 없다.

**판정 기준 3(RB-SLOW의 skipped 는 0보다 커야 하고, RB-LOSS의 skipped 는 0에 가까워야 한다)도 맞았다.** RB-SLOW는 1,176건이 예산으로 걸러졌다(재전송 시도 163건보다도 많다 — 대부분의 재전송 시도 자체가 예산에 막혔다는 뜻이다). RB-LOSS는 0건으로, 예산 조건이 손실 구간에서는 전혀 개입하지 않았다는 것이 수치로 확인된다. 이 카운터가 없었다면 RB-SLOW의 결과가 "예산이 실제로 작동해서" 낮은 것인지 "우연히 재전송이 덜 나가서" 낮은 것인지 구분할 수 없었을 것이다.

**정리.** 상한 여유 기반 재전송 예산은 가설대로 작동했다. 느림 조건(상한 포화)에서는 빈 자리 부족으로 재전송 시도 대부분(163/1,502 ≈ 재전송률 자체가 R1-SLOW의 643/1,517보다 훨씬 낮다)을 막아 최종 실패를 재전송 0 수준으로 되돌렸다. 손실 조건(상한 여유)에서는 예산이 한 번도 걸리지 않아 재전송 1과 동일하게 동작했다. 기본값은 0(예산 없음, 이전 동작 그대로)으로 두고 운영에서 느림형 브라운아웃이 반복되면 `payment.pg.approve-resend-min-headroom`을 켜는 안내로 남긴다.

**다시 볼 조건.** 예산 4(상한의 10%)는 이번 상한(40)에 맞춘 값이다. 상한을 다시 고르면(위 "값을 어떻게 골랐나") 예산도 그 비율로 다시 계산해야 한다. 여러 대(#387)에서는 인스턴스별 상한이 나뉘므로 예산도 인스턴스별 상한 기준으로 해석된다는 점은 아직 따로 재지 않았다.

## 2026-09-28 데드라인 전파: 이미 떠난 고객이 PG 슬롯을 얼마나 차지하는가 (#409)

지금까지 절은 전부 PG 슬롯(위 상한)을 **어떻게 나눌지**를 다뤘다. 이 절은 그 슬롯의 **수요 자체**를 줄일 수 있는지를 본다. 클라이언트가 이미 타임아웃해 화면을 떠났거나 다른 수단으로 재시도했어도, 서버는 그것을 모른 채 PG 승인 호출을 끝까지 붙잡고 있다(Google SRE 데드라인 전파가 다루는 바로 그 낭비). 요청에 `X-Client-Deadline-Ms`(절대 epoch ms) 헤더가 있고 PG를 부르기 <b>직전</b>(상한 세마포어를 잡기 전, `PaymentService.pgApprove`) 이미 지났으면 PG 콜 자체를 생략하고 바로 확정 실패로 돌린다. `payment.deadline-check.enabled`(기본 true)로 끄면 헤더를 받아도 무시한다 — 같은 코드로 "넣기 전" 대조군을 잰다.

**설계 선택.** 확인 지점을 `ResilientPgClient`(세마포어를 직접 쥐는 곳) 대신 `PaymentService.pgApprove`(그 호출 바로 앞)로 잡았다. `ResilientPgClient`에서 확인하려면 `PgApproveCommand`에 데드라인 필드를 얹어야 하는데, 이 커맨드는 `TossPgClient`·`KakaoPayPgClient`·`FakePgClient` 등 PG 어댑터 인터페이스가 공유해 변경 범위가 커진다. `PaymentService`에서 끊으면 PG 어댑터 계층은 전혀 건드리지 않고, 상한 세마포어(`ResilientPgClient.pgCallLimit`) 진입 자체를 막아 "PG에 닿지 않은 것이 보장된다"는 이 클래스의 기존 규칙(상한 초과·서킷 오픈과 동일)을 그대로 탄다. 헤더는 **절대** 데드라인(epoch ms)으로 뒀다 — 상대 타임아웃(요청 보낼 때부터 남은 ms)은 재시도·홉을 거치며 매번 다시 채워질 수 있어 "고객이 이미 포기했다"는 신호 자체가 사라진다.

**판정 기준은 측정 전에 [이슈 #409](https://github.com/dj258255/BE-commerce/issues/409)에 적었다.** 느린 PG(지연 5000ms · read-timeout 2000ms · 상한 40, 이 ADR 운영값) · 도착률 30/s · 60초에서 요청의 30%에 이미 지난 데드라인(-1000ms, `late-` 접두어)을, 70%에 넉넉한 미래 데드라인(+30000ms, `normal-` 접두어)을 실어 OFF(대조군) 대 ON(넣은 뒤)을 비교했다.

| 지표 | OFF(끔) | ON(켬) | 비고 |
|---|---:|---:|---|
| PG로 실제 나간 승인 호출(`fake_pg_approve_calls_total`, 재전송 포함) | 1,517 | 1,391 | -8.3% |
| 상한 거절(`concurrency_limit`) | 1,094 | 563 | -48.5% |
| 데드라인 생략(`deadline_skipped`, late 요청 수와 비교) | (카운터 없음) | 594 | late 594건과 정확히 일치 |
| late 몫 최종 상태 | ABORTED 322(55.4%) · UNKNOWN 259(44.6%) | ABORTED 594(100%) · UNKNOWN 0 | ON은 전부 데드라인 생략 경로 |
| normal 몫 최종 상태 | ABORTED 772(56.3%) · UNKNOWN 599(43.7%) | ABORTED 563(41.5%) · UNKNOWN 795(58.5%) | normal이 PG에 도달하는 비율 +15pp |

DONE(성공)은 양쪽 다 0건이다 — 이 조건(지연 5000ms > read-timeout 2000ms)은 승인이 항상 타임아웃하도록 고른 것이라 PG 승인 자체의 성공률이 아니라 **누가 PG 슬롯을 쓰는지**를 보는 실험이다. 원자료: [`performance/raw/20260928-deadline-load/`](../performance/raw/20260928-deadline-load/)

**가설 판정 — 다섯 개 중 셋은 맞고 둘은 틀렸다.**

1. **틀렸다.** "PG 호출 수가 late 몫만큼(약 30%) 준다"고 예상했지만 실제로는 -8.3%였다. 이 구간은 상한(40)이 이미 포화돼 있어(pg inflight 평균 37~38, 거의 항상 40 근처) **총 호출량 자체가 상한 × (측정 시간 / PG 지연)으로 이미 상한에 묶여 있다.** late 요청이 슬롯을 놓아줘도 그 자리를 normal 요청이 즉시 채우므로, 총 호출 수는 크게 안 줄고 **누가 그 호출을 쓰는지만 바뀐다.** 상한이 안 걸리는(포화되지 않은) 구간이었다면 이 가설이 맞았을 것이다.
2. **절반만 맞았다.** ON에서 late가 100% ABORTED(데드라인 생략)라는 예상은 맞았지만, OFF에서 late가 "대부분 UNKNOWN"이라는 예상은 틀렸다 — 실제로는 ABORTED 55.4% · UNKNOWN 44.6%로 거의 반반이었다. OFF에서는 late 요청도 다른 요청과 똑같이 상한 경쟁에 들어가, 그중 절반 이상이 상한 거절(ABORTED)로 먼저 걸러졌기 때문이다. late·normal이 OFF에서 거의 같은 비율(55.4% 대 56.3%)로 갈린 것 자체가 "OFF에서는 데드라인이 아무 차이를 안 만든다"는 것을 보여주는 증거이기도 하다.
3. **맞았다.** OFF에는 `deadline_skipped` 카운터 자체가 없고(한 번도 증가 안 함), ON에서는 594로 이번 실행의 late 요청 수(594)와 정확히 일치한다. #408에서 매진 판정이 한 번도 서지 않은 것을 카운터로 확인한 것과 같은 방식 — "조건이 실제로 섰다"는 증거를 수치로 남긴다.
4. **맞았다.** normal 몫이 PG에 실제로 도달해 확정(UNKNOWN, 이 조건에서는 타임아웃이 곧 확정)된 비율이 43.7%(OFF) → 58.5%(ON)로 늘었다(건수로는 599 → 795, +32.7%). late 요청이 비운 슬롯을 normal 요청이 대신 썼다는 이 실험의 핵심 주장이 직접 수치로 드러난다.
5. **맞았다, 예상보다 크게.** 상한 거절이 1,094 → 563으로 48.5% 줄었다. "비슷하거나 준다"는 느슨한 예상보다 훨씬 큰 폭으로 줄었다 — late 요청이 상한 경쟁 자체에서 빠지므로 상한 거절이라는 자원(세마포어 진입 시도)을 두고 다투는 인구 자체가 줄어든 결과다.

**정리.** 이 기능의 값은 "PG 호출을 덜 하게 한다"가 아니라 **"상한이 이미 포화된 상황에서, 어차피 나갈 PG 호출의 수혜자를 이미 떠난 고객에서 아직 기다리는 고객으로 옮긴다"**는 데 있다. 상한이 포화되지 않은 정상 구간에서는 late 요청 자체가 드물어(정상 p99 안에서 클라이언트가 포기할 일이 거의 없다) 이 기능이 거의 관여하지 않는다 — 브라운아웃처럼 상한이 포화되는 구간에서만 값이 난다. 기본값은 true(켬)로 뒀다: 끄는 대가(옛 동작 재현)만 있고 켜는 대가는 이번 측정에서 못 찾았다.

**일부러 하지 않은 것.** late 비율(30%)·데드라인 오프셋(-1000ms)의 민감도는 스캔하지 않았다. 실 클라이언트(브라우저·앱)가 실제로 어떤 값을 보낼지(리액트 fetch AbortController의 흔한 타임아웃 3~10초)는 프런트 쪽 작업이라 이번 범위 밖이다. 상한이 포화되지 않은 정상 구간에서의 효과는 이번엔 재지 않았다 — 위 정리대로 거의 없을 것으로 예상하지만 확인하지 않았다.

재현: `bash tools/run-deadline-load.sh`(약 3분, 두 조건). 원자료: [`performance/raw/20260928-deadline-load/`](../performance/raw/20260928-deadline-load/)

## 2026-09-29 데드라인 헤더를 남은 시간으로 바꾼다 (#409 후속)

**바꾼 이유.** 위 절은 `X-Client-Deadline-Ms`(클라이언트 시계의 절대 epoch ms)를 받았다. 이러면 클라이언트 시계가 서버보다 빠를 때 아직 기다리는 고객의 결제도 지난 것으로 판정한다. gRPC의 `grpc-timeout`, Envoy의 `x-envoy-expected-rq-timeout-ms`처럼 **남은 시간**을 넘기고 받는 쪽이 자기 시계로 마감을 계산하는 것이 표준 방식이다. 위 절에서 상대 시간을 기각한 근거("재시도 · 홉을 거치며 다시 채워질 수 있다")는 남은 시간을 매 홉에서 줄여 넘기면 생기지 않는 문제라 약했다.

**결정.** `X-Request-Timeout-Ms`(남은 밀리초)를 받는다. `CheckoutController`가 요청을 받은 순간의 서버 시계에 남은 시간을 더해 마감 시각을 만들고 그 뒤는 그대로다(`PaymentService.pgApprove`가 `now > 마감`이면 PG를 부르지 않는다). 0 이하는 이미 지난 것으로 보고 받은 순간보다 1ms 앞을 마감으로 둔다. 멱등 처리보다 앞에서 계산해 그 대기 시간도 셈에 넣는다. 남은 대가는 요청이 서버에 닿기까지 걸린 네트워크 시간을 빼지 못해 그만큼 늦게 끊긴다는 것이다.

**다시 쟀다.** `tools/run-deadline-load.sh`의 k6가 떠난 몫(30%)에 남은 시간 0, 나머지에 30,000ms를 보낸다. 조건은 위 절과 같다(지연 5000ms · read-timeout 2000ms · 상한 40 · 30/s · 60초). 측정(09-29 08:28~08:32)은 같은 기계에서 다른 작업의 부하 스크립트(`run-d2-holdout.sh`)가 도는 동안 진행했다. 판정은 CPU 경합에 둔감한 건수로 했다.

| 상한 거절 | 609 | 169 (-72.2%) |

PG 호출은 8%대만 줄고(상한이 차 있어 총 호출이 상한에 묶인다) 줄어드는 것은 남은 결제가 상한에 막히는 일이다. 위 절 가설 2("OFF에서 떠난 몫은 대부분 UNKNOWN")는 예산이 켜진 이번 조건에서는 맞았다(69.9%).

**결제 화면도 헤더를 싣는다 (2026-09-30).** 위 측정은 k6만 헤더를 보냈다. 실제 결제 화면(`static/checkout.html`)은 헤더 없이 응답을 끝까지 기다렸고 서버는 확인을 건너뛰었다. 이제 화면이 승인 요청에 `X-Request-Timeout-Ms: 15000`(아래 09-30 측정 뒤 27000으로 고침)을 싣고 15초가 지나면 `AbortController`로 기다림을 멈춘다. 15초는 PG 읽기 타임아웃 5초 × (첫 시도 + 재전송 1회)에 여유 5초를 더한 값이다. 기다림을 멈춘 뒤에는 실패로 단정하지 않고 202(UNKNOWN)와 같이 주문 조회로 결과를 확인한다. 서버는 계속 처리 중일 수 있어 실패로 보여 주면 고객이 다시 눌러 이중 결제를 시도한다. 조회 결과가 `ABORTED`면 "결제가 진행되지 않았다"고 알린다.

로컬에서 두 경우를 확인했다. PG 지연 200ms에서는 요청 헤더에 15000이 실리고 결제가 끝났다. PG 지연 20초(read-timeout 25초)에서는 15.5초에 "응답이 늦어 결제 결과를 확인하고 있습니다"로 바뀌고 21.6초에 조회로 `DONE`을 받았다. 주문마다 결제 행은 하나였다. 남은 한계는 둘이다. 화면이 멈춘 뒤 서버가 PG를 이미 부르고 있으면 그 호출은 끝까지 간다(데드라인은 PG를 부르기 전에만 본다). 조회는 1.2초 간격 10번(약 12초)까지만 하고 그 안에 확정되지 않으면 주문내역에서 확인하라고 안내한다.

## 2026-09-30 화면과 똑같이 움직이는 고객으로 다시 쟀다: 데드라인은 한 번도 서지 않았다

**왜 다시 쟀나.** 위 두 측정의 k6는 요청의 30%에 남은 시간 0을 실었다. 실제 화면은 그런 값을 보내지 않는다. 브라우저로는 동작만 확인했을 뿐 화면 경로에서 데드라인이 서는지는 재지 않았다. `k6/checkout-screen.js`는 화면이 하는 일을 그대로 한다. 헤더에 15000을 싣고 15초에 응답을 끊고 202거나 끊었으면 1.2초 간격 10번 주문을 조회한다. 고객은 한 번만 시도한다. 요청의 2%에는 남은 시간 0을 실어(대조군 `ctrl-`) 데드라인 확인 자체가 작동하는지 함께 봤다.

**측정 전 예상.** 서버 안에서 PG를 부르기 전까지 쓰는 시간은 짧다. 커넥션 대기는 3초에서 끊고 상한은 기다리지 않고 거절한다. 그래서 (A) 운영 설정에서는 화면이 끊는 일도, 화면 고객의 데드라인 생략도 0이고 켬·끔 차이가 없다. (B) 서버 응답이 15초를 넘으면 화면은 끊지만 PG는 이미 불렸으므로 생략은 0이고 조회로 결과를 받는다. (C) 워커가 마르면 끊는 고객이 많아도 생략은 0이다. 서버는 헤더를 받은 순간부터 재므로 톰캣 대기열에서 쓴 시간이 빠진다.

세 예상이 모두 맞았다. 대조군은 켠 실행마다 전부 생략돼(카운터 = 대조군 수, 워밍업 포함) 0이 "확인이 안 돌았다"의 0이 아니다. 상한 거절은 식과 맞는다(A: 1 − 40 ÷ (50 × 5) = 84.0%, B: 1 − 40 ÷ (5 × 20) = 60.0%). C의 워커는 최대 100으로 말랐다.

**읽은 것.**
1. 운영 설정에서는 읽기 타임아웃과 재전송 예산이 응답을 10.1초 안으로 묶어 화면이 끊을 일이 없다. 화면 경로에서 데드라인 확인은 효과가 없다. 위 절의 "상한 거절 72% 감소"는 이미 지난 요청이 들어올 때의 값이다. 이 화면만 있는 지금 구조에서는 그런 요청이 생기지 않는다.
2. 워커가 마르면 고객의 절반 넘게 15초를 넘겨 기다렸지만 서버는 몰랐다. 대기열 시간을 세려면 프록시가 요청을 받은 시각을 헤더로 찍어 줘야 한다(`X-Request-Start` 방식). 지금은 프록시가 없어 하지 않았다.
3. **끊은 고객은 떠난 고객이 아니었다.** C에서 끊은 1,218명과 1,300명은 모두 조회로 결제 완료를 받았다. 화면은 응답을 끊은 뒤에도 조회로 결과를 기다린다. 만약 데드라인이 15초 기준으로 섰다면 이 결제들은 "진행되지 않았다"로 바뀌었다. 그래서 화면이 보내는 남은 시간을 **응답 대기 15초 + 조회 창 12초 = 27초**로 고쳤다(`CONFIRM_DEADLINE_MS`). 값이 커지면 생략은 늘 수 없으므로 위 결과는 그대로 유효하다. 브라우저에서 헤더 27000을 확인했다.
4. A8에서 202를 받은 472명과 480명은 전원 12초 조회 안에 결과를 받지 못했다. 이 측정은 기본 프로필이라 복구 배치가 꺼져 있었다(`worker` 프로필에서만 켠다). 켜져 있어도 배치는 60초 간격이고 첫 재시도는 1분 뒤라 조회 창보다 늦다. 브라운아웃 중 조회 요청마다 PG를 부르면 느린 PG에 부하를 더하므로 바꾸지 않았다. 화면은 "주문내역에서 확인해 주세요"로 안내한다.

**결정.** 서버의 데드라인 확인은 켠 채로 둔다. 비용은 비교 한 번이고 이미 지난 요청을 싣는 클라이언트(앱의 전체 예산 재시도, 앞단 서버를 거치는 호출)가 생기면 바로 작동한다. 다만 지금 결제 화면에 대해서는 효과를 주장하지 않는다.

## 2026-09-30 PG 읽기 타임아웃을 5초에서 60초로 바꾼다

**계기.** 토스페이먼츠 공식 문서는 "결제 처리와 관련된 API 의 Read Timeout 은 60초로 설정하면 돼요"라고 권한다. Stripe SDK 기본값도 80초다. 우리 5초는 이보다 12배 짧았고 설정 주석에 "어느 쪽이 싼지는 아직 안 쟀다"고 남아 있었다. 이 문서의 상한 · 거절 식 · 재전송 예산이 모두 5초 위에 서 있어 그대로 둘 수 없었다.

**다른 PG의 권장값**(2026-09-30 공개 문서 기준). 60초 이상을 권하는 곳이 셋이고 가장 짧은 나이스페이도 30초다. 5초는 어느 권장보다 짧았다.

| PG | 권장 | 근거 |
|---|---|---|
| 토스페이먼츠 | 읽기 60초 | [개발자센터: 타임아웃](https://docs.tosspayments.com/resources/glossary/timeout) "결제 처리와 관련된 API 의 Read Timeout 은 60초로 설정하면 돼요" |
| 포트원 | 읽기 최소 60초 | [REST API V2](https://developers.portone.io/api/rest-v2) "PG 및 결제 원천사의 응답 지연을 고려하여 최소 60초의 읽기 타임아웃 시간을 설정하도록 권장합니다" |
| Braintree(PayPal) | 60초 이상 | [Best Practices](https://developer.paypal.com/braintree/docs/reference/general/best-practices/php/) 60초보다 짧으면 결제는 됐는데 결과를 못 받을 수 있다(10초에 끊고 19초에 결제가 끝나는 예) |
| 나이스페이 | 연결 5초, 읽기 30초 | [매뉴얼: 개발 준비](https://github.com/nicepayments/nicepay-manual/blob/main/common/preparations.md) 타임아웃 정보. 읽기 타임아웃이 나면 망취소 |
| Stripe | SDK 기본 80초 | [stripe-node](https://github.com/stripe/stripe-node) 설정 기본값 80000ms |
| KG이니시스 · NHN KCP · 카카오페이 | 공개 문서에서 찾지 못함 | 카카오페이는 같은 이유(PG가 끊긴 호출을 계속 처리)로 60초에 맞췄다 |

**짧은 타임아웃을 권하는 쪽과 어떻게 맞춰지나.** Shopify는 [결제 시스템 글](https://shopify.engineering/building-resilient-payment-systems)에서 "연결 1초, 읽기 5초가 괜찮은 출발점"이라고 적는다. 다만 HTTP 호출과 DB 쿼리 전반의 출발점이고 "애플리케이션 상황에 달렸고 모니터링으로 정하라"는 단서가 붙는다. [AWS Builders' Library](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter)는 정하는 방법을 적는다. 허용할 가짜 타임아웃 비율(예: 0.1%)을 정하고 받는 쪽 지연의 그 백분위(p99.9)를 쓴다. 또 "타임아웃이나 실패가 부작용이 안 일어났다는 뜻은 아니다". 이 방법을 결제 승인에 대입하면 받는 쪽은 PG와 카드사라 꼬리가 수십 초까지 가고, 가짜 타임아웃은 결과 모름이라 비싸다. 같은 방법이 결제 승인에서는 긴 값을 내고 PG 권장값은 그 결과를 PG가 대신 계산해 준 것으로 본다. 자원 보호는 타임아웃에 맡기지 않는다. Shopify는 외부 서비스를 벌크헤드([Semian](https://github.com/Shopify/semian))로 막고 [JEP 444](https://openjdk.org/jeps/444)도 서비스에 대한 동시성 제한은 세마포어로 하라고 한다. 이 문서의 PG 동시 호출 상한 40이 그 역할이다. 그래서 호출마다 기준이 갈린다.

| 호출 | 타임아웃 | 자원 보호 |
|---|---|---|
| PG 승인 · 취소(부작용이 있고 받는 쪽 꼬리가 김) | PG 권장(60초), 같은 멱등키 재전송, 결과 모름은 복구 배치가 확정 | PG 동시 호출 상한 40 |
| 조회 · DB(부작용 없고 짧음) | 짧게(DB 커넥션 대기 3초) | 진행 중 조회 12개 |

한국 기술 블로그는 타임아웃 값을 공개하지 않고 끊긴 뒤의 처리를 강조한다. 토스는 [레거시 결제 개편](https://toss.tech/article/payments-legacy-5)에서 앞단이 승인 서버보다 먼저 끊겨 "승인은 됐는데 앞단은 실패"가 난 것을 승인 서버의 최대 처리 시간에 상위 타임아웃을 모두 맞춰 풀었다. [카카오페이](https://tech.kakaopay.com/post/msa-transaction/)는 타임아웃을 알 수 없는 에러로 보고 멱등성으로 같은 요청에 같은 답을 준다. 우리 화면 65초 ≥ 서버 60초, UNKNOWN과 같은 멱등키 재전송이 같은 원칙이다.

**다시 볼 조건.** AWS 방법대로라면 최종값은 실제 PG 응답 분포의 p99.9로 정해야 한다. 지금은 실측이 없어 PG 권장값을 쓴다(서킷브레이커의 느린 호출 기준을 "실제 분포가 없어" 두지 않은 것과 같은 이유). 운영 지표에서 PG 승인 p99.9가 권장값보다 크게 짧게 나오면(예: 20초 안) 나이스페이 권장(30초) 쪽으로 줄이는 것을 다시 잰다. 줄일 때도 결제 화면의 조회 창은 서버 타임아웃 이상으로 함께 맞춘다.

**가짜 PG를 먼저 고쳤다.** 지금까지 가짜 PG는 우리가 끊으면 PG의 처리도 같이 끝났다. 실 PG는 끊긴 호출도 끝까지 처리한다. 이걸 흉내 내지 않으면 짧은 타임아웃이 PG의 부하까지 줄이는 것처럼 보인다. 스위치 셋을 더했다(기본은 모두 끔, `FakePgClientPgSideProcessingTest`).
- `pg-side-processing`: 끊어도 PG는 지연만큼 처리를 계속한다. 그동안 같은 멱등키는 토스처럼 409 `IDEMPOTENT_REQUEST_PROCESSING`(우리 쪽 결과 모름), 끝난 뒤에는 처음 결과를 그대로 돌려준다
- `contract-concurrency`: PG 쪽 동시 처리 한도. 끊긴 호출도 센다. 넘으면 처리 전 확정 거절(가정. 토스는 한도 값을 공개하지 않는다)
- `approve-slow-rate` · `approve-slow-latency-ms`: 평소의 느린 꼬리

**측정 전 예상과 판정 기준**(착수 전에 작업 기록에 적음). 상한 40, 화면과 같은 k6(1.2초 × 10번 조회), 복구 배치 켬, 끝난 뒤 미확정이 0이 될 때까지 기다린 DB를 센다.
- T 평소 꼬리(15/s, 90%는 1초 · 10%는 10초, 계약 60): 5초는 느린 10%가 결과 모름, 60초는 0
- B 브라운아웃(50/s, 모든 승인 20초, 계약 60): 5초는 PG가 받는 승인이 초당 약 3건(60 ÷ 20초)으로 60초(초당 2건)의 1.5배
- Bnc: B에서 계약 한도를 뺀 지금까지의 가정. 5초가 60초의 4배, PG 쪽 동시 처리 약 160
- 판정: B에서 5초의 최종 판매가 60초의 2배를 넘지 못하고 T에서 5초가 결제의 5% 이상을 결과 모름으로 만들면 60초로 바꾼다

**바꾼 것.**
- `payment.toss.read-timeout` · `payment.kakaopay.read-timeout` 60s. 카카오페이는 공식 권장값을 찾지 못해 같은 이유로 맞췄다. 가짜 PG 기본값도 60000ms로 맞췄다
- 결제 화면은 응답을 15초만 붙잡고 기다린 뒤 "확인 중"을 띄우고 2초 간격 25번(50초) 조회한다. 조회 창이 서버의 최대 처리 시간(60초 + 여유 5초)을 덮게 했다. 토스가 레거시 개편에서 "승인 서버의 최대 처리 시간을 계산하고, 모든 상위 서버의 타임아웃을 이에 맞추어 재설정"한 것과 같은 원칙이다. 데드라인 헤더는 15 + 50 = 65초다. 브라우저에서 헤더 65000을 확인했고, PG 지연 40초에서 15.5초에 "확인 중"으로 바뀐 뒤 41.6초에 조회로 결제 확정을 받았다(예전 화면은 27초에 "주문내역에서 확인"으로 끝났다)
- 승인이 요청 제한(HTTP 429, `FORBIDDEN_CONSECUTIVE_REQUEST`)에 막히면 처리 전이므로 확정 실패로 돌린다. 이전에는 모르는 코드라 결과 모름이 되어 복구 배치가 없는 결제를 헛조회했다. 취소는 결국 나가야 하므로 지금처럼 재시도로 둔다

**남은 것.**
- PG가 60초를 넘겨 멈추는 경우는 재지 않았다. 60초는 자리를 60초 쥐므로 식으로는 거절이 1 − 40 ÷ (50 × 60) = 98.7%다
- 계약 한도를 동시 처리 수로 모델링했다. 실 PG는 한도를 공개하지 않고 요청 비율로 거는 것으로 보인다
- 첫 Bnc-5s 실행은 측정 스크립트가 복구 대기 중에 죽어 버렸다(`awk ... exit`가 `curl`을 SIGPIPE로 끝내 `pipefail` + `set -e`에 걸림). `run-pg-brownout.sh`를 고치고 그 조건만 다시 쟀다

## 2026-09-28 hedged request: 꼬리 지연 중복 요청 (26절②, Google "The Tail at Scale", #415)

지금까지 절은 전부 승인 <b>하나</b>가 어떻게 흘러가는지를 다뤘다. 이 절은 다른 접근을 본다 — PG 응답 지연이 대부분 빠르지만 드물게 아주 느린 꼬리가 섞여 있을 때, 일정 시간(hedge delay) 안에 안 끝나면 <b>같은 요청을 하나 더 보내</b> 먼저 끝나는 쪽을 쓰면 꼬리(p99)가 줄어드는가, 그 대가(PG 호출 증가)는 얼마인가.

`MultiInstancePgLimitExperimentTest`(#387, 위 "여러 대일 때 상한을 어떻게 나누나" 절)와 같은 방법론 — 로컬 `HttpServer` PG 스텁(실 HTTP, 가상 스레드) + 실 `HttpClient` — 을 그대로 썼다. hedging은 그 테스트의 `GlobalLimitedPgClient`·`AdaptiveLimitedPgClient`처럼 <b>테스트 전용</b> 데코레이터(`HedgedPgClient`)로만 구현했다 — 프로덕션 `ResilientPgClient`는 건드리지 않는다. 26·27절 트레이드오프 실험은 결정된 기능이 아니라 비교 근거를 남기는 것이 목적이다.

**판정 기준은 측정 전에 [이슈 #415](https://github.com/dj258255/BE-commerce/issues/415)에 적었다.** PG 스텁 지연은 요청마다 독립적으로 95% 50ms(빠름)·5% 2000ms(꼬리)를 뽑는다. hedge delay 100ms(빠른 쪽보다 살짝 위, 느린 쪽보다 한참 아래). 요청 300건 · 동시성 30, 3회 실행.

| 지표 | NOHEDGE(1회차/2회차/3회차) | HEDGE(1회차/2회차/3회차) |
|---|---:|---:|
| p50 | 62 / 61 / 60ms | 57 / 57 / 53ms |
| p95 | 2003 / 143 / 147ms | 65 / 64 / 156ms |
| p99 | 2011 / 2012 / 2054ms | 171 / 170 / 166ms |
| PG 호출 수(300건 기준) | 300 / 300 / 300 | 313 / 306 / 320 |
| 호출 증가율 | 0% | 4.3% / 2.0% / 6.7% |
| hedge 발동 | — | 13 / 6 / 20 |
| hedge 승자(원본/중복) | — | 3·10 / 0·6 / 3·17 |

**가설 판정 — 넷 다 맞았다.**

1. **맞았다, 예상보다 크게.** p99가 2011~2054ms → 166~171ms로 3회 모두 약 92% 줄었다. 회차 간 편차가 거의 없어(±0.1%) 이 결과는 안정적이다.
2. **맞았다.** 호출 증가율이 2.0~6.7%로 꼬리 비율(5%) 근처에 머물렀다. 회차 간 편차는 있지만(300건 표본에서 이항분포 5%의 표준편차가 약 1.3%p라 2~6.7%는 정상 범위) 몇 배씩 늘지는 않았다.
3. **맞았다.** hedge 발동 건수(6~20)가 0보다 컸고(조건이 실제로 섰다는 증거), 300건의 2~6.7%로 꼬리 비율(5%, 기대값 15건)과 같은 자리수다.
4. **맞았다.** 발동된 경우 중 다수(10/13, 6/6, 17/20 — 세 회차 모두 과반)는 hedge(두 번째 시도)가 이겼다. 원 요청이 이미 느린 쪽(2000ms)으로 확정된 뒤 hedge를 보내므로, hedge가 정상 지연(50ms)으로 먼저 끝날 확률이 높다는 예상과 맞는다.

**부수 발견: NOHEDGE의 p95가 회차마다 크게 흔들렸다(2003 대 143 대 147ms).** 표본 300건·꼬리율 5%에서 p95 인덱스(285번째 값)가 하필 빠름/느림의 경계에 걸린다 — 그 회차에 꼬리가 15건보다 조금 많이 뽑히면 285번째 값도 꼬리(2000ms대)가 되고, 조금 적게 뽑히면 빠름(100ms대)이 된다. **이 파라미터화(꼬리율 5%, 표본 300)에서는 p95보다 p99가 더 안정적인 지표다** — p99 인덱스(297번째)는 항상 꼬리 쪽에 걸려 회차 간 흔들림이 훨씬 작았다(2011~2054ms, 2%p 이내).

**멱등성 — 확인 못 함, 문서화만 함.** hedge는 같은 커맨드(같은 Idempotency-Key)를 <b>동시에</b> 두 번 보낸다. 기존 재전송(#395/#402)은 <b>순차적</b>(첫 시도가 끝난 뒤)이고 토스 문서는 그 경우("타임아웃 뒤 같은 키로 재전송")의 안전성만 밝힌다. 동시(레이스) 요청을 PG가 내부적으로 어떻게 직렬화·중복 제거하는지는 PG 구현에 달려 있고, 이번 로컬 HTTP 스텁은 매 요청을 그대로 처리할 뿐 멱등키 중복 제거 자체를 흉내 내지 않아 이 실험은 그 질문에 답하지 못한다. **hedging을 실제로 켜려면 그 전에 토스(또는 쓰는 PG)에 동시 동일 키 요청의 계약을 확인해야 한다** — 확인 전까지는 이 실험은 "클라이언트 쪽 지연·호출 수 트레이드오프가 이론상 성립한다"는 근거일 뿐, "켜도 안전하다"는 근거가 아니다.

**일부러 하지 않은 것.** hedge delay(100ms)·꼬리 비율(5%)·꼬리 지연(2000ms)의 민감도는 스캔하지 않았다. 진 쪽 요청을 실제로 취소(연결 종료)하는 것은 구현하지 않았다 — 백그라운드에서 계속 돌게 두므로 PG 쪽 부하 감소 효과는 이 수치보다 낙관적이다. 위 멱등성 절대로 실제 PG 계약 확인, 프로덕션 배선은 범위 밖이다.

재현: `./gradlew -p commerce experimentTest --tests '*HedgedRequest*'`(약 5초 × 3회, Docker 불필요).

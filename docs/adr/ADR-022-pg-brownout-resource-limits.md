# ADR-022. 느린 PG 앞에서 무엇을 먼저 포기할 것인가

- 상태: **미결 (실험 전)**. 대안과 재는 방법까지 정했고, 수치가 나오기 전에는 고르지 않는다.
- 날짜: 2026-09-18
- 관련: [ADR-007](ADR-007-checkout-transaction-boundary.md), [ADR-020](ADR-020-multi-pg-routing-off-by-default.md), `ResilientPgClient`, `TossPgClient`

## 맥락

ADR-007에서 체크아웃을 3단계 사가로 옮겼다. PG 승인이 트랜잭션 밖으로 나가서 **DB 커넥션은 더 이상 PG 응답까지 묶이지 않는다.** 거기까지는 맞다.

그런데 그 ADR 마지막에 이렇게 적어 뒀다.

> **아직 안 잰 것**: 필요한 커넥션 수는 대략 `초당 결제 요청 × PG 응답 시간`이다. PG 지연을 주입한 부하로 풀 점유를 재기 전까지는 "여유 있다"고 쓰지 않는다.

아직 안 쟀다. 그리고 재려고 설정을 다시 보니, 사가가 푼 것은 **DB 커넥션 하나**였다.

| 자원 | 설정 | PG가 느려질 때 |
|---|---|---|
| Hikari 커넥션 | `maximum-pool-size: 20` | 사가 이후 PG 응답과 무관해졌다 |
| 톰캣 워커 스레드 | `threads.max: 100` | **여전히 PG 응답까지 묶인다** |
| PG 동시 호출 | **상한 없음** | 들어온 만큼 전부 나간다 |

PG read-timeout은 `TossPgClient`의 `@Value` 기본값으로 5초다(connect 2초). PG가 5초에 수렴하면 워커 100개가 각각 5초를 붙잡으므로 **처리량 상한이 초당 20건**으로 내려앉는다. 이때 Hikari 풀 20은 오히려 한가하다. 병목이 사라진 것이 아니라 **DB 풀에서 스레드 풀로 옮겨갔다.**

**서킷 브레이커는 이 경우를 못 잡는다.** `ResilientPgClient`의 설정은 5건 창, 실패율 50%, open 5초다. 서킷은 **실패**를 센다. PG가 4.9초씩 걸리면서 **성공**하면 실패율은 0이고 서킷은 열리지 않는다. 죽지 않고 느려지는 장애(브라운아웃)가 완전 장애보다 어려운 이유가 이 설정에 그대로 있다.

## 결정할 것

PG가 느려져 자원이 마를 때 **무엇을 먼저 버릴 것인가.** 네 가지 선택지가 있고 전부 다른 것을 포기한다.

| 선택지 | 포기하는 것 | 이 맥락에서 걸리는 질문 |
|---|---|---|
| **A. PG 동시 호출 세마포어** | 상한을 넘은 요청의 처리 자체(즉시 429) | 상한을 몇으로 잡나. `스레드 100 ÷ PG 5초`는 산수지 근거가 아니다 |
| **B. 느림도 실패로 세어 서킷을 연다** | 아직 성공할 수 있었던 요청 | 임계 응답시간을 넘으면 실패로 볼지, 그 오탐 비용이 얼마인지 |
| **C. read-timeout을 5초에서 2초로** | 5초면 왔을 승인 | **끊은 호출은 전부 `UNKNOWN`이 된다.** 미확정 재고를 내 손으로 만드는 것이다 |
| **D. 대기열에 넣고 나중에 확정** | 즉시 응답이라는 사용자 경험 | 결제가 비동기가 되면 화면·환불·CS 규약이 전부 바뀐다 |

**C가 이 시스템에서 특히 까다롭다.** 타임아웃을 조이면 장애는 빨리 끝나는데, 끊긴 호출은 ADR-007의 규약대로 TIMEOUT(=`UNKNOWN`)으로 흘러 복구 배치의 일거리가 된다. **가용성을 사면서 정합성 부채를 내는 거래**라서, 얼마나 사고 얼마나 내는지를 숫자로 보기 전에는 고를 수 없다.

## 재는 방법

측정 없이는 고르지 않는다(docs/performance의 기존 원칙과 같다).

**준비**: `FakePgClient`에 응답 지연 주입 스위치를 붙인다. `TossPgClient`는 실 PG라 지연을 주입할 수 없고, 앱↔PG 사이에 Toxiproxy를 세우는 것보다 가짜 PG에 지연을 넣는 쪽이 재현이 결정적이다. 기본값 0이면 지금 동작과 같다.

**1단계. 병목이 어디로 옮겨갔는지 본다.** PG 지연을 200ms → 1s → 3s → 5s로 올리며 각 단계에서 다음을 동시에 기록한다.

- Hikari 활성 커넥션 수 (`hikaricp_connections_active`)
- 톰캣 활성 스레드 수 (`tomcat_threads_busy_threads`)
- 체크아웃 p95와 처리량

사가 전후를 같은 방식으로 재면 "커넥션은 풀렸고 스레드는 안 풀렸다"가 그래프 하나로 나온다. 둘 다 Prometheus에 이미 나가고 있으므로 새로 계측할 것은 없다.

**2단계. 세마포어 상한을 고른다.** 5·10·20·상한 없음으로 돌리며 잰다.

- 정상 요청 p95 (상한이 지키는 값)
- 429 거절률 (상한이 내는 비용)
- 상한 없음에서 스레드가 마르기까지 걸리는 시간

**3단계. 타임아웃이 만드는 부채를 센다.** read-timeout 5초와 2초로 같은 부하를 돌리고 `UNKNOWN` 생성 건수와 복구 배치가 확정하기까지의 최고 경과시간을 비교한다.

**나올 문장의 형태**는 이렇다. "몇 ms 빨라졌다"가 아니다.

> PG가 3초를 넘기면 상한 없이는 N초 만에 워커가 마른다. 상한을 10으로 두면 거절률 X%를 내고 정상 요청 p95를 Yms로 지킨다. 대신 타임아웃을 2초로 조이면 미확정이 Z배가 되고 복구 배치가 그만큼 더 돈다.

## 대가 (어느 쪽을 고르든)

**상한을 두면 거절이 생긴다.** 지금은 느려도 언젠가는 처리된다. 상한을 두는 순간 "처리하지 않기로 한 결제"가 생기고, 그것이 사용자에게 어떻게 보일지를 정해야 한다. 결제 실패 화면은 재고 부족과 자원 부족을 구분하지 않는다.

**그리고 이건 ADR-020과 붙어 있다.** 실 PG가 둘이면 브라운아웃은 라우팅으로도 다룰 수 있다. 다만 ADR-020의 규칙대로 **타임아웃은 failover 하지 않으므로**, 느린 PG에서 넘길 수 있는 것은 아직 보내지 않은 요청뿐이다. 이미 나간 요청은 여기서 정한 방식으로 처리해야 한다.

## 다시 볼 조건

- 위 실험을 돌려 수치가 나오면 이 문서의 상태를 채택으로 바꾸고 고른 이유를 적는다
- 실 PG 연동이 늘어 응답시간 분포가 바뀌면 상한을 다시 잰다. 상한은 PG 응답시간의 함수라 PG가 바뀌면 근거가 사라진다

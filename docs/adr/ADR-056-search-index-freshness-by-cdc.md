# ADR-056. 검색 색인은 CDC 로 반영한다. 엔진은 앱 안 Lucene 을 유지한다

- 상태: **채택**. `app.catalog.search.cdc.enabled=true`(kafka 프로파일과 `catalog-cdc` 커넥터가 있을 때 동작). 엔진 기본값 `lucene` 유지
- 날짜: 2026-09-24
- 관련: `RefreshingLuceneSearch`, `LuceneChangeListener`, `EngineIndexer`, `CatalogDocs`, `cdc/register-catalog-connector.json`,
  [실측 리포트](../performance/search-freshness.md), [ADR-051](ADR-051-search-engine-by-quality.md),
  [ADR-055](ADR-055-search-filters-in-engine-and-scale-limit.md), [ADR-047](ADR-047-cdc-for-activity-not-outbox.md), 이슈 #246

## 맥락

앱 안 Lucene 은 10분마다 인스턴스마다 전체를 다시 만든다. 새 상품이 검색에 보이기까지 최대 10분이었다. #244 에서 재고·가격이
필터에 들어가면서 품절된 상품이 "재고 있음" 결과에 최대 10분 남게 됐다. ADR-055 는 엔진 기본값을 이 반영 지연을 보고 정하기로 미뤘다.

## 판정 기준 (이슈 #246 에 측정 전에 적었다)

- 반영 지연 p95 ≤ 3초, 30초 안에 반영 안 된 변경 0건
- 둘 다 통과하면 Lucene 을 유지하고 CDC 반영을 켠다. Lucene 만 탈락하면 기본값을 ES 로 바꾼다

## 결과 (대입)

| | 놓침 | p95 | 인스턴스 사이 차이(중앙값) | 변경 1건당 DB 재조회 |
|---|---:|---:|---:|---:|
| 10분 재색인(지금) | 60/60 | — | — | — |
| Lucene + CDC | 0/600 | **1,122ms** | 405ms | 인스턴스 수만큼 |
| ES + CDC | 0/600 | **1,197ms** | 40ms | 1 |

둘 다 통과 → **Lucene 을 유지하고 CDC 반영을 켠다.**

## 결정

- products·stock 변경을 Debezium 으로 `catalog.change` 토픽에 싣는다. 키는 `product_id` 다
- 받는 쪽은 **이벤트 내용이 아니라 id 로 DB 를 다시 읽어** 반영한다. 모양이 다른 두 표의 이벤트, 순서 바뀜, 중복을 따로 다루지 않는다
- Lucene 은 **인스턴스마다 모든 변경을 받는다**(부팅마다 새 컨슈머 그룹). 문서를 갈아 끼우고 1초마다 검색기를 다시 연다
- 기동 때는 **색인 적재를 시작한 시각의 5초 전부터** 읽는다. 적재와 구독 사이의 변경을 잃지 않게 하려는 것이다
- **10분 전체 재색인은 안전망으로 남긴다.** 재색인 중에 온 변경은 모아 두었다가 새 색인에 다시 반영한 뒤 갈아 끼운다
- ES·OpenSearch 로 바꾸면 같은 토픽을 **색인기 하나**(공유 그룹)가 받는다. 문서 하나의 거절은 세고 넘기고, 엔진이 못 받을 때만 다시 시도한다

## 버린 것

| 안 | 이유 |
|---|---|
| 재색인 주기를 줄이기(예: 10초) | 10만 건 재색인이 1.9초라 가능은 하지만 인스턴스마다 10초에 한 번 전체를 DB 에서 읽는다. 100만 건이면 12.6초라 주기보다 길다(ADR-055) |
| 이벤트 값으로 문서를 만들기 | stock 이벤트에는 상품 필드가 없다. 두 표를 이벤트 안에서 합치려면 순서와 중복을 다뤄야 한다. id 로 다시 읽으면 그럴 일이 없다 |
| 지금 ES 로 옮기기 | 반영 지연은 같은 수준이었다(1.12초 대 1.20초). 프로세스 하나와 1GB 를 더할 근거가 이번에도 없었다 |

## 대가 (정직하게)

- **인스턴스마다 결과가 잠깐 다르다.** 검색기 갱신 타이머가 인스턴스마다 어긋나 반영 시각이 중앙값 405ms 벌어진다. 같은 사용자가
  두 인스턴스를 오가면 방금 본 상품이 다음 요청에 안 보일 수 있다. ES 는 40ms 였다
- **읽는 비용이 인스턴스 수에 비례한다.** 변경 하나를 인스턴스마다 DB 에서 다시 읽는다. 카탈로그를 통째로 다시 넣으면 인스턴스 수 × 행 수다. 몰림은 재지 않았다
- **부팅마다 컨슈머 그룹이 하나씩 남는다.** 브로커의 오프셋 보존 기간이 지나면 사라진다
- 커넥터·브로커 장애 때 반영이 멈춘다. 안전망은 10분 재색인이라 그때는 예전 지연으로 돌아간다

## 다시 볼 조건

- 인스턴스가 늘어 변경 재조회가 DB 에 부담이 될 때, 또는 인스턴스 사이 결과 차이가 문제가 될 때 → ES(색인 하나, 색인기 하나)로 옮긴다
- **다른 서비스가 같은 색인을 읽어야 할 때** → 앱 안 색인은 나눠 쓸 수 없다. ES 로 옮긴다
- 카탈로그가 100만 건에 가까워질 때(ADR-055)

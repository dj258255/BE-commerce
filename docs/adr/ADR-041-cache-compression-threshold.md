# ADR-041. 캐시 압축은 1KB부터 — 근거는 생겼고 적용할 자리는 아직 없다

- 상태: **채택**
- 날짜: 2026-09-21
- 관련: `CacheValueCodec`, `CacheValueCompressor`, `CacheBenchmark`, `ContextStore`,
  [E6 리포트](../../personalization/docs/runs/20260921-e6-캐시-압축-임계값/report.md), [ADR-035](ADR-035-order-tolerant-context-merge.md)

## 맥락

캐시는 DB 조회를 없애도 **네트워크·메모리 비용은 없애지 않는다.** 값이 커지면 Redis 왕복이 tail 에서
튀고(실측: 500KB 에서 p99 2.02ms), 메모리도 그만큼 쓴다. 압축은 그 둘을 줄이는 대신 **CPU 를 쓰고**,
값이 작으면 **오히려 커진다**(표식 + base64 팽창 33%).

정해야 할 것은 하나다: **몇 바이트를 넘을 때부터 압축할 것인가.**

## 결정

**1. 임계값은 1KB 로 정한다.** 그 아래는 압축하지 않는다.

**2. 코덱은 `SNAPPY` 로 정한다** — 저장량이 비슷한 두 코덱에서 **CPU·지연이 낮은 쪽**을 골랐다
(사전 등록 기준). 교과서적 순서(LZ4 가 빠르다)는 이 환경에서 **성립하지 않았다**.

**3. 압축은 아직 켜지 않는다**(기본값 `NONE`). 근거는 생겼지만 **적용할 캐시가 없다** — 아래 「대가」 참고.

**4. 켤 때 쓸 값은 `codec=SNAPPY` · `compress-threshold-bytes=1024`** 다. 설정은 그대로 두고 값만 바꾸면 된다.

## 근거

### 1. 교차점이 관측됐다 (관측)

| 실제 원본 | `LZ4` 저장/원본 | `SNAPPY` |
|---:|---:|---:|
| **187B** | **1.070 (손해)** | **1.070 (손해)** |
| 279B | 0.817 | 0.846 |
| 553B | 0.499 | 0.521 |
| 1.1KB | 0.338 | 0.352 |
| 50KB | 0.168 | 0.163 |
| 500KB | 0.166 | 0.170 |

작은 값에서 압축이 **원본보다 커진다**(187B 에서 7% 증가). 가설이 같은 하네스에서 확인됐다.

### 2. 임계값을 경계가 아니라 **이득이 확실한 곳**에 둔다 (판단)

교차점은 187~279B 사이지만 **거기에 붙이지 않는다.** 그 근처의 이득은 몇 % 라 **값의 압축률이
조금만 달라져도 뒤집힌다**(압축률은 값의 성질이지 우리가 정하는 값이 아니다). 1KB 에서는 **66% 감소**라
이득이 값의 성질에 기대지 않고, CPU 차이는 무시할 수준이다(+2ms/500회).

**"교차점"과 "정할 값"은 다르다.** 교차점은 사실이고, 임계값은 **그 사실 위에서 고르는 결정**이다.

### 3. 큰 값에서 이득은 저장량만이 아니다 (관측)

500KB 에서 **get p99 가 `NONE` 2.02ms → `LZ4` 0.27ms** 로 **7.5배** 내려간다. 압축이 CPU 를 쓰지만
바이트가 줄어 **왕복이 짧아지기** 때문이다. 캐시 값이 커질 때 문제가 되는 것은 평균이 아니라 이 꼬리다.

### 4. 코덱 선택을 실측이 뒤집었다 (관측)

500KB 에서 CPU 가 **`SNAPPY` 242ms vs `LZ4` 359ms** 다(500왕복). 저장량은 사실상 같으므로
(50KB 이하에서 LZ4 가 몇 % 낫고, 50KB 에서 SNAPPY 가 0.163 vs 0.168) 사전 등록 기준에 따라 SNAPPY 다.
**왜 뒤집혔는지는 확인하지 못했다** — 추정(snappy-java 네이티브 vs lz4-java 순수 Java)은 근거로 쓰지 않는다.

### 5. 동시 요청 아래서도 선다 (관측, #266)

한 스레드로 잰 위 결과를 스레드 1 · 8 · 32 로 다시 쟀다([리포트](../../personalization/docs/runs/20260924-cache-concurrency/report.md)).

- 1KB · 32 스레드: 넣고 읽기 p95 SNAPPY 1.57ms, NONE 1.48ms(1.06배) — 임계값 1KB 유지
- 연산당 CPU: 8 · 32 스레드 여섯 칸 중 다섯에서 SNAPPY < LZ4, 1KB · 32 스레드는 같다(64.65µs) — SNAPPY 유지
- **동시성이 오를수록 압축의 이득이 커졌다.** 50KB · 32 스레드 p95 NONE 5.89ms 대 SNAPPY 2.24ms, 500KB get p99 40.21 대 8.42ms.
  공유 연결에서 바이트 수가 줄을 세우기 때문이다

## 버린 대안

| 대안 | 왜 버렸나 |
|---|---|
| **임계값을 교차점(≈240B)에** | 그 근처 이득이 몇 %라 값의 성질에 기대는 결정이 된다. 보수적으로 1KB |
| **임계값을 0(항상 압축)** | 187B 에서 저장량이 **7% 늘어난다**. 아끼는 것 없이 CPU 만 쓴다 |
| **임계값을 50KB(목 fixture 의 값)** | 실측 교차점보다 **200배 높다**. 279B~50KB 구간에서 50~83% 를 그냥 버리는 셈이다 |
| **`LZ4`** | 저장량은 비슷한데 CPU·지연이 실측에서 더 높았다. 통념과 반대지만 실측을 따른다 |
| **지금 기본값을 `SNAPPY`+1KB 로 켜기** | **적용할 캐시가 없다.** 켜 봐야 아무 값도 압축되지 않으므로 설정이 거짓말이 된다 |

## 대가 (정직하게)

- **압축은 base64 팽창 33% 를 안고 간다.** 이 저장소의 Redis 관례가 `StringRedisTemplate` + 문자열이라
  (ADR-035) 임의 바이트를 그대로 넣을 수 없다. **바이너리를 담는 직렬화로 바꾸면 임계값이 더 내려간다** —
  지금 임계값에는 그 관례의 비용이 포함돼 있다
- **적용할 자리가 없다.** 컨텍스트 캐시(`ctx:`)는 **Lua 스크립트가 값을 읽어 병합**하므로(ADR-035)
  압축하면 `cjson.decode` 가 깨진다 — **E2 에서 고친 원자적 병합을 되돌리지 않고는 넣을 수 없다**
- **임계값은 상한이다.** Redis 가 로컬이라 "전송량"이 루프백이다. 원격이면 줄어든 바이트가 지연으로
  돌아와 임계값이 더 내려간다
- **값의 모양에 기댄 결과다.** 컨텍스트 JSON 모양만 쟀다. 고엔트로피 값(사진·임베딩)은 교차점이
  훨씬 오른쪽이고, 압축률이 1을 못 넘을 수도 있다
- **동시 부하를 안 쟀다.** 압축은 CPU 를 쓰므로 요청이 몰리면 **압축이 큐를 만들 수 있다**(E3 과 같은 모양).
  이번엔 한 요청씩 쟀다

## 다시 볼 조건

1. **M7 에서 실제로 켤 때** — 홈 컴포저 결과 캐시는 **불투명하고 큰** 첫 자리다. 켠 뒤 p95·메모리를
   다시 재고 임계값을 확정한다
2. **네트워크가 원격이 될 때** — 임계값을 다시 잰다(지금은 상한이다)
3. **`SNAPPY` 가 `LZ4` 보다 싼 이유가 밝혀질 때** — 네이티브/순수 Java 차이라면 플랫폼이 바뀔 때
   순서가 또 뒤집힌다
4. **바이너리 직렬화로 바꿀 때** — base64 팽창이 사라지면 임계값이 내려간다

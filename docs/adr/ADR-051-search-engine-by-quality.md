# ADR-051. 검색은 앱 안 Lucene 으로 한다: 품질 축을 재니 MySQL 이 못 따라왔다

- 상태: **채택**. 기본값 `app.catalog.search.engine=lucene`
- 날짜: 2026-09-24
- 관련: `ProductSearch`, `RefreshingLuceneSearch`, `EngineQuery`, `FallbackProductSearch`,
  [실측 리포트](../performance/search-quality.md), [ADR-044](ADR-044-no-search-engine-yet.md), 이슈 #236

## 맥락

ADR-044 는 검색 엔진을 **지연 축**으로 판정해 넣지 않았고, "품질 축은 재지 않았다, 품질 요구가 생기면 비용과 무관하게
검토 대상이 된다"고 적었다. 지금 검색은 상품명·브랜드에 `LIKE '%q%'` 를 걸고 신상품순으로 낸다. 관련도 순서가 없고
어형·오타를 다루지 못한다. 이커머스가 검색 엔진을 들이는 큰 이유가 이 품질이라 그 축을 쟀다.

## 판정 기준 (이슈 #236 에 측정 전에 적었다)

1. 가장 나은 엔진의 오타·어형 nDCG@10(B·C·E 평균)이 가장 나은 MySQL 안보다 0.10 이상 높고, 동시성 10 p95 ≤ 100ms 이고,
   엔진이 죽어도 검색이 200 으로 물러서면 → 도입
2. 1 이 아니고 MySQL 안이 지금 것보다 A 에서 0.10 이상 높으면 → 엔진 없이 MySQL 쪽을 바꾼다
3. 엔진 셋 사이는 품질 차이가 0.02 안이면 운영 비용으로 고른다

## 결과 (대입)

| | 오타·어형 nDCG@10 | 동시성 10 p95 |
|---|---:|---:|
| 지금(`like`) | 0.071 | 1,471ms |
| MySQL 최선(`fulltext`) | 0.324 | 205ms |
| 앱 안 Lucene | 0.808 | 30ms |
| Elasticsearch | 0.814 | 47ms |
| OpenSearch | 0.798 | 53ms |

- **기준 1 발동**: +0.49(0.814 − 0.324), p95 30~53ms, ES·OpenSearch 를 멈추자 검색 200 · 물러선 횟수 1
- **기준 3**: 엔진 셋 차이 0.016 → 운영 비용으로 고른다

## 결정

**앱 안 Lucene 을 기본값으로 한다.** ES·OpenSearch 구현도 남긴다(설정 하나로 바꿀 수 있다).

| | Lucene(앱 안) | ES · OpenSearch |
|---|---|---|
| 추가 프로세스 | 없음 | 하나(컨테이너 약 1GB) |
| 색인 | 기동 때와 10분마다 1.4초, 힙 5MB | 밖에서 bulk 3.5초, 디스크 11.6MB |
| 여러 인스턴스 | **인스턴스마다 색인** | 공유 |
| 변경 반영 | 다음 갱신까지 최대 10분 | 색인을 다시 넣는 즉시 |

10만 건 · 5MB 에서 프로세스 하나와 1GB 를 더 운영할 근거가 없다. 인스턴스마다 색인을 만드는 비용(1.4초 × 인스턴스)이
그보다 싸다.

## 설계에서 정한 것

- **엔진은 id 와 순서만 준다.** 가격·재고는 DB 에서 채운다. 색인이 낡아도 화면 가격은 낡지 않고, 낡는 것은 "무엇이 걸리는가"뿐이다
- **정렬을 고르면 후보 안에서 정렬한다.** 관련도 엔진은 상위 500개 후보를 받아 DB 가 가격순 등으로 자른다. 지금 나가던 LIKE 는 일치하는 전체 안에서 정렬하던 동작 그대로다
- **실패하면 `like-fields` 로 물러선다.** 조용히 강등되지 않게 `catalog.search.fallback{engine}` 을 센다
- **색인 갱신은 배치 스케줄러로 돌리지 않는다.** 배치는 워커 하나만 돌지만(ADR-029) 이 색인은 인스턴스마다 있다. 갈아 끼운 옛 색인은 30초 뒤 닫는다(그 사이 검색이 닫힌 색인을 읽지 않게)
- **정확 일치 절을 3배로 둔다.** 1차 실측에서 오타 허용만 걸었더니 `blazer` 가 드문 이웃 `lazer`·`razer` 에 밀렸다(IDF). 정확 일치를 먼저 세우고 오타 허용은 받치는 자리로 내렸다. 대가는 이름 오타 쿼리 E 에서 −0.03

## 버린 것

| 안 | 이유 |
|---|---|
| MySQL FULLTEXT | 정확한 종류 쿼리(A)는 가장 좋았지만(0.852) 오타·어형이 0.324. 어간 추출·오타 허용 분석기를 고를 수 없다 |
| 필드만 넓힌 LIKE | A 는 0.450 → 0.727 로 크게 올랐지만 오타는 0. 동시성 10 p95 848ms |
| Elasticsearch · OpenSearch | 품질이 같고 운영 대상이 하나 는다 |

## 대가 (정직하게)

- **정확한 종류 쿼리에서 FULLTEXT 보다 낮다**(0.77 대 0.85). 오타 허용이 남아 있는 한 비슷한 말이 섞인다
- **새 상품이 검색에 보이기까지 최대 10분**이다(가격·재고는 즉시)
- **ES 와 OpenSearch 의 결과가 같지 않다**(상위 10개 겹침 0.753). 원인은 확인하지 못했다. 엔진을 바꿀 때 같은 쿼리셋으로 다시 재야 하는 이유다
- 정답이 속성 일치다. 동의어·한국어 쿼리는 재지 않았다

## 다시 볼 조건

- **카탈로그가 앱 힙에 부담이 될 때**(색인이 수백 MB) 또는 변경을 즉시 반영해야 할 때 → ES·OpenSearch 로 옮기고, 색인 갱신을 CDC 로 잇는다(ADR-047 의 경로)
- **동의어·한국어 쿼리가 요구될 때** → 분석기를 바꾸고 같은 쿼리셋에 그 묶음을 더해 다시 잰다
- 인스턴스가 많아져 10분마다의 재색인이 DB 에 부담이 될 때

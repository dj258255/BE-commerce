# ADR-076. 판매자별 웹훅 발송 격리 — 공유 풀 대 고정 샤드 대 셔플 샤딩 대 셔플+재시도

- 상태: 채택(비교 실험, 프로덕션 미배선)
- 날짜: 2026-09-28
- 관련: AWS Builders' Library "Workload isolation using shuffle-sharding"(Colm MacCárthaigh), 이슈 #430, `WebhookIsolationExperimentTest`

## 맥락

AWS 원문은 워커 8개에서 둘씩 고르는 셔플 샤딩이 고정 샤드보다 불량 임차인(계속 실패하거나 응답 없는 호출자)의 영향 범위를 훨씬 줄인다고 설명한다(조합 28가지 중 하나라 "just 1/28th"). 지금 알림 모듈(`LoggingNotificationSender`)에는 판매자 웹훅 발송기가 없다 — 로그로만 남긴다. 실제 발송기가 생기기 전에, 불량 판매자(무응답)가 섞였을 때 발송 라우팅 방식이 정상 판매자를 얼마나 지키는지 미리 근거를 남긴다.

## 측정 방법

`WebhookIsolationExperimentTest`(`@Tag("experiment")`, 순수 JUnit, Docker 불필요, 발송기를 새로 만들지 않음)가 발송 워커 8개(각 실제 스레드)·판매자 200명(판매자 0 = 발송량의 약 40%를 차지하는 큰 판매자, 나머지 199명이 60%를 나눠 가짐)을 시뮬레이션한다. 불량 판매자는 무응답 800ms(원문 15초를 스케일 다운, 비율 보존), 정상 호출은 20ms, 기한은 1600ms(원문 30초를 같은 비율로 스케일 다운).

- **SHARED**: 8개 워커 모두 후보, 대기열이 가장 짧은 워커로 보낸다(공유 큐와 같은 효과).
- **FIXED_SHARD**: 판매자를 4샤드(워커 2개씩)로 고정 분할한다.
- **SHUFFLE**: 판매자마다 8개 중 2개를 조합(28가지 중 하나)으로 배정하고 맹목적으로 번갈아 쓴다.
- **SHUFFLE_RETRY**: 배정된 두 워커 중 제출 시점에 대기열이 더 짧은 쪽으로 보낸다(실제 취소·재제출이 아니라 제출 시점 혼잡도 비교로 근사).

측정 전 이슈 #430에 판정 기준을 적었다. 불량 20%(40명)를 주 비교로 잡았지만, 실측(가정 없이 print만) 결과 워커 8개 규모에서는 네 방식 모두 기한 내 발송률이 7~13%로 목표(99%)에 크게 못 미쳐 방식 간 차이가 잡음 수준이었다. 이슈에 보정 결과를 남기고 주 비교 조건을 불량 1명(격리 효과가 원문이 노리는 상황과 일치)으로 바꿨다. 불량 20%·5%는 관찰용으로 남겼다.

## 실측 결과

정상 판매자(큰 판매자·불량 판매자 제외) 기한 내 발송률(DEADLINE_MS=1600):

| 조건 | SHARED | FIXED_SHARD | SHUFFLE | SHUFFLE_RETRY |
|---|---:|---:|---:|---:|
| 불량 1명(주비교) | 24.2% | 55.7% | 56.7% | 58.4% |
| 불량 5%(관찰, 10명) | 21.0% | 22.9% | 27.0% | 42.9% |
| 불량 20%(관찰, 40명) | 7.3% | 7.8% | 9.2% | 13.4% |

## 가설 판정

**측정 전에 적은 원래 기준(불량 20%를 주 비교)으로는 넷 중 하나가 틀렸다.** 기준 1(SHARED 90% 미만)은 7.3%로 맞았고 기준 3(SHUFFLE이 FIXED_SHARD 이상, 9.2% 대 7.8%)과 기준 4(SHUFFLE_RETRY가 SHUFFLE보다 높음, 13.4% 대 9.2%)도 맞았다. 기준 2(격리한 세 방식 모두 SHARED보다 뚜렷이 높다)는 FIXED_SHARD가 7.8%로 SHARED 7.3%와 잡음 수준이라 틀렸다.

아래 기준 1~3은 첫 실행 결과를 본 뒤 불량 1명을 주 비교로 바꿔 새로 적은 것이다. 같은 시뮬레이션을 다시 돌려 확인했으므로 독립된 검증이 아니다. 그 기준으로는 전부 맞았다.

1. **맞았다.** SHARED은 불량 1명에서도 기한 내 발송률이 24.2%로 50% 미만이다.
2. **맞았다.** FIXED_SHARD(55.7%)·SHUFFLE(56.7%)·SHUFFLE_RETRY(58.4%) 모두 SHARED(24.2%)보다 10퍼센트포인트 이상 뚜렷이 높다.
3. **맞았다.** SHUFFLE_RETRY(58.4%)가 불량 1명에서 네 방식 중 가장 높다. 불량 5%·20%에서도 매번 가장 높았다.

관찰 항목(판정 대상 아님)은 보정 때와 달랐다. SHUFFLE 대 FIXED_SHARD의 우열은 보정 실행에서 불량 1명일 때 FIXED_SHARD(55.9%)가 SHUFFLE(51.7%)보다 우세했지만, 최종 실측에서는 FIXED_SHARD 55.7% 대 SHUFFLE 56.7%로 SHUFFLE이 근소 우위였다(1퍼센트포인트, 스레드 스케줄링 잡음 수준). "재시도 없는 셔플 샤딩이 고정 샤드보다 나은지"는 워커 8개 규모에서는 명확한 방향이 없다.

## 이 실험이 답하지 못하는 것

- 실제 웹훅 발송기·HTTP 클라이언트는 만들지 않았다. 8개 워커를 스레드 풀로, 응답을 지연 시뮬레이션으로 근사했다.
- SHUFFLE_RETRY는 실제 취소·재제출이 아니라 제출 시점의 대기열 길이 비교로 근사했다 — 이미 시작된 불량 판매자 자신의 느린 호출은 어느 방식으로도 빨라지지 않는다.
- `NotificationService`·알림 모듈에 실제로 배선하지 않았다.
- 벌크헤드·서킷 분리(기존, 호출 종류별 격리)와의 상호작용은 재지 않았다 — 수신자별 격리만 봤다.
- 워커가 8개보다 훨씬 많을 때(원문 규모에 가까울 때) 셔플 샤딩의 우위가 뚜렷해지는지는 재지 않았다.

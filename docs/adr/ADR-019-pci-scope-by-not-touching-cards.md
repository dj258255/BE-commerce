# ADR-019. 카드번호를 서버가 만지지 않아 카드 데이터 환경의 범위를 줄인다

- 상태: 채택
- 날짜: 2026-09-05

## 맥락

결제 서버를 만들면 가장 먼저 받는 질문이 **"PCI DSS 는 어떻게 했나"** 다.
그런데 이 프로젝트는 PCI 통제를 하나도 구현하지 않았다. 그게 빠뜨린 것인지 고른 것인지
어디에도 적혀 있지 않았다. **적혀 있지 않으면 빠뜨린 것과 구별되지 않는다.**

## 결정

**카드번호(PAN)·유효기간·CVC 를 서버가 받지도 저장하지도 않는다.**
받는 것은 PG가 발급한 `paymentKey` 하나다.

```
브라우저 → PG 결제창(카드 정보는 여기서 PG로 직접) → paymentKey
                                                        ↓
                                          우리 서버는 이것만 받는다
```

그래서 이 서버는 **카드 데이터 환경의 범위를 줄인다**. 다만 외부 PG에 처리를 위탁했다고 해서
가맹점의 PCI DSS 책임이나 공급자 관리 책임이 자동으로 사라지는 것은 아니다. 실제 적용 범위는
결제창 방식, 연동 구조, 로그·모니터링 경계, 계약과 SAQ에 따라 확인해야 한다. 통제를 안 만든 것이
아니라, **우리 서버가 직접 통제해야 할 카드 데이터를 애초에 받지 않는 쪽**을 골랐다는 의미다.

## 왜 이 쪽인가

- **범위를 줄이는 것이 통제를 잘하는 것보다 싸다.** 카드 데이터를 만지는 순간 저장·전송·접근
  통제·로그·정기 점검이 전부 따라온다. 안 받으면 그 전부가 사라진다
- **범위를 줄이는 효과가 있다.** 결제 오케스트레이션이 가맹점 시스템에서 민감 정보를 걷어내
  카드 데이터 환경에 포함되는 시스템을 줄일 수 있다. 다만 이것이 PCI DSS 책임의 전면적인
  면제를 의미하지는 않는다.
- **네트워크 토큰화도 같은 계열이다.** 실제 카드번호 대신 토큰을 쓰면 유출돼도 피해가 작다

## 이 결정이 코드에 남긴 자국

- `PgApproveCommand`에 카드 필드가 없다. `paymentKey`·`orderNo`·`amount`·`installmentMonths` 뿐이다
- `Payment` 엔티티에도 없다. `paymentKey`만 들고 있다
- 마스킹·암호화 코드가 없다. **없어야 맞다** — 있으면 카드 데이터를 받고 있다는 뜻이다

## 대가

- **결제창을 우리가 못 그린다.** 화면 경험이 PG에 묶인다
- **결제창을 우리가 못 그린다**(위와 같은 항목)
- **3DS2 인증 흐름도 없다.** FDS 의 `CHALLENGE` 등급이 이름만 있고 받을 화면이 없는 것이
  이 결정의 그림자다

## 네트워크 토큰화는 "못 하는 것"이 아니라 "하면 안 되는 것"이다

처음에는 이걸 **계약이 없어서 못 한 것**이라고 적었다. 정확하지 않다.

이 프로젝트의 범위에서는 카드번호를 서버가 받아 저장하지 않는다. 네트워크 토큰과 PCI 적용 여부는
토큰의 종류, 복호화 가능성, 키 관리 위치, 연결된 시스템에 따라 달라지므로 “토큰이면 범위 밖”이라고
일반화하지 않는다. 실제 계약과 평가 기준에 따라 PCI 담당자 또는 적격 평가자 확인이 필요하다.

### 가맹점 몫의 토큰화는 이미 했다

카드번호를 못 만지는 가맹점이 할 수 있는 토큰화는 **PG가 준 키를 안전하게 보관하는 것**이고,
그건 구독 결제에 이미 있다.

```java
@Convert(converter = EncryptedStringConverter.class)
private String billingKey;          // 암호화해서 저장

@Column(nullable = false, unique = true, length = 64)
private String billingKeyIndex;     // 블라인드 인덱스 — 복호화 없이 조회·유니크 보장
```

빌링키 자체가 **카드번호의 대체물**이다. 2회차부터는 카드 정보 없이 승인이 된다.
그걸 평문으로 두면 카드번호를 평문으로 두는 것과 위험이 비슷해지므로 암호화했고,
암호화하면 조회가 안 되므로 **블라인드 인덱스**를 따로 뒀다.

**즉 이 축에서 가맹점 서버가 선택한 경계는 분명해졌다.** 남은 PCI 적용 범위와 PG 공급자 책임은
실제 계약·배포 방식·SAQ를 기준으로 별도 확인해야 한다.

## 안 한 것 — 3DS2

**3DS2 는 만들지 않았다.** 인증은 **카드사측 ACS 와 가맹점측 3DS Server**로 나뉘고,
국내에서는 가맹점이 PG가 제공하는 인증창을 태우는 형태가 일반적이다. 계약 위에서만 성립한다.

이 구멍이 코드에 남긴 자국이 있다 — FDS 의 `CHALLENGE` 등급이 **이름만 있고 받을 화면이 없다**.
등급을 넷으로 나눠 놓고 그중 하나를 받을 곳이 없는 것은, 인증 수단이 없기 때문이다.

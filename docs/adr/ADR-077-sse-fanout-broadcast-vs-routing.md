# ADR-077. 여러 대 실시간 알림 전파 — 전체 방송 대 세션 위치 라우팅

- 상태: 채택(비교 실험, 프로덕션 미배선)
- 날짜: 2026-09-28
- 관련: 배달의민족 주문접수 SSE 전환(https://techblog.woowahan.com/23199/), 이슈 #431, `SseFanoutExperimentTest`

## 맥락

배민 기술 블로그는 연결된 서버로 직접 호출, 브로커로 특정 서버 라우팅, 모든 서버로 방송 세 방식 중 방송을 골랐다고 밝혔다. 이유는 결합도(발행자가 연결 상태를 몰라도 됨)와 장애 복구 단순함이다. 대가는 서버가 N대면 각 서버가 전체 이벤트를 다 받는 증폭이다. 지금 알림 모듈에는 SSE 서버가 없다. 실제로 만들기 전에, 인스턴스 수가 늘 때 두 방식의 메시지 수·전달 지연이 실제로 어떻게 벌어지는지 근거를 남긴다.

## 측정 방법

`SseFanoutExperimentTest`(`@Tag("experiment")`, 순수 JUnit, Docker·실제 SSE 서버·Redis 불필요)가 인스턴스 수 N ∈ {2, 4, 8}, 세션 5,000개(`sessionId % N`으로 고정 배정, 스티키 연결 근사), 주문 상태 이벤트 3,000건(세션 중 균등 무작위, 고정 시드)을 시뮬레이션한다. 인스턴스는 단일 스레드 워커 하나의 큐를 쓴다.

- **BROADCAST**: 이벤트마다 모든 인스턴스에 보낸다. 인스턴스는 필터 비용 1ms(자기 세션인지 확인)를 쓰고, 자기 세션이면 전달 비용 3ms를 추가로 쓴다.
- **ROUTED**: 이벤트마다 레지스트리(Redis 세션 위치 조회 근사) 조회 지연 2ms를 기록된 지연에 더하고, 소유 인스턴스에만 전달 비용 3ms로 보낸다. 조회는 실제 스레드를 막지 않고 지연 수치로만 근사한다.

측정 전 이슈 #431에 판정 기준을 적었다. BROADCAST 전달 지연 p95가 "N이 늘어도 개선되지 않는다(또는 나빠진다)"고 예상했지만, 실측(가정 없이 print만)해보니 BROADCAST도 N이 늘면 개선됐다(전달 비용의 몫이 줄어서) — 다만 ROUTED의 개선폭이 훨씬 컸다. 이슈에 보정 결과를 남기고 판정 기준을 "개선폭 차이"와 "모든 N에서 ROUTED가 더 낮다"로 바꿨다.

## 실측 결과

| N | BROADCAST 총 메시지 | ROUTED 총 메시지 | BROADCAST p95(ms) | ROUTED p95(ms) |
|---|---:|---:|---:|---:|
| 2 | 6,000 | 3,000 | 8,846 | 5,292 |
| 4 | 12,000 | 3,000 | 6,198 | 2,624 |
| 8 | 24,000 | 3,000 | 4,863 | 1,332 |

BROADCAST 개선폭(N=2→N=8): 45.0% 감소. ROUTED 개선폭(N=2→N=8): 74.8% 감소.

## 가설 판정

측정 전 이슈 #431(보정 후)에 적은 판정 기준은 전부 맞았다.

1. **맞았다.** BROADCAST 총 메시지 수는 이벤트 수의 정확히 N배(6,000·12,000·24,000). 카운트로 확인했다.
2. **맞았다.** ROUTED 총 메시지 수는 N과 무관하게 3,000건. 카운트로 확인했다.
3. **맞았다.** BROADCAST의 개선폭(45.0%)이 ROUTED의 개선폭(74.8%)보다 20퍼센트포인트 이상 작다(실제 차이 29.8포인트) — 방송은 인스턴스를 늘려도 라우팅만큼 수평 확장이 안 된다.
4. **맞았다.** ROUTED의 p95는 N이 늘수록 뚜렷이(매 구간 40% 이상) 줄었다(5,292→2,624→1,332, 각각 50.4%·49.2% 감소).
5. **맞았다.** 모든 N(2·4·8)에서 ROUTED의 p95가 BROADCAST보다 낮았다.

원래 적은 관찰(판정 대상 아님)은 틀렸다 — "N=2에서는 레지스트리 조회 비용이 덜 상쇄돼 역전될 수 있다"고 예상했지만, N=2에서도 ROUTED(5,292ms)가 BROADCAST(8,846ms)보다 뚜렷이 낮았다. BROADCAST 고유의 필터 비용(모든 인스턴스가 모든 이벤트를 걸러야 하는 고정 비용)이 이 규모에서는 ROUTED의 레지스트리 조회 비용(이벤트당 2ms)보다 항상 컸다.

## 이 실험이 답하지 못하는 것

- 실제 SSE 서버(Spring WebFlux `SseEmitter` 등)·Redis 레지스트리는 만들지 않았다. 인스턴스를 스레드 풀로, 레지스트리 조회는 지연 수치 하나로 근사했다.
- 레지스트리 조회의 실제 네트워크 왕복(동시 여러 건일 때의 큐잉·커넥션 풀 경합)은 재지 않았다.
- 인스턴스 CPU 사용률은 재지 않았다(처리 건수·지연만 봤다).
- 한 대가 죽었을 때 유실·재연결 시간, Last-Event-ID 복구, 재시작 지터는 재지 않았다 — 이 실험의 스코프(메시지 수·지연)를 넘는다.
- `NotificationService`·실제 SSE 엔드포인트에 배선하지 않았다.
- BROADCAST를 고른 원문의 실제 이유(결합도·장애 복구 단순함)는 지연 수치만으로 설명되지 않는다 — 이 실험은 그 가치를 재지 않았다.

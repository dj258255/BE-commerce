# ADR-032. 프론트 스택을 Next.js로 전환한다

- 상태: **채택**
- 날짜: 2026-09-20
- 관련: `apps/web/`, `personalization/web/`(정적 프론트, 이관 대상), [ADR-031](ADR-031-storefront-catalog-read-api.md)

## 맥락

프론트가 두 표면(상점·개인화 콘솔)으로 늘었고, 앞으로 **화면이 30개를 넘을 것**으로 예상한다.
기존 프론트는 빌드 없는 정적 HTML/CSS/JS였다(ADR-031에서 "목적에 맞는 최소 도구"로 선택).

문제는 두 가지였다.

1. **화면이 늘면 공용 상태·컴포넌트 재사용이 필요해진다.** 지금은 공용 자산(`pz.js`) 하나로 버티지만, 상태가 얽히기 시작하면 비용이 급격히 오른다.
2. **"프론트 연동에서만 생기는 문제"를 조기에 보고 싶다.** 지연·타임아웃·부분 실패는 연동 지점을 실제로 통과해야 드러난다.

## 결정

**Next.js(App Router + TypeScript)를 프론트 스택으로 채택한다.**

- 개발은 `rewrites`로 `/api/*`를 Spring으로 프록시해 **same-origin 유지**(CORS 불필요)
- 개인화 자원은 `API_MODE(stub|real)`로 출처를 고른다. 백엔드(M7)가 붙기 전까지 스텁이 목 계약을 HTTP로 서빙
- 스텁에 `?delay=` `?fail=` 주입을 두어 **연동 실패를 의도적으로 재현**할 수 있게 한다
- 상점 카탈로그(`/api/v1/categories`)는 이미 실재하는 Spring API라 모드와 무관하게 Spring을 쓴다

## 버린 대안

| 대안 | 왜 버렸나 |
|---|---|
| **정적 바닐라 유지** | 화면 30개·공유 상태 증가를 감당할 근거가 약해졌다. 다만 이 선택의 비용(아래 "대가")은 실제로 지불한다 |
| **Astro(+React island)** | 이 프로젝트엔 더 맞는 선택이었다(MPA·기본 JS 0·SSG). 다만 "SSR/서버 데이터 페칭까지 가는 길"을 미리 깔아두려는 판단에서 Next를 택했다 |
| **Vite + React SPA** | 타입·컴포넌트 재사용은 얻지만 SSR이 없다. SEO/서버 페칭 요구가 생기면 다시 바꿔야 한다 |
| **차트 라이브러리 도입** | 인라인 SVG로 충분하다(의존성 0 유지) |

## 대가 (정직하게)

이 결정은 공짜가 아니다. 아래는 실제로 지불한/지불할 비용이다.

- **런타임이 둘이 된다.** 지금까지 "한 명령으로 뜨는 데모"였는데, 프론트는 `npm run dev`(3000)가 따로 필요하다. 데모 절차의 단계 수와 실패 지점이 늘었다
- **프론트 공학에 시간을 쓴다.** 이 프로젝트의 차별점은 백엔드의 정합성·측정 서사인데, 스택을 바꾸면 그 시간의 일부가 프론트로 간다
- **설치·빌드 비용**: `node_modules` 352MB, First Load JS 103KB, CI에 `web` job 추가
- **전환 중 이중 구조**: 정적 프론트(`personalization/web`)와 Next가 당분간 공존한다. 계약 fixture는 공유해 갈라짐을 막는다

## 배포 형태

**SSR(Node 유지)을 기본으로 한다.** 이 화면들은 신선도·지연을 측정하는 것이 목적이라 요청 시 계산이 자연스럽다.

- `output: 'export'`(정적)로 바꾸는 조건: 프론트를 백엔드와 **독립적으로** 배포해야 하거나, Node 런타임을 없애야 할 때
- 그때도 잃는 것은 서버 컴포넌트의 데이터 페칭이고, 얻는 것은 배포 단순성이다 — 실측 없이 지금 정하지 않는다

## 다시 볼 조건

- 화면이 30개를 넘고 **공유 상태가 3개 이상** 얽히기 시작하면 → 상태 관리 전략 재검토
- 프론트 빌드·배포가 **백엔드 가용성에 영향**을 주기 시작하면 → 정적 export 또는 분리 배포 검토
- SEO가 실제 요구가 되면 → SSG/RSC 활용 범위 확대

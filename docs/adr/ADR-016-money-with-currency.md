# ADR-016. 금액에 통화를 넣고, 통화가 다르면 연산하지 않는다

- 상태: 채택(1~3단계). 4~6단계는 보류
- 관련: `shared/Money`, `V30__settlement_currency.sql`, ADR-015

## 문제

`Money`가 금액만 들고 있었다.

```java
public record Money(long amount)   // "KRW는 소수점이 없으므로 최소 단위를 long(원)으로 다룬다"
```

주석이 전제를 정직하게 적어뒀지만, 그 전제는 KRW 에만 맞는다. USD 는 최소 단위가 1/100 이고
KWD 는 1/1000 이다. `Money(1000)`이 원이면 1,000원인데 달러면 $10.00 이다.

더 나쁜 것은 **조용히 틀리는 쪽**이다. 통화를 안 들면 1,000원 + $10 이 1,010 이 되고 컴파일도
통과한다. 값 타입이 막아줄 수 있는 실수를 막지 않고 있었다.

## 결정

**① 최소 단위 정수 + 통화.** ISO 4217 이 통화별 최소 단위 지수를 정한다. JDK 의
`Currency#getDefaultFractionDigits()`가 그 값을 준다.

```
KRW · JPY   지수 0        USD · EUR   지수 2        KWD · BHD   지수 3
```

JSR-354(Moneta)를 안 쓴다. `BigDecimal` 기반이고 라이브러리를 하나 더 들이는데, 우리가 필요한
것은 지수와 불일치 차단 둘뿐이라 JDK 로 된다. 이 프로젝트가 BouncyCastle·ShedLock 을 두고
내렸던 것과 같은 판단이다.

**② 통화가 다르면 더하지도 빼지도 비교하지도 않는다.** `compareTo`까지 막는 이유는, 환산해서
비교하고 싶어지는 자리인데 환율은 시점에 따라 달라 값 타입이 정할 수 없기 때문이다. 환산이
필요하면 호출부가 적용 환율을 명시해 같은 통화로 만든 뒤 비교해야 한다.

**통화를 생략하는 팩토리를 두지 않는다.** `Money.of(long)`이 있으면 KRW 로 조용히 기본값이
잡히는데, 그게 이 ADR 이 없애려는 바로 그 종류의 실수다. `Money.krw(long)`으로 매 호출이
통화를 밝힌다.

**③ 정산을 통화별로 가른다.** `uk_settlement_date`가 `(settlement_date)` 하나라, 같은 날
KRW 정산과 USD 정산이 둘 다 나올 수 없었다. 다통화를 붙이는 순간 이 제약이 **정상 동작을**
유니크 위반으로 막는다. 그렇다고 제약을 푸는 것은 안 된다 — 이 제약은 같은 날짜를 두 번 집계해
가맹점 지급이 두 배가 되는 것을 막던 자리다. 통화를 키에 넣어 둘 다 지킨다.

```
uk_settlement_date          (settlement_date)              → 다통화면 정상 동작을 막는다
uk_settlement_date_currency (settlement_date, currency)    → 둘 다 지킨다
```

## 보류: 4~6단계

**④ 원장 계정을 통화별로.** `ledger_entries.account`가 `PG_RECEIVABLE`·`SALES` 둘인데,
통화를 섞으면 차변 합 = 대변 합이라는 불변식이 뜻을 잃는다.

**⑤ 거래에 적용 환율을 저장.** 대사의 전제다. 승인 시점 환율이 없으면 사후에 검산할 방법이 없다.

**⑥ 대사 키와 원인에 통화.** 지금 대사는 `internal_amount`와 `external_amount`를 숫자로
비교한다. 표시 통화(고객이 결제한 통화)와 정산 통화(우리가 받는 통화)가 다르면 두 금액이
애초에 다르고, 그러면 전부 `AMOUNT_MISMATCH`로 뜬다. 원인 여덟 종 어디에도
"환산 때문"이 없어 `FX_CONVERSION_DIFF`를 하나 더 만들어야 한다.

**막고 있는 것은 "환율을 어디서 받아 적을지"다.** ⑤ 없이 ⑥ 을 할 수 없다.

여기서 오해하기 쉬운데, **환율 출처를 우리가 고르는 게 아니다.** 우리가 한국은행 고시환율로
계산해 장부에 적으면 PG는 자기 환율로 정산하므로 **대사가 매일 안 맞는다.** 우리 잘못이 아닌데
불일치가 난다. 국내 카드사는 승인일이 아니라 **매입일**(승인 +2~5 영업일) 환율을 쓰고,
Visa 는 매입 처리일의 Visa 공시 환율, PG 정산은 "정산 전일 특정 은행 N회차 고시 전신환매입율"
처럼 계약서에 박혀 있다. 즉 **PG가 응답과 정산 파일에 실어주는 값을 받아 적어야** 맞는다.

그래서 진짜 막고 있는 것은 **그 응답에 무엇이 오는지 실측할 수 없다는 것**이다.
토스페이먼츠 테스트 머천트로는 해외결제를 켤 수 없고, 켜려면 B2B 계약이 필요하다.
문서로만 보고 필드를 정해 스텁을 만들면, 그 위에 쌓은 대사 검증이 전부 가짜가 된다.

Stripe 가 FX Quotes API로 "정산 시점 환율이 얼마든 그걸로"에서 "이 환율로 갑니다"로 옮긴 것도
같은 문제를 다룬 것이다. 환율은 결제 시점에 안 정해지므로 어느 시점 값을 쓸지를 계약이 정한다.

이 프로젝트의 원칙대로 **재 보기 전에는 구조를 바꾸지 않는다.** 실제로 다른 통화를 받게 되는
시점에 환율 출처를 먼저 정하고 ④~⑥ 을 잇는다.

## 결과

- `Money(long minorUnit, Currency currency)`, `Money.krw(long)`, `Money.fractionDigits()`
- 통화 불일치는 `IllegalArgumentException`. 테스트 8개로 고정
- `settlements.currency` 추가, 유니크를 `(settlement_date, currency)`로 교체
- 기존 행은 전부 KRW. 이 시스템은 아직 KRW 만 만든다

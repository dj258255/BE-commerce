# ADR-029. 실행 단위만 분리하는 것과 저장소까지 분리하는 것

- 상태: **채택(배포 단위 분리를 기준선으로)**. 두 결합이 배포 단위만 나눠도 0 이 되는 것을 실측했다. 서비스·저장소 분리는 그 위에 얹는 별도 선택으로 남긴다.
- 날짜: 2026-09-19
- 관련: [모놀리스 한계 실측](../performance/msa-baseline-experiments.md), [ADR-024](ADR-024-settlement-extraction-data-cutover.md), `application.yml` worker 프로파일

## 맥락

정산 분리 실험(`msa-extraction` 브랜치)은 결합 두 개를 재현했다.

- **scaling coupling** — 결제 트래픽 때문에 인스턴스를 늘리면 정산 스케줄러가 함께 복제되어 같은 날짜를 중복 집계한다
- **deployment coupling** — 무관 모듈의 한 줄 수정도 전체 재시작을 요구해 결제가 배포마다 중단된다

**외부 피드백의 요지는 이 둘이 서로 다른 문제를 한 덩어리로 다뤘다는 것이다.** 두 결합은 **배포 단위를 나누기만 해도 풀린다.** 실험이 실제로 증명한 것도 거기까지다. 저장소·브로커까지 나눠 별도 서비스로 만든 것은 **그 위에 얹은 별도의 선택**인데, 그 근거를 따로 적지 않았다. 그래서 이후의 모든 분리 논의가 반쪽 근거 위에 서 있었다.

이 문서는 그 기준선을 만든다. 배포 단위만 나눈 형태를 먼저 실측하고, 그 위에서 "저장소까지 나눠 추가로 얻는 것"을 따로 판단한다.

## 무엇을 고르는 문제인가

| 선택 | 얻는 것 | 잃는 것 |
|---|---|---|
| **같은 코드·같은 DB, 배포 단위만 분리** | 두 결합이 풀린다. **트랜잭션과 조인이 그대로 남는다** | 코드베이스는 여전히 하나. 팀이 나뉘면 다시 걸린다 |
| **서비스·저장소·브로커까지 분리** | 완전한 독립. 다른 팀·다른 언어도 가능 | 트랜잭션이 사라지고 **메시지 중복·순서·poison·대사·이관**이 전부 새로 생긴다 |

## 만든 형태

**같은 jar, 프로파일 하나로 배포 단위를 둘로 나눈다.** `application.yml` 에 `worker` 프로파일을 추가했다.

- **API 배포** — 프로파일 없이 뜬다. 모든 스케줄러가 기본 off다(`@ConditionalOnProperty` 게이트). 수평 확장·롤링에 제약이 없다
- **워커 배포** — `SPRING_PROFILES_ACTIVE=worker` 로 뜬다. 배치(정산·복구·만료·dunning·outbox 정리 등)를 단일 실행 주체로 소유한다

저장소·브로커를 나누지 않았으므로 **트랜잭션과 조인은 그대로**다. 정산은 여전히 결제와 같은 DB를 본다.

## 실측 (2026-09-19, 로컬 단일 장비)

실험 환경: Apple Silicon 32GB, MySQL 8.4·Redis 7.4·Kafka(Docker/colima), k6 v1.6.1. 정산 항목 2만 건(어제 KST, `k6/seed-settlement-scheduler-split.sql`)을 시드하고 두 형태를 같은 조건으로 돌렸다.

### 실험 2 — 수평 확장 시 스케줄러 중복

**before (모놀리스): 정산 스케줄러를 켠 인스턴스 2개(8081, 8082)를 동시 기동.**

```
15:09:08.612 [8081] WARN  정산 배치가 틱당 페이지 상한에 닿았다 date=2026-09-18 읽은건수=10000
15:09:08.613 [8082] WARN  정산 배치가 틱당 페이지 상한에 닿았다 date=2026-09-18 읽은건수=10000
15:09:15.769 [8081] ERROR Duplicate entry '2026-09-18-KRW-1' for key 'settlements.uk_settlement_date_currency_seller'
15:09:15.781 [8081] ERROR 정산 배치 실패 date=2026-09-18   (DataIntegrityViolationException)
15:09:15.772 [8082] INFO  정산 배치 완료 date=2026-09-18 items=10000 net=97030000
```

두 인스턴스가 같은 틱에 진입해 **같은 1만 건을 통째로 중복 집계**했다. 늦은 쪽이 유니크 제약에 막혀 배치가 실패한다. 정합성은 지켜지지만(트랜잭션 롤백 + DB 유니크), 애플리케이션 가드는 무력하고 인스턴스 수만큼 무의미한 작업이 반복된다.

**after (배포 단위 분리): worker 1개(8081) + API 2개(8080, 8082, 스케줄러 off).**

```
15:10:29.179 [worker 8081] INFO 정산 배치 완료 date=2026-09-18 items=10000 net=97030000
API 8080 스케줄러 로그: 0건
API 8082 스케줄러 로그: 0건
DB: 정산 1행 (중복 없음)
```

**API를 2개로 늘려도 정산 스케줄러는 복제되지 않는다.** 스케줄러를 가진 배포가 하나뿐이기 때문이다. 중복 집계도, 유니크 위반도, 낭비되는 SELECT/UPDATE도 0 이다.

### 실험 3 — 무관 모듈의 배포가 결제를 중단시키는가

같은 형태에서 체크아웃 30VU를 3분간 깔고(`k6/redeploy-blast-radius.js`, BASE_URL=:8080), **93초 지점에 워커만 재배포**했다(정산 모듈 수정을 배포하는 상황의 재현).

| 항목 | 모놀리스 baseline | 배포 단위 분리 |
|---|---|---|
| 실패 요청 | **270건 / 9,870건 (2.7%)** | **0건 / 10,174건 (0.00%)** |
| 다운타임 | 9초 | 결제 API는 멈추지 않음 |
| `[FAIL]` 로그 | 다수 (connection refused) | **0건** |

k6 요약: `http_req_failed 0.00% (0 out of 10174)`, `checks_failed 0 out of 30`, 완료 5,057 iterations.

**무관 모듈(정산 배치)의 배포가 결제를 중단시키지 않는다.** 워커가 재기동되는 동안 결제는 계속 성공했다.

재기동한 워커는 첫 틱에서 같은 날짜를 다시 집계하려다 **멱등하게 건너뛴다.**

```
15:13:13.026 [worker 8081] INFO 정산 재실행 감지 → 건너뜀 date=2026-09-18 sellerId=1
```

즉 워커 재배포는 중복 정산도 만들지 않는다.

## 결론

**배포 단위만 나눠도 두 결합은 0 이 된다.** 이것이 기준선이다.

- 스케줄러 중복: 인스턴스 2개 → **0** (분리 후 API 2개 + 워커 1개)
- 배포 중단: 270건 → **0건** (워커 재배포 중 결제 무중단)

**저장소까지 나눠서 추가로 얻는 것**은 트랜잭션 없는 완전 독립(다른 팀·다른 언어·독립 스키마 진화)이다. **그 대가로 새로 생기는 실패 모드**는 이 저장소가 이미 `msa-extraction` 에서 겪은 것들이다 — 메시지 중복, 순서 역전, poison, 이벤트 스키마 진화, 대사, 그리고 **데이터 이관**(ADR-024 의 조용한 지급 누락). 이건 **공짜가 아니라 별도 결정**이다.

**따라서 이 저장소(main)는 배포 단위 분리를 채택하고, 서비스·저장소 분리는 채택하지 않는다.** 모듈러 모놀리스를 유지하되, 배치 실행 주체를 프로파일로 가르는 것만으로 실측된 두 결합을 제거한다.

## 정직한 한계

- **API 롤링 자체는 재지 않았다.** 로컬에는 로드밸런서가 없어 2개 리플리카 사이로 트래픽을 롤링할 수 없다. 이 실험이 보인 것은 **(a) 2개 리플리카가 스케줄러 중복 없이 병존한다**와 **(b) 워커 재배포가 결제를 멈추지 않는다**까지다. 리플리카 병존이 롤링의 전제조건이므로, 롤링 무중단은 그 위에서 성립한다(K8s Ingress 환경은 `msa-extraction` 브랜치에서 실측됨).
- **로컬 단일 장비 수치다.** 9초 다운타임·270건은 Gradle 데몬이 워밍된 로컬 최적 조건이다. 배포 환경마다 다시 재야 한다.
- **워커는 아직 단일 실행 주체다.** 워커 자체를 다중화하면 스케줄러 중복이 재발한다(리더 선출/ShedLock 후속 과제). 이 실험은 **워커 1개**를 전제한다.

## 다시 볼 조건

- 워커를 2개 이상으로 늘려야 하는 요구가 생기면(배치 물량이 단일 워커 처리량을 넘으면) 리더 선출을 먼저 넣는다. 그 전까지 워커는 1개다
- 팀이 실제로 나뉘어 코드베이스 하나가 걸림돌이 되면, 그때 "저장소까지 나눠 추가로 얻는 것"을 이 문서 기준선 위에서 다시 판단한다

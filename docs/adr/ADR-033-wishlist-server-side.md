# ADR-033. 찜을 서버에 저장하고 로그인을 요구한다

- 상태: **채택**
- 날짜: 2026-09-20
- 관련: `wishlist` 모듈, `V58`, [ADR-018](ADR-018-module-internal-packages.md), [ADR-031](ADR-031-storefront-catalog-read-api.md), `docs/09-ERD-설계.md` §12.8, `docs/10-API-스펙.md` §10

## 맥락

쇼핑몰에 장바구니는 있는데 **찜이 없었다.** 찜은 이커머스의 기본 동작이고, 동시에 **개인화 신호**로
쓸 수 있다(구매보다 자주 발생해 콜드스타트에 유리하다 — `personalization/docs/00-data.md`가
거래 없는 고객 9,699명·상품 995개를 콜드스타트로 기록하고 있다).

문제는 **장바구니와 정책을 맞출지**였다. 확인해 보니 장바구니는 이렇게 동작한다.

- 저장 위치는 `localStorage['becommerce.cart']`다. 서버 테이블이 **없다**
- 비로그인도 담을 수 있다. 로그인은 **체크아웃 진입 시점**에만 강제된다(`Store.auth.require()`)

즉 "장바구니와 같게" 하면 찜도 로컬 저장이 된다. 이슈 #169는 그 반대를 요구했다 —
"로컬 저장으로 흉내내지 않고 **로그인 유도**한다(장바구니와 같은 정책인지 확인하고 맞춘다)".
확인해 보니 장바구니와 **다르다**. 그래서 이 갈림을 결정으로 남긴다.

## 결정

**찜은 서버에 저장하고, 로그인한 사용자만 쓸 수 있다.**

근거는 하나다. **찜을 로컬에 두면 개인화가 소비할 수 없다.** 서버에 남기기로 한 이유가 그것이고,
로컬 저장으로 흉내내면 이 기능이 개인화 서사에서 아무 의미가 없어진다.

반대로 장바구니는 로컬이어도 손실이 없다. 장바구니의 목적은 **"지금 이 화면에서 사는 것"**이고,
그 순간의 브라우저 상태면 충분하다. 결제 시점에 로그인하면 되므로 마찰을 뒤로 미룰 수 있다.
찜은 그 순간에 끝나지 않는다 — 나중의 추천에 쓰이려면 **서버에 남아야** 한다.

## 버린 대안

| 대안 | 왜 버렸나 |
|---|---|
| **장바구니처럼 `localStorage`** | 마찰은 없다. 그러나 서버에 남지 않아 개인화 피처로 쓸 수 없다 — 찜을 만드는 주된 이유 하나를 버리는 셈이다. "남의 위시리스트"라는 개념 자체가 없어져 권한 검증도 성립하지 않는다 |
| **서버 저장 + 비로그인은 로컬 임시(로그인 시 병합)** | 둘 다 얻는 것처럼 보이지만 **구현이 두 배**이고, 병합 충돌 규칙(같은 상품을 로컬과 서버에 각각 담았을 때)을 새로 정의해야 한다. 로그인 사용자에게만 의미 있는 신호를 비로그인 사용자에게까지 넓히는 값이 그 비용을 정당화하지 못한다 |
| **order 모듈 하위 패키지(`order.wishlist`)** | 코드는 가장 적다(카탈로그가 같은 모듈 안이라 `order.catalog`를 직접 쓴다). 그러나 찜은 주문·결제 흐름의 일부가 아니라 **사용자 표면이자 개인화 신호**라 order에 얹으면 정체성 경계가 흐려지고, 나중에 개인화가 찜을 읽을 때 order를 통째로 거쳐야 한다 |
| **찜 전용 페이지 신설** | 계정 버튼이 이미 마이페이지(`orders.html`)를 가리킨다(`store.js` `renderAccount`). 페이지를 늘리면 문서·내비게이션 표면만 늘고 얻는 것이 없다 — 마이페이지의 한 섹션으로 충분하다 |

## 대가 (정직하게)

- **장바구니와 UX가 갈린다.** 같은 화면 안에서 장바구니는 로그인 없이 담기고 찜은 로그인을 요구한다.
  사용자가 "왜 되던 게 안 되지"를 겪을 수 있는 지점이다. 화면은 하트 클릭 시 토스트로 이유를 밝히고
  로그인 화면으로 보낸다(`login.html?next=…`)
- **모듈이 하나 늘고, order에 공개 읽기 포트가 생겼다.** `ProductCatalogFacts`(order 루트)는
  ADR-018이 요구하는 형태다 — `order.catalog`가 내부 패키지라 밖에서 열 수 없다. 위시리스트가
  상품 실존과 카드 값을 얻는 유일한 통로이고, 그 대가로 클래스 하나가 늘었다
- **동시 추가의 창이 남는다.** 멱등의 1차 방어는 사전 조회이고 유니크 제약은 최후 방어선이다.
  두 요청이 동시에 사전 조회를 통과하면 늦은 쪽이 `409 DUPLICATE_REQUEST`를 받는다 — DB는 1건으로
  유지된다. 순차 요청(연타)은 사전 조회가 흡수한다

## 다시 볼 조건

- **개인화가 찜을 실제로 소비하기 시작하면** → 이 결정의 근거가 검증된다. 소비하지 않는다면 서버
  저장의 값이 줄어든다(그때는 "무엇에 썼나"를 먼저 묻는다)
- **비로그인 찜의 마찰이 측정되면** → 로그인 없는 찜(로컬)과 서버 찜을 병행할지 재검토한다.
  지금은 측정이 아니라 판단이다
- **찜 목록이 커지면**(예: 수백 건) → 목록 조회가 `products`를 한 번에 읽는 방식이라
  페이지네이션이 필요해진다. 지금은 사용자당 수십 건을 전제한다

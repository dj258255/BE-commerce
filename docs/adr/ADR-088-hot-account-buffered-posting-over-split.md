# ADR-088. 핫 계정이 생기면 잔액 행을 분개마다 갱신하지 않고 한 집계기가 모아 반영한다. 하위 계정 분할은 만들지 않는다

- 상태: **채택**(조건부 설계 결정, 코드 변경 없음)
- 날짜: 2026-11-27
- 관련: 이슈 #494(측정 전 예측 · 기준과 댓글), [ADR-025](ADR-025-ledger-balance-read-strategy.md)(잔액은 SUM, 스냅샷은 조건부),

## 맥락

지금 원장은 분개를 INSERT만 하고 잔액은 `SUM`으로 읽는다(ADR-025). 그래서 지금은 여러 거래가 같은 행을 갱신하는 자리가 없다.
ADR-025는 행 수가 실측 문턱을 넘으면 잔액 스냅샷을 만들기로 했다. 스냅샷을 분개마다 갱신하면 결제가 몰리는 판매자 계정의 잔액 행 하나에 쓰기가 줄을 선다.

2026-09-22 측정(docs/37)은 그 비용만 쟀다. 워커 8개가 같은 행을 갱신하면 서로 다른 행보다 처리량이 83% 낮았다.
어떤 해법을 쓸지는 정하지 않았다. 결제 시스템 글들이 흔히 드는 해법은 둘이다.

| 선택지 | 쓰기 | 잔액 읽기 | 잃는 것 |
|---|---|---|---|
| A. 한 행 갱신(지금 스냅샷을 만들면 생기는 모양) | 분개 트랜잭션 안에서 잔액 행 `UPDATE` | 한 행 | 같은 행에 쓰기가 직렬화됨 |
| B. 하위 계정 분할(SPLIT-k) | 하위 행 k개 중 하나를 골라 `UPDATE` | k행의 합 | 대사가 k배로 늘고 출금이 있으면 하위 행마다 잔고 검사가 필요함 |
| C. 버퍼 기장(BUFFER) | 분개만 `INSERT`, 한 집계기가 주기마다 모아 잔액 행에 한 번 반영 | 한 행(집계 주기만큼 늦음) | 잔액 행이 늦고 집계기가 멈추면 계속 늦어짐 |

## 측정

09-22 하네스를 그대로 썼다. MySQL 8.4 별도 컨테이너, 워커 8, 워커당 200회, 트랜잭션 안 임계 구간 2ms, 수취(입금)만 있는 계정.
한 실행 안에서 COLD(워커마다 다른 행) · HOT · SPLIT-4 · SPLIT-16 · BUFFER(집계 주기 100ms)를 5회 돌렸다. 회차마다 표를 새로 만든다.
같은 맥의 다른 작업 때문에 COLD가 회차마다 1,015~1,631/s로 흔들려 절대값 대신 **같은 회차 COLD 대비 비율의 중앙값**으로 판정했다(측정 전에 #494에 적은 방식).

| 모양 | COLD 대비 처리량 | COLD 대비 p95 | 잠금 대기(중앙값) | 잔액 반영 지연 | 최종 잔액 == 1,600 |
|---|---:|---:|---:|---:|---|
| COLD | 100% | 1.00배 | 0 | | 5/5 |
| HOT | 15.8% | 7.40배 | 1,599 | | 5/5 |
| SPLIT-4 | 50.9% | 3.33배 | 1,236 | | 5/5 |
| SPLIT-16 | 74.2% | 2.00배 | 513 | | 5/5 |
| BUFFER | 94.5% | 1.20배 | 0 | p95 113ms, 최대 163ms | 5/5 |

시작과 끝의 부하 평균은 5.4와 10.2였다.

### 측정 전 예측과 실측

| 모양 | 예측(#494) | 실측 |
|---|---|---|
| HOT | COLD의 약 20% | 15.8% |
| SPLIT-4 | 50~70% | 50.9% |
| SPLIT-16 | 75~90% | 74.2%(0.8%p 벗어남) |
| BUFFER | 90% 이상, 반영 지연 p95 100~200ms | 94.5%, 113ms |

### 분할이 덜 돌려주는 이유

SPLIT-k에서 한 워커가 고른 하위 행을 나머지 7개 워커 중 누군가 쥐고 있을 확률은 대략 `1 − (1 − 1/k)^7`이다.
k=4이면 86.7%, k=16이면 36.3%로 계산되고, 잰 잠금 대기 비율은 1,236/1,600 = 77.3%와 513/1,600 = 32.1%였다.
같은 식으로 워커 8개에서 충돌을 10% 아래로 내리려면 하위 행이 67개 넘게 필요하다(계산이고 재지 않았다). 그러면 잔액 읽기는 67행의 합이 된다.

## 판정(측정 전 기준 그대로)

1. 모든 모양 모든 회차에서 최종 잔액 == 처리 건수 → 탈락 없음
2. COLD 대비 처리량 80% 이상과 p95 2배 이하 → **BUFFER만 통과**. SPLIT-16은 74.2%로 탈락했고, 같은 하네스의 다른 두 유효 실행에서도 77.8%와 74.0%로 80% 아래였다
3. 후보가 둘 이상일 때만 쓰는 우선순위라 적용하지 않음

## 결정

- 잔액 스냅샷을 만들게 되면 분개 트랜잭션 안에서 잔액 행을 갱신하지 않는다. 분개는 지금처럼 INSERT만 하고 집계기 하나가 주기마다 모아 잔액 행에 한 번 반영한다
- 집계기는 비잠금 읽기로 고른 분개만 PK로 잠가 표시한다(아래 측정 결함 3)
- 바로 맞는 잔액이 필요한 읽기는 스냅샷에 아직 반영하지 않은 분개의 합을 더한다. 이 읽기 비용은 재지 않았다
- 하위 계정 분할은 만들지 않는다
- 지금 코드는 바꾸지 않는다. 원장이 append-only와 SUM이라 핫 행이 없기 때문이다

## 대가

- 잔액 행이 집계 주기만큼 늦다. 주기 100ms에서 p95 113ms, 최대 163ms였다
- 출금(차감)이 있는 계정에는 쓸 수 없다. 늦은 잔액으로 잔고를 검사하면 초과 출금이 난다. 출금 계정은 한 행 조건부 UPDATE(ADR-004 방식)로 두고 직렬화 비용을 받는다
- 집계기가 멈추면 잔액 행이 계속 늦어진다. 반영 안 된 분개 수와 가장 오래된 분개의 나이를 알림으로 봐야 하고, 이 알림은 아직 없다

## 다시 볼 조건

- 출금이 몰리는 핫 계정이 생기면 행별 잔고 검사를 하는 분할이나 계정별 직렬 배치 쓰기를 다시 잰다
- 동시 쓰기가 8보다 크게 늘면 집계기 하나가 따라가는지 다시 잰다
- 이 측정은 한 맥에서 다른 작업 부하 위에 돌렸다. 운영 하드웨어의 절대 처리량으로 읽지 않는다

## 측정 결함 세 가지(판정 기준은 바꾸지 않음)

1. 첫 실행의 요약표가 모양마다 따로 중앙값 회차를 골라 COLD와 다른 모양의 회차를 섞었다. 회차별 비율의 중앙값으로 고쳤다
2. Gradle이 `-Dledger.hot.*`를 테스트 JVM에 넘기지 않아 모양을 고른 실행이 다섯 모양을 다 쟀다. `measurementTest`가 넘기게 고쳤다
3. 버퍼의 쓰기는 INSERT뿐인데 잠금 대기가 1,000번 넘게 났고 반영 지연이 1.2초로 실행 시간 전체와 같았다.
   처음에는 `(applied, id)` 인덱스 범위 잠금을 의심했지만 인덱스를 빼도 그대로여서 버렸다.
   집계기 회차를 찍어 보니 1.2초 동안 두 번만 반영했다. 표가 작을 때 옵티마이저가 `UPDATE … WHERE id IN (…)`에 전체 훑기를 골랐고,
   REPEATABLE READ의 잠금 읽기가 아직 커밋 안 된 새 분개마다 기다리며 표 끝을 쫓아갔다. `FORCE INDEX (PRIMARY)`로 읽은 행만 잠그자 약 100ms마다 반영했고 잠금 대기는 0이 됐다.
   운영 집계기를 만들 때도 같은 함정이 있어 결정에 넣었다

결함이 있던 실행의 원자료는 `raw/20261127-h494-hot-account/README.md`에 상태와 함께 남겼다.

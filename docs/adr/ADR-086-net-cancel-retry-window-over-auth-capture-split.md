# ADR-086. 망취소는 자동 매입을 유지한 채 시간 창 동안 재시도할 수 있게 하고, 승인 · 매입 분리는 만들지 않는다

- 상태: **채택**(설정 추가, 운영 기본값은 그대로)
- 날짜: 2026-11-19
- 관련: 이슈 #476(측정 전 기준과 댓글 세 개), #477(서킷 거절 분류),
  [ADR-003](ADR-003-stock-deduction-timing.md)(재고 차감 시점),
  [02-결제도메인-핵심개념.md](../02-결제도메인-핵심개념.md) "매입을 왜 안 만들었나",
  `CompensationType`, `CompensationExecutor`, `CompensationTask`

## 맥락

재고가 모자라 이미 승인된 카드를 되돌리는 망취소는 "당일 승인취소(매입 전 취소)"라는 전제로 만들었다.
토스페이먼츠 설명으로는 카드 승인이 매일 23:59:59에 마감되고 24:00부터 전날 승인분의 매입이 시작된다.
매입 전 취소는 결제 당일에만 되고 기록이 남지 않는다. 매입 뒤 취소는 보통 D+3일이 걸리고 카드사가 반송하면 가맹점이 직접 환불한다.

지금 망취소는 실패하면 2 · 4 · 8 · 16초 뒤 다시 시도하고 5번째 실패에서 FAILED가 된다.
FAILED가 된 건은 운영자가 재무장하기 전까지 PG에 승인으로 남고, 자정을 넘기면 매입 취소 대상이 된다.
전제가 언제 깨지는지는 잰 적이 없었다.

해외 가맹점은 승인과 매입을 나눠(auth/capture) 재고를 확인한 뒤에만 매입한다.
토스도 수동 정산 요청 API로 매입을 따로 부를 수 있지만 추가 계약이 필요하다.

## 검토한 선택지

| 선택지 | 재고 부족 시 | 망취소가 끝내 실패하면 |
|---|---|---|
| A. 자동 매입 + 망취소 5회(지금) | 승인취소 | 운영자가 자정 전에 재무장하지 않으면 매입 취소(D+3) |
| B. 자동 매입 + 망취소를 시간 창 동안 재시도 | 승인취소 | 창이 끝날 때까지 자동 재시도 |
| C. 승인 · 매입 분리 | 승인 해제 | 승인이 유효기간 뒤 저절로 풀림. 대신 판매마다 매입 호출이 생기고 매입이 실패하면 돈을 못 받음 |

C는 판정 기준 4에 따라 구현하지 않고 숫자와 구조로만 비교했다.

## 측정

#374 하네스를 그대로 썼다. 재고 100, 주문 300건(60초), 이탈 20%, 결과 모름 10%.
가짜 PG에 두 스위치를 넣었다(둘 다 기본 꺼짐).

- 취소 장애: 첫 취소 호출부터 정한 시간 동안 연결 실패(`CANCEL_CONNECT_FAILED` 경로)
- 매입 마감: 첫 승인 뒤 60초를 자정으로 본다. 그 전에 승인된 건이 그 뒤에 취소되면 매입 뒤 취소로 센다

하루를 60초로 줄였으므로 "매입 뒤 취소" 건수는 실제 빈도가 아니다. 장애나 지연이 마감과 겹칠 때 어떤 모양이 되는지만 보여 준다.

### 본 실행(재고 전략 CHECK, 취소 장애 180초)

| 실행 | 판매 | 망취소 | FAILED | PG 승인 → 취소 |
|---|---:|---:|---:|---|
| R1 장애 없음 · A | 100 | 3 | 0 | 2.4 · 2.5 · 2.6초 |
| R2 장애 180초 · A | 100 | 1 | 1(5회 시도 뒤) | 취소 안 됨 |
| R3 장애 180초 · B(창 30분) | 100 | 1 | 0 | 272.9초(장애 종료 뒤 91.4초) |

시작 때 같은 맥의 부하 평균이 64였다(끝날 때 19).
CHECK의 망취소는 매진 경합 타이밍에 따라 0~24건으로 흔들렸다.
같은 조건의 2회차는 집계 단계에서 패키지를 받지 못해 망취소 상태를 세지 못했다(`raw/…-r2/NOTE.txt`).
하네스는 시작 전에 패키지를 확인하고 집계 전에 원본 표를 파일로 뜨게 고쳤다.

### 보조 실행(재고 전략 NONE, 취소 장애 60초)

표본이 1건씩이라 재시도 규칙만 따로 쟀다. NONE은 매진 뒤 결제가 모두 망취소가 되어 판매 시간 내내 흩어져 쌓인다(ADR-003의 116건).
장애를 60초로 줄인 것은 A가 포기하는 경계가 쌓이는 구간 한가운데 오게 하려는 것이다. 예측은 실행 전에 #476에 적었다.

| 실행 | 망취소 | FAILED | 취소된 시각 | 예측 |
|---|---:|---:|---|---|
| R1 장애 없음 · A | 133 | 0 | 승인 뒤 p50 3.2초 · 최대 6.2초 | FAILED 0, 수 초 안 |
| R2 장애 60초 · A | 134 | 72 | 나머지 62건은 장애 종료 뒤 3.8~16.1초 | 장애 시작 뒤 약 20초(±5초) 안에 쌓인 것은 FAILED |
| R3 장애 60초 · B | 133 | 0 | 133건 모두 장애 종료 뒤 4.8~32.8초 | FAILED 0, 장애 종료 뒤 약 70초 안 |

- R2의 경계는 장애 시작 뒤 14.7초(FAILED)와 14.9초(성공) 사이였다. 예측한 20초 ±5초를 0.2초 벗어났다
- 예측은 "첫 시도 뒤 약 40초면 포기"로 계산했는데 첫 시도도 다음 배치 틱(최대 5초)을 기다린다. 원본 표로는 적재부터 5번째 실패까지 44.5초였다
- 그래서 A의 포기 시점은 "적재 뒤 약 45초"로 고쳐 적는다
- 장애 60초가 망취소 134건 중 72건(54%)을 운영자 몫으로 넘겼다

### 측정 중 찾은 결함

R2에서 FAILED 72건 × 5회 시도면 PG 취소 실패 호출이 360번 안팎이어야 하는데 가짜 PG에 닿은 실패는 33번이었다.
나머지 시도는 취소 서킷이 열려 `CallNotPermittedException`으로 거절됐고, 이 예외는 `PaymentException`이 아니라서 결과 분류 없이(`last_outcome = NULL`) 횟수만 올렸다.
FAILED 72건 중 66건이 분류 없이 남았다. FAILED가 되는 시각은 백오프 일정이 정하므로 판정은 바뀌지 않는다. 분류는 #477에서 고친다.

## 판정(측정 전 기준 그대로)

1. 환경: 본 실행 R1의 망취소 3건은 9건 ±50% 밖이다. 부하 평균과 함께 기록하고 그대로 쓴다
2. 본 실행 R2와 보조 R2에서 FAILED가 났다. **지금 규칙은 PG 취소 장애가 적재 뒤 약 45초를 넘기면 자동 처리를 포기하고, 운영자가 자정 전에 재무장하지 않으면 매입 취소가 된다**
3. 본 실행 R3과 보조 R3 모두 FAILED 0이고 장애 종료 뒤 91.4초, 32.8초 안에 모두 취소했다(기준 300초). B를 채택한다
4. C 검토 조건은 둘 다 나오지 않았다. (a) B로 300초를 넘긴 건 없음 (b) 장애가 없을 때 승인 → 취소 최댓값은 6.2초로 1시간에 한참 못 미침
5. C의 비용: 같은 부하에서 판매 100건마다 매입 호출 100번이 새로 생긴다. 매입이 실패하면 상품은 나갔는데 돈을 못 받는 방향이라 망취소 실패보다 피해 방향이 나쁘다. 수동 정산 API는 추가 계약이 필요하다
6. 운영 기본값(망취소 5회)은 바꾸지 않았다

## 결정

- `app.compensation.retry-window-seconds`(환경 변수 `APP_COMPENSATION_RETRY_WINDOW_SECONDS`)를 추가한다. 기본값 0은 지금 규칙(5회)이다
- 0보다 크면 망취소 태스크는 적재 뒤 그 시간 동안 FAILED가 되지 않는다. 백오프 간격은 그대로(상한 300초)라 장애가 끝나면 다음 틱에 취소된다
- 승인 · 매입 분리(C)는 만들지 않는다
- 한정 상품의 기본 경로(`AT_PAYMENT`)는 이미 망취소가 0건이라(ADR-003) 이 결정과 무관하다

## 대가

- 창을 켜면 `compensation.exhausted` 알림이 창 길이만큼 늦게 울린다. 그 사이 장애는 `compensation.processed{outcome="connect_failed"}` 증가율로 따로 봐야 한다
- 창은 매입 마감을 넘지 못한다. 장애가 자정에 걸치면 B도 매입 취소를 막지 못한다. 보조 R3에서 줄인 마감 뒤에 끝난 133건이 그 모양이다. 그 자리를 덮는 것은 C뿐이다
- 장애가 없어도 자정 직전 승인 → 취소가 걸치는 건은 남는다. 승인 → 취소가 최대 6.2초였으므로 자정 6초 전 승인분만 해당한다

## 다시 볼 조건

- 실 PG에서 취소 API 장애가 자정을 넘겨 이어진 사례나 매입 취소 건이 나올 때
- 예약 판매 · 주문 제작처럼 배송 전 고객 취소가 많아져 승인을 오래 잡아 둘 이유가 생길 때(C가 유리해지는 자리)
- 수동 정산 API 계약이 생길 때

# ADR-020. 멀티 PG 라우팅을 만들어 두고 기본으로 끈다

- 상태: 채택
- 날짜: 2026-09-05

## 맥락

`RoutingPgClient`와 `PgSelector`가 있다. 가중치로 주 PG를 정하고, 서킷이 열린 경로는
건너뛰고, 요청이 **PG에 닿지도 못했을 때만** 다음 경로로 넘긴다.

그런데 `app.pg.routing.enabled` 기본값이 `false` 다. **왜 껐는지가 어디에도 없었다.**

## 결정

**기본 off 를 유지한다.** 그리고 그 이유와 켜는 조건을 여기 적는다.

## 왜 껐나

**실계약된 PG가 하나뿐이다.** 지금 라우팅 설정은 두 경로가 모두 `FakePgClient` 다.
가짜 둘 사이를 오가는 것은 **failover 를 증명하지 않는다**.

라우팅을 켜면 얻는 것으로 흔히 말하는 것이 셋인데, 셋 다 지금은 성립하지 않는다.

| 흔히 말하는 값 | 지금 성립하나 |
|---|---|
| 한 PG 장애 시 다른 PG로 넘김 | ❌ 넘어갈 실 PG가 없다 |
| 수수료가 싼 쪽으로 라우팅 | ❌ 계약 수수료가 하나뿐이다 |
| BIN·금액별 승인율 최적화 | ❌ 승인율 데이터가 없다 |

## 그럼 왜 만들어 뒀나

**로직의 값은 PG가 실물이 아니어도 잴 수 있고, 실제로 쟀다.** `RoutingPgClientTest`가
고정하는 것이 라우팅의 **어려운 부분**이다.

- 주 PG가 성공하면 보조를 **부르지 않는다**
- 요청이 PG에 **닿지도 못했을 때만** failover 한다
- **카드 거절은 failover 하지 않는다** — 다른 PG도 거절한다
- **타임아웃도 failover 하지 않는다** — 미확정을 재시도로 읽으면 이중 결제다
- 어댑터가 미확정을 예외로 던져도 failover 하지 않는다
- 주 PG 서킷이 열리면 건너뛴다

**failover 에서 어려운 것은 "넘기는 것"이 아니라 "언제 안 넘기는가"** 이고, 그건 실 PG 없이도
고정할 수 있다. 그래서 로직은 만들고 스위치는 껐다.

## 켜는 조건

1. **실계약된 PG가 둘 이상**일 것
2. 각 PG의 **승인율·수수료를 실측**했을 것 — 가중치를 근거 없이 정하면 그건 그냥 순서다
3. **failover 가 이중 결제를 만들지 않는 것**을 실 PG로 확인했을 것.
   지금은 "요청 미도달일 때만 넘긴다"는 규칙으로 막고 있는데, PG마다 미도달 판정이 다르다
4. **경로마다 서킷을 승인 · 조회 · 취소로 나눴을 것.** 지금은 경로당 서킷 하나를 셋이 같이 쓴다. `ResilientPgClient` 에서 같은 구조가 조회 실패로 새 승인을 막고 건강한 조회로 승인 장애를 가렸다([#372](../34-결제-재시도와-retry-storm-실험.md#2026-09-26-서킷을-승인취소조회로-나눴다-372))

## 대가

**코드가 있는데 안 쓴다.** 쓰지 않는 코드는 썩는다. 그래서 테스트로 고정해 두고,
켤 조건을 여기 적어 **언제 다시 볼지**를 남긴다.

## 두 번째 PG를 붙이려다 어디서 막히는지 직접 확인했다

"계약이 필요하다"는 말이 정확히 무엇을 뜻하는지 몰라서, 카카오페이로 **끝까지 가 봤다.**

| 단계 | 결과 |
|---|---|
| 개발자센터 애플리케이션 등록 | ✅ |
| Client ID · Client Secret 발급 | ✅ |
| **Secret key(dev) 발급** | ✅ |
| 결제 준비 API(`/online/v1/payment/ready`) 호출 | ❌ **HTTP 401 — 권한 없음** |

**키까지는 카카오 계정만으로 된다.** 막힌 곳은 그 뒤였다.

애플리케이션의 `사용 API` 목록에 **온라인결제가 아예 없다.** 있는 것은 얼굴 인식·코드송금·
1/N 정산뿐이다. 기본정보 화면이 이유를 말한다.

> 카카오페이 파트너센터에서 **사업자 등록 후 비즈앱 등록**이 가능합니다.
> 비즈앱 등록 후에는 사용 권한이 있는 비즈API를 사용할 수 있습니다.

**온라인결제 API = 비즈앱 = 사업자등록.** `TC0ONETIME`이 공개 테스트 CID 인 것은 맞지만,
**그것을 부를 권한 자체가 사업자에게만 열린다.**

### 그래서 "계약이 필요하다"의 정확한 뜻

처음에는 이걸 **"API 키를 못 받아서"**라고 적었다. 틀렸다. 키는 받았다.
막는 것은 **사업자등록**이고, 그건 개인 프로젝트가 넘을 수 있는 벽이 아니다.

이 차이가 중요하다. "키가 없어서 못 했다"는 **안 해 본 사람의 말**이고,
"사업자등록이 있어야 온라인결제 API 권한이 열린다"는 **해 보고 막힌 사람의 말**이다.

### 그래서 어댑터는 만들었다 — 그 401 이 진짜라서

처음에는 "검증할 수 없는 코드가 하나 늘 뿐"이라 안 만들려 했다. 그런데 **401 이 진짜 응답**이라
쓸 데가 있다.

라우팅은 "요청이 PG에 **닿지도 못했을 때만** 다음 PG로 넘긴다"는 규칙으로 이중 결제를 막는다.
401 은 **닿은 뒤에 거절된 것**이라 넘기면 안 되는 경우다. **그 구분을 실 응답으로 고정할 수 있다.**

`KakaoPayLiveContractTest`가 실 엔드포인트에 붙어 둘을 고정한다.

- 권한 없는 승인 요청이 **실패로 분류**된다 — 예외로 새지 않는다
- 그것을 **다음 PG로 넘기지 않는다** — 보조 경로가 불리면 그 자리에서 실패하도록 짰다

**성공 경로는 사업자등록 전까지 확인할 수 없다.** 그래서 취소·조회는 아예 구현하지 않고
부르면 명시적으로 실패하게 뒀다 — 조용히 성공을 흉내내는 것이 더 나쁘다.

### 붙이다가 하나 더 찾았다

토스 어댑터가 쓰는 `SimpleClientHttpRequestFactory`로 카카오페이에 붙였더니
**401 응답의 본문이 비어서 왔다.** `curl` 로는 `{"error_code":-401,...}`가 그대로 오는데도 그랬다.

우리는 **HTTP 상태가 아니라 PG 에러 코드로 판정**한다. 본문을 못 읽으면 그 판정이 통째로 무너지고,
`401`이 전부 같은 `401`이 된다. 팩토리를 JDK HttpClient 기반으로 바꿔 해결했다.

토스 쪽은 같은 팩토리로 에러 본문이 정상적으로 읽힌다(실 계약 테스트가 에러 코드까지 확인한다).
그래서 **스프링 일반의 문제로 단정하지 않고, 이 조합에서 관찰된 사실로만 적는다.**

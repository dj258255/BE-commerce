# ADR-007. 체크아웃 트랜잭션 경계: 단일 트랜잭션 → 3단계 사가로 이행

- 상태: **개정 (Superseded by implementation)**. 처음엔 "단일 트랜잭션 유지 + 사가는 마이그레이션 경로"로 채택했으나(아래 원안), 이후 아래 "마이그레이션 경로"를 **실제로 이행**했다(커밋 337c3a0). 지금 코드는 3단계 사가다.
- 날짜: 2026-07-07 (원안) / 2026-07-07 (사가 이행)
- 관련: [ADR-003](ADR-003-stock-deduction-timing.md), [ADR-001](ADR-001-architecture-spring-modulith.md), Phase 2(실패 처리)

> **이행 요약**: `CheckoutService.confirm`을 예약(`CheckoutTx.reserve`, tx) → PG 승인(`PaymentService.pgApprove`,
> **트랜잭션 밖**) → 확정/보상(`CheckoutTx.settle`, tx) 3단계로 재작성했다. PG 외부 콜 동안 DB 커넥션을
> 붙잡지 않으므로, 느린 PG(브라운아웃)가 커넥션 풀을 마르게 해 앱 전체를 마비시키는 연쇄 장애를 막는다.
> 원자성을 포기한 대가인 "멈춘 사가"(예약 후 확정 전 크래시)는 `CheckoutRecoveryService`가 PG 조회로
> 완결/롤백한다. 아래 원안은 "왜 처음엔 단일 tx로 뒀는지"의 기록으로 남긴다.

---

## (원안) 단일 트랜잭션 유지

## 맥락

`CheckoutService`는 클래스 레벨 `@Transactional`이고, `confirm()` 한 트랜잭션 안에서 **포인트 선점 → PG 승인(외부 HTTP) → 재고 차감 → 주문 상태 전이**를 처리한다. 즉 **외부 PG 호출이 DB 트랜잭션 안**에 있다.

이건 널리 알려진 안티패턴이다. "**외부 API 콜 중 DB 커넥션을 붙잡지 마라**". 커넥션을 외부 응답까지 점유하면, PG가 느려질 때 커넥션 풀이 고갈되어 전면 마비로 번진다. 실제 장애 사례가 많다(다운스트림 지연으로 인한 연쇄 결제 실패, 느린 저장프로시저가 커넥션을 소진시킨 수 시간 outage, 트래픽 2배에 ORM 최대 커넥션 고갈 등). **서킷브레이커도 "기다리는 동안 풀이 찬다"**. 완전히 막지 못한다.

고규모/마이크로서비스의 정석은 이 흐름을 **사가(saga)로 쪼개는** 것이다: 짧은 로컬 트랜잭션(예약) → 외부 콜(트랜잭션 밖) → 확정/보상(짧은 트랜잭션). 각 단계는 커넥션을 외부 콜 동안 붙잡지 않는다.

## 결정

**이 시스템(모듈러 모놀리스, 단일 DB, 바운디드 스케일)에서는 체크아웃을 단일 트랜잭션으로 유지한다.** 안티패턴을 인지하되, 아래 트레이드오프 분석에 따라 의도적으로 이 설계를 택한다.

## 근거 / 트레이드오프

**단일 트랜잭션이 주는 것은 로컬 변경끼리의 원자성이다.** (PG는 이 트랜잭션에 참여하지 않는다. 승인이 성공한 뒤 커밋이 실패하면 카드에서는 빠졌는데 우리 DB엔 없다. `UNKNOWN` 복구가 존재한다는 사실 자체가 이 구조도 이미 분산 정합성 문제를 갖고 있다는 증거다.) 포인트 차감·결제 레코드·재고·주문 상태가 **함께 커밋되거나 함께 롤백**된다. 외부 부수효과(PG 승인)만 롤백 불가라 보상이 필요하고, 그것도 이미 처리한다: 승인 후 재고 부족 → 망취소 보상 태스크(durable), PG 타임아웃 → `UNKNOWN` 보존 후 복구 배치가 조회로 확정. 승인 요청은 주문번호를 PG측 멱등키(`Idempotency-Key`)로 싣고 있어(`TossPgClient`), 타임아웃이면 `ResilientPgClient`가 같은 커맨드로 최대 1회(설정값) 재전송한다(#395) — 재전송도 확정에 실패하면 그대로 `UNKNOWN`으로 남고, 복구 배치의 조회 확정 경로는 이전과 같다.

**사가로 쪼개면 잃는 것은 그 원자성이다.** 사가는 격리(isolation)를 포기한다. Phase 1에서 포인트 예약이 커밋된 뒤 크래시로 Phase 3(확정/보상)를 못 하면, **포인트 예약·결제·주문이 어중간하게 멈춘 사가**로 남는다. 이를 복구하려면 "멈춘 사가를 완결 또는 롤백"하는 별도 회복 경로가 필요하다(포인트만 복원이 아니라 상태 기계 전체). 즉 사가는 **원자성을 커넥션 점유와 맞바꾸고, 그 대가로 새 크래시 엣지케이스와 회복 복잡도**를 떠안는다.

**이 맥락에서의 판단.** "외부 콜을 트랜잭션 밖으로"는 **고규모·다중 인스턴스·느린/원격 PG** 환경에서 가장 강한 규칙이다. 이 시스템은:

- **커넥션 점유에 상한을 걸었다.** 다만 처음 적은 근거는 틀렸다. Hikari `connection-timeout: 3s`는 **풀에서 커넥션을 빌리려고 기다리는** 시간 상한이지, 이미 빌린 커넥션의 점유 시간과 무관하다. 점유를 실제로 묶는 건 PG HTTP `read-timeout`인데 **그게 설정돼 있지 않았다**. 지금은 `payment.toss.read-timeout: 5s`(connect 2s)로 걸었고, 끊긴 호출은 TIMEOUT(=UNKNOWN)으로 복구 배치에 흐른다.
- **아직 안 잰 것**: 필요한 커넥션 수는 대략 `초당 결제 요청 × PG 응답 시간`이다. 20 TPS에 PG가 3초면 대기만으로 60개가 필요한데 풀은 그보다 작다. **PG 지연을 주입한 부하로 풀 점유를 재기 전까지는 "여유 있다"고 쓰지 않는다.**
- **단일 DB 모놀리스**라 로컬 변경의 원자성이 저비용으로 손에 들어온다. 사가로 쪼개면 그것도 포기하고 멈춘-사가 회복 경로를 새로 만들어야 하는데, 그 복구를 완성하지 못한 채 쪼개면 지금보다 나쁘다.

따라서 지금 결론은 "유지가 옳다"가 아니라 **한시적 유지**다.

외부 호출을 트랜잭션 안에 둔 위험은 처음 본 것보다 컸고, 완화책이라고 적어둔 `connection-timeout`은 그 위험을 막는 설정이 아니었다. 다만 복구 경로 없이 사가로 옮기는 것도 더 위험하다. **먼저 PG HTTP 전체 타임아웃과 호출 동시성 상한을 두고 풀 점유를 실측한 뒤, 멈춘 시도를 복구할 수 있게 되면 3단계로 옮긴다.**

## 마이그레이션 경로 (스케일이 요구하면)

트래픽이 커지거나 PG 지연이 상시화되어 커넥션 점유가 실측 병목이 되면, 3단계 사가로 이행한다:

1. **Phase 1 (짧은 tx)**: 검증 · `order.startPayment()` · 포인트 예약 · 결제 `IN_PROGRESS` 적재 → 커밋.
2. **Phase 2 (트랜잭션 밖)**: PG 승인. 커넥션을 붙잡지 않는다. (부수 효과: 결제 레코드가 PG 콜 **전에** 커밋돼 있어, 크래시-후-복구의 charge 안전성은 오히려 좋아진다.)
3. **Phase 3 (짧은 tx)**: 결과 반영. 성공이면 재고 차감·`markPaid`·이벤트 발행, 실패/미확정이면 포인트 복원·주문 복귀.
4. **추가 필수**: 멈춘 사가 회복. Phase 1과 3 사이에서 죽은 주문(포인트 예약됨 + 결제 IN_PROGRESS)을 스캔해 PG 조회로 완결하거나 예약 자원을 복원하는 배치. 이게 사가 이행의 진짜 비용이다.

이 경계 재설계는 크라운주얼(체크아웃)을 건드리고 ACID 원자성을 사가 복잡도와 맞바꾸는 **최대·최고위험 변경**이므로, 실측 병목이 확인되기 전에는 착수하지 않는다(YAGNI).

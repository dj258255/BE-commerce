# ADR-014 — 상담 초안: 포트를 먼저 만들고 모델은 나중에

- 상태: 채택 (Accepted)
- 관련: [ADR-011 타임라인 조립](ADR-011-order-timeline-assembly.md), [ADR-012 규칙 기반 원인 분류](ADR-012-rule-based-cause-classifier.md), [11 AI 운영자동화 검토](../11-AI-운영자동화-검토.md)

## 배경

[11 문서](../11-AI-운영자동화-검토.md)에서 만드는 순서를 정했다.

```
① 타임라인 조립기(AI 없음) → ② 규칙 분류기(AI 없음) → ③ CS 답변 초안(AI) → ④ 잔여 후보(AI)
```

①②는 끝났다(ADR-011, ADR-012). ③을 만들 차례인데, **모델을 부르는 코드를 지금 도메인에 박으면 안 되는 이유**가 조사 과정에서 나왔다.

## 왜 지금 모델을 부르지 않나

### 규제 — 생성형 AI는 아직 망분리 예외가 아니다

2026-04-20 시행된 **전자금융감독규정시행세칙** 개정으로, 금융회사·전자금융업자가 일정 보안 규율을 지키면 **내부 업무망에서 별도 혁신금융서비스 심사 없이 SaaS를 이용**할 수 있게 됐다.

**그런데 생성형 AI는 그 대상이 아니다.** 금융당국은 *"SaaS에 이어 향후 생성형 AI 서비스 도입 등과 관련해서도 (…) 신속히 망분리 규제 예외가 적용될 수 있도록 추진할 계획"* 이라고 밝혔다. 즉 **아직 열리지 않았고, 열릴 예정인 상태**다. 코어뱅킹 등 고객 개인신용정보를 직접 처리하는 시스템은 여전히 강한 망분리가 적용된다.

BE-commerce가 다루는 것은 주문번호·결제금액·취소이력이다. 결제 데이터를 외부 API로 내보내는 코드를 지금 도메인에 박아 두면, 규제가 열릴 때가 아니라 **지금** 문제가 된다.

### 평가 순서 — Klarna가 되돌린 이유

Klarna는 AI 상담으로 해결시간을 11분에서 2분으로 줄였다가 되돌렸다. CEO가 인정한 실패 원인은 기술이 아니라 **지표 설계 순서**였다.

> 비용이 지나치게 지배적인 평가 요소였고, 그래서 품질이 낮아졌다

업계 권고도 같다 — *"eval harness를 첫 주에 만들고, 모든 프롬프트·모델 변경을 그것으로 게이팅하라."* 모델을 고른 뒤 잣대를 만들면 **잣대가 그 모델에 맞춰 휜다.**

## 결정

**포트를 정의하고, 기본 구현은 외부 호출이 없는 템플릿으로 둔다. 평가 하네스를 모델보다 먼저 만든다.**

```
OrderTimeline + CauseSuggestion   ← 결정적으로 조립 (ADR-011, ADR-012)
        ↓
   FactPack                       ← 숫자·시각·상태만. 문장 없음
        ↓
   DraftPort                      ← 템플릿이든 모델이든 여기서 갈린다
        ↓
   NumberGuard                    ← 초안의 모든 금액·날짜를 FactPack과 대조
        ↓
   상담원이 검토·수정 후 발송      ← 초안은 고객에게 직접 나가지 않는다
```

### 새 모듈 `assist`

`allowedDependencies = { shared, timeline, reconciliation }`. timeline이 reconciliation에 의존하므로 순환은 없다.

### NumberGuard — 이 설계의 요점

모델이 지어낸 숫자는 근거 있는 숫자와 **문장에서 구별되지 않는다.** "차액 3,000원"과 "차액 3,200원"은 읽는 사람에게 똑같이 그럴듯하다. 그래서 사람 검토에 맡길 수 없다 — 검토자도 그 숫자의 출처를 모른다.

프로덕션에서 쓰이는 방식이 이것이다: **출처 시스템에서 찾을 수 없는 값을 참조하면 그 출력을 거부한다.** Uber Genie도 같은 계열로, LLM에 *"제공된 sub-context 안에서만 답하고 출처 URL을 인용하라"* 를 명시적으로 지시한다.

**검사 범위**를 금액(`원` 접미)과 날짜로 한정했다.

| | 넓히면 | 좁히면 |
|---|---|---|
| 맨 숫자까지 검사 | "항목 2개", "3일 이내" 같은 정상 초안이 대량 반려 | — |
| 금액·날짜만 (**채택**) | — | `원` 없는 지어낸 수치가 샐 수 있음 |

초안이 **실제로 주장하는 사실**이 금액과 날짜라서 이 경계로 잡았다. 모델 어댑터가 붙은 뒤 실측해서 조정할 값이다.

### 평가 하네스가 잣대인지도 검증한다

일부러 값을 지어내는 가짜 구현을 함께 돌린다. **전부 통과시키는 하네스는 잣대가 아니다.**

```
[잣대 검증]
  template                 초안 3/4 (75%)  사실정합 3/3 (100%)
  fixture:invents-amount   초안 3/4 (75%)  사실정합 0/3 (0%)
      └ 승인만: [출처에 없는 금액: 270원]
  fixture:invents-date     초안 3/4 (75%)  사실정합 0/3 (0%)
      └ 승인만: [출처에 없는 날짜: 2026-01-01]
```

## 그 뒤에 실제로 만든 것 (2026-08-30 갱신)

이 ADR 을 쓸 때는 포트와 검증기까지였다. 실데이터를 흘리고 실제 모델을 붙이면서
구성이 늘었다. **결정은 그대로고, 늘어난 것은 그 결정을 따른 결과다.**

| 클래스 | 하는 일 | 왜 필요했나 |
|---|---|---|
| `PromptBuilder` | 프롬프트를 어댑터 밖에 둔다 | 어댑터마다 두면 모델을 바꿨을 때 **모델 탓인지 프롬프트 탓인지** 알 수 없다 |
| `CustomerGlossary` | 내부 용어 → 고객 표현 + 누출 탐지 | 모델이 `PAID`, `AMOUNT_MISMATCH`를 고객 문장에 그대로 썼다 |
| `ShadowDraftRecorder` | 초안을 만들되 **보여주지 않고 기록만** | 보여주면 앵커링이 생겨 "고칠 게 없었다"와 "고칠 생각이 안 났다"가 구분 안 된다 |
| `OllamaDraftAdapter` | 로컬 모델 | 생성형 AI는 아직 망분리 예외가 아니다 — 데이터가 기계 밖으로 안 나간다 |
| `AnthropicDraftAdapter` | 외부 모델 (BYOK) | 규제가 열릴 때를 위해. 키는 **운영자가** 넣는다 |
| `BlindReview` 외 4종 | 초안이 **쓸 만한지** 재는 3단계 절차 | 검증 통과·용어 0%는 "보낼 만하다"는 뜻이 아니다 |
| `TemplateDraftAdapter` | provider 와 무관하게 **항상 빈** | 폴백이자 **대조군**이다. 모델을 켜도 편집률을 맞댈 상대가 있어야 한다 |

### 검증기의 계약을 고쳐 적는다

원래 이 문서는 검증기를 *"타임라인에 있는 숫자만 쓰게 한다"* 로 설명했다. **틀렸다.**

> **"코드가 낸 숫자만 쓰고, 모델이 지어낸 숫자는 쓰지 마라."**

분류기가 계산한 근거(`차액 8,888원`), 사실 문장 속 금액(`내부 10,000 / 외부 9,730`),
사실 문장 속 날짜(에스크로 해제 예정일) — 전부 **코드가 만든 값**이므로 통과해야 맞다.
이걸 좁게 잡아서 실측에서 **4건 중 2건이 오반려**됐고, 하필 확신이 가장 높은 규칙과
초안이 가장 필요한 건이 걸렸다. 자세한 경과는 [13 상담초안 실측](../13-상담초안-실측.md).

### 블라인드 리뷰를 쌍 비교로 넓힌다

원래 이 절차는 초안 **하나**를 공개하고 그것을 고치게 했다. 그런데 활성화 조건 1번이
"편집률 중앙값이 **템플릿보다** 낮을 것"이라, 맞댈 상대가 같은 표본에 있어야 한다.

`draft-provider`를 바꿔 두 회차로 도는 방법은 **안 된다.** 두 번째 회차는 리뷰어가 이미
답을 아는 상태이고, 그건 이 절차가 엔티티로 막아 둔 바로 그 오염이다. 회차 안에서는
순서를 강제하면서 회차 사이로 새게 두면 막은 것이 아니다.

그래서 **한 번의 블라인드 답에 초안 둘을 붙인다.**

| 규칙 | 왜 |
|---|---|
| 공개 시 템플릿·모델을 **같은 사실에서 같은 시점에** 고정 | 모델은 매번 다르게 쓴다. 다시 뽑으면 사람이 본 것과 다른 문장을 채점한다 |
| 화면에는 **A·B 로만**. 어느 쪽이 모델인지 서버가 안 내보낸다 | 알면 "모델이니까 잘 썼겠지"가 편집량에 섞인다 |
| 표시 순서를 **건마다 뒤집는다** | 항상 같은 쪽이 먼저면 먼저 본 것에 기준이 생긴다 |
| 쌍 비교는 **둘 다 고친 건**에서만 | 한쪽만 있는 건을 섞으면 두 중앙값이 서로 다른 표본에서 나온다 |
| 표본이 없으면 **판정하지 않는다**(`null`) | `false`로 내면 안 잰 것과 못 넘은 것이 같아 보인다 |

경로도 `/edited/a` · `/edited/b` 다. `/edited/model`로 두면 개발자 도구를 연 순간
눈가림이 풀린다.

### 숫자와 용어를 같은 잣대로 다루지 않는다

| | 지어낸 숫자 | 내부 용어 누출 |
|---|---|---|
| 성격 | **사실이 틀림** | 틀린 게 아님 |
| 상담원이 고칠 수 있나 | 못 고침 (출처를 모름) | **고칠 수 있음** |
| 처리 | **초안을 버린다** | **표시하고 센다** (`CsDraft.jargon`) |

같은 잣대로 버리면 쓸 만한 초안까지 사라진다. 세는 이유는 프롬프트를 고쳤을 때
나아졌는지 알기 위해서다.

### 모듈 순환을 이벤트로 끊었다

섀도 기록은 **확정 시점**에 일어나야 하는데, `assist`가 이미 `reconciliation`을 의존한다.
반대로 부르면 순환이다. `ReconciliationResolvedEvent`를 발행하고
`assist`가 `AFTER_COMMIT`으로 듣는다 — 대사는 "확정됐다"고 알릴 뿐 누가 듣는지 모른다.
커밋 뒤라 초안 생성이 느리거나 실패해도 확정은 이미 끝나 있다.

### 실측 결과 요약

| | 초기 | 최종 |
|---|---|---|
| 검증 통과율 (템플릿, 실데이터 4건) | 50% | **100%** |
| 검증 통과율 (Qwen3 8B, 12회) | 58% | **100%** |
| 내부 용어 누출 | 발생 | **0%** |
| 초안 생성 지연 중앙값 | — | **8.8초** (프롬프트 확장 후) |

**"상담 시간 N% 단축" 같은 수치는 없다.** 상담원이 없으니 잴 수 없다.

## 구독으로는 안 되지만, 쓸 방법은 있다 (2026-08-31 추가)

"구독하고 있으니 그걸로 쓰게 해달라"는 요청을 받았다. **앱이 구독으로 모델을 부르는 것은 안 된다** —
유료 구독은 채팅 앱과 CLI 를 커버하지 **API 접근을 포함하지 않고 별도 과금**이다.

**그런데 목적은 다른 방법으로 이룰 수 있다.** 알고 싶은 것은
"더 좋은 모델이 어떤 초안을 쓰는가"이고, 그걸 보는 데 **앱이 직접 호출할 필요는 없다.**

```
GET  /api/v1/admin/orders/{orderNo}/cs-draft/prompt     ← 프롬프트를 그대로 꺼낸다
POST /api/v1/admin/orders/{orderNo}/cs-draft/imported   ← 받아온 초안을 되돌린다
```

꺼내서 어디서든 돌리고 되돌리면 **같은 검사**를 태운다 — 숫자 검증, 용어 사전, 루브릭,
(켜져 있으면) 다른 계열 심판까지. **앱에 키를 넣지 않고도 모델을 비교할 수 있다.**

**같은 잣대를 태우는 것이 요점이다.** 안 그러면 "저 모델이 더 잘 쓰더라"가 인상으로만 남는다.
이 프로젝트에서 인상이 틀린 적이 여러 번 있었다 —
편향된 기준으로 8B 와 14B 를 비교해 결론이 뒤집힐 뻔했고(실험 6),
루브릭이 물러서 96% 만점을 성과로 적을 뻔했다(실험 7).

**저장하지 않는다.** 이 경로는 비교용이지 업무 경로가 아니다. `source`를 필수로 받아
`manual:<라벨>`로 표시한다 — 출처 없는 초안을 만들지 않는다.

**데이터는 앱이 내보내지 않는다.** 다만 꺼낸 프롬프트에 주문번호·금액·거래일이 들어 있고,
그걸 어디에 붙여 넣는지는 **꺼낸 사람의 책임**이다. 그 사실을 메서드 주석에 적어뒀다.

### 외부 어댑터의 구멍도 같이 막았다

키 없이 확인할 수 있는 것부터 봤더니 두 개가 비어 있었다.

- **테스트가 하나도 없었다** — 외부 API 응답 모양을 흉내내는 서버로 9건을 고정했다
- **`revise()`가 없었다** — 포트 기본 구현이 빈 값이라, 프로바이더를 그쪽으로 바꾸면
  **2단계 수정이 아무 오류 없이 멈춘다.** 루브릭이 4.10 으로 돌아가는데 로그에는 아무것도 안 남는다

두 번째가 포트에 기본 구현을 둔 대가다. **어댑터를 늘릴 때마다 여기를 같이 봐야 한다.**

## 트레이드오프

| | 지금 모델 붙이기 | **포트 + 템플릿 (채택)** | 로컬 Ollama |
|---|---|---|---|
| 규제 | **현행 망분리 예외 대상 아님** | 외부 호출 없음 | 외부 호출 없음 |
| 문장 품질 | 높음 | 낮음(사실 나열) | 중간 |
| 잣대 | 모델에 맞춰 휨 | **먼저 고정** | 먼저 고정 |
| 운영 비용 | 토큰 과금 | 0 | GPU/메모리 |
| 나중 전환 | — | 어댑터 1개 추가 | 어댑터 1개 추가 |

템플릿을 "임시물"로 두지 않은 이유는 두 가지다. **기준선** — 모델이 붙었을 때 "얼마나 나아졌나"를 잴 상대가 필요하다. **폴백** — 모델이 죽거나 검증에 걸렸을 때 상담원이 빈 화면을 보면 안 된다.

Spring AI가 같은 형태를 표준으로 제공한다는 점도 확인했다. `ChatModel`/`ChatClient` 뒤에서 OpenAI·Anthropic·로컬 Ollama가 **의존성과 설정만 바꿔** 교체되고 비즈니스 로직은 그대로다. 우리 `DraftPort`는 그보다 좁은(초안 생성 한 가지) 포트라 어댑터가 Spring AI를 쓰든 직접 호출하든 상관없다.

## 기대치 — 절반쯤 맞는다

| 사례 | 성능 |
|---|---|
| Uber Genie | 도움률 **48.9%** (70,000+ 질문, 13,000 엔지니어링 시간 절감) |
| Meta 인시던트 RCA | 근본원인이 **상위 5개 안에 42%** |
| Zalando 사후분석 | 최신 모델도 **표면적 귀인오류 ~10%** |

"알아서 다 해준다"는 사례는 없었다. **이 전제로 설계했다** — 그래서 초안이지 답변이 아니고, 검증에 걸리면 버린다.

## 하지 않는 것

- **초안을 고객에게 직접 보내지 않는다.** 상담원이 검토·수정 후 발송한다. 토스뱅크 상담 어시스턴트도 같은 형태다 — 실시간 요약과 **응답 초안**을 상담원에게 제공한다
- **초안이 대사 결과를 바꾸지 않는다.** `assist`는 읽기 전용이다. 쓰기를 붙이면 사람 확인 원칙(ADR-008)을 우회하는 뒷문이 된다
- **검증 실패 초안을 "참고용"으로 보여주지 않는다.** 사람은 눈앞의 문장에 끌려가고(앵커링), 틀렸다는 걸 확인할 방법은 없다

## 다음에 열어야 할 것

1. ~~**모델 어댑터**~~ — **했다.** 로컬(Ollama)은 규제와 무관하므로 붙여서 실측까지 마쳤고,
   외부(Anthropic)는 어댑터와 배관만 만들고 **켜지 않았다**. 예상대로 나머지는 그대로였다 —
   `DraftService`·`NumberGuard`·화면·하네스 중 바뀐 것이 없다
2. ~~**블라인드 리뷰**~~ — **수단은 만들었다**(V26, `assist.review`). 사실만 보고 먼저 쓰게 하고
   그 뒤 초안을 공개해 편집 거리를 잰다. **엔티티가 순서를 강제**하고 서버가 초안을 안 보낸다.
   **아직 표본이 없다** — 사람이 앉아서 써야 하고, 그 사람이 상담원이 아니라는 한계는 남는다
3. **④ 잔여 원인 후보** — ②가 못 가른 것만. `resolveNote` 실데이터가 쌓인 뒤

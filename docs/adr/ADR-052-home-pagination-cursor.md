# ADR-052. 홈 다음 쪽은 커서가 보여 준 것을 들고 다니고, 순서는 요청 시점의 세션이 정한다

- 상태: **채택**
- 날짜: 2026-09-24
- 관련: `HomeCursor`, `HomeComposer#composeNext`, `ProductCatalogFacts#newestInCategory`,
  [실측](../performance/home-pagination.md), 이슈 #237

## 맥락

Netflix GenPage 는 홈을 몇 행씩 나눠 만들고, 다음 쪽을 만들 때 **앞에서 보여 준 행과 그 사이의 세션 활동**을 입력에 붙인다.
이 저장소의 홈은 한 번에 세 행을 만들고 끝났다. 내려도 볼 것이 없고, 보는 동안 한 행동이 화면에 반영되지 않았다.

## 결정

- `GET /api/v1/personalization/homepage?cursor=` — 1쪽은 전과 같고 응답에 `page`·`nextCursor` 가 붙는다(필드 추가라 기존 소비자는 그대로다)
- 2쪽부터는 **대분류별 인기 행**이다. 대분류 순서는 **그 요청 시점에 다시 읽은** 최근 활동이 먼저, 나머지는 인기 표 순서다
- 세션이 순서를 정한 행은 `CATEGORY_POPULAR_SESSION` 으로 표시한다 — 응답만 보고 세션이 작동했는지 안다
- 인기 표에 모자란 대분류는 그 대분류의 신상품으로 채운다(`reason` = "대분류 신상품")
- **커서가 보여 준 상품과 시도한 행을 들고 다닌다.** 서버에 쪽 상태를 두지 않는다

## 판단: 쪽 상태를 어디 두나

| 안 | 얻는 것 | 잃는 것 |
|---|---|---|
| 서버(Redis)에 저장 | 커서가 짧다 | 쪽마다 Redis 쓰기. TTL 이 지나면 중복이 돌아온다. Redis 장애가 홈 아래쪽을 건드린다. 인스턴스가 같은 상태를 봐야 한다 |
| **커서에 싣는다** | 서버 상태가 없다. 어느 인스턴스로 가도 같은 답 | 커서가 쪽마다 커진다(실측 120 → 395자). 클라이언트가 고칠 수 있다 |

커서를 골랐다. 대분류가 5개라 쪽이 3쪽에서 끝나고, 상한 4,096자는 약 10쪽 분량이다. 클라이언트가 커서를 고쳐서 얻는 것은
**자기 화면의 중복**뿐이라 서명하지 않았다. 모양이 틀리거나 너무 긴 커서는 400 이다.

## 실측 (기준은 이슈에 측정 전에 적었다)

| | 결과 | 기준 |
|---|---|---|
| 커서 있을 때 쪽 사이 중복 | 0건(30명) | 0 |
| 커서 없을 때 2쪽 중복 | 평균 8.6개 | 대조군 |
| 세션 반영(IN_PROCESS 기본값) | 대기 0ms 96.7% · 50ms 100% | 90% 이상 |
| 다음 쪽 p95 | 81~86ms | 기록 |

1차에서는 기준을 못 넘었다. 원인 둘 가운데 하나가 설계 결함이었다: 인기 표에 아동복이 0개라, 사용자가 아동복을 봐도
행이 서지 않고 **세션 신호가 조용히 버려졌다.** 신상품으로 채우는 처방을 넣고 다시 쟀다.

## 대가 (정직하게)

- 다음 쪽 p95 가 54ms → 81~86ms. 신상품 채우기 조회가 붙었다
- 신상품으로 채운 행은 "인기"가 아니다. 행 제목은 "○○ 인기"로 같고 항목 `reason` 만 다르다
- 대분류 5개라 3쪽에서 끝난다
- 모델이 행을 만들지 않는다 — 대분류 순서는 규칙이다. 모델이 행을 생성하는 것은 #238(ADR-053)

## 다시 볼 조건

- 중분류 행을 넣어 쪽이 10쪽을 넘게 되면 커서 상한과 크기를 다시 본다
- 커서 조작이 중복 이상의 피해를 낼 수 있게 되면(예: 커서로 노출 기록을 조작) 서명한다

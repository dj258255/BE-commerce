# ADR-066. 홈 다음 쪽의 GenPage 입력은 추천 행과 같은 이력을 따르고, 구매를 쓸 때는 구매만 넣는다

- 상태: **채택**(경로). 전체 기본값(`model.kind=stub` · `history-source=activity`)은 그대로다. `history-source=purchases` 이거나 `rec-history` 실험군일 때만 뜻이 있다
- 날짜: 2026-09-24
- 관련: `RecommendationFacts.pageHistory`, `RecommendationService.purchaseHistoryForModel`, `HomeComposer.composeNext`,
  [리포트](../../personalization/docs/runs/20260924-genpage-next-page/report.md), [ADR-060](ADR-060-genpage-serves-purchases.md), [ADR-061](ADR-061-ab-assignment-and-attribution.md), 이슈 #270

## 맥락

ADR-060 으로 추천 행은 구매 이력을 모델에 넣을 수 있게 됐지만, 홈 2쪽부터는 세션의 조회·클릭 8개를 GenPage `/page` 에 넣었다.
GenPage 는 구매 시퀀스로 학습했으니 이 경로는 학습과 입력이 달랐다(ADR-060 의 "다시 볼 조건"). 한편 2쪽을 설계한 이유 하나가
"1쪽 이후 본 것을 반영한다"(#237)였다. 구매만 넣으면 그 반영이 사라질 수 있어서, 세션을 구매 앞에 붙이는 절충도 같이 쟀다.

## 판정 기준 (이슈 #270 에 측정 전에 적었다)

- 배선: 앱의 2쪽이 엔진을 같은 입력으로 직접 부른 값과 대분류 순서·항목 모두 99% 이상 같다
- 2쪽 p95 ≤ 300ms
- V2(세션 + 구매)의 recall 이 V1(구매)의 0.95배 이상이고 세션 반영이 20%p 이상 높으면 V2, 아니면 V1. 고른 쪽이 V0(세션)보다 recall 이 낮으면 기본을 바꾸지 않는다

## 결과 (대입, 과거 구매가 있는 1,000명)

| | recall@2쪽 | 세션 반영 | 2쪽 p95 |
|---|---:|---:|---:|
| V0 세션(지금) | 0.0013 | 75.0% | 79ms |
| V1 구매 | **0.0251** | 0.0% | 86ms |
| V2 세션 + 구매 | 0.0191(V1 의 0.76배) | 12.8% | 88ms |

배선은 순서·항목 1,000/1,000 일치. V2 는 두 조건 모두 못 넘어 V1 이다.

## 결정

- **모델 입력은 추천 모듈이 고른다.** 홈은 사용자 id 와 세션만 넘긴다(`generatePageRows(userId, session, …)`). 추천 행과 같은 규칙(설정 또는 실험군)으로 구매를 쓸지 정한다 — 한 사용자의 두 경로가 다른 입력을 쓰면 실험 변형이 무엇인지 흐려진다
- 구매를 쓰는 사용자의 2쪽은 **구매만** 넣는다(`app.recommendation.page-history=purchases`, 기본)
- 세션을 앞에 붙이는 변형(`session-then-purchases`)은 설정으로 남긴다. 켜지 않는다
- 모델이 꺼져 있으면 구매를 읽지 않는다

## 버린 것

| 안 | 이유 |
|---|---|
| 세션을 구매 앞에 붙이기(V2) | recall 을 24% 잃고 세션 반영은 12.8% 만 살렸다. 조회 한 건이 구매 수십 건 뒤에 붙으면 모델이 거의 따르지 않는다 |
| 세션 그대로(V0) | 세션 반영 75% 를 지키지만 2쪽이 홀드아웃 구매를 거의 못 맞힌다(0.0013). 조회 한 건으로는 이 사람이 무엇을 살지 모른다 |
| 홈이 직접 구매를 읽기 | 입력 결정이 두 모듈로 갈라진다. 실험군 판정을 홈이 따로 해야 한다 |

## 대가 (정직하게)

- **2쪽이 세션을 따르지 않는다.** 구매를 쓰는 사용자는 1쪽 이후 무엇을 봐도 2쪽 모델 행의 순서가 바뀌지 않는다(규칙 행으로 물러설 때는 여전히 세션을 따른다)
- 과거 구매가 없는 사용자는 빈 이력으로 생성한다. 세션으로 물러서지 않는다. 재지 않았다
- 평가 사용자의 구매는 H&M 거래를 심은 것이고, 조회는 대분류마다 고정한 상품 한 건이다. 실제 세션은 더 길다
- 2쪽 요청마다 주문 표를 한 번 더 읽는다(추천 행과 같은 쿼리, 최근 100건)

## 측정 중에 버린 두 실행

하네스가 세션을 제대로 지우지 못한 채 두 번 돌았다. 첫 번째는 `user_activities` 를 지우지 않아 조회가 409 로 거절됐고, 두 번째는
세션을 도커 Redis 에서 지웠는데 앱은 같은 포트의 로컬 redis-server 에 붙어 있었다. 두 번 다 숫자는 그럴듯했다(두 번째는 "세션 반영 0%").
이제 하네스는 시작 전에 세션이 비었는지 API 로 확인하고, 조회가 하나라도 기록되지 않으면 멈춘다. 자세한 것은 리포트에 있다.

## 다시 볼 조건

- A/B(트러블슈팅 기록 열린 항목 5)에서 2쪽 클릭이 대조군보다 낮으면 → 세션을 어떻게 섞을지 다시 잰다(예: 세션 대분류를 행 순서에만 쓰기)
- 구매가 없는 사용자가 많아지면 → 빈 이력 대신 세션으로 물러서는 규칙을 잰다
- 조회·클릭으로 다시 학습한 모델이 생기면 → V0 을 다시 잰다

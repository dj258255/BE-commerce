# ADR-004. 재고 차감은 조건부 UPDATE 전략을 쓴다

- 상태: 채택 (Accepted)
- 날짜: 2026-07-06
- 관련: [ADR-003](ADR-003-stock-deduction-timing.md), Phase 5(성능)

## 요약

**지금 유효한 결정**

- 재고 차감의 기본 전략은 조건부 UPDATE이다.
- `CheckoutService`가 승인 성공 시 `StockDeductionService.deductConditional`을 호출한다.
- 재고는 한 행(A)으로 유지한다.
  → 동시성 20에서 초당 301건으로 기준 300건을 넘었다(아래 경과 2026-09-27).
- 운영 기본값은 바꾸지 않는다.
  → 초당 1,000건 후보로는 UNIT REPEATABLE READ를 두었다(아래 경과 2026-11-19).
- 세 전략 구현(`StockDeductionService`)은 비교 근거로 코드에 남긴다.

**대가**

- 재고 행 잠금이 커밋까지 풀리지 않아 한 행의 상한은 대략 1초 ÷ 잠금 유지 시간이다.
- 재고 200에 고객 1,000명이 순서대로 시도하면 먼저 온 200명 중 146명만 샀다(아래 경과 2026-11-19).

**다시 볼 조건**

- 결제 확정이 한 상품에 초당 100건을 넘게 몰리는 행사가 생기면 순서 바꾸기(B)와 칸 나누기를 다시 본다.
- 멀티 인스턴스에서 DB 부하를 분산해야 하면 Redis 분산락(Redisson)을 추가로 고려한다.

**기각한 것**

- 낙관적 락은 한 행에 쓰기가 몰리는 hot row에 부적합해 쓰지 않는다.
- 비관적 락은 차감 전후에 여러 읽기와 계산이 필요한 시나리오에서만 가치가 있어 단순 차감에는 쓰지 않는다.

## 맥락

재고 차감은 동시 요청이 몰리는 지점이다(선착순·인기 상품). 음수 재고·초과 판매(oversell)를 막으면서 성능도 지켜야 한다. 후보 3종:

- **비관적 락**: `SELECT ... FOR UPDATE`로 행을 잠그고 차감
- **낙관적 락**: `@Version` + 충돌 시 재시도
- **조건부 UPDATE**: `UPDATE ... SET quantity = quantity - :n WHERE quantity >= :n` (락 없이 원자적)

## 실험

두 환경에서 쟀다. `StockLockComparisonTest`(H2 인메모리)는 CI에서 매번 같은 결과가 나오는
**안전 불변식 검사**로 남기고, `StockLockComparisonMySqlTest`(Testcontainers MySQL 8.4)가 **성능 수치**를 낸다.
인메모리에는 네트워크 왕복도 디스크도 없어 재시도가 사실상 공짜라, 낙관적 락에 유리하게 기우는 조건이기 때문이다.

### 실 MySQL 8.4 (InnoDB): 30스레드가 재고 20에 동시 차감, 워밍업 후 5회 중앙값

| 전략 | 초과판매 | 완판 | 소요(중앙값) | 범위 |
|---|---|---|---|---|
| **조건부 UPDATE** | 0 | 20/20 | **40ms** | 24~49ms |
| 비관적 락 | 0 | 20/20 | 75ms | 59~144ms |
| 낙관적 락 | 0 | 20/20 | 151ms | 99~165ms |

### 고경합: 같은 조건에서 스레드만 150으로

| 전략 | 초과판매 | 완판 | 소요(중앙값) | 범위 |
|---|---|---|---|---|
| **조건부 UPDATE** | 0 | 20/20 | **79ms** | 66~110ms |
| 낙관적 락 | 0 | 20/20 | 429ms | 298~451ms |

세 전략 모두 **안전**(초과판매 0, 최종재고 = 재고 − 성공)했다. 차이는 성능이다.

- **조건부 UPDATE가 최속**(40ms). 락도 재시도도 없이 DB 한 번의 원자적 UPDATE로 끝난다.
- **낙관적 락이 최저속**(151ms). 충돌마다 조회와 갱신을 다시 왕복하는데, 실 DB에서는 그 왕복이 실제 비용이다.
  H2에서는 이 왕복이 거의 공짜라 낙관적(17ms)이 비관적(32ms)보다 빨랐는데 **실 InnoDB에서 순위가 뒤집혔다.**
  측정 환경이 결론을 바꾼 사례다.
- 비관적 락은 중간(75ms). 한 번 줄을 서면 왕복이 한 번뿐이라 재시도보다 싸다. 다만 커넥션을 트랜잭션 동안 점유한다.
- **고경합에서 격차가 벌어진다.** 150스레드에서 조건부 79ms vs 낙관적 429ms(**5.4배**). 재시도 상한 50회 안에서는
  미달판매까지 가지 않았지만, 그 상한을 지키느라 지연이 그만큼 늘었다. 한 행에 쓰기가 몰리는 hot row에
  낙관적 락이 부적합하다는 결론은 같다.
- 데드락 0건, 락 대기 타임아웃 0건. 단일 행 경합이라 대기 그래프가 선형이다.

## 결정

기본 전략으로 **조건부 UPDATE**를 채택한다. `CheckoutService`가 승인 성공 시
`StockDeductionService.deductConditional`을 호출한다.

## 근거 / 트레이드오프

- 단일 자원(재고 행) 차감에는 조건부 UPDATE가 가장 저비용·안전하다.
- 비관적 락은 "차감 전후에 여러 읽기/계산이 필요"한 복잡한 시나리오에서만 가치가 있다. 단순 차감엔 과하다.
- 낙관적 락은 충돌이 드문 자원(사용자별 포인트 등)에 적합하다. 인기 상품 재고처럼 한 행에 몰리는 hot row에는 부적합.
- **멀티 인스턴스에서 DB 부하를 분산**해야 하면 Redis 분산락(Redisson)을 추가로 고려한다(확장 08 문서). 이 프로젝트는 단일 DB 기준으로 조건부 UPDATE가 정답.

## 후속

- 세 전략 구현(`StockDeductionService`)은 비교 근거로 코드에 남겨 둔다.
- 실제 애플리케이션 레벨 부하테스트(k6)는 `docs/performance/`에 방법론과 스크립트로 정리한다.

## 경과

처음 결정 뒤에 이어진 측정과 바뀐 결정을 적은 순서대로 둔다.

### 2026-09-27 한 행이 초당 몇 건까지 버티는가 (#384)

위 실험은 재고 20개를 다 파는 시간(40 · 79ms)만 쟀고 한 행의 처리량 상한은 재지 않았다. 결제 확정(`CheckoutTx.settle`)은 재고 행을 조건부 UPDATE 로 잠근 뒤 같은 트랜잭션에서 주문 상태 변경 · 포인트 적립 · 이벤트 발행 기록을 쓰고 커밋한다. **재고 행 잠금은 커밋까지 풀리지 않으므로** 한 행의 상한은 대략 1초 ÷ 잠금 유지 시간이다.

`HotRowThroughputExperimentTest`(실 MySQL 8.4, `innodb_flush_log_at_trx_commit=1`)로 뒤따르는 쓰기 3건을 같은 개수로 흉내 내 재고를 넉넉히 두고 5초씩 3회 잰 중앙값이다. Shopify 가 한정 판매의 재고 한 행 경합을 단위당 행과 `SKIP LOCKED` 로 푼 것과 대조하려고 쟀다.

| 모양 | 동시성 20 초당 처리량 | 지금 대비 | 잠금 유지 p50 | 완판 검사(재고 200, 64스레드) 데드락 | 한 건 팔 때 UPDATE 수 |
|---|---:|---:|---:|---:|---:|
| **A 지금: 재고 UPDATE → 쓰기 3건 → 커밋** | **301** | 1.0 | 2.99ms | 0 | 1.32 |
| B 쓰기 3건 → 재고 UPDATE → 커밋 | 444 | 1.47 | 1.86ms | 0 | 1.32 |
| C4 재고를 4칸으로, 임의 칸부터 | 718 | 2.4 | 4.74ms | 230 | 2.28 |
| C16 재고를 16칸으로 | 1,245 | 4.1 | 7.43ms | 1,181 | 6.18 |

한 건 팔 때 UPDATE 수에는 매진 뒤 스레드마다 한 번씩 실패한 시도가 들어 있다. 네 모양 모두 초과 판매 0, 팔지 못한 재고 0 이었다.

- **A 는 동시성 4 에서 이미 초당 281건이고 20 · 64 에서도 290~301건에 머문다.** 동시성을 올리면 처리량은 그대로이고 p50 지연만 13ms → 64ms → 210ms 로 는다. 한 행 앞에서 줄을 선다
- **순서를 바꾸면(B) 잠금 시간이 3.0ms → 1.9ms 로 준다.** 남은 1.9ms 는 거의 커밋의 로그 fsync 다. 순서를 바꿔도 한 행의 상한은 초당 약 540건(1 ÷ 1.86ms)을 넘지 못한다
- **칸으로 나누면 처리량은 칸 수만큼 가깝게 는다.** 대가는 매진 직전이다. 빈 칸을 지나가는 트랜잭션이 여러 행을 잠그고 시작 칸이 제각각이라 서로를 기다린다. 16칸에서 재고 200 을 파는 동안 데드락 1,181건, 한 건에 UPDATE 6.18번이었다. 전체 선착순도 깨진다(먼저 온 사람이 빈 칸에 걸려 늦게 온 사람보다 늦을 수 있다)

**결정: 한 행(A)을 유지한다.** 측정 전 기준은 "동시성 20(커넥션 풀 크기)에서 초당 300건 이상이면 유지"였고 301건이었다. 대기열 실험(#383)의 수요가 초당 100명 도착이고 결제 확정까지 가는 것은 그보다 적어 3배 여유가 있다.

**다만 경계에서 통과했다.** 가장 낮은 회차는 288건이었고, 실제 `settle` 은 JPA 플러시와 이벤트 기록을 더 하므로 잠금 시간이 이 실험보다 길 수 있다. 결제 확정이 한 상품에 초당 100건을 넘게 몰리는 행사가 생기면 다음 순서로 다시 본다.

1. B(순서 바꾸기): 스키마 변경 없이 1.47배. 재고 부족이면 앞의 쓰기를 되돌려야 해서 확정 트랜잭션의 모양이 바뀐다
2. 칸 나누기: 칸을 도는 순서를 고정(0번부터)하면 데드락은 줄지만 앞 칸에 다시 몰린다. `READ COMMITTED` 로 빈 칸의 잠금을 바로 놓게 하는 것(Shopify 가 예약 테이블의 갭 락 데드락을 피한 방법)과 같이 재야 한다

재현: `./gradlew -p commerce experimentTest --tests '*HotRowThroughput*'`(약 7분). 원자료: [`performance/raw/20260927-h384-hotrow/`](../performance/raw/20260927-h384-hotrow/)

### 2026-09-28 초과 판매 뒤 사후 정정 대 조건부 UPDATE (26절③, AWS DynamoDB 카운터 패턴, #412)

위 실험은 전부 "쓰기 시점에 정확히 막는" 전략끼리 비교였다. 이 절은 반대 축을 본다 — <b>쓰기 시점에 안 막고(느슨한 카운터, Redis `DECR`) 나중에 정정</b>하면, 지금 기본(조건부 UPDATE)보다 처리량이 느는지, 그 대가(초과 판매·취소 건수)는 얼마인지. `StockLockComparisonMySqlTest`와 같은 방법론(스레드 동시 출발, `SharedContainers`의 실 MySQL·Redis, 5회 중앙값)을 쓴다.

**판정 기준은 측정 전에 [이슈 #412](https://github.com/dj258255/BE-commerce/issues/412)에 적었다.** 재고 20 · 스레드 150(고경합, ADR-004 위 실험의 `HIGH_THREADS`와 동일).

| 지표 | 조건부 UPDATE(MySQL) | 느슨한 카운터(Redis DECR) |
|---|---:|---:|
| burst 중앙값(5회) | 34~35ms | 9~12ms |
| 정정 전 성공(예약) | 20 | 150(무조건 예약) |
| 정정 전 초과 판매 | 0 | 130 |
| 정정 후 초과 판매 | 0(해당 없음) | 0 |
| 취소 건수 | 0 | 130 |

**가설 판정 — 넷 다 맞았다.**

1. **맞았다.** 느슨한 카운터(burst) 중앙값이 조건부 UPDATE보다 짧았다(9~12ms 대 34~35ms, 약 65~74% 감소). 두 전략 모두 같은 행(조건부 UPDATE) 또는 같은 키(Redis)에 원자적으로 접근해 동시성 150에서도 직렬화되지만, Redis `DECR`는 MySQL 행 락 획득 · 트랜잭션 커밋 · `innodb_flush_log_at_trx_commit=1`의 디스크 fsync가 없어 건당 비용이 훨씬 낮다.
2. **맞았다.** 느슨한 카운터는 정의대로 150건 전부 무조건 예약돼 정정 전 초과 판매가 150−20=130건 났다. 조건부 UPDATE는 항상 0건(기존 테스트가 이미 보장하는 불변식).
3. **맞았다.** 사후 정정(가장 늦게 들어온 예약부터 초과분만큼 취소)을 적용하자 재고 정확히 0 · 초과 판매 0으로 수렴했다 — 조건부 UPDATE와 같은 최종 결과다.
4. **맞았다.** 취소 건수(130)가 정정 전 초과 판매(130)와 정확히 일치했다 — "정정이 실제로 일어났다"는 카운터 증거.

**정리.** 느슨한 카운터+사후 정정은 burst 처리량에서 확실히 이득이다. 다만 이 이득은 <b>"쓰기 경로에서 검증을 미룬다"</b>는 선택 자체의 대가를 동반한다 — 이번 조건(재고 20, 스레드 150)에서는 예약의 87%(130/150)가 나중에 취소 대상이었다. 실서비스에 적용하려면 취소된 고객에게 알리고 보상하는 절차(쿠폰·우선순위 재구매권 등)가 필요하고, 그 비용이 이 실험 범위 밖이다. 이 패턴은 <b>초과 예약률이 낮게 유지되는 상황</b>(수요가 재고를 크게 넘지 않는 평시)에서 burst 구간의 지연을 줄이는 용도에 맞지, 이번 실험처럼 수요가 재고의 7.5배(150/20)인 극단적 한정 판매에는 안 맞는다 — 취소 대상이 다수가 되어 "일단 성공"이라는 사용자 경험 자체가 무의미해진다.

**정정 순서(늦게 들어온 것부터 취소)를 고른 이유.** 먼저 예약을 완료한 고객이 취소당하면 "확정됐다고 믿은 것"이 뒤집히는 비용이 더 크다고 판단했다 — 선착순 원칙과도 맞는다. 대안(무작위 취소, 금액 낮은 순 취소)은 비교하지 않았다.

**일부러 하지 않은 것.** 이 실험은 재고·Redis 카운터·정정 로직만 격리해 쟀다(`StockLockComparisonMySqlTest`와 같은 스코프) — 실제 체크아웃·결제·환불 경로에는 연결하지 않았다. 취소된 예약을 실제 주문 취소·환불로 이어붙이는 것, 정정 주기(즉시 대 배치)의 지연 대가, 초과 예약률을 낮추는 다른 방법(예: 재고의 90%까지만 느슨하게 팔고 나머지는 조건부로 전환)은 범위 밖이다.

재현: `TESTCONTAINERS_RYUK_DISABLED=true ./gradlew -p commerce integrationTest --tests '*StockLooseCounterReconciliation*'`(약 10초, 로컬 Docker Desktop에서 Ryuk 컨테이너가 소켓 마운트 오류로 못 뜨면 이 환경변수로 우회한다 — CI 러너에서는 필요 없다).

### 2026-11-19 인기 상품 재고를 초당 1,000건으로 올리려면 무엇을 버리나 (#472)

위 두 절은 "한 행으로 버틸 수 있나"와 "Redis로 먼저 팔고 나중에 고치면 얼마를 취소하나"를 쟀다. 한 행은 초당 301건으로 기준을 1건 차이로 넘었고, 그 너머는 비워 뒀다. 행사 하나가 한 상품에 초당 1,000건을 요구하면 어떤 방식이 그 수를 내는지, 그리고 그 방식이 무엇을 대가로 내는지 이 절에서 잰다.

같은 자리에서 현업은 서로 다른 것을 버렸다.

- Shopify, "We replaced Redis with MySQL for inventory reservations"(2026-05): 판매 단위마다 행을 두고("one row per sellable unit") `SKIP LOCKED`로 잠기지 않은 행을 집는다. 가용 행은 품목 · 로케이션 조합당 1,000개로 묶고 비면 재고 원장에서 채운다. 버린 것은 행 수와 채우는 비용이다
- 京东 재고 플랫폼(developer.jdcloud.com/article/4129 · 3742): 재고를 Redis 캐시에 두고 예약해 핫 상품 예약 TPS를 50에서 1,200으로 올렸다("提升了24倍"). DB와의 동기화는 MQ 재시도와 작업 시스템이 받치고, 그래도 DB와 Redis가 어긋나는 일이 있었다고 적었다. 어긋남은 `【缓存库存数据】+【缓存操作量数据】=【db库存数据】` 대조로 찾는다
- 阿里云 PolarDB 핫 행 최적화(help.aliyun.com/document_detail/178149.html): 같은 행 UPDATE를 짧은 창에 모아 한 번에 잠근다

판정 기준은 측정 전에 [이슈 #472](https://github.com/dj258255/BE-commerce/issues/472)에 적었다. 하네스는 #384의 결제 확정 흉내(재고 차감 뒤 같은 트랜잭션에서 주문 상태 변경 · 포인트 적립 · 이벤트 기록 3건)를 그대로 쓰고 재고를 빼는 방식만 바꿨다(`HotStockStrategiesExperimentTest`, 실 MySQL 8.4 · Redis 7.4, 커넥션 풀 90).

#### 처리량과 지연 (5초 × 3회 중앙값)

| 방식 | 동시성 1 | 동시성 20 | 동시성 64 | 64의 p50 | 64의 p99 |
|---|---:|---:|---:|---:|---:|
| ROW 한 행 조건부 UPDATE(지금) | 221 | 292 | 362 | 172ms | 256ms |
| UNIT 단위당 행 + SKIP LOCKED, REPEATABLE READ | 188 | 1,488 | **2,191** | 22ms | 212ms |
| UNIT 같은 모양, READ COMMITTED | 202 | 1,241 | 1,910 | 24ms | 224ms |
| REDIS Lua 차감 + 비동기 DB 반영 | 238 | 1,971 | **3,809** | 16ms | 37ms |
| BATCH 창 5ms, 최대 64건 | 89 | 480 | 664 | 94ms | 121ms |
| BATCH 창 20ms | 30 | 329 | 693 | 91ms | 118ms |
| BATCH 창 5ms + 요청마다 SAVEPOINT | 84 | 426 | 514 | 121ms | 166ms |

모든 칸에서 오류 0, 측정 뒤 `팔린 주문 수 + 남은 재고 = 처음 재고`를 확인했다.

#### 완판 · 공정성

재고 200에 64스레드가 매진까지 사는 완판 검사에서 일곱 방식 모두 초과 판매 0 · 팔지 못한 재고 0이었다. UNIT READ COMMITTED는 이 과정에서 "가용 행이 비어 보이는데 실제로는 다른 트랜잭션이 잠근 행만 남은" 경우를 4번 만났다. 이때 매진으로 답했다면 그만큼 재고가 남았다. 하네스는 비잠금 `COUNT`가 0일 때만 매진으로 판정하게 해 뒀다.

공정성은 재고 200에 고객 1,000명이 0.5초에 걸쳐 차례로 한 번씩 시도할 때 먼저 온 200명 중 산 사람 수다.

| 방식 | ROW | UNIT · REDIS · BATCH 전부 |
|---|---:|---:|
| 먼저 온 200명 중 산 사람 | **146** | 200 |

ROW는 도착이 처리량(초당 약 300건)보다 빨라 한 행 앞에 줄이 서는데, 그 줄이 도착 순서대로 풀리지 않았다. 원인 후보는 MySQL 8.0이 행 잠금 대기를 도착 순서가 아니라 대기 무게로 고르는 스케줄링(CATS)이고 이 실험에서 따로 확인하지는 않았다. 나머지는 처리가 도착을 따라잡거나(UNIT · REDIS) 큐가 도착 순서를 지켰다(BATCH).

#### REDIS의 장애 주입

**반영 작업이 죽는 자리 × 반영 방식** (재고 5,000, 동시성 20, 1,000건째에 한 번 죽임)

| 반영 방식 | 꺼낸 뒤 DB 반영 전에 죽음 | DB 반영 뒤 정리 전에 죽음 |
|---|---:|---:|
| 꺼내면서 지움 | **DB 재고 17 남음(차감 손실)** | 일치 |
| 처리 중 목록으로 옮기고 반영 뒤 지움 | 일치 | **DB 재고 −8(중복 차감)** |
| 위 + 조작 번호 유니크로 멱등 | 일치 | 일치 |

초과 판매는 여섯 칸 모두 0이었다. 판매는 Redis 재고가 막으므로 DB 재고가 틀려도 당장은 더 팔지 않는다. 틀린 DB 재고가 문제가 되는 것은 다음 표처럼 Redis를 DB에서 다시 채울 때다.

세 반영 방식은 메시지 브로커 컨슈머의 세 전달 보장과 같은 모양이다. 꺼내면서 지우는 것은 오프셋을 먼저 커밋하는 at-most-once, 반영 뒤 지우는 것은 처리 뒤 커밋하는 at-least-once, 조작 번호 멱등은 at-least-once에 멱등 소비를 얹은 것이다. 조작 기록을 Redis 목록이 아니라 카프카 토픽에 두어도 이 표의 칸은 그대로 생긴다(그 구성은 재지 않았다).

**Redis 데이터 유실 뒤 복구** (영속 없는 재시작과 같은 상태를 `FLUSHALL`로 만든다)

| 유실 순간 반영 작업 상태 | 유실 때 미반영 조작 | DB 재고로 다시 채움 | 주문 기록으로 다시 계산 |
|---|---:|---:|---:|
| 따라잡고 있음 | 20 · 19 | **초과 판매 20** | 0 |
| 500ms 멈춰 있음 | 958 · 880 | **초과 판매 958** | 0 |

첫 실행은 반영 작업을 멈추는 동안 판매도 함께 막아 미반영 조작 0에서 유실시켰고, 두 복구 모두 0이었다. 갈릴 조건이 서지 않은 0이라 판매를 받는 동안 반영 작업만 멈추게 고쳐 다시 쟀다. DB 재고로 다시 채우면 초과 판매가 유실 순간의 미반영 조작 수와 정확히 같았다. 반영되지 않은 차감이 Redis와 함께 사라지고, 남은 DB 재고는 그만큼 많다. 주문 기록(`처음 재고 − 팔린 주문 수`)으로 다시 계산하면 0이다. 대신 다시 계산하는 동안 판매를 멈춰야 하고(이 실험에서 약 45~56ms, 반영 작업이 따라잡던 경우), 주문 기록이 같은 DB 안에 있어야 한다.

**대조** (`Redis 재고 + 미반영 조작 = DB 재고`, 100ms마다)

| 상황 | 표본 | 한 번 어긋나면 경보 | 세 번 연속이면 경보 |
|---|---:|---:|---:|
| 장애 없음, 동시성 64로 5초 | 47 | **10번(오탐)** | 0번 |
| 반영 작업이 묶음을 쥔 채 죽음(영구 어긋남) | | 32ms 만에 탐지 | 245ms 만에 탐지 |

대조 공식은 맞지만 한 번 보고 경보하면 표본의 21%가 오탐이었다. 세 값을 읽는 사이에도 판매와 반영이 움직이기 때문이다. 세 번 연속으로 바꾸면 오탐 0에 탐지는 245ms였다.

#### BATCH의 한 건 실패

요청 100건에 1건을 실패하게 만들고(주문 번호를 컬럼 길이보다 길게) 64스레드가 100건씩 보냈다.

| 방식 | 실패한 독 요청 | 함께 실패한 무관한 주문 |
|---|---:|---:|
| 묶음 하나가 한 트랜잭션 | 64 | **4,032** |
| 요청마다 SAVEPOINT | 64 | 0 |

4,032는 64 × 63이다. 독 요청 하나가 같은 묶음의 63건을 끌고 되돌아갔다. 첫 실행에서는 모든 스레드가 같은 걸음에 독 요청을 넣어 독 요청끼리 한 묶음이 됐고 무관한 주문이 0으로 나왔다. 조건이 서지 않은 0이라 걸음을 스레드마다 다르게 바꿔 다시 쟀다(원자료에 두 실행을 다 남겼다). SAVEPOINT는 이 파급을 0으로 만들지만 동시성 64 처리량을 664에서 514로 23% 깎는다.

#### 판정 (측정 전 기준 그대로)

1. **환경**: ROW 동시성 20이 292건으로 #384의 301 ±15%(256~346) 안이다. 같은 환경으로 본다
2. **정합성 게이트**: 장애 없는 완판 검사는 일곱 방식 모두 통과. 장애 주입에서 REDIS는 "DB 재고로 다시 채움" 복구에서 초과 판매 20 · 958이 났다. 기준대로 **REDIS는 "대조와 수동 정정 없이 한정 상품 기본값 불가"**로 적는다. 주문 기록으로 다시 계산하는 복구는 0이었지만, 기준은 방식 단위로 적었고 복구를 잘못 고르는 순간 초과 판매가 나는 방식이라는 사실은 바뀌지 않는다. UNIT · BATCH는 비동기 단계가 없어 한 트랜잭션 안에서 끝나므로 같은 종류의 장애 주입 자리가 없다
3. **처리량 기준(동시성 64에서 초당 1,000건)**: UNIT RR 2,191 · UNIT RC 1,910 · REDIS 3,809가 넘었다. ROW 362, BATCH 514~693은 못 넘었다
4. **결정**: 2와 3을 함께 통과한 것은 UNIT 둘이고 p99가 낮은 쪽은 **UNIT REPEATABLE READ(212ms)**다. 인기 상품 후보로 둔다
5. **공정성**(판정 밖): ROW만 146/200이었다
6. **운영 기본값은 바꾸지 않는다.** 지금 수요(대기열 실험 #383 기준 초당 100명 도착)에서는 한 행으로 충분하다

#### 숫자가 말하는 것

- **초당 1,000건은 정합성을 버리지 않고도 가능했다.** 다만 대가가 처리량 대신 다른 자리로 옮겨 간다. UNIT은 재고를 행으로 펼치고 채우는 일을 떠안고, p99는 ROW와 비슷한 200ms대로 남는다. p50만 172ms에서 22ms로 내려갔다
- **REDIS는 가장 빠르지만 장애 뒤 복구가 판정을 가른다.** 반영 작업이 죽는 자리와 복구 방식을 잘못 고르면 초과 판매가 미반영 조작 수만큼 정확히 난다. 쓰려면 조작 번호 멱등, 주문 기록 기준 복구, 세 번 연속 대조가 함께 있어야 한다. 셋 중 하나만 빠져도 위 표의 어느 한 칸이 그대로 터진다
- **READ COMMITTED는 이 모양에서 이득이 없었다.** Shopify가 격리 수준을 낮춘 이유는 REPEATABLE READ의 잠금이 가용 행을 채우는 INSERT를 막았고 데드락으로 이어질 수 있었기 때문이다. 여기서는 채우는 일을 카운터 행 잠금 아래에서만 해 두 격리 수준 모두 막힘이나 데드락이 없었다
- **BATCH가 못 넘은 것은 합병의 한계가 아니라 이 하네스 모양의 한계다.** 주문 쓰기 3건까지 커밋 스레드 하나로 몰아 묶음당 약 100ms가 걸렸다. PolarDB는 엔진 안에서 핫 행 UPDATE만 합치고 나머지 쓰기는 각 트랜잭션이 병렬로 한다. 같은 것을 애플리케이션에서 흉내 내려면 재고 차감만 묶고 주문 쓰기는 따로 해야 하는데, 그러면 차감과 주문이 한 트랜잭션이 아니게 된다

#### 한계

- 로컬 한 대의 Testcontainers라 Redis 왕복이 짧다. 운영에서는 REDIS 쪽 처리량이 더 낮게 나온다
- UNIT의 가용 행 한도 1,000은 Shopify 값을 그대로 썼다. 상품 수가 많을 때의 행 수 비용은 재지 않았다
- PG 호출은 뺐다. 실제 결제 확정은 PG 승인 뒤에 재고를 빼므로 그 앞단의 지연은 이 표에 없다

# ADR-004. 재고 차감은 조건부 UPDATE 전략을 쓴다

- 상태: 채택 (Accepted)
- 날짜: 2026-07-06
- 관련: [ADR-003](ADR-003-stock-deduction-timing.md), Phase 5(성능)

## 맥락

재고 차감은 동시 요청이 몰리는 지점이다(선착순·인기 상품). 음수 재고·초과 판매(oversell)를 막으면서 성능도 지켜야 한다. 후보 3종:

- **비관적 락**: `SELECT ... FOR UPDATE`로 행을 잠그고 차감
- **낙관적 락**: `@Version` + 충돌 시 재시도
- **조건부 UPDATE**: `UPDATE ... SET quantity = quantity - :n WHERE quantity >= :n` (락 없이 원자적)

## 실험

두 환경에서 쟀다. `StockLockComparisonTest`(H2 인메모리)는 CI에서 매번 같은 결과가 나오는
**안전 불변식 검사**로 남기고, `StockLockComparisonMySqlTest`(Testcontainers MySQL 8.4)가 **성능 수치**를 낸다.
인메모리에는 네트워크 왕복도 디스크도 없어 재시도가 사실상 공짜라, 낙관적 락에 유리하게 기우는 조건이기 때문이다.

### 실 MySQL 8.4 (InnoDB): 30스레드가 재고 20에 동시 차감, 워밍업 후 5회 중앙값

| 전략 | 초과판매 | 완판 | 소요(중앙값) | 범위 |
|---|---|---|---|---|
| **조건부 UPDATE** | 0 | 20/20 | **40ms** | 24~49ms |
| 비관적 락 | 0 | 20/20 | 75ms | 59~144ms |
| 낙관적 락 | 0 | 20/20 | 151ms | 99~165ms |

### 고경합: 같은 조건에서 스레드만 150으로

| 전략 | 초과판매 | 완판 | 소요(중앙값) | 범위 |
|---|---|---|---|---|
| **조건부 UPDATE** | 0 | 20/20 | **79ms** | 66~110ms |
| 낙관적 락 | 0 | 20/20 | 429ms | 298~451ms |

세 전략 모두 **안전**(초과판매 0, 최종재고 = 재고 − 성공)했다. 차이는 성능이다.

- **조건부 UPDATE가 최속**(40ms). 락도 재시도도 없이 DB 한 번의 원자적 UPDATE로 끝난다.
- **낙관적 락이 최저속**(151ms). 충돌마다 조회와 갱신을 다시 왕복하는데, 실 DB에서는 그 왕복이 실제 비용이다.
  H2에서는 이 왕복이 거의 공짜라 낙관적(17ms)이 비관적(32ms)보다 빨랐는데 **실 InnoDB에서 순위가 뒤집혔다.**
  측정 환경이 결론을 바꾼 사례다.
- 비관적 락은 중간(75ms). 한 번 줄을 서면 왕복이 한 번뿐이라 재시도보다 싸다. 다만 커넥션을 트랜잭션 동안 점유한다.
- **고경합에서 격차가 벌어진다.** 150스레드에서 조건부 79ms vs 낙관적 429ms(**5.4배**). 재시도 상한 50회 안에서는
  미달판매까지 가지 않았지만, 그 상한을 지키느라 지연이 그만큼 늘었다. 한 행에 쓰기가 몰리는 hot row에
  낙관적 락이 부적합하다는 결론은 같다.
- 데드락 0건, 락 대기 타임아웃 0건. 단일 행 경합이라 대기 그래프가 선형이다.

## 결정

기본 전략으로 **조건부 UPDATE**를 채택한다. `CheckoutService`가 승인 성공 시
`StockDeductionService.deductConditional`을 호출한다.

## 근거 / 트레이드오프

- 단일 자원(재고 행) 차감에는 조건부 UPDATE가 가장 저비용·안전하다.
- 비관적 락은 "차감 전후에 여러 읽기/계산이 필요"한 복잡한 시나리오에서만 가치가 있다. 단순 차감엔 과하다.
- 낙관적 락은 충돌이 드문 자원(사용자별 포인트 등)에 적합하다. 인기 상품 재고처럼 한 행에 몰리는 hot row에는 부적합.
- **멀티 인스턴스에서 DB 부하를 분산**해야 하면 Redis 분산락(Redisson)을 추가로 고려한다(확장 08 문서). 이 프로젝트는 단일 DB 기준으로 조건부 UPDATE가 정답.

## 후속

- 세 전략 구현(`StockDeductionService`)은 비교 근거로 코드에 남겨 둔다.
- 실제 애플리케이션 레벨 부하테스트(k6)는 `docs/performance/`에 방법론과 스크립트로 정리한다.

## 2026-09-27 한 행이 초당 몇 건까지 버티는가 (#384)

위 실험은 재고 20개를 다 파는 시간(40 · 79ms)만 쟀고 한 행의 처리량 상한은 재지 않았다. 결제 확정(`CheckoutTx.settle`)은 재고 행을 조건부 UPDATE 로 잠근 뒤 같은 트랜잭션에서 주문 상태 변경 · 포인트 적립 · 이벤트 발행 기록을 쓰고 커밋한다. **재고 행 잠금은 커밋까지 풀리지 않으므로** 한 행의 상한은 대략 1초 ÷ 잠금 유지 시간이다.

`HotRowThroughputExperimentTest`(실 MySQL 8.4, `innodb_flush_log_at_trx_commit=1`)로 뒤따르는 쓰기 3건을 같은 개수로 흉내 내 재고를 넉넉히 두고 5초씩 3회 잰 중앙값이다. Shopify 가 한정 판매의 재고 한 행 경합을 단위당 행과 `SKIP LOCKED` 로 푼 것과 대조하려고 쟀다.

| 모양 | 동시성 20 초당 처리량 | 지금 대비 | 잠금 유지 p50 | 완판 검사(재고 200, 64스레드) 데드락 | 한 건 팔 때 UPDATE 수 |
|---|---:|---:|---:|---:|---:|
| **A 지금: 재고 UPDATE → 쓰기 3건 → 커밋** | **301** | 1.0 | 2.99ms | 0 | 1.32 |
| B 쓰기 3건 → 재고 UPDATE → 커밋 | 444 | 1.47 | 1.86ms | 0 | 1.32 |
| C4 재고를 4칸으로, 임의 칸부터 | 718 | 2.4 | 4.74ms | 230 | 2.28 |
| C16 재고를 16칸으로 | 1,245 | 4.1 | 7.43ms | 1,181 | 6.18 |

한 건 팔 때 UPDATE 수에는 매진 뒤 스레드마다 한 번씩 실패한 시도가 들어 있다. 네 모양 모두 초과 판매 0, 팔지 못한 재고 0 이었다.

- **A 는 동시성 4 에서 이미 초당 281건이고 20 · 64 에서도 290~301건에 머문다.** 동시성을 올리면 처리량은 그대로이고 p50 지연만 13ms → 64ms → 210ms 로 는다. 한 행 앞에서 줄을 선다
- **순서를 바꾸면(B) 잠금 시간이 3.0ms → 1.9ms 로 준다.** 남은 1.9ms 는 거의 커밋의 로그 fsync 다. 순서를 바꿔도 한 행의 상한은 초당 약 540건(1 ÷ 1.86ms)을 넘지 못한다
- **칸으로 나누면 처리량은 칸 수만큼 가깝게 는다.** 대가는 매진 직전이다. 빈 칸을 지나가는 트랜잭션이 여러 행을 잠그고 시작 칸이 제각각이라 서로를 기다린다. 16칸에서 재고 200 을 파는 동안 데드락 1,181건, 한 건에 UPDATE 6.18번이었다. 전체 선착순도 깨진다(먼저 온 사람이 빈 칸에 걸려 늦게 온 사람보다 늦을 수 있다)

**결정: 한 행(A)을 유지한다.** 측정 전 기준은 "동시성 20(커넥션 풀 크기)에서 초당 300건 이상이면 유지"였고 301건이었다. 대기열 실험(#383)의 수요가 초당 100명 도착이고 결제 확정까지 가는 것은 그보다 적어 3배 여유가 있다.

**다만 경계에서 통과했다.** 가장 낮은 회차는 288건이었고, 실제 `settle` 은 JPA 플러시와 이벤트 기록을 더 하므로 잠금 시간이 이 실험보다 길 수 있다. 결제 확정이 한 상품에 초당 100건을 넘게 몰리는 행사가 생기면 다음 순서로 다시 본다.

1. B(순서 바꾸기): 스키마 변경 없이 1.47배. 재고 부족이면 앞의 쓰기를 되돌려야 해서 확정 트랜잭션의 모양이 바뀐다
2. 칸 나누기: 칸을 도는 순서를 고정(0번부터)하면 데드락은 줄지만 앞 칸에 다시 몰린다. `READ COMMITTED` 로 빈 칸의 잠금을 바로 놓게 하는 것(Shopify 가 예약 테이블의 갭 락 데드락을 피한 방법)과 같이 재야 한다

## 2026-09-28 초과 판매 뒤 사후 정정 대 조건부 UPDATE (26절③, AWS DynamoDB 카운터 패턴, #412)

위 실험은 전부 "쓰기 시점에 정확히 막는" 전략끼리 비교였다. 이 절은 반대 축을 본다 — <b>쓰기 시점에 안 막고(느슨한 카운터, Redis `DECR`) 나중에 정정</b>하면, 지금 기본(조건부 UPDATE)보다 처리량이 느는지, 그 대가(초과 판매·취소 건수)는 얼마인지. `StockLockComparisonMySqlTest`와 같은 방법론(스레드 동시 출발, `SharedContainers`의 실 MySQL·Redis, 5회 중앙값)을 쓴다.

**판정 기준은 측정 전에 [이슈 #412](https://github.com/dj258255/BE-commerce/issues/412)에 적었다.** 재고 20 · 스레드 150(고경합, ADR-004 위 실험의 `HIGH_THREADS`와 동일).

| 지표 | 조건부 UPDATE(MySQL) | 느슨한 카운터(Redis DECR) |
|---|---:|---:|
| burst 중앙값(5회) | 34~35ms | 9~12ms |
| 정정 전 성공(예약) | 20 | 150(무조건 예약) |
| 정정 전 초과 판매 | 0 | 130 |
| 정정 후 초과 판매 | 0(해당 없음) | 0 |
| 취소 건수 | 0 | 130 |

**가설 판정 — 넷 다 맞았다.**

1. **맞았다.** 느슨한 카운터(burst) 중앙값이 조건부 UPDATE보다 짧았다(9~12ms 대 34~35ms, 약 65~74% 감소). 두 전략 모두 같은 행(조건부 UPDATE) 또는 같은 키(Redis)에 원자적으로 접근해 동시성 150에서도 직렬화되지만, Redis `DECR`는 MySQL 행 락 획득 · 트랜잭션 커밋 · `innodb_flush_log_at_trx_commit=1`의 디스크 fsync가 없어 건당 비용이 훨씬 낮다.
2. **맞았다.** 느슨한 카운터는 정의대로 150건 전부 무조건 예약돼 정정 전 초과 판매가 150−20=130건 났다. 조건부 UPDATE는 항상 0건(기존 테스트가 이미 보장하는 불변식).
3. **맞았다.** 사후 정정(가장 늦게 들어온 예약부터 초과분만큼 취소)을 적용하자 재고 정확히 0 · 초과 판매 0으로 수렴했다 — 조건부 UPDATE와 같은 최종 결과다.
4. **맞았다.** 취소 건수(130)가 정정 전 초과 판매(130)와 정확히 일치했다 — "정정이 실제로 일어났다"는 카운터 증거.

**정리.** 느슨한 카운터+사후 정정은 burst 처리량에서 확실히 이득이다. 다만 이 이득은 <b>"쓰기 경로에서 검증을 미룬다"</b>는 선택 자체의 대가를 동반한다 — 이번 조건(재고 20, 스레드 150)에서는 예약의 87%(130/150)가 나중에 취소 대상이었다. 실서비스에 적용하려면 취소된 고객에게 알리고 보상하는 절차(쿠폰·우선순위 재구매권 등)가 필요하고, 그 비용이 이 실험 범위 밖이다. 이 패턴은 <b>초과 예약률이 낮게 유지되는 상황</b>(수요가 재고를 크게 넘지 않는 평시)에서 burst 구간의 지연을 줄이는 용도에 맞지, 이번 실험처럼 수요가 재고의 7.5배(150/20)인 극단적 한정 판매에는 안 맞는다 — 취소 대상이 다수가 되어 "일단 성공"이라는 사용자 경험 자체가 무의미해진다.

**정정 순서(늦게 들어온 것부터 취소)를 고른 이유.** 먼저 예약을 완료한 고객이 취소당하면 "확정됐다고 믿은 것"이 뒤집히는 비용이 더 크다고 판단했다 — 선착순 원칙과도 맞는다. 대안(무작위 취소, 금액 낮은 순 취소)은 비교하지 않았다.

**일부러 하지 않은 것.** 이 실험은 재고·Redis 카운터·정정 로직만 격리해 쟀다(`StockLockComparisonMySqlTest`와 같은 스코프) — 실제 체크아웃·결제·환불 경로에는 연결하지 않았다. 취소된 예약을 실제 주문 취소·환불로 이어붙이는 것, 정정 주기(즉시 대 배치)의 지연 대가, 초과 예약률을 낮추는 다른 방법(예: 재고의 90%까지만 느슨하게 팔고 나머지는 조건부로 전환)은 범위 밖이다.

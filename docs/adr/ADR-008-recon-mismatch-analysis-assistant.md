# ADR-008. 대사 불일치 확정에 사유를 남기고, 그 위에 1차 분석기를 얹는다

- 상태: 대체됨 (Superseded) — 사유 기록은 구현했고, 분석 방식은 [ADR-012](ADR-012-rule-based-cause-classifier.md)의 규칙 우선 접근으로 대체
- 날짜: 2026-08-27
- 관련: [ADR-002](ADR-002-outbox-event-publication-registry.md), `reconciliation` 모듈, `audit` 모듈

## 맥락

대사는 내부 기록과 PG 정산 파일을 `orderNo`로 대조해 4분류한다(`MATCHED` / `INTERNAL_ONLY` / `EXTERNAL_ONLY` / `AMOUNT_MISMATCH`). 불일치는 `PENDING`으로 예외 큐에 남고, 운영자가 조사한 뒤 `resolve(id)`로 수기 확정한다.

**문제는 그 조사 결과가 아무 데도 안 남는다는 것이다.**

`ReconciliationResult.resolveManually()`의 주석은 이렇게 적고 있다.

> 누가/왜 확정했는지는 엔티티에 컬럼으로 남기지 않고 어드민 **감사 로그**로 남긴다(스키마 변경 최소화).

그런데 **그 감사 로그가 실제로 배선돼 있지 않다.** `AuditService`는 단위 테스트에서만 쓰이고 `src/main` 어디서도 호출되지 않는다. 즉 **의도는 문서에 있는데 구현이 없고, 결과적으로 사유가 어디에도 기록되지 않는다.**

그래서 이런 일이 반복된다.

- 운영자 A가 `AMOUNT_MISMATCH` 한 건을 세 시간 조사해서 "부분취소 2차가 PG 파일에 다음 날로 넘어간 것"이라고 결론 내고 확정한다.
- 다음 주에 같은 패턴이 또 온다. 운영자 B가 **처음부터 다시 조사한다.**
- 조직에 지식이 안 쌓인다.

불일치의 원인 후보는 **열려 있다.** 부분취소 미반영, 수수료 계산 차이, 타임존 경계, PG 파일 지연, 망취소 반영 시점, 위변조. 그리고 새 원인이 계속 생긴다. 이걸 `if` 문으로 다 채우는 건 불가능하고, 채워도 다음 달에 또 늘어난다.

## 결정

**두 단계로 나눈다. 1단계는 AI 없이 하고, 2단계에서 얹는다.**

### Phase 1 — 사유를 남긴다 (AI 없음)

수기 확정에 **사유를 필수로** 받고, `audit` 모듈을 **실제로 배선**한다.

- `resolveManually(actor, cause, detail)`로 시그니처 변경
- `AuditService.record(...)`를 여기서 처음으로 실제 호출한다 (`action = RECON_RESOLVE`)
- 사유는 **구조화된 원인 코드 + 자유 서술** 두 칸으로 받는다. 코드만이면 새 원인을 못 담고, 자유 서술만이면 집계가 안 된다

**Phase 1만으로도 가치가 있다.** 같은 패턴이 반복되는지 세어볼 수 있고, 자주 나오는 원인은 오히려 **규칙으로 자동 확정**할 수 있게 된다. AI가 필요한지 여부도 이 데이터를 보고 정한다.

### Phase 2 — 1차 분석기를 얹는다 (AI)

Phase 1로 사유가 충분히 쌓인 뒤, 불일치 1건에 대해 **원인 후보를 제시**하는 분석기를 붙인다.

- **AI는 확정하지 않는다.** 제안만 하고 `resolve`는 사람만 호출한다
- 제안은 **별도 테이블**에 남긴다. `ReconciliationResult`를 건드리지 않는다
- 컨텍스트는 **읽기 전용**으로 조립한다. AI에 쓰기 권한을 주지 않는다
- 실패하면 **제안이 없을 뿐**, 기존 수기 확정 경로는 그대로 동작한다

## 스키마 (V22)

```sql
-- Phase 1
alter table reconciliation_results
    add column resolved_by   varchar(100) null,
    add column resolve_cause varchar(60)  null,   -- 원인 코드
    add column resolve_note  varchar(500) null,   -- 자유 서술
    add column resolved_at   datetime(6)  null;

-- Phase 2
create table recon_analysis_suggestions (
    id                bigint       not null auto_increment,
    recon_result_id   bigint       not null,
    candidates_json   text         not null,   -- 후보 목록(구조화 출력 그대로)
    model             varchar(60)  not null,
    prompt_version    varchar(20)  not null,   -- 프롬프트가 바뀌면 결과가 바뀐다. 버전을 남긴다
    created_at        datetime(6)  not null,
    accepted_cause    varchar(60)  null,       -- 사람이 채택한 것. null이면 반려/직접입력
    primary key (id),
    key idx_recon_result (recon_result_id)
) engine=InnoDB;
```

**`prompt_version`을 남기는 이유**: 같은 입력에 다른 출력이 나올 수 있는 게 이 층의 본질이다. 나중에 "이 제안이 왜 이렇게 나왔나"를 되짚으려면 어떤 프롬프트였는지가 필요하다. 대사 매칭 엔진을 **결정적**으로 만든 것과 대비되는 지점이라, 그 차이를 스키마에 드러낸다.

## 컨텍스트 조립 — 무엇을 넣고 무엇을 빼나

**넣는 것** (전부 우리 DB에 이미 있다)

| 출처 | 내용 |
|---|---|
| `reconciliation_results` | `orderNo`, 분류, 내부/외부 금액, 거래일 |
| `payments` + `payment_history` | 상태 전이 시각, 승인·취소 금액, **취소 순번** |
| `ledger_entries` | 그 `orderNo`의 분개 (차변/대변) |
| `settlement_items` | 정산 상태(`PENDING_CONFIRMATION`/`CONFIRMED`/`SETTLED`) |
| 과거 확정 이력 | **같은 분류 + 금액차 패턴이 비슷한 N건**과 그때 적은 사유 |

**절대 넣지 않는 것**

- 카드번호, 계좌번호 등 **암호화 대상 필드**(ADR-006). 복호화해서 프롬프트에 넣는 순간 봉투 암호화가 무의미해진다
- 고객 개인정보. 필요한 건 **금액·시각·상태**이지 누구인지가 아니다

이 원칙을 코드로 강제한다. 컨텍스트 조립 함수는 **허용된 필드만** 화이트리스트로 읽는다.

## 출력 계약

자유 텍스트를 받지 않는다. **구조화 출력**만 받는다.

```json
{
  "candidates": [
    {
      "cause": "PARTIAL_CANCEL_NOT_REFLECTED",
      "confidence": "HIGH",
      "evidence": [
        "payment_history: 취소 순번 2가 08-26 23:51에 확정",
        "PG 파일 거래일: 08-27",
        "금액차 3,000원 = 2차 취소 금액과 일치"
      ],
      "nextCheck": "PG 08-27자 파일에 같은 orderNo가 있는지 확인"
    }
  ]
}
```

- `evidence`는 **실제 데이터를 인용**해야 한다. 근거 없이 원인만 대면 반려한다
- `nextCheck`는 **사람이 확정하려면 무엇을 더 봐야 하는가**다. 이게 없으면 제안이 아니라 추측이다
- 후보는 최대 3개. 그 이상은 판단을 돕지 않고 미룬다

## 지켜야 할 네 가지

1. **읽기 전용** — 분석기는 `resolve`를 호출할 수 없다. 확정은 사람만
2. **제안은 상태가 아니다** — `ReconciliationResult`를 건드리지 않는다. 별도 테이블
3. **감사** — 제안 생성 / 채택 / 반려를 전부 `audit_logs`에 남긴다. 규제 대응이자 다음 개선의 데이터
4. **폴백** — LLM 호출 실패 시 제안 없이 넘어간다. 예외를 대사 흐름으로 전파하지 않는다

## 근거

1. **규칙으로 안 되는 자리다.** 원인 후보가 열려 있고 계속 늘어난다. `if` 문으로 채우면 채운 만큼만 잡히고, 안 채운 게 사고가 된다.
2. **판단은 사람이 한다.** 돈이 걸린 확정을 모델이 하면 안 된다. 이 프로젝트가 강제취소에 2인 승인을 둔 것과 같은 이유다.
3. **AI 없이도 1단계는 이득이다.** 사유가 쌓이면 반복 패턴이 보이고, 그건 규칙으로 자동화할 수 있다. **AI가 필요한지 여부도 데이터를 보고 정한다** — "재 보기 전에는 구조를 바꾸지 않는다"는 이 프로젝트의 원칙 그대로다.
4. **감사 로그 배선 문제를 같이 푼다.** `AuditService`가 설계만 되고 호출부가 없던 상태였는데, 이 작업이 첫 실사용처가 된다.

## 트레이드오프 / 포기한 것

- **결정성을 잃는다.** 대사 매칭 엔진은 같은 입력이면 같은 결과가 나오게 만들었는데, 이 층은 그렇지 않다. 그래서 **제안을 도메인 상태와 분리**하고 `prompt_version`을 남긴다.
- **비용이 든다.** 불일치 건에만 호출하고, 대사는 하루 1회 배치라 건수가 제한적이다. 그래도 상한을 둔다.
- **없는 원인을 지어낼 수 있다.** `evidence`에 실제 데이터 인용을 요구하고, 사람이 그 인용을 검증한다. 검증할 수 없는 제안은 반려한다.
- **초기에는 제안이 나쁠 것이다.** 과거 사례가 없으니 당연하다. 그래서 Phase 1을 먼저 한다.

## 대안

- **규칙 기반 원인 분류기**: 자주 나오는 3~4개는 규칙으로 잡힌다. 실제로 **Phase 1 데이터를 보고 그게 충분하면 Phase 2를 안 한다.** 이게 첫 번째 선택지다.
- **FDS에 머신러닝**: 기각. 실사용자 거래가 없어 **학습 데이터가 없다.** 그리고 결제 차단은 고객에게 이유를 설명해야 해서 설명 가능성이 규칙보다 낮아진다.
- **미확정 결제 우선순위 정렬에 AI**: 기각. 금액과 경과 시간으로 **규칙이면 충분하다.**

## 구현 순서

1. `V22` 마이그레이션 (Phase 1 컬럼)
2. `resolveManually(actor, cause, note)` + `AuditService` 실제 배선 + 어드민 화면에 사유 입력
3. **여기서 멈추고 데이터를 모은다.** 원인 분포를 세어 본다
4. 반복 패턴이 규칙으로 잡히면 → 규칙 자동 확정. 안 잡히면 → Phase 2
5. Phase 2: 컨텍스트 조립(화이트리스트) → 구조화 출력 → 제안 테이블 → 화면에 후보 표시

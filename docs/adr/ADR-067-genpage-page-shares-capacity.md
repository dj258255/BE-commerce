# ADR-067. 홈 다음 쪽의 GenPage 호출도 추천 행과 같은 동시 호출 자리를 쓰고, 자리가 없으면 기다리지 않는다

- 상태: **채택**. `app.recommendation.model.page-capacity=shared`(기본). `model.kind=genpage` 일 때만 뜻이 있다
- 날짜: 2026-09-25
- 관련: `GenPageCapacity`, `GenPageModelClient`, `GenPagePageClient`, `RecommendationFacts`,
  [실측 리포트](../../personalization/docs/runs/20260924-overload-real-model/report.md), [ADR-065](ADR-065-admission-by-observed-throughput.md), [ADR-053](ADR-053-genpage-mini-not-default.md), 이슈 #271

## 맥락

ADR-065 의 과부하 게이트와 모델 동시성 4 는 추천 행(`/recommend`)만 지켰다. 홈 다음 쪽의 `/page` 는 같은 모델 서버 CPU 를 쓰는데
게이트도 동시 호출 제한도 거치지 않았다. `/page` 한 번은 `/recommend` 의 약 8배다(모델 서버 직접 최대 처리량 121/s 대 999/s).

## 판정 기준 (이슈 #271 에 측정 전에 적었다. 두 번 고쳤고, 고친 것도 측정 전에 댓글로 적었다)

- 원래: 2쪽 부하에서 추천 행 p95 ≤ 126ms 이고 2쪽 모델 행 실패 ≤ 5% 면 자리 공유 채택
- 두 번째 댓글: 대조(모델 없음)에서도 앱이 무너져 위 부하로는 판정하지 않는다
- 세 번째 댓글: 앱이 버티는 2쪽 부하 P 에서 자리 공유의 busy 폴백 ≤ 1% 이고 2쪽 · 추천 행 p95 가 자리 없음의 1.1배 이내면 기본으로 둔다

## 결과 (대입)

| 조건 | 추천 행 모델 실패 | 2쪽 모델 행 | 2쪽 p95 | 추천 행 p95 | dropped |
|---|---:|---:|---:|---:|---:|
| 자리 없음 · 2쪽 121/s | 214 | 0.0% | 15,215ms | 2,433ms | 수천 |
| 자리 공유 · 2쪽 121/s | 0 | 60.7% | 2,454ms | 514ms | 수천 |
| 자리 없음 · 2쪽 30/s(= P) | 0 | 100.0% | 91.0ms | 11ms | 0 |
| 자리 공유 · 2쪽 30/s(= P) | 0 | 99.9% | 79.6ms(0.87배) | 10ms(0.91배) | 0 |

121/s 는 원래 기준을 못 넘었고, 모델 없이 규칙 행만 만들어도 앱이 무너져 판정에 쓰지 않았다. P = 30/s 에서 세 번째 기준을 넘었다.

## 결정

- **`/recommend` 와 `/page` 가 동시 호출 자리 하나(`model.concurrency`, 4)를 나눠 쓴다**(`GenPageCapacity`)
- 추천 행은 지금처럼 자리를 `busy-timeout-ms`(400ms)까지 기다린다. **2쪽은 기다리지 않는다.** 자리가 없으면 모델을 부르지 않고 규칙 행으로 간다. 2쪽에는 규칙 행이라는 대안이 있어 줄을 설 이유가 없다
- 자리가 없어 물러선 것은 실패와 따로 센다(`recommendation.genpage.page{result=busy}`). 부하 정책이 고른 결과이지 모델이 죽은 것이 아니다
- `page-capacity=none` 은 이전 동작(자리 없이 부른다)으로 남긴다. 비교 측정용이다

## 버린 것

| 안 | 이유 |
|---|---|
| 자리 없이 두기 | 2쪽 121/s 에서 모델 서버가 앱이 포기한 요청까지 계산해 추천 행까지 전부 실패했다(모델 실패 214, 서버 `BrokenPipeError` 70) |
| 2쪽도 자리를 기다리게 하기 | 2쪽은 규칙 행으로 물러설 수 있다. 기다리면 톰캣 스레드를 쥔 채 줄을 늘린다 |
| 2쪽을 ADMISSION 게이트에 넣기 | 게이트의 대기 추정은 건당 비용이 비슷하다고 본다. `/page` 는 `/recommend` 의 8배라 같은 줄로 세면 추정이 틀린다. 자리 공유만으로 모델 실패가 0 이 됐다 |

## 대가 (정직하게)

- **자리가 모자라면 2쪽이 더 비싼 길로 간다.** 규칙 행은 GenPage 행보다 느렸다(2쪽 30/s p95 164.7ms 대 91.0ms). 과부하 때 busy 폴백이 앱 쪽 부하를 늘린다. 재지 않았다
- 2쪽이 추천 행의 자리를 가져간다. 2쪽 한 번이 자리 하나를 약 30ms 쥐므로 추천 행이 기다리는 시간이 는다. P = 30/s 에서는 추천 행 p95 가 오히려 낮았지만(11 → 10ms) 더 높은 부하에서는 재지 못했다
- 판정에 쓴 부하(2쪽 30/s)는 모델 서버의 2쪽 용량(121/s)의 4분의 1이다. 이 머신에서는 앱이 먼저 포화해 모델이 포화하는 부하를 앱을 거쳐 만들 수 없었다
- 모든 것이 한 머신에서 돈다

## 다시 볼 조건

- 모델 서버를 앱과 다른 머신에 두면 → 2쪽 부하를 모델이 포화하는 데까지 올려 자리 없음 대 공유를 다시 잰다
- 2쪽 앱 경로의 용량(이 머신 30~60/s)을 올리면 → 같은 비교를 더 높은 부하에서 다시 잰다(트러블슈팅 기록 열린 항목)
- 규칙 행을 GenPage 행보다 싸게 만들면 → busy 폴백의 대가가 사라진다

## 다시 잰 결과 (#284, 2026-09-25)

위 "다시 볼 조건"의 둘째 줄을 돌렸다. 2쪽 앱 경로가 요청마다 돌던 count 쿼리를 없애 초당 30건에서 120건까지 받게 되어, 모델이 포화하는 부하를 앱을 거쳐 만들 수 있었다([리포트](../../personalization/docs/runs/20260925-page2-capacity/report.md)).

| 2쪽 부하(추천 행 150/s) | page-capacity | 추천 행 coverage · p95 · 모델 실패 | 2쪽 모델 행 · p95 |
|---:|---|---|---|
| 90/s | none | 0.0% · 1,632ms · 254 | 0% · 10,987ms |
| 90/s | shared | 99.9% · 35ms · 0 | 59.7% · 131ms |
| 120/s | none | 0.0% · 1,840ms · 254 | 0% · 12,138ms |
| 120/s | shared | 99.8% · 35ms · 0 | 41.8% · 122ms |

결정은 그대로다. 대가에 적은 "busy 폴백이 더 비싼 길로 간다"는 규칙 행을 싸게 만들어(#284) 이 부하에서는 앱을 무너뜨리지 않았다.

## 모델을 CPU 제한 컨테이너로 떼어 놓고 다시 잰 결과 (#342, 2026-09-26)

"다시 볼 조건"의 첫 줄을 도커 CPU 제한(2개)으로 흉내 냈다([리포트](../../personalization/docs/runs/20260926-page2-model-container/report.md)).
컨테이너 모델은 추천 행 82.5/s · 2쪽 8.9/s 라 부하를 비율로 옮겼다(추천 행 40/s · 2쪽 9 · 18/s, 측정 전 이슈 댓글).

| 2쪽 부하 | 자리 없음: 추천 행 coverage · p95 | 자리 공유: 추천 행 coverage · p95 · 모델 실패 | 자리 공유: 2쪽 모델 행 |
|---:|---:|---:|---:|
| 9/s | 0.0% · 698ms | 96.3% · 182ms · 0 | 0.7% |
| 18/s | 0.0% · 702ms | 88.4% · 230ms · 0 | 0.0% |

- **모델을 떼어 놓아도 자리 없음은 무너졌다.** #284 의 무너짐은 같은 맥의 CPU 경합이 아니라 모델 포화 때문이었다. 자리 공유를 유지한다
- 자리 공유의 추천 행 p95 는 측정 전에 둔 선(126ms, 맥 원생 모델에서 정한 값)을 넘었다. 모델 실패는 0 이었다
- **모델이 느리면 2쪽은 거의 모델을 못 쓴다**(0.7% · 0.0%). 2쪽이 자리를 기다리지 않아서다. 느린 모델을 따로 두면 2쪽 개인화는 사실상 꺼진다. 2쪽에 자리 몫을 따로 줄지는 2쪽이 개인화로 얻는 것을 재야 정할 수 있다(ADR-060 의 A/B 로 열어 둔다)

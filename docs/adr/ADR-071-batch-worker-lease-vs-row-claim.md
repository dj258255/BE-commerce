# ADR-071. 배치 워커 두 대 — 리스 리더 대 행 단위 나눠 갖기

- 상태: 채택(비교 실험, 프로덕션 미배선)
- 날짜: 2026-09-28
- 관련: `CheckoutRecoveryService`(스캔형 복구 배치, ADR-057 백오프), [ADR-070](ADR-070-cache-expiry-stampede-single-flight.md)(같은 26·27절 실험 방법론), 이슈 #420, `BatchWorkerFailoverExperimentTest`

## 맥락

이 저장소의 `CheckoutRecoveryService`는 지금 단일 인스턴스를 가정한다 — 워커를 두 대로 늘리면 스캔이 겹쳐 같은 주문을 동시에 처리할 수 있다(`settle`이 멱등해 안전하긴 하지만 낭비다). AWS Builders' Library의 리더 선출은 이 문제를 "리더만 일한다"로 푼다. 대안인 행 단위 나눠 갖기(competing consumers, SQS 가시성 타임아웃과 같은 개념)는 "누구든 원자적으로 점유한 것만 처리한다"로 푼다. 워커 한 대가 죽을 때 두 방식이 각각 무엇을 대가로 치르는지 쟀다.

## 측정 방법

`BatchWorkerFailoverExperimentTest`(`@Tag("experiment")`, 순수 JUnit, Docker 불필요)로 행 150개(92% 30ms · 8% 500ms 처리, 무작위)를 두 워커(각 병렬 슬롯 3개)가 나눠 처리하게 했다. 점유 시효(리스 TTL이자 가시성 타임아웃) 300ms, 폴링 20ms. 두 조건 모두 워커 A를 400ms 시점에 실행기 강제 종료로 "죽였다"(진행 중이던 행은 완료로 기록되지 않는다 — 처리가 트랜잭션처럼 전부 되거나 전부 안 되거나라고 가정했다).

**공백 시간 정의**: 크래시 이후 <b>죽지 않은 워커(B)</b>가 완료한 첫 행의 시각 − 크래시 시각. 죽은 워커가 강제 종료 직전 경계 근처에서 우연히 끝낸 마지막 한두 건이 "공백이 거의 없었다"는 착시를 만드는 것을 막으려고 죽은 워커의 완료는 이 계산에서 뺐다(1차 구현에서 실제로 이 착시로 판정이 뒤집힌 적이 있다 — 아래 "함정" 참고).

판정 기준은 측정 전 [이슈 #420](https://github.com/dj258255/BE-commerce/issues/420)에 적었다.

## 실측 결과 (3회 반복)

| 지표 | LEASE | ROW-CLAIM |
|---|---:|---:|
| 완료 건수(150건 중) | 150 / 150 / 150 | 150 / 150 / 150 |
| 공백 시간(크래시 → 생존 워커 첫 완료) | 355 / 327 / 342ms | 14 / 5 / 2ms |
| 중복 처리 행 수 | 0 / 0 / 0 | 10 / 9 / 9 |

## 가설 판정

측정 전 이슈 #420에 적은 네 가지 전부 맞았다.

1. **맞았다.** LEASE의 공백 시간이 327~355ms로, 점유 시효(300ms) 근처에서 안정적으로 나왔다.
2. **맞았다.** LEASE의 중복 처리 행 수는 3회 모두 0 — 한 번에 한 워커만 행을 만지는 구조가 실측으로도 지켜졌다.
3. **맞았다, 예상보다 더 크게.** ROW-CLAIM의 공백 시간은 2~14ms로 LEASE의 1/25~1/170 수준이다. B가 죽지 않고 계속 자기 몫을 처리하고 있어 A의 죽음이 전체 흐름을 거의 끊지 않았다.
4. **맞았다.** ROW-CLAIM의 중복 처리 행 수는 9~10건으로, 느린 행 비율(8%, 150건 중 기대값 약 12건)과 같은 자리수다 — 점유 시효(300ms)보다 오래 걸리는 처리(500ms)가 실제로 다른 워커에 다시 집힌다는 증거다.

## 함정: 첫 구현의 두 가지 버그

- **의도치 않은 리더 내부 경합.** 리더의 슬롯 스레드 3개가 "미완료 행을 스캔해서 처리"만 하고 자기들끼리 점유 표시를 안 해, 같은 리더 세션 안에서 슬롯끼리 같은 행을 동시에 집어 LEASE의 중복이 96건까지 나왔다(설계상 0이어야 하는데). 슬롯 스레드끼리도 `compareAndSet`으로 행을 먼저 점유한 뒤 처리하게 고쳐 해결했다.
- **공백 시간 계산이 죽은 워커의 "마지막 한 건"에 속았다.** 초기 계산은 "크래시 이후 가장 이른 완료 시각"을 그대로 공백으로 썼다. `shutdownNow()`가 즉시 스레드를 멈추지 못해, A가 이미 처리 중이던 행이 크래시 경계를 살짝 넘겨 완료되는 경우가 있었고, 그 값이 공백 시간으로 잡혀 한 회차에서 LEASE 공백이 3ms로 나와 판정이 뒤집혔다. 완료 기록에 처리한 워커 id를 남겨 "죽은 워커가 아닌 쪽의 첫 완료"로 고쳐 해결했다.

두 버그 모두 CI에 올리기 전 로컬 반복 실행(3~5회) 중에 드러났다 — 반복 없이 1회만 쟀으면 놓쳤을 값이다.

## 이 실험이 답하지 못하는 것

- **처리량(초당 완료 건수)은 비교하지 않았다.** ROW-CLAIM은 워커 두 대가 항상 동시에 일해 총 소요 시간(`total_ms`)이 대체로 더 짧았지만(3297~4640ms 대 3790~4775ms, 겹치는 구간이 있어 단정하지 않는다), 이번 판정 기준에 처리량을 넣지 않아 통계적으로 검증하지 않았다.
- **점유 시효를 처리 시간 분포에 맞춰 튜닝하지 않았다** — 이번 300ms는 "느린 8%(500ms)를 못 견디는 흔한 실수" 값을 일부러 썼다. 시효를 600ms 이상으로 올리면 ROW-CLAIM 중복이 얼마나 줄고 크래시 감지가 얼마나 느려지는지는 재지 않았다.
- `CheckoutRecoveryService`에 실제로 배선하지 않았다 — 26·27절의 다른 실험과 같은 스코프.

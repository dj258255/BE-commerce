# 숏폼 피드 개인화 랭킹(R27·R28·R29)

> 구현: `media/src/main/java/com/beomsu/becommerce/shorts/ShortsFeedRanking.java`(점수),
> `ShortsFeedRanker.java`(제한 시간·폴백), `ShortViewEvent.java`(R27 신호 저장).
> 설계 근거(왜 커머스의 기존 개인화 Kafka/CDC 경로를 재사용하지 않았는가)는
> [ADR-083](adr/ADR-083-shorts-signal-path.md)을 본다.

## 1. R27 — 시청 신호

영상 하나를 본 한 번의 시청(세션)이 끝날 때(다음 영상으로 스와이프하거나 화면을 떠날 때) 화면이
`POST /api/v1/shorts/{id}/signals`로 아래 다섯 신호를 한 번에 보낸다. 서버는 영상 id·시청자(로그인
userId 또는 비로그인 익명 식별자)·**서버가 받은 시각**(클라이언트 시계를 신뢰하지 않는다)과 함께
`short_view_events`에 한 행으로 남긴다.

| 신호 | 필드 | 정의 |
| --- | --- | --- |
| 시청 시간 | `watchSeconds` | 그 영상이 "보이는 카드"였던 동안 지난 시간(초) |
| 완료 여부 | `completed` | 영상 끝까지 한 번이라도 도달했는가(`loop` 때문에 자연 종료 이벤트가 없어, 재생 위치가 끝 근처에서 처음으로 되감기는 순간을 완료로 본다) |
| 다시 보기 횟수 | `replayCount` | 완료 이후 같은 영상이 다시 끝까지 도달한 횟수 |
| 건너뛰기 | `skippedWithin3s` | 완료하지 못했고 시청 시간이 3초 미만인 채로 다음으로 넘어갔는가 |
| 상품 태그 누름 | `productTagTapped` | 그 시청 동안 영상에 달린 상품 카드를 한 번이라도 눌렀는가 |

## 2. R28 — 점수와 정렬

```
score = 0.5 * completionRate + 0.3 * recency + 0.2 * productMatch
```

| 신호 | 정의 | 신호 없을 때 |
| --- | --- | --- |
| **완료율(0.5)** | 그 영상의 `short_view_events` 중 `completed=true` 비율 | 0 |
| **최신성(0.3)** | `halfLife / (halfLife + age초)`, `halfLife=24시간` — 업로드 24시간이 지나면 절반, 48시간이면 1/3 … 로 서서히 줄어든다(가정값, 실측 전) | — (영상은 항상 `createdAt`이 있다) |
| **상품 선호 일치(0.2)** | 시청자가 최근 관심(완료 또는 상품탭)을 보인 영상들에 달린 상품 id 집합과, 지금 영상에 달린 상품 id의 겹치는 비율 | 0(영상에 상품이 없거나 시청자 이력이 없으면) |

**정렬**: 점수 내림차순. **동점이면 최신순**(id 내림차순 — "id가 생성 순서"라는 이 저장소의 R26
관례와 같다). 비교자가 전부 입력(후보 목록·신호·`now`)의 함수이므로 **같은 요청은 항상 같은
순서**다.

**범위**: 전체 카탈로그를 재정렬하지 않는다. `ShortsFeedService`가 커서로 가져온 한 쪽(최대
`pageSize+1`개, 기본 11개)만 재정렬한다 — R26의 커서 페이지네이션 계약(다음 쪽 계산)을 그대로
유지하기 위한 의도된 제한이다. "후보 생성(최신순 커서)"과 "재정렬(그 후보 안에서 점수순)"을
나눈 흔한 2단 구조와 같다.

### 가중치 변경 이력

가중치를 바꾸면 이 표에 행을 추가한다(상수만 고치고 기록을 남기지 않으면 "왜 지금 이 값인가"를
복원할 수 없다).

| 날짜 | 완료율 | 최신성 | 상품 선호 일치 | 근거 |
| --- | ---: | ---: | ---: | --- |
| 2026-10-08 | 0.5 | 0.3 | 0.2 | 요구사항(R28)이 정한 초기값. 실측 전 — 완료율을 가장 무겁게 둔 이유는 "다 봤다"가 가장 직접적인 품질 신호이기 때문(가정) |

## 3. R29 — 제한 시간과 폴백

점수 계산(완료율 집계·시청자 이력 조회)이 **150ms** 안에 끝나지 않거나 예외를 던지면, 피드는
**그대로 200을 돌려주되** `items`를 원래 순서(최신순 READY)로, 응답에 `fallback=true`를 싣는다.
`items` 자체는 폴백 여부와 무관하게 항상 READY만 담는다 — 폴백은 "개인화를 못 했다"이지 "피드가
고장났다"가 아니다.

**150ms의 근거**: 이 계산은 네트워크 호출이 아니라 DB 집계 질의 1~2회(후보 한 쪽 ≤11건, 시청자
이력 ≤50건)뿐이라 정상적으로는 수 ms 안에 끝난다. `personalization/docs/01-architecture.md`가
적은 "online은 지연 제약, 느리면 폴백" 원칙을 따르되, 숏폼 피드가 이 지연을 전체 요청 지연에
얹는다는 점을 고려해 이 저장소의 다른 온라인 경로 예산(R15 수량 선점 거절 p95 200ms)보다 작은
값을 여유 있게 잡았다. **실측값이 아니라 가정값**이다 — 실제 부하로 완료율·이력 질의 시간을
재면 이 값을 다시 본다(아래 "다시 볼 조건").

## 4. 다시 볼 조건

1. **실제 트래픽이 생기면** — 완료율·최신성·선호 일치 신호가 실제로 체류·구매와 상관이 있는지
   재야 한다. 지금 가중치는 측정이 아니라 요구사항이 준 초기값이다.
2. **150ms가 자주 걸리면(폴백률이 높아지면)** — `app.shorts.personalization.timeout-ms`로
   조정한다. 반대로 거의 안 걸리면 줄여서 더 빨리 포기하게 할 수도 있다.
3. **후보 창(pageSize+1)이 좁아 재정렬 효과가 작으면** — 후보 생성 자체를 넓히는 설계(더 많이
   가져와 재정렬 후 자르기)로 바꾼다. 지금은 R26의 커서 계약을 건드리지 않는 쪽을 택했다.

# 트레이드오프 후보 로드맵

정답이 하나로 정해지지 않는 문제만 모은 목록이다. **각 항목은 "무엇을 포기할지 사람이 먼저 정해야 시작되는" 종류**이고, 그래서 자동화로 대신 풀 수 없다.

이 문서는 실행 지시서다. 항목 하나를 집어 그대로 따라가면 ADR 한 건과 측정 하나가 나온다.

## 이 목록을 쓰는 법

1. **"지금 상태" 를 먼저 코드로 확인한다.** 이 문서의 서술이 낡았을 수 있다. 확인 명령을 같이 적어 뒀다
2. **재기 전에 고르지 않는다.** 측정 없이 고른 값은 상한이 아니라 그냥 천장이다
3. **없는 표본을 만들어 채우지 않는다.** 가정으로 만든 값은 "가정 시나리오"로 표시하고 실측이라고 쓰지 않는다
4. 끝나면 **ADR 을 쓰고 상태를 적는다.** 채택·미결·기각 중 하나이고, 미결이면 **고르기 전에 확인할 것**을 남긴다

## 지금까지 닫은 것

| | 주제 | 결론 | 근거 |
|---|---|---|---|
| A | 느린 PG 앞의 자원 고갈 | 동시 호출 상한 채택, 기본 40 | [ADR-022](adr/ADR-022-pg-brownout-resource-limits.md) · [성능 14절](performance/README.md) |
| B | 정산 집계일과 귀속일 | 집계일 의미는 유지, 구성 조회만 추가 | [ADR-023](adr/ADR-023-settlement-earned-date-vs-swept-date.md) |
| C | 정산 분리 시 과거 데이터 이관 | 미결 항목만 이관(C 안), 전환 예행 완료 | [ADR-024](adr/ADR-024-settlement-extraction-data-cutover.md) |

## 밖에서 받은 지적 (2026-09-19)

정산 분리 회고를 공개하고 받은 피드백이다. **5~8 번 항목이 여기서 나왔다.** 요지는 넷이다.

1. **실행 단위 분리와 저장소 분리를 한 덩어리로 다뤘다.** 실험이 재현한 두 결합(scaling · deployment)은 **배포 단위만 나눠도 풀린다.** 저장소·브로커까지 간 것은 별도의 선택인데 그 근거를 따로 적지 않았다
2. **항목 없음은 전환만의 문제가 아니다.** 이벤트 순서 역전은 정상 운영에서도 가능하므로, 그 복구 경로는 전환용 임시 장치가 아니라 상시 정합성 문제다
3. **이관 중 델타를 안 다뤘다.** 복사 시작과 끝 사이에 들어온 승인·취소·환불
4. **커밋 후 발행 실패 구간을 검증하지 않았다**

**2 번은 이미 답이 있었다.** 항목 없음은 재전달로 풀리고, 끝내 안 풀리면 대사가 잡는다. 다만 **글에 그 구조를 안 써서** 실시간 이벤트 하나에 돈이 걸린 것처럼 읽혔다. 같은 지적으로 "승인 → 매입 → 정산 → 지급으로 업무 단계를 나눠 보라"도 받았는데, 그 답은 [docs/02](02-결제도메인-핵심개념.md) 에 이미 적혀 있다. **매입은 PG·카드사 업무라 상태로 두지 않고, 매입이 만드는 시차만 지급예정일로 모델링했다.**

**설계가 없어서 받은 지적이 아니라, 있는 설계를 글에 못 써서 받은 지적이 절반이다.** 나머지 절반(1·3·4)은 진짜로 비어 있다.

**A·B·C 에서 반복된 패턴이 있다. 셋 다 "데이터가 없어 못 고른다"로 미뤄 뒀는데, 코드를 읽으니 답이 이미 코드에 있었다.** A 는 워커 점유, B 는 하루 500건 천장, C 는 스키마 불일치와 오프셋 순서였다. **새 후보를 잡을 때도 측정 설계보다 먼저 코드를 읽는다.**

## 1. 원장 잔액을 어떻게 읽을 것인가

> **상태: 닫힘(2026-09-19)** — [ADR-025](adr/ADR-025-ledger-balance-read-strategy.md). `SUM(signed amount)` + `(account, direction, amount)` 커버링 인덱스 채택. 스냅샷은 계정별 전체 조회 약 60만 행 / 한 계정 조회 약 130만 행에서 필요해짐(실측). 채택 전에 **잠복 버그**를 하나 잡았다 — `AccountType`은 `CASH`·`PG_FEE`를 쓰는데 DB enum은 2개뿐이라 입금 분개가 저장 불가였다(V50). 성능 리포트 16절.

### 무엇을 고르는 문제인가

| 선택 | 얻는 것 | 잃는 것 |
|---|---|---|
| 매번 `SUM(entries)` | 항상 정확하다. 원장이 유일한 진실이다 | 행이 쌓일수록 느려진다 |
| 잔액 스냅샷 컬럼 유지 | 조회가 상수 시간이다 | **스냅샷과 원장이 갈라질 수 있다**는 새 불변식이 생긴다 |
| 일 단위 스냅샷 + 그 이후만 SUM | 둘의 절충 | 스냅샷 시점 **이전**으로 들어오는 취소·정정을 어떻게 볼지 다시 갈린다 |

회계는 append-only 가 원칙이라 지우고 다시 쓸 수 없다. 그래서 "틀리면 고친다"가 성립하지 않는다.

### 지금 상태 (2026-09-19 확인)

```bash
grep -rn "잔액" commerce/src/main/java/com/beomsu/becommerce/ledger/package-info.java
grep -rn "SUM(" commerce/src/main/java/com/beomsu/becommerce/ledger/            # 없음
grep -n "create table ledger_entries" -A 8 commerce/src/main/resources/db/migration/V1__init.sql
```

- `ledger/package-info.java` 가 **"잔액은 엔트리의 합으로 파생된다"** 고 이미 선언한다. 스냅샷 컬럼은 없다
- **그런데 잔액을 읽는 쿼리가 아무 데도 없다.** 선언만 있고 그 선언을 쓰는 코드가 없다. **SUM 을 고르고 그 대가를 한 번도 치른 적이 없다**
- `ledger_entries(id, transaction_id, account ENUM, direction ENUM, amount)` 이고 **`account` 에 인덱스가 없다.** 계정별 합계는 풀스캔이다
- 로컬 기준 33,970 행. 결제 한 건마다 분개가 쌓이므로 행 수는 거래량에 비례해 단조 증가한다

### 할 일

1. **잔액 조회를 먼저 만든다.** `AccountType` 별 잔액을 `SUM(signed_amount)` 로 내는 조회와 어드민 엔드포인트. 이게 없으면 잴 대상이 없다
2. **행 수를 늘려 가며 잰다.** 10만 · 100만 · 1000만. 각 구간에서 잔액 조회 p95 를 잰다. `docs/performance/` 의 기존 형식(전후 실측)을 따른다
3. **인덱스를 붙여 다시 잰다.** `(account, id)` 커버링 인덱스로 얼마나 벌 수 있는지. **인덱스만으로 충분한 구간이 어디까지인지**가 이 실험의 핵심이다
4. **스냅샷이 필요해지는 지점을 찾는다.** SLO 를 먼저 정한다(예: 잔액 조회 p95 200ms). 그 선을 넘는 행 수가 스냅샷 도입 조건이 된다
5. **스냅샷을 만들지는 4번 결과로 정한다.** 필요 없으면 만들지 않고 "언제 필요해지는지"만 ADR 에 적는다

### 성공 기준

"SUM 이 느려진다"가 아니라 아래 형태의 문장이 나오면 끝이다.

> 원장 N 행에서 계정별 잔액 조회 p95 는 X ms 다. `(account, id)` 인덱스로 Y ms 가 되고, 그 구간은 M 행까지 유지된다. M 을 넘으면 스냅샷이 필요하고, 그때 새로 생기는 불변식은 Z 다.

### 주의

- **원장에 쓰기를 늘리지 마라.** 이 실험은 읽기 비용을 재는 것이다. 분개 로직은 건드리지 않는다
- 인덱스를 추가하면 **쓰기 비용도 같이 는다.** `docs/performance` 에 인덱스 쓰기 비용 실측(`IndexWriteCostMySqlTest`)이 이미 있으니 같은 방식으로 같이 잰다
- 스냅샷을 만들기로 하면 **대조 배치가 반드시 같이 나와야 한다.** 스냅샷과 원장이 갈라졌을 때 알아채는 수단 없이 스냅샷만 두는 것은 하지 않는다

### 산출물

- `docs/adr/ADR-025-ledger-balance-read-strategy.md`
- `docs/performance/README.md` 새 절
- 테스트: `LedgerBalanceReadCostMySqlTest` (`@Tag("integration")`)

## 2. 이벤트 스키마를 바꿔야 할 때

> **상태: 닫힘(2026-09-19)** — [ADR-026](adr/ADR-026-event-schema-evolution.md). 필드 추가 호환을 테스트로 고정(추가는 소비자 배포 없이 안전, Jackson `FAIL_ON_UNKNOWN_PROPERTIES` 설정에 달림). **삭제가 위험한 진짜 이유는 예외가 아니라 조용함** — 옛 소비자의 기본형 필드가 `0` 이 되고 스키마 검사로도 안 잡힌다. 배포 순서 규칙(삭제는 소비자→발행자, 그 사이 롤백 금지)을 이 문서에 못 박았다.

### 무엇을 고르는 문제인가

| 선택 | 얻는 것 | 잃는 것 |
|---|---|---|
| 필드를 절대 지우지 않는다(추가만) | 소비자가 언제 배포되든 안 깨진다 | 스키마가 영원히 자란다. 안 쓰는 필드가 계약에 남는다 |
| 버전을 나눠 토픽을 새로 판다 | 정리가 가능하다 | 전환 기간에 **두 토픽을 동시에 처리**해야 한다 |
| 소비자를 먼저 올리고 필드를 지운다 | 정리가 가능하다 | **배포 순서가 강제된다.** 롤백하면 순서가 거꾸로 꼬인다 |

### 지금 상태

```bash
grep -rn "@Externalized" commerce/src/main/java --include=*.java | head
git show msa-extraction:contracts/src/main/java/com/beomsu/paycontracts/PayTopics.java
```

- 이벤트는 `@Externalized` 로 Kafka 에 나간다([ADR-005](adr/ADR-005-event-externalization-kafka.md)). `msa-extraction` 브랜치에는 `BE-commerce-contracts` 아티팩트로 계약이 분리돼 있다(그 브랜치의 ADR-015)
- **버전 규약이 없다.** 지금은 소비자가 하나(정산 서비스)라 드러나지 않는다
- 전환 예행에서 확인된 사실 하나: **소비자의 저장소 스키마가 발행자와 다를 수 있다**(ADR-024). 계약이 같아도 소비자 내부가 다르면 같은 문제가 난다

### 할 일

1. **필드 추가 호환을 먼저 고정한다.** 새 필드가 있는 페이로드를 옛 소비자가 무시하고 지나가는지 테스트로 박는다. Jackson 설정 하나로 갈리는 자리다
2. **필드 삭제 시나리오를 예행한다.** 소비자를 먼저 올리고 발행자를 나중에 올리는 순서, 그리고 **그 중간에 롤백**해 본다. 어디서 깨지는지가 결과다
3. **배포 순서를 문서로 못 박는다.** "이 변경은 소비자 먼저" 같은 규칙이 계약 파일 옆에 있어야 한다

### 성공 기준

> 필드 추가는 소비자 배포 없이 안전하다. 삭제는 소비자 → 발행자 순서가 강제되고, 그 사이 롤백하면 X 가 깨진다. 그래서 삭제는 Y 주기 안에 끝내거나 하지 않는다.

### 주의

- 계약을 바꾸면서 **의미를 같이 바꾸지 마라.** 필드 이름은 같은데 뜻이 달라지는 변경이 제일 위험하고, 스키마 검사로 안 잡힌다

### 산출물

- `docs/adr/ADR-026-event-schema-evolution.md`
- 테스트: 옛 소비자 × 새 페이로드, 새 소비자 × 옛 페이로드 양방향

## 3. 큰 가맹점 하나가 전체를 느리게 만들 때

> **상태: 닫힘(2026-09-19)** — [ADR-027](adr/ADR-027-settlement-fairness-policy.md). 불공정을 재현: 대형이 틱의 100%를 차지하면 소형 정산이 **2일 지연**. 라운드로빈(상한+재분배)으로 **0일**이 되고, 대가는 **대형 첫날 지급 1000→500건**. 정책을 구현했으나 **지급일 약속이 바뀌는 사업 결정이라 기본 off**. 실험 중 `PAYOUT_HELD`가 DB enum에 없어 지급 보류가 터지는 잠복 버그를 찾아 수정(V52).

### 무엇을 고르는 문제인가

**처리량 ↔ 공정성.** 대형 가맹점에 큐를 몰아주면 소형이 굶고, 공평하게 나누면 대형 처리가 밀린다. 둘 다 좋게 만들 수는 없고, **누구를 굶길지 정하는 문제**다.

### 지금 상태

```bash
grep -rn "groupingBy(SettlementItem::getSellerId)" commerce/src/main/java
grep -n "read-chunk-size\|settlement-max-pages" commerce/src/main/resources/application.yml
```

- 정산 배치는 한 틱에 최대 `settlement-max-pages × read-chunk-size` 건을 읽고 **판매자별로 가른다**. 읽는 순서는 `id` 오름차순이다
- 즉 **판매자 한 곳이 그 틱의 페이지를 다 채우면 뒤의 판매자는 다음 틱으로 밀린다.** 지금은 물량이 작아 안 드러난다
- 유입 제어(rate limiter · 대기열 · fast-fail)는 이미 있고 **사용자 단위**다. 판매자 단위 공정성은 없다

### 할 일

1. **불공정을 먼저 재현한다.** 한 판매자가 틱 용량의 대부분을 차지하는 물량을 넣고, 작은 판매자의 정산이 며칠 밀리는지 잰다. B 에서 만든 `SettlementLatenessScenarioTest` 를 확장하면 된다
2. **정책 셋을 비교한다.** (가) 지금처럼 id 순 (나) 판매자별 라운드로빈 (다) 판매자별 상한 + 남는 용량 재분배
3. **각 정책의 대가를 같은 표에 적는다.** 라운드로빈은 대형 판매자의 지급이 늦어지고, 상한은 용량을 놀릴 수 있다

### 성공 기준

> 판매자 하나가 틱 용량의 P% 를 차지하면 다른 판매자의 정산이 D 일 밀린다. 라운드로빈으로 바꾸면 D 는 줄고 대형 판매자의 지급이 E 일 늦어진다.

### 주의

- **샤딩 키 이야기로 넘어가지 마라.** 이 저장소는 단일 DB 다. 핫 파티션은 이 단계에서 다룰 문제가 아니고, 다루려면 분리가 먼저다
- 공정성 정책을 바꾸면 **지급일 약속이 바뀐다.** 기술 결정이 아니라 사업 약속이라는 것을 ADR 에 적는다

### 산출물

- `docs/adr/ADR-027-settlement-fairness-policy.md`

## 4. FDS 임계값을 운영에서 어떻게 움직일 것인가

> **상태: 닫힘(설계만, 2026-09-19)** — [ADR-028](adr/ADR-028-fds-threshold-with-delayed-labels.md). 지연 라벨 평가 설계(확정/잠정 분리), 비용 함수 `cost = FN·C_fraud + FP·C_falseAlarm`, 차단 건 미지의 낙관 편향을 명시했다. **숫자는 만들지 않았다** — 라벨(차지백)이 없고, 합성 표본으로 임계를 정하면 이 저장소가 이미 겪은 실패(상황 6.2)를 반복한다. 로드맵도 이 항목은 "설계와 한계를 적는 것으로 끝낸다"고 했다.

### 무엇을 고르는 문제인가

**미탐 비용(사기 손실) ↔ 오탐 비용(정상 고객 차단).** 두 비용의 단가가 다르고, 그 비율을 정하는 것은 기술이 아니라 사업 판단이다.

### 왜 어려운가

- **정답 라벨이 수십 일 뒤에 온다**(차지백). 지금 임계를 바꾸면 효과는 한참 뒤에 확인된다
- **막은 건은 사기였는지 영원히 모른다.** 차단된 거래에는 결과가 없다

### 지금 상태

```bash
ls docs/26-*.md docs/27-*.md 2>/dev/null
grep -rn "threshold\|임계" commerce/src/main/java/com/beomsu/becommerce/fraud/ | head
```

- 규칙별 오탐과 켤 조건이 [docs/26](26-FDS-규칙별-오탐.md)·[docs/27](27-FDS-모델-평가와-켤-조건.md) 에 있다. ML 점수는 **심사 큐 정렬에만** 쓰고 결제를 막지 않는다. **FDS 전용 ADR 은 아직 없다** — 이 항목의 산출물이 그 첫 ADR 이 된다
- 차지백 웹훅 경로가 있다(`ChargebackWebhookController`). **지연 라벨의 출처가 이미 코드에 있다**

### 할 일

1. **지연 라벨 평가 설계를 먼저 쓴다.** 코드보다 문서가 먼저다. 언제 라벨이 확정되는지, 그 전까지 성적을 어떻게 볼지
2. **두 비용의 단가를 파라미터로 둔다.** 사기 손실 1건과 오탐 1건의 비용비를 설정값으로 두고, 임계를 움직이며 **비용 합**을 그린다
3. **막은 건의 미지(未知)를 명시한다.** 차단된 거래는 라벨이 없으므로 평가에서 어떻게 다룰지 정한다. 빼면 낙관 편향이 생긴다

### 성공 기준

> 비용비를 1:R 로 두면 최적 임계는 T 다. R 이 바뀌면 T 는 이렇게 움직인다. 다만 차단 건의 라벨이 없어 이 추정에는 X 만큼의 낙관 편향이 있다.

### 주의

- **라벨이 없으면 숫자를 만들지 마라.** 이 항목은 다른 것들보다 "설계만 남고 숫자가 안 나올" 위험이 크다. 그 경우 **설계와 그 한계를 적는 것으로 끝낸다**
- 합성 표본으로 임계를 정하지 않는다. 이 저장소는 합성 표본 때문에 이미 한 번 결론이 뒤집힌 적이 있다(상황 6.2)

- `docs/adr/ADR-028-fds-threshold-with-delayed-labels.md`

## 5. 실행 단위만 분리하는 것과 저장소까지 분리하는 것 (외부 피드백 · 다음으로 할 것)

> **상태: 닫힘(2026-09-19)** — [ADR-029](adr/ADR-029-deployment-unit-vs-service-boundary.md). 같은 jar + `worker` 프로파일로 배포 단위만 나눠 실험 2·3을 재실행: **스케줄러 중복 0**(API 2 + 워커 1), **배포 중단 270건 → 0건**(워커 재배포 중 결제 무중단). 두 결합은 배포 단위만 나눠도 풀린다. 저장소 분리는 별도 선택으로 남긴다. 성능 리포트 15절.

### 무엇을 고르는 문제인가

정산 분리 실험이 **재현한 것은 두 가지뿐이다.** 결제를 확장하면 정산 스케줄러도 복제된다(scaling coupling), 무관 모듈 배포가 결제를 중단시킨다(deployment coupling). **둘 다 실행 단위를 나누면 풀린다.**

| 선택 | 얻는 것 | 잃는 것 |
|---|---|---|
| **같은 코드·같은 DB, 배포 단위만 분리** (API 디플로이 / 배치 워커 디플로이) | 두 결합이 풀린다. **트랜잭션과 조인이 그대로 남는다** | 코드베이스는 여전히 하나. 팀이 나뉘면 다시 걸린다 |
| **서비스·저장소·브로커까지 분리** | 완전한 독립. 다른 팀·다른 언어도 가능 | 트랜잭션이 사라지고 **메시지 중복·순서·poison·대사·이관**이 전부 새로 생긴다 |

**지금 문서는 둘을 한 덩어리로 다뤘다.** 실험은 첫째까지만 증명하고, 둘째로 간 것은 **별도의 선택인데 그 근거를 따로 적지 않았다.**

### 할 일

1. **배포 단위만 나눈 형태를 먼저 만든다.** 같은 jar, 프로파일로 `scheduler` 활성 여부를 가르고 디플로이를 둘로 나눈다
2. **결정 8 의 실험 2·3 을 그 형태에 그대로 돌린다.** 스케줄러 중복이 사라지는지, 배포 중단 270건이 0 이 되는지
3. **0 이 되면 그것이 기준선이다.** 그 위에서 "서비스·DB·브로커까지 나눠서 추가로 얻는 것"이 무엇인지 적는다

### 성공 기준

> 배포 단위만 나눠도 스케줄러 중복과 배포 결합은 0 이 된다. 저장소까지 나눠서 추가로 얻는 것은 X 이고, 그 대가로 새로 생긴 실패 모드는 Y 개다.

**이 실험이 "MSA 를 안 해도 됐다"로 끝나도 그것이 결과다.** 그렇게 나오면 그 사실을 적는다.

### 산출물

- `docs/adr/ADR-029-deployment-unit-vs-service-boundary.md`

## 6. 이관 중에 들어온 변경은 어떻게 할 것인가 (외부 피드백)

> **상태: 닫힘(2026-09-19)** — [ADR-024](adr/ADR-024-settlement-extraction-data-cutover.md) 에 "이관 중 델타" 절 추가. **델타 미탐을 실측으로 재현**(스냅샷 5,063 vs 전환 시점 원본 5,066 → 3건 누락). 고칠 것은 대조 기준 — 스냅샷이 아니라 **전환 시점의 원본**. **목적지 스키마로 예행까지 완료**: 스냅샷 대조 diff 0(놓침) → 원본 대조 diff -1(드러남) → 델타 재복사 diff **0**. 네 선택지 비교표 + (워터마크+델타 재복사) 기본.

### 무엇을 고르는 문제인가

[ADR-024](adr/ADR-024-settlement-extraction-data-cutover.md) 의 절차는 **이관 → 대조 → 트래픽 전환**이다. 그런데 **이관을 시작한 시각과 끝난 시각 사이에 들어온 승인·취소·환불**을 다루지 않는다. 복사에 10분이 걸렸다면 그 10분의 변경분이 새 저장소에 없다.

| 선택 | 얻는 것 | 잃는 것 |
|---|---|---|
| 쓰기 정지(write freeze) | 가장 단순하고 확실하다 | **그 시간 동안 결제가 멈춘다** |
| 워터마크 후 델타 재복사 | 결제가 안 멈춘다 | 델타가 계속 생기면 수렴하지 않을 수 있다 |
| 이중 쓰기 | 델타가 없다 | 두 곳이 다를 때 판정 규칙이 필요하다 |
| 이벤트 재생 | 별도 코드가 없다 | 토픽 보존 기간에 의존한다 |

### 할 일

1. **델타를 먼저 재현한다.** 이관 중에 새 승인을 흘려 넣고, 대조에서 **차이가 잡히는지** 본다. 지금 절차로는 안 잡힐 가능성이 크다
2. 위 네 선택지를 같은 실험에 태워 **정지 시간 · 수렴 여부 · 복잡도**를 표로 만든다
3. 전환 예행을 다시 돌려 **델타까지 포함해 0 이 되는지** 확인한다

### 산출물

- ADR-024 에 "이관 중 델타" 절 추가. 새 ADR 로 쪼개지 않는다. 같은 전환 절차의 일부다

## 7. 커밋은 됐는데 발행이 안 된 구간 (외부 피드백)

> **상태: 닫힘(2026-09-19)** — 장애로 검증했다. Kafka를 내린 채 승인 → SIGKILL → Kafka 복구 → 재기동: **재기동 후 8초 만에 발행**(미완료 0). 재기동 재발행은 Kafka 발행뿐 아니라 **중단된 인-프로세스 리스너까지** 복구한다. 멱등 확인 중 **심사 큐 중복 적재**라는 구멍을 찾아 막았다(V51). 성능 리포트 17절.

### 지금 상태부터 확인한다

```bash
grep -n "republish-outstanding-events-on-restart" commerce/src/main/resources/application.yml
grep -rn "@Externalized" commerce/src/main/java | head
```

**이 자리는 이미 설계돼 있다.** 이벤트 발행이 Spring Modulith Event Publication Registry(= 트랜잭셔널 아웃박스)를 타므로, DB 커밋과 발행 기록이 **같은 트랜잭션**이다. 재기동 시 미완료 이벤트를 다시 발행하는 설정(`republish-outstanding-events-on-restart: true`)도 켜져 있다.

**안 한 것은 그 경로를 장애로 검증한 것이다.** 커밋 직후 프로세스를 죽였을 때 재기동이 정말 발행하는지, 그 사이 소비자가 중복을 어떻게 다루는지를 재현하지 않았다.

### 할 일

1. 커밋 성공 직후 **프로세스를 강제 종료**한다. 재기동 후 이벤트가 나가는지 본다
2. **몇 초 만에** 나가는지 잰다. 그 시간이 정산 지연의 하한이다
3. 재발행으로 소비자가 **같은 이벤트를 두 번** 받았을 때 멱등이 성립하는지 확인한다

### 주의

- **"아웃박스를 썼으니 됐다"로 적지 마라.** 설계는 있고 검증이 없다는 것이 지금 상태다. 그 둘을 구분해 적는다

### 산출물

- `docs/performance/README.md` 새 절 또는 카오스 테스트 추가(`MySqlChaosTest` 옆)

## 8. 격리·발견·복구·검증을 따로 만든다 (외부 피드백)

> **상태: 닫힘(2026-09-19)** — [ADR-030](adr/ADR-030-dlt-replay-and-post-recovery-reconciliation.md). 코드를 읽으니 **복구(재처리)가 이미 있었다**(`POST /admin/dead-letters/{id}/reprocess`) — 로드맵 서술이 브랜치의 Kafka DLT 를 가리킨 것이었다. 실제로 비어 있던 둘을 채웠다: ① 재처리가 멱등하지 않아 **이미 처리된 건을 재처리하면 알림이 두 번 나갔다**(멱등 가드 추가), ② 복구 후 검증 표면이 없었다(`GET /admin/dead-letters/summary` 추가).

### 무엇이 문제인가

넷은 **다른 책임**인데 지금은 둘만 있다.

| 책임 | 지금 |
|---|---|
| **격리** 실패 메시지를 보존한다 | 있다 (DLT) |
| **발견** 이상 상태를 찾는다 | 있다 (대사) |
| **복구** 상태를 실제로 되돌린다 | **없다. 손으로 한다** |
| **검증** 복구 후 정말 정상인지 다시 본다 | **없다** |

[결정 9](adr/ADR-024-settlement-extraction-data-cutover.md)에서 DLT 격리를 고른 근거가 "대사가 최종 방어선이라 이탈이 유실이 아니다"였다. **그 근거는 발견까지만 보장한다.** 복구가 수동이면 발견과 복구 사이가 사람의 속도로 벌어진다.

### 할 일

1. **DLT 재처리 어드민**을 만든다. 격리된 메시지를 조회하고 재발행한다
2. **재처리는 멱등**이어야 한다. 이미 처리된 건을 다시 넣어도 이중 반영되지 않는 것을 테스트로 고정한다
3. **복구 후 대사를 다시 돌려** 불일치가 사라졌는지 확인한다. 이것이 네 번째 책임이다

### 성공 기준

> poison 을 주입해 DLT 로 격리하고, 대사가 그것을 불일치로 잡고, 재처리로 복구하고, 다시 돌린 대사에서 불일치가 0 이 되는 것까지 한 번에 확인한다.

### 산출물

- `docs/adr/ADR-030-dlt-replay-and-post-recovery-reconciliation.md`

## 9. 무중단 스키마 변경과 되돌릴 수 없는 지점 (이 저장소 소재가 아님)

> **상태: 범위 밖(기록만, 2026-09-19)** — 로드맵 판단대로 BE-commerce 에서 하지 않는다. BE-commerce 는 단일 인스턴스 로컬 MySQL 이라 복제 지연을 잴 대상이 없다. DBTower 소재로 넘긴다. **BE-commerce 에서 다만 관련 있는 것**: 이번 작업에서 DB enum 과 코드 enum 이 어긋나 조용히 터지는 잠복 버그를 **둘** 찾았다(원장 `AccountType` V50, 정산 `PAYOUT_HELD` V52). 스키마 변경이 코드와 어긋날 때 검사로 안 잡힌다는 것이 무중단 스키마 문제의 한 단면이다.

**맞바꾸는 것**: 컷오버 락 시간 ↔ 복제 지연 ↔ 디스크. 셋이 동시에 좋아지지 않는다.

**여기 적어 두되 BE-commerce 에서는 하지 않는다.** 이 주제는 DBTower 에 변경 리뷰 게이트와 gh-ost 안내가 이미 있어 그쪽 소재다. BE-commerce 는 단일 인스턴스 로컬 MySQL 이라 복제 지연을 잴 대상이 없다. **BE-commerce 포트폴리오에 넣으면 겉돈다.**

DBTower 쪽에서 할 때의 뼈대만 남긴다.

1. 쓰기가 도는 중에 변경을 건다
2. 복제 지연과 실패 건수를 잰다
3. **중간에 취소해 본다.** 되돌릴 수 없는 지점이 어디인지가 결과다
4. 컬럼 삭제는 **배포 순서**(코드 먼저냐 스키마 먼저냐)를 틀리면 서비스가 죽는다. 롤백 계획이 없으면 그 변경은 못 하는 변경이다

## 10. 결제 포트폴리오 핵심 증거

> **상태: 핵심 설계·단위 검증 닫힘 / 실 PG 운영 검증 미결(2026-09-22)** — 기능을 추가하지 않고 결제 시스템의 판단 근거를 4~5페이지 서사로 압축한다. 상세 기준은 [결제 의사결정 검증](29-결제-의사결정-검증.md), 제출용 초안은 [결제 포트폴리오 초안](30-결제-포트폴리오-초안.md)에 둔다.

### 현재 닫힌 근거

- 승인 타임아웃을 `UNKNOWN`으로 보존하고 조회·웹훅·복구 배치로 확정한다
- 승인 후 내부 실패를 독립 보상 취소로 처리한다
- 웹훅 중복·순서 역전을 payload가 아닌 조회 API 기준으로 수렴시킨다
- 느린 PG에서 동시 호출 상한으로 일반 API 자원을 보호한다
- 복합결제 환불 배분과 원장 차변=대변 불변식을 테스트한다
- 카드 데이터를 받지 않는 경계를 PCI 면제가 아니라 카드 데이터 환경 축소로 설명한다

> 지금 남은 것은 **10 번의 "다음에 확인할 것"** 뿐이고, 그중 둘(UNKNOWN 복구 실측·PG 브라운아웃 회귀)은

## 하지 말 것

- **한 번에 두 항목을 열지 마라.** ADR 이 서로를 인용하기 시작하면 어느 쪽도 못 닫는다
- **측정 전에 코드를 고치지 마라.** A·B·C 에서 세 번 다 "고치려고 읽다가 진짜 원인을 찾았다"
- **결론이 "더 조사가 필요하다"로 끝나면 그건 안 닫은 것이다.** 미결이면 **고르기 전에 확인할 것**을 구체적으로 적어야 닫은 것으로 친다

# 20. 분쟁 증빙 조립: 규칙 기반 수집과 사람 검토

> 상태: 구현 완료. 증빙을 조립하되 외부 제출은 자동화하지 않는다.

## 0. 왜 이걸 하나

이의제기가 들어오면 정해진 기한 안에 증빙을 제출해 다퉈야 한다. 그런데 지금 코드는 이렇다.

```java
public DisputeView submitEvidence(Long id, String memo) {
    dispute.submitEvidence(memo);   // 자유 텍스트 한 덩어리
}
```

**사람이 열한 개 도메인을 뒤져 손으로 쓴다.** 주문이 언제 들어왔고, 결제가 어떤 수단으로
승인됐고, 구매확정이 났고, 환불이 있었는지를 각각 다른 화면에서 찾아 문단으로 만든다.

기한은 대개 7~14일이고, 놓치면 다툴 기회 자체가 사라진다(19 문서에서 그 기한에 알림을 붙였다).
그런데 **알림이 울려도 증빙을 모으는 데 드는 시간은 그대로다.**

## 1. 업계는 이 자리를 자동화한다

- **Stripe Smart Disputes**: 연결 계정을 대신해 증빙을 자동으로 모아 제출한다
- **PayPal**: AI 분쟁 해결로 **처리 시간 80% 단축**을 보고한다
- 공통 통합 지점으로 Stripe disputes · PayPal cases · Shopify orders · Adyen notifications 가 꼽힌다

즉 **흩어진 사실을 하나의 주장으로 엮는 일**이고, 이 프로젝트에서 이미 한 번 판단한 모양이다.
운영자용 서술을 켤 때 근거가 "규칙은 문장을 못 쓴다"였다(18 문서).

## 2. 이 프로젝트가 이미 가진 것

새로 모을 데이터가 없다. 타임라인 조립기가 열한 개 도메인을 이미 한자리에 모은다.

```
ORDER · PAYMENT · LEDGER · SETTLEMENT · ESCROW · RECONCILIATION
POINT · WALLET · AUDIT · DISPUTE · (그 밖)
```

가드도 그대로 쓸 수 있다.

- `NumericProvenanceGuard` — 사실 목록에 없는 숫자가 섞이면 버린다
- `AmountCoverageGuard` — 있어야 할 금액을 빠뜨리면 버린다

**증빙에서 이 둘이 특히 중요하다.** 지어낸 숫자가 섞인 증빙을 카드사에 내면 그 건만
지는 게 아니라 이후 다툼의 신뢰를 잃는다. 금액이 빠진 증빙은 그냥 안 낸 것과 같다.

## 3. 두 층으로 나눴다

**항목 조립은 규칙이다.** 어느 줄이 어느 항목에 속하는지는 그 줄의 출처가 이미 말해 준다.
`PAYMENT`로 시작하는 줄은 결제 사실이고 `ESCROW`는 이행 사실이다. 추론할 것이 없는 자리에
모델을 부르면 지연과 오류만 는다.

```
거래 성립      ORDER · PAYMENT
대금 흐름      LEDGER · SETTLEMENT
이행 증빙      ESCROW
환불·취소 이력  POINT · WALLET
대사 결과      RECONCILIATION
이전 분쟁      DISPUTE
운영자 조치     AUDIT
```

**요약 문장만 모델이다.** 흩어진 사실을 하나의 주장으로 엮는 자리라 규칙이 문장을 못 쓴다.
18 문서에서 운영자용 서술을 켠 것과 같은 논리다.

### 못 채운 항목을 드러낸다

항목이 비면 그 자리를 **빈 채로 두고** 이름을 `gaps`에 올린다.

없는 사실을 그럴듯한 문장으로 메우는 것이 이 기능의 가장 큰 위험이다. 카드사가 한 번 잡으면
**그 건을 지는 것으로 끝나지 않고** 이후 다툼의 신뢰를 잃는다. 비어 있는 것이 보이면
사람이 다른 자료를 찾거나, 약점을 아는 채로 낼 수 있다.

### 요약이 실패해도 증빙은 나간다

가드 둘을 그대로 건다. 지어낸 숫자(`NumericProvenanceGuard`)와 빠뜨린 금액
(`AmountCoverageGuard`)이다. 걸리면 **요약만 버리고 항목은 그대로 낸다.**

요약을 못 만든다고 증빙 전체를 버리면 기능이 없는 것과 같다. 항목만 나가도 사람이 열한 곳을
뒤지던 것보다는 낫다.

### 자동 제출은 안 한다

카드사에 낸 증빙은 되돌릴 수 없다. 그리고 이 시스템은 **승소율을 재 본 적이 없다** —
실측 없이 자동화하지 않는다는 순서를 여기서도 지킨다. 모아만 주고 제출은 사람이 한다.

## 4. 모듈 경계가 설계를 고쳤다

처음에 `dispute` 모듈 안에 뒀다. Modulith 검사가 막았다.

```
Cycle detected: assist -> timeline -> dispute -> assist
```

`timeline`이 이미 `dispute`의 사실을 모으고 있어서, `dispute`가 `assist`를 참조하는 순간
순환이 된다. **증빙 조립은 열한 개 도메인을 가로질러 읽는 일이고 그건 `assist`가 하는 일**
이라는 것을, 검사가 먼저 말해 줬다.

`assist/evidence`로 옮기고 창구도 주문번호로 받게 바꿨다
(`GET /api/v1/admin/orders/{orderNo}/dispute-evidence`).

## 5. 남는 것

- **승소율을 못 잰다.** 실제 분쟁이 없다. 이 기능이 다툼에 도움이 되는지는 아직 모른다
- **항목 구성이 카드사 요건과 정확히 맞는지 확인 못 했다.** 공통으로 요구되는 것을 따랐지만
  카드사·매입사마다 다르고, 실계약 없이는 그 스펙을 못 본다
- 요약 모델은 서술과 같은 것을 쓴다. 증빙용 프롬프트를 따로 재지 않았다

# 13. 상담 답변 초안: 실측 기록

*관련: [ADR-014](adr/ADR-014-cs-draft-port-and-number-guard.md), [ADR-012](adr/ADR-012-rule-based-cause-classifier.md), [11 AI 운영자동화 검토](11-AI-운영자동화-검토.md)*

---

## 왜 이 실험을 했나

ADR-014 에서 상담 초안 포트를 만들고 모델은 붙이지 않았다. 그때의 판단은
"모델을 붙일 가치가 있는지 모르니 잣대부터 만든다"였다.

그런데 잣대만 만들고 재지 않으면 잣대인지 알 수 없다. **실제 데이터를 흘려봐야 한다.**
그래서 앱을 띄우고 진짜 대사 불일치를 만들어 파이프라인 전체를 통과시켰다.

**구성한 것이 아니라 앱이 실제로 만들어낸 상태다** — 주문 생성 → 결제 승인 → (일부는) 부분취소
→ PG 정산 CSV 업로드 → 대사 실행 → 예외 큐 → 원인 제안 → 초안 생성 → 숫자 검증.

## 실험 0. 진짜 데이터를 흘렸더니 검증기가 자기 초안을 반려했다

### 만든 시나리오 (실제 API 호출)

| 케이스 | 만든 방법 | 대사 결과 |
|---|---|---|
| 수수료 차감 | 승인 10,000원 → 정산 파일에 9,730원 | `AMOUNT_MISMATCH` |
| 부분취소 미반영 | 승인 후 3,000원 실제 취소 → 파일에 7,000원 | `AMOUNT_MISMATCH` |
| 설명 안 되는 차액 | 승인 10,000원 → 파일에 1,112원 | `AMOUNT_MISMATCH` |
| 내부에만 있음 | 승인만 하고 파일에서 제외 | `INTERNAL_ONLY` |
| 외부에만 있음 | 파일에만 있는 주문번호 | `EXTERNAL_ONLY` |

### 결과. 4건 중 2건 오반려 (50%)

```
id=1  FEE_CALCULATION_DIFF  (DECISIVE)  verified=false
      rejected=['출처에 없는 금액: 270원', '출처에 없는 금액: 270원']
id=3  SUSPECTED_TAMPERING   (WEAK)      verified=false
      rejected=['출처에 없는 금액: 8,888원', '출처에 없는 금액: 270원']
id=4  PG_FILE_DELAY         (LIKELY)    verified=true
id=5  INTERNAL_RECORD_LOST  (LIKELY)    verified=true
```

**하필 최악의 두 건이 걸렸다.**

- `FEE_CALCULATION_DIFF` — **확신이 가장 높은 규칙**(DECISIVE). 차액이 수수료율과 원 단위까지 맞는 건
- `SUSPECTED_TAMPERING` — **초안이 가장 필요한 건**. 근거가 "설명되지 않는다"뿐이라 사람이 처음부터 조사해야 한다

### 원인. 검증기의 계약이 잘못 정의돼 있었다

반려된 8,888 과 270 은 **분류기가 계산한 근거**다.

> `차액 8,888원이 수수료(270원)로도 취소로도 설명되지 않는다`

이 숫자들은 타임라인 항목의 금액이 아니라 `CauseClassifier`가 산출한 값이다.
그런데 `FactPack.amounts()`가 타임라인 금액만 모으고 있었다.

**검증기가 지키려던 것은 "타임라인에 있는 숫자만 써라"가 아니다.**
**"코드가 낸 숫자만 쓰고 모델이 지어낸 숫자는 쓰지 마라"**가 맞다.
분류기는 코드이므로 그 근거의 숫자는 통과해야 한다.

### 왜 테스트가 못 잡았나

단위 테스트 7개가 전부 통과하고 있었다. **전부 손으로 만든 `FactPack`을 썼기 때문이다.**
내가 만든 입력에는 내가 넣은 숫자만 있었고, 분류기가 계산한 값이 섞이는 상황이 없었다.

> 실제 데이터를 흘려야만 드러나는 결함이 있다. 이번 건이 그랬다.

### 고친 뒤

| | 고치기 전 | 고친 후 |
|---|---|---|
| 검증 통과 | **2 / 4 (50%)** | **4 / 4 (100%)** |
| 오반려 | `FEE_CALCULATION_DIFF`, `SUSPECTED_TAMPERING` | 없음 |

회귀 테스트 2건으로 고정했다 — 분류기 근거 금액이 통과하는 것과, 그럼에도
근거에 **없는** 숫자는 여전히 걸리는 것. 허용 범위를 넓힌 게 아니라 **제자리로 돌린 것**임을
두 번째 테스트가 지킨다.

### 실제로 나온 초안 (수수료 차감 건, 검증 통과)

```
[주문 01M195R3SMD6SEH13ECYSP9V37 확인 결과]

문의하신 주문 건의 처리 내역을 확인했습니다.

· 2026-08-30 · ORDER · 주문 생성 — 항목 1개
· 2026-08-30 · PAYMENT · 결제 IN_PROGRESS → DONE (USER, TOSS_PAYMENTS) — 승인 완료
· 2026-08-30 · LEDGER · 원장 분개 PAYMENT_APPROVED
· 2026-08-30 · RECONCILIATION · 대사 AMOUNT_MISMATCH — 내부 10,000 / 외부 9,730

확인된 금액: 100원, 270원, 10,000원

추정 원인(규칙 분류): FEE_CALCULATION_DIFF (DECISIVE)
  — 차액 270원 = 내부 10,000원 × 270 bps (기대 수수료 270원)
  ※ 제안일 뿐입니다. 확정은 담당자가 근거를 확인한 뒤 하십시오.
```

## 원인 커버리지. 문서가 코드보다 한 칸 앞서 있었다

같은 흐름에서 하나 더 나왔다.

README 와 ADR-012 는 "8종 중 **6종**이 산수나 조회로 결정된다"고 적어뒀는데
**코드에는 규칙이 5개뿐**이었다. `TIMEZONE_BOUNDARY`는 enum 에만 있고 아무도 내지 않았다.
ADR-012 표에서는 그걸 **자동 확정 후보**로까지 올려놨다.

**왜 못 잡았나**: 개별 규칙 테스트는 "이 입력에 이 원인이 나오는가"를 본다.
그래서 **아무도 안 내는 원인은 영원히 안 보인다.** 반대 방향으로 보는 테스트가 없었다.

`CauseCoverageHarnessTest`가 그 방향을 본다.

| 등급 | 종수 | 원인 |
|---|---:|---|
| 산수로 결정 (DECISIVE) | 4 | 부분취소 미반영 · 수수료 차이 · **거래일 경계** · PG 파일 지연 |
| 정황으로 제안 (LIKELY) | 2 | 승인 직후 취소 · 내부 기록 유실 |
| 배제로 남음 (WEAK) | 1 | 위변조 의심 — **사람이 봐야 한다** |
| 규칙 없음 | 1 | `OTHER` — **AI를 논할 자리** |

**세면서 배운 것**: 처음엔 "7종을 가른다"고 셌다. 위변조 의심까지 넣었기 때문이다.
그런데 그건 배제법으로 **남은** 것이지 결정된 게 아니다.
`결정 = DECISIVE + LIKELY = 6`이 문서의 주장과 맞는 셈법이다.
이 구분이 흐려지면 **"규칙이 대부분을 해결한다"고 과장하게 된다.**

이제 테스트가 그 수를 고정한다. 규칙을 늘리거나 줄이면 깨지므로 문서와 코드가 같이 움직인다.

어댑터는 **모델 없이 배관까지 검증**했다(`OllamaDraftAdapterTest`, 6건). 스텁 HTTP 서버로
응답 파싱·프롬프트 내용·5xx·예상 밖 응답 모양·사실 없을 때 호출 안 함을 고정했고,
**모델이 지어낸 숫자가 어댑터를 통과해도 검증기에 걸리는지**를 끝까지 태워 확인했다.

만들어만 두면 검증되지 않은 코드가 남는다. 실제 모델을 붙이는 날 파싱이 틀려 있으면
그게 모델 문제인지 코드 문제인지 구분하느라 시간을 쓴다. 배관은 지금 고정할 수 있다.

### 섀도 모드가 푸는 문제

초안 품질을 재려면 "사람이 얼마나 고쳤나"를 알아야 하는데, 초안을 보여주면
사람이 그것에 끌려간다(앵커링). 그러면 **"고칠 게 없었다"와 "고칠 생각이 안 났다"가
구분되지 않는다.**

이건 이미 겪고 있는 문제다 — `ClassifierAccuracyMetrics`가 자기 수치를 정확도가 아니라
**"일치율"** 이라고 부르는 이유가 그것이다.

섀도는 그 고리를 끊는다. 사람은 지금처럼 규칙 제안만 보고 확정하고, 초안은 옆에서
조용히 만들어져 기록된다. **정답 답변을 지어내지 않고도 대조가 가능해진다.**
홀드아웃(Stripe)과 selective-labels 대응(Feedzai)이 같은 발상이다.

모듈 순환을 피하려고 이벤트로 끊었다 — `assist`가 `reconciliation`을 의존하므로
반대로 부를 수 없다. 대사는 "확정됐다"고 알릴 뿐 누가 듣는지 모른다.
커밋 뒤에 처리되므로 초안 생성이 느리거나 실패해도 확정은 이미 끝나 있다.

### BYOK: 구독으로는 안 된다

"내 Claude 구독으로 돌릴 수 있나"를 확인했다. **안 된다.**

유료 Claude 구독(Pro/Max)은 Claude 앱과 **Claude Code 자체**를 커버하지만
**API 접근을 포함하지 않고 별도 과금**이다. 증거가 하나 더 있다 —
`ANTHROPIC_API_KEY`가 환경변수에 있으면 **Claude Code 조차 구독을 무시하고 API 요금으로
청구**된다. 완전히 다른 경로다.

대신 "쓰는 사람이 자기 걸로 돌린다"는 발상 자체는 표준 패턴이 있다 — **BYOK**.
운영자가 자기 키를 설정에 넣고 요금은 그 사람 계정으로 나간다.
GitHub Copilot CLI·VS Code·Factory 가 같은 방식이고, Copilot CLI 는
**Ollama 같은 로컬 모델까지 같은 구멍으로** 받는다.

결제 도메인에서는 이게 편의가 아니라 **요건**이다 — "당신 키, 당신 계정, 당신 데이터".

키가 없으면 **기동 시점에 막는다.** 호출 시점에 실패하면 그때야 알게 되고,
그 사이 초안이 조용히 비어 나간다.

## 실험 2. 실제 로컬 모델을 붙였다 (Ollama · Qwen3 8B)

### 왜 Ollama 인가, 왜 이 모델인가

**Ollama는 운영에 쓰는 물건이 아니다.** 자체 호스팅 운영은 보통 **vLLM**(또는 SGLang, TGI)이다.

| | Ollama | vLLM |
|---|---|---|
| 용도 | 개발·테스트·엣지 | **운영 서빙** |
| 최대 처리량 | 41 tok/s | **793 tok/s** |
| P99 지연 | 673ms | **80ms** |

그런데 업계에서 널리 쓰는 구성이 정확히 이것이다 —
**"개발·테스트는 Ollama, 운영은 vLLM, 애플리케이션은 게이트웨이 뒤에서 그대로."**
`DraftPort`가 그 게이트웨이다. 노트북 실험에는 Ollama가 맞고, vLLM 으로 옮겨도 어댑터 하나만 갈린다.

**모델은 처음에 `qwen2.5:7b`로 적었는데 근거 없이 고른 값이었다.**
찾아보니 지금 한국어 로컬 모델은 **Qwen3 8B**가 1순위로 꼽혀 바꿨다.

### 먼저 걸린 것. 추론 토큰과 프롬프트 레이블

**추론 토큰(thinking)**이 켜져 있어 한 건에 19초가 걸렸다. Ollama는 이걸 `thinking` 필드로
분리해 주므로 `content`는 깨끗했지만, 시간이 두 배 넘게 든다. 서술만 시키는 일이라
껐다 — **19초 → 5초대**.

**프롬프트 레이블이 잘못돼 있었다.** `[쓸 수 있는 금액]` 이라고 썼더니 모델이 그걸 *잔액*으로
읽고 이렇게 썼다.

> 사용 가능한 금액은 10,000원과 270원입니다.

목록의 성격을 이름에 박아야 했다 — `[인용해도 되는 금액] — 사실이 아니라 표기 허용 목록입니다`.

### 실측: 4건 × 3회 = 12회

| | 고치기 전 | 고친 후 |
|---|---|---|
| 검증 통과율 | **7 / 12 = 58%** | **12 / 12 = 100%** |
| 지연 중앙값 | 5,493ms | 5,233ms |
| 지연 최대 | 7,828ms | 6,997ms |
| 반려 사유 | `출처에 없는 날짜: 2026-09-06` (5건 전부) | 없음 |

**반려가 전부 같은 값이었다.** 에스크로 사실 문장의 `자동해제 예정 2026-09-06T...` 다.
코드가 만든 진짜 날짜인데, `FactPack.dates()`가 `entry.at()`(사건이 일어난 시각)만 모으고
문장이 말하는 **다른 날짜**를 빠뜨렸다.

### 모델이 템플릿은 못 찾는 결함을 찾았다

이번 실험에서 나온 결함 3건은 **찾을 수 있는 층이 각각 달랐다.**

| # | 결함 | 발견 조건 |
|---|---|---|
| 1 | 분류기가 계산한 근거 금액이 반려됨 | 실데이터 + 템플릿 |
| 2 | 사실 문장 속 금액(`내부 10,000 / 외부 9,730`)이 반려됨 | **실제 모델**만 |
| 3 | 사실 문장 속 날짜(에스크로 해제 예정일)가 반려됨 | **실제 모델 + 반복 실행**만 |

2번은 템플릿이 절대 못 찾는다. 템플릿은 `amounts()`를 그대로 찍을 뿐
**사실 문장을 읽고 인용하지 않기 때문**이다. 3번은 12회를 돌려야 보였다 —
모델이 매번 같은 문장을 쓰지 않으므로 1회 실행으로는 놓친다.

셋 다 뿌리가 같다 — **구조화 필드만 모으고 문장 속 값을 빠뜨린 것.**

### 정규식 하나가 더 있었다

날짜를 뽑을 때 `\b(\d{4}-\d{2}-\d{2})\b`로 짰다가 테스트가 잡았다.
`2026-09-06T11:06`의 `T`는 **단어 문자**라 뒤쪽 `\b`가 성립하지 않는다.
ISO 시각이 통째로 안 잡혔다. `(?!\d)`로 바꿨고, 검증기 쪽 패턴도 같은 이유로 함께 고쳤다.

### 실제로 나온 모델 초안

**수수료 차이 (DECISIVE) — 쓸 만하다**

> 주문번호 01M196J2BAGHT2Z70GYJH4N9M5의 결제는 2026-08-30 승인 완료되었습니다.
> 대사 AMOUNT_MISMATCH로 인해 내부 10,000원과 외부 9,730원의 차액 270원이 발생했습니다. 확인 중입니다.

**위변조 의심 (WEAK) — 쓸 만하지 않다**

> 2026-08-30 결제 승인 완료 및 주문 상태 PAID 확인 중입니다.
> 에스크로 보류 자동 해제 예정일은 2026-09-06입니다.

### 남은 품질 문제: 검증만으로는 안 잡힌다

**숫자는 다 맞는데 내용이 문제다.** 이건 `NumberGuard`의 일이 아니다.

1. **내부 용어가 샌다** — `AMOUNT_MISMATCH`, `PAID` 같은 enum 이 고객용 문장에 그대로 나온다
2. **하필 어려운 건에서 약하다** — 위변조 의심 건은 초안이 가장 필요한 자리인데,
   모델이 정작 문제(설명되지 않는 8,888원 차액)를 말하지 않고 에스크로 일정만 읊었다

> **→ 둘 다 실험 3에서 고쳤다.** 아래 참조.

**2번이 중요하다.** 규칙이 못 가르는 자리에서 모델이 뭔가 해줄 것을 기대했는데,
**작은 로컬 모델로는 거기가 제일 약했다.** 업계 기대치와도 맞는다 — Uber Genie 도움률 48.9%,
Meta 인시던트 RCA 상위 5개 안 42%.

> **그래서 지금 결론**: 검증기는 제 몫을 한다(지어낸 숫자 100% 차단, 오반려 0%).
> 그런데 **초안 품질은 아직 상담원에게 내놓을 수준이 아니다.**
> 다음은 모델을 키우는 것(vLLM + 더 큰 모델)이 아니라 **프롬프트에서 내부 용어를 막고,
> 어려운 건에 어떤 컨텍스트가 더 필요한지**를 보는 것이다.

### 자동화가 얼마나 됐나: 정직하게

| 항목 | 값 | 근거 |
|---|---|---|
| 초안 자동 생성 | **100%** (12/12) | 실측, 사람 개입 0 |
| 지어낸 숫자 차단 | **100%** | 픽스처 + 실측 |
| 오반려 | **0%** (전 50% → 58% → 0%) | 실측 3회차 |
| 초안 생성 지연 | 중앙값 **5.2초** | 실측 12회 |
| **바로 발송 가능한 초안** | **아니다 — 편집률 45%** | 실험 5, n=4 (리뷰어 한계 있음) |

마지막 줄이 핵심이다. **"상담 시간 N% 단축" 같은 숫자는 여기 없다.**
초안을 만들고 검증하는 것까지는 자동화됐지만, **그게 쓸 만한지는 사람이 판단해야** 하고
그 사람이 없다. 있는 것만 적는다.

## 실험 3. 남은 품질 문제를 고쳤다 (용어 누출 · 어려운 건)

실험 2에서 검증은 100% 통과하는데 **내용이 문제**로 남았다. 이건 `NumberGuard`가
잡을 수 있는 게 아니다 — 사실이 틀린 게 아니기 때문이다.

### 업계는 이 둘을 다르게 다룬다

찾아보니 두 문제의 처방이 달랐다.

| 문제 | 처방 | 근거 |
|---|---|---|
| 내부 용어 누출 | **글로서리를 프롬프트에 싣고, 출하 전 용어 검수를 따로 둔다** | 번역 실무의 표준 |
| 어려운 건에서 약함 | **few-shot 예시 — 좋은 예와 나쁜 예를 같이** | 고객지원 응답 생성 권고 |

두 번째가 특히 중요했다. 업계 논의는 *"실패는 프롬프트 실패가 아니라 아키텍처 실패다.
아무리 표현을 다듬어도 빠진 정보를 메울 수 없다"* 고 말한다. 우리 경우는 정보가 빠진 게
아니라 **좋은 답이 어떻게 생겼는지를 안 보여준 것**이었다.

### 숫자와 용어를 같은 잣대로 다루지 않았다

이게 설계의 핵심 판단이다.

| | 지어낸 숫자 | 내부 용어 누출 |
|---|---|---|
| 성격 | **사실이 틀림** — 고객을 잘못 인도한다 | 틀린 게 아님 — 창피할 뿐 |
| 상담원이 고칠 수 있나 | 못 고침 (출처를 모름) | **고칠 수 있음** |
| 처리 | **초안을 버린다** | **표시하고 센다** |

같은 잣대로 버리면 쓸 만한 초안까지 사라진다. `CsDraft.jargon`으로 실어 보내
상담원이 보고 다듬게 하고, **세어서** 프롬프트를 고쳤을 때 나아졌는지 알 수 있게 했다.

### 사전은 닳는다: 그래서 모양으로도 잡는다

`CustomerGlossary`는 22개 용어의 번역을 갖고 있지만, enum 이 늘면 사전이 뒤처진다.
그래서 탐지는 사전이 아니라 **모양**으로 한다 — 한국어 문장 안의 대문자 라틴 토큰은
사실상 전부 내부 용어다. 사전에 없는 `SOME_NEW_STATUS`도 잡힌다.

### 실측: 4건 × 3회

| | 실험 2 (전) | 실험 3 (후) |
|---|---|---|
| 검증 통과율 | 100% | **100%** (유지) |
| **용어 누출** | **AMOUNT_MISMATCH · PAID 등 발생** | **0 / 12 = 0%** |
| 지연 중앙값 | 5,233ms | **8,825ms** ← 늘었다 |

**지연이 68% 늘었다.** 프롬프트에 사전 22줄과 예시 3개가 붙은 대가다.
섀도 모드는 커밋 뒤 비동기라 문제가 안 되지만, **어드민 화면에서 사람이 기다리는 경로라면
8.8초는 길다.** 지금은 받아들이고, 문제가 되면 사전을 자주 쓰는 것만 남기거나
예시를 케이스별로 골라 싣는 방향이다(few-shot 선택).

### 어려운 건: 실제로 나아졌다

**전** (위변조 의심, 초안이 가장 필요한 자리)
> 2026-08-30 결제 승인 완료 및 주문 상태 **PAID** 확인 중입니다.
> 에스크로 보류 자동 해제 예정일은 2026-09-06입니다.

문제인 차액을 **한 마디도 말하지 않았다.**

**후**
> 2026-08-30 결제 승인 10,000원이 정상 확인됩니다.
> 결제사 정산 내역과의 **금액 차이 8,888원 원인을 확인 중**입니다.
> 확인이 완료되면 안내드리겠습니다.

### 예시를 베낀 게 아닌지 확인했다

few-shot 을 넣으면 **출력이 예시를 닮는 게 당연하다.** 그래서 "나아졌다"가
모델이 예시를 베낀 것인지 구분해야 한다. **예시에 없는 케이스 두 개**로 확인했다.

**정산 파일 지연** (예시에 없음)
> 결제사 정산 자료 도착 지연으로 인해 내부 기록과 차이가 발생했으며, 원인을 확인 중입니다.

**외부에만 존재** (예시에 없음)
> 2026-08-30 결제 내역은 외부 기록에만 확인되며, 저희 내부 기록에는 해당 주문이 없습니다.

둘 다 용어 누출 0이고, 첫 번째는 **글로서리 번역이 실제로 적용됐다**
(`PG_FILE_DELAY` → "결제사 정산 자료 도착 지연"). 구조를 베낀 게 아니라 규칙이 옮겨졌다.

### 아직 남은 것: 어조

외부에만 존재하는 건의 초안이 이렇게 말한다.

> 저희 내부 기록에는 해당 주문이 없습니다

**사실은 맞는데 고객이 읽으면 불안하다.** 이건 정확성 문제가 아니라 어조 문제고,
검증기도 사전도 못 잡는다. 상담원이 판단할 영역이라 지금은 그대로 둔다 —
**어디까지가 기계의 몫이고 어디부터가 사람의 몫인지**의 경계가 여기다.

## 실험 4. 초안이 쓸 만한지를 잴 수 있게 만들었다 (블라인드 리뷰)

여기까지 잰 것은 **"지어낸 숫자가 없다"(100%)**와 **"내부 용어가 안 샌다"(0%)** 뿐이다.
**둘 다 "보낼 만하다"는 뜻이 아니다.**

### 왜 그냥 "초안 보고 고쳐보기"가 아닌가

가장 쉬운 방법은 초안을 보여주고 "고쳐보세요" 하는 것이다. **그런데 그러면 측정이 오염된다.**
사람이 눈앞의 문장에 끌려가서(앵커링) **"고칠 게 없었다"와 "고칠 생각이 안 났다"가
구분되지 않는다.**

이건 새로운 문제가 아니다. `ClassifierAccuracyMetrics`가 자기 수치를 정확도가 아니라
**"일치율"** 이라고 부르는 이유가 정확히 이것이고, 그 클래스 주석에 한계로 적혀 있다.

### 그래서 순서를 뒤집었다

```
① 사실만 보여준다 → 사람이 직접 답을 쓴다   ← 초안을 보기 **전에**
② 그 뒤 모델 초안을 공개한다
③ 사람이 초안을 발송 가능하게 고친다
```

**①을 건너뛰면 그 표본은 조용히 무의미해진다.** 겉보기엔 데이터가 쌓이는데 앵커링에
오염돼 있다. 그래서 문서나 관례가 아니라 **엔티티가 순서를 강제한다** —
`blindReply` 없이 `reveal()`을 부르면 예외가 난다.

서버도 같이 막는다. `modelDraft`는 ①을 마치기 전까지 **응답에 아예 실리지 않는다.**
화면이 감추는 게 아니라 서버가 안 보낸다 — 클라이언트를 믿고 감추면 개발자 도구로 뚫린다.

### 순서 위반은 오류가 아니라 설계된 거절이다

처음엔 `IllegalStateException`을 던졌는데 **500**이 나갔다. 호출자가
**버그인지 의도된 차단인지 구분할 수 없다.** 전용 예외를 만들어 **409**로 매핑했다.

```
HTTP 409  code=REVIEW_OUT_OF_ORDER
message: 블라인드 답변을 먼저 제출해야 합니다. 초안을 먼저 보면 표본이 오염됩니다.
```

입력 오류(빈 답변)는 400 으로 따로 나간다. **두 실패를 같은 코드로 뭉치면
"내가 절차를 어겼나, 값을 잘못 넣었나"를 모른다.**

### 두 가지를 잰다

| 지표 | 무엇 | 왜 |
|---|---|---|
| **편집률** (모델 → 수정본) | 상담원에게 얼마나 일이 남는가 | 실무 지표. Klarna 의 교훈대로 **품질을 먼저** |
| **괴리** (블라인드 답 ↔ 모델 초안) | 사람과 모델이 얼마나 다르게 쓰는가 | **앵커링에 오염되지 않은 유일한 값** |

문자 단위 편집 거리를 쓴다. 한국어는 조사·어미가 붙어서 **어절 단위로 자르면
"확인됩니다"와 "확인되었습니다"가 완전히 다른 것으로 잡힌다.** 거의 안 고쳤는데도
크게 고친 것으로 나온다.

**중앙값을 쓴다.** 표본이 적을 때 한 건이 통째로 다시 쓰이면 평균이 끌려간다.

### 배관 검증: 표본이 아니다

전 흐름을 실제로 돌려봤다.

```
① 시작              → stage=BLIND, modelDraft=None   ← 초안이 응답에 없다
② 순서 위반 시도    → HTTP 409 REVIEW_OUT_OF_ORDER
③ 블라인드 제출     → stage=BLIND
④ 공개              → stage=REVEALED, source=ollama:qwen3:8b
⑤ 수정본 제출       → stage=DONE
⑥ 집계              → 편집률 15.0%, 괴리 39.1%
```

**이 15%와 39.1%는 아무 의미가 없다.** 블라인드 답을 내가 썼기 때문이다 —
앞에서 "정답을 지어내면 순환"이라고 적어둔 그 문제 그대로다.
**배관이 도는지 본 것이지 초안이 쓸 만한지를 잰 게 아니다.**

집계가 그 한계를 스스로 출력한다.

```
⚠ 편집률은 **표현이 얼마나 다른가**를 재지 **내용이 맞는가**를 재지 않는다.
⚠ 리뷰어는 상담원이 아니라 개발자다. 실제 상담 기준과 다를 수 있다.
⚠ 표본 1건은 통계로 쓰기에 적다. 경향만 본다.
```

**한계를 숫자와 붙여 다니게 했다.** 따로 두면 숫자만 인용된다.

### 어떻게 쓰나

```bash
ollama serve && ollama pull qwen3:8b
APP_ASSIST_DRAFT_PROVIDER=ollama ./gradlew bootRun
# → localhost:8080/admin.html 의 "블라인드 리뷰" 패널
```

대사 결과 ID와 주문번호를 넣고 시작하면 **사실만** 보인다. 답을 쓰고 제출하면
그때 모델 초안이 공개되고, 고친 뒤 집계를 보면 된다.

**한 사람이 같은 건을 두 번 리뷰할 수 없다**(DB 유니크). 두 번째는 이미 답을 아는 상태라
표본이 아니다.

## 실험 5. 실제로 리뷰해봤다. 그리고 개선 시도가 전부 실패했다

### 표본의 한계를 먼저 적는다

리뷰어가 **이 시스템의 프롬프트·글로서리·few-shot 예시를 직접 쓴 사람**이다.
그러니 블라인드 답이 모델에게 가르친 문체로 나올 수밖에 없고, **괴리 수치는 신뢰할 수 없다.**
편집률과 "무엇을 고쳐야 했나"에 무게를 둔다. 이 표본은 쌓아 올릴 기반이 아니라
**교체되어야 할 임시물**이다.

### 결과. 초안은 발송 가능한 수준이 아니다

| 케이스 | 편집률 | 무엇을 고쳐야 했나 |
|---|---:|---|
| 수수료 (DECISIVE) | 36.7% | **확정된 원인인데 "확인 중"으로 흐림** + 청구 금액 언급 없음 |
| 원인 불명 (WEAK) | 38.9% | 추가 청구 여부·다음 절차 빠짐 |
| 파일 지연 (LIKELY) | 52.3% | "정산 확정 대기" 내부 절차 노출 |
| 외부에만 (LIKELY) | **70.8%** | 불안한 표현 + 금액·고객 행동 빠짐 |
| **중앙값** | **45.6%** | 4건 중 2건은 절반 이상 새로 씀 |

**공통 원인이 하나였다.** 발송본이 전부 초안보다 길어졌다.
초안이 **"무슨 일이 있었나"는 말하는데 "그래서 고객은 어떻게 되나"를 말하지 않는다.**

그리고 첫 줄은 **내가 만든 버그**였다. 프롬프트 지시가
*"원인이 적혀 있으면 확인 중으로 쓰라"* 인데, DECISIVE 는 산수로 이미 확정된 것이다.
확정된 것을 "확인 중"이라고 쓰면 고객이 불필요하게 불안해한다.

### 고치려다 세 번 연속 나빠졌다

찾은 원인이 명확해 보여서 프롬프트를 고쳤다. **전부 실패했다.**

| 시도 | 용어 누출 | 편집률 중앙값 |
|---|---:|---:|
| **기준선** | **0%** | **45.6%** |
| ① 확신 등급별 어조 + 고객 영향 마무리 + 내부 절차 금지 | 25% | 60.7% |
| ② ①에 더해 용어 금지를 번호 규칙으로 승격(예시 명시) | **50%** | 63.2% |
| ③ 기준선으로 되돌리고 **고객 영향 마무리만** 추가 | 25% | 59.2% |
| **되돌림** | **0%** | **45.2%** ← 기준선 재현 |

**②가 특히 흥미롭다.** 용어 누출을 막으려고 금지 규칙을 올리면서
`PAID`, `PENDING_CONFIRMATION`을 예시로 적었더니 **누출이 두 배가 됐다.**
금지 예시가 오히려 그 단어를 떠올리게 한 것으로 보인다.

**③이 결정적이다.** 변수를 하나만 바꿔도(문장 두 줄 추가) 용어 누출이 0%→25% 로 깨졌다.
지시를 더할수록 그 뒤에 붙는 글로서리 섹션이 밀려 약해진다.
**프롬프트에는 주의 예산이 있고, 이미 그 한계에 있었다.**

### 이게 하네스가 있어야 하는 이유다

세 번 다 **고쳤다고 생각하고 넘어갈 수 있었다.** 특히 ①은 논리가 맞았다 —
찾은 결함이 진짜였고 처방도 업계 권고대로였다. 그런데 **재보니 나빠졌다.**

Klarna 가 되돌린 것도 이 자리다. 약한 신호에 대고 최적화하면
좋아 보이는 것과 좋아진 것이 갈라진다.

**되돌리고 기준선이 재현되는지까지 확인했다** — 0%, 45.2%.
재현되지 않았으면 "되돌렸다"고 말할 수 없었다.

### 편집 거리의 한계가 실제로 드러났다

①에서 "원인 불명" 케이스의 편집률이 38.9% → 53.7% 로 올랐다. 그런데 **내용은 오히려 좋아졌다** —
빠져 있던 "현재 추가 청구는 없으며"가 들어갔다. 표현이 내 발송본과 달라져서 거리가 벌어진 것이다.

> **편집률은 표현이 얼마나 다른가를 재지 내용이 맞는가를 재지 않는다.**

집계가 caveat 로 출력하던 문장인데, 이번에 **주장이 아니라 관측**이 됐다.

### 그래서 지금 결론

- **초안은 아직 발송 가능한 수준이 아니다** (편집률 45%, 4건 중 2건은 절반 이상 재작성)
- **프롬프트를 더 만져서 될 문제가 아니다.** 세 번 시도해 세 번 나빠졌고,
  주의 예산이 이미 한계다
- 다음에 시도할 것은 프롬프트가 아니라 **모델을 키우거나**(vLLM + 더 큰 모델),
  **케이스별로 예시를 골라 싣거나**(few-shot 선택), **표본을 늘리는 것**이다.
  지금은 n=4 라 무엇을 바꿔도 노이즈와 구분이 안 된다
- 그리고 **리뷰어가 바뀌어야 한다.** 이 표본은 임시물이다

## 실험 6. 기준을 잘못 잡으면 결론이 뒤집힌다

실험 5에서 프롬프트를 더 만져도 안 된다는 결론이 났다. 찾아보니 처방이 있었다.

### 왜 지시를 더할수록 나빠졌나. "lost in the middle"

문서화된 현상이었다. 트랜스포머는 프롬프트의 **앞과 끝**에 높은 주의를 주고
**중간을 잃는다.** 시작 토큰은 문맥을 세우고 끝 토큰은 가장 신선한데,
가운데는 낮은 주의 가중치를 받아 묻힌다.

우리 프롬프트는 `SYSTEM → 글로서리 → 예시` 순이었다. **글로서리가 정확히 중간**이다.
지시를 두 줄 더했더니 더 깊이 밀려 용어 누출이 0% → 25% 로 깨진 것이 설명된다.

권고 처방은 **재배치**다 — 중요한 지시를 앞에, 핵심을 끝에서 반복.
**더하는 게 아니라 옮기는 것**이라 아직 안 해본 수였다.

### 재배치도 실패했다 (시도 4회차)

글로서리를 끝으로 옮겼다(추가 0).

| | 용어 누출 | 편집률 |
|---|---:|---:|
| 기준선 `SYSTEM → 글로서리 → 예시` | 0% | **45.2%** |
| 재배치 `SYSTEM → 예시 → 글로서리` | 0% | 57.4% |

용어는 지켰는데 내용이 나빠졌다. **글로서리를 끝으로 보내면 예시가 중간으로 밀린다.**
내용 품질을 가르치는 건 예시고, 그게 잃어버리는 자리로 갔다.

> **양쪽 끝은 두 자리뿐이라 둘 다 넣을 수 없다.** 기준선이 이미 최적 배치였다.

### 그래서 모델을 키웠다. 그리고 기준의 함정에 빠졌다

파인튜닝은 논외였다. 라벨 **1만 건 이상**이 필요한데 우리는 4건이다.
업계 권고도 *"프롬프트 + 평가로 시작하고, 지표가 정체될 때까지 학습하지 마라"* 다.
남은 수는 모델 크기였다. Qwen3 8B → 14B (로컬이라 데이터는 여전히 안 나간다).

**처음 잰 결과는 14B 가 더 나빴다.**

| 케이스 | 8B | 14B |
|---|---:|---:|
| 중앙값 (발송본 기준) | **45.2%** | 57.7% |

여기서 멈췄으면 "14B 는 쓸모없다"가 결론이었을 것이다. **그런데 기준이 틀렸다.**

**"발송본"은 내가 8B 의 초안을 고쳐 만든 것이다.** 그러니 8B 의 어법에 편향돼 있고,
다른 모델이 똑같이 잘 써도 표현이 다르면 나쁘게 나온다.
**모델을 비교하는 기준이 그중 한 모델에서 파생된 것이었다.**

### 모델 중립 기준으로 다시 재니 뒤집혔다

**블라인드 답**은 초안을 보기 전에 쓴 것이라 어느 모델과도 무관하다.

| 케이스 | 8B | 14B | |
|---|---:|---:|---|
| 수수료 | 62.2% | **50.6%** | 14B 우세 |
| 원인 불명 | 57.1% | **52.2%** | 14B 우세 |
| 파일 지연 | 63.2% | **60.9%** | 14B 우세 |
| 외부에만 | 73.9% | **69.0%** | 14B 우세 |
| **중앙값** | 62.7% | **56.6%** | **4건 전부 14B** |

**같은 데이터, 같은 두 모델, 정반대 결론.** 기준을 무엇으로 잡느냐가 갈랐다.

> **모델을 비교할 기준은 그 모델들과 독립이어야 한다.**
> 한 모델의 출력을 고쳐 만든 정답으로 다른 모델을 채점하면 안 된다.

블라인드 리뷰의 순서 강제(사실만 보고 먼저 쓰기)가 여기서 값을 했다.
그 단계가 없었으면 중립 기준 자체가 존재하지 않았고, **틀린 결론을 그대로 실었을 것이다.**

### 그래도 14B 로 바꾸지 않았다

내용은 낫지만 다른 두 축이 나빠졌다.

| | 8B | 14B |
|---|---:|---:|
| 사람 답과의 거리 | 62.7% | **56.6%** ↓ |
| 용어 누출 | **0%** | 8% ↑ |
| 지연 중앙값 | **8.8초** | 12.9초 ↑ |

**분명한 승리가 아니고, n=4 로는 결정할 수 없다.** 기본값은 8B 로 두고 기록만 남긴다.
`app.assist.ollama.model`로 언제든 바꿀 수 있다.

### 이번에 배운 것

1. **지시를 더하면 뒤에 있는 것이 약해진다.** 프롬프트에는 주의 예산이 있다
2. **재배치도 공짜가 아니다.** 양 끝은 두 자리뿐이라 무언가를 앞으로 보내면 다른 게 밀린다
3. **기준이 결론을 만든다.** 편향된 기준으로 재면 정반대 답이 나온다
4. **표본 4건으로는 아무것도 결정할 수 없다.** 지금까지 잰 것 전부가 그렇다

## 실험 7. 정답 없이 채점하기, 그리고 검사가 무른 걸 잡기

실험 5·6 의 결론은 **표본이 병목**이라는 것이었다. n=4 로는 무엇을 바꿔도 노이즈와 구분이 안 된다.
그런데 표본을 늘리려면 사람이 답을 써야 하고, 그 사람이 편향돼 있다(내가 프롬프트를 썼다).

### 정답 대신 규칙으로 채점한다

찾아보니 이 상황에 쓰는 방식이 따로 있었다 — **reference-free evaluation**.
*"답이 열려 있고 하나의 정답으로는 유효한 변형을 놓칠 때"* 쓴다. **실험 6에서 겪은 그대로다.**

층이 둘이다.

| | 무엇 | 특징 |
|---|---|---|
| **코드 기반 단언** | 형식·필수 키워드·금지어 | 빠르고, 공짜고, **매번 같은 값** |
| LLM 심판 | 어조·의도 충족 | 규칙으로 못 잡는 것. 단 **같은 계열 모델은 자기편을 후하게 준다** |

앞의 것을 만들었다. `DraftRubric`은 5개 항목을 결정적으로 본다.
**항목은 상상해서 만든 게 아니라 블라인드 리뷰에서 실제로 고쳐야 했던 것들이다.**

1. 지어낸 숫자가 없는가
2. 내부 코드가 없는가
3. **핵심 수치를 말하는가** — 정작 문제인 차액을 빼먹는 일이 있었다
4. **고객에게 미치는 영향을 말하는가** — 발송본이 전부 초안보다 길어진 이유
5. 길이가 적당한가

정답이 필요 없으니 **표본을 마음껏 늘릴 수 있다.** 사례를 10건으로 늘려(2.5배) 3회씩 돌렸다.

### 첫 결과가 너무 좋았다: 그래서 의심했다

```
루브릭 평균 4.97/5   만점 29/30 = 96%
```

**블라인드 리뷰는 편집률 45% 라고 했는데 루브릭은 96% 만점이다.** 둘 중 하나가 틀렸다.

무엇으로 통과했는지 뜯어봤다.

```
id=14  루브릭 5/5  영향표현=['안내드리']
id=13  루브릭 5/5  영향표현=['안내드리']
...
상투적 마무리만으로 통과: 6/6
```

**6건 전부가 "안내드리겠습니다" 한 마디로 고객 영향 항목을 통과했다.**
그 문장은 어느 초안에나 붙고 고객에게 아무것도 알려주지 않는다.
**루브릭이 물렀던 것이지 초안이 좋았던 게 아니다.**

### 마무리 인사를 통과 조건에서 뺐다

돈이 어떻게 되는지(`변동이 없`, `추가 청구`)나 고객이 할 일(`보내주시`)을 말해야 통과한다.
`안내드리` 류는 따로 모아 **그것만 있으면 실패로 보고 그 사실을 메시지에 적는다.**

| | 강화 전 | 강화 후 |
|---|---:|---:|
| 루브릭 평균 | 4.97/5 | **4.10/5** |
| 만점 비율 | 96% | **10%** |
| 최다 미충족 | — | **고객 영향 없음 27/30 (90%)** |

### 두 측정이 같은 곳을 가리킨다

이제 **정답 없는 자동 채점**과 **사람의 블라인드 리뷰**가 독립적으로 같은 결함을 짚는다.

| 방법 | 결론 |
|---|---|
| 블라인드 리뷰 (n=4, 사람) | 편집률 45%. 발송본이 전부 초안보다 길어짐 — **고객 영향이 빠져서** |
| 루브릭 (n=30, 코드) | 90% 가 **고객 영향 없음**으로 실패 |

**서로 다른 두 방법이 한 곳을 가리키면 그건 노이즈가 아니다.**
그리고 이제 목표가 하나로 좁혀졌다 — "품질이 나쁘다"가 아니라
**"초안이 고객에게 미치는 영향을 말하지 않는다"** 다.

> 다만 실험 5에서 **바로 그걸 프롬프트로 고치려다 세 번 실패했다.**
> 주의 예산이 한계라 지시를 더할 수 없다. 남은 길은 프롬프트 밖에 있다 —
> 예시를 케이스별로 골라 싣거나(few-shot 선택), 더 큰 모델이거나,
> 초안을 두 단계로 나누는 것(사실 요약 → 영향 문장)이다.

### 화면에도 실린다

상담원이 무엇이 빠졌는지 바로 보게 초안 아래에 표시한다.
점수만 있으면 무엇을 고쳐야 할지 모르므로 **미충족 항목을 문장으로** 적는다.

```
루브릭 4/5 · 미충족: 고객 영향 없음 — 마무리 인사뿐이다. 돈이 어떻게 되는지를 말하지 않았다
```

**버리지 않고 표시한다.** 지어낸 숫자와 달리 이건 틀린 게 아니라 상담원이 채울 수 있는 문제다.

### 이번에 배운 것

**검사를 만들 때는 "무엇으로 통과했는지"를 반드시 뜯어봐야 한다.**
통과율이 높으면 기분은 좋지만, 그게 대상이 좋아서인지 검사가 물러서인지는 다른 문제다.
96% 를 그대로 실었으면 **"초안이 거의 완벽하다"고 문서에 적을 뻔했다.**

## 실험 8. 2단계로 나눴다. 그리고 검사가 세 번 나를 속였다

실험 7에서 목표가 하나로 좁혀졌다 — **초안이 고객에게 미치는 영향을 말하지 않는다(90%)**.
그런데 실험 5에서 그걸 프롬프트로 고치려다 세 번 실패했다. 주의 예산이 한계였다.

### 프롬프트 체이닝: 처방과 경고를 같이 받았다

찾아보니 정확히 이 상황의 처방이 있었다.

> 긴 프롬프트에서는 지시들이 **서로 경쟁하고**, 모델이 어느 제약을 지킬지
> **예측 불가하게** 고른다. 체이닝은 각 단계가 지시 하나에만 집중하게 한다.

그런데 2026년 4월 글이 같이 찌른다.

> **체인이 한 번에 하는 것보다 정말 더 정확한지를 묻는 경우가 드물고, 대부분 아무도 측정하지 않았다.**
> 앞 단계 오류가 뒤로 번질 수 있고, 단계별 정확도가 높아도 전체는 낮아질 수 있다.

**우리는 측정할 수 있었다.** 모놀리식 기준선(4.10/5)과 루브릭이 있으니까.

### 설계: 비평은 모델이 하지 않는다

흔한 self-refine 은 모델이 자기 글을 비평하게 한다. 그러면 **비평 자체가 틀릴 수 있다.**
우리는 더 나은 걸 갖고 있었다 — `DraftRubric`은 **결정적인 비평가**다.

```
① 초안 생성 (기존 프롬프트, 손대지 않음)
② 루브릭 채점 — 결정적, 모델 없음
③ 지적된 것만 짧은 프롬프트로 고침
④ 다시 검증 + 채점 → 나은 쪽만 쓴다
```

**④가 안전 보장이다.** 체인의 위험(오류 전파)을 두 초안을 같은 잣대로 채점해 막는다.
지어낸 값이 들어가면 루브릭 점수와 무관하게 탈락시킨다.
**최악이라도 한 번 더 부른 비용만 든다.**

### 검사가 세 번 나를 속였다

이번 실험의 진짜 이야기는 이쪽이다.

**첫 번째 — 루브릭이 물렀다** (실험 7)
평균 4.97/5, 만점 96%. 그런데 6/6이 `안내드리겠습니다` 한 마디로 통과했다.
그대로 실었으면 **"초안이 거의 완벽하다"** 고 문서에 적을 뻔했다.

**두 번째 — 조였더니 너무 빡빡해졌다**
상투어를 빼면서 `그대로`까지 같이 뺐다. 그래서 모델이
"청구 금액은 **그대로 유지**됩니다"라고 **제대로 쓴 것을 못 알아봤다.**
측정은 4.10 → 4.10, 개선 0으로 나왔고, 하마터면 **"2단계는 소용없다"** 고 결론 낼 뻔했다.

**세 번째 — 통과했는데 내용이 틀렸다** ← 아직 안 잡힘
고치고 다시 재니 만점이 나왔다.

| | 모놀리식 | 2단계 |
|---|---:|---:|
| 루브릭 평균 | 4.10/5 | **5.00/5** |
| 만점 | 10% | **100%** (30/30) |
| 수정으로 개선 | — | **27/27** |
| 지연 중앙값 | 5,894ms | **10,626ms** (1.8배) |

그런데 만점짜리 초안이 이렇게 쓴다.

> 결제 내역은 외부 기록에만 확인되며, **저희 내부 기록에 해당 주문이 없습니다.**
> … 고객 영향은 없으며, **청구 금액은 100,000원으로 그대로 유지됩니다.**

**주문 기록조차 없는 건에 대해 "청구가 멀쩡하다"고 단언한다.**
100,000원은 외부 기록에 있는 값이라 숫자 검증은 통과하고, 영향 표현이 있으니 루브릭도 통과한다.
**둘 다 통과하는데 주장이 틀렸다.**

### 그래서 배운 것. 검사가 통과했다는 것과 결과가 좋다는 것은 다르다

세 번 다 같은 모양이었다.

1. 검사가 무르면 → 나쁜 것이 통과한다
2. 검사가 빡빡하면 → 좋은 것이 떨어지고, **개선을 없는 것으로 만든다**
3. 검사가 맞아도 → **검사 밖의 오류는 그대로 지나간다**

**키워드 목록은 양쪽으로 부서진다.** 여기까지가 코드로 할 수 있는 한계다.
그래서 업계가 두 층으로 나눈다 — 코드 단언으로 잡을 것을 잡고,
**어조·함의·주장의 타당성은 다른 계열 모델이나 사람이 본다.**

### 결론

**2단계 수정은 효과가 있다** — 루브릭 4.10 → 5.00, 27/27 개선.
대가는 **지연 1.8배**다. 섀도 모드는 비동기라 무관하지만 사람이 기다리는 경로면 10초는 길다.

**다만 "만점"을 성과로 인용하면 안 된다.** 위 사례가 그 이유다.
지금 상태는 *"검사할 수 있는 것은 전부 통과한다"* 이지 *"보낼 만하다"* 가 아니다.

다음은 **다른 계열 모델을 심판으로 세우는 것**이다. 같은 계열은 자기편을 후하게 주므로
(Claude 계열이 Claude 계열을, GPT 계열이 GPT 계열을 높게 준다) qwen 이 아닌 모델이어야 한다.
그리고 그 심판이 잡아야 할 것이 방금 그 문장이다 —
**근거가 없는데 단언하는 것.**

## 실험 9. 다른 계열 모델을 심판으로 세웠더니, 내 최적화가 점수 따먹기였다

실험 8에서 코드가 못 잡는 것이 남았다 — **근거 없이 단정하기.**
숫자 검증과 루브릭을 **둘 다 통과**하는데 주장이 틀린 초안이다.

### 왜 Llama 인가

초안을 Qwen이 쓴다. **모델은 자기 계열 출력을 후하게 본다**(self-enhancement).
같은 계열을 심판으로 세우면 통과율만 오르고 아무것도 걸러지지 않는다.
Llama·Mistral 계열은 이 편향을 보이지 않는다는 관측이 있어 `llama3.1:8b`을 골랐다.

설정을 잘못 넣어 조용히 무의미해지는 것을 막으려고, **기동 시 계열이 같으면 경고**한다.

### 심판을 먼저 검증했다

코드를 짜기 전에 프롬프트부터 시험했다. 처음엔 실패했다.

```
① 아는 나쁜 건 → unsupported=False   ← 놓침
   이유: "확인 중인 내용이 사실에 없는 내용을 단정하고 있습니다"  ← 판정과 모순
```

**판정과 이유가 서로 어긋났다.** 8B 모델에게 "근거 없이 단정하는가"는 너무 추상적이었다.
좋은 예·나쁜 예·중립 예 셋을 주자 **3종 모두 맞혔다.**

> 심판을 만들면 **심판이 아는 오류를 실제로 잡는지** 먼저 확인해야 한다.
> 안 하면 무엇을 하는지 모르는 채 숫자만 늘어난다.

### 그리고 심판이 나를 잡았다

10건 × 2회를 돌렸더니 **80%가 근거 없는 단정**으로 표시됐다.
너무 많아서 오탐을 의심하고 뜯어봤는데, **오탐이 아니었다.**

> 차액 8,888원의 원인을 확인 중입니다. … **고객 영향은 없으며, 청구 금액은 그대로 유지됩니다.**
>
> — 심판: *"수수료로도 취소로도 설명되지 않는데 청구 유지라는 근거가 사실에 없다"*

**원인을 모르는데 결과를 장담하고 있다.** 그리고 이걸 만든 건 **내 2단계 수정이다.**

루브릭이 "고객 영향을 말하라"고 요구하니, 모델이 점수를 채우려고 **알 수 없는 것까지 단언**했다.
실험 8의 4.10 → 5.00 이 **일부는 점수 따먹기였다.**

> **지표를 목표로 삼으면 지표가 목표가 된다.** 프록시를 최적화한 전형적인 실패다.
> 다른 계열 심판이 없었으면 이걸 **성과로 인용했을 것이다.**

### 고친 것. 원인을 모르면 영향을 요구하지 않는다

루브릭의 고객 영향 항목을 **원인이 확정된 건(DECISIVE)에만** 적용한다.
수수료 차감이면 청구가 그대로라고 말할 수 있고 말해야 한다.
원인 불명이면 **결과도 모르고**, 그때 요구해야 할 것은 영향이 아니라 **모른다는 사실**이다.

| | 조건부 요구 전 | 후 |
|---|---:|---:|
| 근거 없는 단정 | 80% | **55%** |
| 그중 금액 불일치 | 8건 | **3건** |
| 그중 외부에만 존재 | 8건 | 8건 (그대로) |
| 루브릭 평균 | 5.00/5 | 5.00/5 (유지) |

### 남은 55% 는 다른 데서 온다

외부에만 존재하는 건이 줄지 않았다. 수정 단계가 아니라 **생성 프롬프트의 few-shot 예시**가
원인이다 — 예시 1이 "고객님께 청구된 금액에는 변동이 없습니다"로 끝나서
모델이 그 꼴을 따라 쓴다. 예시가 가르친 것을 예시로 고쳐야 하는데,
**실험 5·6에서 프롬프트를 만질 때마다 나빠졌으므로 함부로 손대지 않는다.**
케이스별로 다른 예시를 싣는 것(few-shot 선택)이 다음 수다.

### 비용

| | 지연 중앙값 |
|---|---:|
| 초안만 | 5,894ms |
| + 2단계 수정 | 10,626ms |
| + 심판 | **26,376ms** |

**심판은 켜두는 물건이 아니다.** 기본을 꺼짐으로 두고 평가할 때만 켠다.
섀도 모드처럼 비동기 경로라면 감당할 수 있지만, 사람이 기다리는 화면에 26초는 못 쓴다.

### 세 층으로 정리됐다

| 층 | 무엇을 잡나 | 걸리면 |
|---|---|---|
| `NumberGuard` | 지어낸 숫자 | **버린다** — 고객을 잘못 인도한다 |
| `CustomerGlossary` · `DraftRubric` | 내부 용어, 빠진 요소 | **표시한다** — 상담원이 고칠 수 있다 |
| `DraftJudge` (다른 계열) | **근거 없는 단정** | **표시한다** — 심판도 틀릴 수 있다 |

아래로 갈수록 확실성이 낮아지고, 그래서 처리도 약해진다.
**확실한 것만 버리고 나머지는 사람에게 넘긴다.**

## 실험 10. 예시를 케이스별로 갈아 끼우고, 금지어를 예시에서 뺐다

### 정적 예시가 문제였다

심판이 잡은 근거 없는 단정의 원인이 **생성 프롬프트의 고정 예시**였다.
예시 하나가 "고객님께 청구된 금액에는 변동이 없습니다"로 끝나 있어서,
모델이 **기록조차 없는 건에도 그 꼴을 복사**했다.

알려진 한계다 — *"정적 프롬프트는 예시가 실제 입력과 크게 다르면 일반화가 안 되고 편차가 커진다."*
처방은 **입력에 맞는 예시를 고르는 것**이고, 실측에서 F1 +7.3% 가 보고된 방식이다.

**늘리지 않고 갈아 끼웠다.** 고정 3개 → 케이스에 맞는 것 1개 + 나쁜 예 1개.
지시를 더할 때마다 나빠졌던 것(실험 5·6·8)을 되풀이하지 않으려면 이래야 한다.

**"모른다"를 가르치는 예시를 기본값으로 뒀다.** 원인 불명이 가장 위험한 자리다.
확언하는 예시만 보여주면 모델은 확언한다 —
*"'모른다'고 말할 수 있는 능력이 옳은 답을 내는 능력만큼 중요하다."*

### 심판이 이번엔 틀렸다

바꾸고 재니 심판이 **70%를 근거 없는 단정**이라고 했다(55%에서 악화).
뜯어보니 **오탐이었다.**

> 초안: 저희 주문 내역에서 찾지 못해 확인 중입니다. 카드사 승인 내역을 보내주시면…
> 심판: *"내부에 이 주문의 기록이 없다는 근거가 사실에 없다"*

사실에 `내부 없음`이 **명시돼 있다.** 초안은 오히려 정확해졌는데 심판이 못 읽었다.

**아는 결함은 코드로 세었다** — 원인이 확정되지 않은 건에 "그대로 유지 / 변동이 없" 류가 있는가.

| | 값 |
|---|---:|
| 근거 없는 단정 (코드로 셈) | **0/20 = 0%** |
| 심판 판정 | 70% ← **오탐** |

그리고 이 검사를 **루브릭 6번째 항목으로 고정**했다.
심판은 흔들리지만 이건 안 흔들린다. **심판은 모르는 결함을 찾는 데 쓰고, 아는 결함은 코드가 지킨다.**

### 금지어를 예시에 적으면 안 된다: 이번엔 검증했다

용어 누출이 0% → 10% 로 재발했다. 샌 것은 **`PAID` 세 건이 전부**였고,
`PAID`는 **나쁜 예시 안에** 두 번 있었다 — *"주문 상태 PAID 확인 중입니다"*,
*"PAID 같은 내부 코드를 쓰지 마십시오"*.

**금지하려고 적은 단어를 모델이 그대로 썼다.**

실험 5에서 같은 현상을 보고 "priming 인 것 같다"고 **추측만** 했었다.
이번엔 토큰만 가려서(`주문 상태(영문 코드)`) 다시 쟀다.

| | 예시에 PAID 있음 | 가림 |
|---|---:|---:|
| 용어 누출 | 10% | **0%** |

**한 단어를 빼서 확인했으므로 이제 추측이 아니다.**

### 최종

| | 시작 | 지금 |
|---|---:|---:|
| 루브릭 | 4.10/5 | **6.00/6 (만점 100%)** |
| 용어 누출 | 발생 | **0%** |
| 근거 없는 단정 | 55~80% | **0%** |
| 지어낸 숫자 | 0% | **0%** (유지) |
| 지연 중앙값 | 5,894ms | **7,250ms** |

지연이 는 것은 2단계 수정 때문이고, 심판은 껐다(기본값).
**심판을 켜면 26초가 되므로 평가할 때만 켠다.**

## 실험 11. 구독을 정당하게 써서 프런티어 모델과 비교했다

"구독하고 있으니 그걸로 쓰게 해달라"는 요청을 받았다.

**앱이 구독 자격증명으로 모델을 부르는 것은 정책 이전에 기술적으로 안 된다.**
CLI 가 쓰는 것은 API 키가 아니라 OAuth 토큰이고, 어댑터가 부르는 Messages API는
`x-api-key`를 받는다. 로컬이든 아니든 인증이 성립하지 않는다.

**그런데 목적은 이룰 수 있다.** 알고 싶은 것은 "더 좋은 모델이 어떤 초안을 쓰는가"이고,
프롬프트 내보내기(`/cs-draft/prompt`)와 되돌리기(`/cs-draft/imported`)가 그 자리다.
프롬프트를 꺼내 대화 안에서 초안을 쓰고 되돌리면 **같은 검사**를 태운다.
이건 구독을 그 용도로 쓰는 것이다 — 개발자가 자기 기계에서 도구를 쓰는 것.

### 결과: 둘 다 만점

| 케이스 | qwen3:8b | 대화(구독) |
|---|---:|---:|
| 기록 없음 | 6/6 | 6/6 |
| 파일 지연 | 6/6 | 6/6 |
| 원인 불명 777원 | 6/6 | 6/6 |
| 원인 불명 5,000원 | 6/6 | 6/6 |

**루브릭이 둘을 구분하지 못한다.**

### 그런데 읽어보면 같지 않다

루브릭이 못 보는 두 가지를 따로 세어봤다.

| | qwen3:8b | 대화(구독) |
|---|---:|---:|
| **안심 문구** ("추가로 청구되지 않는다" 등) | **0 / 4** | **3 / 4** |
| 내부 정보 노출 (정산 확정일·에스크로 등) | 1 / 4 | **0 / 4** |

구체적으로 이렇다.

> **파일 지연 — qwen**: "…확인 중이며, **정산 확정일은 2026-08-30입니다**."
> 고객에게 의미 없는 내부 일정이다. "결제 자체에는 문제가 없다"는 말은 빠졌다.
>
> **원인 불명 — qwen**: "…원인을 확인 중입니다. 결과가 확인되면 안내드리겠습니다."
> **추가 청구 여부를 말하지 않는다.** 고객이 가장 궁금해하는 것이 그건데.

### 왜 루브릭이 못 잡나: 우리가 그렇게 만들었다

실험 9에서 **고객 영향을 "원인이 확정된 건에만" 요구하도록** 바꿨다.
원인 불명인데 영향을 요구했더니 모델이 **알 수 없는 것까지 단언**했기 때문이다.

그 결정은 여전히 맞다. 그런데 부작용이 이거다 —
**"모르니까 아무 말도 안 한다"와 "모르지만 추가 청구는 없다고 약속한다"를 구분하지 못한다.**
둘 다 통과한다. 뒤엣것이 분명히 나은데도.

> **약속과 주장은 다르다.** "추가로 청구하지 않겠다"는 우리가 지킬 수 있는 약속이고,
> "이미 청구된 것이 멀쩡하다"는 확인되지 않은 주장이다.
> 루브릭은 뒤엣것만 막고, 앞엣것을 **권하지는 않는다.**

### 그래서 결론: 모델보다 잣대가 먼저다

**잣대가 프런티어 모델과 8B 를 구분하지 못하면, 그 잣대로는 개선을 이끌 수도 없다.**
지금 상태에서 더 좋은 모델로 바꿔봐야 **숫자가 안 움직인다.**

다음에 할 것은 모델 교체가 아니라 루브릭에 항목을 하나 더 다는 것이다 —
**원인 불명일 때 "추가 청구 없음"을 권장 항목으로.** 다만 필수로 걸면
실험 9의 실패(점수 채우려고 단언)를 되풀이할 위험이 있어, **가점**으로 두고
6/6 위에 7점째를 만드는 쪽을 봐야 한다.

**지금은 달지 않았다.** 표본이 4건이라 무엇을 바꿔도 노이즈와 구분이 안 되고,
이 프로젝트에서 **성급한 루브릭 수정이 이미 여러 번 역효과를 냈다.**
관측을 기록해 두고 표본이 쌓일 때 판단한다.

## 실험 12. 잣대에 가점 축을 달아 천장을 뚫었다

실험 11 에서 프런티어 모델과 8B 가 **둘 다 6/6** 이라 구분이 안 됐다.
읽어보면 분명히 다른데(안심 문구 0/4 대 3/4) 잣대가 못 본다.

**잣대가 구분하지 못하면 그 잣대로는 개선을 이끌 수도 없다.**

### 필수로 걸지 않았다: 그게 요점이다

빠진 것은 알았다. "원인을 몰라도 **추가로 청구하지 않겠다**는 약속은 할 수 있다"는 자리다.

그런데 이걸 **필수 항목으로 걸면 실험 9 의 실패가 되풀이된다** —
루브릭이 요구하니 모델이 점수를 채우려고 **알 수 없는 것까지 단언**했던 그 일이다.

**그래서 재기만 하고 요구하지 않는다.**

- 통과 여부(`passed/total`)를 바꾸지 않는다 — 가점이 없어도 6/6 이다
- **프롬프트에도 넣지 않는다** — 넣는 순간 압력이 된다
- 비교할 때만 `comparable() = passed + bonus`를 쓴다

가점 두 개를 달았다. 둘 다 실험 11 에서 **실제로 차이가 관측된** 축이다.

| 가점 | 왜 |
|---|---|
| 불확실할 때 추가 청구 없음을 약속했다 | **약속과 주장은 다르다** — 지킬 수 있는 것은 말해도 된다 |
| 상관없는 내부 일정을 넣지 않았다 | 정산 확정일·에스크로 일정은 고객에게 의미가 없다 |

### 결과: 구분된다

| | 필수 | 가점 | 합계 |
|---|---:|---:|---:|
| qwen3:8b | 24 / 24 | **4** | **28** |
| 대화(구독) | 24 / 24 | **6** | **30** |

원인 불명 2건에서 갈렸다. 8B 는 "결과가 나오는 대로 안내드리겠습니다"에서 멈추고,
프런티어 모델은 "확인이 끝날 때까지 **추가로 청구되는 금액은 없으며**"를 덧붙인다.

**필수 점수는 여전히 둘 다 만점이다.** 그래서 모델에게 점수 압력이 안 생기고,
그럼에도 **비교는 가능해졌다.**

### 이게 답이었다

실험 9~11 을 관통하는 문제가 하나였다.

> **필수로 걸면 모델이 지어내고, 안 걸면 잣대가 눈이 먼다.**

가점은 그 사이다. **요구하지 않으면서 재는 것.**
프롬프트에 넣지 않았으므로 8B 가 못 받은 가점은 **진짜 차이**지 지시 누락이 아니다.

### 남는 한계

**가점 항목도 결국 내가 골랐다.** 실험 11 에서 관측된 차이를 축으로 만든 것이라
**그 두 축에서는 프런티어 모델이 이기게 되어 있다.** 새로운 차원의 차이는 여전히 못 본다.

그걸 넓히려면 사람이 초안을 읽고 "이건 왜 나은가"를 말해줘야 하고,
그게 블라인드 리뷰가 기다리는 자리다.

## 아직 못 한 것

**초안이 쓸 만한지에 대한 실제 표본이 없다.** 잴 수단은 만들었다(실험 4).
그런데 표본을 만들려면 사람이 앉아서 답을 써야 하고, 아직 아무도 안 썼다.

**리뷰어가 상담원이 아니라는 한계는 남는다.** 개발자가 쓴 답을 기준으로 삼으면
"개발자가 보기에 쓸 만한가"를 재는 것이지 상담 현장 기준이 아니다.
집계가 이걸 caveat 로 항상 같이 출력한다.

**외부 모델(Anthropic)로는 재지 않았다.** 어댑터와 배관은 검증했지만, 생성형 AI는 아직
금융권 망분리 예외가 아니라 결제 데이터를 내보내지 않았다.

**vLLM 으로 옮기지 않았다.** 지금 병목은 처리량이 아니라 초안 품질이다.
처리량이 문제가 되는 시점(동시 상담원 다수)이 오면 어댑터를 하나 더 만든다.

## 실험 13. 프롬프트 재배치 (판정 기준을 결과보다 먼저 적는다)

**목표는 "세 번째 자리를 켜는 것"이 아니라 **상담원이 덜 고쳐도 되는 초안**이다.**
기준에 못 미치면 노출하지 않고 실험 기록으로만 남긴다.

### 가설 (처방이 아니다)

`system()`이 `SYSTEM → 글로서리 → 예시` 순이라 **글로서리가 가운데 있다**. 긴 문맥에서
위치에 따라 주의가 달라진다는 보고가 있고, 실험 6에서 지시를 두 줄 더했을 때 용어 누출이
0% → 25% 로 깨진 것과 방향이 맞는다. **다만 그것만으로 이번 누출의 원인이 위치라고
확정되지는 않는다.** 같은 모델·같은 설정에서 두 배치를 직접 비교해야 안다.

바꾸는 것은 순서뿐이다. **지시를 더하지 않는다** — 더할 때마다 나빠졌다.

### 무엇과 비교하나

셋을 나란히 잰다. 지금 기본값이 템플릿이므로 **"전보다 나아졌나"만으로는 부족하다.**

```
① 템플릿            (현재 기본값. 모델 없이 사실을 시간순으로 잇는다)
② 현행 프롬프트      SYSTEM → 글로서리 → 예시
③ 재배치 프롬프트    지시 앞으로, 글로서리 뒤로, 핵심을 끝에서 반복
```

모델과 생성 설정(`qwen3:8b`, temperature, seed)을 고정한다.

### 표본

**기존 4건은 프롬프트를 고치는 데만 쓰고 평가에서 뺀다.** 같은 건을 보며 고친 뒤 그 건의
점수가 좋아진 것은 실험 3에서 이미 겪은 함정이다. 평가는 **새 사례 12건 이상**으로 한다.

편집률은 사람이 3단계 블라인드 리뷰(직접 작성 → 초안 열람 → 수정)를 마쳐야 나온다.
자동으로 잴 수 있는 것은 용어 누출·숫자 출처·금액 결손·응답시간까지다.

### 활성화 조건 (넷을 다 만족해야 켠다)

| | 기준 | 왜 이 값인가 |
|---|---|---|
| 편집률 중앙값 | **템플릿보다 낮을 것** | "전보다"가 아니라 "지금 쓰는 것보다"가 질문이다 |
| 용어 누출 | **가드 이전 원문에서 0%** | 가드가 막아 준 것은 초안이 좋아진 것이 아니다 |
| 출처 없는 숫자 | **가드 이전 원문에서 0%** | 위와 같은 이유 |
| 응답 p95 | **15초 이하** | 지금 타임아웃 값. 넘으면 템플릿으로 떨어져 의미가 없다 |

넷을 다 만족하면 **사람이 검토하는 초안으로만** 켠다. 발송 자동화가 아니다.
문서에는 **확인한 범위만** 적는다.

### 안 하는 것

- 모델을 키우거나 few-shot 을 늘리는 것. **한 번에 한 가지만 바꾼다**
- 편집률로 "내용이 맞는가"를 말하는 것. 이 숫자는 **표현이 얼마나 다른가**까지다

### 결과: 안 켠다

`qwen3:8b`, 새 사례 12건. 셋을 같은 사례에 대 봤다.

```
방식            용어누출   출처없는수   금액결손      p50        p95    빈초안
① 템플릿          100%        0%         0%       0ms        1ms      0
② 현행 배치         8%        0%        75%    5120ms    15774ms      0
③ 재배치            8%        0%        67%    5335ms    12006ms      0
```

**활성화 조건 넷 중 하나를 못 넘었다.** 용어 누출이 0% 가 아니다(8%, 12건 중 1건).
금액 결손 75% → 67% 는 **12건에서 1건 차이라 노이즈**고, 이것으로 나아졌다고 말할 수 없다.
p95 는 기준(15초) 안에 들어왔다.

**그래서 안 켠다.** `draft-provider`는 `template` 그대로다.

### 왜 안 됐나: 배치가 문제가 아니었다

초안을 열어 보니 문제가 위치가 아니었다.

```
── 재배치 / 미확정 진행중 · 빠진 금액 [31500]
   2026-09-06 결제 승인 요청이 확인됩니다.
   현재 응답이 미확정 상태로 확인 중입니다.
   결제 완료 여부는 확인 중이며, 결과가 나오는 대로 안내드리겠습니다.
```

문장은 깔끔한데 **금액이 아예 없다.** 상담 초안에서 고객이 제일 먼저 볼 숫자다.
하나 더 나왔다.

```
── 재배치 / 가상계좌 입금대기 · 빠진 금액 [70000]
   2026-09-05 결제 승인 기록은 정상 확인됩니다.   ← 사실은 "가상계좌 발급"이다
   추가로 청구되는 금액은 없으며, ...            ← 사실 목록에 없는 말이다
```

**사실에 없는 것을 말한다.** 승인이 아니라 발급인데 승인이라 쓰고, 청구 여부를 단정한다.
이건 프롬프트 앞뒤를 바꿔서 고쳐질 문제가 아니다.

### 그래서 다음에 볼 것

- **가설이 틀렸다는 것까지가 이번 결과다.** "글로서리가 중간에 묻혀서"는 이 모델·이 사례에서
  확인되지 않았다. 두 배치의 차이가 12건에서 1건이다
- 진짜 병목은 **금액 누락과 사실 밖 서술**이다. 배치가 아니라 **무엇을 반드시 쓰게 할 것인가**
  쪽이고, 그건 프롬프트가 아니라 **후처리나 슬롯 채우기**에 가깝다
- 효과를 확인하지 못한 시도는 **운영 성과로 인용하지 않고 개발 기록으로만 남긴다**

`app.assist.prompt-layout`은 남겨 둔다(기본 `current`). 다음에 다시 잴 때 쓴다.

## 실험 14. 금액이 빠지면 되묻는다

실험 13이 남긴 말을 그대로 이어받는다.

> 진짜 병목은 **금액 누락과 사실 밖 서술**이다. 배치가 아니라 **무엇을 반드시 쓰게 할 것인가**
> 쪽이고, 그건 프롬프트가 아니라 **후처리나 슬롯 채우기**에 가깝다

### 되묻는 장치는 이미 있었다

`DraftService.reviseIfWorthIt()`는 루브릭이 짚은 것만 한 번 더 물어보고, 고친 것이 원본보다
못하면 원본을 쓴다. 그런데 **금액 결손일 때 발동하지 않았다.**

```java
DraftRubric.Score before = rubric.score(original, facts);
if (before.failed().isEmpty()) {
    return original;          // 루브릭이 통과시키면 여기서 끝난다
}
```

루브릭이 보는 금액은 **분류기 근거의 첫 금액** 하나다. 사실 목록에 있는 나머지 금액이 통째로
빠져도 루브릭은 통과시킨다. **금액 결손은 루브릭이 안 보던 자리였다.**

`AmountCoverageGuard`는 이미 있었고 평가에서만 쓰이고 있었다. 그것을 되묻기의 근거로 잇는다.

```java
List<String> issues = new ArrayList<>(before.failed());
List<Long> missing = coverageGuard.missing(original, facts);
for (Long a : missing) {
    issues.add("금액 " + format(a) + "원이 초안에 없다");
}
if (issues.isEmpty()) return original;
```

바뀐 초안을 채택하는 조건도 같이 넓혔다. **절대 나빠지지 않는다**는 보장은 그대로다.

```java
boolean better = after.passed() > before.passed()
        || (after.passed() == before.passed() && missingAfter < missing.size());
```

루브릭이 오르거나, 루브릭이 같은데 빠진 금액이 줄었을 때만 바꾼다.

### 채점기를 의심했더니 새던 것은 주문번호였다

걸린 초안을 열어 봤다.

```
문의하신 주문번호 EV-06 결제 건은 결제사 기록에서 확인되지 않으나
정산 파일에만 기록되어 있습니다.
```

**내부 상태 코드가 아니라 주문번호다.** `CustomerGlossary.findJargon()`은 사전이 아니라
모양으로 잡는데(`\b[A-Z][A-Z0-9]+(?:_[A-Z0-9]+)*\b`), 표본의 `EV-06`에서 `EV`가 걸린다.

운영 주문번호는 `Ulid.generate()` 다. ULID는 앞이 타임스탬프라 **첫 글자가 숫자**이고,
정규식은 `[A-Z]`로 시작해야 잡으므로 안 걸린다. 확인했다.

```
주문번호 01ARZ3NDEKTSV4RRFFQ69G5FAV 결제 건은  ->  []
주문번호 EV-06 결제 건은                      ->  [EV]
```

그러니 이 8% 는 **운영에서 날 수 없는 값**이고, 표본이 이 프로젝트가 스스로 정한 기준을
안 지킨 것이다(`15-` 문서: "사실 문장은 지어내지 않고 실제 형식을 그대로 썼다").

**탐지기가 아니라 표본을 고쳤다.** 이 구분이 중요하다. 결과를 보고 채점 기준을 고치면 그 뒤
수치는 아무것도 뜻하지 않는다. 실험 3에서 한 번 겪은 함정이고, `19-` 문서에서 모델이 틀렸다고
채점된 라벨을 지금 고치지 않고 남겨 둔 것도 같은 이유다.

표본의 주문번호 12개를 운영과 같은 ULID 형식으로 바꾸고, 프롬프트와 채점 기준은 그대로 둔 채
세 방식을 처음부터 다시 돌렸다.

## 하네스를 쌍 비교로 고쳤다

편집률을 재려다 **하네스가 그 비교를 못 한다**는 것을 알았다. `reveal`이
`draftService.draftFor()`를 불러 **그때 켜진 provider 의 초안 하나**만 고정하는데,
조건은 "템플릿보다 낮을 것"이라 둘이 필요하다.

`draft-provider`를 바꿔 두 회차로 도는 방법은 안 된다. **두 번째 회차는 리뷰어가 이미
답을 아는 상태다.** 이 실험이 엔티티로 막아 둔 바로 그 오염이 회차 사이로 새는 것이다.

그래서 **한 번의 블라인드 답에 초안 둘을 붙였다.**

| 무엇 | 왜 |
|---|---|
| 공개 시 템플릿·모델 초안을 **같은 사실에서 같은 시점에** 고정 | 모델은 매번 다르게 쓴다. 나중에 다시 뽑으면 사람이 본 것과 다른 문장을 채점한다 |
| 화면에는 **A·B 로만** 준다. 어느 쪽이 모델인지 서버가 안 내보낸다 | 알고 고치면 "모델이니까 잘 썼겠지"가 편집량에 섞여 차이가 방식 차이가 아니게 된다 |
| 표시 순서를 **건마다 뒤집는다** | 항상 같은 쪽이 먼저면 먼저 본 것에 기준이 생기고, 뒤에 온 초안은 그 문장과 얼마나 다른지로 읽힌다 |
| 쌍 비교는 **둘 다 고친 건**에서만 낸다 | 한쪽만 있는 건을 섞으면 두 중앙값이 서로 다른 표본에서 나온다 |
| 표본이 없으면 조건 1을 **판정하지 않는다**(`null`) | `false`로 내면 안 잰 것과 못 넘은 것이 같아 보인다 |

`TemplateDraftAdapter`의 `@ConditionalOnProperty`를 뗐다. 대조군이라 provider 와 무관하게
항상 있어야 한다. 모델 어댑터가 켜지면 그쪽이 `@Primary` 라 `DraftPort` 주입은 그리로 간다.

### 심는 일과 쓰는 일을 갈랐다

고치고 나서 **준비 비용**이 남았다. 초안을 그 자리에서 만들면 건당 10초 안팎이고, 이제
초안이 둘이라 두 배다. 12건이면 답을 제출할 때마다 그만큼 기다린다.

**표본이 0건이던 실제 이유가 판단의 어려움이 아니라 그 대기였다.** 쌍 비교에서 이미 겪어
`NarrativeComparisonSeedTest`로 갈라 뒀고, 여기서도 같게 한다.

그런데 심으려니 걸리는 것이 있었다. `revealed()`가 **초안이 있느냐**로 판정하고 있어서,
미리 심으면 **블라인드 답을 쓰기 전에 공개 상태**가 된다. 화면은 그대로 도는데 표본만
무의미해지는 종류의 사고다. 공개 여부를 `revealed_at` **시각**으로 가르도록 고쳤다.
고정과 공개가 다른 일이라는 것을 타입이 말하게 한 것이다.

| | |
|---|---|
| `preload()` | 초안 둘을 고정한다. 공개는 아니다 |
| `markRevealed()` | 블라인드 답이 있어야 부를 수 있다. 없으면 409 |
| `preloaded()` / `revealed()` | 심은 것과 사람이 본 것을 가른다 |

`scripts/blind-review-session.sh`가 인프라를 올리고 심는 데까지 한다. 사람은 클릭하고
쓰기만 한다.

### 배관 검증. 표본이 아니다

고치고 나서 전 흐름을 실제로 돌려봤다. **여기 나오는 수치는 아무 뜻이 없다** — 블라인드
답과 수정본을 내가 더미로 넣었다. 배관이 도는지 본 것이지 초안이 쓸 만한지를 잰 게 아니다.
실험 4에서 같은 구분을 해 뒀고 여기서도 같다.

```
① 시작           → stage=BLIND, draftA=null, draftB=null
② 순서 위반 시도  → HTTP 409 REVIEW_OUT_OF_ORDER (23ms)
③ 블라인드 제출   → stage=BLIND
④ 공개           → stage=REVEALED, 초안 둘 (35.9초)
⑤ A 수정본       → stage=REVEALED   ← 한쪽만으로는 안 끝난다
⑥ B 수정본       → stage=DONE
⑦ 집계           → 쌍 비교 1건
```

돌려 보고 다섯이 나왔다. **코드만 읽어서는 하나도 안 보였다.**

**① 순서 검사가 모델 호출 뒤에 있었다.** 순서 위반인데도 초안을 두 개 만들고 나서 409 를
냈다. 거절될 요청에 20초 넘게 쓰고, 그동안 화면은 멈춘 것처럼 보인다. 검사를 앞으로
옮기니 23ms 다. **코드만 읽어서는 안 보였고 태워 보니 나왔다.**

**② 로컬에 표본이 될 데이터가 없었다.** 주문은 30만 건인데 결제와 대사가 0건이다. 부하
표본이라 타임라인이 없다. 스크립트가 "미해결 대사 0건"으로 끝나면 그 자리에서 멈춘다.
`tools/seed-blind-review.sql`로 평가 사례 12건과 같은 모양을 심는다. 결제 전이 이력까지
넣어야 사실이 운영과 같아진다 — 그게 없으면 사실이 주문 생성과 대사 결과 둘로 얇아지고,
**편집률이 초안의 값이 아니라 표본의 값**이 된다.

**③ 부분취소 금액은 초안이 말할 수 없다.** 모델이 12,000원·8,000원을 썼다가 검증기에
버려졌다. 그 값은 결제 전이 이력의 **자유 텍스트 사유**에만 있고, 구조화된 사실
(`PaymentFact.amount()`)은 **결제 총액 하나**다. 검증기는 계약대로 동작했다 — 코드가 낸
숫자가 아니면 못 쓴다. 사유는 운영자가 적는 값이라 출처로 삼을 수 없다.

**검증기를 안 고친다.** 여기서 허용 범위를 넓히면 운영자가 사유에 적은 아무 숫자나
고객 문장에 실릴 수 있게 된다. 부분취소 금액을 초안에 쓰려면 그 값이 **구조화된 사실로
올라와야** 하고, 그건 이 실험이 아니라 타임라인 쪽 일이다. 표본에는 이 건을 남긴다.
초안이 없는 것도 결과이고, 실제로 일어나는 일이다.

**④ 스크립트가 앱과 다른 DB를 보고 있었다.** "미해결 대사 0건"이라고 하는데 앱은 멀쩡히
돌았다. 이 기계에 도커 런타임이 둘 떠 있고(colima, Docker Desktop) **양쪽에 `pay-mysql-1`
이 있다.** 둘 다 `:3306->3306` 이라고 보고하는데 호스트 3306 을 실제로 잡은 것은 하나다.
`docker exec`는 현재 컨텍스트로 가므로, 앱은 A 에 쓰고 스크립트는 B 를 봤다.
포트 표기로는 안 갈려서 **스키마가 있는 쪽**으로 고르게 했다. Flyway 가 만든 흔적이
곧 앱이 붙은 곳이다.

**⑤ `health: UP`은 스키마가 있다는 뜻이 아니다.** 컨테이너를 새로 만들면 DB는 비는데,
이전 앱 프로세스는 8080 을 잡은 채 UP 을 낸다. Flyway 는 기동 때 한 번 도는 것이라
다시 돌지 않는다. 스크립트가 "준비됐다"를 찍고 표본 심기만 조용히 실패했다.
**건강 확인에 스키마 확인을 더했고, 못 갖추면 거기서 멈춘다.** 준비가 안 된 채로
넘어가면 뒤가 전부 헛돈다.

고치고 나서 다시 돌린 결과다.

```
표본 12건 · 전부 1단계 · 초안 12건 고정
공개 응답 47ms   (미리 고정하기 전에는 35.9초)
```

**공개가 즉시다.** 심는 일과 쓰는 일을 가른 것이 여기서 값을 한다. 12건이면 리뷰어가
초안을 기다리는 시간만 7분 줄어든다.

괴리 중앙값(블라인드 답 ↔ 모델 초안)은 **67.0%**였다. **그대로 쓴 건은 0건**이고 절반 이상
새로 쓴 건이 4건이다. 즉 **모델 초안도 다 손을 봐야 한다.** 낮아진 것은 손보는 양이지
손볼 필요가 없어진 것이 아니다.

### 이 수치를 누가 냈는지가 가장 큰 한계다

**리뷰어가 이 프롬프트를 만든 사람이다.** 집계가 자동으로 붙이는 한계("리뷰어는 상담원이
아니라 개발자다")보다 한 겹 더 나쁘다. 두 가지가 걸린다.

- **A/B 눈가림이 이 리뷰어에게는 작동하지 않는다.** 템플릿 초안은 내부 코드가 그대로
  박혀 있어 한눈에 갈린다. 무작위 순서는 지켜졌지만 **어느 쪽이 무엇인지는 다 알았다.**
- **모델 쪽에 무르게 굴었을 수 있다.** 이걸 막으려고 **초안을 보기 전에 수정 기준 다섯을
  먼저 적고** 12건 내내 안 바꿨다. ①내부 코드를 우리말로 ②사실의 금액·날짜를 다 넣기
  ③사실에 없는 단정을 지우기 ④다음에 뭘 하면 되는지 넣기 ⑤그 외 문장 다듬기 금지.

편집 중에 판단이 하나 더 필요했다. **비문은 고쳤다**(`금액이 다름으로` → `금액이 달라`).
발송 가능이 기준인데 비문은 발송이 안 된다. 기준 ⑤에 안 적혀 있던 것이라 여기 적어 둔다.

**그래서 이 33.5%는 상담원이 낸 값이 아니다.** **수치 자체를 인용하려면 다른 사람이 다시
재야 한다.** 하네스와 표본은 그대로 있으므로 리뷰어만 바꾸면 된다.

### 2회차에서 수치가 재현되지 않았다 (2026-09-07)

같은 12건, 같은 리뷰어, 같은 기준 다섯으로 **한 번 더 돌렸다.**

| | 1회차 | 2회차 |
|---|---|---|
| 모델 초안 편집률 중앙값 | 33.5% | **71.1%** |
| 템플릿 편집률 중앙값 | 85.0% | 87.0% |
| 조건 1(템플릿보다 낮은가) | 통과 | 통과 |

**방향은 두 번 다 같았고 모델 쪽 수치는 두 배 넘게 벌어졌다.** 원인은 둘이다.

- **기준 다섯에 빠진 규칙이 있었다.** **"A 와 B 를 같은 문장으로 맞출지"가 안 적혀 있었다.**
  1회차는 각 초안의 표현을 살려 고쳤고, 2회차는 둘을 같은 발송본으로 모았다. 발송 가능한
  답이 하나뿐이라 후자가 자연스럽지만, 그러면 모델 초안도 정본에 맞춰 다시 쓰게 되어
  편집률이 올라간다. **미리 정하지 않은 것 하나가 수치를 두 배 움직였다.**
- **검증기에 걸려 빈 초안이 1건에서 2건으로 늘었다.** `BR-01`도 2회차에 버려졌다.
  빈 초안은 편집률 100% 라 12건 중앙값을 그만큼 밀어 올린다.

2회차 건별 편집률은 **19.0% ~ 100%**로 갈렸다. 낮은 쪽(`BR-07` 19.0%, `BR-03` 34.1%)은
모델이 사건을 제대로 짚은 건이고, 높은 쪽은 **헛짚었거나**(`BR-04` 74.7%. 가상계좌
입금 대기를 "승인 완료"로 썼다) **아예 비어 있던 건**이다. 중앙값 하나로 뭉치면 이 갈림이
안 보인다.

**결론: 점추정은 인용하지 않는다.** 이 실험이 말할 수 있는 것은 **모델 초안이 템플릿보다
덜 고친다**까지다. 얼마나 덜 고치는지를 쓰려면 **수정 기준을 A/B 수렴 여부까지 조이고
다시 재야 한다.** 원자료는 `docs/data/blind-review-2026-09-07.tsv`에 있다.

한 가지는 리뷰어와 무관하다. **`BR-02`는 모델 초안이 아예 없었다**(검증기가 부분취소
금액을 출처 없는 숫자로 보고 버렸다). 빈 초안에서 발송본까지는 편집률 100%다. 그 건이
표본에 그대로 들어가 있고, 그래도 중앙값이 33.5% 다.

# 16. 할부 도메인과 시스템 책임

현업 개발자에게 FDS 조언을 받으며 나온 예가 **"고액 할부, 야간 할부, 중복 거래"**였다.
그런데 이 프로젝트에는 할부 개념이 아예 없었다. FDS 규칙 하나 만들자고 아무도 안 쓰는 필드를
만드는 것은 가짜라, 먼저 **할부가 이 도메인의 무엇인지**부터 확인했다.

---

## 1. 할부는 우리 돈 계산을 바꾸지 않는다

이게 핵심이다. **할부는 카드사와 고객 사이의 약속이고, 가맹점과 PG는 그 결과만 받는다.**

- 고객이 12개월로 긁어도 **가맹점은 일시에 전액을 받는다.** 카드사가 고객 대신 일시불로
  지급하고, 고객에게 12개월 나눠 받는다.
- 그래서 **정산 금액이 안 바뀐다.** 대사도 이 값을 보지 않는다.

토스페이먼츠 승인 응답의 `card` 객체가 결과를 돌려준다.

| 필드 | 뜻 |
|---|---|
| `installmentPlanMonths` | 할부 개월. **일시불이면 0**, 최대 12 |
| `isInterestFree` | 무이자 여부 |
| `interestPayer` | 수수료 부담 주체 — `BUYER` / `CARD_COMPANY` / `MERCHANT` |

국내 카드사 공통으로 **건당 5만원 이상**일 때만 할부가 걸린다.
최대 할부기간은 가맹점이 상점관리자에서 제한할 수 있다.

---

## 2. 그럼 서버가 할부로 하는 일은 무엇인가

돈 계산이 안 바뀌니 대부분은 **기록하고 넘기는 값**이다. 일이 생기는 자리는 둘이다.

1. **`interestPayer`가 `MERCHANT` 일 때** — 무이자 이자를 가맹점이 문다. 실제로 돈이 나가고
   정산에서 차감으로 잡힐 수 있다. **이번 범위에 넣지 않았다**(아래 5절).
2. **부분취소** — 부분취소된 매출은 **할부가 원복되지 않는다.** 이 프로젝트에 이미
   `PARTIAL_CANCEL_NOT_REFLECTED` 원인이 있는데, 할부 건에서는 그 처리가 더 까다로워지는 자리다.

---

## 3. 넣은 것

### 값을 승인 경로에 실었다

```
ConfirmRequest.installmentMonths
  → CheckoutService.confirm
  → CheckoutTx.reserve → PaymentService.beginApproval → Payment.initiate(…, months)
  → PaymentService.pgApprove → PgApproveCommand.installmentMonths
```

기존 호출부는 일시불(0) 오버로드로 그대로 둔다. JSON 에 없으면 0 이다.

### 받아들일 값을 도메인에서 막는다

승인 요청을 내보낸 뒤 카드사가 거절하면 그때는 이미 우리 쪽에 `IN_PROGRESS` 행이 남는다.
**우리가 미리 알 수 있는 것은 미리 막는다.**

| 조건 | 결과 |
|---|---|
| 0 | 일시불. 금액 무관 통과 |
| 1~12 이고 금액 ≥ 50,000 | 통과 |
| 1~12 이고 금액 < 50,000 | `INVALID_INSTALLMENT` |
| 음수 또는 13 이상 | `INVALID_INSTALLMENT` |

### 화면에 보이게 했다

타임라인 요약에 `12개월 할부`가 붙는다. 일시불이면 **아무 말도 하지 않는다** —
대부분이 일시불이라 매 줄에 "일시불"이 붙으면 잡음이 된다.

### FDS 가 이 값을 본다

```java
if (req.installmentMonths() >= longInstallmentMonths
        && req.amount() >= installmentAmountThreshold) {
    score += installmentWeight;
    reasons.add("LONG_INSTALLMENT_HIGH_AMOUNT(" + req.installmentMonths() + "개월)");
}
```

**할부 자체는 정상이다.** 안마의자 400만원을 12개월로 긁는 것은 흔하다. 그런데 도난 카드도
같은 모양을 쓴다 — **한도 안에서 결제 금액을 키우는 가장 쉬운 수단**이 할부이기 때문이다.
상품명이 올라와도 정상인지 사람이 바로 못 가른다.

그래서 **차단하지 않는다.** 기본값(6개월 이상 + 100만원 이상)에서 +20 점이고, 고액 가산(+30)과
합쳐도 50 이라 `CHALLENGE`(40) 는 넘고 `REVIEW`(60) 에는 못 미친다. **사람이 들여다볼 이유를
만드는 층**이지 막는 층이 아니다.

같은 회차에 기기·IP velocity 도 더했다. `FraudCheckRequest`가 `ip`와 `deviceId`를 받아놓고
한 번도 쓰지 않고 있었다 — 카드만 세면 **카드를 바꿔 가며 같은 기기·회선에서 두드리는 것**을
못 본다. 임계는 셋 다 다르게 뒀다(카드 5, 기기 8, IP 15). 공용망·NAT 뒤에서는 남남이 IP 를
공유하므로 같은 숫자를 쓰면 IP 규칙이 정상 사용자를 계속 건드린다.

---

## 4. 무엇을 고정했나

- 할부여도 **결제 금액과 잔액이 그대로**인 것(분납은 카드사와 고객 사이의 일이다)
- 5만원 미만 거절, 범위 밖 거절
- 고액 장기 할부는 **점수만 얹고 차단하지 않는 것**
- 소액 장기 할부, 고액 일시불은 **신호가 아닌 것**

---

## 5. 안 넣은 것

- **`isInterestFree` · `interestPayer`** — 가맹점 부담 무이자는 실제로 정산에 영향을 준다.
  넣으려면 승인 응답 파싱과 정산 차감까지 이어져야 해서 이번 범위에서 뺐다. 대사 원인 코드에도
  이 자리를 위한 값이 아직 없다.
- **야간 시간대 규칙** — 조언에 나온 "야간 할부"의 나머지 절반이다. 다만 임계를 정할 근거가
  없어서 넣지 않았다. 근거 없이 상한만 정하는 것은 이 프로젝트가 피해 온 것이다.
- **부분취소 시 할부 처리** — 부분취소된 매출은 할부가 원복되지 않는다는 것까지만 확인했다.

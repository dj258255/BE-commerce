# 42. 라이브 커머스와 숏폼: 명세

> 상점에 판매 채널 둘을 더한다. 판매자가 방송하며 상품을 고정하면 시청자가 영상을 보다가 그 자리에서
> 주문·결제하는 **라이브 커머스**, 그리고 상품이 붙은 세로 짧은 영상을 넘겨 보는 **숏폼 피드**다.
> 결제·재고·정산은 새로 만들지 않는다. 지금 있는 주문·결제 경로를 그대로 타고, 이 문서는 그 앞단의
> 영상·채팅·한정 판매를 다룬다.

## 1. 왜 이 기능인가

이 저장소의 코어는 "실패 이후의 정합성 회복"이다. 재고 동시 차감, rate limit, 멱등 키, 결제 `UNKNOWN`
복구를 실측으로 다뤘다. 라이브 방송의 한정 수량 판매는 이 문제가 가장 몰리는 상황이다. 방송에서
"지금부터 50개"를 외치는 순간 수천 명이 같은 상품을 같은 초에 주문한다. 숏폼은 그 방송 바깥에서
상품을 발견하게 하는 입구다.

## 2. 범위

### 이번에 하는 것

1. **판매자 방송**: 판매자가 브라우저에서 방송을 시작·종료한다(OBS 없이). 방송마다 스트림 키를 발급하고, 키가 맞을 때만 송출을 받는다.
2. **시청**: 시청자가 방송 페이지에서 저지연 영상을 본다. 방송이 끝나면 같은 페이지가 녹화본(다시 보기)으로 바뀐다.
3. **상품 고정**: 판매자가 방송 중 상품을 고정·해제하고, 방송 특가와 한정 수량을 건다. 시청자 화면에는 영상 시점에 맞춰 고정 상품 카드가 뜬다.
4. **방송 중 주문**: 시청자가 고정 상품 카드에서 바로 주문·결제한다. 결제는 기존 주문·결제 API를 쓴다.
5. **한정 수량**: 방송 특가 수량을 넘겨 팔지 않는다. 매진되면 모든 시청자 화면에 바로 알린다.
6. **채팅**: 방송마다 실시간 채팅. 사용자·방 단위 속도 제한, 금칙어 가림, 판매자 공지 고정.
7. **숏폼 업로드**: 판매자가 세로 영상(최대 60초)을 올리고 상품을 연결한다. 업로드한 영상은 여러 화질로 변환된 뒤 공개된다.
8. **숏폼 피드**: 시청자가 세로 영상을 위아래로 넘겨 본다. 영상에 연결된 상품으로 바로 간다. 다음 영상은 미리 불러 둔다.
9. **시청 신호**: 시청 완료율, 다시 보기, 건너뛰기, 상품 태그 누름을 이벤트로 남긴다. 기존 개인화 파이프라인이 이 신호를 읽을 수 있게 한다.
10. **관측**: 방송 동접, 영상 지연, 채팅 처리량, 한정 판매 성공·거절 수, 변환 대기열 길이를 지표로 낸다.

### 이번에 하지 않는 것

- CDN, 여러 노드로 나눈 미디어 서버, 실시간 다중 화질 트랜스코딩(송출 화질 그대로 전달)
- 모바일 앱 송출 SDK, 여러 출연자 동시 방송
- 학습형 추천 모델(규칙 점수까지만)
- 채팅 영구 보관·검색, ML 독성 판정
- 실제 외부 결제사 계약(기존과 같이 테스트 PG)

## 3. 요구사항

### 3.1 방송

- 판매자가 방송을 만들면 시스템은 방송별 스트림 키를 발급해야 한다.
- 송출 요청의 스트림 키가 그 방송의 키와 다르거나 방송이 예정·진행 상태가 아니면 시스템은 송출을 거절해야 한다.
- 송출이 시작되면 방송 상태를 `LIVE`로, 끊기면 `ENDED`로 바꾸고 각각 이벤트(`live.started`, `live.ended`)를 남겨야 한다.
- 송출이 30초 안에 다시 붙으면 같은 방송으로 이어야 한다(끊김 한 번에 방송이 끝나지 않게).
- 방송 녹화본은 방송 종료 뒤 10분 안에 다시 보기로 재생할 수 있어야 한다.

### 3.2 시청과 지연

- 시청자는 방송 페이지에서 로그인 없이 영상을 볼 수 있어야 한다. 주문·채팅은 로그인이 필요하다.
- 같은 PC 로컬 환경에서 송출부터 시청 화면까지의 지연 중앙값은 5초 이하여야 한다(측정 방법은 6절).
- 방송이 끝나면 시청 페이지는 새로고침 없이 "방송이 끝났습니다"와 다시 보기로 바뀌어야 한다.

### 3.3 상품 고정과 동기화

- 판매자가 상품을 고정하면 시청자 화면에 고정 상품 카드가 떠야 한다. 카드에는 상품 이름, 방송 특가, 남은 수량이 보인다.
- 고정·해제·가격 변경 이벤트에는 서버 시각과 순번을 붙여야 하고, 시청자 화면은 자기가 보고 있는 영상 시점이 그 서버 시각에 닿을 때 카드를 바꿔야 한다(영상보다 먼저 가격이 바뀌어 보이지 않게).
- 시청자가 중간에 들어오거나 연결이 끊겼다 붙으면 현재 고정 상태를 다시 받아야 한다.
- 주문 가능 여부와 가격은 언제나 서버 상태로 판정해야 한다. 화면 카드의 값은 표시용이다.

### 3.4 방송 중 주문과 한정 수량

- 시청자가 고정 상품 카드에서 주문하면 기존 주문·결제 흐름으로 이어져야 한다(장바구니를 거치지 않는 바로 주문).
- 방송 특가 한정 수량 N개를 걸면 그 방송에서 확정된 주문 수량 합은 N을 넘으면 안 된다. 동시 주문이 몰려도 같다.
- 같은 사용자가 같은 버튼을 여러 번 눌러도(같은 멱등 키) 주문은 하나만 생겨야 한다.
- 한정 수량을 잡았지만 결제하지 않은 주문은 정해진 시간(기본 5분)이 지나면 수량을 돌려놓아야 한다.
- 결제가 `UNKNOWN`으로 끝난 주문은 기존 복구 흐름으로 확정될 때까지 수량을 잡아 두어야 한다.
- 매진되면 1초 안에 모든 시청자 화면의 카드가 매진으로 바뀌어야 한다.
- 수량을 못 잡은 요청은 결제까지 가지 않고 빠르게 거절해야 한다(거절 응답 p95 200ms 이하, 로컬 측정).

### 3.5 채팅

- 로그인한 시청자는 방송 채팅에 글을 쓸 수 있어야 한다. 글은 같은 방송의 모든 시청자에게 순서대로 보여야 한다.
- 연결이 잠깐 끊겼다 붙은 시청자는 놓친 최근 메시지(최대 200개)를 받아야 한다.
- 사용자당 초당 1개를 넘는 글은 거절하고 그 사실을 본인에게만 알려야 한다. 방 전체가 초당 정해진 수를 넘으면 표시를 묶어 내려야 한다.
- 금칙어(공통 목록 + 방송별 목록)가 들어간 글은 가려서 보여야 한다.
- 판매자는 공지 한 개를 채팅 위에 고정할 수 있어야 한다.

### 3.6 숏폼

- 판매자는 세로(9:16) 영상을 최대 60초, 최대 200MB까지 올릴 수 있어야 한다. 파일은 서버를 거치지 않고 저장소로 바로 올라가야 한다.
- 올린 영상은 `UPLOADING → UPLOADED → PROBING → TRANSCODING → READY` 순서로 상태가 바뀌어야 하고, 실패하면 `FAILED`와 이유를 남겨야 한다. 변환 실패는 정해진 횟수만큼 다시 시도한 뒤 따로 격리해야 한다.
- 변환 결과는 세 가지 화질의 HLS와 썸네일이어야 한다.
- 60초 영상의 업로드 완료부터 `READY`까지 로컬에서 60초 안에 끝나야 한다.
- 판매자는 영상에 상품을 여러 개 연결할 수 있어야 하고, 시청자는 영상에서 연결 상품으로 갈 수 있어야 한다.
- 피드는 `READY` 영상만 보여야 한다. 다음 영상 1~2개는 미리 불러 두되 화면에 보이는 영상만 재생해야 한다.

### 3.7 시청 신호와 추천

- 시청자가 영상을 볼 때마다 시청 시간, 완료 여부, 다시 보기, 건너뛰기(3초 안에 넘김), 상품 태그 누름을 이벤트로 남겨야 한다.
- 피드 순서는 규칙 점수(완료율, 최신성, 시청자의 기존 상품 선호와 연결 상품의 일치)로 정한다. 점수에 쓴 신호와 가중치는 문서로 남긴다.
- 개인화 시스템이 죽어도 피드는 최신순으로 열려야 한다(홈이 그렇듯).

### 3.8 관측과 운영

- 방송별 동접, 시청 지연(클라이언트 보고), 채팅 메시지 처리량과 거절 수, 한정 판매 시도·성공·거절 수, 변환 대기열 길이와 처리 시간을 Prometheus 지표로 내야 한다.
- 방송 시작·종료, 매진, 변환 실패는 운영 로그에 이벤트로 남아야 한다.

## 4. 사람이 할 일(시스템이 하지 않는 것)

- 실제 결제사 계약, 실제 판매자 정산 계좌 등록
- 도메인·TLS 인증서, 외부 공개 배포
- 저장소 권한·협업자·공개 범위 설정

## 5. 기술 제약(조사 결과에 따른 출발점)

근거는 조사 노트에 있고, 바꾸려면 ADR로 남긴다.

| 영역 | 출발점 | 이유 |
|---|---|---|
| 미디어 서버 | MediaMTX 컨테이너 하나(RTMP·SRT·WHIP 송출, LL-HLS·WHEP 시청, fMP4 녹화) | 한 컨테이너로 방송·시청·녹화. MIT. 브라우저 송출 페이지가 있어 OBS가 필요 없다 |
| 송출 인증·이벤트 | MediaMTX의 HTTP 인증 훅 → 스트림 키 검증, 시작·종료 훅 → Kafka | 키 검증과 상태 전이를 기존 백엔드가 맡는다 |
| 상품 고정 동기화 | WebSocket + 서버 시각(`effectiveAt`)·순번, 클라이언트가 재생 시점과 비교 | 자체 호스팅 미디어 서버에서 영상 안 메타데이터 주입 경로를 확인하지 못했다 |
| 한정 수량 | 방송-상품 한도를 Redis에서 선점(TTL) → 기존 MySQL 재고 차감으로 확정 | 재고 차감 정합성은 이미 실측했다(ADR-004). 앞단은 빨리 거절하는 역할만 |
| 채팅 | WebSocket + Redis Pub/Sub 팬아웃 + Redis Streams로 순번·빈 구간 복구 | Pub/Sub만으로는 끊긴 사이 메시지를 잃는다 |
| 숏폼 저장·변환 | MinIO presigned 업로드 → Kafka 이벤트 → FFmpeg 워커, 세로 3단계 fMP4 HLS | 업로드와 변환을 떼어 변환이 밀려도 업로드는 받는다 |
| 화면 | `apps/web`(Next.js) 아래 방송·시청·피드 화면, 재생은 hls.js | 개인화 화면과 같은 앱 |
| 코드 위치 | 저장소 최상위 새 영역 `media/`. 주문·결제·재고 확정은 `commerce/`를 호출 | 결제 코어와 경계를 분명히 |

## 6. 어떻게 확인하나

- **방송**: FFmpeg 시험 패턴(`-re` + 시계 오버레이)으로 RTMP 송출, 시청 화면의 재생 시점과 시계를 비교해 지연을 잰다. 브라우저 WHIP 송출은 화면 시험으로 한 번 확인한다.
- **한정 수량**: k6로 같은 방송 특가 상품에 동시 주문(예: 수량 50개에 1,000명)을 보내 확정 수량 합이 50을 넘지 않는지, 거절 응답 p95를 잰다. 결제 지연·`UNKNOWN`을 섞은 경우도 잰다(실행 순서·준비 스크립트는 `docs/performance/live-order-r15.md`).
- **매진 전파**: 시청자 100명을 WebSocket으로 접속시킨 뒤 매진을 만들어, 전원이 1초 안에 매진 메시지를 받는지와 못 받은 클라이언트 수를 `tools/run-live-order-stock.sh`가 잰다(R14.1).
- **미결제 반환**: 같은 스크립트가 선점 뒤 TTL이 지날 때까지 WebSocket을 열어 두고, 반환 시 수량 복구 이벤트가 실제로 시청자 화면 쪽으로 오는지(카드 수량 갱신)와 그만큼 재주문이 되는지를 함께 확인한다(R13.1).
- **채팅**: 시청자 수를 늘려 가며 메시지 순서 어긋남 0, 끊김 뒤 복구 누락 0을 확인한다.
- **숏폼**: 60초 세로 영상 업로드부터 `READY`까지의 시간과 실패 재시도 경로를 잰다.
- **화면**: 방송 시청 → 고정 카드 → 바로 주문 → 결제 완료까지를 브라우저 시험으로 클릭해 확인한다. 자동 화면 확인(`studio.yaml`의 `pageChecks`)은 실 RTMP 송출 없이도 열려야 하므로, `SCHEDULED` 상태로 상품을 미리 고정해 둔 고정 id 데모 방송(`V82` 마이그레이션, `/live/999001`)을 쓴다. 영상이 재생되지 않아도 고정 카드는 떠야 한다는 3.3절 인수 조건을 만족시키려면, 시청 화면이 WebSocket 스냅샷을 영상 재생 여부와 무관하게 적용할 수 있어야 한다(`LiveViewer.tsx`의 폴백 틱).

## 7. 순서

1. 숏폼(업로드·변환·피드·상품 연결): 영상 파이프라인을 실시간 부담 없이 먼저 세운다.
2. 방송·시청·녹화(MediaMTX, 스트림 키, 상태 전이).
3. 상품 고정·동기화·채팅.
4. 방송 중 주문과 한정 수량(이 문서의 핵심 실험).
5. 시청 신호·추천·관측.

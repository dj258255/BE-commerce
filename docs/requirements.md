# 요구사항

## R1. 방송 생성 시 방송별 스트림 키 발급
- 종류: api · 우선순위: must · 개정: 1
- EARS(event): 판매자가 방송을 생성하면 시스템은 해당 방송 전용 스트림 키를 발급해야 한다.
- 시나리오:
  - R1.1: (Given) 판매자 계정으로 로그인한 상태 (When) POST /live/broadcasts 로 제목을 보내 방송을 만들면 (Then) 201과 함께 상태 `SCHEDULED`, 해당 방송의 streamKey가 응답된다
  - R1.2: (Given) 판매자 A가 만든 방송이 있는 상태 (When) 다른 판매자 B가 그 방송의 스트림 키를 조회하면 (Then) 403이 반환되고 키 값은 응답에 포함되지 않는다
- 인수 조건:
  - 판매자가 방송 생성 API를 호출하면 201과 함께 방송 id, 제목, 상태 `SCHEDULED`, 스트림 키가 응답된다
  - 스트림 키는 방송 단위로 유일하며 다른 방송의 키와 중복되지 않는다
  - 스트림 키는 생성한 판매자 본인에게만 조회되고, 다른 사용자가 조회하면 403을 반환한다
- 상태: 미착수

## R2. 스트림 키·방송 상태가 맞지 않는 송출 거절
- 종류: api · 우선순위: must · 개정: 1
- EARS(unwanted): 송출 요청의 스트림 키가 방송의 키와 다르거나 방송 상태가 `SCHEDULED`·`LIVE`가 아니라면 시스템은 송출을 거절해야 한다.
- 시나리오:
  - R2.1: (Given) 방송 B1의 스트림 키가 `key-b1`이고 상태가 `SCHEDULED`인 상태 (When) 인증 훅에 스트림 키 `key-zzz`로 송출 요청이 오면 (Then) 비 2xx가 응답되어 송출이 거절되고 방송 상태는 `SCHEDULED`로 유지된다
  - R2.2: (Given) 방송 B1의 상태가 `ENDED`인 상태 (When) 올바른 스트림 키 `key-b1`로 송출 요청이 오면 (Then) 비 2xx가 응답되어 송출이 거절된다
- 인수 조건:
  - MediaMTX HTTP 인증 훅 요청의 스트림 키가 해당 방송의 키와 다르면 인증 실패(비 2xx)를 응답해 송출을 거절한다
  - 방송 상태가 `SCHEDULED` 또는 `LIVE`가 아니면(`ENDED` 등) 키가 맞아도 송출을 거절한다
  - 거절 시 사유(키 불일치 / 상태 불일치)를 운영 로그에 남긴다
- 상태: 미착수

## R3. 송출 시작·종료에 따른 방송 상태 전이와 이벤트 발행
- 종류: api · 우선순위: must · 개정: 1
- EARS(event): 송출이 시작되면 시스템은 방송 상태를 `LIVE`로 바꾸고 `live.started` 이벤트를 발행해야 한다.
- 시나리오:
  - R3.1: (Given) 방송 B1이 `SCHEDULED`인 상태 (When) 올바른 스트림 키로 RTMP 송출이 시작되면 (Then) 상태가 `LIVE`로 바뀌고 `live.started` 이벤트가 1건 발행된다
  - R3.2: (Given) 방송 B1이 `LIVE`이고 송출이 끊긴 상태 (When) 끊김 후 20초 뒤 같은 스트림 키로 다시 송출이 붙으면 (Then) 같은 방송 id가 유지되고 상태는 `LIVE`이며 `live.ended`는 발행되지 않는다
  - R3.3: (Given) 방송 B1이 `LIVE`이고 송출이 끊긴 상태 (When) 끊김 후 31초가 지나면 (Then) 상태가 `ENDED`로 바뀌고 `live.ended` 이벤트가 1건 발행된다
- 인수 조건:
  - 송출 시작 훅을 받으면 방송 상태를 `LIVE`로 바꾸고 `live.started` 이벤트를 발행한다
  - 송출이 끊긴 뒤 30초 안에 같은 스트림 키로 다시 붙으면 같은 방송 id를 유지하고 상태는 `LIVE`를 유지하며 `live.ended`를 발행하지 않는다
  - 송출 끊김 후 30초가 지나면 상태를 `ENDED`로 바꾸고 `live.ended` 이벤트를 발행한다
  - `live.started`/`live.ended` 이벤트에는 방송 id와 서버 시각이 포함된다
- 상태: 미착수

## R4. 방송 종료 후 10분 내 녹화본 다시 보기 제공
- 종류: api · 우선순위: must · 개정: 1
- EARS(event): 방송이 `ENDED`로 전이되면 시스템은 10분 안에 해당 방송의 녹화본을 다시 보기로 재생할 수 있게 해야 한다.
- 시나리오:
  - R4.1: (Given) 5분간 송출한 방송 B1이 방금 `ENDED`가 된 상태 (When) 종료 직후 다시 보기 조회 API를 호출하면 (Then) 상태 `PREPARING`과 재생 URL null이 응답된다
  - R4.2: (Given) 방송 B1이 `ENDED`가 된 지 10분이 지난 상태 (When) 다시 보기 조회 API를 호출하면 (Then) 상태 `AVAILABLE`과 재생 가능한 녹화본 URL이 응답된다
- 인수 조건:
  - 방송이 `ENDED`가 된 시각부터 10분 안에 해당 방송의 다시 보기 재생 URL이 조회 API로 응답된다
  - 녹화본 준비 전에는 다시 보기 상태가 `PREPARING`으로 응답되고 재생 URL은 null이다
  - 준비가 끝나면 상태가 `AVAILABLE`로 바뀌고 fMP4 기반 재생 URL이 응답된다
- 상태: 미착수

## R5. 비로그인 시청 허용, 주문·채팅은 로그인 필요
- 종류: api · 우선순위: must · 개정: 1
- EARS(state): 사용자가 로그인하지 않은 동안 시스템은 방송 영상 시청만 허용하고 주문·채팅 요청은 401로 거절해야 한다.
- 시나리오:
  - R5.1: (Given) 로그인하지 않은 방문자 (When) `LIVE` 상태인 방송 페이지에 들어가면 (Then) 영상이 재생되고 채팅 입력란에는 로그인 안내가 표시된다
  - R5.2: (Given) 로그인하지 않은 방문자 (When) 고정 상품 카드에서 바로 주문 API를 호출하면 (Then) 401이 반환되고 주문은 생성되지 않는다
- 인수 조건:
  - 비로그인 사용자가 방송 시청 페이지와 재생 URL 조회를 요청하면 200으로 영상 재생이 가능하다
  - 비로그인 사용자가 방송 중 주문 API를 호출하면 401을 반환한다
  - 비로그인 사용자가 채팅 전송을 시도하면 401을 반환하고, 화면에는 로그인 안내가 표시된다
- 상태: 미착수

## R6. 송출~시청 지연 중앙값 5초 이하
- 종류: nonfunctional · 우선순위: must · 개정: 1
- EARS(ubiquitous): 시스템은 같은 PC 로컬 환경에서 송출부터 시청 화면까지의 지연 중앙값을 항상 5초 이하로 유지해야 한다.
- 시나리오:
  - R6.1: (Given) 같은 PC에서 MediaMTX와 시청 페이지가 떠 있는 상태 (When) 시계 오버레이 시험 패턴을 RTMP로 60초 송출하고 화면 시계와 비교하면 (Then) 20개 표본의 지연 중앙값이 5초 이하로 측정된다
- 인수 조건:
  - FFmpeg 시험 패턴(`-re` + 시계 오버레이)으로 RTMP 송출하고 시청 화면의 시계 값과 송출 시각 차이를 20회 이상 측정해 중앙값이 5초 이하임을 기록한다
  - 측정 환경은 송출·미디어 서버·시청이 모두 같은 PC 로컬인 조건으로 명시한다
  - 측정 결과(표본 수, 중앙값, 최댓값)를 문서에 남긴다
- NFR: 지표 송출 시각과 시청 화면 표시 시각의 차이(지연) · 임계값 중앙값 5초 이하 · 조건 같은 PC 로컬 환경, 단일 송출 1개, 시청 탭 1개, 표본 20회 이상 · 측정 FFmpeg `-re` + 시계 오버레이 시험 패턴 송출 후 화면 시계와 송출 시계 차이 수동 비교 기록
- 상태: 미착수

## R7. 방송 종료 시 시청 화면 자동 전환
- 종류: ui · 우선순위: must · 개정: 1
- EARS(event): 방송 상태가 `ENDED`로 바뀌면 시청 페이지는 새로고침 없이 "방송이 끝났습니다"와 다시 보기 영역으로 전환해야 한다.
- 시나리오:
  - R7.1: (Given) 시청자가 `LIVE` 방송을 보고 있는 상태 (When) 판매자가 송출을 끊고 방송이 `ENDED`가 되면 (Then) 페이지를 새로고침하지 않아도 "방송이 끝났습니다" 문구와 다시 보기 영역이 표시된다
  - R7.2: (Given) 방송이 `ENDED`이지만 녹화본이 `PREPARING`인 상태 (When) 시청 페이지를 보면 (Then) "다시 보기 준비 중" 상태가 표시되고 준비 완료 시 재생 영역으로 바뀐다
- 인수 조건:
  - 방송이 `ENDED`가 되면 시청 페이지가 새로고침 없이 "방송이 끝났습니다" 문구로 바뀐다
  - 같은 화면에서 다시 보기 재생 영역이 나타나고, 녹화본 준비 중이면 "다시 보기 준비 중" 상태가 표시된다
  - 재생 실패 시 재시도 버튼이 포함된 오류 문구가 표시된다
  - 방송 시작 전(`SCHEDULED`)에는 "방송 준비 중" 상태가 표시된다
- 상태: 미착수

## R8. 상품 고정·해제와 고정 상품 카드(동시 1개)
- 종류: api · 우선순위: must · 개정: 1
- EARS(event): 판매자가 방송 중 상품을 고정하면 시스템은 이전 고정을 해제하고 상품 이름·방송 특가·남은 수량이 담긴 고정 상품 카드를 시청자 화면에 표시해야 한다.
- 시나리오:
  - R8.1: (Given) `LIVE` 방송에 고정 상품이 없는 상태 (When) 판매자가 상품 P1을 특가 9,900원·한정 50개로 고정하면 (Then) 시청자 화면에 "P1 / 9,900원 / 남은 수량 50" 카드가 표시된다
  - R8.2: (Given) 상품 P1이 고정된 상태 (When) 판매자가 상품 P2를 고정하면 (Then) P1 고정이 해제되고 시청자 화면에는 P2 카드 1개만 표시된다
- 인수 조건:
  - 판매자가 상품 고정 API를 호출하면 방송 특가와 한정 수량 N이 함께 저장되고 시청자 화면에 고정 상품 카드가 표시된다
  - 카드에는 상품 이름, 방송 특가, 남은 수량이 표시된다
  - 이미 고정된 상품이 있는 상태에서 다른 상품을 고정하면 이전 고정은 자동 해제되고 동시에 고정된 상품은 항상 1개다
  - 판매자가 해제하면 시청자 화면에서 카드가 사라진다
- 상태: 미착수

## R9. 고정 이벤트의 서버 시각·순번 기반 영상 시점 동기화와 재동기화
- 종류: api · 우선순위: must · 개정: 1
- EARS(event): 시청자의 재생 시점이 고정 이벤트의 `effectiveAt`에 도달하면 시스템은 그 시점에 맞춰 고정 상품 카드를 갱신해야 한다.
- 시나리오:
  - R9.1: (Given) 시청자 재생 시점이 서버 시각보다 4초 지연된 상태 (When) 판매자가 특가를 9,900원에서 7,900원으로 바꾸는 이벤트(`seq`=7, `effectiveAt`=T)를 보내면 (Then) 시청자 화면은 재생 시점이 T에 도달한 뒤 7,900원으로 바뀐다
  - R9.2: (Given) 상품 P1이 특가 7,900원·남은 수량 23으로 고정된 방송 (When) 시청자가 WebSocket 재연결하면 (Then) 현재 고정 스냅샷(P1, 7,900원, 남은 수량 23, 최신 seq)이 다시 수신된다
  - R9.3: (Given) 클라이언트가 `seq`=7까지 처리한 상태 (When) `seq`=5 이벤트가 늦게 도착하면 (Then) 해당 이벤트는 무시되고 카드 표시가 바뀌지 않는다
- 인수 조건:
  - 고정·해제·가격 변경 이벤트에 `effectiveAt`(서버 시각)과 단조 증가 `seq`가 포함된다
  - 클라이언트는 현재 재생 시점이 `effectiveAt`에 도달한 뒤에 카드를 갱신해 영상보다 먼저 가격이 바뀌어 보이지 않는다
  - `seq`가 역행하는(이전보다 작은) 이벤트는 무시한다
  - 시청자가 방송 중간에 입장하거나 WebSocket 재연결하면 현재 고정 상태 스냅샷(상품, 특가, 남은 수량, 최신 `seq`)을 다시 받는다
- 상태: 미착수

## R10. 주문 가능 여부·가격은 서버 상태로 판정
- 종류: api · 우선순위: must · 개정: 1
- EARS(ubiquitous): 시스템은 방송 중 주문의 가능 여부와 결제 금액을 항상 서버에 저장된 고정 상태로 판정해야 한다.
- 시나리오:
  - R10.1: (Given) 서버의 방송 특가가 9,900원인 상태 (When) 시청자가 가격 100원을 본문에 넣어 주문 API를 호출하면 (Then) 주문 금액은 9,900원으로 계산되거나 409가 반환되고 100원 주문은 생성되지 않는다
  - R10.2: (Given) 판매자가 상품 P1 고정을 해제한 직후 (When) 시청자가 P1 카드에서 주문 API를 호출하면 (Then) 409가 반환되고 주문은 생성되지 않는다
- 인수 조건:
  - 주문 요청 본문에 클라이언트가 보낸 가격이 담겨 있어도 서버는 저장된 방송 특가로 금액을 계산한다
  - 클라이언트가 보낸 가격이 서버 특가와 다르면 서버 특가를 적용하거나 409로 거절하되, 클라이언트 가격으로 주문이 생성되지 않는다
  - 고정이 해제된 상품으로 주문하면 409를 반환한다
- 상태: 미착수

## R11. 고정 상품 카드에서 장바구니를 거치지 않는 바로 주문
- 종류: api · 우선순위: must · 개정: 1
- EARS(event): 시청자가 고정 상품 카드에서 주문을 누르면 시스템은 장바구니를 거치지 않고 기존 주문·결제 흐름으로 주문을 생성해야 한다.
- 시나리오:

## R22. 숏폼 변환 상태 머신·3회 재시도·격리

- EARS(unwanted): 숏폼 변환이 실패한다면 시스템은 최대 3회까지 재시도한 뒤 해당 작업을 격리하고 상태를 `FAILED`와 이유로 기록해야 한다.

  - R22.1: (Given) 업로드가 끝난 45초 세로 영상 (When) 변환 워커가 정상 처리하면 (Then) 상태가 `UPLOADED → PROBING → TRANSCODING → READY`로 전이된다

## R26. 숏폼 피드 세로 스와이프·READY 필터·프리페치

- EARS(state): 숏폼 피드를 보고 있는 동안 시스템은 화면에 보이는 영상 1개만 재생하고 다음 영상 1~2개는 미리 불러와야 한다.

## R32. media/ 영역 분리와 commerce 호출 경계 및 ADR 문서

- 수량 선점 TTL 기본값은 5분이며 결제 `UNKNOWN`은 예외로 유지된다

- 숏폼 변환 워커는 로컬에서 동시 1건 처리 기준으로 60초 목표를 측정한다
- 피드 규칙 점수 가중치 초기값은 완료율 0.5, 최신성 0.3, 상품 선호 일치 0.2이다

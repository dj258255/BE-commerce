# 트러블슈팅 기록 — 무엇이 남았고, 무엇을 어떻게 닫았나

이 문서는 **"지금 무엇이 열려 있는가"** 와 **"닫은 것은 어떻게 닫았는가"** 를 한 곳에 모은다.
결정의 이유는 [ADR](adr/), 실측 원자료는 [`performance/`](performance/README.md)·
[`personalization/docs/runs/`](../personalization/docs/runs)에 있고, 이 파일은 **그 둘로 가는 색인**이다.

> **왜 따로 두는가.** ADR 68편은 결정 단위라 "지금 뭐가 남았는지" 가 안 보이고,
> 이슈는 닫히면 목록에서 사라진다. **읽는 사람이 현재 상태를 한 화면에서 복원**할 수 있어야 한다.

## 열린 것

| # | 무엇 | 왜 아직인가 | 막힌 지점 |
|---|---|---|---|
| 1 | **토스 공개 웹훅 수신** | 공개 URL 로 실제 재전송을 받아 본 적이 없다. **우리 응답 시간은 쟀다**([성능 §14.6](performance/README.md)) — 재전송은 그 결과로 일어날 수 있는 일이다 | **외부**: 공개 도메인 + 토스 콘솔 설정 |
| 2 | **PCI 책임분계** | 연동 방식(리다이렉트/iframe/직접)에 따라 SAQ 유형이 갈리는데 계약이 없다 | **외부**: 가맹점 계약·SAQ. 적으면 거짓이 된다([ADR-019](adr/ADR-019-pci-scope-by-not-touching-cards.md)) |
| 3 | **두 개 이상 실 PG failover** | 실계약 PG 가 하나뿐이라 가짜 둘 사이를 오가는 것은 증명이 아니다 | **외부**: 두 번째 PG 계약([ADR-020](adr/ADR-020-multi-pg-routing-off-by-default.md)) |
| 4 | **FDS 임계값의 숫자** | 차지백 라벨이 없다. 설계와 비용 파라미터만 정했다 | **데이터**: 지연 라벨([ADR-028](adr/ADR-028-fds-threshold-with-delayed-labels.md)) |
| 5 | **추천 품질의 온라인 판정** | 오프라인 지표는 게이트이고 최종 판정은 A/B 다. **실험 기반은 만들었다**(배정·노출·귀속·분석, 합성 사용자로 검증 — [ADR-061](adr/ADR-061-ab-assignment-and-attribution.md)). **다음에 돌릴 것**: 재구매 우선 혼합 대 지금([ADR-060](adr/ADR-060-genpage-serves-purchases.md)). `APP_RECOMMENDATION_MODEL_KIND=genpage` · `APP_EXPERIMENT_REC_HISTORY_ENABLED=true` 로 켜면 실험군은 추천 행과 홈 다음 쪽 모두 구매 이력을 넣는다(#270). 가상 사용자로 돌릴 때는 `tools/virtual_users/driver.py`(H&M 고객 페르소나가 화면에 보인 상품을 보고 고른다, #292). 분석은 `tools/ab_analysis.py`. 판정 기준(지표·기간·표본)은 켜기 전에 이슈에 적는다 — 합성 검증에서 변형당 500명의 구매 차이 구간이 ±2.8%p 였다 | **데이터**: 실사용자 |
| 7 | **캐시 압축을 켜는 것** | 임계값·코덱은 정했는데 **적용할 캐시가 없다**. 컨텍스트 캐시는 Lua 가 값을 읽어 병합해 압축하면 깨진다 | 구조 — [ADR-041](adr/ADR-041-cache-compression-threshold.md)·[ADR-035](adr/ADR-035-order-tolerant-context-merge.md) |
| 10 | **조회가 승인과 서킷을 같이 쓴다** | 조회 일시 장애 10% 에서도 서킷(창 5)이 열려 복구 배치의 한 틱이 통째로 막혔다. 재시도 없음은 예상 280초가 966초, 30% 에서는 20분 안에 끝나지 않았다([#334](34-결제-재시도와-retry-storm-실험.md#2026-09-26-일시-장애에서-재시도-횟수를-바꿔-봤다-334)). 조회 전용 서킷이나 창 확대는 승인 쪽 영향까지 재야 고를 수 있다 | 구조 — 서킷 분리는 승인 보호와 같이 설계해야 한다 |

**1~5 는 외부 계약이나 실사용자가 필요하다.** 지금 적으면 거짓이 되므로 열어 둔다.
7 · 10 은 구조를 먼저 바꿔야 한다. 9(홈 2쪽 앱 용량)는 닫았다 — 요청마다 돌던 count 쿼리였다([#284 리포트](../personalization/docs/runs/20260925-page2-capacity/report.md), 초당 30 → 120건). 6(셰딩 우선순위)·8(`poll.interval.ms` 비용)은 닫았다([ADR-058](adr/ADR-058-shed-browse-before-webhook.md) · [ADR-059](adr/ADR-059-cdc-poll-and-health.md)).

## 닫은 것 — 핵심 트러블슈팅

### 재 보고 **안 하기로** 한 것

가장 중요한 묶음이다. "고쳤다" 보다 **"재 보고 안 켰다"** 가 판단을 더 드러낸다.

| 무엇 | 넘어야 했던 선 | 실측 | 결정 |
|---|---|---|---|
| **추천 모델 교체** | `repeat_last` MAP@12 **0.0234** (측정 전에 못 박음) | ALS 4구성 최고 **0.0076** — 인기(0.0087)보다도 낮다. alpha·factors 두 축으로 얻은 폭이 **15% 미만**인데 선까지는 207% | **안 넣는다** ([ADR-048](adr/ADR-048-als-model-not-adopted.md)) |
| **GenPage 최소형으로 교체** | 같은 선 **0.023354** | 홀드아웃으로 세 번 골라 0.020937. **검증 기간을 따로 떼고 다시 골라 홀드아웃을 한 번 보니 0.020930** — 결론이 튜닝 방식에 기대지 않는다 | **서빙까지 붙이고 끈다** ([ADR-053](adr/ADR-053-genpage-mini-not-default.md) · [ADR-054](adr/ADR-054-genpage-validation-tuning.md)) |
| **넷플릭스 GenPage 를 옮긴 v2 로 교체** | 같은 선 **0.023354** · 측정 전에 순서 · 기한 · 홀드아웃 한 번 | 검증 주로만 골라(행 고정 · 후보 집합 · WBC · 2에폭) 홀드아웃을 한 번 보니 **0.019268** — 선의 83%, v1(0.020930)보다도 낮다. WBC 는 노출되지 않은 토큰의 로짓 때문에 무너졌다 | **서빙 경로만 남기고 끈다** ([ADR-068](adr/ADR-068-genpage-v2-not-default.md)) |
| **제약을 생성 중 차단** | 목록이 짧아지는 것을 막을 수 있는가 | 사후 필터가 **이미 100% 채우고** 있었다. 생성 중 차단은 서빙 중앙 62→**369ms**, coverage 100→**84%** | **기각** ([ADR-050](adr/ADR-050-post-filter-over-constrained-generation.md)) |
| **전문 검색 엔진 도입** | 지연: 300ms 초과의 원인이 집계인가 · 품질: 오타·어형 nDCG@10 이 MySQL 최선보다 0.10 높은가 | 지연은 **포화**였다(패싯 사전 집계로 닫힘). 품질은 LIKE 0.071 · FULLTEXT 0.324 · Lucene 0.808 | 지연으로는 안 넣었고, **품질로 앱 안 Lucene 을 넣었다**. ES·OpenSearch 는 품질이 같아 운영 비용으로 뺐다 ([ADR-044](adr/ADR-044-no-search-engine-yet.md) → [ADR-051](adr/ADR-051-search-engine-by-quality.md)) |
| **멀티 PG failover 켜기** | 가짜 PG 둘 사이의 전환이 failover 를 증명하는가 | 증명하지 못한다. **켤 조건 셋**을 대신 적었다 | **끈 채로 둔다** ([ADR-020](adr/ADR-020-multi-pg-routing-off-by-default.md)) |
| **정산 공정성 정책 켜기** | 대형이 소형을 밀어내는가 | 재현됐다(소형 **2일 지연** → 라운드로빈으로 0일). 대가는 대형 첫날 지급 **1000→500건** | **만들되 기본 off** — 지급일 약속이 바뀌는 **사업 결정** ([ADR-027](adr/ADR-027-settlement-fairness-policy.md)) |
| **캐시 압축 켜기** | 몇 바이트부터 이득인가 | 교차점 **187B(손해) / 279B(이득)**. 1KB 에서 **66% 감소** | **값은 정하고 안 켠다** — 적용할 캐시가 없다 ([ADR-041](adr/ADR-041-cache-compression-threshold.md)) |
| **모놀리스 분리 근거 하나** | 배치가 결제를 밀어내는가 | **미재현** — 커넥션 풀이 포화되지 않았다 | 그 근거를 **안 쓴다**. 재현된 둘만 근거로 ([ADR-029](adr/ADR-029-deployment-unit-vs-service-boundary.md)) |

### 예상이 틀렸던 것

| 무엇 | 예상 | 실제 |
|---|---|---|
| **CDC 가 아웃박스보다 느리다** | 기본값으로 재니 lag p95 **1,944ms vs 14ms** (139배) | 느린 것은 CDC 가 아니라 **명시하지 않은 기본값**이었다. 튜닝하니 **13ms** — 사실상 같다 |
| **PG 동시 호출 상한이 웹훅을 지킨다** | §14.6 에서 10초 초과 26.1% → 0% | 상한은 PG 를 부르는 워커만 묶는다. 조회가 초당 200건 더해지자 웹훅이 **DB 커넥션 줄**에 서서 15.6% 가 10초를 넘었다. 조회를 먼저 돌려보내 0% |
| **조회 셰딩 문턱 16 은 커넥션 4개를 남겨 웹훅을 지킨다** | 커넥션 20 중 4 를 결제·웹훅 몫으로 남기니까(ADR-058) | 남는 몫이 0 인 20 도 지켰고 풀을 넘는 28 부터 무너졌다(p95 4.1초, 32 에서 10초 초과 22%). 문턱은 몫이 아니라 **커넥션 줄의 길이**를 묶는다. 8·12·16·20 을 재서 12 로 바꿨다([#329](https://github.com/dj258255/BE-commerce/issues/329)) |
| **복구 백오프의 첫 간격을 줄이면 막힌 결제를 빨리 확정한다** | 더 자주 물으니까 | 10분 창에서 확정 지연은 15초 160초 · 1분 178초로 거의 같았다(시도 간격이 막힌 시간만큼 커진다). 조회는 1.4배, 막힌 건이 청크 자리를 가져가 풀리는 건 해소는 1.56배로 늘었다. 지연을 줄이는 것은 상한이다([#330](performance/recovery-backoff.md)) |
| **조회 재시도는 장애 중 PG 호출을 부풀린다** | 실패 한 번에 세 번 부르니까 | 호출마다 따로 실패하면 성공할 때까지의 조회는 재시도와 무관하게 1/(1−실패율)이다. 1·5·10% 에서 건당 조회가 시도 1·2·3회 사이 1.7% 안에서 같았고, 3회는 확정만 앞당겼다. 확정을 늦춘 것은 재시도가 아니라 **서킷**이었다([#334](34-결제-재시도와-retry-storm-실험.md#2026-09-26-일시-장애에서-재시도-횟수를-바꿔-봤다-334)) |
| **리플리카가 둘이고 graceful shutdown 이면 롤링은 무중단이다** | 연결을 못 맺은 요청은 nginx 가 다른 리플리카로 넘기니까(ADR-029 는 병존만 확인했다) | 차례로 재시작만 하자 30건 · 281건이 끊겼다. 먼저 재시작한 쪽이 nginx 의 실패 표시(10초)에 묶여 있는 동안 두 번째를 멈춰 살아 있는 upstream 이 없었다. LB 에서 빼고 재시작한 뒤 넣으면 두 번 다 0 건([#338](performance/rolling-deploy.md)) |
| **한국어 형태소 분석기를 붙이면 한국어 검색이 된다** | 이커머스 한국어 검색의 기본 처방이니까 | 카탈로그 텍스트에 한글이 있는 상품이 **3개**다. 분석기가 쪼갠 한국어가 맞을 곳이 없다. 필요한 것은 분석기가 아니라 사전이었고, 앱의 부서명 라벨로는 0건이 10% 남았다 |
| **가격 변경은 검색 순서와 무관하다** | 점수는 검색어로 정해지니까 | 동점 순서가 문서 번호라, 결과 상품의 가격이 바뀌는 동안 쪽을 넘기면 **30%** 가 안 나왔다. 동점을 id 로 끊어도 9건이 남았다 — 갈아 끼운 문서의 옛 판이 통계에 남아 점수 자체가 움직인다. 무작위 변경으로만 쟀다면 0 이 나와 못 봤다 |

| **후보 자르기는 검색 결과를 눈에 띄게 틀린다** | 상위 500개 안에서만 거르니까 | 첫 페이지는 **153/171 이 같았다**. 틀리는 곳은 "총 N건"과 패싯 개수다(결과 수 95.5% 손실). 눈에 덜 띄는 방식으로 틀린다 |
| **ES 로 옮기면 300만 건 지연이 풀린다** | 검색 전용 엔진이니까 | 단일 노드 ES 도 **148ms** 로 예산(100ms)을 넘었다. 앱 안 Lucene 은 232ms. 푸는 것은 엔진이 아니라 샤드 분할이다 |
| **지각 정산은 트래픽 문제** | 실 트래픽이 없어 못 센다고 미뤄 뒀다 | 재려고 코드를 읽다 **배치 천장(하루 500건)** 을 찾았다. 지각은 트래픽이 아니라 **배치 건강도의 함수** |
| **생성 중 차단이 목록을 지킨다** | 건너뛰고 다음으로 메우니까 | 합성 풀(24개)에서는 **오히려 더 짧아졌다**(최솟값 11→9). 메울 후보가 남아 있을 때만 성립한다 |

| **오타를 허용하면 검색이 나아진다** | 틀려도 찾으니까 | `blazer` 가 드문 이웃 `lazer`·`razer` 에 밀려 **0점**. 드문 말은 IDF 가 높다. 정확 일치 절을 3배로 먼저 세워 A 0.72→0.77 |
| **ES 와 OpenSearch 는 같은 결과를 낸다** | 같은 Lucene · 같은 BM25 · 같은 질의 | 평균 품질은 같았지만(0.814 · 0.798) 상위 10개 겹침 **0.753**. 원인은 나중에 확인했다(#262): 점수는 같았고 **동점을 엔진 안의 문서 순서대로** 둔 것이 전부였다. 그 순서는 적재 중 refresh 가 만든다 |
| **학습 입력과 서빙 입력이 같다** | 같은 모델이니까 | GenPage 는 **구매 시퀀스로 학습**했는데 서빙은 **조회·클릭**을 넣고 있었다. ADR-053 을 머지할 때 몰랐고, 재튜닝에서 재구매 혼합을 서빙할 수 있는지 보다가 알았다 |
| **모델을 넣으면 나아진다** | 스텁보다는 낫겠지 | 기준선의 **3분의 1**. 이미 산 상품을 빼면 **46% 더 떨어진다** — 재구매를 흉내내면서 더 나쁘게 흉내낸다 |

### 조용히 틀려 있던 것 — 실험하다 찾은 버그

실험의 부산물이다. **찾으려고 찾은 게 아니라 재려다 보인 것**이라 따로 적는다.

| 무엇 | 어떻게 조용했나 |
|---|---|
| **워커 지표가 Prometheus 에 안 나가고 있었다** | Spring Boot 가 Tomcat MBean 레지스트리를 기본으로 끈다. **커넥션은 보이고 워커는 안 보이는 상태**였는데, 느린 PG 앞에서 마르는 자원이 바로 그 워커다 |
| **DB enum 에 없는 값을 코드가 쓰고 있었다** | `AccountType.CASH`·`PG_FEE`, `PAYOUT_HELD`. **H2 테스트는 통과하고 MySQL 에서만 실패**한다. 아직 실행된 적 없던 경로라 조용했다(V50·V52) |
| **세션 신호가 아동복에서만 버려지고 있었다** | 홈 다음 쪽이 인기 표(200행)에서만 대분류 행을 만들었는데 아동복이 **0개**였다. 아동복을 봐도 행이 안 서고 오류도 없었다. 페이지네이션 실측의 세션 반영이 60% 로 나와 대상별로 나눠 보고 알았다 |
| **CDC 컨슈머 빈이 아예 없었다** | 게이트가 `KAFKA` 만 열려 있었다. 커넥터는 `RUNNING` 이고 토픽에 쌓이는데 **읽는 쪽이 없어 반영률 0%** — 오류 로그 0건 |
| **재배달이 심사 큐를 두 줄로 만들고 있었다** | 같은 주문이 두 번 쌓였다. DLT 재처리를 멱등으로 만들다 발견 |
| **제약 확인이 요청마다 후보 풀 전체를 읽고 있었다** | 합성 풀(24개)에서는 안 보였고 **실제 카탈로그(10만)에서 405ms → 7ms** 로 드러났다 |
| **부하가 승인 경로를 안 타고 있었다** | 주문만 만들고 `/payments/confirm` 을 안 불렀다. PG 지연 5초인데 **결제 p95 가 13ms** 로 나와서 알았다 — "영향이 없다" 가 아니라 "PG 를 안 불렀다" 였다 |
| **리포트가 k6 Rate 를 못 읽고 있었다** | 이 버전은 `value` 키인데 `rate` 로 읽어 **10초 초과가 전부 0%** 로 보였다. **p95 가 13초인데 초과 0%** 라는 모순으로 알아챘다 |
| **Lucene 인스턴스가 기동마다 토픽 전체를 다시 읽었다** | 적재 시각으로 찾기가 뒤에 레코드가 없으면 위치를 못 정하고 전역 `earliest` 로 떨어졌다. 결과는 맞게 나와서(DB 를 다시 읽으니) **반영 수가 변경 수의 두 배**인 것으로 알았다. 머지 전 |
| **ES 색인기가 비 ASCII 상품을 못 넣었다** | bulk 본문의 문자셋이 없어 기본 문자셋으로 인코딩됐다. 거절된 문서가 배치를 던져 **같은 배치의 다른 변경까지 늦췄다**. 반영 지연 실측에서 20건을 놓쳐 알았다. 머지 전 |
| **미확정 복구가 확정 못 한 건에 막힐 수 있었다** | PG 가 "진행 중"이라 답한 건이 매 주기 앞자리를 다시 차지했다. 청크만큼 쌓이자 뒤의 500건을 **5분 동안 0건** 풀었고, 막힌 건 절반은 한 번도 다시 묻지 않았다. 정렬을 명시해도 같았다(인덱스로 이미 오래된 순이었다). 운영에서 일어난 적은 없고, §14.5 가 "다음 주기로 미뤄진다"고만 적은 곳을 재다 알았다 |
| **GenPage 모델이 모든 사용자를 이력 없는 사용자로 생성하고 있었다** | 앱이 본문을 chunked 로 보냈고 파이썬 모델 서버는 `Content-Length` 만 읽었다. 서빙 채점에서 모델 단독이 오프라인의 **2%**(0.0005)로 나오고 사용자마다 추천이 같아 알았다. 목 테스트는 본문 객체만 봐서 못 잡았다 |
| **CDC 커넥터가 RUNNING 인 채 흐르지 않을 수 있다(재현)** | E1b 에서 한 번 겪고 감시가 없었다. DB 연결을 5분 막자 Connect REST 는 내내 `RUNNING`, 로그에는 재연결 시도만 남았다. 하트비트 나이로 잡게 했다(39초에 60초 초과) |
| **ADR 이 정한 기본값이 설정에 없었다** | ADR-037 은 추천 과부하 기본 정책을 `ADMISSION` 으로 정했는데 설정·코드의 기본값은 처음부터 `BOUNDED` 였다. 그 ADR 의 가정(모델 용량을 안다)을 재려다 알았다. 스텁과 게이트가 같은 설정을 읽어 그 가정도 시험된 적이 없었다 |
| **MAP@12 가 15배 부풀려져 있었다** | 미적중 고객을 평균에서 빼고 있었다. `reindex(fill_value=)` 가 **기존 NaN 은 못 채운다**는 것이 원인 |

### 같은 축을 두 번 재서 뒤집은 것

| 무엇 | 1차 | 2차 |
|---|---|---|
| **유입 제어 용량** | 닫힌 루프로 재서 과소평가 | 열린 루프로 다시 재서 뒤집음 |
| **E1 기본 전달 방식** | `IN_PROCESS` 가 낫다 | 일치율을 재니 **항목을 잃는다** — 기본값을 되돌림 |
| **되채우기·인기 신호** | 퍼뜨리던 신호 | 진짜 인기로 바꾸니 화면이 **−18.4%** 짧아졌고, 되채우기가 **+12.6%** 를 되산다 |

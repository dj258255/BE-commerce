# 40. 용량 모델: 수요 가정으로 공급 실측을 읽는다

## 수요를 먼저 가정하는 이유

공급 측 실측은 이미 쌓여 있다. 모델 서버 용량, 앱 홈 경로 처리량, DB 읽기·쓰기 무릎, PG 브라운아웃에서 마르는 자원까지 이 저장소 문서에 숫자로 남아 있다. 수요 측 모델은 없었다. 목표 수요가 없으면 공급 실측이 몇 배 모자란지, 증설이 언제 필요한지 말할 수 없다. 그래서 새로 재기 전에 수요를 가정으로 세우고 기존 실측과 대조한다.

이 문서에서 수요 수치는 가정이고 공급 수치는 실측이다. 어느 쪽인지 표마다 열로 밝힌다. 실측이 없는 자원은 미측정으로 적고 가정으로 채우지 않는다.

요청 하나가 잡는 자원을 끌어온다. 모델 호출·재고 조회·PG 승인은 실측이다. DB 요청당 조회 수는 가정이다.

## 대조: 자원별 수요 대 공급

각 자원의 수요를 공급으로 나눈 값이다. 1을 넘으면 모자란다. 모델 서버 수요는 홈 요청(1쪽+2쪽, peak 의 15%)이고 앱 홈 2쪽 경로 수요는 홈 2쪽(peak 의 5%)이다.

| 자원 | 공급 구분 | 공급 | 10만 | 30만 | 100만 |
|---|---|---:|---:|---:|---:|
| 모델 서버 1대(/page hybrid, 동시성 4) | 실측 | 9.34/s | 1.34 | 4.01 | 13.38 |
| 앱 홈 2쪽 경로(HYBRID, 동시성 1) | 실측 | 10.2/s | 0.41 | 1.23 | 4.08 |
| DB 읽기 | 실측 | 1,800/s | 0.04 | 0.13 | 0.45 |
| DB 쓰기(결제 경로) | 실측 | 약 120/s | 0.02 | 0.06 | 0.21 |
| PG 처리율 | 미측정 | 분포 없음 | 환산 불가 | 환산 불가 | 환산 불가 |

첫 병목은 모델 서버다. MAU 10만에서 이미 1.34배 모자라고 MAU 100만에서 13.38배가 된다. 모델 서버 1대의 종단 처리량 9.34/s 는 홈 요청 전체 기준 MAU 약 7.5만에서, 홈 2쪽만 기준 MAU 약 22.4만에서 수요가 넘어선다. 앱 홈 2쪽 경로(HYBRID, 10.2/s)는 홈 2쪽 수요 기준 MAU 약 24.5만에서 넘어선다. DB 읽기와 쓰기는 세 단계 모두 여유가 있다. PG 는 실 응답시간 분포가 없어 처리율을 환산하지 못하므로 대조에서 뺀다.

## 기존 데이터로 모델 검증

모델이 기존 실측을 다시 계산해 맞히는지 본다. 맞으면 앞의 대조를 믿을 근거가 하나 늘고 틀리면 모델을 고친다.

### 잠금 직렬 상한

모델 서버는 추론에 잠금 하나를 쓴다. 그래서 처리량 상한은 평균 추론 시간의 역수다.

- 예측식: X = 1/S
- 예측값: S1 hybrid 평균 추론 107ms, 1 ÷ 0.107 = 9.35/s
- 실측값: 9.03/s(동시성 1) · 9.34/s(동시성 4)
- 오차: 동시성 1에서 +3.45%, 동시성 4에서 +0.09%

동시성이 올라도 처리량이 늘지 않는 관측(9.03 → 9.34)이 잠금 직렬과 맞는다. 대기는 왕복 지연으로만 늘어난다.

### Little's Law 왕복시간

닫힌 루프에서 동시성 N, 처리량 X 면 평균 왕복은 W = N/X 다.

- 예측식: W = N/X
- 예측값: 4 ÷ 9.34 = 428.37ms
- 실측값: 왕복 p50 420.75ms (동시성 4)
- 오차: +1.81%

### X6 자리 점유율

v2 모델 서버는 `/recommend`(1쪽 추천 행)와 `/page`(2쪽)가 잠금 하나를 나눠 쓴다. 자리를 공유하지 않을 때 2쪽 부하가 용량에 닿으면 모델 서버가 통째로 무너진다.

- 예측식: 점유율 = 추천 부하/C + 2쪽 부하/Cp. C 22.9/s, Cp 16.5/s 이고 점유율이 1을 넘으면 무너진다
- 예측값: 0.5Cp 에서 6/22.9 + 8/16.5 = 0.75(생존), 1.0Cp 에서 1.23(붕괴), 1.5Cp 에서 1.78(붕괴). 식을 뒤집으면 무너지는 2쪽 부하는 (1 − 6/22.9) × 16.5 = 12.18/s 다
- 실측값: 8/s 생존(추천 행 개인화 100%), 16/s 붕괴(개인화 0%, 모델 실패 181건), 25/s 붕괴
- 오차: 예측 경계 12.18/s 가 실측 경계 8~16/s 안에 있다

BACKEND.md X6 은 첫 점유율을 0.76 으로 적었는데 같은 식으로 다시 계산하면 0.75 다. 반올림 차이다.

## 한계와 다음 단계

- 수요는 전부 가정이다. MAU·DAU/MAU·세션·페이지·API 배수·peak 배수를 바꾸면 표가 통째로 바뀐다. 그래서 재계산 절차(`tools/capacity_model.py --check`)를 함께 남긴다
- DB 읽기 QPS 는 요청당 1조회 가정에 좌우된다. 이 가정이 읽기 수요(peak 의 97%)의 대부분을 정한다. 요청당 조회가 2회면 읽기 QPS 가 두 배가 되어 MAU 100만에서 무릎(1,800/s)의 90% 가 된다
- 공급 수치는 맥 한 대에서 k6·앱·모델 서버가 CPU 를 나눠 쓴 값이다. 배포 하드웨어가 다르면 다시 재야 한다
- 모델 서버 수치는 한 프로세스·잠금 하나 구조다. 수평 확장은 다음 단계(C2 USL 실험)에서 잰다
- PG 는 실 응답시간 분포가 없어 공급 처리율을 대조에 넣지 못했다. 분포가 생기면(외부 계약 또는 실측) 처리율을 환산해 같은 방식으로 대조한다
- 비용 환산은 C3 에서 다룬다

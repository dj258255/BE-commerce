# 결제 오케스트레이션은 장애를 줄이는가, 복잡성을 옮기는가

## 문제

두 개 이상의 PG를 연결하면 한 PG 장애 때 다른 PG로 우회할 수 있다. 하지만 이것만으로 복원력이
생기는 것은 아니다. 결제 상태·토큰·환불 가능 PG·수수료·승인율·정산 파일·고객지원 기준까지
provider별로 달라진다.

Adyen은 orchestration이 provider 장애 의존도를 줄일 수 있지만, 데이터가 분산되고 운영 복잡성이
늘며 장애를 없애는 것이 아니라 위험의 위치를 옮길 수 있다고 설명한다.

참고: [Adyen - Payment Orchestration](https://www.adyen.com/knowledge-hub/payment-orchestration)

## 선택지

| 선택지 | 얻는 것 | 포기하는 것 | 현재 판단 |
|---|---|---|---|
| 단일 PG | 계약·정산·환불 흐름 단순성 | 단일 사업자 장애 영향 | 현재 규모의 기본값 |
| 두 PG active-passive | 장애 우회 가능성 | failover 후 상태 조회·환불 라우팅 복잡성 | 실제 계약 전에는 문서만 |
| 두 PG active-active | 승인율·비용 최적화 가능성 | 라우팅·정산·토큰·관측 복잡성 | 규모 근거 없이는 과잉 |
| 외부 orchestrator | 연결 구현 시간 단축 | 데이터·계약·장애 책임의 추가 경계 | 채택하지 않음 |

## failover에서 먼저 확정해야 하는 것

- UNKNOWN 승인 결과를 다른 PG로 재승인하지 않는다.
- 결제 시 사용한 provider를 payment에 영구 보존한다.
- 환불·취소는 원 승인 provider 또는 계약상 허용된 경로로만 보낸다.
- provider별 transaction reference와 정산 파일을 같은 내부 payment에 연결한다.
- provider 전환 전후 승인율만 보지 않고 중복 승인·환불 실패·대사 지연을 함께 본다.

현재 pay는 provider 라우팅 추상화와 provider 보존 경계를 갖지만, 두 실 PG의 계약 테스트·실패 전환
실험은 계정과 트래픽 없이는 완료라고 부를 수 없다.

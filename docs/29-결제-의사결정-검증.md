# 결제 핵심 의사결정 검증 계획

> 목적: 결제 기능의 개수를 늘리는 대신, 기반 지식·트레이드오프·예측 가능한 운영 커뮤니케이션을 한 흐름으로 증명한다.

## 현재 결론

이 프로젝트의 결제 핵심은 일반적인 결제 성공 경로가 아니다.

```text
PG 승인 요청
  → 결과가 UNKNOWN일 수 있음
  → 조회·웹훅·복구 배치로 확정
  → 내부 처리 실패 시 독립 보상 취소
  → 원장 기록
  → PG 기록과 대사
```

이 흐름을 첫 번째 포트폴리오 사례로 삼고, 느린 PG에서 서비스 전체를 보호하는 자원 격리를 두 번째 사례로 삼는다. 카드·포인트·월렛·구독·가상계좌는 기능 목록이 아니라 위 두 문제를 설명하는 보조 증거로 사용한다.

## 의사결정 1. PG 타임아웃은 실패가 아니라 UNKNOWN이다

### 문제

승인 요청의 네트워크 타임아웃은 요청이 PG에 도달하지 않았다는 뜻이 아니다. PG에서 승인되었지만 응답만 유실되었을 수 있다. 이를 실패로 처리하면 고객은 결제했지만 주문은 실패하는 상태가 된다.

### 선택지

| 선택지 | 얻는 것 | 포기하는 것 |
| --- | --- | --- |
| 타임아웃을 즉시 실패 처리 | 단순한 상태머신, 빠른 사용자 응답 | 이중 결제·결제 후 주문 없음 위험 |
| 승인 요청을 무조건 재시도 | 일시 네트워크 오류 회복 | PG에 도달한 요청이면 이중 승인 위험 |
| UNKNOWN 보존 후 조회 | 정합성 우선, 재시도 경계 명확 | 복구 배치·운영 화면·고객 안내 비용 |
| UNKNOWN 후 즉시 취소 | 유령 승인 정리 시도 | PG에 아직 생성되지 않은 거래는 취소 실패 가능 |

### 결정

승인 결과를 `SUCCESS / FAILED / TIMEOUT`으로 분류하고, `TIMEOUT`은 내부 상태 `UNKNOWN`으로 보존한다. UNKNOWN은 같은 승인 요청을 다시 보내지 않고 다음 순서로 확정한다.

1. PG 결제 조회
2. 웹훅 수신 후 조회 API로 상태 재검증
3. 조회 불가 시 복구 배치
4. 내부 처리 실패가 확인되면 독립 보상 취소
5. 계속 미확정이면 운영자·대사 큐에 남김

### 검증 지표

- UNKNOWN 발생 건수와 비율
- UNKNOWN → 최종 상태 전환 시간 p50/p95
- 복구 배치 처리 성공률
- 보상 취소 재시도 횟수와 최종 실패 건수
- 중복 승인 건수: 목표 `0`
- 결제 완료 후 주문·원장 미생성 건수: 목표 `0`

운영 계측:

- `payment.confirm{outcome}`: 승인 결과별 건수
- `payment.pg.approval.latency`: PG 승인 호출 시간의 p50/p95/p99
- `payment.pg.approval.rejected{reason=concurrency_limit}`: PG 도달 전 상한 거절 수
- `payment.pg.approval.unknown`: PG 승인 결과를 알 수 없어 UNKNOWN으로 보존한 수
- `payment.unknown.oldest.age`: 가장 오래된 UNKNOWN의 경과 시간

현재 구현 근거: `PaymentService`, `PaymentRecoveryService`, `PaymentStatusTest`, `PaymentCancelSagaTest`, `payment/chaos` 테스트와 Toxiproxy 실행 기록.

## 의사결정 2. 웹훅은 알림이지 진실의 원천이 아니다

토스 일반 결제 웹훅에는 서명 헤더가 없고, `PAYMENT_STATUS_CHANGED`와 `DEPOSIT_CALLBACK`의 payload만으로 상태를 확정해서는 안 된다. 토스 문서는 웹훅 수신 후 결제 조회 API를 사용하도록 안내한다. 또한 200 응답을 10초 이내에 보내지 않으면 최대 7회 재전송된다.

- [토스 웹훅 연결 가이드](https://docs.tosspayments.com/guides/v2/webhook)
- [토스 웹훅 이벤트 문서](https://docs.tosspayments.com/reference/using-api/webhook-events)
- [토스 결제 흐름과 금액 검증](https://docs.tosspayments.com/guides/v2/get-started/payment-flow)

### 결정

- 토스 웹훅과 자체 Mock PG 서명 웹훅 엔드포인트를 분리한다.
- 토스 이벤트는 먼저 저장하고, 상태 반영은 비동기로 처리한다.
- 동일 이벤트는 외부 이벤트 식별자로 멱등 처리한다.
- 순서가 뒤집혀도 payload가 아니라 조회 API 결과로 상태 전이를 판단한다.
- 파싱·도메인 처리 실패가 토스 재전송 폭주로 이어지지 않도록 수신 응답과 내부 처리를 분리한다.

현재 구현 근거: `TossWebhookController`, `WebhookController`, `WebhookService`, `TossWebhookNormalizer`, `TossWebhookArrivesFirstIntegrationTest`, `WebhookArrivesFirstIntegrationTest`.

## 의사결정 3. 느린 PG 앞에서는 결제를 모두 살리지 않고 나머지 서비스를 보호한다

### 문제

PG 응답이 느려지면 DB 커넥션을 사용하지 않는 사가 구조에서도 톰캣 워커가 고갈될 수 있다. 따라서 “DB 커넥션이 안전하다”와 “서비스가 안전하다”는 같은 말이 아니다.

### 선택지

| 선택지 | 얻는 것 | 포기하는 것 |
| --- | --- | --- |
| 동시 호출 무제한 | 결제 요청을 최대한 수용 | 일반 조회까지 연쇄 지연 |
| PG 호출 세마포어 | 일반 API의 자원 격리 | 상한 초과 결제의 즉시 거절 |
| read timeout 단축 | 워커 회수, 빠른 사용자 응답 | 끊긴 승인 요청이 UNKNOWN 부채가 됨 |
| 느린 호출을 서킷 실패로 집계 | 브라운아웃 차단 | 아직 성공 가능한 결제의 오탐 거절 |
| 비동기 결제 전환 | 워커 점유 감소 | 즉시 완료 UX와 상태 규약 변경 |

### 결정

PG에 도달하기 전 세마포어를 획득하지 못한 요청은 실패로 확정하고, 이미 PG에 도달한 요청의 타임아웃은 UNKNOWN으로 보존한다. 기본 상한은 현재 가정한 피크와 워커 예산으로 정하며, 실 PG 응답시간 분포가 확보되면 다시 계산한다.

### 검증 지표

- PG 지연별 결제 p95/p99
- 톰캣 busy worker 평균·최대
- 일반 조회 API p95
- 세마포어 거절률
- timeout으로 생성된 UNKNOWN 수
- 결제와 무관한 API의 오류율

현재 실험은 로컬 Apple Silicon·MySQL 8.4·Redis 7.4·가짜 PG 지연 주입 조건이다. 실 PG 운영 수치로 표현하지 않는다. 상세 결과는 [ADR-022](adr/ADR-022-pg-brownout-resource-limits.md)와 [성능 리포트](performance/README.md)에 둔다.

## 의사결정 4. 복합결제 환불은 정책을 먼저 정하고 불변식으로 제한한다

카드·포인트·월렛 복합결제에서 환불 순서는 기술적 정답이 아니다. 현금화 어뷰징, 고객 경험, 각 결제수단의 복원 가능성이 충돌한다.

현재 정책은 `포인트 → 월렛 → 카드` 순서다. 무상 포인트를 카드보다 나중에 환불하면 포인트가 현금으로 바뀌는 경로가 생길 수 있기 때문이다.

검증해야 할 불변식:

```text
취소 금액 = 포인트 복원액 + 월렛 복원액 + 카드 환불액
누적 취소 금액 <= 승인 금액
원장 차변 합계 = 대변 합계
```

현재 구현 근거: `RefundAllocatorTest`, `PartialCancelIdentityTest`, 원장 복식부기 검증, 취소 별도 대사 행.

## 의사결정 5. PCI 범위를 줄였다고 PCI 책임이 사라지는 것은 아니다

카드번호·유효기간·CVC를 서버가 직접 받지 않는 결정은 유지한다. 다만 “PCI DSS 범위 밖”이라는 표현은 “카드 데이터 환경의 범위를 줄였다”로 수정한다.

PCI SSC는 외부 결제업체에 처리를 위탁하면 많은 요구사항이 직접 적용되지 않을 수 있지만, 가맹점의 관리 책임과 공급자 책임 확인 의무가 사라지는 것은 아니라고 설명한다. 토큰화 역시 구성과 키 관리 방식에 따라 PCI 범위를 자동으로 없애지 않는다.

- [PCI SSC 외부 위탁 FAQ](https://www.pcisecuritystandards.org/faqs/does-pci-dss-apply-to-merchants-who-outsource-all-payment-processing-operations-and-never-store-process-or-transmit-cardholder-data/)
- [PCI SSC 결제 토큰 FAQ](https://www.pcisecuritystandards.org/faqs/1326/)

## 포트폴리오에 넣을 최종 사례 2개

### 사례 A. 돈은 움직였지만 결과를 모르는 결제

문제 → 타임아웃을 실패로 처리하면 결제 후 주문 없음이 발생한다.

가설 → 승인 API의 응답 유실을 실패와 분리하고, 조회·웹훅·복구 배치로 확정하면 중복 승인 없이 정합성을 회복할 수 있다.

선택지 → 즉시 실패, 무조건 재시도, UNKNOWN 보존.

결정 → UNKNOWN 보존. 승인 재시도는 금지하고 조회와 보상 취소를 사용한다.

검증 → 네트워크 장애 주입, 프로세스 중단, 웹훅 중복·순서 역전, 최종 상태·원장·주문 불변식 확인.

### 사례 B. 느린 PG가 일반 API까지 끌어내리는 문제

문제 → 사가로 DB 커넥션은 풀었지만 PG 지연이 톰캣 워커를 고갈시킬 수 있다.

가설 → PG 동시 호출 상한이 결제 처리량을 줄이는 대신 일반 API의 지연 전파를 막을 수 있다.

선택지 → 무제한, 세마포어, timeout 단축, 비동기 전환.

결정 → 호출 전 세마포어. PG에 닿지 않은 요청만 즉시 실패로 확정한다.

검증 → PG 지연·도착률을 바꾸며 결제 p95, 조회 p95, 워커 점유, 거절률, UNKNOWN 수를 비교한다.

## 작업 가시성 기준

| 알고 싶은 것 | 남길 곳 |
| --- | --- |
| 현재 무엇을 하는가 | `ROADMAP-TRADEOFFS.md`의 상태와 다음 검증 |
| 왜 하는가 | ADR의 문제·선택지·판단 기준 |
| 언제 끝나는가 | 검증 항목별 예상 결과물과 불확실성 |
| 무엇을 확인했는가 | 성능 리포트·테스트·장애 재현 기록 |
| 무엇이 실제로 바뀌었는가 | `CHANGELOG.md`와 커밋/PR |
| 무엇이 아직 모르는가 | 이 문서의 “미검증” 항목 |

### 미검증으로 남겨야 하는 것

- 실 PG의 승인시간 p99와 실제 장애 분포
- 두 개 이상의 실계약 PG 간 승인율·수수료·failover 안전성
- 실제 계약 환경의 PCI SAQ와 책임분계
- 3DS2 인증 화면과 FDS challenge 전환

모르는 값을 추정해 결과처럼 쓰지 않는다. 실 PG 계약이나 운영 환경이 생겼을 때 검증 조건을 갱신한다.
